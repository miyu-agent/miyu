### 是什么

一个量性能的小程序 `miyu-perf`：照 `23-性能预算.md` 第一节的量法量核心这一边，原始数据和对照预算的表写进 `target/perf-out/`。它是工具 crate，不属于任何一层，谁都不许依赖它（`01-架构.md` 第九节规则 5）。

### 对外的样子

`cargo xtask perf [--no-order] [参数]`，参数原样交给量尺，可以不写。Linux x86_64 上先走排函数的流程（下面「排函数」），量的是排过的程序；`--no-order` 照原来的办法编、不排，这个词不交给量尺：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--runs` | 10 | 冷启动量几次 |
| `--sessions` | 10 | 小会话几个 |
| `--events` | 10000 | 大会话说到第几条事件 |
| `--tail` | 30 | 到了以后再说几轮 |
| `--reloads` | 20 | 重启核心再打开大会话几次：原来 5 次，p95 就是最慢的那一次，一个冷启动的异常值就让闸门红；20 次的 p95 才是真的 p95（施工 V-13，2026-10-20 项目主人定先把量法做稳，预算不动） |
| `--appends` | 2000 | 追加几条 |
| `--reply-bytes` | 3500 | 假模型每次回多少字节的正文 |
| `--streams` | 10 | 流式一轮（施工 V-22）：大会话上说几轮 |
| `--pieces` | 300 | 流式一轮：回答切成几块 |
| `--idle-wait` | 200 | 不订阅大会话以后等几秒再量内存 |
| `--out` | `target/perf-out` | 结果写到哪 |
| `--render` | 不写 | 不量：照这一份原始数据（`.json`）、照 23 现在的预算重出同名的 `.md`，原始数据不动。只编量尺，不编 `miyu` |
| `--gate` | 不写 | 闸门的倍数（施工 V-3）：量完、表写好以后，有预算的哪一行时间超过预算的这么多倍、内存超过预算，报出来、退出码 1。不写的只出表 |
| `--tools` | 不写 | 工具一步（施工 V-29）：写了的只量这一场，每种调用量这么多次（另加头一次不计），别的几场不量 |
| `--tree` | `cargo xtask perf` 填源码树的 `crates/` | 工具一步拷进工作区的树（不拷 `target/`），`grep`、`glob` 在它里面找 |
| `--tools-log` | 不写 | 工具一步：核心的 `MIYU_LOG`；拆得更细写 `debug`（记日志本身也花一点，主数照不写的那一次） |
| `--tag` | 不写 | 工具一步：结果的文件名后面接 `-<标签>` |
| `--order` | 不写 | 排函数（施工 LW-1）：写了的不量，照剧本录清单，写进这个文件；要和 `--emulator`、`--tree` 一起写，不读 `--design`、不写 `--out` |
| `--emulator` | 不写 | 排函数：核心放进哪个模拟器里运行（`qemu-x86_64`） |
| `--head` | 不写 | 排函数（施工 LW-6）：真的终端界面程序，写了的再录第三段（下面「排函数」第 5 条第 7 款）；只在 `--order` 的跑法里认 |
| `--head-order` | 不写 | 排函数：终端界面的清单写进这个文件，写了的再录第四段；要和 `--head` 一起写 |

结果：`target/perf-out/<日期>-<系统>-<架构>.json`（原始数据）和同名的 `.md`（条件、表）。日期是 UTC。同一天再量一次，盖掉同名的。

预算改了（23 F1：实测后校准），用 `cargo xtask perf --render target/perf-out/<那一份>.json` 重出表。

### 怎么走

1. 沙盒在 `target/perf/` 下，每次量之前删掉重建。不放系统的临时目录：那里常是内存盘，同步不算数。
2. 核心的环境照集成测试拉核心的那一套：不拉 models.dev 的目录，缓存目录放进数据根，不用 `$XDG_RUNTIME_DIR`，不走代理。核心空闲一小时才走，量的时候不会自己退出。
3. 系统配置里一家 `perf`（`openai-chat`），地址是假模型服务，模型 `perf/perf-model` 不在目录里，窗口照配置写成 200000（施工 V-2 上）：压缩线 170000，大会话照真用时那样到线就压，量的是压过的会话。V-1 没写窗口，会话一直不压，大会话的投影是把一万条事件整份组装，真用时到不了。
4. 假模型服务和量尺在同一个进程里，时刻可以直接比。每个 `POST` 回同一段字（正文一块、收尾一块带用量、`[DONE]`），别的请求回空的模型列表。用量照请求体、正文的字节数估，四个字节一个 token；带出厂摘要指令那一句的（摘要请求）回一段几百字节的摘要（施工 V-2 上）。它记下请求头读全的时刻：驱动编好整份请求体才发头，所以这个时刻包含组装和编码，不含请求体在回环上传多久。
5. 会话都关着记忆造（`memory: off`，2026-10-17 项目主人定）：这一组量核心自己。以前量尺的会话无人格、本来不接记忆；P-12 起无人格也有记忆，接上以后重启打开大会话 p95 114 ms、追加 p99 78 ms（本机，预算 50、20），这才看出开着记忆的会话一直超预算。开记忆的另量一组，用同样的预算卡（施工 V-9）：大会话再造一个开着记忆的（无人格，`memory: persona`），重启打开、投影、从头投影三行照同样的预算比，原始数据记在 `large_memory`。V-9 把回合索引挪到后台写（`miyu-session/src/memory/lane.rs`）：开回合库要跑一遍 `quick_check`，跟着人格的那一间越用越大，原来整笔压在打开会话上。V-37 下：后台接上时一块块读日志、边读边铺，底子、自己的整份事件不再同时在内存里（`memory.md` 第一条第 6 款）。V-39 下：`session.fork` 里紧接着载入的支线，载入、回合索引都照分叉那一遍读好的底子走，父会话一共只解析一遍（原来三遍）。
6. 每一句话带一个只此一句的记号，量尺照记号认出这一轮的主请求，起标题这些辅助请求跳过。请求编号整个进程里不重复：核心照编号认重发，造会话会交回上一次造的那一个、说话不再开一轮，连接换了、核心重启了都照认。每一次等最多 120 秒，等不到的报是在等什么。
7. 照先后量：
   1. **冷启动**：先空跑一次（第一次起来要建索引），再量 `--runs` 次。每次从拉起 `miyu core` 算起，记三个点：写来 `ready`、握完手、造好会话并订阅上（能提交第一轮）。每次量完停掉核心，等它放开数据根的锁。
   2. **热启动、每多一个会话**：造 `--sessions` 个小会话各说一句，重启核心。歇两秒量核心空闲的内存。再一个个新连上、握手、订阅（订阅时核心才载入它），记这一段。都订阅着、各再说一句，歇两秒量内存。最后再重启一次核心，歇两秒，像头那样连上、握手，照先后问一遍头起来时问的六样（`config.get`、`human.get`、`model.list`、`persona.list`、`preset.list`、`package.list`，参数都空着），歇四秒（核心最后一个请求过去 2 秒还内存，`heap.md` 第 2 条），连着量内存（施工 V-5 下）。
   3. **大会话**：造一个会话，一句一句说，直到说之前的事件数到了 `--events`，再说 `--tail` 轮。每一轮记说出去到模型收到请求、到推来 `turn.ended`。歇两秒量载着它的内存。断开连接，等 `--idle-wait` 秒（会话 actor 空闲 180 秒退出）再量一次。然后重启核心 `--reloads` 次：每次连上、握手、订阅大会话（从头读日志、重放），记这一段；再说一句，记到模型收到请求。最后一次歇两秒量内存。
   4. **流式一轮**（施工 V-22，`measure/stream.rs`）：重启核心、订阅关着记忆的大会话，假模型的回答切成 `--pieces` 块（`Fake::split_into`，一块一个事件，接起来是原文），先说一句不量（载入以后头一次从头投影），再说 `--streams` 轮：每一轮记核心进程花的 CPU（各线程 `/proc/<进程号>/task/*/schedstat` 头一格加起来，只有 Linux 上有）、说出去到 `turn.ended`。量完假模型换回一块。别的几场假模型一次回一整块，核心每收一块要做的活量不出来。
   5. **扩展驱动**（施工 MD-4，`measure/driver.rs`，core1 11-07 照推荐定：进预算、CI 的 perf 那一项拦）：装上 `perf-driver`、配上 `perf/big`（同一个假服务）和 `perfx/big`（扩展驱动），重启核心、打开它（`extension.enable` 带 `approve`）；两个会话各垫四句、每句约 250 KB 的话（协议一行最长 1 MiB），之后每次请求约 1 MB。说至少 20 对（`--streams` 大的照它，`FIRST_PAIRS`），一对里两边各说一句、先后一对一换，记说出去到推来第一段正文的 `model.delta`，一对一对除、取中位数，表里另写一对一对减的中位数（23「扩展提供的模型驱动比内置驱动多的首字时延」，施工 FL-9：原来比两边的 p95，CI 上一边冒一次尖就超；倍数不随机器快慢变，闸门照预算拦、不乘 `--gate`）；再各说 `--streams` 轮，两边都在一秒里匀着交：内置的照假服务切成 `--pieces` 块、一个事件隔一下写（`Fake::pace`），扩展的照记号 `perf-pace` 交 300 段，记每一轮核心花的 CPU，比两边的中位数（23「扩展驱动流式时核心多用的 CPU」）。
   6. **追加并同步**：在进程里，大会话日志里的事件从第一条起，一条一条追加进 `target/perf/append/` 下的一份新日志，每条写一次、同步一次，走会话 actor 落盘用的同一个函数。
   7. **二进制**：`miyu`、`miyu-sandbox`、`miyu-extract`（施工 K-5，知识库抽字的小程序，随主程序放在旁边）的字节数；拷一份 `strip` 以后再量，没有 `strip` 的平台不写。
8. 内存读 `/proc/<进程号>/smaps_rollup` 的 `Pss`、`Anonymous`、`Rss`，核心和它拉起的子进程各一行，子进程照 `/proc/<进程号>/task/*/children` 找。只有 Linux 上读得到，别的平台写「不量」。
9. 对照预算的表：
   - 预算照 23 第二节的表读，第一格是名字。只写了一个数的照 p50 比，写了分位的照那个分位比；内存照核心进程的 PSS 比。
   - 比的几项：

     | 表里的一行 | 量的是哪一段 | 照 23 的哪一行比 |
     |---|---|---|
     | 热启动：订阅一个没载入的小会话 | 连上、握手、订阅 | 热启动到能提交第一轮 |
     | 热启动：重启核心后打开大会话 | 连上、握手、订阅 | 热启动到能提交第一轮 |
     | 一次请求的投影 | 大会话到了以后的那几轮，收到 `session.send` 的回应（这一句落了盘才回）到模型收到请求：组装、编码、连接，不含落盘的同步（施工 V-2 中；以前量的是说出去到收到请求，同步占了大半） | 一次请求的投影（增量，一万条事件的会话） |
     | 从头投影 | 重启、打开大会话以后头一次说，同样从落了盘算到模型收到请求：没有投影缓存，这一次从头算 | 同一个会话从头投影一次 |
     | 追加一条事件并同步 | 每一条的写加同步 | 追加一步的事件并同步 |
     | 核心空闲 | 一个会话都没载入时核心的 PSS | 核心空闲、没有会话载入 |
     | 连着一个头 | 头起来时问的六样过去、安静下来以后核心的 PSS（施工 V-5 下） | 核心空闲、连着一个头 |
     | 每多一个活动会话 | 小会话都订阅着时核心 PSS 涨的，除以会话数 | 核心里每多一个活动会话 |

   - 判：没超的「过」，超了的「超」，量不了的「不量」。
   - 23 第二节缺了要比的一行，量尺一开始就报错，不白量。
10. 没有预算的也列出来：冷启动的三个点、说出去到模型收到请求（含这一句落盘的同步，大会话到了以后的那几轮、重启以后头一次各一行：和投影那两行一比就是同步占了多少，施工 V-2 中）、流式一轮的核心 CPU 和一轮多久（施工 V-22；以前的原始数据没有，`--render` 时不出这两行）、大会话有多大、载着它和空闲以后的内存、二进制大小。另有一张「会话长大的一路上」：照说之前的事件数每一千条一档，报说一句到收到请求、落了盘到收到请求、一轮的 p50、p95。V-2 中以前的原始数据没有「落了盘到收到请求」，`--render` 时照说出去到收到请求算（上界）。
11. 条件写机器（CPU 型号、逻辑核数、内存）、系统、内核、rustc、提交（工作区有没提交的改动的标「+改动」）。不写主机名、用户名、路径。

### 工具一步（施工 V-29）

模型发出一个工具调用以后，核心多久把结果送回模型：agent 干活时这一段占的时间最长（2026-10-31 项目主人要每个工具都够快）。只量、不进闸门，没有预算；`cargo xtask perf --tools 20` 单独跑。

**怎么走**

1. 工作区在沙盒下的 `tools/`：两 KB 的小文件、8 MB 的大文件（十万行）、改的文件、拷进来的树（`--tree`），起成一个新的 git 仓库：`grep`、`glob` 在仓库里时照仓库根往下的 `.gitignore` 走，不另起一个仓库整棵树都被源码树的 `target/` 挡掉。
2. 核心照别的几场拉起，有 `systemd-run` 的放进自己的 scope（`systemd-run --user --scope`，进程号不变）：连子进程的 CPU 读得到。会话都关着记忆、不起标题，照出厂预设（`full`）的工具面，工作目录是工作区。
3. 假模型照剧本回（`fake/script.rs`）：提到这一轮记号的请求，照请求体里已经有前几次调用的结果（照调用编号数，驱动交回结果用的是供应商给的编号），回下一次调用（正文一句 `Checking.`、一个调用、`tool_calls` 收尾带用量、`[DONE]`），都回完了回那一句收尾。一轮里同一种调用一次接一次。
4. 每一步记：假模型把带调用的回答连同 `[DONE]` 写完的那一刻，到读全带着这次结果的下一个请求头；两头各读一次核心的 CPU（各线程的 `schedstat`；在 scope 里的再读 cgroup 的 `cpu.stat`，核心拉起的 `miyu-sandbox`、命令本身都算，挪到子进程的活照算，2026-10-30 项目主人定）。每种的头一次不算（头一回拉起沙盒、文件还不在页缓存里），之后的报 p50、p95。
5. 量哪几种（工具名、参数照 `resources/software/basesystem/tools/*.json`，`tools/calls.rs`）：`read` 小文件、8 MB 文件的末尾 200 行、列目录（`read` 读目录）；`write` 4 KB（同一个文件一次次盖）；`edit` 一处；`grep` 在树里搜（默认只列文件、带行两种）；`glob` 在树里找；`shell` 的 `true`、`echo`、`cat` 小文件，在工作区这一级（关进沙盒）和完全放开（沙盒关着）各一遍，两边一比是沙盒的开销。最后一种是挂着一个立即答的守卫的「read 小文件」（施工 HK-1，设计 65 第六节，目标多 1 毫秒以内）：核心起来以前往沙盒的数据根装一个扩展包 `perf-guard`（`[guard] tools = ["read"]`，开关关着，前面那几种不问它；程序是拷过去的量尺本身，带参数 `guard-extension` 起来只握手、每个 `tool.guard` 当场答 `allow`），别的几种量完打开它（`extension.enable` 带 `approve`）、等它在跑，再量这一种；和头一种一比就是守卫的开销。守卫那一种前面还有一种：挂着一个慢的 `tool.after` 收件人的「read 小文件」（施工 HK-2，设计 65 第六节：慢的收件人不拖回合）：另装一个扩展包 `perf-after`（`[after] tools = ["read"]`，开关关着；程序同样是量尺本身，带参数 `after-extension` 起来只握手、之后每读一行睡 200 毫秒），量完前面那几种打开它（`approve` `events.read`），量完关掉再开守卫；和头一种一比看回合等不等它。
6. 「什么都不做」的对照：同样一句回答不带调用，这一轮结束，量尺收到 `turn.ended` 当场再说一句；量回答写完到下一个请求头，拆成写完到收到 `turn.ended`、再说一句到核心落了盘回应、回应到请求头三段。这是核心收一轮、来回一趟、组装下一次请求的底子；工具一步减去它，大致是工具本身加上判权限、派、收回来的那几跳。
7. 拆段（`tools/split.rs`，不改核心）：停了核心以后读会话日志、运行日志，每一处取它在一步里头一回出现的时刻减去回答写完的那一刻，几十步取平均。会话日志：带这次调用的 `message.assistant`（actor 收到「说完了」）、这次的 `tool.result`（结果交进内核）；运行日志：`running`（判过权限、派之前）、`ran`（actor 收到做完）、`request`（交给请求模型的端口），`--tools-log debug` 另有每条输入、每个动作一行。时刻只到毫秒。顺手查每次调用的结果都是 `ok`，不是的报出来不白量。
8. 结果：`target/perf-out/<日期>-tools-<系统>-<架构>[-<标签>].json`（每一步的毫秒和两种 CPU、对照、拆段）和同名的 `.md`。条件另记量之前、量完的 `/proc/loadavg`、握手回应里的 `sandbox`。没有 `--render`：表只照这一份数出。

### 闸门（施工 V-3，23 F4）

1. CI 每次推上去都量一遍（只在 Linux 上，预算照 Linux 定的）：编 release、照出厂参数量，不等闲够了退下（`--idle-wait 0`，那一项没有预算，等它要多三分多钟）。表贴进这一次跑的摘要，也印进日志（摘要经接口取不出来）。
2. 闸门的倍数是 1（施工 V-5 下，2026-10-14 项目主人定超了预算就拦）：时间、内存都照预算本身拦。以前（V-3）时间照 1.5 倍拦，下面是那时候的理由，留着当来历：GitHub 的机器是 4 个逻辑核的 EPYC 7763，比开发的机器慢、抖：第一次量（V-3 上，2026-10-11）重开大会话 p95 128.8 ms，本机绑 4 个核也有 62.6 ms，查出来是重开时整份日志读了三遍（V-2 三补修了）；修了以后重开 p95 54.4 ms、投影 p95 2.6 ms、追加 p99 0.4 ms，都在预算里（V-3，2026-10-11）；离预算最近的是重开（九成），1.5 倍给它留了六成多的抖动，原来那样读三遍的 128 ms 照样拦得下。内存不随机器快慢变：空闲 27.3 MB、每多一个会话 0.96 MB，和本机差不到 1 MB。

### 排函数（施工 LW-1）

2026-11-21 项目主人定。核心的发行程序（Linux x86_64 的 `miyu`）里，启动和日常对话真正执行过的函数排在代码段的最前面、挨在一起。

**为什么。** 内核按片把代码映射进内存：一次缺页会把前后 64 KiB（`fault_around_bytes`）已经在页缓存里的页一起映射进来。函数散着放时，执行过的每一个函数都带进一片没有执行的邻居。2026-11-21 实测（核心 `36bd3c4e4`）：代码段 24.3 MB，启动、连上终端界面、空闲下来一共执行过 4.0 MB 的函数，留在内存里的代码却有 17.9 MB；发过一条消息、做过九次工具调用以后执行过 6.3 MB，留在内存里 20 MB 以上。排在一起以后，留在内存里的代码约等于执行过的函数。

**怎么走**

1. 清单是一个文本文件，一行一个函数名（符号表里的原名），照第一次执行的先后。核心的清单放在 cargo 的 target 目录下的 `order/miyu.txt`，终端界面的放在同一处的 `order/miyu-tui.txt`（施工 LW-6），都不入库：函数名跟着代码变，每次构建现录。
2. 流程（`xtask/src/order.rs`）：把清单写成空文件，带着 `MIYU_LINK_ORDER` 编 release 的核心；编量尺；运行 `miyu-perf --order <清单> --emulator qemu-x86_64` 录出清单；清单变了，cargo 只把 `miyu` 重新链接一遍；最后核对。
3. 链接参数由 `crates/miyu/build.rs` 加，不用 `RUSTFLAGS`：`RUSTFLAGS` 一变所有依赖都要重编，还会带到构建脚本和过程宏上；构建脚本的 `rustc-link-arg-bin` 只加在 `miyu` 的链接上，符号名不变，依赖不重编。参数是 lld 的 `--symbol-ordering-file` 和 `--no-warn-symbol-ordering`（清单里有链接器挪不动的名字，例如 `_start`）。工具链钉的版本在 x86_64 Linux 上默认用自带的 rust-lld。
4. 录清单用 QEMU 的用户态模拟器，带 `-d in_asm`：模拟器只在一块代码第一次要执行时翻译它，并把这一块每条指令的地址写进日志，所以日志就是执行过的代码的全集，先后就是第一次执行的先后。不用覆盖率工具：标准库是预先编好的，覆盖率记不到它，而启动时执行的有一大半是它。地址减去程序的装载起点（读模拟器进程的 `/proc/<进程号>/maps`），照 `nm` 列出的符号表换成函数名。日志有两种写法，都认（`order/listing.rs`）：带反汇编库的 QEMU 一条指令一行；不带的（Ubuntu 24.04 的 `qemu-user`）一块只写起点、下面跟字节原文。只有起点也够用，认的是这一块落在哪个函数里；两种 QEMU 在同一份程序上录出来的清单只差几个函数。
5. 剧本（`miyu-perf --order`，`order/script.rs`）。沙箱里配三家供应商：`perf`（明文）、`perftls`（HTTPS 上的 HTTP/1.1）、`perfh2`（HTTPS 上的 HTTP/2），都指向量尺自己的假模型；核心照 `SSL_CERT_FILE` 信任假模型的测试证书（系统的证书库接在前面，核心读证书时和平常一样要读一整批）。
   1. 先原生运行两遍、各自停掉：第一遍连上、握手、问头起来时问的六样、开一个关着记忆的会话、在三个模型上各说一句；第二遍连上、握手、问六样。这样后面录的是第三次启动：数据根已经建好，模型目录的摘要已经缓存，这才是用户平常的状态（第二次启动还在整理第一次留下的摘要）。
   2. 第一段（模拟器里）：启动；连上、握手、问六样；开一个关着记忆的新会话，照 `session.configure` 换模型，在三个模型上各说一句；开一个开着记忆的会话说一句；「工具一步」里的 14 种调用各做一次（守卫、`tool.after`、扩展驱动那几种不做）；歇 4 秒（核心安静 2 秒以后归还内存、记账）；停掉。
   3. 第二段（模拟器里，同一个数据根）：启动；连上、握手、问六样；订阅第一段的会话（核心从日志载入它）、说一句；歇 4 秒；停掉。
   4. HTTPS 的两句要假模型对应的那个口确实收到了请求才算，等不到就报错，不退回明文。
   5. 「问六样」以外还照终端界面真发的问（`script.rs` 的 `head_extras`、`watching`，照 2026-11-21 钉在 `heads.toml` 的终端界面抄，参数也照它）：订阅配置、会话列表、软件包、通知、定时、总线、部件几条流，问会话上下文、命令目录；打开会话以后订阅它的部件、说正在看它、问它的用量。只问六样的时候，这些路上的三百多个函数（约 0.4 MB）散在清单以外，配着真的终端界面时核心空闲的代码页是 9.1 MB，录上以后是 6.1 MB。头改了问法，这里跟着改。
   6. 清单里第一段的函数在前，第二段新执行到的接在后面。每一段的日志写完清单就删掉。核心是照原来的办法直接结束的，退出那一路的函数不在清单里。
   7. 配着真的终端界面再录两段（施工 LW-6，`order/head.rs`）：`miyu-perf --order` 带了 `--head <终端界面程序>` 的，在前两段以后接着录第三段；同时带了 `--head-order <终端界面的清单文件>` 的，再录第四段。只写 `--head` 的只录第三段，这是给终端界面还不认清单的时候用的；只写 `--head-order` 的、不在 `--order` 的跑法里写的都报错。两段开始以前，沙箱的系统配置加上 `[ui] welcomed = true` 和 `[tui] auto_pick = true`，跳过欢迎和选人格；家目录、`XDG_CONFIG_HOME`、`XDG_DATA_HOME`、`XDG_STATE_HOME`、`TMPDIR` 都指进量尺工作目录下的 `user/`，`MIYU_DISTRO_PACKAGES` 指向一个空目录，核心和终端界面都不碰真的家目录、也看不到宿主装的软件包。主程序、终端界面的环境是整份给的：宿主的 `PATH`、`LANG`、`LC_*`，`TERM=xterm-256color`、`COLORTERM=truecolor`，数据根、资源、证书和核心一样，不设 `XDG_RUNTIME_DIR`（三方都照数据根里的 `run/` 找套接字）。
      1. 第三段：核心照前两段的办法在模拟器里起。原生起主程序 `miyu`（不带参数），放进一个 160×45 的伪终端；主程序连上正在运行的核心、换成终端界面。量尺像 kitty 那样回答终端界面问终端的几样（光标位置、DA1、前景背景色、16 色、图形协议、字格和窗口大小、键盘协议、同步输出，同核心仓库 `bench/rivals/term.py`）：没人回答的话，终端界面要等 6 秒超时才画输入框，走的路也不一样。等输入框画出来（去掉转义序列以后屏幕上出现 `❯`），量尺读这个进程的 `/proc/<进程号>/exe`、`cmdline`、`environ`：程序要是 `--head` 给的那一个，命令行参数和主程序加的环境变量记下来给第四段用。然后照剧本走：打一句话，等它出现在输入框里再回车，等假模型收到这一轮的主请求（提到这一句的记号、带工具表）、屏幕上画出回答、会话日志里这一轮结束（`turn.ended`）；再打一句触发工具调用的话，假模型照「工具一步」的剧本把工作区这一级的 11 种调用各回一次，每个请求带着的结果要照先后对上，等这一轮结束；歇 4 秒；结束终端界面，停掉核心。这一段的日志接在核心清单后面，新执行到的函数排在已有的后面。
      2. 第四段：核心原生起。`<模拟器> -d in_asm -D <日志> <终端界面程序>` 带着第三段记下的参数和环境放进伪终端，同样的剧本；装载起点读模拟器进程的 `/proc/<进程号>/maps`，符号表用 `nm` 读终端界面的程序，清单写进 `--head-order`。
      3. 两段的工作区各自新建（`tools-3/`、`tools-4/`），工具调用都在新的文件上做。等输入框、等回答、等一轮结束最多各 600 秒；哪一样等不到都报错停下，报的是在等什么、屏幕上最后是什么。终端界面的清单是空的也报错。
      4. 伪终端用 `rustix` 的 `openpt` 开（同 `crates/miyu/tests/support/pty.rs`），不用 `unsafe`；子进程的标准输入、输出、错误都是从端，窗口大小设在从端上，没有控制终端（终端界面不靠它）。不借 util-linux 的 `script`：隔着它，模拟器不是量尺的子进程，读装载起点还要往下找一层。
6. 核对（`xtask/src/order/verify.rs`）：清单里在符号表里找得到的函数合计 L 字节；这些函数按字节算要有九成以上落在代码段开头的 1.25 L 以内，不到就报错。换了链接器、参数没有生效时在这里拦下，不会悄悄不排。
7. 在哪些命令里做：`cargo xtask perf`（闸门量的就是排过的程序）和 `cargo xtask dist`（本机是 `linux-x86_64` 时）。两个命令都认 `--no-order`：照原来的办法编，不排。`cargo xtask perf` 没有终端界面，只走上面第 2 条。`cargo xtask dist` 的先后（施工 LW-6）：
   1. 核心照第 2 条编、录（照协议问的两段）、重链、核对。
   2. 编终端界面。终端界面钉的提交的检出里有 `build.rs`、里面认 `MIYU_LINK_ORDER` 的，先把 `order/miyu-tui.txt` 写成空文件，带着这个变量编；不认的，在标准输出上说一行 `终端界面钉的提交还不认排函数，这一次不排它`，照原来的办法编，后面只录核心的第三段。
   3. 编网页、搭好发行包目录以后，对着这个目录运行 `miyu-perf --order <核心清单> --emulator … --miyu <目录>/miyu --resources <目录>/resources --work … --tree … --head <目录>/miyu-tui --head-order <终端界面清单>`（终端界面不认清单的不写 `--head-order`）。量尺整份重写核心清单，前两段也重录：清单以对着真发行包录的为准。
   4. 核心照新清单重链；终端界面认清单的，在它的检出里带着它的清单再编一遍。两个程序重新拷进发行包目录，各自照自己的清单核对（第 6 条，核对的函数对任意程序都一样）。
   5. 然后才打压缩包、搭分包。每一步说一行在做什么；哪一步失败就报哪一步、哪条命令，停下，不悄悄不排。没有装模拟器又没有写 `--no-order` 的，当场报错并说明要装什么（Debian、Ubuntu、Arch 的包都叫 `qemu-user`）。CI 的 `perf` 一项和发版的 `linux-x86_64` 一项先装模拟器。
8. 排核心的 `miyu`；`cargo xtask dist` 另排终端界面的 `miyu-tui`（施工 LW-6）。`miyu-sandbox`、`miyu-extract` 用完就退出，不排。Linux aarch64、macOS、Windows 的程序和原来一样。

**剧本要跟着用户的真实状态走。** 用户平常会执行、剧本却没有录到的路径，函数散在清单以外，每碰到一处带进一片邻居页，而闸门量的场景和剧本是同一套，看不出来。新加了用户平常会用到的路径（新的工具、新的后台任务），在剧本里补一段。打包时配着真的终端界面录的两段（上面第 5 条第 7 款）补上的是终端界面那一边的路径，闸门量的仍然是量尺自己的剧本。

**量到的**（2026-11-21，另一台测试机，`cargo xtask perf --idle-wait 0`，同一份代码先 `--no-order` 再排）：

| 项目 | 没排 | 排过 |
|---|---|---|
| 核心空闲、没有会话载入 | 20.8 MB | 9.5 MB |
| 核心空闲、连着一个头 | 26.4 MB | 13.0 MB |
| 载着大会话 | 33.5 MB | 22.9 MB |
| 每多一个活动会话 | 1.03 MB | 0.98 MB |

时间类的各行（热启动、投影、冷启动、流式一轮）都在原来的抖动以内。清单 8809 个函数、6.8 MB，录一遍约 20 秒；整个流程比原来多一次整体优化的链接。

配着真的终端界面量（本机，`heads.toml` 钉的终端界面，第三次启动，本机 HTTPS 假模型，三次取中位）：

| 状态 | 核心，没排 | 核心，排过 | 其中代码页 |
|---|---|---|---|
| 连着终端界面空闲 | 27.5 MB | 15.4 MB | 18.1 → 6.1 MB |
| 发过一条消息 | 29.8 MB | 18.6 MB | 19.7 → 8.4 MB |
| 再做九次工具调用 | 31.2 MB | 20.3 MB | 20.2 → 9.7 MB |

**和真的终端界面还差的。** 2026-11-21 用真的终端界面当驱动录的清单排出来，核心空闲的代码页是 4.6 MB、发过一条消息 6.9 MB，比量尺的剧本少 1.5 MB 上下。原因是量尺的沙箱和真的发行包不一样：沙箱里没有装终端界面的软件包（读它的配置项走的是另外几条路），量尺也不走终端界面收发的每一样。所以 `cargo xtask dist` 对着搭好的发行包、配着真的终端界面再录两段（施工 LW-6，上面第 5 条第 7 款）：发行的核心带着这两样录到的函数，终端界面也照它自己的清单排。闸门量的场景和量尺的剧本是同一套，`cargo xtask perf` 没有终端界面，所以闸门量到的仍然是只照量尺剧本排的程序，看不出这一段。打包时录到的（2026-11-22，本机真跑 `cargo xtask dist`，终端界面是带着字表新读法的那一份）：核心清单 9147 个函数、7134 kB（只录量尺那两段时 8978 个、7059 kB），终端界面的清单 1546 个函数、2436 kB，四段录一遍约 45 秒。用打出来的发行包量（沙箱数据根，本机 HTTPS 假模型，第三次启动，三次取中位）：核心空闲的代码页 5.2 MB（只照量尺的剧本排是 6.1 MB），终端界面空闲的代码页 1.9 MB（没排是 7.6 MB）；核心加终端界面合计空闲 19.2 MB、发过一条消息 22.8 MB、做过九次工具调用 25.1 MB（LW 线以前是 42.1、45.5、47.1 MB）。

**还没有的。** 真机执行、模拟器里没有执行的函数还散在清单以外（2026-11-21 实测发过一条消息以后约 0.4 MB：加密库照 CPU 型号选的汇编版本、zstd 解压）；压缩、记忆抽取、子代理、MCP、扩展、知识库这几条路还没有录进剧本；网页界面的程序还没有排；Linux aarch64、macOS（`ld64 -order_file`）、Windows（`lld-link /order`）还没有做；函数内部的冷热分块（BOLT、PGO）没有做。

### 重定位打包（施工 LW-2）

2026-11-21 项目主人定。Linux x86_64（glibc）的 release 构建，`miyu` 链接时加 `-z pack-relative-relocs`（`crates/miyu/build.rs`）。

1. **为什么。** 位置无关的程序启动时，动态链接器要把整张重定位表读一遍，读过的页留在内存里。核心的 `.rela.dyn` 有 1.2 MB，几乎全是「这个位置加上装载起点」这一种。打包成 RELR 以后是 `.relr.dyn` 16.5 KB 加 `.rela.dyn` 5.4 KB。
2. **要什么。** glibc 2.36 以上（程序里多一个 `GLIBC_ABI_DT_RELR` 的版本要求，低于它的动态链接器直接拒绝启动）。Linux 的基线是 glibc 2.39（设计 12），发版在 Ubuntu 24.04 上编。
3. **只加在哪。** 只有 Linux、x86_64、glibc、release 四样都对上才加（`build.rs` 的 `packs`）；dev 构建不加，日常的编译、测试不变。aarch64 的链接器（GNU ld）到 2.43 才认这个参数，没有做。`miyu-sandbox`、`miyu-extract` 没有做。
4. **量到的**（2026-11-21，另一台测试机，`cargo xtask perf --idle-wait 0`，都排过函数）：核心空闲 9.5 → 8.2 MB，连着一个头 13.0 → 12.0 MB。

### 三家对比（施工 V-7，23 F6）

发版前和 jcode、codex 比一次：同一台机器、同一个模型端点、各自干净的沙箱家目录、同一套场景，量 CPU、内存、读写、硬盘。上面的量尺只量核心、每次都跑；这里量的是人真用的一整套（核心加终端界面），只在发版前跑。

**在哪**

| 文件 | 管什么 |
|---|---|
| `bench/rivals/main.py` | 入口：参数、照先后跑各场景。开头带 `uv` 认的依赖（`pyte`），`uv run` 直接跑 |
| `rivals.toml` | 每一家怎么配、怎么起、屏幕上看到什么算到了首屏、长会话的编号怎么找、装好的是哪几个文件。加一家只加一张表 |
| `places.py` | 程序、端点、输出目录在哪；占位怎么换 |
| `rival.py` | 一家：照它那张表换好占位，配沙箱家目录 |
| `conditions.py` | 量的条件 |
| `homes.py` | 家目录模板：做、存、还原 |
| `term.py` | 伪终端：像 kitty 那样回答终端界面问的几样，用 `pyte` 看屏幕 |
| `meter.py` | 一个 systemd scope 的计量：CPU、内存、读写、唤醒 |
| `reap.py` | 收拾残留的后台进程：只杀家目录指着沙箱的 |
| `leaks.py` | 跑完查输出目录里有没有 key：别家可能把环境写进自己的家目录（codex 的 `shell_snapshots`）；用转发的连真 key 一起查 |
| `relay.py` | 本机转发（施工 V-27）：各家连它，它换上真 key、补会话头再转给上游，每个请求记一行用量 |
| `screen.py`、`task.py`、`long.py`、`disk.py` | 各场景 |
| `summary.py` | 汇成表 |
| `fixture/calc/` | 真任务那一轮要修的小项目 |
| `test_rivals.py` | 不跑别家的那几条：表写得对、占位都认识、汇表 |

**怎么跑**

```
OPENAI_BASE_URL=… OPENAI_API_KEY=… MIYU_BENCH_MODEL=… uv run bench/rivals/main.py --tui <终端仓库> all --into target/perf-out --tag v<版本>
```

经本机转发（施工 V-27，上游要每段对话带会话头的，例如 opencode）：

```
MIYU_BENCH_MODEL=… uv run bench/rivals/main.py --tui <终端仓库> --upstream https://opencode.ai/zen/go/v1 --upstream-key-env OPENCODE_GO_API_KEY all --into target/perf-out --tag v<版本>
```

1. 端点、key、模型名只从环境变量来，三家用同一个。key 留在环境变量里交给各家：Miyu 的配置写成 `{ env = "OPENAI_API_KEY" }`，codex、jcode 照它们自己认的变量名去读，不写进任何文件、不打印；结果里只记模型名，不记地址。用转发的（`--upstream`）：真 key 只在 `--upstream-key-env` 那个变量里，测具只把它交给转发进程，各家的环境里去掉这个变量，`OPENAI_BASE_URL` 换成转发上这一家的路径、`OPENAI_API_KEY` 换成假的；这时不用设 `OPENAI_BASE_URL`、`OPENAI_API_KEY`。
2. 核心照 `--core`（默认这个仓库），终端界面照 `--tui`（终端界面的仓库，里面有装成软件包的 `tui/` 和编好的 `target/release/miyu-tui`；包的目录和编号同名，设计 48，2026-11-12 以前叫 `miyu-tui/`，旧的仓库一开始就报），都要先 `cargo build --release`。jcode、codex 照 `--jcode`、`--codex`，不写的照 `PATH` 找。`--only` 只量几家，`--cpus` 绑到几个核上。
3. 子命令可以分开跑：`homes`（做模板）、`screen`、`task`、`long gen`、`long open`、`disk`、`summary`；`all` 照这个先后全跑。`--runs`（默认 5）、`--settle`（默认 13 秒）、`--idle`（默认 60 秒）。
4. 家目录、模板、工作目录、原始结果都在 `--out`（默认 `target/rivals/`）下。`summary --into target/perf-out --tag <名>` 再写一份 `target/perf-out/<日期>-rivals-<名>.md`、同名 `.json`（汇总的数，加每一轮的原始结果 `runs`；命令输出的最后几行带着本机路径，不入库）。
5. 只在 Linux 上量：CPU、内存照 cgroup v2 和 `/proc` 读，要 systemd 的用户会话。别的系统上一开始就说清楚、退出码 2。

**怎么走**

1. 被测的程序都放进自己的 systemd scope 跑：CPU 照 scope 的 `cpu.stat`（退出了的子进程也算），内存报进程树的 PSS 之和和 scope 的 `memory.peak`，读写照每个进程 `/proc/<进程号>/io` 相加（写报两样：交给系统的 `wchar`，落到盘上的 `write_bytes`），唤醒照每个线程的上下文切换相加。都去掉 `XDG_RUNTIME_DIR`：沙箱的核心把套接字放进自己的数据根（`ipc.md`）。
2. 模板：每家在空的沙箱家目录里配好模型（Miyu 走 `miyu pkg install` 装终端界面的包、`miyu config set` 配模型，和人配的是同一条路；`tui.auto_pick` 开着（CL-8 补跟着终端改名），新会话照默认的人格、预设开，不然首屏是「请选择预设」的框、没有输入框，施工 V-27），跑一轮很短的任务，开两次终端界面、每次看到首屏等它安静再关、收掉后台进程，存成模板（第一次开留下的活有的要下一次起来才做完：Miyu 的核心在后台拉了新的模型目录，下一次起来才整理成摘要存进缓存；只开一次就存，每一轮冷启动都多做一遍，核心多花一百多毫秒 CPU、多写 1.6 MB，量的不是人平常起来的样子，施工 V-27 查出）。每次关掉界面以后，后台进程照「好好退出」收（自己的 `stop`、SIGTERM 等它收尾）。存、还原都不拷套接字（后台进程收掉时来不及删的，例如 Miyu 的 `run/core.sock`）。家目录、缓存都在沙箱里（Miyu 的缓存跟 `XDG_CACHE_HOME` 走、不跟 `MIYU_HOME` 走，也指进沙箱，`store.md`）。每次量之前照模板还原，还原完先 `sync`：拷出来的脏页没落盘，被测的程序一 fsync，文件系统会顺手一起刷，块设备的写就算到它头上（btrfs 上实测一轮多出 17 MiB）。三家的起点一样（23 第四节：jcode 测别家用真实的家目录，这里不照搬）。
3. 首屏：伪终端里起终端界面，屏幕上出现 `rivals.toml` 写的那几个字算到了。做模板时就开，对不上的当场报，改 `marker`。两家都挑「界面报出用哪个模型」那一刻，不挑先画的架子（施工 V-27 核对）：Miyu 的输入框照机器缓存里记的先画，那时底下写着「正在连接核心…」，连上核心才有权限级别，再晚几十毫秒状态行报出模型名，首屏字就是模型名（`{model}`，字里的占位照样换）；jcode v0.99.1 先画一个空架子（约 20 ms 就有输入框，写着「connecting to server…」），连上自己的服务头上那一行才报出 `OpenAI-compatible: <模型>`。
4. 场景：
   1. **冷启动到首屏**：没有后台进程，从起终端界面算到首屏；记时间、CPU、PSS。
   2. **空闲**：接着冷启动，首屏后先等 `--settle` 秒，再量 `--idle` 秒：CPU、每秒醒几次、终端每秒收到几个字节、结束时的 PSS。首屏后每秒的 CPU 都记下，汇表时出每秒的中位数，照它看收尾要等多久。
   3. **热启动到首屏**：后台进程（Miyu 的核心、jcode 的服务）先起来歇 3 秒，再开终端界面到首屏；两个 scope 相加。没有后台进程的一家不量。
   4. **三个会话同时开**：开三个终端界面都到首屏，同样先等 `--settle` 秒，再空闲 `--idle` 的一半：三个加起来的 PSS、空闲的 CPU。
   5. **一轮真任务**：不开终端界面，各家的一次性命令修好 `fixture/calc` 的 bug（先跑测试、读代码、改、再跑测试）：用时、CPU、峰值 PSS、读写、家目录多了多少，测试过没过。家目录多了多少报两种口径（2026-10-31 项目主人定，施工 V-27），两家同一种口径各一列：「直接杀掉」是命令跑完、等 CPU 停下以后，后台进程（Miyu 的核心、jcode 的服务）还活着时盘上的样子，等于这时崩溃、断电剩下的（SQLite 没合回去的 `-wal`、`-shm` 都在里面）；「好好退出以后」是再让它照自己的办法正常退出（`rivals.toml` 的 `stop`：jcode 是 `server stop`；没写的不跑，Miyu 的核心收到 SIGTERM 自己收尾），剩下的进程发 SIGTERM 最多等 30 秒，还不走的才硬杀（记在结果的 `shut.forced` 里），再量一次，等于平时正常用剩下的。CPU、内存、读写照退出之前的读。jcode v0.99.1 的 `server stop` 不带 `--force` 只印一句提醒、返回 0、服务不退（施工 V-34 查出，10-31 那次一样）：它「好好退出」实际走的是后面的 SIGTERM，服务 40～70 ms 就退、没有硬杀过；jcode 写的是 JSON 文件，两种口径本来就几乎一样，数照用。以后再动测具时改成 `server stop --force`。
   6. **长会话**：照同样的 50 轮话造各家自己的长会话（每轮二十几行填充文字，最后一轮只回一个记号），再开终端界面接着它，到屏幕上看见那个记号：时间、CPU、PSS。会话编号照各家存会话的地方找最新的那一个：Miyu 是数据根的 `root/sessions/<编号>/`（单人的，`store.md`），jcode 是 `.jcode/sessions/<编号>.json`。
   7. **硬盘**：装好占多大（`rivals.toml` 的 `install`，照占的块算，硬链接只算一次），家目录跑过一次多大，长会话那一个会话自己的文件多大。家目录跑过一次的数据同样报两种口径：模板是好好退出以后存的（「好好退出以后」）；做模板第二次开终端界面、关掉界面以后、让后台进程退出之前记下盘上有什么（`results/home-crash-<表名>.json`，「直接杀掉」）。配置参考（`var/cache/config/config.schema.json`、`reference.toml`）这类核心生成的文件照实算在数据里（项目主人定：不为数字好看省）。家目录分两样（2026-10-31 项目主人定，施工 V-27）：会一直复用的缓存（`rivals.toml` 的 `caches`：模型目录、图标这类）单列一行，不算进「跑过一次多了多少」；剩下的是跑一次产生的数据（会话、日志、索引这些），Miyu 的这部分再按文件列出来（最大的 25 个，其余合成一行），看是什么占的。
5. 本机转发（`relay.py`，施工 V-27）：
   1. 各家连 `http://127.0.0.1:<端口>/<表名>/v1`，路径里的表名分出是哪一家；转发换上真 key、去掉压缩（流里的用量才读得出来），转给上游，流着回的原样流回去。
   2. 会话头 `x-opencode-session`：opencode 要每段对话带一个稳定的（不带回 400 `MissingSessionID`）。客户端带了的原样转；没带的照「这一家、这一场、这段对话第一句用户的话」算一个（`ses_` 加哈希）：同一段对话往后接着说的每一次请求都一样，换一场、换一段对话就换。测具在每一轮开头告诉转发现在是哪一场（`POST /_scene/<表名>`：`homes`、`screen-<轮>`、`task-<轮>`、`long-gen`、`long-open-<轮>`）。两家一样补；会话头是不是客户端自己带的记在日志里（`own_session`）。
   3. 每个请求记一行进 `results/relay.jsonl`：哪一家、哪一场、模型、状态码、流不流、会话头是谁带的、用了多久、用量（输入、其中缓存命中、输出、推理）；出错的记上游回的前 300 个字。不记请求体、回应体、key。汇表时照场合计成「模型用量」一节（请求数、出错几次、输入、缓存命中、输出），以后比 token 用。
6. 每个子命令跑完查一遍输出目录：哪个文件里有 key（测具自己不写，别家可能写），报出文件，不印 key。
7. 表：每一项报中位数，括号里是最小到最大。条件写机器（CPU 型号、逻辑核数、内存、内核）、绑没绑核、模型名、用没用转发、三家的版本、核心和终端的提交（有没提交的改动的标「+改动」）、终端是不是 `heads.toml` 钉的那一份、负载（量之前的 1、5、15 分钟负载，每一轮开头记的 1 分钟负载的最小到最大，施工 V-27：别的会话在编译时时间类的数会抖，CPU、内存、读写受的影响小）。不写主机名、用户名、路径、地址。

**发版前**

1. 核心照要发的那个提交编 release；终端界面照 `heads.toml` 的 `rev` 检出、编 release。
2. 照上面「怎么跑」跑 `all`，`--tag` 写要发的版本。
3. 和上一次发版前量的那一份比（结果不入库，自己留着上一份）：Miyu 哪一项比上次差了，先查清楚再发。
4. 两份结果和发版的提交一起入库；`target/rivals/` 整个删掉（别家的家目录里可能存着 key）。
