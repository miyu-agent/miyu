## 施工单 LW-18：macOS 上闲下来也把堆里空着的还给系统

状态：做完（2026-11-22）。LW 线（轻量化）。

### 目的

2026-11-22 头一次在 macOS 上量了占用（一台 M1，macOS 15.6；核心加终端界面，口径是 `phys_footprint`，就是活动监视器「内存」那一列）：空闲 18.1 MB，轻量化以前的 rc.2 是 19.6 MB。LW 线前面的十几步在 macOS 上几乎没有效果，因为最大的几项只在 Linux 上生效。

逐区看（`vmmap`）：空闲时核心的堆写过 7.3 MB，在用的只有 1.7 MB；终端界面写过 5.8 MB，在用 1.4 MB。两个进程合起来有 10 MB 是放掉以后分配器留着没还的。核心里「安静下来把堆里空着的还给系统」那一步（`miyu_heap::trim`）在 macOS 上是空的，代码和蓝图写的是「macOS 的分配器自己会还」，实测它不还，要等系统内存紧了才还。

### 蓝图改哪几节

- `heap.md`：「是什么」里 macOS 归到「留着不还」的一边；「在哪」「对外的样子」里 `trim` 的 macOS 做法；「怎么走」加第 6 条；「守着它的」加 macOS 的测试。

### 做法

1. `crates/miyu-heap/src/lib.rs`：macOS 单独一份实现，`trim` 调 libSystem 的 `malloc_zone_pressure_relief(NULL, 0)`。调它的地方不用动：核心里安静下来、读完模型目录、会话退下、库闲下来这几处本来就调 `trim`。
2. `trim` 交回的「还了没有」：这个函数自己交回的字节数靠不住，另看进程的占用前后落了没有，两样里有一样说还了就算还了。
3. 终端界面经 `miyu-client` 用的是同一份 `trim`，升级钉住的核心以后跟着生效；它现在只在正文少了一大截、换上大块回应以后才还，「起来安静以后还一次」在终端界面的仓库里另做。

### 不做什么

- 不在 macOS 上调分配器的参数，不换分配器。
- 不做「32 KiB 以上的块直接向系统要」：用环境变量 `MallocMediumZone=0`（让这些块不进分配器的中等区）对照过，核心加终端界面只再少 0.1 到 0.7 MB。
- macOS 的发行包排函数是另一件事，这一步不做。

### 验收

1. macOS 上 `cargo test -p miyu-heap`：放掉 32 MB 小块、还一次以后进程的占用落回去 16 MB 以上。在那台 M1 上连跑 25 遍都过；CI 的 macOS 上跑。
2. 那台 M1 上重量三个状态，核心的占用比改以前低。
3. Linux、Windows 上的行为和测试不变。

### 量到的

2026-11-22，M1 MacBook Pro，macOS 15.6，沙箱数据根，第三次启动，每个状态起三遍取中位，单位 MB。「改以前」是 main；「插库实验」是不改程序、往两个进程里插一个每 3 秒调一次 `malloc_zone_pressure_relief` 的小库；「改以后」的核心是这一步，终端界面是 main 加上「起来以后还一次」并用这一步的 `miyu-client`。

| 状态 | 改以前 | 插库实验 | 改以后 |
|---|---|---|---|
| 空闲 | 18.1（核心 10.2 + 终端界面 7.9） | 14.7（8.3 + 6.4） | 14.8（8.2 + 6.6） |
| 说过一句 | 20.7（12.3 + 8.4） | 15.7（9.3 + 6.4） | 16.0（9.1 + 6.9） |
| 九次工具调用 | 20.8（12.3 + 8.5） | 16.1（9.7 + 6.4） | 16.9（9.7 + 7.2） |

各遍的合计（kB）：改以前空闲 18033、19249、18097，说过一句 20465、19649、20689，九次工具调用 21809、20833、20753；改以后空闲 14754、14706、14770，说过一句 15507、16018、16050，九次工具调用 16722、16642、17553。

RSS（`ps`）几乎没有变（核心空闲 24.8 → 25.3 MB）：还回去的页系统标成可以回收，仍然算在 RSS 里，不再算进占用。

### 测试里踩到的

- 1 KiB 的块有时放掉当场就由分配器自己还了，再叫它还就看不出差别，测试十遍里有四遍不过。改用 512 字节的块以后稳定。
- 两条「放掉一大片再看还没还」的测试在同一个进程里一起跑时互相干扰（一条叫分配器还，会把另一条刚放掉的也还了），加了一把锁让它们一条一条跑。
