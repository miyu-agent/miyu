## 施工单 LW-12：核心的线程缓存少留

状态：已完成（2026-11-22），等待合进 main。这一步属于 LW 线（轻量化）。2026-11-21 项目主人定：能优化的都做，收益小也做，只按收益从大到小排先后；优化不能靠牺牲速度换数字。

### 目的

glibc 的每条线程有自己的缓存（tcache）：线程释放的小块先进入缓存，不回到 arena，每种大小默认最多留 16 块。核心有十几条常驻的线程，每一条都留着一份。施工 LW-5 量到这些缓存里攒着约 0.8 MB，但是这个上限在进程里无法修改（`mallopt` 没有这一项），当时没有做。

这一步把上限设成每种大小留 4 块。glibc 只在进程启动时读取环境变量 `GLIBC_TUNABLES`，所以做法是让核心带着这个环境变量启动。

### 要拍板的

这一步没有需要项目主人决定的产品取舍，下面两项技术细节按推荐的做法确定：

1. **留几块：4 块。** 一块都不留时内存只再少 0.3 MB，但是多项时延慢一成左右（见「量到的」），不符合「不靠牺牲速度换数字」。
2. **怎样让所有启动方式都带上：`miyu` 拉起时设在命令上，其他方式启动的核心重新执行自己一次。** 没有选「在每一份托管文件里写环境变量」，因为打包目录里的托管文件有六种（systemd 用户服务和系统服务、dinit、runit、OpenRC、XDG 自启动），分散在六处容易漏，而且写死在文件里会覆盖你自己设置的 `GLIBC_TUNABLES`。重新执行只发生在核心启动的那一刻，不改变进程号。

### 不做什么

- 不改终端界面和其他头：终端界面只有 7 条线程，同样的设置只少约 0.1 MB。
- 不改 `ARENAS`、`MMAP_FROM` 这两个已有的参数。
- 不把这一项传给核心运行的命令：AI 运行的命令和你在自己的终端里运行时，分配器的行为保持相同。
- 不加配置项：想用其他值时，自己在环境里写 `GLIBC_TUNABLES=glibc.malloc.tcache_count=<值>`，核心不会修改它。

### 验收

1. `crates/miyu-heap/src/launch.rs` 的测试：没有设置时设上这一项，原来的值记成空的；原来有其他项时保留在前面并记下；人自己写了留几块时不设；只有 glibc 上交回变量；命令拿回拉起的一方原来的值。
2. `crates/miyu-basesystem/src/shell/env/tests.rs`：核心带着这一项时，命令拿到的是原来的值，原来没有设置时不传；核心没有带着时按原样传。
3. `crates/miyu/tests/tuned.rs`（真的拉起核心，读它的环境）：直接运行的核心也带上了这两项；人自己设置的其他项保留并记下；人自己写了留几块时保持原样；其他平台什么都不带。
4. 量：内存量尺交替量改前、改后各两遍；`miyu-perf` 的各项时延和默认设置比较，没有退步。
5. 实测：在沙箱里用四种方式启动核心（直接运行、带着其他参数直接运行、自己写了留几块、`miyu core start`），查看进程号、环境变量和启动日志。

### 风险

- **重新执行自己出问题**：重新执行失败时核心仍然正常启动，只是不带这一项；带上以后不会再次重新执行，所以不会循环。工作区里所有直接运行 `miyu core` 的测试都会经过这一步。
- **在模拟器、调试器里运行核心**：重新执行以后，新的进程不再受用户态模拟器（`qemu-x86_64`）的控制。量尺录排函数的清单时已经带上环境变量，所以不会重新执行。自己在模拟器或者 heaptrack 里运行 `miyu core` 时，需要先在环境里设好 `GLIBC_TUNABLES=glibc.malloc.tcache_count=4`。
- **glibc 以后改了这个可调参数的名字**：glibc 会忽略不认识的名字，核心仍然正常运行，只是这一项不生效；启动日志的 `tunables` 和内存量尺可以发现。
- **扩展、MCP 服务继承了这一项**：它们由核心直接启动，会带着同样的设置。影响只是它们的线程缓存也少留，功能不受影响。

### 量到的

2026-11-22，本机，沙箱数据根，发行版核心（没有排函数）。

**选留几块**（`miyu-perf --idle-wait 0`，三种设置各运行一次，用环境变量切换）：

| | 默认（16 块） | 留 4 块 | 不留 |
|---|---|---|---|
| 核心空闲、连着一个头 | 24.8 MB | 23.7 MB | 23.4 MB |
| 载着一万条事件的大会话 | 33.9 MB | 31.7 MB | 30.3 MB |
| 重启核心后打开大会话（p50） | 12.6 ms | 11.8 ms | 13.9 ms |
| 追加一条事件并同步（p50） | 1.7 ms | 1.7 ms | 2.0 ms |
| 从头投影：打开开着记忆的大会话后第一次说（p50） | 1.2 ms | 1.3 ms | 2.2 ms |
| 流式一轮核心花的 CPU（p50） | 3.6 ms | 3.1 ms | 4.2 ms |

**改前改后**（内存量尺，核心连着一个终端界面，改前是叠在这一步下面的 LW-11，两边交替各量两遍，每遍三次取中位；数字是核心的堆加匿名内存的 PSS）：

| | 改前（两遍） | 改后（两遍） | 平均少了 |
|---|---|---|---|
| 空闲 | 4548、4804 kB | 4036、3824 kB | 约 0.75 MB |
| 说过一句以后 | 5664、5576 kB | 5008、4908 kB | 约 0.66 MB |

核心的线程数、线程栈、代码页都没有变化。

**实测**（沙箱，发行版核心）：

- 直接运行 `miyu core`：进程号不变，从启动到输出 `ready` 用了 13.6 ms；进程的环境里有 `GLIBC_TUNABLES=glibc.malloc.tcache_count=4` 和空的 `MIYU_GLIBC_TUNABLES`；启动日志记下 `heap tuned … tunables="glibc.malloc.tcache_count=4"`。
- 带着 `GLIBC_TUNABLES=glibc.malloc.arena_max=4` 直接运行：环境里是 `glibc.malloc.arena_max=4:glibc.malloc.tcache_count=4`，`MIYU_GLIBC_TUNABLES` 是 `glibc.malloc.arena_max=4`。
- 带着 `GLIBC_TUNABLES=glibc.malloc.tcache_count=0` 直接运行：环境保持原样，没有 `MIYU_GLIBC_TUNABLES`。
- `miyu core start`：拉起的核心的命令行是 `core`，环境里已经带着这两项。
- macOS、Windows 上没有这一步，没有手动实测；`crates/miyu/tests/tuned.rs` 在三平台 CI 上验证其他平台什么都不带。
