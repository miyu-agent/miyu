## 施工单 CS-11：在终端前台跑 `miyu core` 时只当前台壳，核心另开会话

状态：做完，等验收（分支 `step/CS-11-前台核心放下终端`，PR #66）。接 CS-10「要拍板的」：人在终端前台直接跑 `miyu core` 时，核心带着那个终端当控制终端，它起的 `zsh -i` 这类照继承抢得走前台。

### 经过

1. 2026-11-27 项目主人先定 CS-10 推荐的 C：核心起来时放下控制终端（`TIOCNOTTY`）。照做了第一版（`release_terminal`），Linux 全绿，macOS CI 上 Ctrl+C 停不下核心（60 秒没走）：XNU 上终端按键的信号走 `pgsignal(…, checkctty=1)`，只发给带 `P_CONTROLT` 的进程，`TIOCNOTTY` 正好清掉它；Linux 照进程组发，不看这个。放下终端、子进程打不开 `/dev/tty` 这两样在 macOS 上是成的。
2. 同日项目主人改定：A、B、C 都不选，改成「前台壳」（core1 查过别家，opencode v2 的 process-daemon 是同一个结构：前台的界面拉起 `setsid` 的守护进程）。第一版的 `release_terminal`、`TIOCNOTTY`、会话头的守卫都删掉，两个平台一个写法。

### 照的图纸

- 施工单 CS-10「要拍板的」；`internal/blueprint/core.md`「起来的先后」开头、「子进程随核心退出」；`tools/shell.md`「怎么走」。

### 改了什么

- `crates/miyu-core/src/front.rs`（新）：`foreground()`。这个进程有控制终端（`miyu_pipe::controlling_terminal`：能打开 `/dev/tty` 就算有）的，只当前台壳：
  - 照 CS-10 的 `new_session` 把真正的核心拉起到新会话里：程序是自己（`current_exe`），参数、环境变量原样带过去，标准输出、标准错误还接着这个终端，标准输入接空；
  - 先装好 `SIGINT`、`SIGTERM`、`SIGHUP`、`SIGQUIT` 的处理再拉起，收到的原样转给核心（`kill` 的安全接口）；
  - 核心退出，照它的退出码退出，被信号杀掉的照 shell 的写法交 128 加信号号；
  - 不开库、不拿锁、不装运行日志：数据根的锁、`core.log` 照常归真正的核心。不另写 `fork`，用现成的 `new_session`。
- `crates/miyu/src/main.rs`：`miyu core` 的两条路（头拉起的快路、照命令行树解析出来的）进核心以前先问 `foreground()`。头拉起的（`miyu core start`、终端界面、网页软件）、systemd、launchd 起的核心没有控制终端，不走前台壳；壳拉起的那一个也没有，不会再套一层。
- `crates/miyu-pipe/src/session.rs`：`new_session` 同一个命令设两次（测试夹具设一次、`connect_or_start` 的 `detach` 又设一次）的照样起得来：第二次 `setsid()` 回 `EPERM` 时自己已经是会话的头，当成了；只设了 `process_group` 的照旧起不来。门禁第二趟撞到（59 条测试红，拉起核心时 `EPERM`），加了单元测试 `twice_is_once`。
- `crates/miyu-pipe/src/terminal.rs`：只剩 `controlling_terminal`（`open("/dev/tty", O_RDWR | O_NOCTTY | O_CLOEXEC)` 成不成）。
- 测试：CS-10 那几条抢终端的命令在 `crates/miyu/tests/support/grab.rs`，`terminal.rs`、`terminal_front.rs` 共用。`support/mod.rs` 的 `core_staying` 在 Unix 上另开会话：人在终端里跑测试时测试进程有控制终端，不然测试拉起的 `miyu core` 会当前台壳，`kill` 杀到的是壳。
- 文档：蓝图 `core.md`「起来的先后」开头、守着它的；`tools/shell.md`；`ipc.md` 守着它的。

### 壳被 `SIGKILL` 时核心怎么办

照主人给的默认：核心不跟着走，同头拉起的核心（头没了照旧跑，等别的头来连，要停用 `miyu core stop`），写进了蓝图。没改成跟着走：能接的信号（Ctrl+C、`SIGTERM`、关终端的 `SIGHUP`、`SIGQUIT`）都转给了核心，剩下的只有 `SIGKILL`、壳自己崩了，这时核心和头拉起的一样是一个正常在跑的核心，不丢东西；要跟着走得让核心再认一个「壳还在」的信号（例如标准输入接一根管道、读到结尾就停），核心多一种起法。

### 不做什么

- 不动看门的、共用组、`basesystem` 起命令的那一段（V-48 一条不动）。
- Windows 不动：没有这一层。
- 不动 CS-9 改过的「停下」。

### 验收

1. `crates/miyu/tests/terminal_front.rs`（Unix）三条：伪终端里 `python3` 开新会话、`TIOCSCTTY`，换成交互式的 bash，测试往里敲 `miyu core`。
   - 前台是壳那一组（不是 bash、不是核心），测试从主端每 20 毫秒看一次，一直没换；照 `support/grab.rs` 跑的几条（`python3` 抢终端的小程序、`sh -c 'exec </dev/tty'`、`bash --norc -i`、`bash -lic`、`zsh -i`、`zsh -i -c`、`zsh -lic`，没有的跳过）都跑完、打不开 `/dev/tty`、印出 hi；命令问出来的会话号是核心的进程号（核心自己开了会话）。往主端写 Ctrl+C，核心有计划地停下（`stopped reason=signal`），之后在 bash 里 `echo $?` 是 0。
   - 关掉主端（终端关了）：bash 转发 `SIGHUP`，壳再转给核心，核心退出。
   - 核心被 `SIGKILL`：bash 里 `echo $?` 是 137。
2. 改前红：`foreground()` 一律交回 `None`（同 main 上的样子）时第一条红在「前台是壳」（前台就是核心自己）；同样的底子上第一版测试（不放下终端）红在行为上：`bash`、`bash_lic`、`zsh` 30 秒没跑完，前台换过五次。后两条（关终端、退出码）不走前台壳也是绿的，守的是壳没把这两样弄坏。改后四条（连 CS-10 的 `terminal.rs`）全绿，本机 0.65 秒。
3. CS-10 的 `terminal.rs` 照旧绿。
4. 门禁、Windows 版 clippy、三平台 CI。

### 实测

2026-11-27，本机 Linux（bash 5.3），这一步的 debug 版，`MIYU_HOME` 指临时目录，伪终端里交互式的 bash 敲 `miyu core`（`scratchpad/cs11/manual2.py`）：

| 情形 | 壳 | 核心 | 结果 |
|---|---|---|---|
| 按 Ctrl+C | 前台、在 bash 的会话里、带着终端 | 壳的子进程，自己的会话，`tty=0` | 0.05 秒核心、壳都退了，`echo $?` 是 0，日志 `stopped reason=signal` |
| 关掉终端 | 同上 | 同上 | 0.05 秒都退了 |
| `SIGKILL` 杀壳 | 同上 | 同上 | 壳没了，核心 3 秒后还在跑（照「壳没了核心照旧」），另发 `SIGTERM` 停下 |
