# BO-2　直接敲 `miyu` 打开界面时不读软件包清单、不搭命令行树

## 为什么

2026-11-27 的基准测试里，核心已经在运行时打开终端界面，到能打字是 31.9 毫秒；同一批里 LiteMiyu 是 10.8 毫秒，jcode 是 20.4 毫秒。

把这段时间拆开（本机，rc.4 的发行包，20 次的中位数）：到能打字 15.2 毫秒，其中约 6.6 毫秒花在启动器 `miyu` 上，然后才换成 `miyu-tui`。直接起 `miyu-tui`、不经启动器的，到能打字是 10.4 毫秒。

启动器在这 6.6 毫秒里做的事：

1. 把装着的软件包清单全读一遍、解析一遍（32 份 TOML），为的是找软件包加的子命令。
2. 搭整棵命令行树两次（一次列内置的子命令，一次解析），拼帮助页。
3. 解析出「没写子命令」以后，连上核心问 `ui.head`，再把全部清单读第二遍，找这个界面包的程序，换成它。

直接敲 `miyu` 是人最常用的一种写法。这种写法没有第一个词，第 1、2 步的结果一样都用不上：没有要转交的子命令，没有要印的帮助，没有要报的错。

## 怎么改

主程序一起来先看：一个参数都没有、标准输入和标准输出都是终端的，直接走打开界面的那一步（`miyu_cli::head::open`），第 1、2 步不做。

打开界面的那一步原封不动，照命令行树解析出「没写子命令」的也走同一个函数，所以两条路的行为相同：连核心、问 `ui.head`、照清单找界面包、没装时说的话、退出码都不变。不在终端里（被脚本调、接管道）的照旧走命令行树，印帮助、退出码 2。

没有动第 3 步里读第二遍清单的做法。只读 `ui.head` 那一个包的清单能再省一点，但读全部清单时会顺手查包和包之间撞没撞（撞了的不算装着），只读一份就查不了，行为会变。

## 改动

- `crates/miyu/src/main.rs`：`main` 里加快路；打开界面的那几行拎成 `head`，快路和命令行树的「没写子命令」共用。
- 蓝图 `cli/main.md`「怎么走」第 0、3 条。

## 验收

- 门禁全绿。行为由现成的 `crates/miyu/tests/heads.rs` 守着：在伪终端里敲 `miyu` 照 `ui.head` 拉起清单里的界面；`ui.head` 指着没装的说装了哪几个、退出码 1；不在终端里的印帮助、退出码 2。
- 同一棵工作树、同一条命令编两份核心（改过的和没改的），放进同一个发行包里，交替各量 4 组、每组 20 次，本机负载 3 到 5。这一遍改过的那一份还带着 BO-3、BO-4，那两步不碰启动。

| 指标 | 没改的 中位数 / 最小 | 改过的 中位数 / 最小 | 差 |
|---|---:|---:|---:|
| 到第一块输出 | 8.43 / 7.41 ms | 6.72 / 5.42 ms | −1.7 ms |
| 到能打字 | 14.05 / 11.97 ms | 12.45 / 10.28 ms | −1.6 ms |
| 到能打字，界面一侧的 CPU | 14.39 / 11.78 ms | 12.72 / 9.97 ms | −1.7 ms |
| 到能打字，核心的 CPU | 5.70 ms | 5.76 ms | 不变 |

四组里每一组改过的都比没改的快，各组的中位数不交叠（到第一块输出：没改的 8.27 到 8.63 毫秒，改过的 6.62 到 6.97 毫秒）。到能打字少了约一成。

更早在本机负载 17 到 39 时量过两遍（只改这一步的和没改的，各 7 组），那时每样都慢，差也大一些：到第一块输出少 2.2 到 3.7 毫秒。
