# BO-3　一轮任务当中不合库的写前日志

## 为什么

2026-11-27 的基准测试照真实的使用记录回放了 45 分钟。它量每一步的自身开销：模型答完上一步，到下一个请求发出，减去命令自己运行的时间。运行命令的那种步里，Miyu 有 7.8% 的步在回答到了以后多等约 10 毫秒，命令才开始跑；同一份剧本下 LiteMiyu 没有这种步。

把这些步照「这一步之前核心安静了多久」排开，是一个台阶：

| 这一步之前安静了多久 | 样本 | 回答到了以后到命令开始（中位数 / P90） | 超过 8 毫秒的步 |
|---|---:|---:|---:|
| 1.5 到 1.9 秒 | 118 | 2.9 / 3.4 ms | 0% |
| 2.05 到 2.2 秒 | 26 | 12.5 / 15.1 ms | 57.7% |
| 2.2 到 3 秒 | 68 | 13.4 / 14.8 ms | 97.1% |
| 3 秒以上 | 73 | 14.0 / 32.3 ms | 100% |

原因是闲时合回写前日志（施工 V-28）定的那 2 秒：

1. 库最后一次提交过去 2 秒，`miyu-wal` 线程把每个库的 `-wal` 合回主库、截成 0 字节。
2. `-wal` 空了以后，这个库的下一次写要先写一个新的日志头，并对它同步一次。`synchronous = NORMAL` 的库平时提交不同步，只有这一次要同步。
3. 回答一到，会话写下这一批事件，在同一个调用里接连提交会话索引（`sessions.db`）和用量汇总（`usage.db`）。两个库各等一次同步，写完命令才开始跑。

跟踪系统调用看到的就是这两次同步：一次约 9 毫秒，一次约 6 毫秒，之后才出现「开始运行这条命令」的那一行日志。

V-28 当时写的是「一轮任务里等模型的那几秒也算安静，那时合一次，几毫秒」。它没有算到合完以后下一步要付的这两次同步。真模型答一步通常是几秒到二十几秒，所以实际使用时几乎每一步都是这样：先合一遍（同步 `-wal`、同步主库），下一步再等两次同步。基准测试回放得比真人用得密，只有 7.8% 的步碰上。

## 怎么改

合和放页缓存分开等：

- 放页缓存（施工 LW-15、LW-29）不碰磁盘，照旧在库安静满 2 秒时做，接着把空出来的页还给系统。
- 合回、截短改成库安静满 30 秒才做。这 30 秒里只要又有一次提交或者读，就回去重新等。合完再放一遍合的时候读进来的页。

30 秒的理由：它要盖住平常的一步。答得更久的一步照旧会合一次，那一步本身就是几十秒，多的十来毫秒不算什么。一轮任务结束、人停下来以后，30 秒合上。

没有选的做法：

- 把索引、用量两个库的提交挪到后台线程。这样连平时每步约 0.5 毫秒的提交也离开了关键路径，但读这两个库的地方都要先等后台写完，改动面大；而且每一步还是会合一遍、多写几次盘。
- 合完以后马上往 `-wal` 里写一帧，把头的同步提前到空闲的时候做。这是拿多写盘换时间，`-wal` 也不再是 0 字节。

不变的：

- 崩溃安全不变，合还是 SQLite 自己的检查点。
- 好好退出时 SQLite 关上连接自己合回、删掉 `-wal`，这一条不变。
- 被杀、断电时留在数据根里的 `-wal`：原来安静 2 秒以后是 0 字节，现在要安静满 30 秒。没合的那一截最多到 SQLite 自己做检查点的约 4 MB，下次开库合回。
- 内存回落的时刻不变（2 秒）。

## 改动

- `crates/miyu-store/src/sqlite/idle.rs`：加 `shrink_all`（只放页缓存）和 `stays_quiet`（接着等一阵，有过一声就交回假）；`checkpoint_all` 照旧合完再放一遍。
- `crates/miyu-core/src/wal.rs`：`QUIET`（2 秒）到了只放页缓存；加 `MERGE`（30 秒），一直安静到它才合。
- `crates/miyu-store/src/sqlite/idle/tests.rs`：只放页缓存时 `-wal` 原样留着；接着等的时候有过一声就不合、不等到头；一声都没有的才合。
- 蓝图 `store.md`「怎么走」第 14 条第 1、5、7 款和文件表，`heap.md`、`core.md` 的文件表。

## 验收

- 门禁全绿。
- 同一个驱动、同一份剧本，改前改后各跑一遍：每一步之前故意隔 1.5、1.9、2.1、2.5、4 秒，量回答到了以后到命令开始的时间。实测见下表。

| 每步之前隔多久 | 改前：回答到了以后到命令开始（中位数 / P90） | 改后（中位数 / P90） |
|---:|---:|---:|
| 1.5 秒 | 6.3 / 13.9 ms | 5.1 / 15.9 ms |
| 1.9 秒 | 6.1 / 11.8 ms | 3.6 / 10.1 ms |
| 2.1 秒 | 57.7 / 236.3 ms | 2.5 / 4.5 ms |
| 2.5 秒 | 50.5 / 365.1 ms | 3.2 / 6.5 ms |
| 4 秒 | 30.3 / 276.4 ms | 4.4 / 7.2 ms |

每一格 39 步。量的时候本机有别的编译在跑，负载在 11 到 43 之间，盘也忙，所以改前在 2 秒以上的那几格比归因时量到的 13 毫秒大得多：这一处等的是落盘同步，盘越忙等得越久。改后 2 秒处的台阶没有了。

改前改后用的是同一棵工作树、同一条命令编的两份核心，放进同一个发行包，同一份剧本各跑一遍。
