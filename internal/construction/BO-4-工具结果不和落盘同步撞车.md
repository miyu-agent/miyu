# BO-4　工具结果的写入不和落盘同步撞车

## 为什么

2026-11-27 的基准测试照真实的使用记录回放，量每一步的自身开销。读文件的那种步，Miyu 是 9.4 毫秒，同一份剧本下 LiteMiyu 是 1.6 毫秒。多出来的 8 毫秒很稳，和一步里读几个文件无关。

在另一台测试机（基准测试用的那一台）上重现了：

| 条件 | 读文件的一步（中位数） | 运行命令的一步（中位数） |
|---|---:|---:|
| 一步接一步连着跑 | 1.5 ms | 3.1 ms |
| 每步之前隔 0.3 秒 | 10.8 ms | 9.9 ms |

核心自己的运行日志里，隔 0.3 秒的读文件那一步是这样的：回答到了，2 毫秒以后工具开始，工具当场跑完，然后过了 8 毫秒才发下一个请求。多出来的时间全在「工具跑完」到「发下一个请求」之间，这一段只做一件事：把工具的结果写进会话日志。

原因是两件事撞在一起：

1. 带工具调用的回复写进日志以后，马上在后台对日志做一次落盘同步（施工 V-18 定的提交点，施工 V-19 挪到后台）。工具不等它。
2. 工具的结果是往同一个文件后面追加。btrfs 上，同步的那一阵拿着这个文件的锁，这时候的追加要等同步做完。

读文件、找文件这类工具不到 1 毫秒就出结果，写结果的那一下正撞在同步上。盘闲了一会儿以后的头一次同步又特别慢。单独探盘（一个线程同步，另一个线程 0.5 毫秒以后往同一个文件追加）：

| 盘闲了多久 | 同步一次（中位数） | 追加被挡（中位数） |
|---:|---:|---:|
| 0 | 1.9 ms | 0.01 ms |
| 0.1 秒 | 3.6 ms | 0.6 ms |
| 0.3 秒 | 10.3 ms | 6.9 ms |
| 1 秒 | 10.3 ms | 6.7 ms |
| 2.5 秒 | 27.0 ms | 23.3 ms |

真模型答一步都不止 0.3 秒，所以实际使用时每一次读文件、找文件都这样等，模型想得越久等得越久。基准测试里运行命令的那种步不明显，是因为替身命令自己要跑一阵，同步在它跑着的时候做完了。

## 怎么改

带工具调用的那一批晚一点同步：等这一条回复要的工具都出了结果、结果写进去了再同步，一次盖住两批；最多等 100 毫秒，工具跑得更久的照旧在它跑着的时候同步。

- 只有「要同步的理由只是带了工具调用」的一批才等。外面交来的（人的话、桥的事件）、会话造好、一轮收尾、撤销、恢复，照旧马上同步。
- 等的时候，来了非同步不可的一批、有回应要等同步才能交、会话要停下，都马上做。
- 账只数最近那一条回复的调用。更早的回复被打断、没等到结果的，不让后面的一直等。

同步的次数不变（每步还是一次），只是挪了开始的时刻。

落盘的保证：同步本来就在后台做，工具不等它。断电以后日志里看不到「派过这个工具」的那一小段时间，原来是一次同步那么长，现在最多再多 100 毫秒；工具出结果快的，它的结果也一起同步了，比原来多保住一批。

100 毫秒的理由：读、找、改文件和大多数短命令在这以内出结果。还会撞上的只剩「正好在第 100 毫秒到同步做完之间出结果」的工具。

没有选的做法：

- 写日志也挪到后台线程，actor 不再等写。这样连锁都碰不到，但「程序崩了，写过的事件照样在」这一条保证要改，动的是会话存储的根基。
- 先把结果攒在内存里，等同步做完再写。同样会让一小段时间里的事件只在内存里。

## 改动

- `crates/miyu-session/src/actor/durable/later.rs`（新）：一批里有几个工具调用、几个结果、能不能等（`Seen`）；晚一点同步的账（`Later`）。
- `crates/miyu-session/src/actor/durable.rs`：`Syncing` 带上这本账。
- `crates/miyu-session/src/actor/store.rs`：写完一批照账定这一次同步等不等；派同步时要等的先等被叫、最多 100 毫秒；交扣着的回应、停下以前把等着的叫起来。
- 测试 `actor/durable/later/tests.rs`：带工具调用的回复等到结果都写进去才同步；非同步不可的一批、扣着的回应、停下会把它叫起来；碰外面的、一轮收尾的不等；被打断的回复不拖住后面的。

## 验收

- 门禁全绿。
- 同一个驱动、同一份剧本，改前改后各跑一遍（连着跑、每步之前隔 0.3 秒）。实测见下表。

本机，改前改后交替各跑两遍，每格 59 步。本机有别的编译在跑，负载在 9 到 28 之间；本机的盘也没有那台测试机那样「闲 0.3 秒以后同步就慢」得明显，所以改前的差距比那台机器上小。

| 条件 | 步 | 改前 中位数 / P90（两遍） | 改后 中位数 / P90（两遍） |
|---|---|---:|---:|
| 连着跑 | 读文件 | 1.4 / 1.9，2.2 / 3.4 ms | 2.0 / 2.7，1.5 / 1.9 ms |
| 每步之前隔 0.3 秒 | 读文件 | 4.3 / 10.1，4.5 / 113.2 ms | 2.8 / 4.1，2.4 / 2.7 ms |
| 每步之前隔 0.3 秒 | 运行命令，命令跑完到下一个请求 | 2.2 / 4.1，3.8 / 35.9 ms | 2.3 / 3.8，1.6 / 2.0 ms |

隔 0.3 秒的读文件一步回到了连着跑的水平。连着跑的不变。

### 三步合起来（BO-2、BO-3、BO-4）对改之前

同一棵工作树、同一条命令编两份核心（这三步都带着的，和这三步之前的 main），放进同一个发行包，同一份剧本交替各跑两遍，每格 49 步，本机负载 3 到 8。表里是自身开销的中位数 / P90，两遍各写一个。

| 每步之前隔多久 | 步 | 改之前 | 三步合起来 |
|---|---|---:|---:|
| 连着跑 | 读文件 | 1.5 / 1.8，1.4 / 1.9 ms | 1.2 / 1.6，1.3 / 1.6 ms |
| 连着跑 | 运行命令 | 3.3 / 3.9，2.9 / 3.3 ms | 2.5 / 2.9，2.3 / 2.9 ms |
| 0.3 秒 | 读文件 | 4.3 / 5.1，4.5 / 12.1 ms | 2.6 / 3.5，2.3 / 2.7 ms |
| 0.3 秒 | 运行命令 | 4.5 / 6.3，4.4 / 5.4 ms | 4.2 / 5.4，3.6 / 4.1 ms |
| 2.5 秒 | 读文件 | 29.6 / 101.0，16.7 / 83.3 ms | 3.5 / 4.8，3.0 / 4.0 ms |
