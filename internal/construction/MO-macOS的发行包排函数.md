## 施工单：macOS 的发行包排函数（链接器垫片照起点清单排，发版时探针跑一轮更新起点清单）

状态：定稿（2026-11-22）。第一版由轻量化的会话审过、改了重链的做法（见第 4 条「考虑过、没有选的」）；core1 审过第二版，照推荐定，补了下面「core1 审的时候补的」四条。编号就用 MO-1～MO-5，总表里单列一组，属于 LW 线（轻量化）。接着 LW-1（核心排函数）、LW-6（配着真的终端界面再录）、LW-14（剧本补上常用操作和抽记忆）。

### 目的

Linux x86_64 的发行包已经照第一次执行的先后排代码段，macOS 的还没有排。2026-11-22 在一台 M1 MacBook 上做的实验表明，排过以后核心空闲时程序自己的 `__TEXT` 常驻从 12.2 MB 降到 4.8 MB，终端界面从 5.1 MB 降到 2.4 MB；说过一句、九次工具调用两个状态，两个进程合计也各省 10 MB 左右（下面「量到的」）。这份施工单把它落进 `cargo xtask dist`，让 macos-aarch64 的发行包每次发版都排好。

macOS 上没有 Linux 那套录法：QEMU 的用户态模拟器只跑 Linux 的程序，调试器要开开发者模式，dtrace 要关掉系统完整性保护。实验用的是「页探针」：一个用 `DYLD_INSERT_LIBRARIES` 插进被测程序的动态库，进 `main` 以前把代码页设成不可访问，每碰到一页就记下是谁碰的、再放开这一页。它一遍只记得到每一页第一个碰它的函数，不像模拟器那样一遍录全，所以清单要一遍遍补。

这一版的做法分三件事：

1. **出厂的程序只让 cargo 链一次。** rustc 照常驱动链接，但用的链接器是一个「垫片」：它在这一次链接里把仓库里的名字清单换成这一次的符号，加上苹果链接器的 `-order_file`，再调真的 `cc`。一遍 LTO、一次链接，链完以后 rustc 该做的（去符号、签名）照常做。
2. **发版时探针只跑一轮**，跑的就是要发出去的那两个程序。这一轮的结果不改这一次的程序，只用来写出给下一次用的名字清单。
3. **清单靠一次次发版收敛。** 头一版起点清单在借来的 Mac 上手工迭代到收敛；之后每次发版（含 `-rc.N` 演练）补一轮，由做发版的会话提交回仓库。

### 蓝图改哪几节

- `perf.md`「排函数」：加一款「macOS」，写清楚和 Linux 不同的三处：链接器垫片照仓库里的名字清单排；探针代替模拟器，每次发版跑一轮、只更新起点清单；清单跨发版收敛。表里补上新加的文件和 `--probe` 参数。
- `perf.md` 的参数表：`--probe` 一行，写明它和 `--emulator` 二者择一。
- 设计 59（发版）里 macOS 那一台的步骤：多「编探针、带垫片编、核对、跑一轮探针、写出名字清单」几步；`--no-order` 照旧能关掉；构建产物多一份名字清单。

### 现在 Linux 上怎么走（新方案要接在上面）

1. `order::run`：写空清单，带 `MIYU_LINK_ORDER` 编核心（`crates/miyu/build.rs` 给 `miyu` 一个程序加 lld 的 `--symbol-ordering-file`），编量尺，`miyu-perf --order --emulator qemu-x86_64` 录第一段、第二段、抽记忆的那一段，照清单让 cargo 重链核心，用 `verify.rs` 核对。
2. 终端界面认清单的，带一份空清单编。
3. 搭好发行包目录以后，`order::staged` 对着它再录一遍（加 `--head`、`--head-order`；第三段核心在模拟器里，第四段终端界面在模拟器里，每段都逛一圈）。核心重链，终端界面带着它的清单再编；`dist.rs` 把两个程序重新拷进目录，各自核对。

Linux 的清单在同一次打包里现录现用。macOS 的清单这一次用的是仓库里的，现录的那一轮留给下一次。这是两边最大的不同。

### 做法

#### 1. 剧本照旧用量尺现有的，只把「放进模拟器」换成「插探针」

推荐：直接用 `miyu-perf --order` 现有的五段（第一段、第二段、配着终端界面的第三段和第四段、抽记忆的那一段），连同逛一圈，一步不删。理由：剧本覆盖的操作是 LW-14 一样样量出来的，两个系统上用户做的事一样；另起一套剧本要维护两份，终端界面改了字时还要改两处。

量尺要新加的：

1. **参数 `--probe <探针动态库>`**（`crates/miyu-perf/src/args.rs`）。它和 `--emulator` 二者择一，都要和 `--order` 一起写。用法字符串和 `perf.md` 的参数表同步改。
2. **一种起法 `Probed`**（`crates/miyu-perf/src/sandbox.rs`，和 `Traced` 并列，放进 `Launch`）：不换程序，只给被测进程加几个环境变量：`DYLD_INSERT_LIBRARIES=<探针>`、`MIYU_PAGES_OUT=<这一段的输出前缀>`、`MIYU_PAGES_PROGRAM=<被测程序的绝对路径>`，还有下面第 2 条的 `MIYU_PAGES_REARM_MS`。起来最多等多久用 `START_PATIENCE`，不用 `TRACED_PATIENCE`：程序以接近原生的速度跑。
3. **第四段**（`order/head.rs`）：现在是「`<模拟器> -d in_asm -D <日志> <终端界面>`」，macOS 上改成直接起终端界面、带上面几个变量，命令行参数和主程序加的环境变量照第三段看到的给（`Launched` 不用改）。
4. **装载起点**：Linux 读 `/proc/<pid>/maps`（`sandbox.rs` 的 `base_of`），macOS 没有 `/proc`。探针写下的地址已经减掉了滑动、换成符号表里的地址，所以 macOS 上不要装载起点：`Running::base` 和 `base_of` 只在 Linux 上编，`Probed` 那一路传 0。
5. **读探针的文件**（`order/listing.rs`）：加一个读法，读探针写的记录（格式见下面第 2 条），照记录的先后把碰的地址交给同一个 `Listing`；之后的换函数名、去重、照先后写清单都和 Linux 共用。一段里可能有几个进程的文件（每个进程一份），只读旁注里写着被测程序的那几份。另外要交出「碰过哪几页」，下面第 3 条去掉没用到的名字时用。
6. **符号表**：苹果的 `nm`（llvm-nm）认 `--defined-only --numeric-sort -S`，但 Mach-O 没有符号大小，`-S` 那一列全是 0（2026-11-22 在那台 M1 上核实过）。`Symbols::parse` 现在会把每个函数当成一个字节，几乎什么都对不上。要改成：大小是 0 的，用下一个函数的起点减去自己的起点（最后一个函数到 `__text` 的末尾）。`xtask/src/order/verify.rs` 的 `functions` 同样要这样补，不然核对时合计字节是 0，直接报错。两处用同一个算法，各自在 `tests.rs` 里加一份苹果 `nm` 的样例输出。
7. **写出的是什么**：Linux 上 `--order` 写的是这一遍执行过的全部函数。macOS 上同一个参数写的是探针这一遍看到的函数（照第一次看到的先后），另写一份碰过的页号。和起点清单合并、去掉没用到的都交给 xtask（下面第 3 条），量尺只管录。
8. **Linux 专有的几处要绕开**：`systemd-run --scope` 只在 Linux 上用（`scoped` 本来就是可选的）；`miyu_heap::launch::vars` 设的是 glibc 的环境变量，在 macOS 上设了也没有害处，照旧。量尺在 macOS 上能编，但 `--order` 这一路从来没有在 macOS 上跑过。伪终端（`order/terminal.rs`）、假模型的 TLS、逛一圈的屏幕识别在苹果的伪终端上有没有差别，要在 MO-2 里真跑一遍才知道。

实验用的 Python 脚本（`pss_mac.py`、`tracerun.py`、`iterate.sh`）一份都不进仓库。

#### 2. 探针

**放哪、怎么编**：C 源码放 `crates/miyu-perf/probe/pagetrace.c`（录清单归量尺管，它和 `order/` 放在一起）。xtask 在 macOS 上排函数时用 `cc -O2 -dynamiclib -o <target>/order/pagetrace.dylib crates/miyu-perf/probe/pagetrace.c` 编。macos-latest 自带 Xcode 的命令行工具，有 `cc`。仓库里不放编好的二进制。门禁在 macOS 的 CI 上编一次，免得它坏了到发版才发现。

**实验里改过、必须保留的三处**：

1. **只关 `__text` 整页的部分**，不关整个 `__TEXT` 段。原版关整个 `__TEXT` 时，核心起子进程会把 `__const`、`__cstring` 里的串直接交给内核；内核碰到不可访问的页不发信号，而是让系统调用失败（EFAULT），核心报「无法启动核心：Bad address (os error 14)」。只关 `__text` 以后，只读数据就记不到了；不过苹果的链接器本来也排不了它们。
2. **每个进程各写一个文件**：`<MIYU_PAGES_OUT>.<pid>`，旁边的 `.exe` 文件写着程序路径和前两个参数。主程序换成终端界面时进程号不变，探针在新的程序里重新初始化，这份文件也会重写，记录里就是终端界面的。
3. **定时落盘**：一个后台线程每 0.3 秒写一次，不靠 SIGUSR1。程序自己装了 SIGUSR1 的处理函数时，原来的写法会被顶掉。量尺停进程以前已经歇过 `QUIET`，最多丢最后 0.3 秒。

**正式版另加的**：

- `MIYU_PAGES_PROGRAM`：只在可执行文件的路径和它一样时才动手；别的进程（`miyu-sandbox`、`miyu-extract`、换成终端界面以前的主程序）载入了也什么都不做，核心起的沙盒子进程不受干扰。
- 写文件时先写临时文件再改名，量尺不会读到写了一半的文件。
- 只认 arm64（`__ss.__pc`）；x86_64（`__ss.__rip`）用 `#if` 留着，不测。

**发版时只跑一轮**：每次报这一轮新看到的清单外函数的个数，核心、终端界面各一个数。实验里从照 Linux 清单对过来的起点出发，第一轮是核心 167 个、终端界面 30 个；收敛以后核心停在 15 个左右，终端界面 3 个。核心超过 200 个或者终端界面超过 50 个时，提醒「起点清单太旧，这次排的效果打了折扣」，不报错。

**「定时重新关上」：推荐第一版就做。**

第一版草稿里我把它往后放，理由是当时每一轮都能重链、再跑，多跑几轮就能补齐。现在一次发版只有一轮，一轮能补多少直接决定清单收敛得多快，也决定正式版用的那份清单好到什么程度，所以值得在第一版就做。

- **怎么做**：后台线程每隔 `MIYU_PAGES_REARM_MS` 毫秒（推荐 20，没设的不重关，和实验时一样）把已经放开的 `__text` 页再全部设成不可访问。下一个碰到这一页的函数会再被记一次。一轮里每一页被记几百次，而不是一次。
- **代价**：实验里两个程序常用的代码页合起来约 470 页。每 20 毫秒全部重关一次，最多每秒约两万四千次缺页，每次在信号处理里花几微秒，估计慢一到两成。剧本里等屏幕上的字最多等 120 秒，慢这一点等得起。这个数是估的，要在借来的 Mac 上量。
- **记不全的仍然记不全**：同一页里放开以后接着执行的函数仍然看不到，所以它是抽样。不过跑得越久、重关越勤，漏掉的越少。只执行一次、又恰好跟在别的函数后面落在同一页上的函数，还是要靠下一次发版补。
- **格式怎么变**：每页只记一次时，记录数等于页数（一两千条）。重关以后同一个地址会被记很多次，所以探针在自己这边去重：一张开放寻址的散列表，以碰的地址为键，只在第一次见到这个地址时追加一条记录。记录照第一次见到的先后排，每条两个 64 位数：碰的地址、标志（执行还是读）。不再记 pc 和页号：页号能从地址算出来，pc 只有调试时有用。开头仍然是 `__TEXT` 的虚拟地址、页大小、记录数。记录的上限照 `__text` 的大小定，例如每 64 字节代码一条，核心约 34 万条、2.6 MB 的内存。满了就不再记，并在文件里标出「满了」，量尺读到这个标记时报一句。
- **记的不只是函数的开头**：从别的页返回到这一页时，碰的地址落在函数中间。换函数名时本来就是「地址落在哪个函数里」，不受影响。
- **验证**（放在下面「头一版起点清单」那件事里做）：拿照 Linux 清单对过来的起点，跑一轮带重关的，和实验里不带重关迭代 7 轮补到的那约 400 个函数比，看一轮能找到几成。找到的少于一半，就说明效果不如预期，再和 core1 商量。

#### 3. 起点清单

推荐：**仓库里放名字清单当起点**；每次发版，macOS 那一台在出厂的程序上跑一轮探针，产出新的名字清单；由做发版的会话把它提交回仓库。

- **放哪、写什么**：`xtask/order/macos-miyu.txt`、`xtask/order/macos-miyu-tui.txt`，一行一个名字。Rust 的函数写解开以后、不带 crate 哈希的名字（哈希跟着版本号、工具链变，名字不变），用 `rustc-demangle` 的不带哈希的写法（`{:#}`）；C 的函数（sqlite、ring 这些）写源码里的名字。名字后面的 `.llvm.<数字>`、`.<数字>` 这种编译器加的后缀去掉，同一个函数的几份拷贝都对得上。
- **头一版**：在借来的 Mac 上手工迭代到收敛（下面「拆步」里 MO-3 的前置任务）。不指望 CI 从 Linux 的清单一次次慢慢补：那样要好几次发版才收敛，前几次发出去的包只拿到约八成的效果。
- **每次发版产出新的**：xtask 把本轮的结果合进起点清单，写进 `target/dist/order/macos-miyu.txt`、`macos-miyu-tui.txt`。`release.yml` 把它们作为 macOS 那一台的构建产物传上去，不进 Release。合并的规则：
  1. 起点清单里的名字照原来的先后留着；
  2. 本轮看到的清单外函数照第一次看到的先后接在后面；
  3. 去掉落在「本轮一页都没被碰过」的页上的清单内名字。清单里的函数挤在代码段开头，一整页都没被碰过，说明这一页上的函数这一次都没有用到。没有这一条，清单只会越来越长，排在前面的那一段一个版本比一个版本宽。
- **谁提交、落后多少**：每次演练、正式发版以后，做发版的会话把构建产物里的两份提交回仓库（用 `cargo xtask order-seed <下载下来的目录>`，它只做拷贝和检查格式）。发版前总有一次 `-rc.N` 演练，演练产出的清单提交以后再打正式标签，所以正式版用的清单最多落后一次演练。不让 CI 自己推提交。
- **不更新也不会坏**：实验里拿 Linux 上录的清单（另一个系统，有些路径都不一样）也对上了 93.7%，拿到了约八成的效果。起点越旧，效果越打折扣，但不会出错。

另外两种起点都不推荐：

- **同一次发版里，Linux 那一台先录完、传给 macOS**：`release.yml` 的四台现在是并行的，要改成 macOS 等 linux-x86_64。Linux 那一台带模拟器，是四台里最慢的，整趟发版会变成两段时间相加；而且 Linux 的清单是另一个系统的路径，只对得上九成多。
- **从空清单开始**：每一轮最多给每个被碰过的页添一个函数（带重关会多一些），一次发版只有一轮，要很多次发版才收敛。

#### 4. 链接器垫片

**是什么**：两层。

1. 一个很薄的 shell 脚本，xtask 在 `<target>/order/shim/cc` 写出来，内容只有两种走法。环境变量 `MIYU_ORDER_NAMES` 没设时，`exec /usr/bin/cc "$@"`，原样交给真的链接器。设了的话，`exec <xtask 的程序> order-link "$@"`。xtask 程序的绝对路径在写脚本时由 `std::env::current_exe()` 填进去。
2. xtask 的子命令 `order-link`：做下面「垫片做的事」，最后调真的 `/usr/bin/cc`，参数是原来的参数加一个 `-Wl,-order_file,<这一次的符号清单>`。解名字和起点清单、合并用的是 xtask 里同一份 `rustc-demangle`，同一份代码（`xtask/src/order/seed.rs`）。

脚本叫 `cc`，是因为 rustc 照链接器的文件名猜它是哪一种：叫 `cc` 时，它给参数的方式和不写 `-C linker` 时一样。

**`MIYU_ORDER_NAMES` 写什么**：起点清单的绝对路径，另带 `MIYU_ORDER_REPORT=<报告文件>`。垫片把「清单几个名字、对上几个、写出几个符号、读符号表用了多久」写进报告，xtask 编完以后读出来印。不靠链接器的标准错误：rustc 在链接成功时不一定把它印出来。

**xtask 怎么让 rustc 用它**：

- 核心：`cargo rustc --release --locked -p miyu --bin miyu -- -C linker=<垫片>`，环境里带上两个变量。`-C linker` 只加在最后这一个程序上，不影响构建脚本和过程宏的链接；`MIYU_ORDER_NAMES` 也只有这一次链接用得到（构建脚本、过程宏不经垫片）。
- `miyu-sandbox`、`miyu-extract`：另跑一条 `cargo build --release --locked -p miyu-sandbox -p miyu-extract`，不排。
- 终端界面：在它的检出里 `cargo rustc --release --locked --bin miyu-tui -- -C linker=<垫片>`（经 `head_cargo`，不带外面的环境），只是另设上终端界面的那两个变量。

**和现在的 `cargo build` 是否等价**：我核对下来有一处可能不同，要在前置任务里核实。

- 现在是 `cargo build -p miyu -p miyu-sandbox -p miyu-extract` 一条。cargo 的特性解析（resolver 2）会把这次选中的几个包对共同依赖开的特性合在一起；拆成 `-p miyu` 单独编以后，如果 `miyu-sandbox`、`miyu-extract` 给某个共同依赖开了 `miyu` 没开的特性，`miyu` 拿到的那个依赖就会少几个特性，编出来的代码不一样。这一条只能实测：在借来的 Mac 上把两种编法各编一次（垫片不设 `MIYU_ORDER_NAMES`，原样调 `cc`），`cmp` 两份 `miyu`。一样的就说明这一份提交上拆开没有影响；也可以用 `cargo tree -e features` 两种写法比一遍特性，以后改依赖时重比。
- 如果不一样，改用 `cargo build -p miyu -p miyu-sandbox -p miyu-extract --config 'target.aarch64-apple-darwin.linker="<垫片>"'`。这样三个包仍然一起编，特性和现在一样。但这时 `miyu-sandbox`、`miyu-extract`、构建脚本也经过垫片（本机编本机时，`target.<三元组>.linker` 也管构建脚本），所以垫片要再认一下 `-o` 后面的输出：只有输出是 `deps/miyu-<哈希>` 的才排，别的照原样调 `cc`。
- 别的方面没有差别：`cargo rustc` 带的 `--release`、`--locked` 和 profile 都和 `cargo build` 一样；去符号、签名由 rustc 和链接器照常做；`--bin miyu` 只编这一个程序，库照旧作为依赖编。要注意的一件事：`-C linker` 改了 `miyu` 这个程序的编译参数，之后 `dist` 里不能再对 `-p miyu` 跑一次普通的 `cargo build`，不然它会重编、覆盖掉排过的那一份。现在的 `dist.rs` 没有这样做，写进代码注释防以后改坏。

**垫片怎么认出要排的输入**：

- rustc 给 `cc` 的参数里，要读的是落在 cargo 的 target 目录里的 `.o`（fat LTO 以后只有一个 `*-cgu.0.rcgu.o`，几十 MB，Rust 的代码连标准库都在里面），还有 rustc 临时目录（`deps/rustcXXXXXX/`）里的 `.rlib`、`.a`（C 写的依赖编出的本地库，例如 zstd、sqlite、ring 的 C 部分）。`-l`、`-L`、`-framework` 这些系统库不读。参数以 `@` 开头的是响应文件，先读开再认。
- 对这些输入跑 `nm --defined-only`（不带 `-n`、`-S`：这里只要名字），只留代码段的（`t`、`T`）。读归档时 `nm` 会逐个成员列出来；没被链接进去的成员也会列出来，这不要紧：清单里写了链接器用不到的符号，苹果的链接器跳过它们，实验里也没有警告。
- 要多久：核心的 LTO 目标文件约 40 MB、6 万多个符号。我估 `nm` 读它一两秒，几个本地库加起来不到一秒，没有实测。报告里记下实际用的时间。
- 也可以不读输入，先链一份临时的、对它跑 `nm`、再链一次。那就是一次链接变成两次，和这一版「只链一次」的原则相背，我不推荐；只在读输入的办法对不上（例如对上的比例比实验低很多）时再考虑。

**名字和符号怎么对**（`seed.rs`，都是纯函数，Linux 上也有单元测试）：

- Mach-O 的每个符号先去掉开头的一个下划线，再看：以 `_R` 开头的是 Rust 的，用 `rustc-demangle` 解成不带哈希的名字；别的（C 函数）原样就是名字。这样 C 函数多一个下划线的问题统一处理掉了。实验里漏了这一条，Linux 清单只对上 85%，补上以后是 93.7%。
- 名字后面的 `.llvm.<数字>`、`.<数字>` 后缀先去掉再对。
- 一个名字对上几个符号时（同名的局部函数、泛型展开解出来一样的、LTO 拷出的几份），都排进去，照它们在输入里出现的先后。
- 清单里对不上的名字跳过，报告里写对上的比例。对上的不到一半时，在 xtask 的输出里提醒「起点清单太旧」，不报错。
- 写出的符号清单用 Mach-O 的原名（带开头的下划线），一行一个，这是 `-order_file` 认的写法。

**垫片自己出错时让链接失败**：`nm` 不在、起点清单读不了、符号清单写不进、报告写不进时，`order-link` 在标准错误上说清楚是哪一样，退出码非零，不调真的 `cc`。rustc 会报链接失败，cargo 停下，`dist` 跟着停下。不悄悄地不排。

**核对排上了没有**：编完以后，`order::check` 对 `target/release/miyu`、终端界面的 `miyu-tui` 照旧用 `verify::check`：清单里的符号按字节九成以上落在代码段开头。这里补上第 1 条第 6 款说的「大小用下一个函数的起点算」，报错文字里的「排序清单是 lld 的参数」改成照系统说。核对用的清单是垫片写出的那份符号清单（不是名字清单）。cargo 在 release 里默认只去调试信息，符号表留着（实验里没排的核心有 6 万多个符号），所以拷进发行包目录以后再对发出去的那一份核对一次，和 Linux 一样。

**LiteMiyu 记过的坑**：让 cargo 照 profile 的 `strip = true` 一步做完时，苹果的链接器不照清单排。Miyu 的 release 没有写 `strip`，用的是默认的只去调试信息，这种情况下排不排得上没有实测过。前置任务里要核实，核对也会在每次打包时把它抓出来。

**考虑过、没有选的**：

- **抓下链接命令、直接重链迭代**（第一版草稿的推荐）：一次重链只要 0.3 秒，一次发版就能迭代到收敛。但出厂的程序不是 rustc 驱动链出来的，要靠「重放一个字节不差」证明等价，还要自己补上 rustc 链完以后做的事。我对这几处都没有把握，而它们只是为了在一次发版里收敛，不值得担。
- **`build.rs` 加 `-order_file`，每一轮经 cargo 重链**：产物由 cargo 编，但每一轮两个程序各做一次 fat LTO。macos-latest 上我估一次 10～15 分钟，迭代几轮就超过发版任务 90 分钟的时限。而且起点清单是名字，`build.rs` 拿不到这一次的符号，还得先编一遍。

#### 5. 流程里的先后

1. （取头、对版本以前）`order::tools()` 在 macOS 上找 `cc`、`nm`，编好探针，写好垫片，读一遍两份起点清单；缺了什么当场报。
2. 带垫片编核心的 `miyu`（第 4 条），读报告、印对上的比例；`miyu-sandbox`、`miyu-extract` 照旧编。
3. 带垫片编终端界面，同样读报告、印比例。
4. 编量尺 `miyu-perf`、网页，搭发行包目录（和现在一样）。
5. 核对：对发行包目录里的 `miyu`、`miyu-tui` 各跑一次 `order::check`。
6. 带探针跑一轮量尺的五段：`miyu-perf --order <核心的记录> --probe <探针> --head <目录里的 miyu-tui> --head-order <终端界面的记录> --miyu <目录里的 miyu> --resources <目录里的 resources/> …`。探针跑的就是要发出去的那两个程序，不另外重链；探针是运行时插进去的，不改程序文件。
7. 合并，写出下一次的名字清单（第 3 条），印两个程序各新看到几个清单外函数；太多的提醒。
8. 打压缩包、分包（和现在一样；分包里的 `miyu`、`miyu-tui` 就是第 2、3 步编出来的）。

代码放哪：

- `xtask/src/order.rs` 留作两个系统共用的入口，Linux 专有的部分不动。`SUPPORTED` 从一个布尔值改成「这台怎么排」：Linux x86_64 用模拟器，macOS aarch64 用垫片加探针，别的不排。
- 新加 `xtask/src/order/macos.rs`：写垫片、两条 `cargo rustc`、读报告、跑探针那一轮、写名字清单。
- 新加 `xtask/src/order/seed.rs`：名字和符号互换、合并、去掉没用到的页，都是纯函数。
- 新加 `xtask/src/order/link.rs`：`order-link` 子命令，在 `xtask/src/main.rs` 里登记。
- `dist.rs` 在两处分支：编核心、编终端界面的地方（macOS 走 `cargo rustc` 带垫片），搭好目录以后（Linux 走 `staged`，macOS 走核对加探针那一轮）。
- `cargo xtask perf` 在 macOS 上先不接排函数（它量的是闸门，闸门只在 Linux 上跑），见「不做什么」。

**终端界面仓库的 `build.rs` 一行都不用改**：垫片从外面经 `-C linker` 进来，对任何一个钉的提交都适用。xtask 在 macOS 上不设 `MIYU_LINK_ORDER`，它那里「别的系统设了这个变量就失败」的保护照旧有用。`tui_list` 用「`build.rs` 里有没有写 `MIYU_LINK_ORDER`」判断终端界面认不认清单，这个判断只在 Linux 上用。

#### 6. Intel 的 Mac

只做 macos-aarch64。发版只出这一种（`dist.rs` 的 `HOST` 里没有 macos-x86_64，`release.yml` 只有 `macos-latest`）。探针里留着 x86_64 读 pc 的那一行，不测、不接。

#### 7. 失败时怎么办

推荐：**和 Linux 一样，报错停下，不退回不排的包。** 理由：退回去的话，没排的包会悄悄发出去，内存涨了 10 MB 也没人知道。发版前本来就有 `-rc.N` 的演练，在演练里停下的代价只是改一次、再推一个标签。报错里写清楚是哪一步、临时怎么绕过。

- 垫片出错（`nm` 不在、清单读不了、写不进）：链接失败，打包停下。
- 起点清单对上的不到一半：不算失败，提醒「起点清单太旧」。
- `order::check` 不到九成：报错停下（多半是去符号或别的什么让链接器没照清单排）。
- 探针那一轮：探针编不过、起来以后一条都没记到（文件不在、记录数是 0）、剧本某一段等不到，都报错停下。记录数是 0 时，多半是程序带了加固运行时（hardened runtime），系统不让插库，报错里要写这个可能。
- 探针那一轮新看到的清单外函数太多：不算失败，提醒。
- 记录满了：不算失败，在输出里说一句。

探针那一轮不改这一次的程序，它停下会挡住一次本来排好了的发版。所以我另外建议加一个 `--no-probe`：程序照起点清单排，只是不跑这一轮、不写新的名字清单。它只给急着发版时手工用，`release.yml` 里默认不带。要不要加，见「要拍板的」。

#### 8. 验收

**自动的**（每次打包都做，写进 `cargo xtask dist`）：

1. 垫片的报告：两个程序都对上了一半以上的名字（不到的提醒）。
2. `order::check` 对发出去的 `miyu`、`miyu-tui`：清单里的符号按字节九成以上排在代码段开头。
3. 探针那一轮两个程序都有记录，名字清单写出来了，不是空的。
4. `cargo xtask dist-check` 照旧逐个查四个压缩包。

**内存**（手工做一次，在一台 M1 MacBook 上）：用 `-rc.N` 演练打出来的 macos-aarch64 一体包，和上一次没排的发行包比，用实验那套量法（它在仓库外面）。两份前后挨着量，同一时刻只量一份。量这几样：

- 三个状态：空闲、说过一句、九次工具调用，每个状态起三遍取中位。
- 两个进程（核心、终端界面）各自的程序 `__TEXT` 常驻、RSS、footprint。

达到的标准：起点清单是手工收敛过的那一版时，核心空闲的 `__TEXT` 常驻在 6.5 MB 以内，终端界面的在 4.5 MB 以内；footprint 不比没排的高（波动 ±0.3 MB）。终端界面原来定的是 3 MB 以内（实验的「迭代以后」是 4.8、2.4 MB，留出剧本不同、代码改过的余量），2026-11-23 前置任务以后改成 4.5 MB，原因见下面「MO-3 的前置任务量到的」。

### 要拍板的（技术细节，已按推荐定，2026-11-22 轻量化的会话定；core1 审的时候可以改）

- **xtask 加 `rustc-demangle` 依赖**：加。名字和符号互换用，垫片和写清单共用一份；它是 Rust 官方的 crate，标准库的回溯本来就用它，不会进发出去的程序。
- **怎么让 rustc 用垫片**：用 `--config 'target.aarch64-apple-darwin.linker="<垫片>"'`，三个包照现在的样子一起编，不拆成 `cargo rustc -p miyu`。理由：拆开编以后 cargo 给共同依赖合的特性可能不一样，就算这一次 `cmp` 一样，以后改依赖时也可能悄悄变；一起编就不用一直守着这件事。代价是另外两个程序和构建脚本也经过垫片，所以垫片照 `-o` 后面的输出认：只有输出是 `deps/miyu-<哈希>`（终端界面是 `deps/miyu_tui-<哈希>` 或者它实际的名字，前置任务里看一眼）的才排，别的原样调 `cc`。第 4 条里写的 `cargo rustc` 的做法作为没选的留着。
- **探针第一版就带「定时重新关上」**：做，理由见第 2 条。
- **`--no-probe`**：加，只给手工用，默认不带。
- **起点清单由谁提交回仓库**：做发版的会话在每次演练、正式发版以后提交，不让 CI 自己推提交。

### core1 审的时候补的（2026-11-22）

1. **探针只出现在量尺起的沙箱进程里。** `DYLD_INSERT_LIBRARIES` 只由量尺在录清单时设给它自己起的被测进程；发出去的程序、发行包里的任何启动脚本都不带这个变量，探针的动态库也不进发行包。`cargo xtask dist` 的核对加一项：搭好的发行包目录和打出来的压缩包里没有探针的动态库（照文件名和 Mach-O 的 `LC_ID_DYLIB` 认），有就报错停下。
2. **时间要有实测。** `release.yml` 里 macOS 那一台多出来的时间（编探针、垫片读符号表、带探针跑五段）在 MO-4 的施工单里写实测的数，离发版任务 90 分钟的时限要留出余量；不够就在 MO-4 里一起调时限并写明理由。
3. **起点清单的交接要写清楚。** MO-4 的施工单写明构建产物叫什么名字、在 `release.yml` 的哪一步传上去、`cargo xtask order-seed` 怎么用，做发版的会话照着在每次演练、正式发版以后把新的一份提交回来。
4. **借那台 M1 之前先和项目主人约时间。** 前置任务（头一版起点清单手工迭代到收敛）要在那台机器上编几遍、占满核，开工以前问清楚什么时候可以用，不在主人用着的时候占满它。MO-1 里只编探针、对着已有的被测程序试，不编整份源码，可以随时做。
5. `release.yml` 的那一步（MO-4）由轻量化的会话做，core1 审。

### 不做什么

- 不在一次发版里迭代、不重链：出厂的程序只由 cargo 链一次。
- 不排 `__const`、`__cstring`、`__eh_frame` 这些只读数据：苹果的链接器只照有名字的符号排。
- 不做 macos-x86_64。
- `cargo xtask perf` 在 macOS 上不接排函数：闸门只在 Linux 上量。
- 不改 release 的去符号设置：符号表照旧留着。要不要为了包小 10 MB 去掉，另议；去掉以后崩溃时的回溯就没有函数名了，内存不变（实验里 `__LINKEDIT` 的常驻都是 32 kB）。
- 不改核心、终端界面的产品代码；终端界面仓库什么都不改。

**MO-2 实际的做法和上面写的不一样的几处**（2026-11-23）：

### 风险

1. **默认的去符号设置下排不排得上。** LiteMiyu 实测过，`strip = true` 时苹果的链接器不照清单排，原因没有查清。Miyu 的 release 用的是默认的只去调试信息，实验里绕开了这一步（直接重链、自己去符号），没有测过「rustc 驱动链接、照默认设置去调试信息」时 `-order_file` 还管不管用。如果不管用，垫片这条路要么改 release 的 `strip` 设置，要么在垫片里处理。缓解：前置任务里先核实；每次打包的 `order::check` 不到九成就停下，不会悄悄发出没排的包。
2. **垫片认输入、对符号。** 垫片要从 rustc 给的参数里认出 LTO 目标文件和本地库，再从它们的符号表里对出名字。可能出问题的地方：rustc 换版本以后改用响应文件、改了临时目录的样子，或者目标文件里的局部符号名和链接以后的不一样（`-order_file` 对局部符号的写法有讲究）。表现是对上的比例掉下去，或者 `order::check` 不过。缓解：报告里每次印比例，比例比上一次低很多时就去查；核对不过时停下。
3. **拆开编以后特性不一样。** `cargo rustc -p miyu` 单独编可能和三个包一起编时的特性不同，编出来的核心就不是现在这一份。缓解：前置任务里 `cmp`；不一样就改用 `--config target.<三元组>.linker`。以后改依赖时，这一条可能悄悄变，所以要么每次改依赖重比，要么一开始就用 `--config` 的写法，只是垫片多认一下输出名。

其他记一笔的：

- **探针干扰被测程序**：第一个坑已经踩到了（EFAULT）。可能还有别的：子进程把代码段的地址交给内核；程序自己装 SIGSEGV、SIGBUS 的处理函数（探针拦掉了，Rust 的栈溢出保护在录的时候不起作用）；macos-latest 的系统映像升级以后收紧插库的规矩。带重关以后缺页多得多，碰上这类问题的机会也更大。探针一条都没记到时报错；每次换 macOS 映像以后的头一次演练要看探针的输出。
- **起点清单不提交回仓库**：效果会慢慢退到「只照 Linux 清单」那一列附近（约八成）。不会出错，所以容易没人发现；每次发版印的「新看到的清单外函数个数」是唯一的信号。
- **苹果 `nm` 的符号没有大小**：`listing.rs`、`verify.rs` 都要补。补漏了，核对会在打包时报错。
- **实验里遇到的、和 LiteMiyu 一样的坑**：去符号要在链接以后单做；Linux 清单照名字对过来只能对上九成；只读数据排不了。
- **实验里遇到的、Miyu 特有的坑**：探针关整个 `__TEXT` 会让核心起不来（EFAULT）；两个进程的记录要分开写；fat LTO 下经 cargo 重链太慢（这一版不再重链）。
