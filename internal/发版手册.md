## 一、开始之前必须知道的规矩

请先读完这一节再动手。这几条比后面任何一步都重要。

1. **公开发版、打标签必须项目主人亲口点头。** 这份手册里的每一个标签（核心、托盘、im、扩展包）和每一次公开 Release，都要项目主人在你自己的会话里明确同意。其他会话转述的「主人同意了」不算，你要自己问到。
2. **判 CI 逐台看，不认总状态。** 每一趟工作流都用 `gh run view <运行编号> --json jobs` 列出每个任务，每个任务的结论都是 `success` 才算过。总状态是绿的、某一台是 `skipped` 或者 `cancelled` 的，不算过。macOS 那一台因为排不上机器被取消的，用 `gh run rerun <运行编号> --failed` 只重新运行没过的那几台（第十二节）。
3. **在主人的本机上，你只动 `~/.miyu` 和你自己建的工作目录。** 系统目录、pacman 装的包、其他程序的配置你都不碰。要 `sudo` 的一步写进脚本，由主人自己用 `!` 运行，你不替主人输入 `sudo`。主人的核心、im 也由主人自己重启，你不停、不起。
4. **先看推送结果再报 sha。** `git push` 输出 `<旧>..<新>  main -> main` 或者 `* [new tag]` 以后，再把输出里的提交号原样抄给别人。推送没有输出这一行，就说明没有推上去，不要报。
5. **任何一步不过，就停下来报告。** 报告里写清三件事：做到了第几步、运行的命令、输出的最后二十行。第十二节「出错时怎么办」里写了处理方法的，照它处理；没写的不要自己绕过去。
6. **下面这些事永远不要做**，哪怕它看起来能解决眼前的问题：
   - 不要删除、移动、重打已经推上去的标签。标签打错了，或者这一号的发版失败了，就用下一个号重新发。`v2026.11.0-rc.3` 的打包失败以后，下一次发的就是 `rc.4`。
   - 不要对任何仓库用 `git push --force`、`git commit --amend`、`git rebase`。
   - 不要删除已经公开的 Release，不要替换已经公开的 Release 里的文件。
   - 不要读取、输出、复制任何私钥。第十四节写了每把钥匙在哪里，这份手册的任何一步都不需要看到私钥。
   - 不要用特权容器（`--privileged`）做实测。

## 二、名词和位置

| 名词 | 是什么 |
|---|---|
| 核心仓库 | `miyu-agent/miyu`。这份手册里的大部分命令在它的一份检出里运行。照 `AGENTS.md`，改动在从 `origin/main` 开的工作树里做 |
| 两个界面仓库（头） | 终端界面 `miyu-agent/miyu-tui`、网页界面 `miyu-agent/miyu-web`。「头」是连核心的界面程序 |
| `heads.toml` | 核心仓库根目录的文件，记着打包时取两个界面仓库的哪一个提交（`[tui]`、`[webui]` 的 `rev`） |
| 托盘仓库 | `miyu-agent/miyu-applet`。它自己打 deb、rpm、msi、dmg 和只装托盘的包，发在它自己的 Release 上 |
| 软件源仓库 | `miyu-agent/packages`。`collect.yml` 每天把官方仓库最新 Release 里的 `.miyu` 收进索引，发布在 `https://miyu-agent.github.io/packages/index.json` |
| `miyu-rev` | 软件源仓库根目录的文件，一行核心的提交号：收录程序和打包模板照这一版的核心读清单 |
| AUR 的检出 | `~/Documents/aur/<包名>/`，一个包一个 git 仓库（`ssh://aur@aur.archlinux.org/<包名>.git`） |
| Homebrew 的 tap | 待核实，见第十一节第 4 项 |
| 版本 | 核心 `Cargo.toml` 里 `[workspace.package]` 的 `version`，写法是 `年.月.这个月第几版`，从 0 数起，月和序号不补零，例如 `2026.11.0`。核心、终端、网页、托盘四件同一个版本号；扩展包各自用 semver |
| 正式版的标签 | `v` 加版本，例如 `v2026.11.0` |
| 预发布的标签 | 正式版的标签后面加 `-rc.N`，例如 `v2026.11.0-rc.5`。N 从 1 开始，每次加 1，失败烧掉的号不再用 |
| 发版钥匙 | 给 `SHA256SUMS` 签名的 Ed25519 钥匙，编号 `ca6918041857843c`。公钥写在 `packaging/install.sh` 的 `KEY_ID`、`KEY` 和 `crates/miyu-source/src/sign.rs` 的 `RELEASE` 里 |

发预发布时不需要改 `Cargo.toml`：`release.yml` 的「演练标签用标签里的版本」那一步，在 CI 的每台机器上临时把工作区版本改成标签里的版本、刷新 `Cargo.lock`，不提交。`cargo xtask dist` 取到两个头以后，也照这个 rc 号临时改头的版本（`xtask/src/dist/stamp.rs`）。所以一次预发布里所有程序都自报同一个 rc 号。

一次发布在 GitHub Release 上有十五个文件。下面用 `2026.11.0-rc.5` 举例：

| 文件 | 说明 |
|---|---|
| `miyu-2026.11.0-rc.5-linux-x86_64.tar.gz`、`…-linux-aarch64.tar.gz`、`…-macos-aarch64.tar.gz`、`…-windows-x86_64.zip` | 一体包，四种系统各一个。安装脚本、`miyu upgrade` 装的是它。里面有 `miyu`、`miyu-sandbox`、`miyu-extract`、`miyu-tui`、`miyu-web`，Linux 和 macOS 上另有看门的 `miyu-watchdog`，加上 `resources/`（带两个头的包文件夹）、`LICENSE`、`THIRD-PARTY-LICENSES.txt`、`README.txt` |
| `miyu-core-2026.11.0-rc.5-<系统>.tar.gz` | 只有核心的分包，Linux 两种和 macOS 各一个，给 AUR、Homebrew 打包用 |
| `tui-<终端版本>-<系统>.tar.gz` | 终端界面的分包，同上三种。版本照终端自己的清单，和核心同号 |
| `webui-<网页版本>-<系统>.tar.gz` | 网页界面的分包，同上三种 |
| `SHA256SUMS` | 上面十三个压缩包的校验和 |
| `SHA256SUMS.sig` | `SHA256SUMS` 的签名，是一个 JSON：`{"key":"<钥匙编号>","signature":"<base64>"}` |

另外，macOS 那一台还传一份构建产物 `order-macos-aarch64`（下一次用的排函数起点清单，留 30 天），它不进 Release，第 8 步（第十节）把它收回仓库。

## 四、步骤 1：要带的改动进 main，换钉

1. 确认要带的改动都已经合进核心仓库的 `main`

   ```bash
   git -C <核心检出> fetch origin
   git -C <核心检出> log --oneline origin/main -10
   ```

   如果还有要带的改动在分支上，先照 `AGENTS.md` 的施工规矩合进来，不要把没合的东西带进标签。

2. 找两个界面仓库 `main` 上 CI 逐台 `success` 的提交

   ```bash
   gh run list -R miyu-agent/miyu-tui --workflow ci.yml --branch main -L 5 --json databaseId,headSha,conclusion
   gh run view <运行编号> -R miyu-agent/miyu-tui --json jobs -q '.jobs[]|"\(.name) \(.conclusion)"'
   ```

   网页界面把 `miyu-agent/miyu-tui` 换成 `miyu-agent/miyu-web` 再查一遍。每一行都是 `success` 的那一趟，它的 `headSha` 就是可以钉的提交。

   正式版另外要查两个头的版本和核心一样（第十一节第 1 项）：

   ```bash
   gh api "repos/miyu-agent/miyu-tui/contents/Cargo.toml?ref=<终端的提交>" -q .content | base64 -d | grep -m1 '^version'
   gh api "repos/miyu-agent/miyu-tui/contents/tui/package.toml?ref=<终端的提交>" -q .content | base64 -d | grep -m1 '^version'
   gh api "repos/miyu-agent/miyu-web/contents/Cargo.toml?ref=<网页的提交>" -q .content | base64 -d | grep -m1 '^version'
   gh api "repos/miyu-agent/miyu-web/contents/webui/package.toml?ref=<网页的提交>" -q .content | base64 -d | grep -m1 '^version'
   ```

   四行都要是 `version = "<正式版的版本>"`。预发布不用查：rc 号由 `cargo xtask dist` 临时盖上。

3. 换钉，单独提交一个「build(钉)」

   在从 `origin/main` 开的工作树里，把 `heads.toml` 里 `[tui]`、`[webui]` 的 `rev` 换成上一步找到的两个完整提交号，其他内容不改。照 `AGENTS.md` 运行门禁 `cargo xtask check`，全过以后提交、合进 `main`、推送。提交信息的写法例如：

   ```text
   build(钉): rc.6 换钉，终端 bff5003f、网页 5f7fdd34 (<编号>)
   ```

   如果两个头钉的提交没有变，这一步可以跳过，标签就打在 `main` 最新的那个提交上。

   推送以后，照第一节第 4 条读 `git push` 的输出，记下 `main` 上这个提交的完整提交号，下面叫 `<提交>`。

## 五、步骤 2：等 main 上这个提交的 CI 逐台变绿

1. 找到这个提交的 CI

   ```bash
   gh run list -R miyu-agent/miyu --workflow ci.yml --commit <提交> --json databaseId,status,conclusion
   ```

2. 等它运行完，再逐台看

   ```bash
   gh run watch <运行编号> -R miyu-agent/miyu --interval 60 > /dev/null
   gh run view <运行编号> -R miyu-agent/miyu --json jobs -q '.jobs[]|"\(.name) \(.conclusion)"'
   ```

   `gh run watch` 建议放在后台运行，运行完会通知你，不要反复轮询。CI 一趟约 37 分钟。

   看到这六行都是 `success` 才算过：`tested`、`check (ubuntu-24.04)`、`check (macos-latest)`、`check (windows-latest)`、`randomized`、`perf`。

   如果有一台不是 `success`，就不能打标签。被取消的照第十二节处理；真的失败了，停下来报告。

## 六、步骤 3：打标签

**这一步做完以后不能撤销。** 标签一推上去，`release.yml` 就开始打包。推之前，确认项目主人已经在你的会话里同意发这个标签（第一节第 1 条）。

1. 确认这个号还没有用过

   ```bash
   gh release list -R miyu-agent/miyu -L 8
   git -C <核心检出> ls-remote --tags origin 'v2026.*'
   ```

   这次的号是已经用过的最大的号加 1。失败烧掉的号也算用过。

2. 确认标签和版本对得上

   ```bash
   git -C <核心检出> show <提交>:Cargo.toml | sed -n '/^\[workspace\.package\]/,/^\[/s/^version = "\(.*\)"$/\1/p'
   git -C <核心检出> merge-base --is-ancestor <提交> origin/main && echo 在main上
   ```

   第一条输出的是工作区的版本，标签要么是 `v<这个版本>`（正式版），要么是 `v<这个版本>-rc.N`（预发布）。对不上的标签会在 `release.yml` 的第一步「标签和版本对得上」停下，这个号就白烧了。正式版要先用 `cargo xtask version` 定号（第十一节第 1 项）。第二条要输出 `在main上`：标签不能打在以后会被删掉的分支提交上。

3. 打带注释的标签，推上去

   ```bash
   git -C <核心检出> tag -a <标签> -m <标签> <提交>
   git -C <核心检出> push origin <标签>
   ```

   算过：推送输出 `* [new tag]  <标签> -> <标签>`。

## 七、步骤 4：等 release.yml 出草稿

1. 找到这一趟

   ```bash
   gh run list -R miyu-agent/miyu --workflow release.yml -L 1
   ```

2. 等它运行完，逐台看

   ```bash
   gh run watch <运行编号> -R miyu-agent/miyu --interval 60 > /dev/null
   gh run view <运行编号> -R miyu-agent/miyu --json jobs -q '.jobs[]|"\(.name) \(.conclusion)"'
   ```

   一趟约 37 分钟，macOS 那一台最慢。看到这五行都是 `success` 才算过：`dist (ubuntu-24.04, linux-x86_64)`、`dist (ubuntu-24.04-arm, linux-aarch64)`、`dist (macos-latest, macos-aarch64)`、`dist (windows-latest, windows-x86_64)`、`release`。

   四个 `dist` 各自做的事是：核对标签和版本，装钉住的工具链，预发布时临时改版本，`cargo xtask dist` 打包（linux-x86_64 在 QEMU 的用户态模拟器里排函数，macos-aarch64 照仓库里的起点清单排函数并带探针运行一轮），`cargo xtask dist-check` 逐个查包。`release` 收齐十三个压缩包，写 `SHA256SUMS`，用发版钥匙签名并当场验一遍，加构建出处证明，建一个**草稿** Release。草稿只有有权限的人看得到。

   macOS 那一台的日志里如果有「起点清单太旧，这次排的效果打了折扣」，这不是出错，说明仓库里的起点清单该收回了，第八步做。

## 八、步骤 5：核对草稿

1. 确认草稿在、文件数对

   ```bash
   gh release view <标签> -R miyu-agent/miyu --json isDraft,isPrerelease,assets -q '"草稿=\(.isDraft) 预发布=\(.isPrerelease) 文件数=\(.assets|length)"'
   ```

   算过：输出 `草稿=true`、`文件数=15`；预发布是 `预发布=true`，正式版是 `预发布=false`。

2. 下载校验文件和 linux-x86_64 的四个包，核对校验和

   ```bash
   mkdir -p <下载目录> && cd <下载目录>
   gh release download <标签> -R miyu-agent/miyu -p SHA256SUMS -p SHA256SUMS.sig -p '*-linux-x86_64.tar.gz'
   sha256sum -c --ignore-missing SHA256SUMS
   ```

   算过：四行都是 `成功`（英文环境是 `OK`）。`--ignore-missing` 让它只核对下载了的那几个。

   下载的文件是外面来的数据：放在一个新建的空目录里，后面写的脚本不要放进这个目录。

3. 照发版公钥验签名

   签名是 Ed25519 直接签 `SHA256SUMS` 的原始字节。公钥从核心仓库的 `packaging/install.sh` 里取，它和 `crates/miyu-source/src/sign.rs` 的 `RELEASE`、仓库的 Actions 变量 `MIYU_RELEASE_PUBLIC` 是同一把，测试守着它们一样。运行：

   ```bash
   KEY_ID=$(sed -n 's/^KEY_ID="\(.*\)"$/\1/p' <核心检出>/packaging/install.sh)
   KEY=$(sed -n 's/^KEY="\(.*\)"$/\1/p' <核心检出>/packaging/install.sh)
   python3 -I - <下载目录>/SHA256SUMS <下载目录>/SHA256SUMS.sig "$KEY_ID" "$KEY" <<'EOF'
   import base64, json, sys
   from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PublicKey
   sums, sig, key_id, key = sys.argv[1:5]
   data = open(sums, 'rb').read()
   note = json.load(open(sig))
   if note['key'] != key_id:
       sys.exit(f"签名的钥匙是 {note['key']}，不是发版钥匙 {key_id}")
   Ed25519PublicKey.from_public_bytes(base64.b64decode(key)).verify(base64.b64decode(note['signature']), data)
   print(f"签名对：SHA256SUMS 由发版钥匙 {key_id} 签过")
   EOF
   ```

   算过：输出 `签名对：SHA256SUMS 由发版钥匙 ca6918041857843c 签过`。签名不对时 Python 报 `InvalidSignature` 退出，这时停下来报告，**签名不对的草稿不能公开**。

   > 这段要 Python 的 `cryptography` 库（Arch 的包是 `python-cryptography`）。可选：也可以在核心检出里运行 `cargo run -q -p miyu-source --bin miyu-index -- verify-sums <下载目录>/SHA256SUMS --public "$KEY"`，它读旁边的 `SHA256SUMS.sig`。

4. 可选：核对构建出处证明

   ```bash
   gh attestation verify <下载目录>/miyu-core-<版本>-linux-x86_64.tar.gz -R miyu-agent/miyu; echo "退出码 $?"
   ```

   算过：退出码是 0。

5. 解开看程序自报的版本和包里的东西

   ```bash
   x=$(mktemp -d)
   for f in <下载目录>/*-linux-x86_64.tar.gz; do tar -xzf "$f" -C "$x"; done
   "$x/miyu-<版本>-linux-x86_64/miyu" --version          # 应该是 miyu <版本>
   "$x/miyu-<版本>-linux-x86_64/miyu-tui" --version      # 应该是 miyu tui <版本>
   "$x/tui/bin/miyu-tui" --version                        # 同上
   grep -m1 '^version' "$x/tui/package.toml" "$x/webui/package.toml"   # 两行都是 version = "<版本>"
   ls "$x/miyu-<版本>-linux-x86_64/miyu-watchdog" "$x/miyu-core-<版本>-linux-x86_64/miyu-watchdog"
   ls "$x/webui/pages/resources/fonts" "$x/miyu-<版本>-linux-x86_64/resources/packages/webui/pages/resources/fonts"
   ```

   算过：两个 `--version` 都输出这一版；两个 `package.toml` 的版本都是这一版；两处 `miyu-watchdog` 都在；两处 `fonts` 目录里都有 `.woff2`、`.ttf` 字体文件。`miyu-web` 没有 `--version`，网页的版本看它的 `package.toml`。

   这几样有一样不对，就停下来报告，不要公开。

## 十、步骤 8 到步骤 10：排函数清单、扩展包、装到主人本机

### 步骤 8：收回 macOS 的排函数清单

macOS 的 `miyu`、`miyu-tui` 照仓库里 `xtask/order/macos-miyu.txt`、`macos-miyu-tui.txt` 这两份起点清单排函数。每次打包，macOS 那一台带页探针对着要发的程序运行一轮，合并出下一次用的起点清单，作为构建产物 `order-macos-aarch64` 传上去。CI 不自己推提交，所以每次预发布、正式版发完以后，由你把它收回仓库。不收的话不会出错，但是排函数的效果会一次次变差，日志里「核心本轮新看到 N 个清单外的函数」的 N 会越来越大。正式版用的清单要来自它之前那一次预发布，所以正式版的标签要打在收回了清单的提交上。

1. 下载这一趟的构建产物（只留 30 天）

   ```bash
   gh run download <发版那一趟的运行编号> -R miyu-agent/miyu -n order-macos-aarch64 -D <清单目录>
   ls <清单目录>        # macos-miyu.txt、macos-miyu-tui.txt
   ```

2. 在从 `origin/main` 开的工作树里收回、提交

   ```bash
   cargo xtask order-seed <清单目录>
   git diff --stat
   ```

   `order-seed` 只拷贝和检查格式，两份都过了才拷，每份输出一行 `xtask/order/<文件>：N 个名字（原来 M 个）`。`git diff --stat` 应该只有 `xtask/order/` 下的这两个文件。门禁全过以后提交、合进 `main`、推送，提交信息例如 `build(排函数): 收回 rc.6 的 macOS 起点清单 (<编号>)`。

### 步骤 9：扩展包进软件源

扩展包（例如 `antigravity`、`embed`）各自在自己的仓库打标签（`v` 加上它 `package.toml` 里的 `version`），它们的 `release.yml` 经软件源仓库的打包模板 `pack.yml` 把 `.miyu` 传进那个标签的 Release。打标签同样要项目主人点头。各平台的 `.miyu` 都出来以后，收进软件源：

```bash
gh workflow run collect.yml -R miyu-agent/packages
gh run list -R miyu-agent/packages --workflow collect.yml -L 1
gh run watch <运行编号> -R miyu-agent/packages --interval 30 > /dev/null
gh run view <运行编号> -R miyu-agent/packages --json jobs -q '.jobs[]|"\(.name) \(.conclusion)"'
```

`collect` 这一个任务是 `success` 以后，核对发布出来的索引和那个包的 Release 对得上：

```bash
repo=miyu-agent/<包的仓库>; id=<包编号>; tag=<包的标签>
curl -fsSL https://miyu-agent.github.io/packages/index.json | jq -r --arg id "$id" '.packages[]|select(.id==$id)|.version'
diff <(gh release view "$tag" -R "$repo" --json assets -q '.assets[]|select(.name|endswith(".miyu"))|"\(.name) \(.digest|ltrimstr("sha256:"))"' | sort) \
     <(curl -fsSL https://miyu-agent.github.io/packages/index.json | jq -r --arg id "$id" '.packages[]|select(.id==$id)|.files[]|"\(.url|split("/")|last) \(.sha256)"' | sort) \
  && echo "对得上：$id $tag"
```

算过：第一条输出这个包的新版本；第二条输出 `对得上：…`，没有 `diff` 的差异行。GitHub Pages 的索引有 600 秒的缓存，刚发布完看到的是旧的，等十分钟再查一遍再下结论。

**`collect` 在 `deploy-pages` 那一步失败（找不到 `github-pages` 的制品）时，不要用 `gh run rerun`。** 重新运行同一趟会让它里面出现两份制品，又失败一次（2026-11-27 遇到过）。要用 `gh workflow run collect.yml -R miyu-agent/packages` 新起一趟。

### 步骤 10：装到主人本机

主人要在自己的 Arch 上用这一版的时候做。做法是：你在自己的工作目录里把这次发布的分包做成 pacman 包，写一个脚本；主人自己运行这个脚本，脚本里停核心、备份数据根、`sudo pacman -U`、核对、再起核心。

1. 做包（不装）

   在 `~/.cache/miyu-remake/deploy-<月日>/` 下，照上一次的 `build.sh` 改版本号和四个提交号（核心、终端、网页、托盘）：
   - 从这次的 Release 下载 `miyu-core`、`tui`、`webui` 的 linux-x86_64 分包和 `SHA256SUMS`，照第八节核对校验和、签名，确认核心的提交就是标签指的那一个。核心、终端、网页不在本机编。
   - 托盘：如果托盘仓库有这一版的 Release，就用它的只装托盘的 `miyu-applet-<版本>-linux-x86_64.tar.gz`；如果没有，就在托盘仓库的一份拷贝（`git clone --local`）里把 `pins.toml` 的 `[core]` 和 `Cargo.toml` 里 `miyu-client` 的 `rev` 改成核心的标签提交、版本改成这一版，本机编、用 `packaging/solo.py` 打包。拷贝不提交，原仓库不碰。
   - 照核心仓库 `packaging/aur/<包>/PKGBUILD.in` 填好 `miyu-core`、`miyu-tui`、`miyu-webui`、`miyu-applet`、`miyu-agent` 五份（托盘有 Release 时可以直接用 `cargo xtask packaging`，见第十一节第 4 项），`makepkg -f -d` 出 pacman 包，不装。包的 sha256 和版本写进 `pkg/VERSIONS.txt`。
   - 退回用的上一版 pacman 包拷一份到 `rollback-pkg/`，核对 sha256。

2. 写主人运行的脚本

   照上一次的写在 `~/.cache/miyu-remake/owner-run/<日期>-deploy.sh`，哪一步不对就停下：先查一遍（账号、数据根、包的 sha256 和版本、现在装着的版本、终端界面已经关了、备份的空间够）→ 停托盘、网页、核心 → 把数据根 `~/.miyu` 整份备份 → `sudo pacman -U` → 核对每个包的版本和 `miyu --version` → `miyu pkg update`、`miyu pkg upgrade --yes`（每个扩展包原来开着还是关着，升级以后保持不变）→ 输出结果和退回的步骤。

3. 交给主人

   回复里给主人一行命令，主人用 `!` 运行，`sudo` 的密码由主人自己输入：

   ```bash
   bash $HOME/.cache/miyu-remake/owner-run/<日期>-deploy.sh
   ```

   主人运行完，你读脚本的输出核对版本。im 和托盘由主人自己重新打开。

## 十一、步骤 11：正式版另外要做的

正式版先照第四到第十节走一遍，下面这几项穿插在里面做。每一项开工之前都要项目主人点头。

1. **定号，头同号**（第四节之前）

   - 版本号由项目主人定。2026-11 的第一个正式版是 `2026.11.0`，核心的 `Cargo.toml` 现在已经是它；如果拖到 12 月，改成 `2026.12.0`（设计 59 第十节第 5 条）。
   - 改核心的版本用 `cargo xtask version <年.月.序号>`：它改 `[workspace.package] version`，运行 `cargo metadata` 让 `Cargo.lock` 跟着改，再读回来查一遍。它只收正式版的写法，不收 `-rc.N`。
   - 两个头的版本要和核心一样：终端的 `Cargo.toml` `[package]` 和 `tui/package.toml`，网页的 `Cargo.toml` `[workspace.package]` 和 `webui/package.toml`。如果不一样，`cargo xtask dist` 会停下，说先把 `heads.toml` 钉到定了号的提交。两个头怎么改版本由它们自己的仓库做（待核实：两个界面仓库各自改版本的流程）。托盘的 `Cargo.toml` 同样要是这个版本。
   - 正式版之前至少有一次同样代码的 `-rc.N`，而且那一次的排函数清单已经收回（第十节步骤 8）。

2. **写发版说明**（第九节步骤 6 之前）

   设计 59 第五节写的是「发版说明照 `docs/next-release-note.md` 的草稿整理」，但是核心仓库里现在没有这个文件（待核实：说明由谁写、写在哪）。说明里至少要有：从哪里装（安装脚本、AUR、Homebrew、托盘的安装包）、旧版用户怎么迁移（运行 `miyu migrate`）、怎么核对（`sha256sum -c SHA256SUMS`、`SHA256SUMS.sig`、`gh attestation verify`）。说明里不写内部的施工编号、机器名、地址。

3. **托盘出包**（核心公开以后）

   托盘仓库 `miyu-agent/miyu-applet` 的 `release.yml`（工作流名「打包」）在推 `v*` 标签时打完整的安装包（deb、rpm、msi、dmg，带核心和网页）和只装托盘的包（Linux 两种 tar.gz、macOS 的 zip），附件带 `SHA256SUMS`（不签名）。
   - 把 `pins.toml` 的 `[core]` `rev` 和 `Cargo.toml` 里 `miyu-client` 的 `rev` 都改成核心正式版标签指的提交（`pins.toml` 开头说两处要钉同一个提交）。`[web]` 的 `rev` 钉哪一个，待核实：`pins.toml` 的注释写的是「网页照它的 main，不照核心 heads.toml 里钉的那一版」。
   - 推一个 `step/` 分支，三台的「打包」都 `success`，出包手测；合进托盘的 `main`。
   - 在托盘 `main` 上打带注释的标签 `v<版本>`，推上去。版本要和托盘 `Cargo.toml` 的一样，`packaging/version.py --tag` 会查。
   - 注意：**托盘的 `release.yml` 推了标签就直接建公开的 Release，没有草稿这一步**（`gh release create … --prerelease --latest=false`），所以推标签就是公开发布。
   - 正式版要把它改成正式的：`gh release edit v<版本> -R miyu-agent/miyu-applet --prerelease=false`。要不要同时设成 Latest，待核实。

4. **AUR、Homebrew**（核心、托盘都公开以后，照 `RL-5-系统源打包.md`「发版那天」）

   1. 填模板

      ```bash
      mkdir -p <填的目录>/sums
      gh release download v<版本> -R miyu-agent/miyu -p SHA256SUMS -p SHA256SUMS.sig -D <填的目录>/sums
      # 照第八节第 3 步核过签名再用
      gh release download v<托盘版本> -R miyu-agent/miyu-applet -p SHA256SUMS -O <填的目录>/sums/APPLET-SHA256SUMS
      cargo xtask packaging v<版本> --sums <填的目录>/sums/SHA256SUMS --applet v<托盘版本> --applet-sums <填的目录>/sums/APPLET-SHA256SUMS --out <填的目录>/out
      ```

      算过：输出一串 `写好了 …`，有 `aur/` 下七份（`miyu-core`、`miyu-tui`、`miyu-webui`、`miyu-agent`、`miyu`、`miyu-applet` 的 `PKGBUILD`，`miyu-agent-git` 的 `PKGBUILD`，`miyu` 另有 `miyu.install`），`homebrew/Formula/` 下四份、`homebrew/Casks/miyu-applet.rb`。缺哪一份、版本对不上时它报错，什么都不写。

   2. 先真装一遍

      ```bash
      gh workflow run packaging-test.yml -R miyu-agent/miyu --ref main -f tag=v<版本> -f applet_tag=v<托盘版本>
      ```

      照第五节的办法等它、逐台看，`ubuntu-24.04`（Arch 容器里 `test-aur.sh install`）和 `macos-latest`（`test-brew.sh install`）两个任务都 `success` 才往下走。它会真下载、装、查、卸，还会造一个旧的 0.7.4 看 `-Syu` 能不能换成新的一整套。

   3. 推 AUR

      每个包一个 AUR 仓库。还没有的包，第一次推送就是在 AUR 上建这个包。推送是对外发布，由项目主人自己推，或者项目主人当面同意以后推。顺序是：`miyu-core`、`miyu-tui`、`miyu-webui`、`miyu-applet`、`miyu-agent`，然后是过渡包 `miyu`，最后 `miyu-agent-git`。`miyu-agent` 依赖前面四个，过渡包 `miyu` 依赖 `miyu-agent`，前面的没推上去时后面的装不上。每个包这样做：

      ```bash
      cd ~/Documents/aur
      [ -d <包> ] || git clone ssh://aur@aur.archlinux.org/<包>.git
      cp <填的目录>/out/aur/<包>/* <包>/
      cd <包> && makepkg --printsrcinfo > .SRCINFO
      git add PKGBUILD .SRCINFO        # 过渡包 miyu 另加 miyu.install
      git commit -m "<pkgver>"
      git push
      ```

      `pkgver` 是版本去掉 `-`：正式版就是 `2026.11.0`，预发布写成 `2026.11.0rc5` 这样。推完用克隆确认，不看有缓存的网页：

      ```bash
      rm -rf <检查目录> && git clone -q --depth 1 https://aur.archlinux.org/<包>.git <检查目录> && grep pkgver <检查目录>/.SRCINFO
      ```

      过渡包 `miyu` 推上去以后，旧版用户照常 `-Syu` 就会换成新版的一整套，装上时输出运行 `miyu migrate` 的提示。旧版的 `miyu-git` 照设计要删掉（待核实：在 AUR 上提删除请求的做法）。旧版的 `miyu-voice` 依赖 `miyu=0.7.4`，过渡包推上去以后它的依赖就对不上了（待核实：怎么处理，见第十五节）。

   4. paru、yay 那一问

      在干净的 Arch 容器里（`archlinux:latest`，不加特权）各装一次 paru、yay：先装旧的 `miyu` 0.7.4，再 `paru -Syu`、`yay -Syu`，看是不是不问冲突就换成了一整套、输出了 `miyu migrate` 的提示。照实写进发版说明。这一项要包真的在 AUR 上才测得到，还没有做过。

   5. 推 Homebrew

      把 `<填的目录>/out/homebrew/Formula/` 下的四份放进 tap 仓库的 `Formula/`，`Casks/miyu-applet.rb` 放进 `Casks/`，提交、推送，再在一台 Mac 上 `brew install` 合集确认装得上。

      **tap 是哪个仓库，待核实。** 模板和 `docs/zh/guide/install.md` 写的是 `miyu-agent/homebrew-miyu`（装法 `brew tap miyu-agent/miyu`、`brew install miyu-agent`、`brew install --cask miyu-applet`），但是 2026-11-28 GitHub 上没有这个仓库。组织里有的是 `miyu-agent/homebrew-tap`，里面现在只有 LiteMiyu 的配方和它自己的工作流。旧版的 tap `SHORiN-KiWATA/homebrew-miyu` 里的 `miyu` 配方要改成提示换新 tap（待核实：改成什么样）。

5. **软件源的 `miyu-rev` 要不要升**

   `miyu-rev` 只管收录程序和打包模板照哪一版的核心读清单和写索引。到 2026-11-28 为止，它每次升级都是因为核心认了清单的新写法（例如 `[[driver]]` 的新字段），扩展包要用这些写法才升。所以判断方法是看核心从 `miyu-rev` 到这次的标签，读清单、写索引的代码有没有改：

   ```bash
   rev=$(gh api repos/miyu-agent/packages/contents/miyu-rev -q .content | base64 -d | tr -d '[:space:]')
   git -C <核心检出> diff --stat "$rev"..<标签> -- crates/miyu-source crates/miyu-config
   ```

   如果没有输出，就不用升。如果有改动、而且是扩展包要用的新写法，在软件源仓库把 `miyu-rev` 改成标签指的提交（推送会自动触发一趟 `collect`）。正式版是不是一律钉到正式版的提交，待核实。

6. **im 同一天打标签**

   im 和赞助记录在 `miyu-agent/miyu-im` 一个仓库里，版本用 semver（2026-11-22 发到 `v0.3.5`）。它的 `release.yml` 推 `v*` 标签时经 `pack.yml` 打 `im`、`im-sponsor` 两个包，三种系统各一个 `.miyu`，传进那个标签的 Release。正式版那天：
   - 确认要发的 im 版本已经合进 im 的 `main`、CI 逐台 `success`；
   - 项目主人点头以后，在 im 的 `main` 上打带注释的标签 `v<im 的版本>`（两份清单里同一个 `version`），推上去；
   - 等 im 的 `release.yml` 逐台 `success`，照第十节步骤 9 收进软件源、核对索引。

   待核实：im 的 `Cargo.toml` 里钉的核心提交要不要换成核心正式版的提交；im 的发版说明由谁写。

7. **收回排函数清单**：正式版发完以后，照第十节步骤 8 再收回一次。

8. **其他**（设计 59 第五节，待核实具体做法）：
   - 官网的「下载」换成真的地址；
   - 主人装机脚本 `shorin-arch-setup`、`shorin-niri`、`shorin-dms-niri` 里改成新包名和新命令的三个分支合进去；
   - 这之后才处理 AUR、旧 tap 里旧的 `miyu`（AUR 上的 `miyu` 已经由过渡包接替，不删）。

## 十二、出错时怎么办

下面是已经遇到过的、或者工作流里写明了的情况。表里没有的，停下来报告。

| 现象 | 原因 | 处理 |
|---|---|---|
| `release.yml` 某个 `dist` 是 `cancelled`，没有开始运行 | GitHub 没有分到机器，macOS arm64 的机器紧张时会这样 | 等这一趟结束，运行 `gh run rerun <运行编号> -R miyu-agent/miyu --failed`，只重新运行没过的那几台，已经过了的不重做，标签不用动。再照第七节逐台看。重新运行两次还分不到机器，停下来报告 |
| CI 某一台是 `cancelled`，原因同上 | 同上 | 同上，`-R miyu-agent/miyu` 换成那个仓库 |
| 「标签和版本对得上」那一步报 `标签 … 和 Cargo.toml 的版本 … 对不上` | 标签打错了 | 这个号烧掉了，不删标签。先查清楚要发的版本，再用下一个号重新发 |
| 「标签和版本对得上」那一步报 `… 不是 年.月.序号` | 工作区的版本写法不对 | 用 `cargo xtask version` 定号、提交，用下一个号重新发 |
| `dist` 真的运行了、失败了，例如 2026-11-23 `rc.3` 的 linux-x86_64 在「对着发行包录清单」那一步失败 | 打包出错 | 停下来报告，附上 `gh run view <运行编号> -R miyu-agent/miyu --log-failed` 的最后四十行。不要删标签，修好以后用下一个号重新发 |
| `dist` 报头的版本和核心的不一样，要先把 `heads.toml` 钉到定了号的提交 | 正式版的头还是旧的版本号 | 回到第四节第 2 步，钉到两处版本都是这一版的提交，用下一个号重新发 |
| `release` 在「签名（发版钥匙）」那一步报 `没有密钥 MIYU_RELEASE_KEY` 或者 `没有变量 MIYU_RELEASE_PUBLIC` | 仓库的密钥或变量没有了 | 你处理不了。停下来告诉项目主人，钥匙由项目主人自己放进仓库的设置 |
| `release` 报 `… 的 Release 已经发布了，不覆盖` | 这个标签的 Release 已经公开 | 不要动它。这是在保护已经公开的文件 |
| `release` 因为其他原因失败，四个 `dist` 都过了 | 例如出处证明的服务临时出错 | `gh run rerun <运行编号> -R miyu-agent/miyu --failed` 只重新运行 `release`。如果同一个标签已经有草稿，它会改说明、覆盖上传，不会建第二个。重新运行一次还不过，停下来报告 |
| `sha256sum -c` 有一行不是 `成功`，或者签名验不过 | 下载坏了，或者文件不对 | 删掉下载目录重新下载一次。还是不对，停下来报告，不要公开 |
| `install-test` 某一台失败 | 安装脚本或者这次的包有问题 | 停下来报告，附上 `--log-failed` 的最后四十行。只是日志里有撞限流的 `WARNING` 不算失败 |
| `collect` 在 `deploy-pages` 失败，找不到 `github-pages` 的制品 | GitHub Pages 的部署偶尔出错 | 不要 `rerun`，用 `gh workflow run collect.yml -R miyu-agent/packages` 新起一趟 |
| 索引里的版本还是旧的 | GitHub Pages 有 600 秒的缓存 | 等十分钟再查一遍。还是旧的，看 `collect` 那一趟的摘要里这个包收没收到 |
| macOS 的日志里有「起点清单太旧」 | 仓库里的起点清单很久没有收回 | 不是出错。这一次照发，发完照第十节步骤 8 收回 |
| `cargo xtask order-seed` 报格式不对，一份都没拷 | 构建产物里的清单坏了 | 停下来报告。仓库里的清单没有动，这一次不收 |
| `cargo xtask packaging` 报缺哪一份、版本对不上 | `SHA256SUMS` 不是这一次的，或者托盘的版本不对 | 检查下载的是不是这次的标签，托盘的标签写对了没有 |

## 十三、发完以后才发现问题

已经公开的版本有问题时，不要删除它，也不要替换它的文件。做法是修好问题，用下一个号重新走一遍这份手册：预发布用下一个 `-rc.N`；正式版出了问题，修复版是 `年.月.序号` 的序号加 1（例如 `2026.11.1`），要不要发、什么时候发由项目主人决定。

已经推到 AUR、Homebrew 的，也照这个办法：发了修复版以后再推一次新的，不改已经推上去的那一版。

## 十四、关于密钥

这份手册的任何一步都不需要你看到私钥。

| 钥匙 | 在哪里 | 谁用 |
|---|---|---|
| 发版钥匙的私钥 | 核心仓库的 Actions 密钥 `MIYU_RELEASE_KEY` | `release.yml` 的「签名」那一步，填进 `MIYU_INDEX_KEY` 交给 `miyu-index sign-sums` |
| 发版钥匙的公钥 | 核心仓库的 Actions 变量 `MIYU_RELEASE_PUBLIC`；仓库里的 `packaging/install.sh`、`crates/miyu-source/src/sign.rs` | `release.yml` 签完当场验；安装脚本、`miyu upgrade` 核对签名；你在第八节核对签名 |
| 软件源的索引钥匙 | 软件源仓库的 Actions 密钥 `MIYU_INDEX_KEY`，和发版钥匙不是同一把 | `collect.yml` 给 `index.json` 签名 |
| AUR | 项目主人自己的 SSH 钥匙，加在项目主人的 AUR 账号上 | 推 AUR 由项目主人自己推，或者当面同意以后推 |
| Homebrew 的 tap | 不需要另外的钥匙，用有写权限的 GitHub 账号推 | 推配方 |

钥匙是项目主人自己生成、自己放进仓库设置的，私钥不经任何会话。钥匙失效时由项目主人自己更新。你可以用 `gh secret list -R miyu-agent/miyu` 看密钥的名字和更新时间，这条命令不会显示密钥的内容。
