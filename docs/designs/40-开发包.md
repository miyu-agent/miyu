## 开发包

给第三方作者写扩展用的两个小库：Python 一个、Rust 一个。它们不给扩展多出本事，扩展能做什么由协议定（`04-核心协议.md`、`05-内核接口.md`）；它们把每个扩展都要写一遍的那部分包起来：握手、一行一条的收发、几个调用同时来时照 `id` 对着回、`tool.cancel`、配置推送、标准输入读到头就退、退出码 1 的规矩。

状态：已定（2026-10-20：项目主人定了 Python、Rust 都做；主会话审过，第七节照推荐定）。

### 一、为什么要有

- 三个现有的扩展各写了一遍：miyu-memes、miyu-render 的 `src/wire.rs` 逐字一样（91 行），miyu-im 另写了一套。改协议的人要去三个仓库改三遍。
- 以后的脚本、扩展多半用 Python 写（2026-10-20 项目主人）。手写 JSON-RPC 容易漏：同时来的调用、取消、退出码 1、读到头就退，作者文档写了，不等于每个人都照做。
- 作者能离开 Miyu 测自己的扩展：开发包带一个假核心。

### 二、放在哪、什么许可证

- 一个仓库 `miyu-agent/miyu-sdk`，两个目录 `python/`、`rust/`，MIT（核心仓库 README：「给扩展用的开发包用 MIT」）。核心仓库不依赖它，Miyu 本体一个字节不多。
- 作者文档 `docs/authors/extensions.md` 加一节「用开发包写」，指过去；手写 JSON 的那个例子照旧留着：协议不挑语言。

### 三、Python

- **一个文件** `miyu_ext.py`，只用标准库（`json`、`sys`、`threading`），支持 Python 3.9 起（macOS 的命令行工具带的那一版）。作者把它拷进自己的包文件夹（放在程序旁边）就能 `import`，不用 pip，`miyu pkg install` 照常记哈希；想用 pip 装也行，同一份文件。
- 样子：

  ```python
  #!/usr/bin/env python3
  from miyu_ext import Extension

  ext = Extension()

  @ext.tool("hello_greet", "Greet someone by name.",
            {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]},
            access="read", display_name={"en": "Greet", "zh": "打招呼"}, subject="name")
  def greet(args, call):
      return f"{ext.config.get('hello.greeting', 'Hello')}, {args['name']}!"

  ext.run()
  ```

- 管的：`hello`（照回应的 `protocol` 核对主版本，对不上照退出码 1 的规矩在标准错误说清「这一版开发包认协议 N，核心是 M」再退：重启也没用，主会话审时加）、`provide`（登记的工具变了再发一次整份）、`tool.call` 每次一个线程（`call.cancelled` 看有没有被取消）、`command.call`、`method.call`（`@ext.command`、`@ext.method`）、`extension.config`（`ext.config` 跟着换、`@ext.on_config`）、`ext.call(method, params)` 调核心的方法（`blob.put`、`model.call` 这些）、读到头退出、`ext.fatal(msg)` 写标准错误、退出码 1。
- 回答：交字符串就是一块文字；交 `Result(blocks=…, error=…, data=…, detail=…)` 是完整的写法，格子同协议参考。
- 配合 X-34：带 `#!` 的一个 `bin/<名字>` 三个平台都能跑。

### 四、Rust

- crate `miyu-ext`：同步、只依赖 `serde`、`serde_json`，照 memes 的 `wire.rs` 收拢，加上握手（同样核对主版本）和分发；概念、名字和 Python 那份一一对应。
- memes、render、im 各自的仓库里换过去，是它们自己的施工，不在核心这边。

### 五、怎么测

- 两份各带一个假核心（进程里经管道演核心：握手、发 `tool.call`、取消、推配置、关标准输入），各自的测试照它跑；各带一个例子扩展。
- 不做两份共用的协议录像：跨仓库的测试框架，花的力气配不上（2026-10-20 项目主人定照表剪）。

### 六、不做的

- 别的语言（Node、Go）的开发包：等有作者要。
- 从协议的类型生成代码：协议的单一真相源在核心的 Rust 类型里（04 第二节），开发包只包作者常用的那几样，手写更短。
- 脚本工具（`scripts/` 下一次跑完的）的帮手：脚本的写法是开头注释加标准输入，用不着库；脚本交结构化结果另定（看了项目主人现有的 Python 脚本再说）。

### 七、决定

**SDK1. 一个仓库两个目录，MIT**

- **已定（草稿）**：`miyu-agent/miyu-sdk`，`python/`、`rust/`。
- 未选：两个仓库。说明、例子、发版各一份，两份对应的概念容易走岔。
- 重开条件：两份的发版节奏差得远。

**SDK2. Python 只用标准库、一个文件、能直接拷进包里**

- **已定（草稿）**：不用 pip 也能用；不带依赖，装包不用联网装别的。
- 未选：发成带依赖的 pip 包（`pydantic` 这类）。作者的机器、Windows 上的 Python 千差万别，Miyu 不替人装 Python 的东西（别人的活不揽）。
- 重开条件：标准库写不出的常用本事。

**SDK3. 线程，不用 asyncio**

- **已定（草稿）**：一次调用一个线程，作者写普通的函数。
- 未选：asyncio。作者要会 `async`，写错了整个扩展卡住；扩展的调用一次几个，线程够用。
- 重开条件：实测线程数成了瓶颈。
