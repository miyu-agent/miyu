## 整理会话

整理记忆（dream，`docs/blueprint/memory.md` 第七条）不再是记忆模块里看不见的一次性请求，改成跑在一个会话里：思考、流式的字、用量、用时、叫停都和正经会话走同一套事件和日志，头照画正文时间线的那一套画它。人叫的（`/dream`、`memory.dream`、`miyu memory dream`）和后台自己合的都这样。

状态：DS1 到 DS8 已定（2026-10-20 记忆的会话写，主会话对过；DS5 照主会话改），DS9 等项目主人定。方向项目主人 2026-10-20 定（经网页的会话转来）：「dream 的本质不就是一个特殊的会话吗？为什么和正经会话的日志完全不同？」，选了改成特殊会话；又补「不止是人叫的整理。自动的整理也是！」。施工照第五节。

### 一、现在是什么样

- 合并照批走（第七条）：一间一把锁（`Merges`），每批拼一段请求（指令、摘要、新记的、相关的、轮到重看的），经一次性入口 `OneShot::call_watching` 发 `memory.organizer`，读回一段 JSON（改的、作废的、摘要），核对过落进记忆日志（`ext.memory.saved`、`retired`、`summary`，最后 `merged`）。发以前记 `merging`，没合成记 `merge_failed`。
- 头看得到的：记忆日志那几行（R-12 上的 `memory` 流），整理时边写边推的 `memory.dreaming`（R-21）。看不到的：模型的思考、原样的回答、每批花了多少、想了多久。用量只进账号的 `usage.oneshot`（用途 `memory`）。
- 叫停：一间一份、叫它的会话一份的 `Hushes`（R-22、R-23），正在等模型的那一批放弃。

### 二、改成什么样

一趟整理开一个**整理会话**：

1. **一趟一个会话，一批一轮。** 合并任务起来时开会话（人叫的那一趟、后台的那一趟都是一趟），每一批是这个会话的一轮：合并任务以记忆模块的名义发一条 `message.user`（这一批拼好的请求，原样），内核照常开轮、发请求、流式收、记 `model.called`、`message.assistant`、`turn.ended`。批和批之间不带上下文：下一批开轮以前清空（同 `/clear`），请求和现在一样大。
2. **会话是裸的。** 没有人格、没有 core 那几行、没有工具、没有预设、记忆关着；模型照 `memory.organizer`。system 是空的，和现在的一次性请求逐字节一样。
3. **结果照旧落进记忆日志。** 轮结束、回答读得成的，核对过落 `saved`、`retired`、`summary`、`merged`，和现在一样；会话日志是这一趟的过程，记忆日志照旧是记忆的真相。`merging` 多一格 `session`，记忆页照它跳到那个会话。
4. **叫停就是打断这个会话的轮。** 打断了的那一轮 = 放弃的那一批（R-22 的规矩不变），记 `merge_failed`（`why: stopped`）。
5. **用量记在这个会话的账上。** 每一轮的 `model.called` 带用量、花费，照会话记进用量表；用途照会话的种类定，整理会话记 `memory`（第六节 DS5）。
6. **谁说的。** 每批那条 `message.user` 记成 `by: module`（记忆模块）。内核本来不让模块在没人看着的会话里开轮，只给 `kind` 是 `dream` 的开这个口子。
7. **不起标题、不进回合库、不压缩。** 起标题那一路照 `kind` 跳过，标题照规矩写（「整理记忆 · <人格名>」，头照连接的语言画也行）；回合索引（R-2）、抽取、联想都不碰它（记忆关着已经挡掉大半，再照 `kind` 明确跳过回合索引）；批间清空了到不了压缩的门槛，照 `kind` 再关掉自动压缩；空闲退出照常。
8. **归谁。** 会话的属主是那一间的主人：人格那一间照账号，会话那一间照那个会话的属主。多用户以前就是管理员。

头看到的：会话列表里多一种会话（`kind: "dream"`），点开就是一条正文时间线：每批一轮，思考可以展开，回答是这一批的决定。

### 三、别家

没有别家把后台的记忆整理做成会话的。Claude Code 的压缩、标题是同一个会话里的辅助请求，不另开会话；Letta 的 sleep-time agent 是另一个常驻的 agent，有自己的上下文和工具（`memory_rethink` 之类），记忆块是它用工具改的。我们取中间：会话是看得见的过程，决定照旧是一次读回、核对、落盘（DS3）。

### 四、和别的会话的关系

| | 子代理 | 支线 | 整理会话 |
|---|---|---|---|
| 怎么来的 | 她调 `subagent` | `session.fork` | 记忆模块开 |
| 父会话 | 有（`parent`） | 有 | 没有；人在会话里叫的记 `from` |
| 回报 | `child.reported` | 不回报 | 不回报：结果在记忆日志里 |
| 记忆 | 关 | 照父会话 | 关 |
| 工具 | 照父会话的预设 | 照父会话 | 没有 |
| 删父会话 | 连带删 | 连带删 | 不受影响 |

### 五、施工拆分（草案）

1. **D-1 内核、会话表：整理这种会话。** `session.created` 多 `kind: "dream"` 和 `dream: {persona | session, manual, from?}`；裸的快照（不拼人格、core 几行、场所说明，工具面空，记忆关）；模块在这种会话里开轮；不起标题、不进回合库、不自动压缩；用量表的用途照 `kind`；`session.list`、`sessions.changed` 的一项多 `kind`；她的 `sessions` 工具不列；留多久照 DS9。主会话做。
2. **D-2 记忆：合并跑在会话里。** 合并任务开会话、一批一轮、批间清空、轮结束读回答落盘；`merging` 多 `session`；叫停接打断（`/dream stop`、`/stop`、`memory.dream_stop`、Ctrl+C）；`memory.dream` 回应多 `session`；`usage.oneshot` 这一路合并不再用。记忆的会话做。
3. **D-3 网页、终端：画整理会话。** 记忆页列整理会话、正在跑的标出来；卡片里用正文时间线画；`/dream` 那一张跳到它。头的会话做。

R-26（整理时推思考、推用量）不做了：会话那一套都有。写了一半的放着不合。

### 出处

- 起因：网页的会话转来项目主人 2026-10-20 的两句话（第一段状态）。
- 子代理会话怎么造、记什么、怎么停、用量怎么记：`crates/miyu-endpoint/src/sessions.rs` 的 `Sessions::spawn`，`crates/miyu-session/src/open.rs`、`snapshot.rs`、`agents.rs` 的 `face`、`report.rs`，`crates/miyu-endpoint/src/sessions/orphans.rs`，`route/once.rs` 记账的那一段。
- 合并怎么跑：`docs/blueprint/memory.md` 第七条，`crates/miyu-session/src/memory/merge.rs`、`merge/land.rs`、`merge/hush.rs`。

### 六、决定

**DS1. 另立一种会话，不挂在发起的会话下面**

- **已定（2026-10-20 主会话对过）：`session.created` 多 `kind: "dream"`，不写 `parent`；人在会话里叫的记 `dream.from`（那个会话），照它接 `/stop`。**
- 为什么：后台的整理、`miyu memory dream`、网页记忆页的「整理」都没有发起的会话；记忆一间是照人格的，不属于哪个会话。挂成子会话的话，子代理那一套全会误伤：没有 `<父>/<任务>` 的 cause 要记 `WARN` 不回报，父会话日志里没有 `job.started` 的会被当成派到一半的空子会话收掉，删父会话连带删掉整理的过程。
- 未选：照子代理挂在发起的会话下面（主会话原来的倾向，对过以后放弃：复用会话表、视图、叫停那一整套，内核少开口子）。只有人在会话里叫的那一种挂得上，另两种还是要另立；回报、收孤儿、连带删都要加例外。
- 重开条件：整理以后要回报给叫它的会话（例如她自己叫整理、要等结果）。

**DS2. 一趟一个会话，一批一轮，批间清空**

- **已定（2026-10-20 主会话对过）：同上第二节第 1 条。**
- 为什么：一批的请求本来就自带要的全部（指令、摘要、这一批），带上前几批的只会多花；一趟一个会话，时间线上一眼看完这一趟。
- 未选 A：一批一个会话。一趟十几批就十几个会话，列表里刷屏。
- 未选 B：一趟一个会话、批间不清空。第 n 批带着前 n-1 批的请求和回答，越往后越贵，前几批的决定还会干扰后面的。
- 重开条件：无。

**DS3. 决定照旧是一段 JSON，不换成工具调用**

- **已定（2026-10-20 主会话对过）：这一步照旧读回答里的 JSON，核对过一起落；网页照 R-21 的 `memory.dreaming`（同一股流解析出来的一条条决定）画成一条条。**
- 为什么：R-16、R-19 的指令和核对是照「一次交回全部」量出来、调好的（误删 0、矛盾全对）；几道核对要一批的决定放在一起看（重复的两条不能都删）。换成工具调用：一批要两次请求（调工具、再收尾），输入翻倍；一条一条落就核对不了整批；指令要重写、测评集要重量。
- 未选：换成写记忆的工具（主会话的倾向：时间线上就是一条条工具调用，和正文一样）。好处是头不用另解析；代价如上。
- 重开条件：项目主人要时间线上是工具卡片；先在整理的测评集上量工具调用那一版不比现在差，再换。

**DS4. 叫停就是打断**

- **已定（2026-10-20 主会话对过）：`/dream stop`、`memory.dream_stop`、Ctrl+C、叫它的会话的 `/stop`（照 `dream.from`）都变成打断整理会话正在跑的那一轮；`Hushes` 留着当「谁能叫停」的登记，叫停时去打断。合完的批留着、打断的那一批放弃、下次再合，回执（R-22 再补）照旧。**
- 重开条件：无。

**DS5. 用量记在会话上，用途照会话的种类定**

- **已定（2026-10-20 主会话改）：内核事件不加格；执行器记用量表时照会话快照里的 `kind` 填用途，`dream` 记 `memory`。`usage.query` 照用途分的照旧分得出记忆花了多少，照会话分的也看得到这一趟。合并不再记 `usage.oneshot`。**
- 为什么：用途是会话级的事实，一轮里每一条都一样，记在每条 `model.called` 上是重复；照会话的种类定，以后别的特殊会话（例如压缩要是也做成会话）同一套。
- 未选 A：每条 `model.called` 带 `purpose: "memory"`（记忆的会话原来的推荐）。理由同上。
- 未选 B：不记用途。照用途看账时整理的花费会混进对话里。
- 重开条件：无。

**DS6. 后台的整理也走会话**

- **已定（项目主人 2026-10-20）：人叫的、后台自己合的都开整理会话。** `dream.manual` 分得出是哪一种。
- 抽取（第六条）不在这一份里：项目主人只说了整理。照样是一次性请求；要也改成会话，另说。

**DS7. 列表里有，默认不和对话混在一起**

- **已定（2026-10-20 主会话对过）：`session.list` 照常列整理会话，带 `kind`；头的主会话列表默认不列，记忆页、`/dream` 那一张卡片里列、能点开；她的 `sessions` 工具不列。删一个整理会话只删过程，记忆不动。**
- 为什么：后台一天合几趟，混在对话里刷屏；过程又要看得到。
- 重开条件：项目主人要在主列表里看到。

**DS8. 记忆日志那几行照留**

- **已定（2026-10-20 主会话对过）：`merging`、`merged`、`merge_failed` 照留（记忆页的进度、下次从哪接、连着失败几次都靠它们），`merging` 多 `session`；R-21 的 `memory.dreaming` 照留（DS3）。R-26 新加的推思考、推用量不做。**
- 重开条件：无。

**DS9. 留多久**

- **推荐：每一间只留最近 20 趟整理会话，多的照删会话的路删最早的（进回收处，同人删的）；正在跑的不删。** 设置项 `memory.dream_keep`（趟数，`0` 是不留：合完就删）。
- 为什么：后台一天合几趟，每趟日志里存着每批请求的原文（几十 KB 到几百 KB），不删会越攒越多；看过程多半只看最近几趟，记忆的真相在记忆日志里，删了过程不丢东西。照趟数比照天数好懂：不常聊的人格一个月才合一两趟，照 30 天删就一趟都不剩。
- 未选 A：留 30 天。理由同上。
- 未选 B：全留。
- 重开条件：项目主人要照天数，或者要全留。
