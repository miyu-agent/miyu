### 二、看一眼多什么

`package.install` 带 `preview: true` 的回应：

1. **`source`：这个包从哪来**（拍板点 1 定字段名，这里照推荐写）：

   | 值 | 什么时候 | 怎么定 |
   |---|---|---|
   | `official` | 从软件源装，条目是官方的 | 条目的 `official` 是真，而且是官方那个源（`feed.tier == Official`）。同现在 `glance.rs` 的判法 |
   | `community` | 从软件源装，别的情况 | 官方源里社区收录的；配置里自己加的源（`packages.sources.<名字>`）里的一律算社区：加源是信那把钥匙，包里的东西还是没人审过 |
   | `file` | 从本机包文件夹、`.miyu` 包文件装 | `package.install {"path"}`。从软件源缓存里拿 `.miyu` 手装的也是 `file`：核心看不出它原来是哪一条 |
   | `shipped` | 装回卸掉的出厂包 | `package.install {"package"}` 走装回那条路。出厂的本来就被信任，不审批 |

   - 原来那一格「源的名字」改叫 **`feed`**，和本地库 `desc` 的 `feed` 同名；从软件源装的都写（官方的写 `official`），别的没有。
   - 查过：终端（`miyu-tui`）、网页（`miyu-web`）都不读看一眼的 `source`，只有本仓库命令行的 `summary.rs` 读，跟着一起改。
   - 系统加装层（设计 60，施工 SD-1 还没做）以后装回被卸掉的系统加装包，写 `distro`。那一层不经 `miyu pkg install` 装，能力怎么批见拍板点 8。

2. **`capabilities`：要的能力**。形状照旧 `[{"id", "name", "summary"}]`，照能力表的先后。
   - 名字、一句说明是**核心的字**（`resources/core/human/<语言>.json` 的 `extensions/capabilities/<编号>`、`…/summary`，中、英、日三份十七项都齐），照连接的语言挑。包不能写自己的说法（拍板点 2）。
   - 每一项另加 **`held: true`**：这个包这一刻已经批过、这次装完照旧留着的（第四节第 3 条的「接着用」）。新装的没有；升级、重装的，命令行照它把新要的标出来。
   - 没声明能力的包没有这一格（照旧）。

3. **一起装的、推荐的也带**：`with` 的每一项、`recommends` 的每一项多 `source`、`feed`、`capabilities`（同上，写了的才有）。依赖可以来自不同的源（先在同一个源找，找不到再找官方的），各写各的。

4. 只照索引说的（从软件源装的看一眼不下载）：能力照索引条目的 `capabilities`，`held` 照装着的那一份算。

5. `package.upgrade` 带 `preview` 的：`upgrades` 每一项多 `source`、`feed`、`capabilities`（新版声明的、带 `held`），另多 `with`（这次一起装的新依赖，形状同上）。

### 四、能力装的时候就批

1. **协议**：`package.install`、`package.upgrade` 多一个参数 **`approve`**：`{"<编号>": ["<能力>", …], …}`，这一次装上的每个包（要装的、一起装的依赖、升级的）各写各的。
   - 写成按编号分的一张表，不写成一个 `true`：看一眼和真装是两条请求，中间索引可能刷新了、包文件夹可能被改了，新的一版多要的能力人没看过。照表批，表里没有的就是没批。
   - 名字不是十七个能力之一的、编号写法不对的 `bad_params`；是能力、但这一份清单没声明的不理（同一个道理：清单变了）；编号不是这一次装的不理。
   - 不写 `approve` 的照现在：装上，不批（老的头照旧能用，打开时再批）。
   - 批不完不拒装：表里没盖住的那几样照旧没批，打开时再问（第六节）。
2. **谁带**：
   - 命令行：答了「是」（或 `--yes`，拍板点 6），把看一眼时列出来的每个包的能力编号照原样带上；推荐的答了「是」的同样。
   - 她的工具（`miyu_tool::PackagesPort`）：`install`、`fetch`、`upgrade` 多一个参数，传问人的卡片上那一份（看一眼的回应）；完全放开那一级不问人，照样传看一眼的那一份（定了的 D：完全放开的直接做）。她开扩展（`enable`）照旧把声明的全批：装的时候已经批过，这一步多半什么都不用批。
   - 两个头：第三节的表。
3. **记什么、记在哪**：照旧记在 `etc/extensions.json` 的 `approved`，形状不变（包的编号到能力名的列表，照名字排、不重，空的不写）。不另记谁批的、什么时候批的：一个人用，批的就是主人；这份文件是 `deny_unknown_fields`，加格子要升写法的版本，旧核心就读不了了。装成以后照下面的算法重算这个包那一项：

   ```text
   接着用 = 旧的 approved[编号]，只在「来路没变」时才算，不然是空的
   新的 approved[编号] = (接着用 ∪ approve[编号]) ∩ 这一份清单声明的
   ```

   - **来路没变**：装之前本地库 `desc` 里记的和这次一样都是从软件源装的，而且 `feed`、`origin` 都一样。本机文件装的、换了源的、换了来源仓库的、本地库没记的都算变了，前面批过的不接着用。修第一节的毛病 4。
   - **和清单声明的取交集**：清单不再要的那几样从 `approved` 里去掉。修第一节的毛病 3（以后加回来要重新批）。
   - 照这个算法，`package.enable`、`extension.enable` 批的时候也改成记「交集」（现在记的是声明的全部，结果一样，只是写法统一）。
4. **什么时候写**：在 `packages/manage.rs` 的 `from_path` 里：
   - 拷文件之前先读出旧的 `desc`（要它判断来路）；
   - 拷进去、重读通过、本地库记好以后，在 `switch_packages` 拉起扩展**之前**，拿扩展开关那把锁（`one_at_a_time`）读、改、写 `extensions.json`；这样 `start = "always"` 的扩展一装上就批过了，`switch_packages` 照旧拉起（拍板点 4）。
   - 来路要传进去：从软件源装的一条路（`source/fetch.rs` 经 `archive::install`）现在是装完才 `set_origin`，改成把 `feed`、`origin` 一起交给 `from_path` 判断和记。
   - 装不成、撤回的不写。写不进的记一行 `WARN extension approval not recorded`，装照算成：这个包照旧停在「要批准」，打开时再批（第六节）。
5. **各种装法**：

   | 装法 | 怎么批 |
   |---|---|
   | 从软件源装（`install <编号>`、`-S`） | 确认那一屏的能力，答是就批；一起装的依赖同一屏、同一下 |
   | 推荐的（第二句答是） | 另印的那一段，答是就批 |
   | 从本机包文件夹、`.miyu` 装 | 确认那一屏，答是就批；来路算变了，前面批过的不接着用 |
   | 升级（`upgrade`、`-Su`） | 新要的列在确认屏上，答是就批（拍板点 5）；来源仓库变了的照旧不升（37 第四节第 6 条），所以升级一定是来路没变，旧的接着用 |
   | 装回出厂的 | 不批：出厂的算全批过（照旧） |
   | `--yes`、`--noconfirm` | 照拍板点 6 |
   | 标准输入关着、没写 `--yes` | 照旧不装（「已取消：没有收到确认」） |
   | 她的工具 | 照她装包那张权限表：工作区问人一次（卡片就是确认屏），完全放开直接批，只读不能装 |
   | 系统加装层（SD-1 以后） | 不经 Miyu 装，没有确认那一下：拍板点 8 |

6. **之后不再问**：批全了的包 `unapproved` 是空的，`extension.enable`、`package.enable` 不带 `approve` 也开得了；命令行装好以后问「现在启用？」照旧（`start = "manual"` 的装完默认不开，37 第四节第 4 条不变），答是发 `package.enable`，仍然带上看一眼的那几个能力（装的时候写不进的，这一下补上；已经批过的什么都不变）。
7. **撤销**：拍板点 7。

### 五、和现在的打开时批怎么并存

1. **打开时批照旧留着，当兜底**：`extension.enable`、`package.enable` 的 `approve`，扩展的 `unapproved`、`needs_approval`，网页扩展页的「批准并开启」都不动。走到它的只剩这几种：
   - PK-3 以前装的、装了没开过的；
   - 没带 `approve` 装的（老的头，例如没跟上的网页）；
   - 确认屏上的那一份和真装的不一样，多出来的那几样；
   - 装的时候写不进 `extensions.json` 的；
   - 系统加装层的（拍板点 8 照推荐）。
2. **旧数据不迁**：已经批过的照旧在 `approved` 里，算法一样认；装了没批的照旧没批，下次打开时问。不在核心起来时替装着的包补批：那等于没问就批了。
3. 第一节的几处毛病一起修：毛病 1 随第二节第 1 条（字段改名）；毛病 2 随第三节「推荐的」；毛病 3、4 随第四节第 3 条的算法（下一次装、升级、打开时生效，不另扫一遍旧数据）；毛病 5 归网页，通知时写上。
4. 不在这一步的：
   - 装着的包 `package.list`、`package.info` 的 `from` 还是 `shipped`、`official`、`local` 三种，从软件源装的社区包也写 `official`（`packages/fill.rs` 的注释写着「以后有了社区软件源再分出 community」）。要分得记下装的时候是不是官方的条目，本地库 `desc` 多一格；和这一步的看一眼不相干，另排。
   - 扩展进程关进沙盒：照旧另做（`extensions.md`「还没有的」）。没关进沙盒以前，`network`、`fs.*` 挡的只是经核心做的事，所以第三节「注意」那句要写「不在沙盒里」。

### 八、要拍板的

| | 问的 | 选项 | 推荐 |
|---|---|---|---|
| 1 | 看一眼里「从哪来」那一格叫什么 | A. 叫 `source`（派工单写的），现在那一格「源的名字」改叫 `feed`；B. `source` 照旧是源的名字，另开一格（比如 `trust`） | **A**：只有本仓库命令行读旧的 `source`（终端、网页都不读），改得动；`feed` 和本地库 `desc` 同名；B 让同一份回应里两格意思打架，旧的 `source` 本来就把「官方源」和「官方包」混在一起（第一节毛病 1） |
| 2 | 能力的名字、说明用谁的字 | A. 只用核心的字；B. 核心的字，另让作者在清单里写一句「为什么要」，确认屏标明是作者说的；C. 作者自己写 | **A**：十七个能力是核心定的，它能做什么核心说了算；作者的字能把「替主人说话」说轻；三种语言的字都齐。要「为什么」以后再加 B，不影响这一步 |
| 3 | 社区、本机文件的「注意」写多少 | A. 只写「这个包没经过官方审核」；B. 再接「它带的程序会以你的身份在这台机器上跑，不在沙盒里」（只给带程序、MCP 服务、脚本的包） | **B**：扩展还没关进沙盒，没批 `network` 也照样能自己联网；只写「没审核」、再列「联网」这样的能力，人会以为没列的它就做不了 |
| 4 | `start = "always"` 的扩展装上就批了，装好当场跑不跑 | A. 跑：作者写了常驻，人在装的时候批过了；B. 装上一律先关着（开关写成关），要人再开一次 | **A**：表情包、渲染这类常驻扩展装上就该能用；`manual` 的照旧装完默认不开，命令行照旧问「现在启用？」 |
| 5 | 升级时新多要的能力 | A. 升级确认屏列出新要的，答是就批（同装）；B. 升级不批，新版停在「要批准」等人去开（现在的样子） | **A**：和装一个规矩；B 下升级完扩展就停了，人还得去软件包页找它 |
| 6 | `--yes`、`--noconfirm` 批不批 | A. 批：定了的 B「`--yes` 直接当是」；B. `install --yes` 批，`upgrade --yes` 不批新多的能力；C. 都不批，`--yes` 只装，打开时再批 | **A**：和定了的 B 一致，写 `--yes` 的人知道自己在跳过确认。B 防的是「作者账号被盗、新版多要能力、定时脚本 `-Syu --yes`」这一种，但同一个被盗的新版不多要能力、只改代码，照样跑起来，挡得很窄 |
| 7 | 撤销批准有没有入口 | A. 不做，卸掉就是撤销（现在也只有这一条）；B. `package.disable`、`extension.disable` 加 `revoke: true`，命令行 `miyu pkg disable --revoke`，网页关的时候能勾；C. 关掉就清批准，下次开再问 | **A**：少批一样扩展就整个不拉起，部分撤销没意义；想不让它跑关掉就行，想清干净就卸。真有人要再做 B |
| 8 | 系统加装层（设计 60，施工 SD-1）的扩展怎么批 | A. 照现在打开时批：Miyu 里没有装的那一下；B. 和出厂的一样算批过：系统源各家自己审（设计 60 第四节第 3 条） | **A**：AUR 这类系统源也是没人替 Miyu 审，核心又看不到装的那一下；打开时批的那一套本来就留着，不用另做。SD-1 做的时候照这一条 |

**定了的**（core1 2026-11-05，第 3、6 条项目主人在旁边定的）：八条都照 A/推荐。

1. A：「从哪来」叫 `source`，原来那格「源的名字」改名 `feed`。
2. A：能力的名字、说明只用核心写的字。
3. B：社区、本机文件写「这个包没经过官方审核」；带程序、MCP 服务或脚本的再加「它带的程序会以你的身份在这台机器上跑，不在沙盒里」。这一句单放一个 key、写成好删的：项目主人同天定了扩展沙盒在首个正式版前做（设计 62），**设计 62 落地后改**这一句。
4. A：`always` 的装好当场跑。
5. A：升级确认屏列出新多要的能力，答「是」就批。
6. A：`--yes`、`--noconfirm` 都算批；输出里照样列出批了哪些。
7. A：不做撤销入口，卸掉就是撤销。
8. A：系统加装层照现在打开时批。
