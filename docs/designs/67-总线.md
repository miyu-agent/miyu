## 用户态总线

包声明自己提供哪个名字（`provides`，一个名字只有一家；`plugs`，可以多家并存），头和别的包照名字找、照名字调，核心查到是谁、转过去；谁也不写死谁的包名。照 Linux 的 D-Bus：系统调用进内核，不走 D-Bus；D-Bus 只管用户态程序之间互相找、互相调。Miyu 一样：核心协议里的专门方法（会话、回合、事件、存储、工具、驱动、挂接点）不动，总线只管包和包、头和包之间的服务。从现有的 `package.call`（施工 F-6 中、X-18）升级而来。

状态：定稿（2026-11-09）。项目主人 2026-11-09 定了方向：做用户态总线，避免包之间硬依赖（第十节 B1 到 B3）；第九节的技术项 core1 同一天研究后拍板（B4 到 B9）。第一个用户是语音（`20-语音.md`），总线 BUS-2 合了语音才施工。时机：首个正式版之前（项目主人 2026-11-09 改定：「这关乎到后续的社区扩展如何制作，是大改动」；语音同样发版前做）。第一节、第五节的现状照 main `d0dec0c49` 的代码盘的。

### 一、为什么

**现在「找到对方并调它」有好几套找法**：

| 调什么 | 怎么找到对方 |
|---|---|
| 核心自己的功能 | 方法名，如 `session.send` |
| 工具 | 工具名，有登记和装包时的撞名检查 |
| 模型驱动 | 供应商配置里写明 `driver`（设计 66） |
| 斜杠命令、界面块 | 各自登记的名字 |
| 别的包的方法 | **包名加方法名**：`package.call {"package", "method", "params"?}` |

最后一种写死了对方是谁。现有的几处：
- `miyu-im/crates/miyu-im/src/core/route/long.rs:27`：长消息转图写死 `("miyu-render", "markdown")`；
- `miyu-memes/src/save.rs:153`：取图写死调 `miyu-im` 的 `chat.media`；
- `miyu-im/crates/miyu-im-sponsor/src/main.rs:175`：写死调 `miyu-im` 的 `chat.venue`。

社区要是做了一个更好的渲染包，im 的代码就得改；表情包只认官方的 im，换一个平台桥就取不了图。

**也已经有人自己搭了半个总线**：`miyu-im/crates/miyu-im/src/core/hooks.rs` 订阅 `packages` 流，找 `status` 是 `running`、`export.methods` 里有 `chat.event`、`chat.inbound`、`chat.outbound`、`chat.score` 的包，照编号先后一个个调。这就是「照名字找、多家并存」，只是约定写在 im 自己的代码里，别的包要用得各写一遍。

**每多一种跨包的功能，就得往核心里加一种专门的登记**：语音的识别、合成，按设计 66 的驱动装不下（只装得下聊天），照老办法要在核心里加两个用途、几种驱动；以后的 OCR、翻译、生图、桌面通知也一样。

### 二、分界线

| | 相当于 | 包括 | 上不上总线 |
|---|---|---|---|
| 核心协议的专门方法 | 系统调用 | 会话、回合、事件、存储、blob、配置、工具、驱动、挂接点、斜杠命令、界面块 | **不上**。这些带着专门的规矩：工具有参数结构、权限级别、效果和职能（设计 63、64），驱动有流式、重试、冷却（设计 66），挂接点有先后和拦截（设计 65）；摊平成通用调用，规矩就丢了 |
| 包和包、头和包之间的服务 | D-Bus | 语音的 `stt`、`tts`，渲染，表情包取 IM 的图，IM 的插件挂接 | **上** |

- **核心不拆成进程挂在总线上**（微内核那种）：`01-架构.md` 第七节定的是「决定速度、决定正确性的部分在一个进程里」，事件日志的一致、前缀缓存的稳定都靠它。
- **以后的规矩**：新的跨包功能先上总线；只有它要进到回合里、带内核级的规矩时（要按权限级别判、要流进模型的循环），才在核心里给它开专门的登记。

### 三、名字

**两种声明**，写在清单的 `[export]` 里（和现有的 `methods` 放一起，位置是第九节第 1 条）：

```toml
[export]
provides = ["stt"]                         # 我提供 stt；一个名字只有一家
plugs    = ["tts.engine"]                  # 我接进 tts.engine；可以多家
methods  = ["stt.transcribe", "stt.record", "tts.engine.synthesize"]
```

| | `provides` | `plugs` |
|---|---|---|
| 意思 | 我提供这个功能，大家直接调我 | 我接进某个功能，当它的一个选项 |
| 几家 | 一个名字只有一家：装第二家报冲突（`package_conflict`，新的一种 `bus`），照 pacman 先卸一个（项目主人 2026-11-09 定） | 多家并存，由用它的那一方列出来挑 |
| 怎么调 | `bus.call {"name": "stt", "method": "transcribe"}` | `bus.call {"name": "tts.engine", "package": "miyu-say-gptsovits", "method": "synthesize"}`：要写挑的是哪一家 |
| 例子 | `miyu-voice-input` 的 `stt`、`miyu-say` 的 `tts` | 社区的 `miyu-say-gptsovits`；IM 的插件挂接 |

- **名字管一组方法**：名字 `stt` 下的方法照 `stt.<方法>` 写进 `methods`，总线只转名字底下、写进了 `[export]` 的。不另造接口描述语言：方法的参数、回应写在提供方的文档里，公认的名字（`stt`、`tts`……）写进参考文档，像 freedesktop 的规范。
- **写法**：小写字母、数字、`-`，点分几段，同现有方法名的规则（`miyu-config` 的 `links.rs`）。总线的名字和核心协议的方法名是两个名字空间，不会撞。
- **不设官方名字登记处**：谁先装谁占着，撞了装包时说清是哪个包占的。公认的名字由参考文档列出。

### 四、协议

| 方法 | 谁调 | 做什么 |
|---|---|---|
| `bus.call {"name", "method", "params"?, "package"?}` | 头、扩展 | 照名字找到提供者，转成现有的反向调用 `method.call`（带 `from`），回什么交回什么；在后台答。`plugs` 的要写 `package` |
| `bus.list {"name"?}` | 头、扩展 | 列出总线上的名字：`[{"name", "kind": "provides"\|"plugs", "package", "ready"}]`；写了 `name` 只列这一个 |
| 推送 `bus.changed {"name", "providers"}` | 核心发给订阅了 `bus` 流的 | 一个名字有人提供了、没人了、换人了、可用了、不可用了 |

- **「可用」从登记了方法算**：现在扩展握手（`hello`）以后就算 `running`，到它调 `package.methods` 登记方法之间，`package.call` 回 `program_not_running`。`ready` 照「这个名字底下写进 `[export]` 的方法都登记了」算，头照它画入口，不会画出一个点了报错的麦克风。
- **出错**：沿用 `package.call` 的那几个（`program_not_running`、`unregistered`、`not_exported`、`method_timeout`、`method_failed`、`needs_approval`），加 `no_provider`（这个名字没有包提供）和 `package_required`（`plugs` 的没写挑哪家）。
- **权限照旧**：人的连接（头）调得到全部；扩展要声明 `packages.call`、人批过（施工 X-18、X-30）。批的单位要不要从「能调别的包」细到「能调哪几个名字」是第九节第 4 条。
- **blob 两个方向都交**（2026-11-09 c0 对照语音复核时提，BUS-2 必做）：结果里的 blob 照 `package.call` 现在的 `blob_grants.pass` 交给调的一方；调的一方写在 `params` 里、它自己拿得到的 blob，转出去之前同样交给被调的一方（人的连接照它读得到的给）。现在的 `package.call` 只往回交，语音把音频交给 `stt.transcribe`、社区引擎、`tts.play` 都会被 `blob.get` 拒。
- **时限照旧**：照提供方登记的 `timeout_ms`。
- **命令行** `miyu bus list`：印谁提供了什么、可不可用，照 `busctl list`。查「为什么终端里没有麦克风」「长消息为什么没转图」用。

### 五、和现有的怎么接

- **`package.call` 留着**：包调自己（自己的后台页、命令行连核心调自己），和界面块、宿主页这类本来就带着包编号的，照旧用它。跨包的改用 `bus.call`。扩展经 `package.call` 调别的包这条路要不要收掉是第九节第 2 条。
- **现有写死包名的改成照名字**（各仓库的会话做）：

  | 现在 | 改成 |
  |---|---|
  | im 调 `("miyu-render", "markdown")` | miyu-render 声明 `provides = ["render"]`，im 调 `render.markdown` |
  | 表情包调 `miyu-im` 的 `chat.media` | im 声明 `provides = ["chat"]`，表情包调 `chat.media` |
  | sponsor 调 `miyu-im` 的 `chat.venue` | 同上，调 `chat.venue` |
  | im 自己扫 `export.methods` 找插件 | 插件声明 `plugs = ["chat.hook"]`（名字由 im 定），im 照 `bus.list` 找，挂接的先后照旧 |

  以后接 Telegram 的桥只要也声明 `chat`（或者 im 一个包接几个平台，照 IM 设计 07），表情包一行不改。
- **`backstage/calls.rs` 开头的注释**说「没在跑的照用到时拉起、最多等 60 秒」，代码里没有这一段，实际直接回 `program_not_running`。施工时照实改注释；按需拉起见第六节。

### 六、不做的

| 不做 | D-Bus 里叫 | 为什么不做 | 重开条件 |
|---|---|---|---|
| 广播、订阅 | 信号 | 现有的推送（`package.event`、各个流）够用 | 有两个以上的包要听同一种广播 |
| 第一次调时才拉起提供者 | 按需拉起 | 现在扩展都是常驻的，没人要 | 语音的 `miyu-voice-input` 实测要省常驻内存时 |
| 接口的版本号 | 接口版本 | 没有第二版接口 | 公认名字第一次要改不兼容的形状 |
| 方法参数的自描述 | introspection 的签名 | 参数写在提供方的文档里；`bus.list` 只列名字 | 有通用工具要照签名生成调用 |
| 限频、记账 | | 被调的一方自己看 `from` 挡（同 X-18） | 有包被别的包刷 |

### 九、交 core1 研究、拍板的（2026-11-09 拍了，见第十节 B4 到 B9）

1. **声明写在哪**：`[export]` 底下（推荐：和 `methods` 一起，作者一眼看全「我对外给什么」），还是 `[package]` 底下。
2. **扩展经 `package.call` 调别的包这条路收不收**：推荐总线做好、BUS-4 迁完以后收掉（扩展只能经 `package.call` 调自己），省得两条路；人的连接照旧都能用。
3. **名字底下的方法怎么写**：推荐方法名带名字前缀（`stt.transcribe`），`bus.call` 写短名、核心拼上；另一种是名字和方法分开登记。
4. **扩展调总线的权限批到多细**：现在批 `packages.call` 就能调所有导出的方法。推荐第一版照旧；`tts` 这类会出声、会花钱的，被调的一方看 `from` 自己挡。要细到名字的，批的界面和 `61-装包说清来源和能力.md` 一起改。
5. **`ready` 的算法**：推荐「`provides` 的名字底下导出的方法全登记了」；`plugs` 的同理按一家算。
6. **`bus` 流和 `packages` 流合不合**：推荐另起，头只听自己关心的；合进 `package.changed` 也行，头自己算。

### 十、决定

**B1. 做用户态总线**（2026-11-09 项目主人定）
- **已定：包和包、头和包照名字找、照名字调，不写死包名。**
- 未选 A：照旧 `package.call` 写包名。换一个包、接一个社区包都要改调的一方的代码。
- 未选 B：每种跨包功能在核心里开专门的登记（如把识别、合成做成模型的用途）。核心跟着每个功能长，不装的人也看得到配置。
- 重开条件：无。

**B2. 分界线：核心的专门方法不上总线**（2026-11-09 项目主人同意）
- **已定：会话、回合、事件、存储、工具、驱动、挂接点这些照旧走核心协议的专门方法；总线只管用户态的服务。核心不拆成进程。**
- 未选：把整个架构改成总线（核心的功能也挂成总线上的名字）。工具、驱动、挂接点的专门规矩会丢；改动大，头、包、参考文档全要跟着改。
- 重开条件：无。

**B3. 两种声明**（2026-11-09 项目主人定）
- **已定：`provides` 一个名字一家，装第二家报冲突；`plugs` 多家并存，由用它的一方挑。**
- 未选：同一个名字也能多家，软件包页上挑一家。多一个设置项，没装两家的人也要面对；真有人要再改。

**后续再定**：第九节六条，core1 研究后定。

**B4. 声明写在 `[export]` 底下**（2026-11-09 core1 拍板，第九节第 1 条）
- **已定：`provides`、`plugs` 和 `methods` 一起写在 `[export]`，作者一眼看全对外给什么。** `[export]` 照旧只给扩展包写（要有程序答）。
- 未选：写在 `[package]` 底下。和方法分开两处，作者要对着两处写。

**B5. 扩展经 `package.call` 调别的包这条路发版前收掉**（2026-11-09 core1 拍板，第九节第 2 条）
- **已定：BUS-4 迁完以后（BUS-5）收掉，扩展只能经 `package.call` 调自己，跨包一律走 `bus.call`；人的连接照旧都能用。** 协议 1 发出去以后只加不改，要收只能在发版前收。
- 未选：两条路都留着。社区作者照旧会写死包名，总线白做。

**B6. 方法名照名字带前缀，一个名字只能是一种**（2026-11-09 core1 拍板，第九节第 3 条）
- **已定：`methods` 里写全名（`stt.transcribe`），`bus.call` 写短名（`transcribe`），核心拼上；名字下面的方法要写进 `methods` 才转。同一个名字在装着的包里只能是一种：一家 `provides` 了，别家不能 `plugs` 它，反过来也一样，撞了报 `bus` 冲突。** 所以 im 自己 `provides = ["chat"]`，插件挂接另起名字 `chat.hook`（方法 `chat.hook.event` 等）。照名字找到包以后只在那个包的 `[export]` 里查方法，名字一个是另一个的前缀也不会转错。
- 未选：名字和方法分开登记（`provides = { stt = ["transcribe"] }`）。多一层结构；现有方法名本来就带点，带前缀照旧一张表写完。

**B7. 权限第一版照旧**（2026-11-09 core1 拍板，第九节第 4 条）
- **已定：批了 `packages.call` 就能调所有导出的方法；会出声、会花钱的（`tts` 这类），被调的一方看 `from` 自己挡。**
- 重开条件：社区里有包滥调，或者要按名字批，和 `61-装包说清来源和能力.md` 的批的界面一起改。

**B8. `ready` 照登记算**（2026-11-09 core1 拍板，第九节第 5 条）
- **已定：程序在跑，并且这个名字底下写进 `[export]` 的方法都登记了，才算 `ready`；`plugs` 的每一家分开算。** 头照它画入口；扩展握手以后到登记方法之间不算可用，那段空档里 `bus.call` 回 `program_not_running`（同现在）。

**B9. `bus` 流另起**（2026-11-09 core1 拍板，第九节第 6 条）
- **已定：另起 `bus` 流，推 `bus.changed`；不并进 `packages` 流。** 头只听自己关心的，名字变了不用自己从包列表里算。

**B10. 短名只有一段**（2026-11-09 c0 对照语音复核时提，core1 采纳）
- **已定：`bus.call` 的 `method` 是一段、不带点；名字底下的方法是 `<名字>.<一段>`。所以 `stt.engine.transcribe` 只在 `stt.engine` 底下，不在 `stt` 底下。** 一个包同时声明 `stt` 和 `stt.engine` 时，`ready` 不会重复算，`bus.call {"name": "stt", "method": "engine.transcribe"}` 也调不到它。现在计划里的短名都是一段，没有代价。
- 未选：一个方法归同一个包里最长的那个名字前缀。规矩藏在算法里，作者看清单看不出来。
