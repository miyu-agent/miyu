## 下载量、趋势、最新

软件源的索引每个包多三格：这一版什么时候上的、一共下载过几次、近 7 天下载了几次。网页、终端的「下载软件」照它们按最新、下载量、趋势排。

状态：已定（2026-10-31 项目主人定三种排序都做，网页、终端同一天来要；2026-10-30 项目主人问过「下载软件有没有下载量」，当时答没有）。第二到第四节是技术细节，主会话定。

### 一、三格

| 格 | 是什么 | 怎么来 | 没有的时候 |
|---|---|---|---|
| `published` | 这一版第一次进索引的时刻，`2026-10-31T09:00:00Z` 这样的写法 | 生成索引时照上一份索引沿用；编号、版本和上一份对得上的照抄，变了的（新包、升了版）写这一次生成的时刻 | 以前生成的索引没有；第一次加这一格时，已有的包都写这一次的时刻 |
| `downloads` | 这个包各版本、各系统的发布文件一共被下载了几次 | 生成索引时照每个文件的地址认 GitHub 发布页（`https://github.com/<主>/<仓库>/releases/download/<标签>/<文件名>`），问 GitHub 那一份发布的 `download_count`，同一个包所有版本、所有系统的加起来（旧版不在索引里，照发布页上这个包的全部发布算） | 文件不在 GitHub 发布页上的、问不成的不写 |
| `downloads_week` | 近 7 天新增的下载次数 | 软件源旁边多一份 `stats.json`，存最近 8 天每天的 `downloads`（照日期，UTC）；生成时拿今天的减 7 天前那一天的 | 不满 7 天的历史不写；`downloads` 没有的不写 |

1. 不用 `published` 的时候照 GitHub 发布的时刻：自建的软件源、镜像都有这一格，而且「第一次进这个软件源」才是用户看到的「新」。
2. 下载量是全部版本加起来：只算当前版，升一次版就清零，排序会乱跳。
3. 趋势是一周：一天的太抖，一个月的太慢。

### 二、生成

1. `miyu-index` 生成索引时多两步：读上一份 `index.json`（沿用 `published`）；带 `--github` 时问 GitHub（照环境变量 `GITHUB_TOKEN`，没有的照匿名，限额低）取下载数，写进 `stats.json`、算 `downloads_week`。不带 `--github` 的（本机试软件源）只有 `published`。
2. `stats.json`：`{"version": 1, "days": [{"date": "2026-10-31", "downloads": {"<包编号>": 123}}]}`，只留最近 8 天，和 `index.json` 放在一处。不签名：只用来算趋势，索引里的数才是交给核心的，索引照旧整份签名。
3. `miyu-agent/packages` 仓库的 Actions 每天跑一次（现有的那一次），带 `--github`，`stats.json` 跟着 `index.json` 一起发到 Pages。

### 三、协议

1. `package.search` 每一项多 `published`、`downloads`、`downloads_week`，索引里没有的不写。
2. 核心读索引照旧认：以前生成的没有这三格，读进来就是没有。三格的写法不对的（不是时刻、不是非负整数）当没有，不丢整条。

### 四、头

1. 「下载软件」的排序：最新照 `published` 倒着排，下载量照 `downloads`，趋势照 `downloads_week`，都是没有的排在最后、再照编号。
2. 索引里一个包都没有某一格的（旧索引、自建的软件源没开 `--github`），那一种排序灰掉或者不给。

### 五、怎么拆

| 步 | 做什么 |
|---|---|
| DL-1 | 核心：索引的三格、读的时候认、`package.search` 交出去 |
| DL-2 | `miyu-index`：沿用 `published`、`--github` 取下载数、`stats.json` |
| DL-3 | `miyu-agent/packages` 的 Actions 带上 `--github`，`stats.json` 跟着发 |
| 头 | 网页、终端的排序 |
