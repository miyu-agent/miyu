## 发版

核心怎么发一个正式版：打成什么包、经哪些渠道到人手里、怎么校验、发之前查什么。补 `12-进程形态与分发.md` 第六、八节没落地的部分。那两节写了要有什么；到 2026-11-04，核心仓库的 CI 只有测试，没有发版这一步，版本号还是 `0.0.0`，「测试包 1」是手工打的。

状态：已定（2026-11-04，项目主人定了渠道、版本号、钥匙；细节主会话照推荐定）。已定的见第七节。施工 RL（第六节）。

### 一、什么时候发

项目主人 11-03、11-04 定：核心正式发版放在最后。下面几样都做完才发：

1. 官网和面向用户的 wiki 上线（主人另开的会话做）。
2. Benchmark 对比出结果：资源和交互速度（BM-1，4c，等性能优化做完，在 .91 上跑）；Terminal-Bench 主人自己处理。
3. 旧版迁移程序就位（`27-从旧版迁过来.md` 和单独仓库 `miyu-migrate` 的设计），因为这一版要接管旧版的渠道（第三节第 3 条）。
4. 软件包先进官方源：im、赞助记录、表情包、渲染、终端、网页、外观包、embed、FH-5 下的脚本包。

### 二、两条线

项目主人 11-03 定的：

- **桌面用户**装托盘程序 `miyu-applet` 的安装包：deb、rpm、AUR 的 `miyu-applet`、Windows msi、macOS dmg。包里带核心和网页，不带终端。这条线 `miyu-applet` 仓库已经能打（DT-6、AP-2），跟着核心的版本号一起发。
- **命令行用户**装核心仓库发的命令行版：三平台的压缩包、一行安装脚本、Homebrew、AUR 的 `miyu`。deb、rpm 只由 `miyu-applet` 出，免得两个包抢同一个 `/usr/bin/miyu`。

### 三、命令行版

1. **压缩包**，一种系统一个：
   - 种类：`miyu-<版本>-linux-x86_64.tar.gz`、`-linux-aarch64.tar.gz`、`-macos-aarch64.tar.gz`、`-windows-x86_64.zip`；
   - 里面：`miyu`、`miyu-sandbox`、`miyu-extract`；
   - `resources/`：核心的资源，加上照 `heads.toml` 取来的 `packages/miyu-tui/`、`packages/miyu-webui/`（含网页的 `pages/`）；
   - `LICENSE`（AGPL-3.0 全文）、`THIRD-PARTY-LICENSES.txt`（核心和两个头的，`cargo xtask notices`）；
   - `README.txt`：中英两段，写怎么用、装在哪、怎么卸。
   程序照旁边的 `resources/` 找资源（`miyu-store/src/resources.rs`）。
2. **安装脚本**，从 GitHub Releases 下载：
   - Linux、macOS 用 `install.sh`，Windows 用 `install.ps1`，都装在当前用户的目录里，不要管理员；
   - 先核对 SHA-256 再装；
   - Linux 装 `.miyu` 的文件类型，照设计 12 第六节；
   - 装完说下一步：第一次打开怎么走引导，要不要 `miyu service enable`。
   - 以后的 `miyu upgrade` 由脚本装的那一份自己升级（设计 12 第五节），排在 RL-4。
3. **新包名，不强迫旧用户升级**（2026-11-04 项目主人定）：
   - AUR 新开 `miyu-agent`（装发的压缩包）、`miyu-agent-git`（照源码编），写 `provides=(miyu)`、`conflicts=(miyu)`、`replaces=(miyu)`。旧的 `miyu`、`miyu-git` 从 AUR 删掉。
   - 旧用户更新时被问「miyu 和 miyu-agent 冲突，要不要替换」；不想换的忽略就行，旧版留在 0.7.4。换了的照迁移程序的发行说明走（设计 27 第二节、`miyu-migrate`）。
   - 旧版 Miyu 的仓库不归档，变成新的 `miyu-agent/miyu`（2026-11-04 项目主人提：一百多颗星和搜索排名跟着仓库走，GitHub 不能把星星挪到别的仓库）：旧仓库 `SHORiN-KiWATA/miyu-agent` 转进组织、改名 `miyu`，旧网址 301 跳过来；旧版的 main 存成 `legacy-0.7` 分支，旧的 v0.7.x 标签、Release 原样留着（旧 AUR 包照样下得到）；重制版的分支、标签照原 sha 推进去。现在的重制版仓库先让出名字（改成临时名），Release（模型、测试包）重传，核对完归档。在发版那天做，见第五节。
   - `replaces` 在 AUR 包上被不被问、怎么问，看用的是哪个 AUR 助手（pacman 只对官方仓库的包认 `replaces`）。发之前在容器里拿 paru、yay 各装一次旧版、再更新，照实测写进发行说明：问的就照上面说；不问的写清楚手动换的命令。
   - Homebrew 照同样的意思：tap `homebrew-miyu` 新加 formula `miyu-agent`，旧的 `miyu` formula 从 tap 里删掉（2026-11-04 项目主人定：旧包直接从源里删，不留，别的软件一贯这么做）。已经装了的人留着旧版，想换的自己装 `miyu-agent`。
   - 真相源照旧在核心仓库的 `packaging/`：AUR 的 PKGBUILD、Homebrew 的 formula，别让它们和 AUR 克隆脱节。
   - AUR 的 `miyu-agent` 和 `miyu-applet` 互相写 `conflicts`，都 `provides=(miyu)`。
   - 旧版的 `miyu-voice` 标成孤包，写明新版语音以后作为软件包提供（2026-11-04 项目主人定）。

### 四、怎么校验

1. 每次发布附 `SHA256SUMS`：每个压缩包一行。
2. **签名**：`SHA256SUMS` 用项目的 Ed25519 发版钥匙签，签法和软件源的索引同一套（设计 37，`miyu-index sign`），只是另用一把钥匙，私钥放在核心仓库的 Actions secret 里。安装脚本、以后的 `miyu upgrade` 用编进程序或者写进脚本的公钥核对。
3. 再加 GitHub 的构建出处证明（`actions/attest-build-provenance`）：不用另管钥匙，`gh attestation verify` 查得到是哪一次 CI 打的。
4. **发布前查包**（设计 12 第八节 R14）：解开每个压缩包，资源齐不齐（照清单逐项），`miyu --version` 报的是不是这一版，`miyu check` 在临时数据根里跑一遍过不过。有一样不对，这一趟不发。

### 五、发版那一天的流程

之前就能做的，先做好、不合：
- 查出所有写死 `miyu-agent/miyu`、`SHORiN-KiWATA/miyu-agent`（`SHORiN-KiWATA/Miyu`）网址和引用重制版 Release 的地方：核心、两个头、im、软件源、托盘程序、各包仓库的发版流程；
- 主人自己的装机脚本 `shorin-arch-setup`、`shorin-niri`、`shorin-dms-niri` 里装的是 AUR 的 `miyu`，初始化调的是旧命令 `miyu fish-init`，说明里写的是旧命令（`miyu normal`、`dev`、`remove-shell-hook`）。各开一个分支改成 `miyu-agent` 和新版的命令（`miyu shellhook install`），先不合。

发版那天照这个先后，旧用户、旧脚本一直有能装的东西：

1. 换仓库（第三节第 3 条）：旧仓库变成 `miyu-agent/miyu`。这时 AUR 上旧的 `miyu` 还在，从旧 Release 下载，跳转后照样能装，旧脚本不受影响。

2. 版本号：`Cargo.toml` 的 `[workspace.package] version` 改成这一版，`heads.toml` 钉两个头已经打了标签的版本。
3. 打标签 `v<版本>` 推上去：`release.yml` 照第三、四节打包、查包、签名，建一个**草稿** Release，把包、`SHA256SUMS`、签名传上去。
4. 项目主人看过草稿，当面同意以后，自己点发布（公开发布要主人当面同意）。
5. 发了以后：
   - `packaging/` 的 AUR PKGBUILD、Homebrew formula 换上这一版的哈希，发 AUR 的 `miyu-agent`、tap 的 `miyu-agent`；
   - 合主人装机脚本那三个分支；
   - 这之后才删 AUR、tap 里旧的 `miyu`：脚本改好之前旧包一直在，没有哪一段时间装不上；
   - `miyu-applet` 跟着打它的安装包；
   - 官网的「下载」换成真地址；
   - 发版说明照 `docs/next-release-note.md` 的草稿整理。
