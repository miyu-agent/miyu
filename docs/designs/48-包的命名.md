## 包的命名

包的编号是短名：不带 `miyu-`，也不带接入方式（`scripts-`、`skills-`）；出厂的基础包叫 `base-<名字>`。配置键和会话事件用的前缀从包编号上拆下来，由清单另外声明。

状态：已定（2026-11-12 项目主人定第一节，取代 2026-10-29 定的 `miyu-<归属>-<名字>`；10-29 定的配置前缀照旧；2026-10-30 主会话补第三节的拆法、第五节的搬家，都是技术细节）。来历：10-29 项目主人在虚拟机里以新用户身份敲 `miyu pkg search`，短名和 `miyu-scripts-*` 混在一起看不出哪个是谁出的，定了官方包一律 `miyu-<归属>-<名字>`（施工 PN-3 起出厂包叫 `miyu-base-*`）；11-12 改成编号去掉 `miyu-` 和接入方式，谁出的、怎么接入交给界面上的标签说。

### 一、命名规矩

1. 包的编号全小写，单词之间用连字符，不用下划线；不带 `miyu-`，不带接入方式（`scripts-`、`skills-` 这些）。很短的通用词就用短的。
2. 编在核心里的出厂包：`base-<名字>`，例如 `base-read`、`base-edit`、`base-ask-user`、`base-memory`、`base-roleplay`、`base-net`。基础系统组里的包、组外的出厂包（记忆、知识库、长期目标、联网、角色扮演、mermaid、作者工具、软件工程师人格）一样。包编号和工具名不同：工具 `read` 归包 `base-read`。
3. 界面：`tui`、`webui`。网页不叫 `web`，那是网页软件的程序名。外观包写明给哪个头：`tui-theme-<名字>`（例如 `tui-theme-ascii`）、`webui-theme-<名字>`。
4. 扩展：`embed`、`im`、`im-sponsor`、`memes`、`render`、`migrate`、`ocr`；表情包内容包 `memes-shorin-collection`；语音 `voice-input`、`say`、`voice-assistant`。
5. 只带脚本、技能的包：以前的 `miyu-scripts-<名字>`、`miyu-skills-<名字>` 就叫 `<名字>`。
6. 不跟着改：
   - GitHub 仓库名和网址（`miyu-agent/miyu-ocr`、`miyu-agent/miyu-tui`）；
   - 程序的文件名（`bin/miyu-ocr`、`miyu-tui`、`miyu-web`、`miyu-embed`）；
   - 包里的子命令名（`[command] name`），人照旧敲 `miyu tui`、`miyu web`、`miyu im`；
   - 配置键的前缀规矩（第二节）；
   - `miyu` 本身：核心程序、`miyu pkg`；
   - 系统包管理器里的包名：AUR、Homebrew 照旧是 `miyu-core`、`miyu-tui`、`miyu-webui`、`miyu-agent`。Release 里给它们用的两个头的分包照编号叫 `tui-<版本>-<系统>.tar.gz`、`webui-<版本>-<系统>.tar.gz`（核心那一份照旧 `miyu-core-*`）。
7. 包是扩展、脚本还是技能，由界面照清单画成标签，归界面；核心不为它加清单字段。
8. 还没发版，改名不做兼容：核心不认旧编号。项目主人部署里的旧数据用仓库外的一次性工具搬（第五节）。

### 二、前缀：配置键、会话事件不跟着编号变

1. 清单的 `[package]` 有一项 `prefix = "<前缀>"`。不写就等于包编号。前缀的写法是配置键里一段编号的写法（`miyu_config::key::ID`：小写字母打头，`[a-z0-9_-]`，不超过 32 个字符，不能是 `con`、`nul` 这类 Windows 保留名），比包编号（最多 64 个字符）短。（2026-11-13 照代码改，AD-1 发现：原来写「和包编号一样」，可清单读 `prefix` 查的是 `key::ID`，不是包编号的写法；32 和代码对得上，改的是前半句，施工 AD-2。）
2. 前缀管两样东西：
   - 包声明的设置项，键是 `<前缀>.<名字>`，例如 `im.qq.token`、`tui.theme`；
   - 扩展往会话里记的事件，种类是 `ext.<前缀>.<名字>`，例如 `ext.im.venues.queued`。
3. 前缀先到先得：出厂的包先占，装的包照装的先后，和装着的撞了，装的时候拒绝（`package_conflict`，说是哪个包占着）；读的时候撞上的（核心升级后出厂的新带了同一个前缀），后读到的那一份不收（`prefix_taken`）。声明了配置项的包，前缀还不能是核心自己的设置组（`settings_taken`）。
4. 出厂包都写短前缀，和施工 PN-3 以前的编号相同：`base-memory` 写 `prefix = "memory"`，`base-net` 写 `prefix = "net"`。所以配置里的 `memory.*`、`net.*` 都不用动。编号本来就短的（`tui`、`im`）前缀就是编号，写不写一样。
5. 按包编号的照旧按包编号，不走前缀：
   - 开关 `packages.<编号>.off`；
   - 数据根里的 `packages/<编号>/`、`var/lib/<编号>/`；
   - 扩展的开关、批过的能力；
   - 预设里的 `[software] <编号>`；
   - `[content.<编号>]`、`depends`、`recommends`；
   - `ui.head`。

### 三、和包编号脱钩的几样东西

施工 PN-2 以前，代码里同一个字符串同时是包编号、功能编号、资源目录名、界面文字的键前缀、内核模块编号。改名只改包编号，其余几样照旧：

1. **功能编号不变。** 没写 `[features]` 的包，功能编号以前默认就是包编号。改名前先把这几个包的功能写明，编号照旧：`memory`、`goal`、`knowledge`、`roleplay`、`clicall`、`project-docs`、`authoring`。预设的 `[features]`、代码里按功能查开没开的地方都认功能编号。
2. **按功能找包，不再拿功能编号当包编号。** 查一个功能所在的包开没开、在不在组里，先查这个功能属于哪个包，再看那个包。
3. **资源目录名、界面文字的键不变。** `resources/software/<目录>` 和日志里存着的 `software/<目录>/…` 照旧是短名。代码里把「包编号」和「资源目录」拆成两个常量。
4. **内核模块编号不变。** `memory`、`goal`、`knowledge`、`project-docs` 记在日志里，是来源和事实种类，和包无关。

### 四、要跟着改的地方

- **核心**（施工 PN-5）：出厂包的目录、注册表、`ui.package`、按包隐藏设置项的表、组的先后、出厂预设的 `[software]`、`ui.head` 的默认值（`tui`）、语义模型的 worker 名（`embed`，记忆包的 `recommends.workers` 一起改）、`heads.toml` 的两张表（`tui`、`webui`，发版取头仓库里和编号同名的包文件夹）、两个头的分包名、系统源模板里的包文件夹。
- **头和扩展的仓库**：终端、网页、im、embed、表情包、语音等各自的清单改编号，包文件夹改名（终端 `tui/`、网页 `webui/`）；表情包的 `[content.<编号>]` 跟着 im 的新编号。各自在核心合进 main 以后钉新的核心再改。
- **官方软件源**：`names.toml` 认领新编号；旧编号的那几行照旧留着，先到先得的记录不删。

### 五、项目主人部署里的旧数据

在仓库外写一次性的搬家工具，照 10-29 搬单用户布局的办法：默认只演练，`--apply` 才动；核心在跑就不动；改之前先备份；改完核对。产品里不加改名的方法，也不加事件。

- 核心的数据：场所编号、包编号（`miyu-base-*` 换成 `base-*`，`miyu-tui` 这些换成短名），由核心这边的工具搬。
- im 自己状态目录里的数据：由 im 的脚本搬。
- 顺序：停 im → 停核心 → 核心的工具 → im 的脚本 → 装新核心和新 im → 启动。
