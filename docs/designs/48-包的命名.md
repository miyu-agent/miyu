## 包的命名

官方包的编号一律以 `miyu-` 打头，再按归属分组；配置键和会话事件用的前缀从包编号上拆下来，由清单另外声明，保持短名。

状态：已定（2026-10-29 项目主人定命名和配置前缀；2026-10-30 主会话补第三节的拆法、第五节的搬家，都是技术细节）。项目主人 10-29 在虚拟机里以新用户身份敲 `miyu pkg search`，短名（`tui`、`web`、`embed`、`im`、`theme-ascii`、`edit`）和 `miyu-scripts-*` 混在一起，看不出哪个是谁出的。

### 一、命名规矩

1. 官方包写成 `miyu-<归属>-<名字>`，全小写，单词之间用连字符，不用下划线。
2. 编在核心里的内置包：`miyu-base-<名字>`，例如 `miyu-base-edit`、`miyu-base-ask-user`、`miyu-base-memory`。基础系统组里的包、组外的内置包（记忆、知识库、长期目标、联网、角色扮演、mermaid、作者工具）一样。
3. 界面：`miyu-tui`、`miyu-webui`。不叫 `miyu-web`，那是网页软件的程序名和仓库名。终端主题：`miyu-tui-theme-<名字>`。
4. 扩展：`miyu-embed`、`miyu-im`。原本就带前缀的不变：`miyu-im-sponsor`、`miyu-memes`、`miyu-render`、`miyu-scripts-*`、`miyu-skills-*`。表情包内容包：`miyu-memes-shorin-collection`，和仓库同名。
5. 包里的子命令名（`[command] name`）不变，人照旧敲 `miyu tui`、`miyu web`、`miyu im`。
6. 还没发版，改名不做兼容：核心不认旧编号。项目主人部署里的旧数据用仓库外的一次性工具搬（第五节）。

### 二、前缀：配置键、会话事件不跟着变长

1. 清单的 `[package]` 新加一项 `prefix = "<前缀>"`。不写就等于包编号。前缀的写法和包编号一样（小写字母打头，`[a-z0-9_-]`，不超过 32 个字符）。
2. 前缀管两样东西：
   - 包声明的设置项，键是 `<前缀>.<名字>`，例如 `im.qq.token`、`tui.theme`；
   - 扩展往会话里记的事件，种类是 `ext.<前缀>.<名字>`，例如 `ext.im.venues.queued`。
3. 前缀先到先得：出厂的包先占，装的包照装的先后，和装着的撞了，装的时候拒绝（`package_conflict`，说是哪个包占着）；读的时候撞上的（核心升级后出厂的新带了同一个前缀），后读到的那一份不收（`prefix_taken`）。声明了配置项的包，前缀还不能是核心自己的设置组（`settings_taken`）。
4. 官方包都写短前缀，和改名前的编号相同：`miyu-tui` 写 `prefix = "tui"`，`miyu-im` 写 `prefix = "im"`，`miyu-base-memory` 写 `prefix = "memory"`。所以旧日志里的 `ext.im.*`、配置里的 `im.*`、`memory.*` 都不用动。
5. 按包编号的照旧按包编号，不走前缀：
   - 开关 `packages.<编号>.off`；
   - 数据根里的 `packages/<编号>/`、`state/packages/<编号>/`；
   - 扩展的开关、批过的能力；
   - 预设里的 `[software] <编号>`；
   - `[content.<编号>]`、`depends`、`recommends`；
   - `ui.head`。

### 三、和包编号脱钩的几样东西

改名前，代码里同一个字符串同时是包编号、功能编号、资源目录名、界面文字的键前缀、内核模块编号。改名只改包编号，其余几样照旧：

1. **功能编号不变。** 没写 `[features]` 的包，功能编号以前默认就是包编号。改名前先把这几个包的功能写明，编号照旧：`memory`、`goal`、`knowledge`、`roleplay`、`clicall`、`project-docs`、`authoring`。预设的 `[features]`、代码里按功能查开没开的地方都认功能编号。
2. **按功能找包，不再拿功能编号当包编号。** 查一个功能所在的包开没开、在不在组里，先查这个功能属于哪个包，再看那个包。
3. **资源目录名、界面文字的键不变。** `resources/software/<目录>` 和日志里存着的 `software/<目录>/…` 照旧是短名。代码里把「包编号」和「资源目录」拆成两个常量。
4. **内核模块编号不变。** `memory`、`goal`、`knowledge`、`project-docs` 记在日志里，是来源和事实种类，和包无关。

### 四、要跟着改的地方

- **核心**：出厂包的目录、注册表、`ui.package`、按包隐藏设置项的表、组的先后、出厂预设的 `[software]`、`ui.head` 的默认值（`miyu-tui`）、语义模型的 worker 名（`miyu-embed`，记忆包的 `recommends.workers` 一起改）、`heads.toml`。
- **头和扩展的仓库**：终端、网页、im、embed 的清单改编号、写 `prefix`；表情包 `[content.im]` 改 `[content.miyu-im]`，收藏包改名。各自在核心合进 main 以后钉新的核心再改。
- **官方软件源**：`names.toml` 认领新编号；旧编号的那几行照旧留着，先到先得的记录不删。

### 五、项目主人部署里的旧数据

在仓库外写一次性的搬家工具，照 10-29 搬单用户布局的办法：默认只演练，`--apply` 才动；核心在跑就不动；改之前先备份；改完核对。产品里不加改名的方法，也不加事件。

- 核心的数据：场所编号、包编号，由 sub1 的工具搬。
- im 自己状态目录里的数据：由 im 的脚本搬。
- 顺序：停 im → 停核心 → 核心的工具 → im 的脚本 → 装新核心和新 im → 启动。
