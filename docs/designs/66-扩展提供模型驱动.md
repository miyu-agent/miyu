## 扩展提供模型驱动：`model.driver`

扩展登记一种模型驱动，主人在供应商的配置里写明用它，这家供应商的每一次调用就交给扩展：核心给中间形状的请求，扩展流式交回统一的增量，
最后交用量或者出错的分类。三种常用驱动（`openai-chat`、`anthropic`、`openai-responses`）照旧在核心里。补 `05-内核接口.md` 第一、
七节，`15-模型与供应商.md` 第二节；协议上加核心发给扩展的 `driver.call`、`driver.cancel`，扩展发给核心的 `driver.delta`。

状态：已定（core1 2026-11-06：第十二节七条照推荐；借 agent CLI 订阅做成扩展包、现在先不做，主人 2026-11-06 定，见第十一节、
第十四节），首个正式版以前施工 MD-1 到 MD-4（第十三节；项目主人 2026-11-07 定挪到发布前）。
来源：扩展缺口报告第 2 条。

### 一、为什么

驱动表是封死的：`crates/miyu-models/src/provider.rs` 的 `enum Driver { OpenAiChat, Anthropic, OpenAiResponses }`，配置里写别的名字
读不进。可是设计 05 第一节的贡献表第一行就是「模型驱动：DeepSeek、Anthropic、借用别的 agent CLI 的订阅」，设计 15 的驱动表里也有
「借用 agent CLI 的订阅：走子进程」，第七节的规格表写着 `transport` 是「HTTP，或者子进程」，都没落地。

缺口报告里的用法：
- 借订阅：Claude Code、Codex、Antigravity 这类，要登录、刷新令牌，有的还要走它自己的子进程；
- 线上写法不是那三种的：要签名的（云厂商的请求签名）、走 WebSocket 的、私有部署的网关；
- 试新供应商：先用扩展接上，用的人多了再考虑进核心。

这些都不该一家家写进核心：各家的登录、签名、私有字段变得快，进了核心就要跟着发版。

### 二、现在有什么

- **驱动只编码、解码，不发请求**（`miyu-drivers/src/driver.rs`）：
  - `fragments`、`fragments_memo` 把请求编成字节（`Encoded {body, messages, path}`），V-42 的备忘录让没变的部分逐字节相同、不重编；
  - `decoder()` 解响应的分片，交出统一的 `Delta`（`miyu-kernel/src/accumulate.rs`：`Start {index, kind}`、`Text`、`Private`、
    `End`、`Truncated`），流结束时 `finish` 交 `Ending {deltas, usage, error}`；
  - `classify(&Failure)` 把 HTTP 失败归成 `Classified`；`auth(key)` 写请求头；`models_path`、`parse_models` 读供应商的模型列表。
- **请求是执行器发的**：`miyu-session/src/route/exchange.rs` 编码、交 `miyu-http/src/send.rs` 发，流有空闲时限和总时限
  （`idle`，总时限是它乘 `TOTAL_FACTOR`）。key 在 `route/choice.rs` 从 `secret::Reference` 解成 `Endpoint`，只在执行器里。
- **中间形状**：
  - `Request`（`miyu-kernel/src/request.rs`）：`tools`、`system`、`messages`、`stable`、`continuation`、`described`、`output_cap`、
    `used`；`canonical_bytes()` 是规范字节（紧凑 JSON、字段照结构体的先后），`fingerprint()` 是工具面、system、每条消息各一个哈希；
  - `Call`（`miyu-drivers/src/lib.rs`）：`model`、`max_output`、`inputs`、`effort`、`temperature`。
- **用量、计费、出错**：
  - `Usage`（`event/model.rs`）：`uncached`、`cache_read`、`cache_write`、`output`、`reasoning`；价格照 `miyu-models/src/price.rs`
    的 `Tariff::cost` 算，冻结进 `model.called`；
  - `ErrorClass`：`Retryable`、`RateLimited`、`ContextTooLong`、`Auth`、`Quota`、`ContentPolicy`、`Unclassified`；
  - 重试在内核（`session/retry.rs`：至多 5 次，退避 1、2、4、8、16 秒，至多等 120 秒），冷却在 `miyu-models/src/cooldown.rs`，
    换池在 `route/ended.rs`、`route/pool.rs`。
- **扩展协议**（`blueprint/extensions.md`）：标准输入输出上的 JSON-RPC，核心亲手拉起。核心问扩展的都是一问一答（`Peer::call`：
  `tool.call` 60 秒、`method.call` 30 秒），`Peer::notify` 只发不等。**还没有流式回结果的先例**：`tool.progress` 没做
  （`providers.md`），远程工具不收进度（`remote.rs`）；扩展调模型的 `model.call` 也是整份回答（`blueprint/models.md`）。
- **性能预算**（`23-性能预算.md`）：没有首字时延这一项；「人整段等着的，上限 50 毫秒」（F5）管的是核心自己的活。实测编码约
  0.08 毫秒每 100 KB，编码加发出一跳约 0.2 毫秒。

**别家**（只作参考）：
- pi 的 `pi.registerProvider(name, {baseUrl?, apiKey?, api, models, oauth?, streamSimple})`：扩展交一个流式函数和模型表，登录、刷新
  令牌也是扩展自己的（`oauth`）；magpie 照这个形状把 pi 的供应商包跑起来，「插件登录、列模型、发每一次请求」。
- dsh 的 `ctx.llm.registerAdapter(providers, adapter)`：把几个供应商的编号挂到一个适配器上，返回撤销的函数。
- 两家都是同一个进程里的函数，没有进程之间的来回，也就没有本设计第五、六节的问题；借来的是「扩展接一整次调用、自己管登录」这个切法。

### 三、怎么切：扩展接一整次调用

核心留下的：
- 组装请求、规范字节、指纹（不变）；
- 选供应商、选模型、池、冷却、重试、换池、压缩后重试（不变，第八节）；
- 照增量拼回复、落盘、派工具调用（不变：扩展交的就是现在驱动交的 `Delta`）；
- 计价（`Tariff`，扩展不报价钱）。

扩展做的：从中间形状编成线上的字节、登录、发出去、解响应、归类出错。也就是现在驱动加执行器发 HTTP 的那一段。

在执行器里是 `route/exchange.rs` 的一个分岔：供应商的驱动是扩展的，不走「编码、`miyu-http` 发、解码」，改成发 `driver.call`、
收 `driver.delta`、收结尾；交给内核的仍是同一串 `Delta` 和同一个结尾。内核看不出这一次是谁接的。`miyu_drivers::Driver` 这个
接口不动：扩展驱动不是它的一个实现（它是纯函数，扩展这一头要发请求）。

另外两种切法，不推荐：
- **扩展只交编码、解码，核心发 HTTP**：每个响应分片都要过一次进程来回去解码，流式时来回最多；借订阅、走子进程、走 WebSocket
  的根本不是 HTTP，接不上。
- **核心编码，扩展只管发**：签名、私有字段往往要改请求体，核心编出的字节不一定是它要发的；借订阅的线上写法也不是那三种。

### 四、登记和选用

1. **清单里静态声明**，核心起来就知道，`miyu check` 不用扩展在跑也能查配置：
   ```toml
   [[driver]]
   name = "antigravity"      # 驱动名；配置里写成 "<包编号>/antigravity"
   cache = "contract"        # contract、best_effort、none，同 05 第七节的缓存类型
   key = "optional"          # none、optional、required：要不要核心交 key（第九节）
   images = false            # 看得了图的才写 true，图照第五节交过去
   ```
   - 声明了 `[[driver]]` 的包必须声明能力 `model.driver`（第十节），反过来也一样，不对的清单读不进；
   - 驱动名照编号的写法，一个包里不能重。
2. **只有明写的才用它**：供应商的配置写 `driver = "<包编号>/<驱动名>"`：
   ```toml
   [providers.ag]
   driver = "pi-antigravity/antigravity"
   ```
   - 内置驱动的名字没有 `/`，带 `/` 的就是扩展的；
   - 驱动的选法（手写的 > 模型档案的 > npm 表 > 默认）里，只有手写这一格会指向扩展：档案、npm 表、默认永远是内置的三种。
     扩展装上了，也接不走主人原来配好的供应商。
3. **家族**：私有数据（思考的签名、供应商自己的调用编号，03 第九节）照驱动家族认领。扩展驱动的家族是 `<包编号>/<驱动名>`，
   和内置的三家不会撞：它交的私有数据只回给它自己，内置驱动的也不会交给它。
4. **模型的资料**：照现在一格格查（`blueprint/models.md`）。扩展可以实现 `driver.models`（可选，同 `parse_models` 的那一格「供应商
   的列表」），回 `{"models": [{"id", "window"?, "max_output"?, "tools"?, "vision"?, "reasoning"?}]}`；不实现的，主人手写。
5. **配置查不过的**（包没装、没批、驱动名不在清单里）：`miyu check` 报，核心照旧起来，这家供应商当用不了（第八节第 5 条）。
   - 怎么认（施工 MD-1，core1 11-07 照推荐定 A）：`providers.<id>.driver` 的选项是内置的三种，加上装着、声明了 `[[driver]]` 的
     `<包>/<驱动名>`（同 N-5 的搜索来源，头的下拉框列得出）。只对这一格、只对 `<包编号>/<驱动名>` 这个写法（包编号照包名的规则，
     驱动名照清单 `name` 的规则）开一个窄口子：这时不在选项里的（没装、写错了驱动名）不丢，照原样留下，记一条警告 `unknown_driver`；
     运行时这家供应商当用不了，单个模型当场 `no_model`，池里照现成的规矩跳过、换下一个，**绝不退回内置驱动**：主人给扩展配的 key、
     地址不能拿去走别的协议。别的不合法写法照旧 `not_an_option`。`config.set` 写进去时同样收这种写法；读回、`miyu check`、头的
     下拉框（列不到时显示原值）三处一致；改回内置名、删掉这一格都照常。
   - `miyu check` 另报装着的那几个：包没批 `model.driver`（`driver_unapproved`，错误），驱动 `key = "required"` 这一家没配 key
     （`driver_key_missing`，错误），`key = "none"` 这一家却配了（`driver_key_unused`，警告）。

### 五、通道：协议

走扩展现成的那一条标准输入输出连接，不另开管道。

1. **`driver.call`**（核心发给扩展，要回答）：
   - 参数：`{"call", "driver", "request", "fingerprint", "params", "key"?, "base_url"?, "blobs"?}`
     - `call` 是这一次调用的编号，`driver.delta`、`driver.cancel` 照它对；
     - `request` 是 `Request` 的规范字节原样（同 `canonical_bytes()`），加上不进规范字节的 `output_cap`、`described`；
     - `fingerprint` 是指纹（工具面、system、每条消息各一个哈希），扩展可以拿它做自己的缓存，第七节也用它；
     - `params` 是 `Call` 里的 `model`、`max_output`、`effort`、`temperature`；
     - `key`、`base_url` 见第九节；
     - `blobs`：声明了 `images` 的，请求里的图照 `{哈希: {"media_type", "data"}}` 交过去（base64），没声明的不交，请求里照
       `described` 用转述。
   - 回答：`{"usage"?, "error"?, "sent"?}`，在所有 `driver.delta` 之后（同一条连接，先后是保住的）：
     - `usage` 同 `Usage` 的五格；
     - `error` 是 `{"class", "message", "retry_after_ms"?}`，第八节；
     - `sent` 是这一次真发出去的字节的 SHA-256，第七节。
2. **`driver.delta`**（扩展发给核心的通知，不要回答）：`{"call", "deltas": [...]}`，一份里可以有几条增量，和 `Delta` 一一对应：
   `{"start": {"index", "kind"}}`（`kind` 是 `text`、`reasoning`、`{"tool_call": {"name"}}`）、`{"text": {"index", "text"}}`、
   `{"private": {"index", "data"}}`、`{"end": {"index"}}`、`"truncated"`。
   - 核心照现在的累加器查（块照先后开、开了才有字、收了不再写）；不对的，这一次调用当 `Unclassified` 结束，理由写「驱动交的
     增量不对」，记一行 `WARN`；
   - 不认识的 `call`（已经结束的、被打断的）丢掉，不报错。
3. **`driver.cancel`**（核心发给扩展的通知）：人打断、回合被取消时发 `{"call"}`，核心当场照打断收尾，不等扩展。
4. **时限**：同内置驱动走 HTTP 时的空闲时限和总时限（15 第五节：基数 180 秒、照思考强度放大；
   `miyu-http` 的 `idle`、`TOTAL_FACTOR`）：发出去到第一条增量、两条增量之间，
   都不能超过空闲时限。超了的发 `driver.cancel`，当 `Retryable` 结束，理由写「驱动没动静」。
5. **扩展崩了、连接断了**：在等的调用当 `Retryable` 结束，理由写「驱动断了」；扩展照现成的退避重新拉起（`extensions.md`「崩了」）。
6. **并发**：一个扩展可以同时接好几次调用（几个会话、旁路请求），照 `call` 分开；核心不另限并发，照池和冷却现成的规矩。
7. **方法名**：用 `driver.*`，不用 `model.*`：`model.call` 已经是扩展调模型的方法，方向相反。

### 六、性能

内置驱动不受影响：没有扩展驱动的配置，执行器的路一点不变。

用扩展驱动的，比走内置驱动多的是：
- **请求过去一跳**：规范字节本来就算着（哈希用它），写进管道。100 KB 的请求，序列化约 0.08 毫秒，管道一次写完；1 MB 的约 1 毫秒。
  扩展那一头解析、重编，看它用的语言（Bun、Node 解 1 MB 的 JSON 几毫秒）；
- **每段增量回来一跳**：一行 JSON，核心解析是几十微秒。模型一秒出一两百个 token，一秒最多几百条，加起来是毫秒级的 CPU；
  扩展把一次读到的几段并成一条 `driver.delta` 就更少；
- **首字时延**：多的是上面两跳加扩展自己的编码，几毫秒，对比供应商的首字（几百毫秒到几秒）看不出来；
- **同一条连接排队**：同一个扩展的大工具结果和增量走同一条管道，会让增量晚一行到。一行写完是毫秒以内，第一版不分连接。

「人整段等着的上限 50 毫秒」（F5）管的是核心自己的活，模型的时间不算在里面；但核心为扩展驱动多做的这一段要钉住，设计 23 加一项
（第十二节第 7 条）：

| 场合 | 预算 | 量法 |
|---|---|---|
| 扩展驱动比内置驱动多的首字时延 | p95 5 ms | `miyu-perf` 起一个收到就回一段字的假扩展，1 MB 的请求，和内置驱动打本机假服务比 |
| 扩展驱动流式时核心多用的 CPU | 一秒 300 段增量，核心多用的 CPU 在 1% 以内 | 同一个假扩展，一秒交 300 条 |

以后要是量出来请求过去那一跳太贵（长会话、每回合都交一整份），再考虑照指纹只交扩展没有的消息；第一版不做。

### 七、缓存前缀

不变量 3（`02-内核.md`：同样的日志、同样的策略，请求逐字节相同）在核心这一头照旧成立：交给扩展的 `request` 就是规范字节，同一状态
一字不差。线上的字节是扩展编的，核心看不见，只能要求、查、记：

1. **要求**：扩展的编码必须只看 `driver.call` 的参数：不放时间、随机数，字段的先后固定（05 第七节对内置驱动的同一条要求）。
   写进作者文档。
2. **查**：声明 `cache = "contract"` 的驱动必须实现 `driver.encode`，参数同 `driver.call`，回 `{"body"}`：它会发的字节，不真发。
   - 作者用 `miyu dev driver-check <包编号>` 查：照 `docs/designs/samples/drivers/` 现成的样本请求，每份编两次、重启扩展再编一次，
     三次要逐字节相同；只在末尾加一条消息的两份请求，编出来的字节在稳定区结束之前要相同；
   - 官方软件源收这样的包时照这个查（软件源的规矩另写）。
3. **记**：`driver.call` 的回答带 `sent`（真发出去的字节的哈希），核心记进 `model.called`，挨着请求的哈希。
   - 同一个请求哈希出现第二次（重试、重放对照），`sent` 却不一样的，记一行 `WARN`「驱动 <名字> 同样的请求编出了不同的字节」，
     每个驱动每次核心运行记一次；
   - 用量里的 `cache_read` 照旧记，主人看得出这家的缓存命中。
4. **声明管压缩**：`cache` 照 05 第七节影响压缩的策略：`none` 的照没有缓存的算，`best_effort` 的照尽力而为。
5. **私有数据**：照第四节第 3 条只回给同一个家族，落盘的那一份重放时原样交回，不重问扩展。

内置驱动的备忘录（V-42）只是核心编码省时间，扩展驱动用不上，也不需要。

### 八、用量、计费、出错、重试、换池

1. **用量**：结尾的 `usage` 照五格记；没报的记成没报，`model.called` 的用量写空、金额写空，计费页照「没报用量」显示，不估。
   压缩照内核自己的估算（`Request.used`），不靠它。
2. **计费**：价格照现在的查法（手写的、模型档案的、目录的），`Tariff::cost` 算，冻结进 `model.called`。扩展不报价钱：报了也不收。
   借订阅的，主人或者包自带的模型资料把价格写成 0。
3. **出错的分类**：`error.class` 是 `retryable`、`rate_limited`、`context_too_long`、`auth`、`quota`、`content_policy`、
   `unclassified` 之一，同 drivers 现成的分类（`classify.rs`）；不认识的当 `unclassified`。`rate_limited` 可以带 `retry_after_ms`，
   同内置驱动解出来的等多久。`message` 是第三方写的字：截到 500 个字、只给人看（时间线、错误提示），不进模型的上下文。
4. **重试、冷却、换池都在核心**，照内置驱动一样走：重试至多 5 次、退避，限速照它说的等，冷却记到这个模型、这把 key，用完了换池里的
   下一个，`context_too_long` 压缩后重试。
   - 扩展自己不重试已经交过增量的调用：交了一半再从头来，回复会重；
   - 还没交增量时连不上、要刷新令牌，扩展自己处理，算在空闲时限里。
5. **驱动不在**（包关着、没批、停下了 `stopped`、清单里没有这个驱动名）：不重试，照「这个端点用不了」走：有池换池里的下一个，
   没有的用人话报「模型驱动 <包>/<名> 不在：<原因>」。正在退避、等着重新拉起的（`waiting`）当 `Retryable`，`retry_after_ms` 照它的
   `retry_in`。具体落到哪一格分类，施工时照 `route/ended.rs` 定，行为照这一条。

### 九、密钥

扩展不该拿到别的供应商的 key：

1. **只交这一家的**：`driver.call` 的 `key` 是这一次调用的供应商配置里引用的那一把（`route/choice.rs` 解出来的，一家一把，
   施工 8-25），别的一把不交。`base_url` 同理，是这一家写的。扩展驱动的供应商可以不写地址（自己登录、走订阅的用不着），不写的不交（施工 MD-2，
   照推荐定）。
2. **只交给明写了它的供应商**：第四节第 2 条，档案、npm 表、默认都不会指向扩展，主人给 Anthropic、DeepSeek 配的 key 不会被一个新装
   的扩展拿走。
3. **声明管交不交**：`key = "none"` 的驱动，配置里写了 key 也不交，`miyu check` 提醒一句；`required` 的没写 key，查不过。
4. **自己登录的**（OAuth、订阅的令牌）：扩展自己存在自己的数据目录里，核心不经手；登录照现成的扩展命令、页面做，不另开口子。
5. **日志**：`driver.call` 的参数进日志时 `key` 写成 `***`，同 `Endpoint` 现在的写法。
6. **它看得到什么**：用它的模型时，发给模型的全部对话（含场所里群友的话、工具结果、图）都经过它，这比 key 要紧。确认屏照这个写
   （第十节）；场所的会话用不用这家模型，照旧是主人选模型时定。

### 十、能力和批准

1. **新加一项能力 `model.driver`**（`miyu-config/src/package/capability.rs`：施工 XG-1 下加了 `tools.commands` 以后是十八项，
   施工 LP-1 加了 `login.page`（第十九项，排在 `act_for_external` 后面）以后是十九项，这是第二十项；表里排在 `search` 后面，同是「人选了它，
   就把内容交给它」的一类）：
   - 一句说明：「提供模型驱动：用它的模型时，发给模型的全部对话都经过它」；
   - 照 PK-3 装的时候批，确认屏列出它声明的驱动名（设计 61 第三、四节的写法）；开着的照「能力批过才拉起」。
2. **不附带网络**：它自己要上网的，另外声明 `network`；只走本机子进程、本机服务的可以不声明。
3. **出厂的内置驱动不走这一路**，也不要这项能力。
4. **收回**：主人关掉、卸掉、撤了批准的，用它的供应商照第八节第 5 条当「驱动不在」，会话不坏，换池或者报错。

### 十二、拍板点

1. **切法：扩展接一整次调用**：
   - 推荐：核心交中间形状、扩展编码、发、解、归类，交回统一的增量（第三节）；借订阅、子进程、WebSocket 都接得上，每个分片不过来回；
   - 另一种是扩展只交编解码、核心发 HTTP：接不了非 HTTP 的，流式来回多，不推荐。
2. **通道：同一条标准输入输出连接，`driver.delta` 通知**：
   - 推荐：不加新的连接方式，先后由同一条连接保住；
   - 另一种是每次调用另开管道，不和工具结果排队，代价是平台上各写一套，第一版不值。
3. **缓存：`contract` 的必须实现 `driver.encode` 过 `driver-check`，结尾报 `sent`**：
   - 推荐：核心看不见线上字节，只能查和记；
   - 另一种是只靠作者自觉，出了问题主人只看到账单变贵，不推荐。
4. **密钥：只交这一家配置里引用的那一把，只交给明写了这个驱动的供应商；自己登录的扩展自己管**：
   - 推荐；
   - 另一种是核心一概不交 key、都让扩展自己管：主人要在两个地方配 key，已经用 `secret` 存好的用不上。
5. **能力：新加第二十项 `model.driver`，装时批**（原来写第十九项，施工 LP-1 先占了第十九项 `login.page`）：
   - 推荐：看得到全部对话，比 `network` 要紧得多，要单独说清楚；
   - 另一种是并进 `network`，批的时候主人看不出它能看到对话。
6. **驱动不在的不重试、有池换池**：
   - 推荐：关了、停了的等也等不来；只有正在退避的照它的 `retry_in` 等；
   - 另一种是一律当可重试，会话会卡 2 分钟（重试的上限）才换池。
7. **设计 23 加两项**（第六节的表）：扩展驱动多的首字时延 p95 5 毫秒、流式多的 CPU 1% 以内，作为策略数据（F1）。
