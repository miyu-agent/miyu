## 扩展工具的效果和声明

扩展经 `provide` 登记的工具，结果也能带效果（`file.changed` 这些），第三方的 `edit` 改了文件，看差异、她看过的、压后重读都走内置那一套；规格里多三格声明：`paths`（哪几个参数是路径）、`background_parameters`、`runs_commands`。

状态：定稿（2026-11-05 主会话分身写，core1 当天定五条，见末尾「定了的」）。XG-1 上做了（2026-11-06，施工单 `docs/construction/XG-1上-扩展工具的效果.md`），XG-1 下做了（2026-11-06，施工单 `docs/construction/XG-1下-扩展工具跑命令.md`：通道挪进新的一层 `miyu-call`）。施工 XG-1（拆法见第七节第 5 条、第八节）。来由：测试会话 e0 的扩展缺口报告第 3 条；设计 00 第四节第 4 点「内置功能不开后门」；设计 44 第三节第 3 条写了「扩展经 `provide` 交的工具要用的话，以后在规格里加同名的两格」；设计 10 第五节本来就写着「第三方编辑器只要报出 `file.changed`，diff 显示……照样能用」，`providers.md` 一直没给这一格。

### 一、现在缺什么

1. **扩展交不了效果**：`tool.call` 的回应只认 `blocks`、`error`、`end_turn`、`sent`、`detail`、`data`、`state`（`crates/miyu-endpoint/src/provide/remote.rs` 的 `Answer`）。第三方 `edit` 改了文件，时间线上没有 +N −M，`view.detail` 的 `files` 是空的；她先读过的文件被它改了，接着用内置 `edit` 被拦「读过以后又被改了」，要重读。
2. **路径不过链**：扩展的工具 `targets()` 是空的，照「不报路径的调用」判（`session/guard.md` 第四条：`read`、`write` 一律放行）。工作区一级下，第三方写工具改工作区外面的文件不问人；内置 `edit` 会问。
3. **两样声明只有内置能写**：`Tool::background_parameters`、`Tool::runs_commands` 是 trait 方法，`RemoteTool` 没实现，扩展换掉 `shell` 后前台会话照样看到后台参数，说明后面也接不上 `miyu call` 那一段。
4. **撤销不改回文件**（施工 U-1，2026-10-15 项目主人定，`10-自带软件.md` 第七节）：内置 `edit` 也一样。效果现在喂的是看差异（`view.detail`、条目的增删行数）、她看过的（`session/tools.md` 第 2 条）、压后重读（`compaction.md` 第九条），撤销只照有效历史重建她看过的。所以「第三方 edit 撤销撤得回」照字面讲，内置的也做不到——见第七节第 1 条。

### 二、规格多的三格（`provide` 的每一件）

| 格 | 写法 | 不对的 `bad_tool`，`problem` 是 |
|---|---|---|
| `paths` | `[{"parameter": "file_path", "write": true}]`：参数是 `input_schema.properties` 顶层的一个，类型是字或字的数组；`write` 不写是假。写了 `write: true` 的，`access` 要是 `write` | `paths` |
| `background_parameters` | `["run_in_background"]`：顶层参数名，不能在 `required` 里（去掉了请求就对不上格式） | `background_parameters` |
| `runs_commands` | 布尔，不写是假；要批过能力 `tools.commands`（第七节第 3 条） | `runs_commands`；没批的回 `needs_approval` |

- 都写在 `provide` 的规格里，和 `access`、`clicall`、`timeout_ms` 放一起（设计 44 原话「在规格里加同名的两格」），跟着登记缓存原样存。清单（`package.toml`）只列工具名，不加（第七节第 2 条）。
- 不写这三格的工具，登记、工具面逐字节和现在一样（`request_shape_probe` 比一遍）。
- `Tool::background_parameters` 的签名从 `&'static [&'static str]` 改成借自己的（`Vec<&str>`）：扩展的名字是登记时读进来的字。

### 三、`paths`：先过链，核心前后各读一次

1. `RemoteTool::targets` 照 `paths` 从参数里取路径（数组的每一项各一条），交给权限链，和内置 `edit` 走同一张判法表：工作区外的写问人、数据根拒、私密目录照表。参数缺、不是字的不出这一条（同内置「参数不对交回空的」）。
2. `tool.call` 多一格 `checked`：链判过的真实位置，照报的先后（就是 `Call::checked`）。扩展应当写这几个位置；链接在判过以后被换掉的，它写的就不是判的那个，照内置 `write` 的规矩自己核对（作者文档写明）。
3. 发 `tool.call` 之前，核心在阻塞线程里把 `checked` 里写的那几条各读一份留着（改前；不在的记成新建）。一份超过 20 MiB 的不读，它的 `file.changed` 照第四节第 3 条丢掉。不写的工具不读，不多花一次磁盘。

### 四、回应多一格 `effects`

1. 写法照 `tool.result` 里效果的那一份（`kernel/events-bodies.md`「效果」），收四种：
   - `{"kind": "file.changed", "path"}`；可以带 `before`、`after`（哈希）、`before_text`、`after_text`，带了的要和核心读的对得上，对不上整条丢；
   - `{"kind": "file.read", "path", "lines"?}`：`hash` 不收，核心读盘算；
   - `{"kind": "file.trashed", "path", "trash"}`：`trash` 只给人看（U-1 起不移回来），至多 4096 字；
   - `{"kind": "todo.written", "todos", "done"?}`：只查写法（设计 44：换掉 `todowrite` 的包要它，`/todo` 和网页的待办才接得上）。
   - 别的种类（`job.*`、`peer.watch` 要核心的账本和端口，扩展起不了会话的任务；`file.shown` 是 `show` 的；`package.state` 已经有 `state`）整条丢，不像内核读日志那样原样留：不可信的东西不进日志。
2. **核心不信扩展说的内容，只信它说「哪条改了」**：
   - 路径换成真实位置后要在 `checked` 里：`file.changed`、`file.trashed` 要是写的那几条，`file.read` 读写都行。没声明 `paths` 的工具，文件效果一条都不收（同 `shell`：命令改的文件没有差异）。
   - `file.changed`：改前用第三节第 3 条留的那份，改后由核心现读；两份一样的丢（没改）。`file.trashed`：路径现在要不在了。`file.read`：哈希照现读的整份。
   - 读成的照内置的样子做成 `miyu_tool::Effect`，交给执行器：存 blob、小的写原文（V-18）、记她看过的，从这一步起和内置 `edit` 交的分不出来。
3. 丢的记一行 `WARN tool effect dropped tool=… kind=… why=…`（`why` 是 `not_checked`、`unchanged`、`mismatch`、`too_big`、`kind`、`shape` 之一），结果别的格照常，不算出错，不告诉她。回应 `error` 为真时丢的 `todo.written` 不算写错、不记（第 4 条，同 `state`；core1 2026-11-06 定）。
4. `error` 是真的照样收文件效果：改了一半出错，改了的是真的，藏起来更糟。`todo.written` 出错的不收（同 `state`）。超时、被掐的没有回应，没有效果（照现在）。

### 五、报假效果拿不到什么；和设计 62

1. 撤销、恢复、重做不写文件（U-1），报假效果写不坏别的文件，也借不到写的权限。
2. 核心照效果读盘的只有两处：这一节的改后、压后重读（`compaction.md` 第九条）。两处的路径都只能是这次调用过了链的，报 `~/.ssh/id_rsa` 进不了压后重读、进不了她的上下文。
3. 改前改后的字节都是核心自己读的：报假内容骗不了看差异的人，最多少报（不报就没有差异，和 `shell` 一样）。
4. 扩展现在没进沙盒、以本人身份跑（设计 61「以你的身份跑」），本来就能自己读写这些文件。这一套守的是「核心不替扩展多做一步」：设计 62 把扩展关进沙盒以后照样成立。`paths` 过了链的写路径正是 62 要按调用放开写的那几条（能力 `fs.write`），62 直接用，不另发明。

### 六、`background_parameters`、`runs_commands` 核心拿它做什么

1. `background_parameters`：`RemoteTool` 照登记的交回，后台运行关着的会话造工具面时去掉（`agents.rs` 现成的 `entry.without`）。扩展照「没给就是假」。扩展起不了会话的后台任务（不收 `job.started`），这一格只管前台会话看不见。
2. `runs_commands`，照内置 `shell` 的几处，一处不按名字：
   - 说明后面接 `miyu call` 那一段（`Tool::clicall_section`）：模板从 `shell` 的资源挪成核心的字一份，`shell` 也读它，字节不变。
   - 通道：会话照现在的条件开（`nested/port.rs` 的 `channel`），`tool.call` 多一格 `channel: {"sock", "token", "bin"}`，扩展把 `MIYU_CALL_SOCK`、`MIYU_CALL_TOKEN` 设进它起的命令、`bin` 放 `PATH` 最前。通道的服务从 `miyu-basesystem/src/shell/channel` 挪到共用的一层（施工时照层序表挑，`miyu-ipc` 一类），认人那一步分两种：`shell` 照这条命令的进程组（现状），扩展照「连上来的是这个扩展进程的子孙」（Linux 照 `/proc` 的父进程链，macOS `proc_pidinfo`，Windows 照快照的父进程号）加令牌。这次调用答了、超时、被掐，通道关（`miyu call` 退出码 3）。
   - `miyu check` 没有沙盒时的 `sandbox_shell` 提醒照它（现成，不用改）。
   - 人在会话里跑命令（设计 57）不交给扩展：`session.send {shell: true}` 认「能给人跑命令的」那一件（`run_for_person` 交得出的），只认 `runs_commands` 会挑到扩展、拿到 `None`。改成 trait 多一个 `serves_person()`，内置 `shell` 是。

### 七、要拍板的点

1. **「撤销撤得回」怎么算**（e0 的红测试照字面会和 U-1 冲突）。
   - A（推荐）：照内置现状。红测试改成「第三方 `edit` 和内置 `edit` 改同一个文件，`tool.result` 的效果、`view.detail` 的差异、条目的增删行数一样；接着用内置 `edit` 不用重读；撤掉那一轮，她看过的照有效历史退回去，文件不动，两边一样」。理由：U-1 是项目主人定的，改回文件交给 git；XG-1 要的是「和内置一样」，不是给扩展多一样内置都没有的。
   - B：重开 U-1，撤销重新改回文件（内置、扩展一起）。要项目主人定，不在 XG-1 里。
2. **声明写在哪**（派工单写「清单里」，设计 44 写「规格里」）。
   - A（推荐）：`provide` 规格。理由：同一件工具的别的属性（`access`、`clicall`、`timeout_ms`）都在这里，`paths` 要对照 `input_schema` 查，清单里只有工具名，查不了。装之前要让人看到的那一样（会跑命令）由第 3 条的能力管，能力本来就写在清单里、装的时候列出来。
   - B：清单每件工具一张小表。两处各写一半，一件事两个真相源。
3. **`runs_commands` 要不要一项新能力 `tools.commands`**（「工具会跑命令，命令里能以这个会话的身份调她的工具」）。
   - A（推荐）：要，开的时候人批，出厂的算批过。理由：通道给扩展的子进程这一次调用期间以会话身份调脚本能调的工具（记忆、会话这些只读的也在里面），是扩展原来没有的一条路；设计 61 装包时照能力列给人看。代码只多一行能力表、`provide` 一处查。
   - B：不要，`tools` 够了。
4. **文件效果信多少**。
   - A（推荐，第三、四节）：要声明 `paths`、过链；扩展只说哪条改了，改前改后核心自己读。报假什么都拿不到，开发包也最省事（`Reply.changed(path)` 一行）。
   - B：不要 `paths`；扩展照事件的写法交改前改后（小的原文、大的先 `blob.put` 给哈希），核心只核对改后和盘上一样、路径在会话这一刻不问人就能写的范围里。多文件的工具（整仓改名）也能报；可改前是扩展说了算，人看到的差异可能是编的，判范围还得在会话那一层另开一个口子。
   - C：照收不查。62 以后就是越权读文件的口子，不取。
5. **施工拆分**。
   - A（推荐）：两步。XG-1 上：`paths`、`effects`、`background_parameters`、红测试转绿；XG-1 下：`runs_commands`（能力、说明那一段、通道挪出来和两种认人、人跑命令只认内置）。理由：通道挪动碰 `shell` 和三个平台，单独一步好验、好回退；上一步就够 e0 的测试。
   - B：一步做完。

### 九、已知边界

- `core/clicall.txt`（进 system 的那一句）写的是「see the shell tool」：会话里只有扩展的跑命令工具、没有内置 `shell` 时，这句指错了地方。不改（core1 2026-11-06）：几乎所有会话都有内置 `shell`，这句是对的；为了这种少见的会话改它，所有人的 system 前缀都要冷一次，前缀稳定第一。
- 认「扩展进程的子孙」照父进程链：Windows 进程快照里的父进程号可能是被重用过的旧编号，现在不比进程起来的先后，靠令牌兜着（core1 2026-11-06 接受）。以后要再加「父进程起得比子进程早」的比较。
- 认「扩展进程的子孙」、扩展进程自己不算，是防误用（令牌漏给别的进程、命令甩出去以后还在调），不是安全边界：扩展起一个子进程就能调。对扩展真正的关口是能力 `tools.commands` 要人批（第七节第 3 条）。e0 复核提，施工 XG-1补 照这样改了作者文档、参考、蓝图的措辞。
