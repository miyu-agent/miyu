## 脚本调工具（clicall）

她在 `shell` 里跑的命令和脚本，可以用 `miyu call <工具> …` 调这个会话的工具。这件事叫 clicall，命令叫 `miyu call`。结果交给脚本，不进上下文；她只看到命令最后打印的东西。要调很多次工具、调用之间有逻辑、要的是汇总的活（搜一串关键词再筛、读一批文档再数、几十个 MCP 查询再和本地的 `git log` 对照），中间结果不用一轮一轮过模型，分支、串联、加总、去重、比较交给代码。

状态：MC1 到 MC14 已定（2026-10-20）：MC1 到 MC4、MC7 到 MC9、MC11 主会话照推荐定；MC5、MC6、MC10 和 MC12 到 MC14 项目主人定，MC10 留名接受（`24-威胁模型.md` T2、第三节）。其余内容为草案，施工照第十一节。

### 一、多出来的是什么

`shell` 本来就能读写文件、`grep`、跑 `git`、`gh`、`curl`。脚本经 `miyu call` 调 `read`、`edit`、`grep`，什么能力都没多，只多出要处理的事：编辑前要先读过、效果、diff、看过的文件。

真正多出来的，是 **shell 够不着、只有核心才有的能力**：

- 核心拿着来源和密钥的：`web_search`（多家来源、冷却、兜底，设计 36）、`web_fetch`（抓不下来的请别家代抓）、MCP 服务器（GitHub 这类，连接和凭据在核心里）。
- 核心拿着数据的：记忆、知识库。数据根在沙盒里是藏起来的（`11-权限与沙盒.md` 第四节），命令读不到。

所以这一份的口径是：**脚本的世界就是 shell 的世界，只补上核心独有的那几样**（MC2）。一次 `miyu call` 是一次嵌套调用，挂在那次 `shell` 调用下面，后台命令的挂在它的任务下面；内核照直接调用的同一条链判（MC3）。

### 二、别家怎么做

2026-10-19 拉的源码，在 `~/.cache/codemode-survey-2026-10-19/`。

| | Codex `89461ea` | opencode `ceaef65` | dsh `687f282e` |
|---|---|---|---|
| 代码在哪跑 | 单独的宿主进程，每次一个新的 V8 isolate，gRPC 连回核心 | 自己写的 JS 解释器，碰不到网络、文件、进程 | 每次一个 Node 子进程，套和 bash 同一套沙盒 |
| 和宿主怎么说话 | gRPC 走标准输入输出 | 同一个进程 | 继承的 fd 7，4 字节长度加 JSON；环境变量只作标记，读到就删 |
| 子调用走哪条链 | 和直接调用完全同一条，来源标签带代码块和序号 | 同一条执行管线 | 同一条审批链，编号 `父编号:ptc:n` |
| 代码里能调哪些 | 默认都能；问人、`sleep`、换上下文窗口、派子代理不能 | 自带的 shell、读写改、grep、搜索、抓网页都不能，主要是 MCP | 除了自己和 `workflow` 都能 |
| 要人确认时 | 等，不设时限，结果扣住 | 每个子调用都问；拒一个，并发挂着的一起拒 | 等，算进 120 秒；「等确认吃掉时限」没解决 |
| 交给代码的结果 | JSON 型给对象，别的给字符串 | 结构化；MCP 的文本像 JSON 就试着解析 | 一律结构化（原来给字符串，程序只能从字里抠任务编号，改了） |
| 子调用进不进上下文 | 不进 | 不进 | 不进（图片补在外层结果后面） |
| 长任务 | 30 秒先交回，后台接着跑，`wait` 取；跨回合的排队等下一轮 | 不管 | 结束时先叫停、再收掉在途的；之后到的丢掉，失败的不重放 |
| 评测 | 没有；新的 10 个模型默认「只能用 code mode」 | 没有；默认开 | 没有；默认关，明说不承诺省 token |

学到的：

1. **子调用一律走直接调用的那条链**，三家都是，没有一家另写一套权限。
2. **都没有让 shell 回调。** 它们先造一个什么权限都没有的运行环境，代码只能经工具碰外界。shell 本来就有权限，所以 `miyu call` 不当安全边界，只守一条：不多给（第八节）。
3. **结构化的结果**：dsh 吃过亏才改。
4. **控制通道的另一头不可信**：dsh 限帧的大小、编号要递增、名字要在白名单里，违反了就杀进程。
5. **父调用结束时先叫停、再收尾**，之后到的丢掉，绝不重放（dsh）。
6. **子调用自己排队，别排进外层占着的那条队**（Codex 给子调用单开一把锁，不然会自己等自己）。
7. **日志别撑爆**：dsh 一开始把子调用的结果全文写进日志，一轮涨几 MB。
8. **都没有评测数据**：这一份第十节的实测不能省。dsh 的 fd 只交给它自己起的 Node 进程；我们的脚本会再起 Python、Node 子进程，继承描述符这条路在实测里断了（第五节第 2 条）。

### 三、哪些工具能调

1. **能不能调，两道都过才行**（MC2）：
   - **访问类别**，内核的硬规矩：只准 `read`、`network`、`execute`。`write`、`install`、`venue`、`outbound` 和不认识的，不管工具自己怎么写，一律拒。第一版的嵌套调用不改长期的东西、不在场所里留下后果。`execute` 的照直接调用判：沙盒能用就在沙盒里跑，用不了的要人确认、得到退出码 4。
   - **字段 `clicall`**，布尔。`Spec` 和快照里的 `ToolEntry` 各一格，照 `need_load` 的加法（施工 L-1）。默认值按来处分：

   | 来处 | 默认 | 改法 | 为什么这样默认 |
   |---|---|---|---|
   | 内置工具、软件包带的工具 | 关 | 说明文件 `tools/<名字>.json` 里写 `"clicall": true` | 它们能报效果、发消息、结束回合（`Done` 的 `effects`、`sent`、`end_turn`），嵌套调用不认这些（第四节第 7 条）；开不开由写它的人说 |
   | 扩展 `provide` 的 | 关 | 写 `"clicall": true` | 同上 |
   | MCP 服务 | 开 | `[[mcp]]`、个人设置的服务表里写 `clicall = false`，这个服务的工具都算 | MCP 工具交回的只有内容，报不了效果、发不了消息；连接和凭据在核心里，正是 shell 够不着的 |
   | 脚本工具 | 开 | 开头注释写 `# Clicall: no` | 交回的只有输出，跑在沙盒里，不多给能力；她只知道它的名字，不知道脚本在哪、参数怎么交（`MIYU_ARGS_JSON`），经 `miyu call` 调是一样的口子 |

   人在个人设置里能盖过上表的默认（2026-10-20 项目主人定，施工 M-2）：`clicall.tools.<工具名>` 按单个工具，`clicall.mcp.<服务名>` 按 MCP 服务，先照工具自己那一项、再照服务那一项、都没写的照来处，同 `need_load` 的 `loading.*`（施工 L-3）。类别不准的照样拒。

   MCP 的权限照直接调用判：服务标了只读的算 `read`、放行；别的算 `network`，工作区一级要人确认，脚本里得到退出码 4（MC4）。脚本工具算 `execute`。

2. **出厂开的**：`web_search`、`web_fetch`、`memory_search`、`kb_search`、`kb_read`，表情包的 `meme_search`（2026-10-20 项目主人加），和 `history`、`sessions`、`session_usage`、`packages`（2026-10-21 项目主人定的通则，施工 M-2 补、再补）。都是只读的、不报效果、不起任务。

   **开不开的通则**（2026-10-21 项目主人定，取代 10-20 那句「只读、搜索类、和会话本身无关的」）：要读、要查的工具，并且 shell 原本不方便做到的，就开。以后加的工具照它定默认值；写给第三方作者的说明也照它劝。照这一条：
   - 开：上面那几件。`history`、`sessions`、`session_usage`、`packages` 读的是数据根里的东西，沙盒里的 shell 读不到；脚本能先列会话、再用 `history` 的 `session` 挨个翻。
   - 不开：`read`、`glob`、`grep` 是只读的，但 shell 自己就能读、能找，开了省不下请求（第十节第六轮实测：开着 18 次一次都没用），`read` 还要记「看过」。`jobs` 能停任务、`goal` 能设和结束目标，不只是读。别的会改东西、发东西、问人。
   - 注意：工具登记的访问类别不够当依据。发消息、派子代理、问人这几件登记的都是 `read`，挡住它们的是 `clicall` 这一格（第 4 条：内核两道都查）。

3. **出厂不开的，和为什么**：

   | 工具 | 为什么 |
   |---|---|
   | `read`、`glob`、`grep`、`write`、`edit`、`trash`、`show` | shell 自己能做；开出去要守「先读过」、效果、diff |
   | `shell` | 就是它自己 |
   | `subagent`、`jobs`、`send_message`、`goal`、`todowrite`、`ask_user` | 会改东西、发东西、问人，或者和回合绑着，脚本里调语义不清 |
   | `load_tools` | 内核当场答、结果进上下文才有用；脚本要格式用 `--schema`（第六节） |
   | `package` | 装卸要人确认 |
   | `remember`、`forget`、`kb_save`、`kb_edit`、`kb_delete`、表情包的写类、`render_image` | 写长期的东西，出处要挂在回合上；第一版不开 |
   | QQ 平台的工具（`chat_send`、`recall`、`mute` 这些 `venue` 类，和 `members`、`skip_reply`） | 在场所里留下后果，或者只在一轮里有意义；批量从脚本发出去风险最大 |

4. **内核拦**：名单写进 shell 的说明（第九节），但拦在内核：类别不准的、`clicall` 不是 `true` 的，内核当场拒（dsh 踩过只在说明里不列、照样调得成的坑）。
5. **要先加载的工具**（设计 25 W9）照样能调，不用先 `load_tools`：参数照完整格式校验，和 W9「不加载直接调」一致（2026-10-20 和内核那边对过）。MCP、脚本工具默认就是要先加载的（W9 于 2026-10-20 改），工具多的 MCP 服务不占 tools 数组；脚本这边本来也只列名字（第九节），要格式用 `--schema`。
6. **场所会话不另外关**：`venue` 类一律调不了，剩下的群里能直接调的，脚本里调也一样。外部身份的会话照旧只在关住读的沙盒里跑命令（`11-权限与沙盒.md` 施工 5-12），`miyu` 执行不执行得了照第五节第 4 条。

### 四、内核：嵌套调用

1. **编号**：`NestedId`，父级的编号加一个从 1 数的序号。父级是前台那次调用的 `CallId`，写成 `call_12_1#3`；或者后台命令的任务编号 `JobId`，写成 `j7#3`（MC5）。用 `#` 不用 `.`：`j7.3` 已经是子会话 `j7` 派出去的第 3 个任务（`kernel/ids.md`）；`#` 也和界面上的 `#序号` 一致。解析时照最后一个 `#` 切；写出来再读回去要一样，有往返测试。`CallId` 不动，也不加后缀（它只认回复里的调用，`ledger/shape.rs`）。执行器的「派、判、跑」照收嵌套编号。
2. **输入**：执行器交 `NestedCall {parent, n, name, args}`。内核照 `start_tools` 的那几样查：
   - 父级还活着、开了通道（第五节）：前台的是这一步里正在跑的调用，后台的是还没报告的任务。不然拒（「所属的命令已经结束」）。
   - 工具在工具面上、`clicall` 是 `true`（`ToolRule` 多这一格）；参数照 `repair` 修；只读生效时写的当场拒（白名单里没有写的，照样查，名单以后会变）。
3. **判**：出 `GuardTool`，带嵌套编号、这一刻实际生效的级别、本会话放行过的规则（`grants.granted()`），执行器照旧在阻塞线程里 `judge`。后台的也照这一刻的级别判，不照任务起来时的（命令本身的沙盒收不紧，嵌套调用每次现判，收得紧）。「这一刻」照内核记着的现在生效的那一级：收紧当场算，放宽要等下一次模型请求以后才算（同 `session.set_permission_level`），所以回合外只会更严、不会更松（2026-10-20 内核那边审过，照推荐定）。结论：
   - 放行：派。
   - 拒绝：记一条、回给脚本，退出码 1，拒绝的那一句照直接调用的原话。
   - 要问人：**不问**，记一条、回给脚本，退出码 4。有没有人在场都一样（MC4）。本会话放行过的规则照样算：人选过「本会话都允许」的，链判出来就是放行。
4. **跑**：出 `RunTool`，带嵌套编号。执行器照 `Tools::run` 造 `Call`，但：
   - 没有任务端口（不能起后台）、没有子代理、没有提问端口、没有目标端口。
   - 沙盒照这一刻的级别写，和直接调用一样。
   - 不开通道：只有直接调用的 `shell` 开（第五节第 1 条）。嵌套调起的脚本工具拿不到通道，不会一层套一层。
5. **排队**：嵌套调用一个父级一条队，**不进这一步的调度**。父 `shell` 是 `execute`，在 `Step::ready` 里独占；嵌套的要是也排进去，会自己等自己（Codex 那把单开的锁）。队里只读的一起跑，别的照到的先后一个一个。同时在跑的有两道上限：一个父级 8 个，整个会话（前台加所有后台任务）16 个，免得几个后台脚本一起把搜索的额度打满；数在策略快照里。到了上限的不拒，排队等：前台的等的时间算在父 shell 的超时里，后台的等到有空位或任务结束。对端断开、父级结束时，排着的也照「已取消」记一条（第 6 条）。
6. **收尾**：
   - 嵌套调用跑完，执行器先把结果存成 blob，交 `NestedDone`；内核记事件（第七节），落了盘，执行器再把结果交回脚本。照「回答落了盘再交」。
   - 前台：父调用交回来（`ToolDone`），还没了结的嵌套调用先叫停、记「已取消」，再记父调用的结果。账本守：父调用的 `tool.result` 之前，它的嵌套调用都已了结。
   - 后台：任务结束（跑完、被叫停、撤销时停掉任务、会话停下），还没了结的先叫停、记「已取消」，再记 `job.reported`。账本守：任务的 `job.reported` 之前，它的嵌套调用都已了结。
   - 打断（`cancel_step`）时，前台的嵌套调用跟着父调用一起停；后台任务照旧不受打断影响，它的嵌套调用也接着跑。
   - 之后才到的结果丢掉，不重放（dsh）。核心崩了重启：嵌套调用没有「开始」的事件，不用补；父调用、任务照旧各自的补法。
7. **嵌套调用不带效果、不发消息、不结束回合**：`Done` 里的 `effects`、`sent`、`end_turn` 不认。能调的工具本来就不报（第三节第 1 条）；报了的是开错了，执行器记一行 `ERROR`、丢掉，结果照常交回。这样只认 `tool.result` 效果的那一批（任务、留言、diff、待办）都不用改。
8. **不算步数**：步数上限数的是模型请求，嵌套调用不算。后台任务的嵌套调用在回合之外也能来，不开回合、不叫醒她：它的结果只给脚本，任务结束时照旧由 `job.reported` 开一轮。

### 五、通道

1. **哪些 shell 开**：这个会话的工具面上有能调的工具，前台、后台的 `shell` 都开（MC5）；三个平台都开（MC13）。子代理的 shell 开的是子会话自己的通道，用子会话的工具和权限。
2. **形状**（MC6）：一次 `shell` 调用一个端点，只为这一条命令开：
   - Linux、macOS：一个 Unix 套接字，放在只有本人进得去的目录里（`0700`，在临时目录下，不在数据根里），名字随机。
   - Windows：一个命名管道 `\\.\pipe\miyu-call-<随机>`，访问控制开给本人，另给本人沙盒里的命令只够连上、读写的权限（施工 M-3 下改：Windows 沙盒成了 MXC 的基础容器，令牌是 AppContainer 的，只开给本人的连不上）。
   - 告诉子进程的是两个环境变量：`MIYU_CALL_SOCK`（路径或管道名）、`MIYU_CALL_TOKEN`（128 位随机的令牌），在 `env::passed` 之后加，同 `MIYU_ARGS_JSON`。环境变量所有语言起子进程都默认继承。
   - 每次 `miyu call` 连上去，发一个请求、收一个回答：4 字节大端长度加 UTF-8 JSON，请求里带协议版本和令牌。
   - **为什么不用继承的描述符**（原来的做法，编号 3）：Python 的 `subprocess` 默认关掉 0、1、2 以外的描述符，Node 起子进程只交标准输入输出，Go 要显式传。脚本里再起一层子进程的 `miyu call` 就连不上。实测里说明写了「Python 也行」以后，13 次用了 `miyu call` 的运行有 10 次栽在这上面，反复调试，比旧写法还费（第十节第四轮）；换成环境变量以后 0 次。
3. **认人**：两道都过才答，过不了的回退出码 2（`miyu call only works from processes started by the command Miyu ran.`）。
   - 令牌对得上。
   - 连上来的进程是这条命令的进程：Linux、macOS 照对方的进程号（Linux `SO_PEERCRED`，macOS `LOCAL_PEERPID`）查它的进程组，要等于 `shell` 起命令时的那一组（整组杀掉用的同一个，`process.rs` 的 `Group`）；Windows 照 `GetNamedPipeClientProcessId` 拿进程号，查它在不在这条命令的作业对象里（`IsProcessInJob`）。
   - 有了第二道，令牌漏了（打进日志、`env` 印出来）也只有这条命令自己的进程树用得上。`setsid`、`start_new_session` 出去的进程离开了进程组，从一开始就调不成（原型实测：bash、Python 里调都成；`setsid` 出去的被拒）。
4. **找得到 `miyu`**：核心起来时，在一个沙盒读得到、只放这一个东西的目录里放一个 `miyu`，指向自己的可执行文件（`Env.exe`）；开了通道的命令，这个目录放在 `PATH` 最前面。只有这一个文件，挡不住别的程序；又保证 `miyu call` 和核心是同一个版本。Linux、macOS 放符号链接；Windows 建符号链接要特权，放硬链接，建不成的照核心所在的目录。目录在哪画蓝图时定，不能在数据根里（沙盒藏着数据根）。外部身份的会话只放行几个系统目录，那里执行不了的，`miyu call` 照「命令找不到」失败，第一版不另管。
5. **沙盒要放行这一个端点**：Landlock（内核 7.1 起拦连路径上的套接字）、macOS 的 Seatbelt（`base.sb` 有 `(deny network-outbound (remote unix-socket))`）照这一条命令的套接字路径各加一条放行，别的照旧拦。M-3 先在两个平台上实测。
6. **另一头不可信**：
   - 请求帧超过 1 MiB 的断开；一次连接只收一个请求；同一个父级同时连着的不超过 32 个，多了的直接断开（脚本看到退出码 3）。
   - 协议版本对不上回一句、退出码 2。
   - 核心写回结果不能被卡住：写是异步的，对方不读就等到父级结束时一起关。
7. **作废**：父级一结束（前台的调用跑完、超时、打断，后台的任务结束，会话停下），关掉端点、删掉套接字，令牌跟着作废；脚本里等着的 `miyu call` 读到结尾，退出码 3。
8. **不在会话里的 `miyu call`**（MC11）：你在自己的终端里敲、Claude Code 这类别的程序调，没有这两个变量，或者有、但连不上、令牌和进程不对，一律退出码 2，**不退回去经核心的协议调**。
   - 有没有通道不看环境变量在不在：变量谁都能设，设了也过不了第 3 条。
   - 不退回是因为：会话里跑在沙盒外的命令（`outside_sandbox`，人确认过的）读得到本机令牌。没有通道就改走协议、以本人的身份调，就绕过了这个会话的权限。
   - 会话之外没有「借谁的权限、用哪个人格的记忆、在哪个工作目录」可以照，要的话是另一样东西：Miyu 的工具给别的程序用。现在给别的程序的口子是跟她说话（`miyu ask -s <会话> --from <名字>`，`22-命令行.md` 第四节），不是直接用她的工具。

### 六、`miyu call` 的样子

```text
miyu call <工具> [--<参数> <值>]…
miyu call <工具> --json '<JSON 对象>'
miyu call <工具> --json -              （参数从标准输入读）
miyu call --schema <工具>…             （一次查几件）
miyu call <工具> --schema
```

1. **具名参数**：`--query "niri 输入法"`、`--limit=8`；同一个参数写几次的是数组。值一律当字符串发，内核照工具的格式用 `repair` 修成数、布尔、数组，和修模型写错的参数是同一个函数。嵌套的对象用 `--json`。在 bash 里拼 JSON 是写脚本失败的大头（引号、转义），具名参数把它绕过去。
2. **`--schema`**：打印这件工具完整的说明、参数格式，再加一行 `Result:`，是结果的样子（有结构化结果的写字段，没有的写 `text`）。后面跟几个名字就一件一件印，有一件不成的照印报错、其余照常，退出码取不成的那件的。`miyu call <工具> --schema` 也认：实测里她常这么写。执行器照快照答，不进内核、不记事件。
3. **结果**：
   - 有结构化结果的，成功了一律标准输出一行 JSON，中文不转义；搜不到的也交同一个样子，列表是空的（原型实测：搜不到时交一句文字，脚本照 JSON 解析就崩了）。结构化结果放在 `Done` 新加的一格 `data`：只交给脚本，不进上下文，也不进 `tool.result`。出厂的四件照它们现在的 `detail` 填（`web_search` 交 `links` 那一张、`memory_search`、`kb_search`、`kb_read` 交各自的那份）；MCP 交 `structuredContent`（现在有文字时它被丢掉了，这里留下来）。
   - 没有的，照原样输出文字，末尾带换行。`web_fetch` 就是这样：正文本来就是 Markdown，分页照旧，翻页带 `--page`。
   - 图片不交：标准错误写一句「图片没有交给脚本」，文字照常输出。
   - 不另截断：工具自己的上限照旧（`web_fetch` 一页 3 万字），帧的上限 16 MiB。最后进上下文的只有 shell 的输出，那一层照旧截（3 万字，头尾各留）。
4. **退出码**：照 `22-命令行.md` O1。

   | 码 | 意思 | 标准错误的例子 |
   |---|---|---|
   | 0 | 成功，结果在标准输出 | |
   | 1 | 工具执行了但出错，或者权限拒绝 | 工具自己的原话；拒绝照直接调用的原话 |
   | 2 | 用法不对，没执行 | `No tool named web_serch. Did you mean web_search?` `miyu call does not work for chat_send; call it directly. Tools that work with miyu call: web_search, web_fetch, mcp__github__*.` `Bad args for kb_read: path is required.`（后面跟上这件的 `--schema`，省得再查一次） `miyu call only works inside a command Miyu runs.` `miyu call only works from processes started by the command Miyu ran.` |
   | 3 | 被打断，或所属的命令已经结束 | `Interrupted.` `The command this call belongs to has ended.` |
   | 4 | 要人确认，没做 | `This call needs approval, which a script cannot ask for. Call mcp__github__create_issue directly.` |

   报错是给她看的，一律英文（`26-提示词.md` J3），放在资源文件里、登记；一句话，能指个改法的跟一个（MC8）。

### 七、日志和界面

1. **事件 `tool.nested`**：每个到了内核的嵌套调用记一条，了结时记：父级编号（调用或任务）、序号、工具名、参数原文、结局（`ok`、`error`、`denied`、`needs_approval`、`cancelled`）、用时、结果（存成 blob，事件里只放哈希和字节数）。`by` 记 `Kernel`，归属照 body 里的父级编号认，和 `job.reported` 一样；不为它改 `By`（`By::Tool` 只装得下 `CallId`，任务编号、`NestedId` 都放不进去）。
2. **不进上下文**：组装请求时跳过（`miyu-assemble/src/render.rs` 的跳过列表，同 `question.*`、`tool.approval_*`）。压缩只认消息、回复、工具结果，不用另登记。请求的样子要逐字节不变：`request_shape_probe` 和 `docs/designs/samples/requests` 下的样本证明前缀没动。
   - 撤销：前台的照它落的那一轮，撤销一轮，那一轮的 `tool.nested` 跟着出有效历史。后台的照父任务归属：任务起来的那一轮被撤销，任务照现有的规矩停掉，它的 `tool.nested` 跟着那一轮出有效历史，不照它自己落在哪一轮（多半在回合外，或之后别的回合里）。账本、有效历史各一条测试。
3. **账本**：父级还活着才收：前台的是正在跑、还没记结果的调用，只在回合里；后台的是还没报告的任务，回合内外都收（第四节第 8 条）。
4. **界面**：一律照事件画，头不预先判断这次 `shell` 会不会调工具（MC14）。
   - `shell` 那一行照旧是「执行命令 · 用时 · 标题」，后面多一段 `· #序号 工具显示名`，是最近一次嵌套调用，例如 `执行命令 · 12s · 统计关键词 · #7 网页搜索`。没调过的没有这一段，调了的随事件刷新。一套画法兼容两种情况，不靠猜命令里有没有 `miyu call`（调用可能在脚本文件里、Python 里，也可能写了没走到）。
   - 显示名照 `display_name`，跟着界面语言（`05-内核接口.md`）；没有显示名的照工具名。序号就是嵌套调用的序号（第四节第 1 条）。
   - 所以嵌套调用开始时推的临时事件、了结时的 `tool.nested` 都要带：父级编号、序号、工具名。显示名由视图投影照工具名补（`04-核心协议.md` 的条目文字）。
   - 展开那次 `shell`：一行一个嵌套调用，`#序号 显示名 参数摘要 → 结局 · 用时`，点开看结果。参数摘要照 `summary` 挑的那个参数。这一块是给人审脚本到底调了什么的（第八节）。
   - 后台命令的嵌套调用挂在任务那一行下面，画法相同。
   - 开始时那一条用协议里现成的临时推送（不落盘、没有 seq，`docs/reference/events.md`），样本放进 `docs/designs/samples/transient/`，不另造一种。
   - 头断了重连：快照里带上还没了结的嵌套调用（父级、序号、工具名），照现在「正在跑的工具」那一格的办法给，重连以后接着刷新。
5. **要改的**：事件表和正文、账本、组装、样本 `docs/designs/samples/events/tool.nested.jsonl`、协议参考的中英两份、蓝图 `kernel/events.md`、推给头的推送和快照。

### 八、安全

1. **口径**：`miyu call` 不是安全边界，只守「不多给」：嵌套调用能做的，她直接调都能做，判法一样（MC3）；白名单都是只读的（MC2）。
2. **通道会到这条命令的所有子孙进程手里**：那次 shell 调用里起的一切，`make`、`npm install` 的安装脚本、`cargo` 的 `build.rs`，只要还在这条命令的进程组里，在父级结束之前都能调白名单里的工具。后台命令的通道活到任务结束，时间可能很长。搜索、抓网页不算新口子：沙盒本来就不管网络（`11-权限与沙盒.md` 第四节）。**新口子是记忆、知识库，和 MCP 服务里的私有数据**：数据根在沙盒里藏着，命令原来读不到，现在开着通道的命令能经 `memory_search`、`kb_read`、MCP 读到，再经网络发出去。项目主人 2026-10-20 留名接受（MC10，`24-威胁模型.md` 第三节）。
3. **压着它的几样**：
   - 只在那次调用、那个任务活着的时候；只认这条命令进程组（作业对象）里的进程（第五节第 3、7 条）。
   - 只读的白名单；写的、对外的不开。
   - 每一次都记 `tool.nested`、挂在 shell 或任务下面给人看：一次 `npm install` 下面冒出来的 `memory_search`，人看得见。
   - 后台的嵌套调用每次照这一刻的级别判：人切到只读，下一次就照只读（第四节第 3 条）。
4. **想过、没选的**：命令里写了 `miyu call` 才开通道。她常常先把脚本写进文件再 `python3 x.py`，命令里看不出来，这一条会让最常见的用法失败。

### 九、给她看的字

两处：`shell` 的说明末尾一段，讲怎么用；system 里一段，讲什么时候用（MC12）。两处都只在这个会话的工具面上有能调的工具时才带。

**`shell` 的说明末尾**：

```text
Commands and scripts you run here can call tools: miyu call <tool> --<param> <value>... (or --json '<object>'; --json - reads it from stdin). It works from any language that can run a command (bash, Python, ...), so tools become functions in real programs: branch on their results, chain and combine several tools, run calls in parallel, mix them with local files and programs, and keep only what matters. Write the whole program at once: call, process and print the answer in one script, rather than saving results and inspecting them step by step. Each call prints its result to stdout: one line of JSON in the shape below, or text for tools without one. Tool results stay inside the script; only its final output comes back to you, so print just what you need. Exit codes: 1 the tool failed or was denied, 2 bad usage, 3 interrupted, 4 needs approval (call that tool directly instead). miyu call --schema <tool>... prints the parameters of one or more tools. Tools that work with miyu call: {tools}.
Example: {example}
JSON shapes: {shapes}
```

**system 里**：

```text
You can write programs that call tools. When a task takes many tool calls or real logic around them (branches, loops, one tool's results feeding another, tool results mixed with local files or programs) and you only need the outcome, write it as one script with miyu call (see the shell tool) and print only the answer. For one or two calls, or when you need to read the results yourself, call the tools directly.
```

1. **她怎么知道哪些能调**：`{tools}` 照这个会话工具面上两道都过的（第三节第 1 条）生成。预设关掉的软件包不在工具面上，也就不列。
   - 一个 MCP 服务的写成 `mcp__github__*`；脚本工具、别的照名字列。
   - 工具面在一个会话里不变，这一段也就不变，不碰前缀；人改了预设、装了包，下一个回合工具面重算时一起换（`25-工具加载.md` 第五节的口径）。
   - 调了不能调的，退出码 2 的那一句后面跟上能调的名单（第六节第 4 条）。
   - **名单只说 `miyu call` 能调什么**：写成 `Tools that work with miyu call: …`，主语就是 `miyu call`。不写 `Callable here`、`Available tools` 这类话：放在 shell 的说明里，她会读成「这个会话只能用这几件」。原来跟在后面的 `Call every tool directly as usual.` 去掉了：它也能读成「都直接调、别用 `miyu call`」（2026-10-20 项目主人定）。
2. **`{example}` 照会话的 shell 换**，同 `{shell}`：核心起来时定一次，会话里不变，不碰前缀。三种做的是同一件事（数一次搜索里各网站出现几次）：

   | shell | 例子 |
   |---|---|
   | PowerShell（5.1、7） | `miyu call web_search --query niri \| ConvertFrom-Json \| ForEach-Object { $_.links.site } \| Group-Object \| Sort-Object Count`（自带的，不靠别的程序） |
   | bash、zsh，`PATH` 上有 `jq` | `miyu call web_search --query niri \| jq -r '.links[].site' \| sort \| uniq -c` |
   | bash、zsh，没有 `jq`、有 `python3` | `miyu call web_search --query niri \| python3 -c 'import sys,json,collections; print(collections.Counter(l["site"] for l in json.load(sys.stdin)["links"]))'` |
   | 都没有 | 这一行不带 |

   jq 和 Python 两行实测效果一样（第十节第五轮）；PowerShell 那行等 Windows 的通道做出来在虚拟机上测。
3. **`{shapes}`**：能调的工具里有结构化结果的，一件一段 `名字 {字段…}`，照它们的 `data` 生成；没有的统一一句 `web_fetch and MCP tools without structured output print text.`。
4. 照「给模型看的字克制、有账」：两处都量 token、登记（`26-提示词.md` 第十节），施工 M-4。

### 十、实测

照 `00-设计理念.md`「加字之前先实测」。原型（工作树 `.worktrees/M-0-脚本调工具原型`，分支 `step/M-0-脚本调工具原型`，只为实测，不合）走捷径：不进内核，执行器当场 `Guard::judge`、当场跑；说明和 system 那段照环境变量换。真的工具、真的模型：第一轮官方 `deepseek-flash`，以后 ClinePass 的 `deepseek-v4.1-flash`。题、脚本、每一次的原始记录在 `~/.cache/miyu-remake/m0-eval/`（`results*.jsonl`、`summary*.txt`、`prompts/`）。

1. **题**：只挑 shell 做不到的，能算出标准答案的自动判分。
   - A1：10 个关键词各搜一次，数 github.com 的条数、一共几个网站（`web_search`）。
   - A2：知识库 10 篇文档，各数一个词出现几次，列前 5（`kb_read` 翻页）。
   - A4：知识库里搜 8 个词，各报排第一的出自哪篇（`kb_search`）。
   - W1：搜 5 个词，结果里的 GitHub 仓库去重、逐个打开，看提没提到 niri（搜索 → 抓网页串联）。
   - W2：读工作目录里的词表，每个词搜知识库、读排第一那篇的全文、数次数（本地文件 → 搜 → 读 → 数）。
   - 对照：C2 一次搜索就够；C3 读一篇就够。看会不会乱用。
2. **量**：从会话日志取请求次数、token（没命中缓存的、命中缓存的、输出，三样都算钱，合计看）、用时、判分、`miyu call` 用了几次。每格 4 到 6 次。
3. **结果**：

   | 轮 | 比的 | 看到的 |
   |---|---|---|
   | 一（官方 flash，3 次） | 关、开 | 27 次里只用了 4 次：不知道该用。知识库内容在磁盘别处有副本，模型直接 grep，测歪了，换成只有一个数据根重测 |
   | 二（4 次） | 关；只写 shell 说明；只写 system；shell 说明加 system 一句 | A2 关着的 4 次都超时、0 分，开着的 12 次全对；「shell 说明加 system 一句」最省：18 次请求、33 万 token，关着的 42 次、140 万。只写 shell 说明的用得少（A4 一次没用） |
   | 三（4 次，并行） | 关；第二轮写法；「写成程序」的新写法 | 重活：W2 关着的 45 次请求、187 万 token（答对的两次是在磁盘上找到旁路副本），开着的 14～22 次、12～23 万，全对。轻活：A1、A4、W1 用了脚本请求反而多，新写法比第二轮写法费 |
   | 四（4 次） | 新写法的几种改法 | 新写法费的主因找到了：说明写了 Python，她就用 Python 的 `subprocess` 调，描述符断了（第五节第 2 条）；换成环境变量 |
   | 四重跑（4 次） | 同上，通道修好 | 四道题全部 token 的中位数合计：第二轮写法 387k，新写法 199k，加例子的（第九节那一版）164k，压缩版 201k。正确率都满分 |
   | 五（6 次） | 例子用 jq、用 Python | 194k 对 196k，一样 |
   | 六（6 次，2026-10-20） | `read`、`glob`、`grep` 开不开给脚本（名单里多三个名字、原型真放行） | 三道碰一批本地文件的题（两道纯本地、一道本地加知识库），开着的 18 次里脚本一次都没调这三件：纯本地的直接用 `rg`、Python 数完，不经 `miyu call`；配知识库的只经它调 `kb_search`，本地文件 Python 自己读。token 中位数合计 138k 对 148k，各题方向不一，是波动；正确率一样 |

4. **结论**：
   - 过了第十节原定的线：要调很多次的活（A2、W2）请求次数少一半以上，正确率不降（关着的做不出来）。
   - 只调几次、能一次并行发完的活（A1、A4）省不了请求，全部 token 和关着的差不多或更少。
   - 对照题几十次里只有一次用了 `miyu call`：一次搜索，两次请求，没多花。
   - 读、找本地文件的工具开给脚本用不上（第六轮）：脚本本来就能读，她也这样做。项目主人 2026-10-20 照这一轮定：`read`、`glob`、`grep` 不开。
   - 一行例子比口头叮嘱管用：只加「一次写完、格式不用试」的那版反而更费；加了例子，她照着写一行管道就办完。
5. **要注意的**：每格只有 4 到 6 次、一个模型。搜索来源偶尔交回垃圾结果（ASMR 网站、example.com），她会反复重搜，W1 噪声很大，取中位数。沙盒整盘能读，测试会话会去磁盘上找旁路副本、交叉核对，开着的那几组的开销也被抬高了。

### 十一、施工拆分（草案）

| 步 | 做什么 |
|---|---|
| M-1 | 内核的嵌套调用：`NestedId`（父级是调用或任务）、两种输入、`GuardTool`/`RunTool` 收嵌套编号、一父一队和会话的总上限、父调用结束和任务结束时收尾、`tool.nested`、账本（前台只在回合里、后台回合内外）、组装跳过、样本、协议参考。用测试里的假执行器驱动，不接通道 |

### 十二、决定

**MC1. 走 shell 回调，不另做运行代码的工具**

- **已定（2026-10-20 主会话照推荐定）：她在 shell 里用 `miyu call` 调工具。**
- 未选：另做一个 `exec_code`，在 V8、QuickJS、自己的解释器里跑（Codex、opencode、pi、dsh）。要另起一个运行环境；两个能写代码的入口，她每次要挑；和 `gh`、`jq`、`git` 混不起来。
- 重开条件：实测她在 shell 里写脚本的失败率明显高于别家在受限运行环境里的。

**MC2. 只开放 shell 做不到的，白名单**

- **已定（2026-10-20 主会话）：访问类别只准 `read`、`network`、`execute`（内核拦）；再看 `clicall`：内置、软件包、扩展的默认关，写了才开，出厂开 `web_search`、`web_fetch`、`memory_search`、`kb_search`、`kb_read`；MCP、脚本工具默认开，能关。**
- 未选 A：一律默认开、逐个拉黑。软件包、扩展的工具能报效果、发消息、结束回合（例如表情包的 `meme_send` 类别是 `read`，交回 `sent` 当成这一轮的回话、默认结束回合），不声不响开给脚本，嵌套调用又不认这些，脚本以为发了、其实什么都没发；文件工具开出去要守一串不变量，却不多给能力。
- 未选 B：一律默认关。MCP 和脚本工具正是 shell 够不着、又报不了效果的那一类，默认关就要人一件一件去开。
- 重开条件：实测里常见的活缺了某件不在名单上的工具。

**MC3. 嵌套调用由内核判**

- **已定（2026-10-20 主会话）：每次 `miyu call` 是挂在父级下面的嵌套调用，内核照直接调用的同一条链查、判，执行器照同一个 `Tools::run` 跑；结果记 `tool.nested`，不进上下文。**
- 未选：执行器旁路只调 `Guard::judge`。判的时候要的级别、放行过的规则、只读、参数修正都在内核里。
- 重开条件：无。

**MC4. 要人确认的不等**

- **已定（2026-10-20 主会话）：链判出「要问人」的，当场拒，退出码 4，告诉她直接调；有没有人在场都一样。人选过「本会话都允许」的照放行。**
- 为什么：脚本是做批量的，一项一项问人，批量本身就不成立；要人点头的那一件，她直接调，人照常确认。后台的本来也没人等着问。
- 未选 A：停下来等，不设时限（Codex）。shell 的超时最后照样杀掉。
- 未选 B：等，算进 shell 的时限（dsh）。dsh 记着这是没解决的坑；一步里也没有挂这种确认的位子，要另造一套状态。
- 重开条件：实测里常见的活经常停在退出码 4 上。

**MC5. 前台、后台的 shell 都开**

- **已定（2026-10-20 项目主人定）：前台的挂在那次调用下面，调用结束就作废；后台的挂在任务下面，任务结束就作废。**
- 为什么：带 `miyu call` 的脚本不能放后台，长的批量活就只能卡在前台的超时里；实测里也撞见她把脚本放到后台、调不成、退回去一件一件直接调。任务本来就有自己的一生（`job.started` 到 `job.reported`），嵌套调用挂上去，账本和收尾都有现成的边界。
- 未选：只给前台（原来的 MC5）。理由是父调用结束以后的嵌套调用挂在哪、回合结束了怎么办；挂在任务下面就答了。
- 重开条件：后台脚本经常把搜索额度、会话的总上限打满。

**MC6. 通道是环境变量里的端点加令牌，只认这条命令的进程**

- **已定（2026-10-20 项目主人定，照实测改）：一次 shell 调用一个 Unix 套接字（Windows 是命名管道），路径和令牌放在环境变量里；连上来的要令牌对、进程在这条命令的进程组（Windows 是作业对象）里。**
- 未选 A：继承的描述符（原来的 MC6，编号 3 上的入口）。Python、Node、Go 起子进程默认不交多余的描述符，脚本里再起一层就断；实测 13 次里栽了 10 次（第十节第四轮）。
- 未选 B：经核心的协议套接字加本机令牌。那两样是故意藏着的，不能为这个开口子。
- 未选 C：只靠令牌。令牌打进日志、`env` 印出来就漏了；加上进程的检查，漏了也只有这条命令自己的进程用得上。
- 重开条件：某个平台上拿不到对方的进程号，或者合法的用法常常离开进程组。

**MC7. 结果结构化优先，不另截断**

- **已定（2026-10-20 主会话）：有 `Done.data` 的交一行 JSON（搜不到的也交），没有的交文字；图片不交；只有工具自己的上限。**
- 未选：照直接调用截断。截断是护上下文的，结果不进上下文。
- 重开条件：无。

**MC8. 参数和报错为写脚本的她设计**

- **已定（2026-10-20 主会话）：具名参数为主、`--json` 兜底，类型交给 `repair`；`--schema` 一次能查几件、带结果的样子，`<工具> --schema` 也认；参数不对的报错直接附上格式；报错一句话加一个改法。**
- 未选：只收 JSON；`--schema` 一次一件；报错只一句、不加建议。
- 重开条件：实测里具名参数反而更容易写错。

**MC9. 嵌套调用不带效果**

- **已定（2026-10-20 主会话）：不认 `effects`、`sent`、`end_turn`，不给任务端口。**
- 未选：照 `tool.result` 接效果。任务、留言、diff、待办那一批消费方都只认 `tool.result`，都得改；白名单里也没有报效果的工具。
- 重开条件：要开放写类工具时。

**MC10. 开着通道的命令能读记忆、知识库、MCP 的数据**

- **已定（2026-10-20 项目主人留名接受）：接受。** 只在那次调用、那个任务活着时，只认那条命令的进程，只读，每次都记下来挂在 shell 或任务下面给人看（第八节第 3 条）。家目录里的密钥读得到、网络不管，这一条以前就接受了（`24-威胁模型.md` 沙盒那一行）；新多的是数据根里的记忆和知识库，和 MCP 凭据背后的数据。后台也开以后，开着的时间可能很长。
- 未选：第一版不开 `memory_search`、`kb_search`、`kb_read`，只开搜索、抓网页、只读的 MCP。口子小一半，用处也小一截（第十节的 A2、W2 都是知识库）。
- 写在 `24-威胁模型.md` 第三节。
- 重开条件：出现借这条路把记忆、知识库发出去的实际事故，或者要开放写类工具时。

**MC11. 不在会话里的不退回**

- 未选：没有通道就以本人的身份经协议调。会话里跑在沙盒外的命令读得到本机令牌，这样就绕过了会话的权限。

**MC12. 给她看的字：shell 说明讲怎么用，system 讲什么时候用，例子照 shell 换**

- **已定（2026-10-20 项目主人定，照第十节四轮实测）：第九节那两段；例子照会话的 shell 换（PowerShell、有 jq 的、有 Python 的、都没有的不带）。**

- 未选 B：例子写死 bash 加 jq。Windows 上是 PowerShell，别处不一定装了 jq。

**MC13. 三个平台第一版都开**
