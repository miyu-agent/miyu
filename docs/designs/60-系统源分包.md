## 系统源分包和系统加装层

系统的包管理器（AUR、Homebrew，以后可能有 scoop）里怎么发 Miyu：拆成几个有依赖关系的包、`miyu-agent` 作总包，第三方也能经系统源发扩展。为此核心的软件包多一层「系统加装」。改 `59-发版.md` 第三节、第六节，补 `31-软件包.md` 第二节、`55-数据根仿FHS.md` 第二节。

状态：草案（2026-11-05）。项目主人定了方向（第七节），细节待拍板（第八节）。施工 SD（第六节）。

### 一、为什么

2026-11-05 项目主人从用户的角度提：照 KDE Plasma 那样，源里有核心、终端、网页、托盘这些包，彼此写依赖，装 `miyu-agent` 就是装全套；也要允许别人经系统源发 Miyu 的扩展（AUR、GNOME 扩展都这么做，有人就喜欢这么装）。

设计 59 原来的做法是一个包装全套（核心加两个界面），插件只走官方源。装完能用，但没法只装一部分；系统源里也没有地方放别人的扩展：系统装的东西只能塞进核心自己的资源目录，和核心的文件混在一起。Homebrew 更做不到：每个配方装在自己的目录里，核心照自己的真实位置只看得到自己带的那一份。

### 二、系统源里有哪些包

照项目主人 11-05 的划分：

| 包 | 带什么 | 依赖 |
|---|---|---|
| `miyu-agent-core` | `miyu`、`miyu-sandbox`、`miyu-extract`，核心的资源 | 无 |
| `miyu-agent-tui` | 终端（`miyu-tui` 和它的包文件夹） | core |
| `miyu-agent-webui` | 网页（`miyu-web` 和它的包文件夹，含页面） | core |
| `miyu-agent-im` | 接入通讯平台和赞助记录 | core |
| `miyu-app` | 托盘程序（桌面端，`miyu-app` 仓库发） | core、webui |
| `miyu-agent` | 空的总包 | 见第八节第 1 条 |

以后有桌面端（desktop）也照这样单独成包。别的扩展（表情包、渲染、embed、外观、脚本包、第三方的）默认走官方源 `miyu pkg install`，也允许谁经系统源发（第四节）。

`-git` 版本照源码编：`miyu-agent-git` 一个包编全套、`provides` 上面几个，免得每个都要一个 `-git`（AUR 的惯例）。

### 三、系统加装层

1. **三层**，照先后读，后面的同编号盖过前面的：
   - 出厂（`shipped`）：核心自己资源目录的 `packages/`，跟核心一起装；
   - 系统加装（`distro`）：系统包管理器另外装的包；
   - 装上的（`home`）：数据根的 `opt/`，`miyu pkg install` 装的。
2. **系统加装在哪**，照 XDG 和各家包管理器的习惯，不解开链接：
   - Linux：`$XDG_DATA_DIRS` 里每一处的 `miyu/packages/`（没设时 `/usr/local/share`、`/usr/share`），先列的优先；
   - Homebrew：`<前缀>/share/miyu/packages/`，前缀照 `miyu` 所在目录往上一级算，不解开链接（解开就进了 Cellar 里核心自己那一份）；
   - Windows：先不设（第五节）。
   - 测试、演练用环境变量 `MIYU_DISTRO_PACKAGES` 指一处，设了就只看它。
3. **核心自己的资源不放进这一处**：分包以后 `miyu-agent-core` 把程序和资源放在 `/usr/lib/miyu/`（`/usr/bin/miyu` 是链接），资源目录的找法照旧（设计 12 第三节：程序真实位置的旁边）。这样出厂、系统加装两层不会是同一个目录。压缩包、安装脚本照旧，两个界面仍在出厂层。
4. **谁管**：系统加装那一层只归系统包管理器。
   - `miyu pkg remove` 碰到它，照出厂包的办法在 `etc/removed/` 记一笔、不再加载，文件不动，说清楚「这是系统装的，要删用系统的包管理器」。
   - `miyu pkg install` 同编号的照旧装进 `home`、盖过它（想早用新版的人）。
   - `package.list` 的 `layer` 多一种 `distro`；`package.check` 也查这一层（照系统包管理器装好的文件比）。
5. **装不装得上照旧查**：核心读到每一层的包都照清单查协议版本、适用系统、依赖。对不上的不加载，`miyu check` 报原因（编号、哪一层、为什么）。第三方打包写错依赖，坏的只是那一个包。

### 四、第三方经系统源发扩展

1. 作者文档 `docs/authors/` 加一节「经系统源发」：包文件夹装到哪（第三节第 2 条），程序放在包文件夹的 `bin/`，包名建议 `miyu-<编号>`，依赖写 `miyu-agent-core`、版本照清单的协议写下限。
2. 官方源和系统源可以都有：同一个包两边都发的，系统源的进 `distro`，用户自己装的进 `home` 盖过它。
3. 不另设审核：系统源由各家自己审（AUR 靠用户自己看 PKGBUILD），核心只管装上以后照规矩读、查。

### 五、各家

1. **AUR**：照第二节分包，`packaging/` 里每个包一份 PKGBUILD，真相源照旧在核心仓库（im、托盘的 PKGBUILD 放各自仓库还是这里，见第八节第 3 条）。
2. **Homebrew**：tap `homebrew-miyu` 里每个包一个 formula，`depends_on` 写依赖，`miyu-agent` 是只写依赖的总 formula；托盘做成 cask。
3. **Windows**：1.0 照旧是压缩包（命令行版）和 msi（托盘）。以后加 scoop bucket，清单写依赖，系统加装那一处到时候再定。
4. **压缩包、安装脚本**：照旧一个包装全套（核心加两个界面，都在出厂层），给不用包管理器的人。

### 八、要项目主人定的

1. **总包 `miyu-agent` 带哪些**：
   - 推荐：core、tui、webui（命令行用户的全套，服务器上也装得了），im、托盘写成可选依赖（`optdepends`，装的时候提示）；
   - 或者：连 im、托盘一起，装了就是所有东西（服务器上会多装托盘的图形依赖）。
2. **托盘的 deb、rpm 还带不带核心**：分包以后 AUR 的 `miyu-app` 改成依赖 core、webui；deb、rpm 没有我们的软件源可依赖，推荐照旧把核心和网页打在里面、和 `miyu-agent-core` 写冲突。
3. **im、托盘的 PKGBUILD 放哪**：推荐都放核心仓库 `packaging/`（一处管、发版当天一起换哈希）；或者各放各的仓库。
