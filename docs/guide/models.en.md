# Models

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Miyu can chat only after you connect a model provider. This page covers how to connect one, how to switch, where keys go, and what Miyu does when a model fails. Chinese version: [models.md](models.md).

## Fastest: miyu setup

1. Type `miyu setup`.
2. Under "Pick a provider:", type a number. The list has the common providers, any model services running on this machine (marked "local <address>"), and a last row "Custom". Providers you have already set up are marked "configured", and ones whose key is in an environment variable are marked "key found".
3. Paste the key. It is not shown as you paste. If an environment variable was found, it does not ask. Press `Ctrl+C` to cancel; on Linux and macOS, `Ctrl+D` before you have typed anything also cancels.
4. Wait for the test. If it works, it prints "connected"; if it cannot list the models, it asks you for the model name. If the test fails, it asks "Save anyway? [y/N]"; if you do not save, you go back to the previous step.
5. Under "Pick the model for chat:", type a number, or press Enter to take the one marked "(recommended)".
6. When you see "set models.chat = …", you are done.

The common providers, in the order listed:

| Name | Id |
|---|---|
| OpenCode Zen | `opencode` |
| OpenCode Go | `opencode-go` |
| ClinePass | `cline-pass` |
| DeepSeek | `deepseek` |
| Anthropic | `anthropic` |
| OpenAI | `openai` |
| OpenRouter | `openrouter` |
| Moonshot (Global) | `moonshotai` |
| Moonshot (China) | `moonshotai-cn` |
| Zhipu GLM (China) | `zhipuai` |
| Z.AI (Global) | `zai` |
| Qwen (Global) | `alibaba` |
| Qwen (China) | `alibaba-cn` |
| MiniMax (Global) | `minimax` |
| MiniMax (China) | `minimax-cn` |

For one that is not in the table, pass the id from the model catalog to `--provider`. Three options each skip a step: `--provider <id>` skips choosing a provider, `--env <variable>` takes the key from that variable in the core's environment instead of asking you to paste it, and `--model <model>` skips choosing a model. Outside a terminal, `--provider` is required, and the key is read from a pipe:

```bash
echo "$KEY" | miyu setup --provider deepseek
```

```powershell
$key | miyu setup --provider deepseek
```

If you choose "Custom", it asks in turn for `Base URL:`, "API protocol:" (`OpenAI compatible`, `Anthropic`, `OpenAI Responses`), and the key (can be left empty). After the test succeeds, it asks for this provider's id; press Enter to take the one made up from the address.

`miyu setup` writes to `etc/config.toml` under the data root (by default `~/.miyu`, and `%USERPROFILE%\.miyu` on Windows), that is `~/.miyu/etc/config.toml`, and what it writes takes effect right away:

| What you chose | What it writes |
|---|---|
| Pasted a key | `providers.<id>.key = { secret = "<id>" }`; the key is stored in the secrets file, under a name that is the id |
| A key was in an environment variable | `providers.<id>.key = { env = "<variable>" }` |
| A service on this machine | `providers.<id>.local = true` |
| Custom | `providers.<id>.driver`, `providers.<id>.base_url`, and, if you pasted a key, also `key = { secret = "<id>" }` |
| A provider already set up | Leaves that provider alone |

Each of these also writes `models.chat = "<id>/<model>"`. If you type `miyu ask` before any model is set up, in a terminal it runs through `miyu setup` first.

## Changing the default model

`models.chat` is the model new sessions use by default, written as `provider/model` or `@pool`:

```sh
miyu config set models.chat deepseek/deepseek-v4-pro
```

The change applies to new sessions; open sessions do not change.

## Where keys go

The config cannot hold the key itself, only a reference:

- `{ secret = "name" }`: taken from the secrets file `~/.miyu/etc/private/secrets.toml`. On Linux and macOS only you can read and write this file (`0600`); on Windows Miyu sets no separate permissions and the file inherits the access control of the data root. On all three platforms the system keychain is not used, and the key is written in this file as plain text.
- `{ env = "VARIABLE" }`: taken from the environment variable as it was when the core started, and never written to any file.

If you use an environment variable, set it in a window first, then run `miyu setup` in that same window. A core that is already running cannot see a variable set later, so stop it first:

```bash
export DEEPSEEK_API_KEY='sk-fake'
miyu core stop
miyu setup --provider deepseek --env DEEPSEEK_API_KEY
```

```powershell
$env:DEEPSEEK_API_KEY = 'sk-fake'
miyu core stop
miyu setup --provider deepseek --env DEEPSEEK_API_KEY
```

A variable set this way is visible only to a core started from this window. A core started by a service installed with `miyu service enable` cannot see the variables in your shell; if a core that keeps running needs the key, use the secrets file, see [Services and environment variables](service.en.md#the-service-and-environment-variables).

Use `miyu provider` to store, view and remove secrets:

| Command | What it does |
|---|---|
| `miyu provider login [<name>]` | Stores one key. Without a name, you choose from the ones used in the config and the ones already stored, or type a new name. What you paste is not shown, and it can also read from a pipe |
| `miyu provider list [--format text\|json]` | Lists the stored ones, and the ones used in the config but not yet stored (in grey), with who uses them. Keys are not shown |
| `miyu provider logout [<name>]` | Removes one. Without a name, you choose from the stored ones |

A name starts with a lowercase letter, contains only lowercase letters, digits, `-` and `_`, and is at most 64 characters. `login` only stores the key; the config still needs a line that refers to it:

```bash
echo "$KEY" | miyu provider login acme
```

```powershell
$key | miyu provider login acme
```

```toml
[providers.acme]
key = { secret = "acme" }
```

A provider has only one key. If you want to use several quotas together, set them up as several providers and put them in the same pool.

## Writing a provider by hand

Open `~/.miyu/etc/config.toml` (or use `miyu config edit`), with one table per provider, `[providers.<id>]`. The id starts with a lowercase letter, contains only lowercase letters, digits, `-` and `_`, and is at most 32 characters. When you refer to a model, write `<id>/<model>`, with the model name as the provider calls it.

| Field | Description |
|---|---|
| `base_url` | The API address; the driver appends the path to it. A recognized provider can leave it out. Can also be `{ env = "VARIABLE" }` |
| `driver` | The driver, see the table below. A recognized provider uses its own; for an unrecognized one, leaving it out means `openai-chat` |
| `key` | `{ secret = … }` or `{ env = … }`. With none set, no auth header is sent |
| `name` | The name shown in the interface. With none set, the name of that provider in the catalog is used, and failing that, the id |
| `catalog` | Which provider in the model catalog this one corresponds to; for example, a relay that only forwards DeepSeek writes `deepseek` |
| `local` | A service on this machine; the price counts as 0. With none set, it is decided from the address: `127.0.0.1`, `localhost` and `::1` count as this machine |
| `price_multiplier` | Price multiplier; 1 if not set |

For the other fields, see the [config key reference](config-keys.en.md).

| Driver | Sends to | Auth header |
|---|---|---|
| `openai-chat` | `<address>/chat/completions` | `Authorization: Bearer <key>` |
| `anthropic` | `<address>/messages` | `x-api-key: <key>` |
| `openai-responses` | `<address>/responses` | `Authorization: Bearer <key>` |

Packages can bring drivers too; write `driver` as `<package id>/<driver name>`. For example the community package `antigravity` (Linux and macOS only) brings the driver `antigravity/antigravity`, which hands requests to the Antigravity CLI on this machine and uses your login there; for how to install and configure it, see the package's own page (the "Upstream" line of `miyu pkg info antigravity`). To write a driver yourself, see [Writing a model driver](../authors/extensions.en.md#writing-a-model-driver).

You do not have to list the models one by one. Miyu asks the provider for its model list (`<address>/models`), adds the ones from the matching provider in the catalog and the ones named in the config, and gives you the combined list to choose from. Model names in a reference are not checked, so a model that is not in the list can still be used.

An OpenAI-compatible third-party service:

```toml
[providers.acme]
name = "Acme"
base_url = "https://api.acme.example/v1"
driver = "openai-chat"                  # optional: an unrecognized provider defaults to it
key = { secret = "acme" }               # store it with miyu provider login acme

[models]
chat = "acme/acme-large"
```

Ollama on this machine:

```toml
[providers.ollama]
base_url = "http://127.0.0.1:11434/v1"  # for the id ollama, this line and the next can be left out
driver = "openai-chat"
local = true

[providers.ollama.models."qwen3:8b"]
window = 32768                          # for a model whose window is unknown, Miyu does not compact the context early

[models]
chat = "ollama/qwen3:8b"
```

If a model name contains `.`, `:` or `/`, put that part of the table header in double quotes.

For what the provider's list and the catalog lack, fill it in under `[providers.<id>.models."<model>"]`; what you write overrides what comes from elsewhere:

| Field | Description |
|---|---|
| `window` | Context window, in tokens |
| `max_output` | The most tokens it can output in one go |
| `inputs` | What it accepts: `text`, `image`, `pdf`, `audio`, `video` |
| `effort` | The default thinking level; write one of its levels, for example `high`; write `off` if it can turn thinking off |
| `temperature` | The default temperature, 0 to 2 |
| `price_multiplier` | This model's multiplier; it overrides the one written on the provider |
| `price.input`, `price.output`, `price.cache_read`, `price.cache_write`, `price.currency` | Price per million tokens; the currency is `USD` if not set. If you write a single field, the whole set you wrote is used |

These keys are read only from the system config; they cannot be written in a project config. A change to these provider fields takes effect next turn.

## The three uses

| Key | What it controls | Allowed values |
|---|---|---|
| `models.chat` | The model new sessions use by default | `provider/model`, `@pool` |
| `models.vision` | Looks at images for the chat model when the chat model cannot | `provider/model`, `@pool` |
| `models.embedding` | Computes vectors, used to find memories and knowledge base content | `local` (the default, `miyu-embed` on this machine), `off` (search by keywords only), `provider/model` |

```toml
[models]
chat = "deepseek/deepseek-v4-flash"
vision = "acme/acme-vision"
embedding = "local"
```

## Pools: cheap ones for chores, expensive ones for real work

A pool is several models grouped together; you refer to one as `@poolname`. Three pools always exist and cannot be deleted; they start out empty:

| Pool | Called in the interface | Who uses it |
|---|---|---|
| `lite` | Lite pool | Naming sessions |
| `normal` | Everyday pool | Sorting memories |
| `flagship` | Flagship pool | `advisor`: when the AI is stuck, it asks a stronger model for help |

If `lite` or `normal` is empty, or its members are all cooling down or all failing, the session's own model is used. If `flagship` is empty, `advisor` answers "No model in the flagship pool".

To put models in a pool, write `pools.<pool>.models`. Members can only be `provider/model`, in the order written. You can also create pools of your own:

```toml
[pools.lite]
models = ["deepseek/deepseek-v4-flash"]

[pools.flagship]
models = ["deepseek/deepseek-v4-pro"]

[pools.daily]
models = ["deepseek/deepseek-v4-flash", "acme/acme-large"]
strategy = "ordered"
subagent = true
description = "Everyday work, cheap"

[models]
chat = "@daily"
```

`strategy` is how requests are spread:

| Value | Called in the terminal | How it spreads |
|---|---|---|
| `pin` | Pinned per session | A session keeps using one member, and the next new session gets the next one |
| `rotate` | Rotate per request | Every request moves to the next member |
| `ordered` | Fall back when unavailable | Every request starts from the first member, and the later ones are used only when the first fails |

When it is not written, it is `pin`; if the providers of all the members have `cache = "per_request"`, it is `rotate`.

For a pool with `subagent = true`, the AI can pick it when it dispatches a subagent; `description` is the one-line description the AI sees, written in English. The three fixed pools have it on by default, and pools you create have it off by default. A change applies to new sessions.

In the web UI, pools are on the "Model pools" tab of the "Models" settings page, one card per pool, with a "Subagents can pick it" switch on the last row. Click "+ New model pool" below the cards, write a name, and a "Subagents can pick it" switch appears under the name (off by default); press Enter to create it. A change is saved straight into `~/.miyu/etc/config.toml`.

In the terminal, on the "Providers & models" settings page, open the "Pools" page and open a pool or create one. Under "Strategy" there is a "Subagents can pick it" field; choose "On" or "Off". A new pool starts at "Off".

## Switching models temporarily

- Command line: `miyu ask --model deepseek/deepseek-v4-pro "…"`; `--model @flagship` works too. When used together with `-c` or `-s`, that session is switched over and keeps using it from then on.
- Terminal: type `/model`, choose one in the "Models" box, and press Enter. It takes effect from the next turn. One that is cooling down or has no key set cannot be chosen. `/config` opens the settings page; go to "Providers & models", which has three pages, "Providers", "Default models" and "Pools"; `/connect` goes straight to "Providers & models".
- Web UI: click the model name in the footer of the input box; the menu has two pages, "Models" and "Model pools". You can also type `/model` followed directly by `provider/model` or `@pool`, and the menu does not open. `/config` opens the "Models" page of settings.

## The model catalog

Context windows, prices, what inputs a model accepts, and the addresses and drivers of recognized providers all follow the catalog at [models.dev](https://models.dev). A copy comes with the install, and the core fetches newer ones in the background:

| Key | Default | Description |
|---|---|---|
| `models.catalog.update` | `true` | Turned off, only the copy that came with the install and ones already fetched are used. The environment variable `MIYU_CATALOG_UPDATE=false` overrides it |
| `models.catalog.url` | `https://models.dev/api.json` | Where to fetch it from. Can also be `{ env = "VARIABLE" }` |
| `models.catalog.every` | `24h` | Fetch again only when the copy on hand is older than this, 1 hour to 30 days |

## Rate limits and used-up quota

When `models.chat` names a single model:

- Rate limited, cannot connect, 5xx, stalled: the same step is retried up to 5 more times. If the provider says how long to wait, Miyu waits that long, except that a wait of 2 minutes or more is not waited out and the turn ends with an error; if it does not say, Miyu waits 1, 2, 4, 8, 16 seconds.
- Authentication failed, quota used up: no retry, and the turn ends with an error.

When it names a pool, the member that failed is put into cooldown, and the next member that is not cooling down is used right away. In the terminal a line "↻ Switched model: A → B" appears. If all members are cooling down, Miyu waits for the one that recovers earliest. After a `pin` pool switches, the session keeps using the one it switched to.

On the nth consecutive failure the cooldown is `base × 2^(n−1)`, at most `max`; one success resets it to zero. If the provider says to wait longer, that is followed, but it still does not exceed `max`. Cooldown is kept only in memory, and restarting the core clears it.

| What went wrong | Keys | Default `base` / `max` |
|---|---|---|
| Rate limited | `models.cooldown.rate_limited.base`, `.max` | `30s` / `10m` |
| Cannot connect, 5xx, stalled | `models.cooldown.retryable.base`, `.max` | `10s` / `5m` |
| Authentication failed | `models.cooldown.auth.base`, `.max` | `10m` / `2h` |
| Quota used up | `models.cooldown.quota.base`, `.max` | `30m` / `30m` |

If the quota is used up and the provider said when it resets, the cooldown lasts until then, at most one day, regardless of `max`. A cooldown stops only that model of that provider; the provider's other models keep working.

## Usage and cost

- Terminal: `/usage` shows usage and cost on this machine, by day and by model; `/context` shows this session's, split by purpose.
- Web UI: the "Usage" page in settings can be viewed by model, session, purpose and venue.

Amounts are shown in `usage.currency` (`USD` by default), converted at the exchange rate of the day of each charge; if the rate cannot be fetched, no amount is shown. Prices follow the catalog; a service on this machine counts as 0; for a relay that marks prices up or gives a discount, write `price_multiplier`.

## When something goes wrong

| What you see | What to do |
|---|---|
| "no model configured", `no model configured: set models.chat` | Run `miyu setup`, or write `models.chat` |
| `miyu setup` says "the core has not read XXX_API_KEY (set after the core started)" | The core started before that variable existed. Run `miyu core stop` and then `miyu setup` again, or just paste the key |
| `provider "acme" has no usable key` | The key was not stored, or the core's environment does not have that variable. Use `miyu provider list` to see which one is not set |
| `provider "acme" needs base_url: it matches nothing in the catalog` | The catalog does not recognize this provider; write `base_url` |
| "Not found. Check the endpoint address and model name." | `base_url` must go up to the part before the path the driver appends, and the model name must be the same as on the provider's side |

`miyu check` checks the config for mistakes.
