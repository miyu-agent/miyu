# Rescue

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

When Miyu is broken (the core will not start, the config is ruined, or a head will not open), `miyu rescue` starts LiteMiyu so that the AI can help you fix it in the terminal. This page covers what LiteMiyu is, how to install it, and how to use it to repair Miyu. Chinese version: [rescue.md](rescue.md).

## What LiteMiyu is

LiteMiyu is a separate program, `litemiyu`: one process, one file, running full screen in the terminal, and it can talk to a model, read and write files, and run commands by itself. It does not use Miyu's core, and does not read Miyu's sessions and memory. Only Linux x86_64 (glibc 2.39 or later) can use it.

Its things live in its own directories, unrelated to Miyu's data root (`~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows):

| What it keeps | Where |
|---|---|
| Config `config.toml`, keys `secrets.toml` | `~/.config/litemiyu/` |
| Sessions, memory | `~/.local/share/litemiyu/` |
| Cache | `~/.cache/litemiyu/` |
| Run log, input history | `~/.local/state/litemiyu/` |

If variables such as `XDG_CONFIG_HOME` are set, they are followed.

## Install

- Arch Linux: install `litemiyu` from the AUR, for example `paru -S litemiyu`. The program is at `/usr/bin/litemiyu`.
- Other distributions: download `litemiyu-<version>-linux-x86_64.tar.gz` and `SHA256SUMS` from the [releases page](https://github.com/miyu-agent/litemiyu/releases), verify them, then put the `litemiyu` inside into a directory in `PATH`:

  ```sh
  sha256sum -c SHA256SUMS
  tar xf litemiyu-<version>-linux-x86_64.tar.gz
  install -m755 litemiyu-<version>-linux-x86_64/litemiyu ~/.local/bin/
  ```

`miyu rescue` looks for `litemiyu` in this order: the directory of the `miyu` you typed, the directory where `miyu` actually is (after resolving links), and `PATH`. Relative directories in `PATH` do not count.

## Using miyu rescue

```sh
miyu rescue [<arguments>…]
```

It does not connect to the core, and does not start the core:

1. From Miyu's system config `~/.miyu/etc/config.toml` and the secrets file, it works out which provider the default model (`models.chat`) connects to, which model, which API and which key.
2. It puts these four things into four environment variables and hands them to LiteMiyu. One that you already set yourself is left alone.

   | Environment variable | What it is |
   |---|---|
   | `LITEMIYU_RESCUE_BASE_URL` | The address of the provider |
   | `LITEMIYU_RESCUE_MODEL` | The model name |
   | `LITEMIYU_RESCUE_API` | The API: `openai-chat`, `anthropic`, `openai-responses` |
   | `LITEMIYU_RESCUE_API_KEY` | The key; not set if the default model has no key |

3. It runs `litemiyu --rescue`, followed by the arguments you wrote, passed on as they are. The exit code is LiteMiyu's.

Where Miyu's data root is is not handed to LiteMiyu. When repairing, tell the AI.

LiteMiyu knows three arguments, which override the environment variables when written: `--base-url <url>`, `--model <name>` and `--api <kind>`. The key is read only from the environment variable.

In a few cases where things cannot be filled in, `miyu rescue` first prints a warning line, fills in none of the four variables, and still starts LiteMiyu, which then uses its own config:

| What you see | Why |
|---|---|
| `miyu: warning: cannot read Miyu's configuration: …; litemiyu will find a model itself` | The config or the secrets file cannot be read at all, or the default model cannot be used. If only one item is written wrongly, that item is skipped and the rest are read as usual |
| `miyu: warning: the chat model uses the extension driver <package>/<driver>, which litemiyu cannot use; litemiyu will find a model itself` | The default model goes through a driver that comes with a package |

## How rescue mode differs from usual

`litemiyu --rescue` is made for repairing things:

- It writes nothing to disk: no session is recorded, no config is changed, no input history is kept. It works even when the disk is full or the directory is read-only. When you close it, it is gone.
- The AI has only five tools: `read`, `write`, `edit`, `shell` and `jobs`. No web, subagents, memory, skills or MCP.
- The AI has no special instructions about Miyu; what to fix and where the files are, you say clearly in your first message.
- There is no permission level to switch; files and commands are done directly, and Miyu's data root can be changed too. Dangerous commands are recognized as in Miyu (see [Permissions and sandbox](permissions.en.md#commands-that-need-confirmation)): the kinds refused outright are still refused; the kinds that need confirmation ask you first, and you can only allow this one time or refuse, with no switch.
- The right side of the top border of the input box says "rescue · nothing saved". The command list has no `/sessions`, `/config`, `/loop`, `/model` or `/effort`; the external editor of `Ctrl+G` cannot be used.

## One repair

Example: after you edit `~/.miyu/etc/config.toml` by hand, typing `miyu` reports "the core couldn't start: …".

1. Type:

   ```sh
   miyu rescue
   ```

   The screen changes to LiteMiyu's full-screen interface, and the input box says "rescue · nothing saved".

2. Tell the AI what is going on, for example:

   ```text
   The Miyu core will not start. Its data root is ~/.miyu, the system config is ~/.miyu/etc/config.toml, and the core log is ~/.miyu/var/log/core.log.
   Read the last few dozen lines of the log to find the cause, fix the config, and tell me what you changed.
   ```

3. The AI reads the log, changes the files, and at the end says what it changed. Look it over.
4. Press `Ctrl+D` (when the input box is empty) or type `/exit` to quit.
5. Type `miyu` and see whether the core starts.

If the config file cannot be read at all, step 1 first prints the warning that Miyu's configuration cannot be read. If LiteMiyu has no model configured either, it does not enter the interface, prints what is missing and the usage, and exits (exit code `2`); the first line is:

```text
litemiyu --rescue: no model to use; missing LITEMIYU_RESCUE_BASE_URL, LITEMIYU_RESCUE_MODEL.
```

In that case give it a model yourself (replace the address and model name with your provider's; the key is a fake one):

```sh
LITEMIYU_RESCUE_API_KEY=sk-example miyu rescue --base-url https://api.deepseek.com/v1 --model deepseek-chat
```

Without `--api` it uses `openai-chat`. If no key is given it still goes in, and the interface notes "No key given (LITEMIYU_RESCUE_API_KEY); requests go without authentication".

To avoid typing by hand next time: while Miyu is still fine, run `litemiyu provider import` once, to import Miyu's providers, keys and default model into LiteMiyu's own config.

If the `miyu` program itself is broken and cannot be typed, run `litemiyu --rescue` directly, and give the model with environment variables and arguments as above.

## Other systems

There is no LiteMiyu on macOS or Windows. `miyu rescue` cannot find it and prints:

```text
miyu: litemiyu not found
hint: only Linux is supported for now
```

The exit code is `1`. On Linux, when it cannot be found, the hint changes to how to install it.

On macOS and Windows, when the core is broken, check it yourself as below:

1. Look at the last few dozen lines of the core log, and find the cause of the error:

   ```bash
   tail -n 50 ~/.miyu/var/log/core.log
   ```

   ```powershell
   Get-Content -Tail 50 $HOME\.miyu\var\log\core.log
   ```

2. If a hand edit broke the config, open `~/.miyu/etc/config.toml` in an editor and change the broken lines back. A config that cannot be read in at all when the core starts is treated as empty, and the core still starts; then type `miyu check` and fix the lines it prints the line numbers of.
3. After fixing, type `miyu core stop` to stop the core that is running, then type `miyu` to open it.

For what each error means and what to do, see [Troubleshooting](troubleshooting.en.md#the-core-will-not-start-or-cannot-connect).

## How LiteMiyu is used normally

Run without `--rescue` and it is the normal mode, with sessions and config saved to disk:

```sh
litemiyu            # start a conversation
litemiyu -c         # open the most recent session
litemiyu config     # open the settings screen
litemiyu doctor     # self-check: config, model, directories, Miyu, terminal
```

- The first run goes through the opening first: connect a provider (if there is a Miyu on the machine, "Import from Miyu…" is listed first), choose the model for the main conversation, and choose the key mode and light or dark.
- Keys: `Enter` sends, `Alt+Enter` or `Ctrl+J` starts a new line, `@` completes a file path, `Ctrl+C` interrupts while it answers, `Ctrl+D` quits when the input box is empty. Type `/help` to see all keys and commands.
- `litemiyu doctor` exits with code `1` when one item is bad. If it reports that Miyu can be found and how many providers can be imported, `litemiyu provider import` can be used.
- Every command has `--help`, for example `litemiyu provider --help`.

## When it cannot be fixed

Take the last few dozen lines of `~/.miyu/var/log/core.log`, and report the problem as in [Troubleshooting](troubleshooting.en.md#reporting-a-problem).
