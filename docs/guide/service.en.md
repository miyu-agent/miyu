# Keeping it running, and servers

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Starting the core at boot, running it on a server with no desktop, opening the web UI from other machines and phones, reading logs and stopping it are all on this page. For how to install, see [Installing, upgrading and uninstalling](install.en.md). Chinese version: [service.md](service.md).

## How the core normally runs

The core is `miyu` running in the background; sessions, models and schedules all live in it. The heads (terminal, web UI, tray) only connect to it.

- When a head cannot reach the core on startup, it starts one and connects once it is ready. This works without installing a service.
- Only one core runs per data root at a time. The data root is `~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows, or the value of `MIYU_HOME` if set.
- By default the core stays up, even when all heads are closed.

To have it exit by itself when idle, enter a number of minutes in "Advanced → Core → Core idle exit" on the settings page (type `/settings` in the terminal or web UI), or run:

```sh
miyu config set core.idle_exit 30
```

It exits after this many minutes in a row with no connection and no turn running. `0` keeps it up always (the default); the allowed range is `0` to `525600`. A change takes effect immediately, and it can only be written in `~/.miyu/etc/config.toml`.

To stop it by hand:

```sh
miyu core stop
```

It tells the running core to stop and returns once the core has exited; if no core is running, it does nothing. A turn that is running stops first and picks up again the next time that session is loaded.

To close only the web UI and leave the core running: `miyu web --stop`.

## Starting at boot or login

With the service installed, the core starts at boot or login, so chat platforms and schedules do not have to wait for you to open a head.

```sh
miyu service enable
```

| Command | What it does |
|---|---|
| `miyu service enable` | Writes the service file and hands it to the system's service manager |
| `miyu service disable` | Stops the service, removes it from the service manager and deletes the service file |
| `miyu service status` | Shows whether it is installed and whether it is on |

All three commands take `--format json`, which prints one line `{"installed", "on", "file", "manager"}`; on failure it is `{"error", …}`.

The service runs the `miyu` you are typing now (its real location, with links resolved). If `MIYU_HOME` is set, it is written into the service too. If you moved `miyu` or changed the data root, run `miyu service enable` again to rewrite it.

What each system uses:

| System | What it uses | File it writes | When it starts |
|---|---|---|---|
| Linux with a systemd user session | systemd user service | `~/.config/systemd/user/miyu.service` | Now, and at every login after that |
| Linux without a systemd user session | Desktop autostart | `~/.config/autostart/miyu.desktop` | At the next desktop login |
| macOS | launchd user agent | `~/Library/LaunchAgents/io.github.miyu-agent.core.plist` | Now, and at every login after that |
| Windows | Task Scheduler, task named `Miyu` | `%USERPROFILE%\AppData\Local\Miyu\miyu-task.xml` | At the next login |

On Linux, if `XDG_CONFIG_HOME` is set, the first two files are written under it.

When `miyu service enable` succeeds, it prints "enabled and started …" (systemd, launchd), "enabled …, starts at the next desktop login" (desktop autostart) or "enabled …, starts at the next login" (Task Scheduler). `status` prints "installed, enabled: …", "installed, not enabled: …", "installed, starts at desktop login: …" or "not installed". It asks the service manager with these commands:

| System | Command |
|---|---|
| systemd | `systemctl --user is-active miyu.service` (checks whether it is running now) |
| launchd | `launchctl print gui/<your uid>/io.github.miyu-agent.core` (checks whether it is registered) |
| Task Scheduler | `schtasks /Query /TN Miyu` (checks whether it is registered) |
| Desktop autostart | It cannot ask; it only checks whether the file exists |

### What to know about each system

| | systemd user service | Desktop autostart | launchd | Task Scheduler |
|---|---|---|---|---|
| When the core exits | Restarted 5 seconds after an abnormal exit, not after a normal one | Not restarted; the next time you open a head, the head starts it | Restarted when the exit code is not `0`, not when it is `0` | On failure, retried every 1 minute, at most 3 times |
| When nobody is logged in | Starts at login, stops at logout; after `sudo loginctl enable-linger $USER` it stays up with nobody logged in | Does not run | Does not run | Does not run |
| When `MIYU_HOME` is set | Written into the service file | Written into the service file | Written into the service file | Cannot be installed |

- On macOS and Windows there is no way to keep the core running with nobody logged in. On Linux you can instead install a system service as in [Running on a server](#running-on-a-server).
- Task Scheduler needs no administrator rights and only starts the core when you log in.
- On Windows, when `MIYU_HOME` is set, `miyu service enable` prints "cannot install the service: a Windows scheduled task cannot carry MIYU_HOME", and on the next line "hint: unset MIYU_HOME and try again". If you want another data root and also want it to start at login, use "Start at Login" in the tray, see [Data and backups](data.en.md#moving-it-to-another-location).

### Making the service take over now

If a core started by a head is already running, the one the service starts sees that a core is running and exits normally (exit code `0`); it does not push the running one out. To make the service take over now:

1. Stop the running core: `miyu core stop`.
2. Install the service again: `miyu service enable`. It rewrites the service file from the current `miyu` location and `MIYU_HOME`, then hands it to the service manager.

| System | After step 2 |
|---|---|
| Linux (systemd user service), macOS | The service starts the core right away |
| Linux (desktop autostart), Windows | It only registers again; the service starts the core at the next login. Until then, when you open a head, the head starts a core as usual |

The same two steps switch the core to the new version after an upgrade.

### The service and environment variables

The core the service starts cannot see variables you set in your shell. The service file `miyu service enable` writes carries only `MIYU_HOME` (if it is set) and no other variable; a Task Scheduler task does not even carry `MIYU_HOME`.

For a key written in the config as `{ env = "variable" }`, the core reads the environment it was started in, not your shell's. To make it work for a core started by the service, use the secrets file instead: `miyu provider login` stores the key there, the config says `{ secret = "name" }`, and the core reads it from the secrets file, with no environment variable involved.

If you must use an environment variable:

- systemd user service: run `systemctl --user edit miyu` and add an `Environment=` line (how to write it: see [Keys in environment variables](#keys-in-environment-variables)). If you edit `miyu.service` directly, the next `miyu service enable` overwrites it.
- The launchd plist and the desktop autostart `miyu.desktop`: if you edit them by hand, the next `miyu service enable` overwrites them in the same way.

If the tray is installed, you can also use "Start at Login" in the tray menu to have the tray start at login, see [Tray](heads/applet.en.md).

## Running on a server

This section applies to Linux only. There are no server examples for macOS or Windows; to keep the core running there, use `miyu service enable` from the previous section.

On a server, run the core as a dedicated system user, with the data root in `/var/lib/miyu` rather than under someone's home directory. `miyu service` only manages your own user; a system-level service has to be installed by hand as below.

The `packaging/` directory of the Miyu repository has ready-made examples. All of them run `/usr/bin/miyu core` as the `miyu` user, with the data root `/var/lib/miyu` and the cache `/var/cache/miyu`:

| Init system | Example | Where to put it |
|---|---|---|
| systemd | `packaging/systemd/system/miyu.service` | `/etc/systemd/system/` |
| systemd, web UI | `packaging/systemd/system/miyu-web.service` | `/etc/systemd/system/` |
| OpenRC | `packaging/init/openrc/miyu` | `/etc/init.d/miyu`, made executable |
| runit | `packaging/init/runit/miyu/run` | The whole directory goes into `/etc/sv/miyu`, `run` made executable, then linked into the service directory |
| dinit | `packaging/init/dinit/miyu` | `/etc/dinit.d/miyu`, with environment variables written into `/etc/dinit.d/miyu.env` |

If `miyu` is not in `/usr/bin` (for example, installed by the install script), change the paths in the example to its location.

### Starting the core with systemd

1. Create the system user:

   ```sh
   sudo useradd --system --home-dir /var/lib/miyu --shell /usr/sbin/nologin miyu
   ```

2. Get the example and install it:

   ```sh
   curl -fsSLO https://raw.githubusercontent.com/miyu-agent/miyu/main/packaging/systemd/system/miyu.service
   sudo cp miyu.service /etc/systemd/system/
   sudo systemctl enable --now miyu
   ```

   Following `StateDirectory` and `CacheDirectory` in the example, systemd creates `/var/lib/miyu` and `/var/cache/miyu`, owned by `miyu`, with `0700` on the data root. The OpenRC example creates both directories itself before every start; for runit and dinit you create them first, run `chown miyu:miyu`, and run `chmod 0700` on the data root.

3. Check that it came up: `sudo systemctl status miyu`.

### Running commands on the server

The core only accepts command lines from the same system user and the same data root as itself. Every `miyu` command you run on the server needs to be wrapped like this:

```sh
sudo -u miyu env MIYU_HOME=/var/lib/miyu XDG_CACHE_HOME=/var/cache miyu config get models.chat
```

Connecting a model (see [Models](models.en.md)) works the same way, with the key read from a pipe:

```sh
echo "$DEEPSEEK_API_KEY" | sudo -u miyu env MIYU_HOME=/var/lib/miyu XDG_CACHE_HOME=/var/cache miyu provider login deepseek
```

### Keys in environment variables

For a key written in the config as `{ env = "variable" }`, the core reads the environment it was started in, not your login shell's. For a core started by a service, put the variable into the service:

- systemd: run `sudo systemctl edit miyu` and add

  ```ini
  [Service]
  Environment=DEEPSEEK_API_KEY=sk-example
  ```

  or point `EnvironmentFile=` at a file only root can read. After the change, run `sudo systemctl restart miyu`.
- dinit: write it into `/etc/dinit.d/miyu.env`.
- OpenRC, runit: add it next to the `export` line in the example.

If you do not want the key in a service file, store it in the secrets file with `miyu provider login` and write `{ secret = "name" }` in the config.

For a service installed with `miyu service enable` on your own computer, see [The service and environment variables](#the-service-and-environment-variables).

### Running the web UI with systemd

The web UI program `miyu-web` exits, with exit code 0, after 600 seconds in a row with no browser connected and no media files being served, and the service manager does not start it again; with LAN access on, it does not exit. To run it as a service, first make it stay up:

1. Turn off the idle exit:

   ```sh
   sudo -u miyu env MIYU_HOME=/var/lib/miyu XDG_CACHE_HOME=/var/cache miyu config set web.idle_seconds 0
   ```

2. Get the example:

   ```sh
   curl -fsSLO https://raw.githubusercontent.com/miyu-agent/miyu/main/packaging/systemd/system/miyu-web.service
   ```

3. Replace `ExecStart=` with the real location of `miyu-web`, keeping `serve` after it. On the AUR install it is `/usr/share/miyu/packages/webui/bin/miyu-web`; for the install script it is next to `miyu`:

   ```ini
   ExecStart=/usr/share/miyu/packages/webui/bin/miyu-web serve
   ```

4. Install it:

   ```sh
   sudo cp miyu-web.service /etc/systemd/system/
   sudo systemctl enable --now miyu-web
   ```

Starting the web service also starts the core service, and when the core service stops, the web service stops with it. By default the web UI listens only on `127.0.0.1` on the server itself; how to open it from other machines is in the next section.

## Opening the web UI from other machines and phones

The web UI's settings can only be written in `~/.miyu/etc/config.toml`:

| Key | Default | Description |
|---|---|---|
| `web.listen` | `127.0.0.1` | Which address to listen on. `127.0.0.1` can be opened only from this computer; `0.0.0.0` is all of this computer's addresses; you can also write one of them |
| `web.port` | `8300` | The port, used by this computer and by other devices, `1` to `65535` |
| `web.idle_seconds` | `600` | After how many seconds in a row with no browser connected and no media files being served it exits, `0` to `86400`; `0` means never. It does not exit when LAN access is on. Not shown on the settings page |

Access from other devices always needs the access password. Opening it with `miyu web` on this computer does not.

### LAN

1. On this computer, run `miyu web --settings access` to open "Settings → General → Access".
2. Turn on "Allow local network access". If no access password is set yet, "Set an access password" appears first; once it is set, the switch turns on.
3. The settings page lists the addresses other devices use, plus a QR code. Scan it with a phone and enter the access password to get in.

Whether you change the address and port on the settings page, with `miyu config set` or in the config file by hand, the web UI switches over at once. The "takes effect after restart" that `miyu config set` prints at that point is not accurate.

LAN access is plain HTTP: anyone on the same network can see the access password, the login token and the conversation. Turn it on only on a network you trust, such as your own home. When you are away, first connect back to that network through an encrypted tunnel such as Tailscale or WireGuard, then open the LAN address. On macOS, if other devices cannot connect, go to "System Settings → Network → Firewall → Options" and allow incoming connections for `miyu-web`.

If you forget the access password, run `miyu web --reset` on this computer and set a new one in the page it opens. To make every browser sign in again: `miyu web --logout`.

### A server with no desktop

A server has no browser, so first go in from your own computer through SSH port forwarding to set the access password:

1. On your computer, run this (the two ports must be the same, both the server's `web.port`):

   ```sh
   ssh -L 8300:127.0.0.1:8300 you@server.example
   ```

2. On your computer, open `http://127.0.0.1:8300` in a browser. The web UI treats this connection as the server itself and lets you in without a password.
3. Go to "Settings → General → Access" and set the access password; if you want LAN access, also turn on "Allow local network access".

Anyone who comes in through `ssh -L`, `socat` or other forwarding that adds no headers is treated by the web UI as the server itself: no password, able to read files on the server, and able to change the access password without the old one. Use this path only for yourself.

### Reverse proxy

When the web UI is opened through a reverse proxy such as nginx or cloudflared on the same machine, the web UI treats the visitor as another device: it needs the access password, and features that work only on the local machine (choosing directories on the server, reading its files) are not available.

- The proxy must add forwarding headers: `Forwarded`, `X-Forwarded-For`, `X-Real-IP` and the like; one is enough. Without them, the web UI treats whoever the proxy forwards as the server itself.
- The web UI only accepts requests whose `Host` is `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`; when it listens on the LAN, it also accepts this computer's IP plus the port. It does not accept domain names.
- The conversation goes over a WebSocket at `/ws`, which only accepts an `Origin` of `http://` plus those addresses. When the proxy serves the page on its own domain or over HTTPS, this connection is rejected (403).

For how to use the web UI, see [Web UI](heads/web.en.md).

## Logs

| Whose | Where |
|---|---|
| Core | `~/.miyu/var/log/core.log`; at 10 MB it is replaced with a new file, and `core.log.1` to `core.log.5` are kept |
| Web UI | `~/.miyu/var/log/webui/web.log` |
| Tray | `~/.miyu/var/log/miyu-applet.log` |
| Packages | `~/.miyu/var/log/<id>/` |

On a Linux server, replace `~/.miyu` with `/var/lib/miyu`.

The core's `core.log` is written by the core itself on all three platforms; both a core started by a service and one started by a head write to it. For a core managed by systemd, you can also use `journalctl --user -u miyu` (for a system service on a server, `journalctl -u miyu`) to see the output systemd recorded for the service. The launchd plist and the Task Scheduler task have no output destination set, so there is only `core.log`.

The core's log has one entry per line, in English, and does not record conversation content or keys. Use `log.level` to set how much is recorded: "Advanced → Runtime log → Runtime log level" on the settings page, or:

```sh
miyu config set log.level debug
```

| Value | What it records |
|---|---|
| `error` | Errors only |
| `warn` | Errors and warnings |
| `info` | Normal (default) |
| `debug` | Detailed, for troubleshooting |
| `trace` | Most detailed |
| `off` | Nothing |

A change takes effect immediately, and it can only be written in `~/.miyu/etc/config.toml`. If the environment variable `MIYU_LOG` is set, that one start follows it. Run `miyu core stop` first, then open a head in the window where it is set:

```bash
MIYU_LOG=debug miyu
```

```powershell
$env:MIYU_LOG = 'debug'
miyu
```

In PowerShell, a variable set this way stays on for everything started later from this window; when you no longer want it, run `Remove-Item Env:MIYU_LOG`.

## Stopping

| What to stop | How |
|---|---|
| This run of the core, including one started by a service | `miyu core stop` |
| This run of the web UI | `miyu web --stop` |
| A start-at-boot setup you installed | `miyu service disable` |
| A system service on a server | `sudo systemctl disable --now miyu-web miyu`; for other init systems, use their own way |

A core stopped by `miyu core stop` exits normally (exit code `0`). The systemd user service and launchd restart only after an abnormal exit, so they do not start it again; with systemd, `miyu service status` then changes to "installed, not enabled", while launchd asks whether it is registered, so it stays "installed, enabled". The service starts as usual at the next login.

`miyu service disable` removes it from the service manager and deletes the service file; for the systemd user service (`disable --now`) and launchd (`launchctl bootout`) it also stops the core the service started. For Task Scheduler and desktop autostart, Miyu only removes the registration and deletes the file, and does not stop the core separately; to stop it, run `miyu core stop`.

## Read-only sessions on Windows

The Windows sandbox needs a desktop session. When the core is not in a desktop session (for example, it was started over an SSH connection), no command can run in a read-only session; the output is `miyu-sandbox: cannot confine: no desktop session, programs in the sandbox cannot start here; use Miyu from the desktop, or turn the sandbox off`, with exit code `125`. Use Miyu from the logged-in desktop, or switch to full access. See [Permissions and sandbox](permissions.en.md).
