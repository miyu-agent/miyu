# Letting the AI keep working on its own

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page covers five things that let the AI work without waiting for you to speak: subagents, background commands, schedules, loops and goals, and also what limits them when nobody is watching, and how to stop them. Chinese version: [automation.md](automation.md).

| What you want to do | Use |
|---|---|
| Split a big job among several helpers to work in parallel | Subagents |
| Run a long command in the background and talk once it finishes | Background commands |
| Run something automatically every morning | Schedules |
| Look at something every few minutes | Loops `/loop` |
| Give a goal and have the AI work until it is done | Goals `/goal` |

Each of these five is a shipped package, and exists only when the preset has it on: subagents `base-subagent`, background running `base-jobs`, schedules `base-schedule`, loops `base-loop`, goals `base-goal`. The shipped presets "Everything" and "Development" have all of them on; for how to turn things on and off in a preset, see [Personas and presets](personas-presets.en.md).

## Subagents

A subagent is another session that the AI opens. The AI uses the `subagent` tool to hand a task to it; it works in the background, and when it is done, the last thing it said is sent back as its report to the session that sent it. If the AI calls `subagent` several times in one step, that sends out several at once.

### How to start

Just tell the AI, for example "Send out three subagents to check which functions in `api/`, `web/` and `cli/` are unused, and summarize for me". Whether to send any, and how many, is up to the AI.

When the AI sends one, it can choose:

| Option | What it does | When left out |
|---|---|---|
| Model pool `pool` | The subagent uses a model from this pool. Only a pool with `subagent = true` can be chosen, see [Models](models.en.md) | It uses the model that the sending session is using at that moment |
| Persona `persona` | The subagent uses this persona. Only a persona with `subagent = true` in `persona.toml` can be chosen; the only shipped one is `software-engineer` | No persona |
| Continue the current conversation `fork` | The subagent carries on from this session's conversation as of this step, sees everything said before, and has the same model and persona as the sending session. With `fork` written, you can no longer choose a model pool or persona; a forked subagent cannot fork again | The subagent sees only the message it was given, and cannot see this session |
| Read-only `read_only` | The subagent can only read and not change | It follows the permissions of the sending session |
| Attachments `attachments` | Files handed to the subagent along with the task, at most 8 | None |

A subagent uses the same working directory, the same preset and the same permission level as the session that sent it; if the sending session is read-only, the subagent is read-only too.

A subagent can send out one more level of subagents, and no deeper. Only sessions on this machine can send them; sessions on chat platforms do not have this tool.

### What you see while it runs

- Terminal: below the input box there is a blank line, then a `● Main session` line, then one line per subagent, showing its name, what it is doing, and how many tokens and how long it has used. When the input box is empty, press `↓` to move onto these lines, and `Enter` to switch into that subagent's session; select the `● Main session` line and press `Enter` to switch back; select a subagent and press `x` to stop it.
- Web UI: the middle of the line below the input box says "Background tasks: N"; click it open to list this session's background commands and subagents, with the ones a subagent sent out hanging under it. Click "Open subagent session" to switch in. The "Background tasks" card in the right sidebar lists them too, and clicking one opens the subagent's session in the main area.

After you switch into a subagent's session, you can talk to it directly. Its report will note "The user also talked to this subagent during the task.", which the AI that sent it can see.

### How the report comes back

When a subagent finishes a turn and goes idle, it sends the last thing it said in that turn back to the session that sent it. A report is at most 30000 characters; if it is longer, the beginning and the end are kept, half each. If the sending session is idle, it starts a turn on receiving the report and carries on; if it is working, it sees the report at its next step. The AI and the subagent can also leave messages for each other with `send_message`.

### How to stop

- Ask the AI to stop one with the `jobs` tool.
- Terminal: in the main session, when no turn is running, press `Esc` twice in a row to stop all the subagents it sent out; when switched into a subagent, press `Esc` twice or `Ctrl+C` to stop it. You can also select that line and press `x`.
- Web UI: in "Background tasks", click "Stop" or "Stop all".
- `/stop`: interrupts this turn, then stops the background commands and subagents this session sent out.

### When background running is turned off

If the preset has "Background" (`base-jobs`) turned off, after the AI sends a subagent it waits in place for its report, and goes to the next step only once it has arrived.

## Background commands

When the AI runs a command with `shell`, it can put it in the background: it gets a job id at once (for example `j1`) and carries on with other things; when the command finishes, the result comes back by itself, and the AI does not need to ask. This needs "Background" turned on in the preset.

### How to start

- Tell the AI "run `npm run build` in the background and tell me when it is done".
- A foreground command that has not finished after its time limit (120 seconds if the AI does not set one, and at most 600 seconds) is moved to the background and keeps running.

### Watching the log

When the AI runs a background command, it can ask to "watch" it: every time the command writes a line to standard output, the AI is woken once, which suits waiting for a certain line to show up in a log. Lines that come close together (within 200 milliseconds) are merged into one wake-up. Standard error does not wake the AI; it is only written to the output file.

If a watched command wakes the AI 120 times within an hour, it is stopped and recorded as "Stopped: output too frequent".

### What you see while it runs

- Terminal: below the input box there is a "Background: N" button. When the input box is empty, press `↓` to move onto it, and `Enter` opens the "Background" panel: `↑` and `↓` select, `Enter` expands to show the output, `x` stops, and `Esc` closes. When a command ends, one line "Background command done · <title> · <elapsed>" is recorded on the timeline; failed and stopped ones are written differently.
- Web UI: the same as for subagents, in "Background tasks: N" and in the "Background tasks" card of the right sidebar; click "View command and output" to see the output.

### How to stop

- Have the AI stop it: it uses the `jobs` tool to list, read the output, and stop.
- In the terminal's "Background" panel, press `x`; in the web UI, click "Stop".
- `/stop` stops all of this session's background commands and subagents.

When the core stops or restarts, all running background commands are stopped, recorded as "stopped when the core restarted".

### Limits and defaults

| Limit | Value |
|---|---|
| How long one background command can run at most | `jobs.max_running`, `30m` by default, and it can be `1m` to `2h`. When it is reached, the command is stopped and recorded as "stopped: ran too long" |
| How much one background command can output at most | 5 GB; when it is reached, the command is stopped and recorded as "stopped: too much output" |
| How many times a watched command can wake the AI in an hour | 120 |

To change the longest running time: on the settings page (type `/settings` in the terminal or the web UI), "General → Sessions → Longest background command", or:

```sh
miyu config set jobs.max_running 1h
```

It takes effect from the next turn. This limit applies only to background commands, not to subagents.

## Schedules

A schedule hands a message to a session when its time comes, so that the AI runs a turn. Tasks are recorded in `~/.miyu/root/schedules.db` (the data root is `~/.miyu` by default, and `%USERPROFILE%\.miyu` on Windows).

### Adding with commands

There are three ways to write the time, with an example of each:

```sh
# cron: weekdays at 8 am
miyu schedule add --cron '0 8 * * 1-5' Check last night's CI and list any failures

# run once at a given time
miyu schedule add --at '2026-12-01 09:00' Remind me to submit the monthly report

# at an interval, at least 60 seconds
miyu schedule add --every 2h --session 0198c2a4-7e1b-7c3d-9a2f-4b5c6d7e8f90 Check the build queue
```

Where it runs:

- With `--session <id>`: each time, it is handed to this existing session.
- Without it: each time, a new session is opened. `--persona`, `--no-persona`, `--preset` and `--cwd` decide which persona, preset and working directory the new session uses; the persona and preset you leave out follow the defaults, and the working directory is each new session's own default workspace, `~/.miyu/root/workspace/<session id>/`.

To view, stop and delete:

```sh
miyu schedule                 # list all; each line starts with the task id, for example t1
miyu schedule pause t1        # pause
miyu schedule resume t1       # resume; the next run is counted again from now
miyu schedule rm t1           # delete
```

For each argument, see [Command line](cli.en.md#miyu-schedule).

### Adding in the web UI

The web UI's settings has one more page, "Scheduled tasks": one row per task, showing the message, when, where it runs and the next time, which can be switched on and off, paused, resumed and deleted. Click "New", fill in "Say"; for "When" choose "Daily", "Every", "Once" or "Custom" (Custom takes a five-field cron); for "Run in" choose "New session each time" or "A session". Click a task to see the result of its last run.

The "Scheduled tasks" card in the right sidebar lists the tasks that run on this session, together with loops.

The terminal has no schedules page; use `miyu schedule`.

### Letting the AI set one

Tell the AI "remind me to write a diary at 10 every night", and the AI uses `cron_create` to create one on this session, which sends the message back to this session at that time.

- It writes a five-field cron, in the machine's time zone. One that runs only once deletes itself after running.
- In one session the AI can create at most 20. All schedules together (yours, the AI's, and those created by packages) are at most 200; when full, only new creation is refused.
- Tasks the AI created and tasks you created by command are in the same table. `miyu schedule` and the web UI's "Scheduled tasks" page both list the AI's (the web UI labels them "By AI"); the AI uses `cron_list` to see all those that run on this session, including those you pointed at this session with `--session`, and can delete them with `cron_delete`.
- When a task the AI created comes due, if this session's preset has "Scheduled tasks" turned off, it does not run this time. Yours do not depend on the preset.

### When the time comes

- If the session is in the middle of a turn, the message is queued after that turn.
- If the session it was handed to has been deleted: the task stops and stays in the table for you to delete.
- Runs missed while the core was not running are not made up. After the core starts, the next run is counted from now. For punctuality, keep the core running, see [Keeping it running, and servers](service.en.md). To run even when nobody is logged in, only Linux can do it (`loginctl enable-linger`, or install it as a system service); on macOS and Windows the service is on only while you are logged in, see [What to know about each system](service.en.md#what-to-know-about-each-system).

### Permissions and confirmation

- A session opened anew each time: it follows the rules for a new session, full access; if `permission.start_read_only` is set, read-only. Nobody is watching such a session: anything that needs confirmation is not done, and "Needs confirmation, no one to confirm" is recorded on the timeline, and the AI tries another way; the AI also cannot ask you questions. For the rules of confirmation see [Permissions and sandbox](permissions.en.md).
- One that runs in an existing session: it follows that session's own permissions. Sessions opened in the terminal or the web UI pop up a confirmation box, and if nobody answers by `permission.confirm.timeout` (300 seconds by default), it is denied automatically.

### Where to see the results

- When a session opened anew each time finishes, the terminal and the tray pop up a system notification, "Scheduled task done" (in the tray, "Scheduled task finished") or "Scheduled task didn't finish", and clicking it opens that session. Whether the terminal can pop one up depends on the terminal and the system: on Windows only a terminal that recognizes notification sequences itself, such as WezTerm, can, see [Terminal](heads/tui.en.md#notifications). The tray pops them up on all three systems, see [Tray](heads/applet.en.md#notifications).
- Those sessions are in the session list like any other session; open one to see its timeline.
- On the web UI's "Scheduled tasks" page, click a task to see the last result; a skipped one gives the reason, for example "The session is gone; the task stopped".

## Loops: /loop

A loop makes a message run over and over in this session. There are three ways to write it: a fixed interval, no interval, and nothing at all. As soon as you type it, it runs once first.

### Fixed interval

```text
/loop 5m Look at CI and tell me if anything failed
```

The interval is written `30s`, `5m`, `2h` or `1d`, and can also go at the end: `/loop Look at CI every 5m`. The minimum is 60 seconds; anything shorter is counted as 60 seconds.

### No interval: the AI decides the next time

```text
/loop Watch the deployment, and look again at the next step
```

In each turn, the AI uses `schedule_wakeup` to decide how long until the next run (at least 60 seconds), and can also use it to stop the loop. If in some turn the AI does not set a next run, the loop stops.

### Nothing at all: autonomous loop

```text
/loop
```

With no specific request, the AI decides what to do and when the next time is, and the reply is "Loop started: the AI decides what to do and when to run next". Like the one with no interval, it runs once right away, uses `schedule_wakeup` each turn to set the next run, and stops if it does not; the only difference is that what is handed to the AI each time is not a message you wrote, but a fixed sentence in English:

```text
No new instructions. Continue on your own judgment, then schedule the next wakeup or stop.
```

The message shown in the terminal sidebar's "Loop" section, and for this loop in the list `miyu schedule` prints, is this sentence too.

In the web UI, typing a bare `/loop` in a new session that is not yet open does not open a session; it only shows "Type what to say on each loop"; say something first to open the session, then type it.

### Written wrongly

If only an interval is written with no message (`/loop 5m`, `/loop every 5m`), no loop is created and the usage is returned:

```text
Invalid arguments. Usage:
/loop  No prompt: let the AI decide what to do and when
/loop <interval> <prompt>  Send it at a fixed interval, such as 5m or 2h
/loop <prompt>  Let the AI pick when to run next
/loop off  Stop this session's loops
```

An interval that cannot be recognized (`/loop 5x look`) is not an error; the whole line is treated as a message of the no-interval kind.

### What you see while it runs

- Terminal: on the line above the input box, on the right, the time of the next run is written, to the left of it when there is a goal; the sidebar gets a "Loop" section, with how often, the next run, and the message.
- Web UI: at the top right of the input box, the time of the next run; the right sidebar's "Scheduled tasks" card has it, marked "Loop".

### How to stop

```text
/loop off
```

This stops this session's loop, and the reply is "Stopped this session's loops.". `/stop` does not stop loops.

### How it differs from schedules

Loops and schedules are recorded in the same table, and `miyu schedule` lists loops too. The difference is that a loop follows this session:

- It runs only in the session where you typed `/loop`, and a session has only one loop at a time; typing `/loop` again replaces the old one.
- When the session is deleted, the loop stops with it.
- Only sessions whose preset has "Loop tasks" turned on have `/loop`; otherwise it answers "No such command".

Like schedules, loops run on the core, so the terminal or the web UI does not need to stay open; runs missed while the core is stopped are not made up.

## Goals: /goal

This gives the session a goal. While a goal is on, as soon as the session goes idle it starts the next turn by itself, until the AI reports it is done or stuck. Only the main session on this machine can use it; subagents and sessions on chat platforms do not have it.

### Set, view, stop

| Type | What it does |
|---|---|
| `/goal Fix all the failing tests under tests/` | Sets a goal, and the session starts running when it is idle. If there is already an unfinished one, this changes it; a stopped or stuck one carries on running after it is changed |
| `/goal --rounds 20 Fix all the failing tests under tests/` | Same as above, at most 20 rounds. `0` means no limit, and so does leaving it out; when changing a goal, what you leave out stays as it was |
| `/goal` | See progress: the goal, the state, which round |
| `/goal pause` | Pause |
| `/goal resume` | Resume |
| `/goal clear` | Clear |

The AI can also set a goal itself with the `goal` tool, but if this session already has a goal, only you can change it.

### What counts as done, and what happens when stuck

- Done: the AI thinks it is finished, reports completion with the `goal` tool, and then writes a wrap-up for you. The state becomes "Completed", and no new turn starts.
- Stuck: the AI reports being stuck and writes a reason, and the state becomes "Blocked: <reason>". A goal must have run at least 3 rounds before it can be reported stuck; if you spoke during that time, this limit does not apply. A stuck goal is handled like a stopped one: `/goal resume`, or change the goal, and it carries on.
- Reaching the number of rounds set by `--rounds` is recorded as stuck.
- If a turn ends with the AI using no tool at all, the state becomes "Waiting for reply", and it waits for you to say something before running on.
- While a background command is still running, the next turn is not started; it waits for the command to report, for at most 20 minutes, and after that it starts as usual.
- After the core restarts, a goal that was on becomes paused, and you need `/goal resume`.

Apart from `--rounds`, there is no limit on time or cost. Each turn's own limit is in "When nobody is watching" below.

### Where to see it

- Terminal: on the right of the line above the input box it says "Goal · round N" (with a round limit, "Round N/M"), and for stopped, waiting and blocked ones it shows the state instead. Click it with the mouse to open a floating window, with the goal, state, rounds, time spent and usage.
- Web UI: at the top right of the input box, the goal and which round. Click it to open a layer, where you can change the goal text, and "Pause", "Resume" and "Clear".

## When nobody is watching

The turns above that start by themselves (turns opened by schedules, loops and goals, and turns woken by reports from background commands and subagents) are all subject to the limits below:

| | A turn you start in a session someone is watching | A turn that starts by itself in a session someone is watching | A session nobody is watching | Subagents | Forked subagents |
|---|---|---|---|---|---|
| Which ones | The ones you start by saying something in the terminal or the web UI | Those started by schedules, loops and goals, or woken by reports | Sessions a schedule opens each time, sessions on chat platforms, `miyu ask` | Sent out by `subagent` | Sent out by `subagent` with `fork` |
| Most model requests in one turn | No limit | The preset's `[limits] unattended_steps`, `500` by default | Same as the left, counted for every turn | `800`, regardless of the preset | `500`, regardless of the preset |
| Things that need your confirmation | A confirmation box pops up and waits for `permission.confirm.timeout` (300 seconds by default); if nobody answers, it is denied automatically | Same as the left | Not done; "Needs confirmation, no one to confirm" is recorded | It follows the session that sent it: if that session has someone watching, the confirmation box pops up on your side, marked with which subagent it is | Same as subagents |
| The AI asking you (`ask_user`) | Can, and waits for your answer as long as it takes | Can, and waits for your answer as long as it takes | This tool does not exist | No | No |

When a turn reaches its request limit, that turn stops there, and the web UI says "Request limit reached". To change the limit, write it in the preset file:

```toml
[limits]
unattended_steps = 200
```

See [Personas and presets](personas-presets.en.md).

Cost has no automatic limit. To keep an eye on it, see the usage section of [Models](models.en.md#usage-and-cost): `/usage` and `/context` in the terminal (split by use, with subagents listed separately), and the "Usage" page in the web UI's settings.

To stop everything:

| What to stop | How |
|---|---|
| This turn, background commands, subagents | `/stop` |
| Loops | `/loop off` |
| Goals | `/goal pause` or `/goal clear` |
| Schedules | `miyu schedule pause <id>`, `miyu schedule rm <id>`, or the web UI's "Scheduled tasks" page |

## When something goes wrong

| What you see | What to do |
|---|---|
| "Needs confirmation, no one to confirm" | Nobody can confirm in a session that a schedule opened anew. Change it to run in a session you have open with `--session`, or turn off that kind of protected command in [Permissions and sandbox](permissions.en.md) |
| The web UI's schedule says "The session's preset turned this off; skipped" | A task the AI created, and that session's preset has "Scheduled tasks" or "Loop tasks" turned off. Turn it on in the preset |
| "The session is gone; the task stopped" | The session it was handed to was deleted. Delete this task and create a new one |
| "Couldn't open a new session; skipped" | The persona, preset or working directory chosen when it was created cannot be used now. Delete it and create it again |
| "The schedule table was broken; all scheduled tasks are gone" | The wakeup table could not be read, and the core replaced it with an empty one. Create them again |
| A background command's "Stopped: output too frequent" | A watched command wrote too many lines. Have the AI use something like `grep` to keep only the lines worth seeing |
| A goal stays at "Waiting for reply" | Say something back, or `/goal resume` |
| A goal does not move after the core restarts | `/goal resume` |
| `/loop` answers that there is no such command | This session's preset does not have "Loop tasks" turned on |
