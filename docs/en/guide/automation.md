# Letting the AI work on its own

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page covers five features that let the AI work without waiting for you to speak: subagents, background commands, schedules, loops and goals, along with the limits that apply to them when nobody is watching, and how to stop them.

| What you want to do | Use |
|---|---|
| Split a big job among several helpers that work in parallel | Subagents |
| Run a long command in the background and deal with it once it finishes | Background commands |
| Do something automatically every morning | Schedules |
| Check on something every few minutes | Loops `/loop` |
| Give the AI a goal and have it work until the goal is done | Goals `/goal` |

Each of these five features is provided by a shipped package, and you can use it only when the preset has that package turned on: subagents are `base-subagent`, background running is `base-jobs`, schedules are `base-schedule`, loops are `base-loop`, and goals are `base-goal`. The shipped presets `Everything` and `Development` both have all five turned on; for how to turn packages on and off in a preset, see [Personas and presets](personas-presets.md).

## Subagents

A subagent is a separate session that the AI opens. The AI uses the `subagent` tool to hand a task to the subagent, which does the work in the background; when it is done, the last thing it said is sent back as its report to the session that sent it out. If the AI calls `subagent` several times in one step, it sends out that many subagents at once.

### Sending out subagents

Just tell the AI, for example "Send out three subagents to check which functions in `api/`, `web/` and `cli/` are unused, and summarize for me". Whether to send any, and how many, is up to the AI.

When the AI sends out a subagent, it can choose these options:

| Option | What it does | When left out |
|---|---|---|
| Model pool `pool` | The subagent uses a model from this pool. Only a pool with `subagent = true` can be chosen, see [Models](models.md) | It uses the model the sending session is using at that moment |
| Persona `persona` | The subagent uses this persona. Only a persona with `subagent = true` in `persona.toml` can be chosen; among the shipped personas, only `software-engineer` qualifies | No persona is used |
| Continue the current conversation `fork` | The subagent carries on from this session's conversation as of the current step, can see everything said before, and has the same model and persona as the sending session. With `fork` written, a model pool and persona can no longer be chosen; a forked subagent cannot fork again | The subagent sees only the message it was given, and cannot see this session's content |
| Read-only `read_only` | The subagent can only read, and cannot change anything | It follows the permissions of the sending session |
| Attachments `attachments` | Files handed to the subagent along with the task, at most 8 | No attachments |

A subagent uses the same working directory, the same preset and the same permission level as the session that sent it; if the sending session is read-only, the subagent is read-only too.

A subagent can send out one more level of subagents, but no deeper. Only sessions on this machine can send out subagents; sessions on chat platforms do not have this tool.

### Checking on it while it runs

While subagents are running, you can see them in the interface:

- Terminal UI: below the input box there is a blank line, then a `● Main session` line, then one line per subagent, showing its name, what it is doing, and how many tokens and how much time it has used. When the input box is empty, press `↓` to move onto these lines, and `Enter` to switch into that subagent's session; select the `● Main session` line and press `Enter` to switch back; select a subagent and press `x` to stop it.
- Web UI: the middle of the line below the input box says `Background tasks: N`; click it to expand a list of this session's background commands and subagents, where subagents sent out by a subagent hang under it. Click `Open subagent session` to switch in. The `Background tasks` card in the right sidebar lists them too, and clicking one opens the subagent's session in the main area.

After you switch into a subagent's session, you can talk to it directly. Its report will then note `The user also talked to this subagent during the task.`, and the AI that sent it can see this.

### Receiving the report

When a subagent finishes a turn and goes idle, it sends the last thing it said in that turn back to the session that sent it. A report is at most 30000 characters; if it is longer, the beginning and the end are kept, half each. If the sending session is idle, it starts a new turn as soon as the report arrives and carries on; if it is working, it sees the report at its next step. The AI and the subagent can also leave messages for each other with `send_message`.

### Stopping subagents

You can stop subagents in the following ways:

- Ask the AI to stop a particular subagent with the `jobs` tool.
- Terminal UI: in the main session, when no turn is running, press `Esc` twice in a row to stop all the subagents this session sent out; when you have switched into a subagent's session, press `Esc` twice or `Ctrl+C` to stop it. You can also select that line and press `x`.
- Web UI: in `Background tasks`, click `Stop` or `Stop all`.
- `/stop`: interrupts this turn, then stops the background commands and subagents this session sent out; this session's loop is stopped too.

### When background running is turned off

If the preset has `Background` (`base-jobs`) turned off, the AI waits in place for a subagent's report after sending it out, and goes on to the next step only once the report has arrived.

## Background commands

When the AI runs a command with `shell`, it can put the command in the background: the AI gets a job id at once (for example `j1`) and carries on with other things; when the command finishes, the result comes back automatically, and the AI does not need to ask for it. This feature needs `Background` turned on in the preset.

### Putting a command in the background

A command runs in the background in two cases:

- You tell the AI "run `npm run build` in the background and tell me when it is done".
- A foreground command that has not finished after its time limit (120 seconds if the AI does not set one, and at most 600 seconds if it does) is moved to the background and keeps running.

### Watching the log

When the AI runs a background command, it can ask to "watch" it: every time the command writes a line to standard output, that line reaches the AI right away, which suits waiting for a certain line to show up in a log. Lines that come out close together (within 200 milliseconds) are merged and reach the AI once. Standard error does not reach the AI; it is only written to the output file.

If a watched command reaches the AI 120 times within an hour, the command is stopped and recorded as `Stopped: output too frequent`.

### Checking on it while it runs

While background commands are running, you can check on them in the interface:

- Terminal UI: below the input box there is a `Background: N` button. When the input box is empty, press `↓` to move onto the button, and `Enter` to open the `Background` panel: use `↑` and `↓` to select, `Enter` to expand and see the output, `x` to stop, and `Esc` to close. When a command ends, a line `Background command done · <title> · <elapsed>` is recorded on the timeline; failed and stopped commands are written differently.
- Web UI: the same as for subagents, in `Background tasks: N` and in the `Background tasks` card of the right sidebar; click `View command and output` to see the output.

### Stopping background commands

You can stop background commands in the following ways:

- Have the AI stop them: the AI uses the `jobs` tool to list commands, read their output, and stop them.
- In the terminal UI's `Background` panel, press `x`; in the web UI, click `Stop`.
- `/stop` stops all of this session's background commands and subagents.

When the core stops or restarts, all running background commands are stopped and recorded as `stopped by core restart`.

### Limits and defaults

| Limit | Value |
|---|---|
| How long one background command can run at most | Set by `jobs.max_running`, `30m` by default, and it can be set from `1m` to `2h`. When the time is up, the command is stopped and recorded as `stopped: time limit` |
| How much one background command can output at most | 5 GB; when it is reached, the command is stopped and recorded as `stopped: output too large` |
| How many times a watched command can reach the AI within an hour | 120 |

To change the longest running time, change it in `General → Sessions → Maximum background command runtime` on the settings page (type `/settings` in the terminal UI or the web UI to open it), or run:

```sh
miyu config set jobs.max_running 1h
```

The change takes effect from the next turn. This limit applies only to background commands; it does not limit subagents.

## Schedules

A schedule hands a message to a session at the set time, so that the AI runs a turn. Tasks are recorded in `~/.miyu/root/schedules.db` (the data root is `~/.miyu` by default, and `%USERPROFILE%\.miyu` on Windows).

### Adding with commands

There are three ways to write the time; here is an example of each:

```sh
# cron: weekdays at 8 am
miyu schedule add --cron '0 8 * * 1-5' Check last night's CI and list any failures

# run once at a given time
miyu schedule add --at '2026-12-01 09:00' Remind me to submit the monthly report

# at an interval, at least 60 seconds
miyu schedule add --every 2h --session 0198c2a4-7e1b-7c3d-9a2f-4b5c6d7e8f90 Check the build queue
```

Which session the task runs in:

- With `--session <id>`: each time, the message is handed to this existing session.
- Without it: each time, a new session is opened. `--persona`, `--no-persona`, `--preset` and `--cwd` decide which persona, preset and working directory the new session uses; if you leave out the persona or preset, the default one is used, and the working directory is each new session's own default workspace, `~/.miyu/root/workspace/<session id>/`.

To view, pause and delete tasks, you can use:

```sh
miyu schedule                 # list all; each line starts with the task id, for example t1
miyu schedule pause t1        # pause
miyu schedule resume t1       # resume; the next run is counted again from now
miyu schedule rm t1           # delete
```

For each argument, see [Command line](cli.md#miyu-schedule).

### Adding in the web UI

The web UI's settings has a page called `Scheduled tasks`: each task takes one row, showing the message, when it runs, which session it runs in, and when it runs next; you can switch tasks on and off, pause, resume and delete them. Click `New`, fill in `Say`, choose `Daily`, `Every`, `Once` or `Custom` for `When` (Custom takes a five-field cron), and choose `New session each time` or `A session` for `Run in`. Click a task to see the result of its last run.

The `Scheduled tasks` card in the right sidebar lists the tasks that run on this session, and loops are listed there too.

The terminal UI has no schedules page, so you use the `miyu schedule` command.

### Letting the AI create one

You can tell the AI "remind me to write a diary at 10 every night", and the AI uses `cron_create` to create a schedule on this session, which sends the message back to this session when the time comes.

- The AI writes a five-field cron, in the machine's time zone. A task that runs only once deletes itself after it runs.
- In one session, the AI can create at most 20 schedules. All schedules together (yours, the AI's, and those created by packages) can be at most 200; when that is reached, only new ones are refused.
- Tasks the AI created and tasks you created by command are recorded in the same table. Both `miyu schedule` and the web UI's `Scheduled tasks` page list the AI's tasks (the web UI labels them `By AI`); the AI uses `cron_list` to see all the tasks that run on this session, including those you pointed at this session with `--session`, and can also delete them with `cron_delete`.
- When a task the AI created comes due, if this session's preset has `Scheduled tasks` turned off, the task does not run this time. Tasks you created do not depend on the preset.

### When the time comes

When a schedule comes due, it is handled as follows:

- If the session is in the middle of a turn, the message is queued after that turn.
- If the message goes to a session opened by `miyu ask`, and no terminal UI or web UI has that session open at the moment: schedules you created still run. Schedules and loops the AI created in such a session only record the message in the session without starting a turn, and you see it the next time you speak in that session; `miyu schedule` shows the last run as `recorded, handled at the next message`.
- If the session it was handed to has been deleted: the task stops and stays in the table for you to delete.
- Runs missed while the core was not running are not made up. After the core starts, the next run is counted from now. If you need it to run on time, keep the core running, see [Keeping it running, and servers](service.md). If it also has to run when nobody is logged in, only Linux can do that (`loginctl enable-linger`, or install it as a system service); on macOS and Windows the service runs only while you are logged in, see [What to know about each system](service.md#differences-between-systems).

### Permissions and confirmation

- A session opened anew each time: it follows the rules for a new session and uses full access; if `permission.start_read_only` is set, it is read-only. Nobody is watching such a session: anything that needs confirmation is not done, `Needs confirmation, no one to confirm` is recorded on the timeline, and the AI tries another way; the AI also cannot ask you questions. For the rules of confirmation, see [Permissions and sandbox](permissions.md).
- A task that runs in an existing session: it follows that session's own permissions. Sessions opened in the terminal UI or the web UI pop up a confirmation box, and if nobody answers by `permission.confirm.timeout` (300 seconds by default), the request is denied automatically.

### Seeing the results

After a schedule runs, you can see the results in these places:

- When a session opened anew each time finishes, the terminal UI and the system tray pop up a system notification, `Scheduled task finished` or `Scheduled task didn't finish`, and clicking it opens that session. Whether the terminal UI can pop one up depends on the terminal and the system: on Windows, only a terminal that recognizes notification sequences itself, such as WezTerm, can do it, see [Terminal UI](heads/tui.md#notifications). The system tray pops up notifications on all three systems, see [System tray](heads/applet.md#notifications).
- Those sessions are in the session list like any other session, and you can open one to see its timeline.
- On the web UI's `Scheduled tasks` page, click a task to see its last result; if a run was skipped, the reason is given, for example `The session is gone; the task stopped`.

## Loops: /loop

A loop makes a message run over and over in this session. There are three ways to write a loop: with a fixed interval, with no interval, and with nothing at all. As soon as you enter the `/loop` command, it runs once first.

### Fixed interval

```text
/loop 5m Look at CI and tell me if anything failed
```

The interval can be written as `30s`, `5m`, `2h` or `1d`, and it can also go at the end: `/loop Look at CI every 5m`. The shortest interval is 60 seconds; anything shorter is counted as 60 seconds.

### No interval: the AI decides the next time

```text
/loop Watch the deployment, and look again at the next step
```

In each turn, the AI uses `schedule_next` to decide how long until the next run (at least 60 seconds), and can also use it to stop the loop. If in some turn the AI does not decide on a next run, the loop stops.

### Nothing at all: autonomous loop

```text
/loop
```

When you give no specific request, the AI decides what to do and when to run next, and the reply is `Loop started: the AI decides what to do and when to run next`. Like the form with no interval, it runs once right away, uses `schedule_next` each turn to decide the next run, and stops if it does not decide; the only difference is that what reaches the AI each time is not a message you wrote, but a fixed sentence in English:

```text
No new instructions. Continue on your own judgment, then schedule the next round or stop.
```

The message shown in the `Loop` section of the terminal UI's sidebar, and for this loop in the list `miyu schedule` prints, is this sentence too.

In the web UI, if you type only `/loop` in a new session that has not started yet, no session is started; it only shows `Type what to say on each loop`. Say something first to start the session, then type `/loop`.

### Wrong usage

If you write only an interval and no message (`/loop 5m`, `/loop every 5m`), no loop is created, and the usage is returned instead:

```text
Invalid arguments. Usage:
/loop  No prompt: let the AI decide what to do and when
/loop <interval> <prompt>  Send it at a fixed interval, such as 5m or 2h
/loop <prompt>  Let the AI pick when to run next
/loop off  Stop this session's loops (clear or stop works too)
```

If the interval cannot be recognized (`/loop 5x look`), it is not an error; the whole line is treated as a message of the no-interval kind.

### Checking on it while it runs

While a loop is running, you can check on it in the interface:

- Terminal UI: the time of the next run is shown on the right of the line above the input box, and a goal, if there is one, is shown to its left; the sidebar gets a `Loop` section, showing how often it runs, the time of the next run, and the message.
- Web UI: the time of the next run is shown at the top right of the input box; the `Scheduled tasks` card in the right sidebar also lists the loop, marked `Loop`.

If you have just reverted a turn and not dealt with it yet, the loop waits instead of running right away: typing `/loop` then ends its reply with `A revert is still pending, so the loop waits: it starts after you say something or run /restore`. Because what happens after a revert is up to you, the loop starts only after you say something or run `/restore`.

### Stopping a loop

Run:

```text
/loop off
```

This command stops this session's loop, and the reply is `Stopped this session's loops.`. You can write `clear` or `stop` in place of `off` (if more words follow, the line is still taken as the message to say). `/stop` stops loops too: while it interrupts this turn, it also turns off this session's loop. If you type `/loop` while the AI is working step by step, the loop runs for the first time only after that turn ends.

### How it differs from schedules

Loops and schedules are recorded in the same table, and `miyu schedule` lists loops too. The difference is that a loop belongs to this session:

- A loop runs only in the session where you typed `/loop`, and a session can have only one loop at a time; typing `/loop` again replaces the old loop.
- When the session is deleted, the loop stops with it.
- Only sessions whose preset has `Loop tasks` turned on have the `/loop` command; otherwise it is not in the command list.

Like schedules, loops are run by the core, so the terminal UI or the web UI does not need to stay open; runs missed while the core is stopped are not made up.

## Goals: /goal

A goal is something you set for a session to achieve. While a goal is on, as soon as the session goes idle it starts the next turn by itself, until the AI reports that the goal is done or stuck. Only the main session on this machine can use goals; subagents and sessions on chat platforms do not have this feature.

### Setting, viewing and stopping a goal

| Type | What it does |
|---|---|
| `/goal Fix all the failing tests under tests/` | Sets a goal, and the session starts running when it is idle. If there is already an unfinished goal, this changes it; a paused or stuck goal carries on running after it is changed |
| `/goal --rounds 20 Fix all the failing tests under tests/` | Same as the line above, but runs at most 20 rounds. `0` means no limit, and leaving it out also means no limit; when you change a goal, the settings you leave out keep their old values |
| `/goal` | Shows the progress: the goal, the state, and which round it is on |
| `/goal pause` | Pause |
| `/goal resume` | Resume |
| `/goal clear` | Clear |

The AI can also set a goal itself with the `goal` tool, but if this session already has a goal, only you can change it.

### Done and stuck

- Done: when the AI thinks the work is finished, it reports completion with the `goal` tool, and then writes a wrap-up for you. The state becomes `Completed`, and no new turn starts.
- Stuck: when the AI reports being stuck, it writes a reason, and the state becomes `Blocked: <reason>`. A goal must have run at least 3 rounds before it can be reported stuck; if you spoke during that time, this limit does not apply. A stuck goal is handled the same way as a paused one: run `/goal resume`, or change the goal a little, and it carries on running.
- Reaching the number of rounds set by `--rounds` is recorded as stuck.
- If a turn ends without the AI using a single tool, the state becomes `Waiting for reply`, and it waits for you to say something before it runs on.
- While a background command is still running, the next turn does not start; it waits for the background command to report, for at most 20 minutes, and after that the next turn starts as usual.
- After the core restarts, a goal that was on becomes paused, and you need to run `/goal resume` to resume it.

Apart from `--rounds`, goals have no limit on time or cost. Each turn's own limit is described in "When nobody is watching" below.

### Seeing the progress

- Terminal UI: the right of the line above the input box says `Goal · round N` (`Round N/M` when a round limit is set), and when the goal is paused, waiting for a reply or blocked, the state is shown there instead. Click it with the mouse to open a floating window showing the goal, state, rounds, time spent and usage.
- Web UI: the top right of the input box shows the goal and which round it is on. Click it to open a layer where you can change the goal text, and also click `Pause`, `Resume` and `Clear`.

## When nobody is watching

The turns above that start automatically (turns started by schedules, loops and goals, and turns triggered by reports from background commands and subagents) are all subject to the limits below:

| | A turn you start in a session someone is watching | A turn that starts automatically in a session someone is watching | A session nobody is watching | Subagents | Forked subagents |
|---|---|---|---|---|---|
| Which ones | Turns you start by saying something in the terminal UI or the web UI | Turns started by schedules, loops, goals and reports | Sessions a schedule opens each time, sessions on chat platforms, `miyu ask` | Subagents sent out by `subagent` | Subagents sent out by `subagent` with `fork` |
| Most model requests in one turn | No limit | Set by the preset's `[limits] unattended_steps`, `500` by default | Same as the column to the left, counted for every turn | `800`, not affected by the preset | `500`, not affected by the preset |
| Things that need your confirmation | A confirmation box pops up and waits for `permission.confirm.timeout` (300 seconds by default); if nobody answers, the request is denied automatically | Same as the column to the left | Not done; `Needs confirmation, no one to confirm` is recorded | It follows the session that sent it out: if that session has someone watching, the confirmation box pops up on your side, marked with which subagent it is | Same as subagents |
| The AI asking you (`ask_user`) | Yes, and it waits for your answer as long as it takes | Yes, and it waits for your answer as long as it takes | This tool does not exist | No | No |

When a turn reaches its limit on model requests, that turn stops there, and the web UI shows `Request limit reached`. To change the limit, write it in the preset file:

```toml
[limits]
unattended_steps = 200
```

For details, see [Personas and presets](personas-presets.md).

Cost has no automatic limit. If you want to keep an eye on it, see the usage section of [Models](models.md#usage-and-cost): run `/usage` and `/context` in the terminal UI (split by use, with subagents listed separately), or look at the `Usage` page in the web UI's settings.

To stop everything, you can use:

| What to stop | How |
|---|---|
| This turn, background commands, subagents | `/stop` |
| Loops | `/loop off`, or `/stop` |
| Goals | `/goal pause` or `/goal clear` |
| Schedules | `miyu schedule pause <id>`, `miyu schedule rm <id>`, or the `Scheduled tasks` page in the web UI |

## Troubleshooting

| What you see | What to do |
|---|---|
| `Needs confirmation, no one to confirm` | Nobody can confirm anything in a session that a schedule opened anew. Change the task to run in a session you have open with `--session`, or turn off that kind of protected command in [Permissions and sandbox](permissions.md) |
| A schedule in the web UI says `The session's preset turned this off; skipped` | This is a task the AI created, and that session's preset has `Scheduled tasks` or `Loop tasks` turned off. Turn it on in the preset |
| `The session is gone; the task stopped` | The session the task was handed to has been deleted. Delete this task and create a new one |
| `Couldn't open a new session; skipped` | The persona, preset or working directory chosen when the task was created cannot be used now. Delete the task and create it again |
| `The schedule table was broken; all scheduled tasks are gone` | The schedule table could not be read, so the core replaced it with an empty one. You need to create your schedules again |
| A background command shows `Stopped: output too frequent` | A watched command wrote too many lines. Have the AI use a command like `grep` to keep only the lines worth seeing |
| A goal stays at `Waiting for reply` | Reply with something, or run `/goal resume` |
| A goal does not move after the core restarts | Run `/goal resume` |
| `/loop` is not in the command list | This session's preset does not have `Loop tasks` turned on |
