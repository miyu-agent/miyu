# Rescue

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

When Miyu is broken (the core will not start, the config has been broken by an edit, or an interface will not open), you can use `miyu rescue` to start LiteMiyu and let the AI help you fix Miyu in the terminal. This page explains what LiteMiyu is, how to install it, and how to use it to repair Miyu.

## What is LiteMiyu?

LiteMiyu is a separate program, `litemiyu`: a single process and a single file that runs full screen in the terminal, and can talk to a model, read and write files, and run commands on its own. It does not use Miyu's core, and does not read Miyu's sessions or memory. For now it is available only on Linux x86_64 (glibc 2.39 or later).

LiteMiyu keeps its files in its own directories, which do not affect Miyu's data root (`~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows), and vice versa:

| Contents | Location |
|---|---|
| Config `config.toml`, keys `secrets.toml` | `~/.config/litemiyu/` |
| Sessions, memory | `~/.local/share/litemiyu/` |
| Cache | `~/.cache/litemiyu/` |
| Run log, input history | `~/.local/state/litemiyu/` |

If variables such as `XDG_CONFIG_HOME` are set, the files go where those variables say.

## Installing LiteMiyu

LiteMiyu has to be installed separately, and how depends on your distribution:

- Arch Linux: install `litemiyu` from the AUR, for example by running `paru -S litemiyu`. The program is installed at `/usr/bin/litemiyu`.
- Other distributions: download `litemiyu-<version>-linux-x86_64.tar.gz` and `SHA256SUMS` from the [releases page](https://github.com/miyu-agent/litemiyu/releases), verify them, then put the `litemiyu` from the archive into a directory in your `PATH`:

  ```sh
  sha256sum -c SHA256SUMS
  tar xf litemiyu-<version>-linux-x86_64.tar.gz
  install -m755 litemiyu-<version>-linux-x86_64/litemiyu ~/.local/bin/
  ```

`miyu rescue` looks for `litemiyu` in this order: the directory of the `miyu` you ran, the directory where `miyu` actually is (after resolving links), and then `PATH`. Relative directories in `PATH` are not counted.

## Using miyu rescue

Run:

```sh
miyu rescue [<arguments>…]
```

This command does not connect to the core and does not start the core; instead it does the following:

1. From Miyu's system config `~/.miyu/etc/config.toml` and the secrets file, it works out which provider the default model (`models.chat`) connects to, which model it uses, which API and which key.
2. It puts these four things into four environment variables and hands them to LiteMiyu. If you have already set one of these variables yourself, your value is kept.

   | Environment variable | Contents |
   |---|---|
   | `LITEMIYU_RESCUE_BASE_URL` | The address of the provider |
   | `LITEMIYU_RESCUE_MODEL` | The model name |
   | `LITEMIYU_RESCUE_API` | The API: `openai-chat`, `anthropic`, `openai-responses` |
   | `LITEMIYU_RESCUE_API_KEY` | The key; if the default model has no key, this variable is not set |

3. It runs `litemiyu --rescue`, passing the arguments you wrote after it unchanged. The exit code is LiteMiyu's exit code.

The location of Miyu's data root is not passed to LiteMiyu, so you need to tell the AI when repairing.

LiteMiyu recognizes three arguments, and any you write override the environment variables: `--base-url <url>`, `--model <name>` and `--api <kind>`. The key can only be passed through the environment variable.

In the following cases where the variables cannot be filled in, `miyu rescue` first prints a warning line, fills in none of the four variables, and still starts LiteMiyu, which then uses its own config:

| What you see | Why |
|---|---|
| `miyu: warning: cannot read Miyu's configuration: …; litemiyu will find a model itself` | The config file or the secrets file cannot be parsed at all, or the default model cannot be used. If only one item is written wrongly, that item is skipped and the rest are read as usual |
| `miyu: warning: the chat model uses the extension driver <package>/<driver>, which litemiyu cannot use; litemiyu will find a model itself` | The default model uses a driver that comes with a package |

## How rescue mode differs from normal mode

`litemiyu --rescue` is made specifically for repairing things, and differs from normal mode in these ways:

- It writes nothing to disk: no session is recorded, no config is changed and no input history is kept. So it works even when the disk is full or the directory is read-only. Once you close it, nothing is left behind.
- The AI has only five tools: `read`, `write`, `edit`, `shell` and `jobs`. There is no web access, no subagents, no memory, no skills and no MCP.
- The AI has no special instructions about Miyu, so you need to say clearly in your first message what to fix and where the files are.
- There is no permission level to switch; files and commands are acted on directly, and Miyu's data root can be changed too. Dangerous commands are recognized the same way as in Miyu (see [Permissions and sandbox](permissions.md#commands-that-need-confirmation)): the kinds that are refused outright are still refused; the kinds that need confirmation ask you first, and you can only allow this one time or refuse, with no switch to change that.
- The right side of the input box's top border shows `rescue mode`. The command list has no `/sessions`, `/config`, `/loop`, `/model` or `/effort`, and the external editor on `Ctrl+G` cannot be used.

## A repair example

Here is an example of a complete repair: after you edit `~/.miyu/etc/config.toml` by hand, running `miyu` reports `the core couldn't start: …`.

1. Run:

   ```sh
   miyu rescue
   ```

   The screen switches to LiteMiyu's full-screen interface, and the input box shows `rescue mode`.

2. Tell the AI what is going on, for example:

   ```text
   The Miyu core will not start. Its data root is ~/.miyu, the system config is ~/.miyu/etc/config.toml, and the core log is ~/.miyu/var/log/core.log.
   Read the last few dozen lines of the log to find the cause, fix the config, and tell me what you changed.
   ```

3. The AI reads the log, changes the files, and at the end tells you what it changed. Check its changes yourself.
4. Press `Ctrl+D` (when the input box is empty) or type `/exit` to quit.
5. Run `miyu` and check whether the core starts normally.

If the config file cannot be parsed at all, step 1 first prints the warning that Miyu's configuration cannot be read. If LiteMiyu has no model configured either, it does not enter the interface; instead it prints what is missing and the usage, then exits (exit code `2`). The first line is:

```text
litemiyu --rescue: no model to use; missing LITEMIYU_RESCUE_BASE_URL, LITEMIYU_RESCUE_MODEL.
```

In that case you need to give it a model yourself (replace the address and model name with your provider's; the key in the example is a fake one):

```sh
LITEMIYU_RESCUE_API_KEY=sk-example miyu rescue --base-url https://api.deepseek.com/v1 --model deepseek-chat
```

When `--api` is not given, `openai-chat` is used. When no key is given, it still enters the interface, and the interface shows `No key given (LITEMIYU_RESCUE_API_KEY); requests go without authentication`.

If you do not want to type these by hand next time: while Miyu is still working, run `litemiyu config` to open the settings screen, choose `Import from Miyu…` where providers are added to import Miyu's providers and keys into LiteMiyu's own config, and then pick the model for the main conversation. When neither environment variables nor arguments give a model, rescue mode uses the model in LiteMiyu's own config.

If the `miyu` program itself is broken and cannot run, you can run `litemiyu --rescue` directly, and give it the model through environment variables and arguments as described above.

## Other systems

There is no LiteMiyu on macOS or Windows. When `miyu rescue` cannot find it, it prints:

```text
miyu: litemiyu not found
hint: only Linux is supported for now
```

The exit code is `1`. On Linux, when LiteMiyu cannot be found, the hint is replaced with how to install it.

On macOS and Windows, if the core is broken, you need to investigate it yourself with the following steps:

1. Look at the last few dozen lines of the core log to find the cause of the error:

   ```bash
   tail -n 50 ~/.miyu/var/log/core.log
   ```

   ```powershell
   Get-Content -Tail 50 $HOME\.miyu\var\log\core.log
   ```

2. If a hand edit broke the config, open `~/.miyu/etc/config.toml` in an editor and change the broken lines back. When the core starts, a config that cannot be parsed at all is treated as empty, and the core still starts; in that case, run `miyu check` and fix the lines at the line numbers it prints.
3. After fixing, run `miyu core stop` to stop the running core, then run `miyu` to open it.

For what each error means and how to deal with it, see [Troubleshooting](troubleshooting.md#the-core-will-not-start-or-cannot-connect).

## Using LiteMiyu normally

Running it without `--rescue` gives you normal mode, in which sessions and config are saved to disk:

```sh
litemiyu            # start a conversation
litemiyu -c         # open the most recent session
litemiyu config     # open the settings screen
litemiyu ask "…"    # say one thing and print the answer, without the full-screen interface
```

- The first time you run it, it starts with a setup guide: connect a provider (if Miyu is installed on the computer, `Import from Miyu…` is listed first), choose the model for the main conversation, and choose the key mode and a light or dark theme.
- Keys: `Enter` sends, `Alt+Enter` or `Ctrl+J` starts a new line, `@` completes a file path, `Ctrl+C` interrupts while the AI is answering, and `Ctrl+D` quits when the input box is empty. Type `/help` to see all keys and commands.
- Providers, models and sessions are all managed in the full-screen interface (commands such as `/config` and `/sessions`); the command line has only the commands above.
- Every command has `--help`, for example `litemiyu ask --help`.

## When the repair fails

If it still cannot be fixed, take the last few dozen lines of `~/.miyu/var/log/core.log` and report the problem as described in [Troubleshooting](troubleshooting.md#reporting-a-problem).
