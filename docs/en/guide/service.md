# Keeping it running, and servers

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page explains how to start the core automatically at boot, how to run it on a server with no desktop, how to open the web UI from other computers and phones, and how to read the logs and stop the core. For how to install, see [Installing, upgrading and uninstalling](install.md).

## How the core runs

The core is simply `miyu` running in the background; sessions, models and schedules all live in the core. Interfaces such as the terminal UI, the web UI and the system tray only connect to it.

- If an interface cannot connect to the core when you open it, the interface starts a core itself and connects once the core is ready. So Miyu works fine without installing a service.
- Only one core runs per data root at a time. The data root is `~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows, or the directory `MIYU_HOME` points to if you have set it.
- By default the core keeps running, and does not exit even when all interfaces are closed.

If you want the core to exit by itself when idle, enter a number of minutes in `Advanced → Core → Idle exit time` on the settings page (type `/settings` in the terminal UI or the web UI), or run:

```sh
miyu config set core.idle_exit 30
```

Once this is set, the core exits after this many minutes in a row with no connection and no turn in progress. `0` means it keeps running (the default), and the allowed range is `0` to `525600`. A change takes effect immediately, and this setting can only be written in `~/.miyu/etc/config.toml`.

To stop the core by hand, run:

```sh
miyu core stop
```

This command tells the running core to stop and returns once the core has exited; if no core is running, it does nothing. A turn in progress stops first and continues the next time that session is loaded.

To start the core by hand and check whether it is running, you can use:

```sh
miyu core start
miyu core status
```

`start` only starts the core; it opens no interface and no browser, and does nothing if the core is already running. `status` shows whether the core is running, its version and the data root; for details, see [`miyu core`](cli.md#miyu-core).

If you only want to close the web UI and keep the core running, run `miyu web stop`; to check whether the web UI is running, run `miyu web status`.

## Starting the core at boot or login

Once the service is installed, the core starts automatically at boot or login, so chat platforms and schedules do not have to wait for you to open an interface before they start working. Run:

```sh
miyu service enable
```

| Command | What it does |
|---|---|
| `miyu service enable` | Writes the service file and hands it to the system's service manager |
| `miyu service disable` | Stops the service, removes it from the service manager and deletes the service file |
| `miyu service status` | Shows whether the service is installed and whether it is enabled |

All three commands accept `--format json`, which makes them print one line `{"installed", "on", "file", "manager"}`; on failure they print `{"error", …}`.

The service runs the `miyu` you are running now (its real location, with links resolved). If `MIYU_HOME` is set, it is written into the service as well. If you later move `miyu` or change the data root, run `miyu service enable` again to rewrite the service file.

Each system uses the following:

| System | What it uses | File it writes | When it starts |
|---|---|---|---|
| Linux with a systemd user session | systemd user service | `~/.config/systemd/user/miyu.service` | Right away, and at every login after that |
| Linux without a systemd user session | Desktop autostart | `~/.config/autostart/miyu.desktop` | At the next desktop login |
| macOS | launchd user agent | `~/Library/LaunchAgents/io.github.miyu-agent.core.plist` | Right away, and at every login after that |
| Windows | Task Scheduler, with a task named `Miyu` | `%USERPROFILE%\AppData\Local\Miyu\miyu-task.xml` | At the next login |

On Linux, if `XDG_CONFIG_HOME` is set, the first two files are written under it.

When `miyu service enable` succeeds, it says `enabled and started …` (systemd, launchd), `enabled …, starts at the next desktop login` (desktop autostart) or `enabled …, starts at the next login` (Task Scheduler). `status` shows `installed, enabled: …`, `installed, not enabled: …`, `installed, starts at desktop login: …` or `not installed`. These are the commands `status` uses to ask the service manager:

| System | Command |
|---|---|
| systemd | `systemctl --user is-active miyu.service` (checks whether the core is running now) |
| launchd | `launchctl print gui/<your uid>/io.github.miyu-agent.core` (checks whether it is registered) |
| Task Scheduler | `schtasks /Query /TN Miyu` (checks whether it is registered) |
| Desktop autostart | It cannot be asked; only whether the file exists is checked |

### Differences between systems

The service managers on different systems behave differently when the core exits or when nobody is logged in:

| | systemd user service | Desktop autostart | launchd | Task Scheduler |
|---|---|---|---|---|
| After the core exits | Restarted 5 seconds after an abnormal exit, not restarted after a normal exit | Not restarted; the next time you open an interface, the interface starts the core | Restarted when the exit code is not `0`, not restarted when it is `0` | On failure, retried every 1 minute, at most 3 times |
| When nobody is logged in | Starts at login, stops at logout; after you run `sudo loginctl enable-linger $USER`, it keeps running even with nobody logged in | Does not run | Does not run | Does not run |
| When `MIYU_HOME` is set | Written into the service file | Written into the service file | Written into the service file | Cannot be installed |

- On macOS and Windows there is no way to keep the core running while nobody is logged in. On Linux you can also install it as a system service by following [Deploying to a server](#deploying-to-a-server).
- Task Scheduler needs no administrator rights, and only starts the core when you log in.
- On Windows, if `MIYU_HOME` is set, `miyu service enable` says `cannot install the service: a Windows scheduled task cannot carry MIYU_HOME`, followed on the next line by `hint: unset MIYU_HOME and try again`. If you want to use another data root and also want the core to start at login, you can use `Start at Login` in the system tray; for details, see [Data and backups](data.md#changing-the-data-root-location).

### Making the service take over now

If a core started by an interface is already running, the core the service starts notices that a core is already running and exits normally (exit code `0`); it does not replace the one that is running. To make the service take over the core right away:

1. Stop the running core: `miyu core stop`.
2. Install the service again: `miyu service enable`. It rewrites the service file from the current `miyu` location and `MIYU_HOME`, then hands it to the service manager.

| System | After step 2 |
|---|---|
| Linux (systemd user service), macOS | The service starts the core right away |
| Linux (desktop autostart), Windows | It only registers again, and the service starts the core at the next login; until then, when you open an interface, the interface starts a core itself as usual |

The same two steps switch the core to the new version after an upgrade.

### The service and environment variables

The core the service starts cannot see variables you set in your shell. The service file `miyu service enable` writes carries only `MIYU_HOME` (if you have set it) and no other variable; a Windows Task Scheduler task does not even carry `MIYU_HOME`.

For a key written in the config as `{ env = "variable" }`, the core reads it from the environment it was started in, and cannot see the variables in your shell. If you want a core started by the service to use that key, switch to the secrets file: store the key there with `miyu provider login` and write `{ secret = "name" }` in the config, so the core reads it from the secrets file and does not depend on environment variables.

If you must use an environment variable:

- systemd user service: run `systemctl --user edit miyu` and add an `Environment=` line (for how to write it, see [Keys in environment variables](#keys-in-environment-variables)). If you edit `miyu.service` directly, your change is overwritten the next time you run `miyu service enable`.
- The launchd plist and the desktop autostart `miyu.desktop`: changes you make by hand are likewise overwritten the next time you run `miyu service enable`.

If the system tray is installed, you can also use `Start at Login` in the tray menu to have the system tray start at login; for details, see [System tray](heads/applet.md).

## Deploying to a server

This section applies to Linux only. There are no server examples for macOS or Windows; if you want the core to keep running there, use `miyu service enable` from the previous section.

On a server, run the core as a dedicated system user, with the data root in `/var/lib/miyu` rather than under someone's home directory. Because `miyu service` only manages your own user, a system-level service has to be installed by hand with the steps below.

The `packaging/` directory of the Miyu repository has ready-made examples. All of them run `/usr/bin/miyu core` as the `miyu` user, with the data root `/var/lib/miyu` and the cache `/var/cache/miyu`:

| Init system | Example | Install location |
|---|---|---|
| systemd | `packaging/systemd/system/miyu.service` | `/etc/systemd/system/` |
| systemd, web UI | `packaging/systemd/system/miyu-web.service` | `/etc/systemd/system/` |
| OpenRC | `packaging/init/openrc/miyu` | `/etc/init.d/miyu`, made executable |
| runit | `packaging/init/runit/miyu/run` | Put the whole directory into `/etc/sv/miyu`, make `run` executable, then link it into the service directory |
| dinit | `packaging/init/dinit/miyu` | `/etc/dinit.d/miyu`, with environment variables written into `/etc/dinit.d/miyu.env` |

If `miyu` is not in `/usr/bin` (for example, if you installed it with the install script), change the paths in the example to its actual location.

### Starting the core with systemd

1. Create the system user:

   ```sh
   sudo useradd --system --home-dir /var/lib/miyu --shell /usr/sbin/nologin miyu
   ```

2. Download the example and install it:

   ```sh
   curl -fsSLO https://raw.githubusercontent.com/miyu-agent/miyu/main/packaging/systemd/system/miyu.service
   sudo cp miyu.service /etc/systemd/system/
   sudo systemctl enable --now miyu
   ```

   Following `StateDirectory` and `CacheDirectory` in the example, systemd creates `/var/lib/miyu` and `/var/cache/miyu`, owned by `miyu`, with permissions `0700` on the data root. The OpenRC example creates both directories itself before every start; for runit and dinit, you need to create the two directories first, run `chown miyu:miyu`, and run `chmod 0700` on the data root.

3. Confirm that the core has started: run `sudo systemctl status miyu`.

### Running commands on the server

The core only accepts command lines from the same system user, using the same data root, as itself. So every `miyu` command you run on the server needs to be wrapped like this:

```sh
sudo -u miyu env MIYU_HOME=/var/lib/miyu XDG_CACHE_HOME=/var/cache miyu config get models.chat
```

Connecting a model (see [Models](models.md)) is written the same way, with the key read from a pipe:

```sh
echo "$DEEPSEEK_API_KEY" | sudo -u miyu env MIYU_HOME=/var/lib/miyu XDG_CACHE_HOME=/var/cache miyu provider login deepseek
```

### Keys in environment variables

For a key written in the config as `{ env = "variable" }`, the core reads it from the environment it was started in, and cannot see the variables in your login shell. So if the core is started by a service, you need to put the variable into the service:

- systemd: run `sudo systemctl edit miyu` and add:

  ```ini
  [Service]
  Environment=DEEPSEEK_API_KEY=sk-example
  ```

  or point `EnvironmentFile=` at a file that only root can read. After the change, run `sudo systemctl restart miyu`.
- dinit: write it into `/etc/dinit.d/miyu.env`.
- OpenRC, runit: add it next to the `export` line in the example.

If you do not want to put the key in a service file, you can store it in the secrets file with `miyu provider login` and write `{ secret = "name" }` in the config.

For a service you installed with `miyu service enable` on your own computer, see [The service and environment variables](#the-service-and-environment-variables).

### Running the web UI with systemd

The web UI program `miyu-web` is shipped to keep running and never exit by itself (`web.idle_seconds` is `0`), so it can run as a service as it is. When it runs as a service, do not set `web.idle_seconds` to anything other than 0: because an idle exit has exit code 0, the service manager does not start it again.

1. Download the example:

   ```sh
   curl -fsSLO https://raw.githubusercontent.com/miyu-agent/miyu/main/packaging/systemd/system/miyu-web.service
   ```

2. Replace the path in `ExecStart=` with the real location of `miyu-web`, keeping `serve` after it as before. When installed from the AUR the path is `/usr/share/miyu/packages/webui/bin/miyu-web`; when installed with the install script it is next to `miyu`:

   ```ini
   ExecStart=/usr/share/miyu/packages/webui/bin/miyu-web serve
   ```

3. Install the service:

   ```sh
   sudo cp miyu-web.service /etc/systemd/system/
   sudo systemctl enable --now miyu-web
   ```

Starting the web UI service also starts the core service; when the core service stops, the web UI service stops with it. By default the web UI listens only on `127.0.0.1` on the server itself; how to open it from other computers is in the next section.

## Opening the web UI from other computers and phones

To open the web UI from other devices, you need to change a few web UI settings, all of which can only be written in `~/.miyu/etc/config.toml`:

| Key | Default | Description |
|---|---|---|
| `web.listen` | `127.0.0.1` | The address to listen on. `127.0.0.1` means only this computer can open it; `0.0.0.0` means all of this computer's addresses; you can also write one particular address |
| `web.port` | `8300` | The port, used both by this computer and by other devices, from `1` to `65535` |
| `web.idle_seconds` | `0` | How many seconds in a row with no browser connected and no media files being served before it exits, from `0` to `86400`; `0` means it never exits. It does not exit while LAN access is on. This setting is not shown on the settings page |

Access from other devices always requires the access password; opening it with `miyu web` on this computer does not.

### LAN access

1. On this computer, run `miyu web --settings access` to open `Settings → General → Access`.
2. Turn on `Allow local network access`. If no access password is set yet, `Set an access password` pops up first; once the password is set, the switch turns on.
3. The settings page lists the addresses for other devices to use, plus a QR code. Scan it with your phone and enter the access password to get in.

Whether you change the address and port on the settings page, with `miyu config set`, or by editing the config file by hand, the web UI switches over immediately. The `takes effect after restart` that `miyu config set` prints in this case is not accurate.

> LAN access uses plain HTTP, so anyone on the same network can see the access password, the login token and the conversation. Only turn it on in a network you trust, such as your own home. When you are away, first connect back to that network through an encrypted tunnel such as Tailscale or WireGuard, then open the LAN address. On macOS, if other devices cannot connect, go to `System Settings → Network → Firewall → Options` and allow incoming connections for `miyu-web`.

If you forget the access password, run `miyu web --reset` on this computer and set a new one in the page that opens. If you want every browser to sign in again, run `miyu web --logout`.

### A server with no desktop

A server has no browser, so you first connect in from your own computer through SSH port forwarding to set the access password:

1. On your computer, run this (the ports on both sides must be the same, both the server's `web.port`):

   ```sh
   ssh -L 8300:127.0.0.1:8300 you@server.example
   ```

2. On your computer, open `http://127.0.0.1:8300` in a browser. The web UI treats this connection as the server itself and lets you in without a password.
3. Go to `Settings → General → Access` and set the access password; if you need LAN access, also turn on `Allow local network access`.

> Anyone who connects through `ssh -L`, `socat` or other forwarding that adds no forwarding headers is treated by the web UI as the server itself: no password is needed, they can read files on the server, and they can change the access password without entering the old one. So keep this path for yourself only.

### Reverse proxy

If you open the web UI through a reverse proxy such as nginx or cloudflared on the same machine, the web UI treats the visitor as another device: the access password is required, and features that only work on the local machine (choosing directories on the server, reading files on the server) are not available.

- The proxy must add forwarding headers: `Forwarded`, `X-Forwarded-For`, `X-Real-IP` and the like; any one of them is enough. Without them, the web UI treats whoever the proxy forwards as the server itself.
- The web UI only accepts requests whose `Host` is `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`; when it listens on the LAN, it also accepts this computer's IP plus the port. It does not accept domain names.
- The conversation runs over a WebSocket at `/ws`, which only accepts connections whose `Origin` is `http://` plus one of those addresses. If the proxy serves the page on its own domain or over HTTPS, this connection is rejected (403).

For how to use the web UI, see [Web UI](heads/web.md).

## Logs

When something goes wrong, you can check the logs. Here is where each part keeps its log:

| Log | Location |
|---|---|
| Core | `~/.miyu/var/log/core.log`; at 10 MB it switches to a new file, keeping `core.log.1` to `core.log.5` |
| Web UI | `~/.miyu/var/log/webui/web.log` |
| System tray | `~/.miyu/var/log/miyu-applet.log` |
| Packages | `~/.miyu/var/log/<id>/` |

On a Linux server, replace `~/.miyu` with `/var/lib/miyu`.

`core.log` is written by the core itself on all three platforms; whether the core was started by a service or by an interface, it logs here. If the core is managed by systemd, you can also use `journalctl --user -u miyu` (for a system service on a server, `journalctl -u miyu`) to see the output systemd recorded for the service. The launchd plist and the Task Scheduler task have no output location set, so there is only `core.log`.

The core's log has one entry per line, in English, and does not record conversation content or keys. You set how detailed the log is with `log.level`, either in `Advanced → Runtime log → Runtime log level` on the settings page, or by running:

```sh
miyu config set log.level debug
```

| Value | What it records |
|---|---|
| `error` | Errors only |
| `warn` | Errors and warnings |
| `info` | Normal information (default) |
| `debug` | Detailed information, for troubleshooting |
| `trace` | Most detailed |
| `off` | Nothing |

A change takes effect immediately, and this setting can only be written in `~/.miyu/etc/config.toml`. If the environment variable `MIYU_LOG` is set, that one start logs according to its value. First run `miyu core stop`, then open an interface in the window where the variable is set:

```bash
MIYU_LOG=debug miyu
```

```powershell
$env:MIYU_LOG = 'debug'
miyu
```

Once you set it this way in PowerShell, every program started later from this window carries the variable; when you no longer need it, run `Remove-Item Env:MIYU_LOG`.

## Stopping the core and services

Use a different command depending on what you want to stop:

| What to stop | How |
|---|---|
| This run of the core, including one started by a service | `miyu core stop` |
| This run of the web UI | `miyu web stop` |
| A start-at-boot setup you installed | `miyu service disable` |
| A system service on a server | `sudo systemctl disable --now miyu-web miyu`; for other init systems, follow their own way |

A core stopped with `miyu core stop` counts as a normal exit (exit code `0`). Because the systemd user service and launchd only restart the core after an abnormal exit, they do not start it again here; with systemd, `miyu service status` then changes to `installed, not enabled`, while launchd checks whether it is registered, so it still shows `installed, enabled`. At the next login, the service starts the core as usual.

`miyu service disable` removes the service from the service manager and deletes the service file; for the systemd user service (`disable --now`) and launchd (`launchctl bootout`), it also stops the core the service started. For Task Scheduler and desktop autostart, Miyu only removes the registration and deletes the file, and does not stop the core separately; if you want to stop it, run `miyu core stop`.

## Read-only sessions on Windows

The Windows sandbox needs a desktop session. If the core is not in a desktop session (for example, it was started over an SSH connection), no command can run in a read-only session; the output is `miyu-sandbox: cannot confine: no desktop session, programs in the sandbox cannot start here; use Miyu from the desktop, or turn the sandbox off`, with exit code `125`. To fix this, use Miyu from the logged-in desktop, or switch to full access. For details, see [Permissions and sandbox](permissions.md).
