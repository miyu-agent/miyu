# Models

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Miyu can chat only after you connect a model provider. This page explains how to connect a provider, how to switch models, where keys are stored, and what Miyu does when a model fails.

## Quick setup: miyu setup

`miyu setup` is the fastest way to set up a model. It walks you step by step through choosing a provider, entering the key and choosing a model:

1. Run `miyu setup`.
2. Under `Pick a provider:`, type a number. The list has the common providers, any model services running on this machine (marked `local <address>`), and a last row `Custom`. Providers you have already set up are marked `configured`, and providers whose key is in an environment variable are marked `key found`.
3. Paste the key; it is not shown on the screen as you paste. If the key was already found in an environment variable, you are not asked. Press `Ctrl+C` to cancel; on Linux and macOS, pressing `Ctrl+D` before you have typed anything also cancels.
4. Wait while Miyu tests the connection. If the connection works, it shows `connected`; if it cannot list the models, it asks you to enter the model name. If the test fails, it asks `Save anyway? [y/N]`, and if you choose not to save, you go back to the previous step.
5. Under `Pick the model for chat:`, type a number, or press Enter to use the model marked `(recommended)`.
6. When you see `set models.chat = …`, the setup is complete.

The common providers are listed below, in the order they appear in the list:

| Name | Id |
|---|---|
| OpenCode Zen | `opencode` |
| OpenCode Go | `opencode-go` |
| ClinePass | `cline-pass` |
| DeepSeek | `deepseek` |
| Anthropic | `anthropic` |
| OpenAI | `openai` |
| OpenRouter | `openrouter` |
| Moonshot (Global) | `moonshotai` |
| Moonshot (China) | `moonshotai-cn` |
| Zhipu GLM (China) | `zhipuai` |
| Z.AI (Global) | `zai` |
| Qwen (Global) | `alibaba` |
| Qwen (China) | `alibaba-cn` |
| MiniMax (Global) | `minimax` |
| MiniMax (China) | `minimax-cn` |

If the provider you want is not in the table, pass its id from the model catalog after `--provider`. Three options each skip one step: `--provider <id>` skips choosing a provider; `--env <variable>` reads the key from that variable in the core's environment, so you do not need to paste it; `--model <model>` skips choosing a model. When you are not running it in a terminal, `--provider` is required, and the key is read from a pipe:

```bash
echo "$KEY" | miyu setup --provider deepseek
```

```powershell
$key | miyu setup --provider deepseek
```

If you choose `Custom`, Miyu asks in turn for `Base URL:`, `API protocol:` (`OpenAI compatible`, `Anthropic`, `OpenAI Responses`) and the key (the key can be left empty). After the test succeeds, it asks for this provider's id; press Enter to use the id made up from the address.

`miyu setup` writes the configuration to `etc/config.toml` under the data root (by default `~/.miyu`, and `%USERPROFILE%\.miyu` on Windows), that is `~/.miyu/etc/config.toml`, and it takes effect as soon as it is written. What gets written depends on what you chose:

| What you chose | What it writes |
|---|---|
| Pasted a key | `providers.<id>.key = { secret = "<id>" }`; the key is stored in the secrets file, under a name that is the id |
| A key was in an environment variable | `providers.<id>.key = { env = "<variable>" }` |
| A service on this machine | `providers.<id>.local = true` |
| Custom | `providers.<id>.driver`, `providers.<id>.base_url`, and, if you pasted a key, also `key = { secret = "<id>" }` |
| A provider already set up | That provider's configuration is not changed |

In every case it also writes a line `models.chat = "<id>/<model>"`. If you run `miyu ask` before any model is set up, in a terminal you go through `miyu setup` first.

## Changing the default model

`models.chat` is the model new sessions use by default, written as `provider/model` or `@pool`. For example:

```sh
miyu config set models.chat deepseek/deepseek-v4-pro
```

The change applies to new sessions; sessions that are already open do not change.

## Storing keys

The config file cannot hold the key itself, only a reference to it. A reference can be written in two ways:

- `{ secret = "name" }`: read from the secrets file `~/.miyu/etc/private/secrets.toml`. On Linux and macOS, only you can read and write this file (`0600`); on Windows, Miyu sets no separate permissions, and the file inherits the access control of the data root. None of the three platforms uses the system keychain, and the key is written in this file as plain text.
- `{ env = "VARIABLE" }`: read from the environment variable as it was when the core started, and never written to any file.

If you use an environment variable, set it in a terminal window first, then run `miyu setup` in that same window. A core that is already running cannot see a variable set after it started, so you need to stop it first:

```bash
export DEEPSEEK_API_KEY='sk-fake'
miyu core stop
miyu setup --provider deepseek --env DEEPSEEK_API_KEY
```

```powershell
$env:DEEPSEEK_API_KEY = 'sk-fake'
miyu core stop
miyu setup --provider deepseek --env DEEPSEEK_API_KEY
```

A variable set this way is visible only to a core started from this window. A core started by a service installed with `miyu service enable` cannot see the variables in your shell; if a core that keeps running needs the key, use the secrets file, see [Services and environment variables](service.md#the-service-and-environment-variables).

Use `miyu provider` to store, view and remove secrets:

| Command | What it does |
|---|---|
| `miyu provider login [<name>]` | Stores one key. If you leave out the name, you can choose from the names used in the config and the names already stored, or type a new name. What you paste is not shown, and the key can also be read from a pipe |
| `miyu provider list [--format text\|json]` | Lists the stored secrets, and the ones used in the config but not yet stored (shown in grey), along with who uses them. The keys themselves are not shown |
| `miyu provider logout [<name>]` | Removes one secret. If you leave out the name, you can choose from the stored ones |

A name starts with a lowercase letter, contains only lowercase letters, digits, `-` and `_`, and is at most 64 characters. After `login` stores the key, if the system config already has this provider (there are settings under `providers.<name>`) but no `key` yet, it also adds the line that refers to the key, `key = { secret = "<name>" }`, and tells you so; if the config doesn't have this provider yet, it only stores the key and you write the reference yourself. For example:

```bash
echo "$KEY" | miyu provider login acme
```

```powershell
$key | miyu provider login acme
```

```toml
[providers.acme]
key = { secret = "acme" }
```

A provider has only one key. If you want to use several quotas together, set them up as several providers and put them in the same pool.

## Writing a provider by hand

To set up a provider by hand, open `~/.miyu/etc/config.toml` (or run `miyu config edit`) and write one table per provider, `[providers.<id>]`. The id starts with a lowercase letter, contains only lowercase letters, digits, `-` and `_`, and is at most 32 characters. When you refer to a model, write `<id>/<model>`, using the provider's own name for the model.

| Field | Description |
|---|---|
| `base_url` | The API address; the driver appends the path to it. A recognized provider can leave it out. It can also be written as `{ env = "VARIABLE" }` |
| `driver` | The driver to use, see the next table. A recognized provider uses its own driver; for an unrecognized provider, leaving it out means `openai-chat` |
| `key` | `{ secret = … }` or `{ env = … }`. If it is not set, requests are sent without an auth header |
| `name` | The name shown in the interface. If it is not set, the name of that provider in the model catalog is used, and if the catalog has none, the id is used |
| `catalog` | Which provider in the model catalog this one corresponds to; for example, a relay that only forwards DeepSeek writes `deepseek` |
| `local` | Marks this as a service on this machine, so its price counts as 0. If it is not set, this is decided from the address: `127.0.0.1`, `localhost` and `::1` count as this machine |
| `price_multiplier` | The price multiplier; it is 1 if not set |

For the other fields, see the [config key reference](config-keys.md).

| Driver | Sends to | Auth header |
|---|---|---|
| `openai-chat` | `<address>/chat/completions` | `Authorization: Bearer <key>` |
| `anthropic` | `<address>/messages` | `x-api-key: <key>` |
| `openai-responses` | `<address>/responses` | `Authorization: Bearer <key>` |

DeepSeek's official provider uses `openai-chat` by default. To use DeepSeek's own web search, change its `driver` to `openai-responses`; see [Web search and fetching pages](web-search.md#using-the-search-built-into-deepseeks-responses-api).

Packages can also bring drivers; in that case, write `driver` as `<package id>/<driver name>`. For example, the community package `antigravity` (Linux and macOS only) brings the driver `antigravity/antigravity`, which hands requests to the Antigravity CLI on this machine and uses your login in the Antigravity CLI; for how to install and configure it, see the package's own documentation (the `Upstream` line in the output of `miyu pkg info antigravity`). To write a driver yourself, see [Writing a model driver](../dev/extensions.md#writing-a-model-driver).

You do not need to list the models one by one. Miyu asks the provider for its model list (`<address>/models`), adds the models of the matching provider in the model catalog and the models named in the config, and gives you the combined list to choose from. Model names in a reference are not checked, so a model that is not in the list can still be used.

An OpenAI-compatible third-party service can be written like this:

```toml
[providers.acme]
name = "Acme"
base_url = "https://api.acme.example/v1"
driver = "openai-chat"                  # optional: an unrecognized provider defaults to it
key = { secret = "acme" }               # store it with miyu provider login acme

[models]
chat = "acme/acme-large"
```

Ollama on this machine can be written like this:

```toml
[providers.ollama]
base_url = "http://127.0.0.1:11434/v1"  # for the id ollama, this line and the next can be left out
driver = "openai-chat"
local = true

[providers.ollama.models."qwen3:8b"]
window = 32768                          # for a model whose window is unknown, Miyu does not compact the context early

[models]
chat = "ollama/qwen3:8b"
```

If a model name contains `.`, `:` or `/`, put that part of the table header in double quotes.

Data that the provider's model list and the model catalog lack can be filled in under `[providers.<id>.models."<model>"]`, and the values you write here override values from other sources:

| Field | Description |
|---|---|
| `window` | The size of the context window, in tokens |
| `max_output` | The most tokens the model can output in one go |
| `inputs` | The kinds of input it accepts: `text`, `image`, `pdf`, `audio`, `video` |
| `effort` | The default thinking level; write one of this model's levels, for example `high`; a model that can turn thinking off can take `off` |
| `temperature` | The default temperature, from 0 to 2 |
| `price_multiplier` | This model's price multiplier; it overrides the multiplier written on the provider |
| `price.input`, `price.output`, `price.cache_read`, `price.cache_write`, `price.currency` | The price per million tokens; if the currency is not set, it is `USD`. As soon as you write any one price field, the whole set of prices you wrote is used |

These keys are only valid in the system config and cannot be written in a project config. A change to these provider fields takes effect from the next turn.

## The three uses

Miyu uses models for three purposes, and each purpose is set by one key:

| Key | What it controls | Allowed values |
|---|---|---|
| `models.chat` | The model new sessions use by default | `provider/model`, `@pool` |
| `models.vision` | Provides multimodal abilities when the chat model doesn't support them | `provider/model`, `@pool` |
| `models.embedding` | Computes vectors, used when searching memories and the knowledge base | `local` (the default, `miyu-embed` on this machine), `off` (search by keywords only), `provider/model` |

```toml
[models]
chat = "deepseek/deepseek-v4-flash"
vision = "acme/acme-vision"
embedding = "local"
```

## Pools: cheap ones for chores, expensive ones for real work

A pool groups several models together, and you refer to it as `@poolname`. Three pools always exist and cannot be deleted; they start out empty:

| Pool | Called in the interface | Who uses it |
|---|---|---|
| `lite` | Lite pool | Naming sessions |
| `normal` | Everyday pool | Sorting memories |
| `flagship` | Flagship pool | `advisor`: when the AI is stuck, it asks a stronger model for help |

If `lite` or `normal` is empty, or its members are all cooling down or all failing, the session's own model is used. If `flagship` is empty, `advisor` answers `No model in the flagship pool`.

To put models in a pool, write `pools.<pool>.models`. Members can only be written as `provider/model`, and they are kept in the order written. You can also create pools of your own, for example:

```toml
[pools.lite]
models = ["deepseek/deepseek-v4-flash"]

[pools.flagship]
models = ["deepseek/deepseek-v4-pro"]

[pools.daily]
models = ["deepseek/deepseek-v4-flash", "acme/acme-large"]
strategy = "ordered"
subagent = true
description = "Everyday work, cheap"

[models]
chat = "@daily"
```

`strategy` decides how requests are spread across the members:

| Value | Called in the terminal | How it spreads |
|---|---|---|
| `pin` | Pinned per session | A session keeps using the same member, and the next new session gets the next member |
| `rotate` | Rotate per request | Every request moves on to the next member |
| `ordered` | Fall back when unavailable | Every request starts from the first member, and the later members are used only when the first one fails |

When it is not written, it is `pin`; if the providers of all the members have `cache = "per_request"`, it is `rotate`.

For a pool with `subagent = true`, the AI can pick it when it dispatches a subagent; `description` is the one-line description the AI sees, and it must be written in English. The three fixed pools have this on by default, and pools you create have it off by default. A change applies to new sessions.

In the web interface, pools are on the `Model pools` tab of the `Models` settings page, with one card per pool, and the last row of each card is the `Available to subagents` switch. Click `+ New model pool` below the cards and enter a name; an `Available to subagents` switch appears under the name (off by default), and pressing Enter creates the pool. Changes are saved straight into `~/.miyu/etc/config.toml`.

In the terminal interface, go to the `Pools` page of the `Providers & models` settings page and open a pool or create a new one. The field below `Strategy` is `Available to subagents`; choose `On` or `Off`. A new pool starts at `Off`.

## Switching models temporarily

If you only want to use another model for a while, you can do it in the following ways:

- Command line: `miyu ask --model deepseek/deepseek-v4-pro "…"`; you can also write `--model @flagship`. If you use it together with `-c` or `-s`, that session switches to this model and keeps using it from then on.
- Terminal interface: type `/model`, choose a model in the `Models` box, and press Enter; the change takes effect from the next turn. A model that is cooling down or has no key set cannot be chosen. `/config` opens the settings page; under `Providers & models` there are three pages, `Providers`, `Default models` and `Pools`; `/connect` goes straight to `Providers & models`.
- Web interface: click the model name in the footer of the input box; the menu has two pages, `Models` and `Model pools`. You can also type `/model` followed directly by `provider/model` or `@pool`, and then the menu does not open. `/config` opens the `Models` page of settings.

## The model catalog

Context windows, prices, the inputs a model accepts, and the addresses and drivers of recognized providers all come from the catalog at [models.dev](https://models.dev). A copy of the catalog comes with the install, and the core fetches newer copies in the background:

| Key | Default | Description |
|---|---|---|
| `models.catalog.update` | `true` | When it is off, only the catalog that came with the install and catalogs already fetched are used. The environment variable `MIYU_CATALOG_UPDATE=false` takes priority over it |
| `models.catalog.url` | `https://models.dev/api.json` | The address the catalog is fetched from. It can also be written as `{ env = "VARIABLE" }` |
| `models.catalog.every` | `24h` | The catalog is fetched again only when the copy on hand is older than this; the range is 1 hour to 30 days |

## Rate limits and used-up quota

What Miyu does when a model fails depends on whether `models.chat` names a single model or a pool. When `models.chat` names a single model:

- Rate limited, cannot connect, 5xx, stalled: the same step is retried up to 5 more times. If the provider says how long to wait, Miyu waits that long, but if the wait is 2 minutes or more, Miyu does not wait and the turn ends with an error; if the provider does not say, Miyu waits 1, 2, 4, 8 and 16 seconds in turn.
- Authentication failed, quota used up: there is no retry, and the turn ends with an error.

When it names a pool, the member that failed goes into cooldown, and Miyu immediately switches to the next member that is not cooling down. The terminal interface shows a line `↻ Switched model: A → B`. If all members are cooling down, Miyu waits for the member that recovers earliest. After a `pin` pool switches, the session keeps using the member it switched to.

On the nth consecutive failure, the cooldown is `base × 2^(n−1)`, at most `max`; a single success resets it to zero. If the provider asks for a longer wait, Miyu follows the provider, but still does not exceed `max`. Cooldowns are kept only in memory, and restarting the core clears them.

| What went wrong | Keys | Default `base` / `max` |
|---|---|---|
| Rate limited | `models.cooldown.rate_limited.base`, `.max` | `30s` / `10m` |
| Cannot connect, 5xx, stalled | `models.cooldown.retryable.base`, `.max` | `10s` / `5m` |
| Authentication failed | `models.cooldown.auth.base`, `.max` | `10m` / `2h` |
| Quota used up | `models.cooldown.quota.base`, `.max` | `30m` / `30m` |

If the quota is used up and the provider said when it resets, the cooldown lasts until then, at most one day, and in this case `max` does not apply. A cooldown stops only that model of that provider; the provider's other models keep working as usual.

## Usage and cost

You can see usage and cost in two places:

- Terminal interface: `/usage` shows usage and cost on this computer, by day and by model; `/context` shows the current session's usage, split by purpose.
- Web interface: the `Usage` page in settings, which you can view by model, session, purpose and venue.

Amounts are shown in `usage.currency` (`USD` by default), and each charge is converted at the exchange rate of its day; if the rate cannot be fetched, no amount is shown. Prices come from the model catalog; a service on this machine counts as 0; if a relay marks prices up or gives a discount, write `price_multiplier`.

## Troubleshooting

These are common problems when setting up models, and how to fix them:

| What you see | What to do |
|---|---|
| `no model configured`, `no model configured: set models.chat` | Run `miyu setup`, or write `models.chat` |
| `miyu setup` says `the core has not read XXX_API_KEY (set after the core started)` | The core started before that variable was set. Run `miyu core stop` and then run `miyu setup` again, or just paste the key |
| `provider "acme" has no usable key` | The key was not stored, or the core's environment does not have that variable. Run `miyu provider list` to see which one is not set |
| `provider "acme" needs base_url: it matches nothing in the catalog` | The model catalog does not recognize this provider, so you need to write `base_url` |
| `Not found. Check the endpoint address and model name.` | `base_url` must go up to the part before the path the driver appends, and the model name must be the same as on the provider's side |

Run `miyu check` to check the config for mistakes.
