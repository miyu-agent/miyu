# Configuration

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Miyu's settings are written in TOML files. This page explains where the config files are, how to change them, when a change takes effect, how to set things for a single repository, how to store secrets, and how to find out why a setting did not take effect. For what each key is and what values it takes, see the [config key reference](config-keys.md).

## Where the config files are

Miyu reads the following three files:

| File | Location | Who writes it |
|---|---|---|
| System config | `etc/config.toml` under the data root (by default `~/.miyu`, on Windows `%USERPROFILE%\.miyu`), that is `~/.miyu/etc/config.toml` | You edit it by hand, or change it through `miyu config set` or the settings page in the terminal UI or web UI |
| Project config | `.miyu/config.toml` in a repository | Only by hand |
| Secrets file | `~/.miyu/etc/private/secrets.toml` | `miyu provider login`, or you edit it by hand |

`miyu config path` prints the full path of the system config, and `miyu config path --project` prints the full path of the project config for the current directory. If the file does not exist yet, the command still prints where it should be, and then says `the file does not exist yet`.

A system config looks like this:

```toml
#:schema ../var/cache/config/config.schema.json

[ui]
language = "zh"

[models]
chat = "deepseek/deepseek-v4-flash"

[providers.deepseek]
key = { secret = "deepseek" }

[permission.confirm]
timeout = 600

[jobs]
max_running = "45m"

```

A key is split into parts at each `.`: the leading parts are the table header, and the last part is written inside the table. For example, `permission.confirm.timeout` is `timeout` under `[permission.confirm]` above. Durations are written as quoted strings, a number followed by `s`, `m` or `h`; without a unit the number is in seconds. A config file can be at most 1 MiB.

## Changing a setting

The three ways below all change the same file, `~/.miyu/etc/config.toml`:

- Command line: run `miyu config set <key> <value>`.
- Settings page: type `/settings` in the terminal UI or the web UI. Running `miyu config` directly in a terminal opens the settings page of the default interface (`ui.head`).
- Edit the file by hand, or run `miyu config edit`.

The command line and the settings page change only that one item; comments, blank lines, the order of entries and keys Miyu does not recognize are all kept as they were. As soon as you save a file you edited by hand, the core reads it again, so you do not need to restart.

1. To change a setting, run:

   ```sh
   miyu config set permission.confirm.timeout 600
   ```

   It prints one line on standard error: `set permission.confirm.timeout = 600 (takes effect next turn)`. If the item already had that value, it prints `already 600, nothing changed`.

2. To see the value currently in use, run:

   ```sh
   miyu config get permission.confirm.timeout
   ```

3. To see where the value comes from, run `miyu config explain permission.confirm.timeout` (see "Finding out why a setting did not take effect" below).

If you no longer want the item, run `miyu config unset permission.confirm.timeout`, which prints `removed permission.confirm.timeout, now 300 (default)`.

### When a change takes effect

Each key has a registered time at which changes to it take effect, and both `miyu config set` and `miyu config explain` tell you which one:

| What it prints | Meaning | Examples |
|---|---|---|
| `Takes effect immediately` | The new value is used right after the change | `ui.language`, `log.level`, `core.idle_exit`, model cooldowns |
| `Takes effect next turn` | Open sessions use the new value from the next turn on; the turn running now still uses the old value | Provider addresses and keys, protected commands, compaction |
| `Applies to new sessions` | Sessions started from now on use the new value; sessions already open do not change | `models.chat`, `persona.default`, `permission.start_read_only` |
| `Takes effect after restart` | The interface (terminal UI, web UI) reads it only the next time it starts | `ui.startup`, and keys in packages that do not declare when they take effect |
| `Takes effect after the core restarts` | The core reads it only the next time it starts | `core.workers` |

For how to stop the core and start it again, see [Keeping it running, and servers](service.md).

### Writing values on the command line

Each type of value is written on the command line as follows:

| Type | How to write it | Example |
|---|---|---|
| Switch | `true`, `false` | `miyu config set compaction.prepare false` |
| Number | Write it as is | `miyu config set compaction.line 70` |
| Text, option, model, duration | Write it as is; you can also add double quotes | `miyu config set jobs.max_running 45m` |
| List | A TOML array, wrapped whole in single quotes; you write the whole list, and it replaces the old list | `miyu config set skills.external.dirs '["~/.agents/skills", "~/my-skills"]'` |
| Secret reference | A TOML inline table | `miyu config set providers.acme.key '{ secret = "acme" }'` |
| List whose items each have several fields | An array of inline tables | `miyu config set tui.footer '[{ part = "usage" }, { part = "model", shown = false }]'` |

Lists and inline tables are read as TOML, and TOML strings can use either double or single quotes. In PowerShell, use double quotes outside and TOML single-quoted strings inside. This is because Windows PowerShell 5.1 strips the inner double quotes when it passes arguments to a program, while the lines below work as they are in both 5.1 and PowerShell 7:

```powershell
miyu config set skills.external.dirs "['~/.agents/skills', '~/my-skills']"
miyu config set providers.acme.key "{ secret = 'acme' }"
miyu config set tui.footer "[{ part = 'usage' }, { part = 'model', shown = false }]"
```

If one part of a key contains characters such as `.` or `:`, put double quotes around that part, and then wrap the whole key in single quotes:

```bash
miyu config set 'providers.ollama.models."qwen3:8b".window' 32768
```

In Windows PowerShell 5.1, the double quotes in such a key are stripped as well. In that case, use single quotes inside the key and double quotes outside: `miyu config set "providers.ollama.models.'qwen3:8b'.window" 32768`; or change it by hand with `miyu config edit`.

`miyu config set` changes only one key at a time. A whole table (for example an MCP server, `[mcp.<name>]`) has to be edited in the file by hand.

## All miyu config commands

`miyu config` has the following subcommands:

| Command | What it does | Example |
|---|---|---|
| `miyu config` | When run in a terminal, opens the settings page of the default interface; when not run in a terminal, prints help | `miyu config` |
| `get [<key>…]` | Prints the final value. With one key, it prints only the value; with several keys or none, it prints one `key = value` per line | `miyu config get models.chat` |
| `set <key> <value>` | Changes one item in the system config | `miyu config set ui.language zh` |
| `unset <key>` | Removes one item from the system config, so it goes back to the default | `miyu config unset ui.language` |
| `edit` | Opens the system config in an editor, and checks it before saving | `miyu config edit` |
| `explain <key>` | Shows what each layer says for this item, and which layer is in effect | `miyu config explain log.level` |
| `path` | Prints the full path of the system config | `miyu config path` |
| `trust` | Shows what the project config in the current directory would change, and then lets you decide whether to trust it | `miyu config trust` |

| Option | Used with | What it does |
|---|---|---|
| `--project` | `edit`, `path` | Works on the project config of the current directory instead |
| `--format <text\|json>` | `get`, `explain` | The output format; `text` by default |
| `--yes` | `trust` | Trusts it right away, without asking |
| `--no` | `trust` | Does not trust it, without asking |

`set` and `unset` change only the system config. If you add `--project` to `set`, it changes no file and reports the error `the project config can only be edited by hand`, with exit code `2`.

`miyu config edit` uses the editor in `VISUAL`; if that is not set, it uses `EDITOR`; if neither is set (or both are empty), it uses `vi` on Linux and macOS and `notepad` on Windows. The editor's command string runs through `sh -c` on Linux and macOS and through `cmd /c` on Windows, so a form with arguments works on both, for example `code --wait`:

```bash
export VISUAL='code --wait'
```

```powershell
$env:VISUAL = 'code --wait'
```

`miyu config edit` puts a copy next to the original file for you to edit. After you close the editor:

- If nothing changed: it prints `nothing changed`.
- If there are errors: it prints one line per error, and then asks `N errors, not saved. Press Enter to keep editing, or type q to give up:`. If there are only warnings, it saves anyway.
- If the file was changed elsewhere while you were editing: it does not save, prints `the file changed during editing; not saved`, keeps the copy and tells you where the copy is.

`edit` has to run in a terminal.

## Setting things for a single repository

The project config is `.miyu/config.toml` in a repository. It applies only to sessions started in that repository, and it can only tighten limits. Right now there is only one item you can write in it:

```toml
[permission]
start_read_only = true          # new sessions opened in this repository start read-only
```

Writing `false` does not count. Other keys written in a project config do not count either, and `miyu config explain <key>` marks that line with `← does not count: not allowed in this layer`.

1. In the repository, run `miyu config edit --project`, or create the file yourself. If the file does not exist yet, it is created under the directory level that has `.git`; if there is no `.git` anywhere above, it is created under the current directory.
2. In the repository, run `miyu config trust`. It lists `<file> would set (a project config can only tighten limits):` followed by each item, and then asks `Trust '<file>'? [y/N]`.
3. Type `y`, and it prints `trusted (will ask again if the file changes)`.

A project config that you have not trusted has no effect. In such a repository, `miyu ask` starts by printing `project config <file> is not trusted; not used this time`. The terminal UI and the web UI do not ask; you need to run `miyu config trust` on the command line. Whenever the file's content changes, you have to trust it again. If you are not running in a terminal, you need to pass `--yes` or `--no`. If you answered that you do not trust it, you are not reminded again until the file changes.

Miyu starts from the session's working directory and looks upward for `.miyu/config.toml` one level at a time, using only the nearest one. It stops looking once it reaches the level that has `.git`; it does not look in the home folder itself or above it, and it does not look inside the data root.

## Layering order

A key's final value is stacked up from the bottom, and each upper layer overrides the layers below it:

1. Default.
2. System config.
3. Project config: it counts only if you have trusted it and it tightens limits.
4. Environment variables: only `log.level` (`MIYU_LOG`) and `models.catalog.update` (`MIYU_CATALOG_UPDATE`) read environment variables, and they apply only to the core started this time.

If a value you change with `miyu config set` is still overridden by a layer above, it prints an extra warning line, for example `log.level is overridden by the environment; using "debug"`.

## Secrets

The config does not hold the key itself, only a reference to it:

- `{ secret = "name" }`: read from the secrets file `~/.miyu/etc/private/secrets.toml`. On Linux and macOS, Miyu sets the file's permissions to `0600` every time it writes it, so only you can read and write it; on Windows no permissions are set separately, and the file keeps the access control inherited from the data root. None of the three platforms uses the system keychain; the key is written in this file as plain text.
- `{ env = "VARIABLE" }`: read from the environment variable as it was when the core started, and never written to any file. A core started by a service does not see the variables in your shell; see [Keeping it running, and servers](service.md).

Use `miyu provider` to store, view and remove secrets. It does not manage only model provider keys; it can store a secret under any name:

| Command | What it does |
|---|---|
| `miyu provider login [<name>]` | Stores a secret. What you paste is not shown, and it can also read from a pipe. Without a name, you choose from the names used in the config and the ones already stored |
| `miyu provider list [--format text\|json]` | Lists the stored secrets, and the ones used in the config but not stored yet, along with who uses them. Values are not shown |
| `miyu provider logout [<name>]` | Removes a secret |

A name starts with a lowercase letter, contains only lowercase letters, digits, `-` and `_`, and is at most 64 characters long. For example, to store a Tavily key for web search:

```bash
echo "$TAVILY_KEY" | miyu provider login tavily
miyu config set net.search.tavily.key '{ secret = "tavily" }'
```

```powershell
$tavilyKey | miyu provider login tavily
miyu config set net.search.tavily.key "{ secret = 'tavily' }"
```

You can also edit the secrets file by hand, with one `name = "value"` per line; changes take effect as soon as you save.

The keys that can hold a reference are:

| Key | `{ secret }` | `{ env }` |
|---|---|---|
| `providers.<id>.key`, `net.search.exa.key`, `net.search.deepseek.key`, `net.search.tavily.key`, `net.search.brave.key`, keys a package declares as secrets | Yes | Yes |
| `providers.<id>.base_url`, `models.catalog.url`, `net.search.searxng.url`, `packages.source`, `packages.sources.<id>.url` | No | Yes |
| Values in an MCP server's `env`, `bearer`, `headers` | Yes | Yes |

If a secret-type key is written in plain text, it is reported as the wrong type, and the item does not count. If the referenced secret is not stored yet, or the environment variable is not set, only a warning is reported, and the item has no key when it is used.

## Environment variables

You can set the following environment variables:

| Variable | What it does |
|---|---|
| `MIYU_HOME` | Where the data root is. It must be an absolute path, and a leading `~` is replaced with the home folder. When unset, it is `~/.miyu` |
| `MIYU_LOG` | The run log level of the core started this time; it overrides `log.level`, and can be `error`, `warn`, `info`, `debug`, `trace` or `off` |
| `MIYU_CATALOG_UPDATE` | When set to `false`, the core started this time does not fetch the model catalog in the background; it overrides `models.catalog.update` |
| `MIYU_RESOURCES` | Points the resource folder somewhere else; used when developing Miyu |
| `MIYU_DISTRO_PACKAGES` | Makes Miyu look for Miyu packages installed by the system package manager only under this absolute path; used for testing |

An environment variable set in a shell applies only to that window and to the core started from that window:

```bash
export MIYU_LOG=debug
```

```powershell
$env:MIYU_LOG = 'debug'
```

The core reads the environment as it was at the moment the core started, so if the core is already running, you need to run `miyu core stop` first. If you want windows you open later to pick the variable up, or want the service started at login and the system tray to carry `MIYU_HOME`, see [Data and backups](data.md#changing-the-data-root-location).

The variables below are what Miyu passes to extensions, package commands, scripts, MCP servers and commands the AI runs when it starts them. Package authors use them; you do not need to set them:

| Variable | What it is |
|---|---|
| `MIYU_PROGRAM` | The real location of the main program `miyu` |
| `MIYU_HOME` | The data root |
| `MIYU_RESOURCES` | The resource folder |
| `MIYU_APP_DIR` | The package's folder |
| `MIYU_CONFIG_DIR` | The package's own config folder `~/.miyu/etc/<id>/` |
| `MIYU_STATE_DIR` | The state folder of the package, script or MCP server |
| `MIYU_CACHE_DIR` | A cache folder that can be deleted |
| `MIYU_LOG_DIR` | The package's log folder `~/.miyu/var/log/<id>/` |
| `MIYU_TMP_DIR` | The package's scratch folder, emptied before each start |
| `MIYU_RUNTIME_DIR` | The package's runtime folder, used for locks and sockets |
| `MIYU_IMAGES_DIR` | The folder where a script puts images to hand to the AI |
| `MIYU_PICTURES_DIR`, `MIYU_VIDEOS_DIR`, `MIYU_DOCUMENTS_DIR`, `MIYU_DOWNLOADS_DIR` | The folders under `~/.miyu/root/` that are meant for you to look at |
| `MIYU_ARGS_JSON` | The arguments when a script is called, as JSON |
| `MIYU_CALLER_VENUE` | Which kind of session this call comes from |
| `MIYU_CALLER_OWNER` | Whether the one speaking is you: `1` or `0` |
| `MIYU_SETTINGS_JSON` | The final values of this package's settings, as JSON |
| `MIYU_MODEL`, `MIYU_EFFORT` | Only in commands the AI runs: this turn's model and thinking effort |
| `MIYU_SESSION_LOG` | Only in commands the AI runs: this session's log folder |
| `MIYU_CALL_SOCK`, `MIYU_CALL_TOKEN` | Only in commands the AI runs: the address and token `miyu call` uses to connect back to this session |

For how each variable is used, see [Writing a Miyu package](../../authors/README.en.md).

## Editor completion

When the core starts, it generates two files and puts them in `~/.miyu/var/cache/config/`:

- `config.schema.json`: a JSON Schema of the system config, with each key's name, description, allowed values and default.
- `reference.toml`: every key with its default, for you to browse. Changing it has no effect at all.

Both files are written in the language set by `ui.language`. They are generated again after you change the interface language, or install or uninstall packages.

A system config created by the core has this as its first line:

```toml
#:schema ../var/cache/config/config.schema.json
```

If your editor has a TOML plugin that understands this line (Taplo and the like), you get completion and hover descriptions, and mistakes are marked as you type. If a file you created yourself lacks this line, just copy it to the first line. The project config has no schema.

## Finding out why a setting did not take effect

If a setting did not take effect, go through the following steps:

1. To see which layer is in effect, run:

   ```sh
   miyu config explain permission.start_read_only
   ```

   ```text
   Start new sessions read-only (permission.start_read_only): When on, new sessions begin read-only. The AI can look around and plan, and you turn read-only off when files should change. A project config can only turn it on. Applies to new sessions.
     true   project config  ~/src/app/.miyu/config.toml:2  ← in effect
     false  system config   ~/.miyu/etc/config.toml:5
     false  default
   ```

   The first line of the output is the item's name, its description and when it takes effect. Below it, from top to bottom, each layer takes one line: the value, which layer, and the file and line it is written on. The line in effect is marked `← in effect`, and one overridden by an environment variable is marked `← in effect, for this launch only`. A value that is written but does not count is marked with the reason: `← does not count: not trusted yet`, `← does not count: looser than the layers below` or `← does not count: not allowed in this layer`.

2. To check for mistakes, run `miyu check`.

3. Check when the setting takes effect: for an `Applies to new sessions` setting you need to start a new session, and for a `Takes effect after restart` setting you need to reopen the terminal UI or the web UI.

### What happens when something is written wrong

When something in the config is written wrong, the result depends on the kind of mistake:

| What is wrong | Result |
|---|---|
| Unknown key | A warning, with the closest key name. The key stays in the file and has no effect |
| Wrong value type, not one of the options, out of range, malformed | An error. Only this item is dropped, and the value from the layer below is used instead; if the layer below has none, the default is used |
| Written in a layer where it is not allowed | An error. This item does not count |
| TOML syntax error | An error. The whole file does not count: when the core starts, it treats the file as empty; while the core is running, it keeps using the last version it read successfully |
| Referenced secret not stored, environment variable not set | A warning |

`miyu config set` and the settings page reject a wrong value outright, and do not change a single character of the file. `miyu config edit` does not save when there are errors. If the file has errors, `miyu ask` starts by printing `the configuration has N errors`, and suggests running `miyu check`.

### miyu check

`miyu check` checks whether the config files you wrote by hand contain mistakes. You can use:

```sh
miyu check                 # check everything
miyu check ~/.miyu/etc/config.toml   # check only this file
```

It checks the files you write by hand that Miyu reads, using their current content on disk: the system config (including the MCP servers in it), the project config of the current directory, the secrets file, each persona's `persona.toml` and `prompts/examples.md`, each preset, each package's manifest, and also skipped scripts and skills, and lines in schedules that cannot be understood. If you give it a file, it checks only that file. It prints one line per problem:

```text
~/.miyu/etc/config.toml:12:3 error: …
```

The last line is the total, for example `1 error, 2 warnings`, or `no problems` if there are none; after that it prints the indexing progress of the semantic model and of memory and knowledge bases, which does not count as a problem. If there are errors, the exit code is `1`. Adding `--format json` prints the output as JSON.

## Package settings

A package can declare its own settings in its manifest, and these settings are written in the same `~/.miyu/etc/config.toml`. Their keys take the form `<prefix>.<name>`: the prefix is the `prefix` written in the package manifest, or the package id if none is written. The terminal UI's prefix is `tui`, and the web UI's prefix is `web`:

```toml
[tui]
keys = "vim"

[web]
port = 8400
```

You can also change these keys on the settings page, or with `miyu config set tui.keys vim`. If the package does not declare when its keys take effect, they take effect the next time the interface starts. When you uninstall a package, its keys stay in the file by default but have no effect, and they work again if you reinstall the package; only `miyu pkg remove --purge` removes them as well. For the keys of the shipped terminal UI and web UI, see the [config key reference](config-keys.md).
