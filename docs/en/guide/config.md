# Configuration

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Miyu's settings are written in TOML files. This page covers where the files are, how to change them, when a change takes effect, settings for a single repository, storing secrets, and why a setting did not take effect. For what each key is and what values it takes, see the [config key reference](config-keys.md). Chinese version: [中文](../../zh/guide/config.md).

## Where the files are

| File | Location | Who writes it |
|---|---|---|
| System config | `etc/config.toml` under the data root (by default `~/.miyu`, on Windows `%USERPROFILE%\.miyu`), that is `~/.miyu/etc/config.toml` | You by hand, `miyu config set`, the settings page in the terminal or web UI |
| Project config | `.miyu/config.toml` in a repository | By hand only |
| Secrets file | `~/.miyu/etc/private/secrets.toml` | `miyu provider login`, or by hand |

`miyu config path` prints the full path of the system config, and `miyu config path --project` prints the path of the project config for the current directory. If the file does not exist yet, it still prints where it should be, followed by "the file does not exist yet".

A system config looks like this:

```toml
#:schema ../var/cache/config/config.schema.json

[ui]
language = "zh"

[models]
chat = "deepseek/deepseek-v4-flash"

[providers.deepseek]
key = { secret = "deepseek" }

[permission.confirm]
timeout = 600

[jobs]
max_running = "45m"

```

Keys are split at `.`: the leading parts are the table header, and the last part is written inside the table. `permission.confirm.timeout` is `timeout` under `[permission.confirm]` above. Durations are written as quoted strings: a number followed by `s`, `m` or `h`; without a unit it is seconds. The file can be at most 1 MiB.

## Changing a setting

All three ways change the same file, `~/.miyu/etc/config.toml`:

- Command line: `miyu config set <key> <value>`.
- Settings page: type `/settings` in the terminal or web UI. Typing `miyu config` in a terminal opens the settings page of the default interface (`ui.head`).
- Edit the file by hand, or use `miyu config edit`.

The command line and the settings page touch only that one item; comments, blank lines, order and unknown keys stay as they were. When you save the file after editing it by hand, the core reads it again, with no restart needed.

1. Change it:

   ```sh
   miyu config set permission.confirm.timeout 600
   ```

   It prints one line on standard error: "set permission.confirm.timeout = 600 (takes effect next turn)". If the value was already that, it prints "already 600, nothing changed".

2. See the value now in use:

   ```sh
   miyu config get permission.confirm.timeout
   ```

3. See where it comes from: `miyu config explain permission.confirm.timeout` (see "Why a setting did not take effect" below).

To drop it: `miyu config unset permission.confirm.timeout`, which prints "removed permission.confirm.timeout, now 300 (default)".

### When it takes effect

Each key has a registered time at which changes take effect, and both `miyu config set` and `miyu config explain` tell you:

| What it prints | Meaning | Examples |
|---|---|---|
| Takes effect immediately | The new value is used right away | `ui.language`, `log.level`, `core.idle_exit`, model cooldowns |
| Takes effect next turn | Open sessions use the new value from the next turn; the turn running now keeps the old one | Provider addresses and keys, protected commands, compaction |
| Applies to new sessions | Sessions opened from now on use the new value; open ones do not change | `models.chat`, `persona.default`, `permission.start_read_only` |
| Takes effect after restart | A head (terminal, web UI) reads it only the next time it starts | `ui.startup`, and keys in packages that do not declare when they take effect |
| Takes effect after the core restarts | The core reads it only the next time it starts | `core.workers` |

For how to stop the core and start it again, see [Keeping it running, and servers](service.md).

### Writing values on the command line

| Type | How to write it | Example |
|---|---|---|
| Switch | `true`, `false` | `miyu config set compaction.prepare false` |
| Number | As is | `miyu config set compaction.line 70` |
| Text, option, model, duration | As is, double quotes allowed | `miyu config set jobs.max_running 45m` |
| List | A TOML array, wrapped whole in single quotes; you write the whole list and it replaces the old one | `miyu config set skills.external.dirs '["~/.agents/skills", "~/my-skills"]'` |
| Secret reference | A TOML inline table | `miyu config set providers.acme.key '{ secret = "acme" }'` |
| List of items with several fields | An array of inline tables | `miyu config set tui.footer '[{ part = "usage" }, { part = "model", hidden = true }]'` |

Lists and inline tables are read as TOML, and TOML strings can use double or single quotes. In PowerShell, use double quotes outside and TOML single-quoted strings inside: Windows PowerShell 5.1 strips the inner double quotes when it passes arguments to a program, and written this way the lines work as is in both 5.1 and PowerShell 7:

```powershell
miyu config set skills.external.dirs "['~/.agents/skills', '~/my-skills']"
miyu config set providers.acme.key "{ secret = 'acme' }"
miyu config set tui.footer "[{ part = 'usage' }, { part = 'model', hidden = true }]"
```

If one part of a key contains characters such as `.` or `:`, put that part in double quotes and wrap the whole key in single quotes:

```bash
miyu config set 'providers.ollama.models."qwen3:8b".window' 32768
```

Windows PowerShell 5.1 strips the double quotes in such keys as well. Use single quotes inside the key and double quotes outside: `miyu config set "providers.ollama.models.'qwen3:8b'.window" 32768`; or change it by hand with `miyu config edit`.

`miyu config set` changes one key at a time. A whole table (for example an MCP server `[mcp.<name>]`) has to be edited in the file by hand.

## All miyu config commands

| Command | What it does | Example |
|---|---|---|
| `miyu config` | In a terminal, opens the settings page of the default interface; outside a terminal, prints help | `miyu config` |
| `get [<key>…]` | Prints the final value. With one key, prints only the value; with several or none, one `key = value` per line | `miyu config get models.chat` |
| `set <key> <value>` | Changes one item in the system config | `miyu config set ui.language zh` |
| `unset <key>` | Removes one item from the system config, back to the default | `miyu config unset ui.language` |
| `edit` | Opens the system config in an editor and checks it before saving | `miyu config edit` |
| `explain <key>` | What each layer says for this item and which layer is in effect | `miyu config explain log.level` |
| `path` | Prints the full path of the system config | `miyu config path` |
| `trust` | Shows what the project config in the current directory would change, and lets you decide whether to trust it | `miyu config trust` |

| Option | Used with | What it does |
|---|---|---|
| `--project` | `edit`, `path` | Uses the project config of the current directory instead |
| `--format <text\|json>` | `get`, `explain` | Output format, `text` by default |
| `--yes` | `trust` | Trusts it without asking |
| `--no` | `trust` | Does not trust it, without asking |

`set` and `unset` change only the system config. `set` with `--project` changes nothing and reports "the project config can only be edited by hand", with exit code `2`.

`miyu config edit` uses the editor in `VISUAL`, then `EDITOR`; if neither is set (or both are empty), it uses `vi` on Linux and macOS and `notepad` on Windows. The editor string runs through `sh -c` on Linux and macOS and through `cmd /c` on Windows, so a form with arguments works on both, for example `code --wait`:

```bash
export VISUAL='code --wait'
```

```powershell
$env:VISUAL = 'code --wait'
```

It puts a copy next to the original file for you to edit. After you close the editor:

- Nothing changed: prints "nothing changed".
- Errors: prints them one per line and asks "N errors, not saved. Press Enter to keep editing, or type q to give up:". If there are only warnings, it saves anyway.
- The file was changed elsewhere while you were editing: does not save, prints "the file changed during editing; not saved", keeps the copy and tells you where it is.

`edit` has to run in a terminal.

## Settings for a single repository

The project config is `.miyu/config.toml` in a repository. It applies only to sessions opened in that repository, and it can only tighten limits. Right now there is only one thing you can write in it:

```toml
[permission]
start_read_only = true          # new sessions opened in this repository start read-only
```

Writing `false` does not count. Other keys in a project config do not count either; in `miyu config explain <key>`, that line is marked "← does not count: not allowed in this layer".

1. In the repository, type `miyu config edit --project`, or create the file yourself. If the file does not exist yet, it is created under the level that has `.git`; if there is no `.git` anywhere above, it is created under the current directory.
2. In the repository, type `miyu config trust`. It lists "<file> would set (a project config can only tighten limits):" and each item, then asks "Trust '<file>'? [y/N]".
3. Type `y`. It prints "trusted (will ask again if the file changes)".

A project config that is not trusted has no effect. In such a repository, `miyu ask` starts by printing "project config <file> is not trusted; not used this time". The terminal and web UI do not ask; you have to type `miyu config trust` on the command line. When the file's content changes, you have to trust it again. When not running in a terminal, pass `--yes` or `--no`. If you answered that you do not trust it, you are not reminded again until the file changes.

Miyu looks for `.miyu/config.toml` from the session's working directory upward, level by level, and uses only the nearest one. It stops at the level that has `.git`, does not look in the home folder itself or above it, and does not look inside the data root.

## Layering order

A key's final value is built up from the bottom; upper layers override lower ones:

1. Default.
2. System config.
3. Project config: counts only if trusted and if it tightens.
4. Environment variables: only `log.level` (`MIYU_LOG`) and `models.catalog.update` (`MIYU_CATALOG_UPDATE`) read them, and only for the core started this time.

When `miyu config set` changes something that a layer above still overrides, it prints an extra warning line, for example `log.level is overridden by the environment; using "debug"`.

## Secrets

The config does not hold the key itself, only a reference:

- `{ secret = "name" }`: taken from the secrets file `~/.miyu/etc/private/secrets.toml`. On Linux and macOS, Miyu sets its permissions to `0600` every time it writes it, so only you can read and write it; on Windows no permissions are set separately, and it inherits the access control of the data root. None of the three platforms uses the system keychain; the key is written in this file as is.
- `{ env = "VARIABLE" }`: taken from the environment variable as it was when the core started, and never written to any file. A core started by a service does not see the variables in your shell, see [Keeping it running, and servers](service.md).

Use `miyu provider` to store, view and remove secrets. It is not only for model provider keys; it can store a secret under any name:

| Command | What it does |
|---|---|
| `miyu provider login [<name>]` | Stores one. What you paste is not shown, and it can also read from a pipe. Without a name, you choose from the ones used in the config and the ones already stored |
| `miyu provider list [--format text\|json]` | Lists the stored ones, and the ones used in the config but not yet stored, with who uses them. Values are not shown |
| `miyu provider logout [<name>]` | Removes one |

A name starts with a lowercase letter, contains only lowercase letters, digits, `-` and `_`, and is at most 64 characters. For example, to store a Tavily key for web search:

```bash
echo "$TAVILY_KEY" | miyu provider login tavily
miyu config set net.search.tavily.key '{ secret = "tavily" }'
```

```powershell
$tavilyKey | miyu provider login tavily
miyu config set net.search.tavily.key "{ secret = 'tavily' }"
```

You can also edit the secrets file by hand, one `name = "value"` per line; it takes effect when you save.

Keys that can hold a reference:

| Key | `{ secret }` | `{ env }` |
|---|---|---|
| `providers.<id>.key`, `net.search.exa.key`, `net.search.deepseek.key`, `net.search.tavily.key`, `net.search.brave.key`, keys a package declares as secrets | Yes | Yes |
| `providers.<id>.base_url`, `models.catalog.url`, `net.search.searxng.url`, `packages.source`, `packages.sources.<id>.url` | No | Yes |
| Values in an MCP server's `env`, `bearer`, `headers` | Yes | Yes |

A secret-type key written in plain text is reported as the wrong type, and the item does not count. If the referenced secret is not stored yet, or the environment variable is not set, it is only a warning, and the item has no key when it is used.

## Environment variables

The ones you can set:

| Variable | What it does |
|---|---|
| `MIYU_HOME` | Where the data root is. It must be an absolute path; a leading `~` is expanded to the home folder. Unset, it is `~/.miyu` |
| `MIYU_LOG` | The run log level of the core started this time, overriding `log.level`: `error`, `warn`, `info`, `debug`, `trace`, `off` |
| `MIYU_CATALOG_UPDATE` | When set to `false`, the core started this time does not fetch the model catalog in the background, overriding `models.catalog.update` |
| `MIYU_RESOURCES` | Points the resource folder elsewhere; used when developing Miyu |
| `MIYU_DISTRO_PACKAGES` | Looks for Miyu packages installed by the system package manager only under this absolute path; used for testing |

Set in a shell, it applies only to that window and the core started from it:

```bash
export MIYU_LOG=debug
```

```powershell
$env:MIYU_LOG = 'debug'
```

The core reads the environment as it was at the moment it started; if one is already running, run `miyu core stop` first. To make windows you open later pick it up, and to have the service started at login and the tray carry `MIYU_HOME`, see [Data and backups](data.md#moving-it-to-another-location).

These are what Miyu gives extensions, package commands, scripts, MCP servers and commands the AI runs when it starts them. Package authors need them; you do not set them:

| Variable | What it is |
|---|---|
| `MIYU_PROGRAM` | The real location of the main program `miyu` |
| `MIYU_HOME` | The data root |
| `MIYU_RESOURCES` | The resource folder |
| `MIYU_APP_DIR` | The package's folder |
| `MIYU_CONFIG_DIR` | The package's own config folder `~/.miyu/etc/<id>/` |
| `MIYU_STATE_DIR` | The state folder of the package, script or MCP server |
| `MIYU_CACHE_DIR` | A cache folder that can be deleted |
| `MIYU_LOG_DIR` | The package's log folder `~/.miyu/var/log/<id>/` |
| `MIYU_TMP_DIR` | The package's scratch folder, emptied before each start |
| `MIYU_RUNTIME_DIR` | The package's runtime folder, for locks and sockets |
| `MIYU_IMAGES_DIR` | The folder where a script puts images to hand to the AI |
| `MIYU_PICTURES_DIR`, `MIYU_VIDEOS_DIR`, `MIYU_DOCUMENTS_DIR`, `MIYU_DOWNLOADS_DIR` | The folders under `~/.miyu/root/` meant for you to look at |
| `MIYU_ARGS_JSON` | The arguments when a script is called, as JSON |
| `MIYU_CALLER_VENUE` | Which kind of session this call comes from |
| `MIYU_CALLER_OWNER` | Whether the one speaking is you: `1`, `0` |
| `MIYU_SETTINGS_JSON` | The final values of this package's settings, as JSON |
| `MIYU_MODEL`, `MIYU_EFFORT` | In commands the AI runs: this turn's model and thinking effort |
| `MIYU_SESSION_LOG` | In commands the AI runs: this session's log folder |
| `MIYU_CALL_SOCK`, `MIYU_CALL_TOKEN` | In commands the AI runs: the address and token `miyu call` uses to connect back to this session |

For how each is used, see [Writing a Miyu package](../../authors/README.en.md).

## Editor completion

When the core starts, it generates two files in `~/.miyu/var/cache/config/`:

- `config.schema.json`: a JSON Schema of the system config, with each key's name, description, allowed values and default.
- `reference.toml`: every key with its default, for you to browse. Changing it has no effect.

Both are written in the language of `ui.language`. They are rewritten after you change the interface language or install or uninstall packages.

The first line of a system config the core creates is:

```toml
#:schema ../var/cache/config/config.schema.json
```

If your editor has a TOML plugin that understands this line (Taplo and the like), you get completion, hover descriptions, and mistakes marked as you type. If you created the file yourself and it lacks this line, copy it to the first line. The project config has no schema.

## Why a setting did not take effect

1. See which layer is in effect:

   ```sh
   miyu config explain permission.start_read_only
   ```

   ```text
   Start new sessions read-only (permission.start_read_only): When on, new sessions begin read-only. The AI can look around and plan, and you turn read-only off when files should change. A project config can only turn it on. Applies to new sessions.
     true   project config  ~/src/app/.miyu/config.toml:2  ← in effect
     false  system config   ~/.miyu/etc/config.toml:5
     false  default
   ```

   The first line is the name, the description, and when it takes effect. Below it, from top to bottom, is one line per layer: the value, which layer, and the line it is written on. The line in effect is marked "← in effect"; one overridden by an environment variable is marked "← in effect, for this launch only". A value that is written but does not count is marked with the reason: "← does not count: not trusted yet", "← does not count: looser than the layers below", "← does not count: not allowed in this layer".

2. Check for mistakes: `miyu check`.

3. Check when it takes effect: for "Applies to new sessions", open a new session; for "Takes effect after restart", reopen the terminal or web UI.

### What happens when something is wrong

| What is wrong | Result |
|---|---|
| Unknown key | Warning, with the closest key name. It stays in the file and has no effect |
| Wrong value type, not one of the options, out of range, malformed | Error. Only this item is dropped; the value from the layer below is used, or the default if there is none |
| Written in a layer where it is not allowed | Error. This item does not count |
| TOML syntax error | Error. The whole file does not count: when the core starts, it treats the file as empty; while it is running, it keeps using the last version it read successfully |
| Referenced secret not stored, environment variable not set | Warning |

`miyu config set` and the settings page reject a wrong value outright and do not touch a single character of the file. `miyu config edit` does not save when there are errors. If the file has errors, `miyu ask` starts by printing "the configuration has N errors" and suggests running `miyu check`.

### miyu check

```sh
miyu check                 # check everything
miyu check ~/.miyu/etc/config.toml   # check only this file
```

It checks, as they are on disk now, the files you write by hand that Miyu reads: the system config (including the MCP servers in it), the project config of the current directory, the secrets file, each persona's `persona.toml` and `prompts/examples.md`, each preset, each package's manifest, and also skipped scripts and skills and unreadable lines in schedules. Given a file, it checks only that one. One line per problem:

```text
~/.miyu/etc/config.toml:12:3 error: …
```

The last line is the total, for example "1 error, 2 warnings", or "no problems" if there are none; after that it prints the indexing progress of the semantic model and of memory and knowledge bases, which does not count as a problem. If there are errors, the exit code is `1`. `--format json` prints JSON.

## Package settings

A package can declare its own settings in its manifest; they go in the same `~/.miyu/etc/config.toml`. The key is `<prefix>.<name>`: the prefix is the `prefix` written in the package manifest, or the package id if none is written. The terminal interface's prefix is `tui`, the web UI's is `web`:

```toml
[tui]
keys = "vim"

[web]
port = 8400
```

These keys can also be changed on the settings page, or with `miyu config set tui.keys vim`. Keys in packages that do not declare when they take effect apply the next time the head starts. When you uninstall a package, its keys stay in the file by default without effect, and work again if you reinstall it; only `miyu pkg remove --purge` removes them too. For the keys of the shipped terminal and web UI, see the [config key reference](config-keys.md).
