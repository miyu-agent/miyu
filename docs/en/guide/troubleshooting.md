# Troubleshooting

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

If Miyu will not start, cannot connect, does not respond, or shows an error you do not understand, start on this page. Errors that belong to a single feature are described in the "When something goes wrong" section of that feature's page; this page collects the general ones.

## Run miyu check first

`miyu check` checks the files you write by hand and that Miyu reads, and it is the first step in tracking down a problem. Run:

```sh
miyu check
```

It checks what is on disk right now, so a file you have just edited is checked too, even before the core has reread it. When you give no file name, it checks all of the following:

| What is checked | Where |
|---|---|
| System config | `~/.miyu/etc/config.toml` |
| The project config of the current directory | The `.miyu/config.toml` found by searching upward from the current directory |
| The secrets file, and secrets and environment variables that the config refers to but that cannot be found | `~/.miyu/etc/private/secrets.toml` |
| Whether the personas, presets, knowledge bases, providers and pools named in the config exist | System config |
| Settings left in the config by packages that have been uninstalled | System config |
| Each persona's `persona.toml` and `prompts/examples.md` | The persona directory |
| Each preset | The preset directory |
| The manifest of each package, both shipped ones and ones you installed | The package directory |
| The checks that packages bring with them | The programs that packages declare |
| Scripts, skills and slash command templates that did not load, and ones covered by another with the same name | Under packages and `~/.miyu/root/` |
| MCP servers that are written wrongly, and tools that are listed but not registered | System config, package manifests |
| Rows in the schedule table that cannot be read | The schedule table |
| Broken tool descriptions and prompt overrides | The override files |
| Model drivers provided by extensions: the package has not been approved, or a key that should be configured is not | System config |
| Installed package files that have been changed or are missing | The package directory |

The `~/.miyu` above is the data root (`~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows); if you set the environment variable `MIYU_HOME`, it is the directory that variable points to. To check only one file, write it after the command:

```sh
miyu check ~/.miyu/root/personas/miyu/prompts/examples.md
```

### Reading the result

Each problem takes one line: the file, the line, the column, `error` or `warning`, and a description of the problem. The line after the problems is the total, and below it is the state of the semantic model. For example:

```text
~/.miyu/etc/config.toml:3:9 error: log.level must be error, warn, info, debug, trace or off, not "verbose"
~/.miyu/etc/config.toml:12:1 warning: There is no models.chatt. Did you mean models.chat?
~/.miyu/etc/config.toml:20:7 warning: providers.acme.key refers to the secret acme, which is not set
1 error, 2 warnings
Semantic model: local:granite-embedding-97m-multilingual-r2, indexing
  Memory: engineer 120/120
  Knowledge bases: handbook 30/42
```

- `error`: the syntax is wrong, so the setting at this spot does not take effect; if the TOML itself cannot be read, the whole file does not take effect. When there are errors, the exit code is `1`.
- `warning`: a key it does not recognize, or a secret, environment variable, persona, preset or knowledge base that the config refers to but that does not exist yet. Miyu keeps running; these settings are just not used. When there are only warnings, the exit code is `0`.
- When there are no problems at all, it prints `no problems`.
- The semantic model lines are not problems. They tell you which model is in use, and how many memories, past conversations and knowledge-base entries have been indexed (indexed/total). When the semantic model is not installed, it prints `Semantic model: not installed, keyword search only`, with a hint to run `miyu pkg install embed`. When it is turned off, it prints `Semantic model: off (models.embedding = "off"), keyword search only`. If you switched to a remote model, there is one more line at the end, `No auto recall: memories, knowledge bases (no measured threshold for this model; search still works)`, because only the built-in model recalls memories and knowledge bases automatically; other models are used only when searching.

With `--format json` it prints one line, `{"problems": […]}`. Each problem has `kind`, `file`, `code`, `level` and `message`, and problems with a line and column also have `line` and `column`. When everything is checked, there is also `embedding`.

`miyu check` needs to connect to the core, and starts the core first if it is not running. This means that when the core cannot start, `miyu check` cannot run either: in that case read "The core will not start, or cannot connect" below first, and if that does not solve it, use [Rescue](rescue.md).

## Logs

When something goes wrong, the logs usually record why. Each program's log is here:

| Whose | Where |
|---|---|
| The core | `~/.miyu/var/log/core.log`; when it reaches 10 MB it is rotated, and `core.log.1` to `core.log.5` are kept |
| Packages, extensions | `~/.miyu/var/log/<id>/`; what an extension program writes to standard error, the core records in `stderr` in this directory |
| The web UI | `~/.miyu/var/log/webui/web.log` |
| The system tray | `~/.miyu/var/log/miyu-applet.log` |
| Terminal UI crashes | `tui/crash.log` under the cache directory: on Linux `~/.cache/miyu/tui/crash.log` (under `XDG_CACHE_HOME` if you set it), on macOS `~/Library/Caches/Miyu/tui/crash.log`, on Windows `%LOCALAPPDATA%\Miyu\cache\tui\crash.log` |

To see the last few dozen lines, run:

```sh
tail -n 50 ~/.miyu/var/log/core.log
```

In Windows PowerShell, run: `Get-Content -Tail 50 $HOME\.miyu\var\log\core.log`.

The core's log has one entry per line, written in English, and it does not record conversation content or keys. Every time the core starts, it writes one `starting` line with the version and the process id. To record in more detail, change `log.level`:

```sh
miyu config set log.level debug
```

`log.level` can be `error`, `warn`, `info` (the shipped default), `debug`, `trace` or `off`, and the change takes effect immediately. To record in detail just this once, first run `miyu core stop`, then open Miyu as shown below: the core started this way logs at `debug` this time, overriding `log.level`.

```bash
MIYU_LOG=debug miyu
```

```powershell
$env:MIYU_LOG = 'debug'
miyu
```

For more, see [Keeping it running, and servers](service.md#logs).

## The core will not start, or cannot connect

When an interface or the command line opens, it first connects to the core; if it cannot connect, it starts a core and waits for it to finish starting. If it is still not connected after 3 seconds, the command line first prints `miyu: the core is still starting…` and keeps waiting, for up to 10 minutes; if the core exits while starting or reports an error, you get the error right away instead of waiting the full 10 minutes. Press `Ctrl+C` while waiting to quit at once. A data root runs only one core at a time, and that core holds `~/.miyu/run/core.lock`.

| What you see | Cause | What to do |
|---|---|---|
| `the core couldn't start: …` | The core hit an error while starting; what follows the colon is the reason the core gave. | Fix what the reason says. If you do not understand the reason, read the last lines of `core.log`. |
| `the core didn't start and gave no reason; see … in the data root` | The core exited without giving a reason. | Read the last lines of `~/.miyu/var/log/core.log`. |
| `miyu: the core is still starting…` | This is not an error: the core is starting more slowly than usual, for example because the disk is busy or several cores are starting at once. | Wait for it. |
| `timed out waiting for the core to start` | The core's process is still there, but it was still not up after 10 minutes, most likely because it is stuck. | Read the last lines of `core.log`, then end it as the section "The old core is still running" below describes, using the process ID on the last `starting` line of `core.log`, and open Miyu again. |
| `another program is starting the core and it took too long` | Another interface is starting the core, and it was still not up after 10 minutes. | The same as the row above. |
| `miyu: the core hasn't answered yet, still waiting…`, and in the end `the core never answered, stopped waiting` | The core is connected but never answers, and the wait lasts up to 10 minutes; most likely the core is stuck. | The same as `timed out waiting for the core to start`. |
| `cannot launch the core: …` | The core program cannot be found, or you have no permission to run it. | Reinstall Miyu, see [Installing, upgrading and uninstalling](install.md). |
| `… isn't a Miyu data root …` | Something else is already at the location of the data root. The data folder of the old 0.7 version also produces this message. | If it is the data folder of the old 0.7 version, move it aside as the second half of the message says, install the migration package and migrate, see [Migrating from the old 0.7 version](migrate.md); if it is not, set `MIYU_HOME` to an empty folder. |
| `… is an old Miyu data root, which this version doesn't read …` | This is a data root left by a development build from before the release. | Set `MIYU_HOME` to an empty folder. |
| `… uses a layout this version doesn't know …` | A newer version of Miyu has written to this data root. | Use the version that wrote it, or switch to another data root. |
| `… is not owned by the current user or is accessible to other users, so it was not connected to` (Linux, macOS); `The other end of named pipe … is not a process of the current user, so it was not connected to` (Windows) | Linux, macOS: the directory that holds the socket does not belong to you, or other users can enter it, so Miyu does not connect to the socket in it. Windows: the program at the other end of the named pipe is not run by your user. | Linux, macOS: make that directory enterable by you only, for example by running `chmod 700 <directory>`. Windows: close the program that holds the pipe, then open Miyu again. |
| `the core couldn't start: the socket path … is too long, and it doesn't fit in the temporary folder either` (Linux, macOS) | The data root's path is too long. | Use a shorter `MIYU_HOME`, or set `TMPDIR` to a directory with a short path. |
| `the core couldn't start: something else is at …: a file that isn't a socket, or another program listening. It was left alone` (Linux, macOS); `the core couldn't start: named pipe … is taken by another program. It was left alone` (Windows) | Linux, macOS: another file or program holds the socket's location. Windows: another program holds the name of the named pipe. | If what holds it is not Miyu's, move that file away or close that program. |
| `lost connection to the core` | The core exited or crashed partway through. | Read `core.log`, then open Miyu again. |

Where the socket is on each system:

| System | Where |
|---|---|
| Linux | `$XDG_RUNTIME_DIR/miyu-<fingerprint>/core.sock` when `XDG_RUNTIME_DIR` is set, otherwise `~/.miyu/run/core.sock`; when the path is too long, it falls back to `$TMPDIR/miyu-<uid>/` |
| macOS | `~/.miyu/run/core.sock`; when the path is too long, it falls back to `$TMPDIR/miyu-<uid>/` |
| Windows | The named pipe `\\.\pipe\miyu-<fingerprint>`, open only to your user |

### The old core is still running

After an upgrade, a core that is already running is still the old version, and a new interface that connects to it may report `Protocol version mismatch. Upgrade to the same release.`. In that case stop the old core first; the next time you open Miyu, the core that starts is the new version. Run:

```sh
miyu core stop
```

If you installed the start-at-boot service and want the service to keep managing the core, run `miyu service enable` once more, see [Keeping it running, and servers](service.md#making-the-service-take-over-now).

If `miyu core stop` says `the core is still running but cannot be reached: the token or socket location in the data root's run/ is gone`, then `~/.miyu/run/` was deleted while the core was still running. As the hint says, find the process id on the last `starting` line in `core.log`, then end that process:

```bash
kill <process id>
```

```powershell
Stop-Process -Id <process id>
```

### The core is slow to stop

After the core receives a stop signal (for example when you stop the startup service, or run `kill <process ID>`), it first stops the running sessions and extensions, then exits. This takes at most 30 seconds; after 30 seconds the core exits anyway. If you do not want to wait, send the stop signal once more: the core exits at once on the second one and writes `second stop signal, exiting now` to `core.log`.

If the core is still starting and not yet ready to accept connections, there are no sessions to stop yet, so the core exits at once on the first stop signal and writes `stopped reason=signal ready=false` to `core.log`.

### No interface opens at all

If the core is broken and no interface opens, use `miyu rescue` to enter LiteMiyu's rescue mode and repair it; rescue mode does not go through the core. LiteMiyu has only a Linux x86_64 build, and none for macOS or Windows. For details see [Rescue](rescue.md).

## No model configured, or a wrong key

Miyu needs a configured model and key before it can hold a conversation. The common messages and what to do about them:

| What you see | What to do |
|---|---|
| `no model configured`, with the hint to run `miyu setup`; `miyu ask` exits with code `5` | Run `miyu setup`, see [Models](models.md). |
| `miyu check` warns `… refers to the secret …, which is not set` | Run `miyu provider login <name>` to store the key. |
| `miyu check` warns `… refers to …, which was not set when the core started` | The core started before this variable was set. Run `miyu core stop`, then open Miyu again in the shell where the variable is set. A core started by the start-at-boot service cannot see variables in your shell, see [Keeping it running, and servers](service.md#the-service-and-environment-variables). |
| `Model request failed.`, authentication failed | The key is wrong or has expired; run `miyu provider login <name>` again. |

## The model keeps failing

`Models cooling down. Try again later.` and `No model is available.` mean that the provider rate-limited you, the quota ran out, or the provider could not be reached, so Miyu set that model aside for a while. For how many times it retries, how long the cooldown lasts, and how to use a pool to switch to another model, see [Models](models.md#rate-limits-and-used-up-quota).

## A command was refused, or it keeps waiting for confirmation

A command the AI runs can be stopped by the permission settings, or left waiting for confirmation. The common cases:

| What you see | Cause |
|---|---|
| `Read-only mode, not run` | The session is read-only and cannot write. |
| The confirmation box keeps waiting | It is waiting for you to click allow or deny; if nobody clicks in time, it is denied automatically and shows `No one confirmed in time, denied automatically`. |
| `Needs confirmation, no one to confirm`; `miyu ask` exits with code `4` | In `miyu ask` and on chat platforms nobody can confirm on the spot, so the steps that need confirmation are not done. |

For how to switch permission levels, which commands need confirmation, and how to turn confirmation off, see [Permissions and sandbox](permissions.md).

## A package will not install, or an extension will not start

When installing a package or starting an extension fails, the common messages and what to do about them:

| What you see | What to do |
|---|---|
| `Invalid manifest, cannot install.` | Run `miyu pkg info <package directory>`; it only looks and does not install, and it tells you what is wrong in the manifest. |
| `Required packages are missing.` | Install the packages it depends on first; `miyu pkg info <id>` shows the dependencies. |
| `Not supported on this system.` | The package has no build for your kind of system. |
| `Package source unreachable.` `Package download failed.` | Check the network, then wait a while and run `miyu pkg update` again. |
| `<program> not found: … says miyu <name> runs it. Reinstall the package and try again.` | Reinstall it with `miyu pkg install <id>`. |
| `user interface 'tui' is not installed` | Install it back with `miyu pkg install tui`. |
| An extension stopped | Read `~/.miyu/var/log/<id>/stderr`, which holds the errors the extension reported itself. |

`miyu pkg check` checks whether the installed files have been changed. For details see [Packages](packages.md).

## The terminal UI displays incorrectly

When the terminal UI does not display correctly, the common cases and what to do about them:

| What you see | What to do |
|---|---|
| Icons show as boxes or question marks | The font has no Nerd Font icons. Install a Nerd Font, or run `miyu config set tui.icons plain` to use plain characters. |
| The colors are wrong or too harsh | On the settings page, adjust `Colors`, `Color mode` and `Background fill` under `Appearance → Color scheme`; the matching config keys are `tui.theme`, `tui.theme_mode` and `tui.theme_background`. |
| The command line's output has color codes that look like garbage | Set the environment variable `NO_COLOR=1`. |
| The terminal UI crashed | The crash record is in `tui/crash.log`; for its location see "Logs" above. |

If you installed the shell integration, you can run `miyu shellhook doctor`. It first lists which shells the integration is installed into, then checks the core, the terminal and the clipboard one by one. The output looks like this:

```text
✓ The core is reachable
✗ The terminal doesn't say it's truecolor (COLORTERM isn't truecolor): at most 256 colors
✗ Can't read the terminal's colors: following the terminal uses its 16 colors only (tmux and the like need passthrough)
✓ Ctrl+V reads the clipboard with wl-paste
```

This is the output on a Wayland desktop on Linux. In other environments, the last line is:

| System | The last line |
|---|---|
| Linux, without Wayland | `Ctrl+V reads the clipboard with xclip` or `… with xsel` |
| macOS | `Ctrl+V reads the clipboard with pbpaste` |
| Windows | `Ctrl+V reads the clipboard with powershell` |

If no clipboard command is found at all, it shows `✗ No clipboard command found (…): Ctrl+V can only use the terminal's own paste`, and the parentheses list the commands that were tried on this machine.

For the terminal UI's settings see [Terminal](heads/tui.md).

## The web UI will not open

When the web UI will not open or you cannot sign in, the common messages and what to do about them:

| What you see | What to do |
|---|---|
| `port 8300 is in use`, with the hint to pick another with `miyu web --port <port>` | Use another port. If you have never specified a port, when 8300 is taken Miyu tries 8301 to 8309 in turn, and reports this error only when all of them are taken. |
| `cannot open a browser; open the address above` | Open the address it printed in a browser yourself. On a machine with no desktop, use `miyu web --print`. |
| The sign-in page says `Wrong access password` | If you forgot the password, run `miyu web --reset` on this computer and set a new one in the page that opens. |
| The whole page says `No access password yet` | On the computer that runs Miyu, run `miyu web --settings access` to set one. |
| `Too many attempts. Try again in N s` | Wait for the number of seconds it says to pass, then try again. |

The web UI's own log is `~/.miyu/var/log/webui/web.log`. To open the web UI from another device or through a reverse proxy, see [Keeping it running, and servers](service.md#opening-the-web-ui-from-other-computers-and-phones).

## Mistakes in the config

When a config file has a mistake in it, Miyu handles it as follows:

- `miyu ask` starts with `the configuration has N errors`, with the hint to run `miyu check` to see them. Fix them by the line numbers `miyu check` prints.
- If a whole config file cannot be read when the core starts, that file is treated as empty, and the core starts anyway. If you break the config by hand while the core is running, the core keeps using the last copy it read successfully.
- When a file cannot be read, `miyu config set` does not change it and reports `Config file is invalid. Fix it first.` instead. `miyu config edit` checks the file before saving.
- If a setting does not take effect, run `miyu config explain <key>`. It lists what each layer says, which layer takes effect, and why a layer that was written does not.
- If you see `project config … is not trusted; not used this time`, run `miyu config trust` in that directory, read the config, then decide whether to trust it.

For details see [Configuration](config.md).

## Reason codes

When the core refuses to do something, it gives a reason code and one sentence. Interfaces and the command line show the sentence; a program that connects to the core over the protocol directly reads `data.reason`. The common reason codes:

| Reason code | The sentence shown | What to do |
|---|---|---|
| `no_model` | No model is available. | Run `miyu setup`, or write a usable model in `models.chat`. |
| `cooling` | Models cooling down. Try again later. | Wait a while, or configure a pool, see [Models](models.md). |
| `model_failed` | Model request failed. | Read the details in the interface; if authentication failed, store the key again. |
| `unknown_model` | Model or pool not found. | Write it as `provider/model` or `@pool`, and make sure the provider is configured. |
| `unknown_provider` | Provider not found. | Configure that provider first, see [Models](models.md). |
| `unknown_secret` | Secret not found. | Run `miyu provider login <name>`. |
| `session_not_found` | Session not found. | Write the full session id; a deleted session cannot be recovered. |
| `turn_running` | A turn is in progress. | Wait for this turn to end, or interrupt it first, then undo, compact or delete. |
| `archived` | This is an archive. It can't be continued. | Export it again without `--archive`. |
| `session_read_only` | The session log is broken; only the part before it can be viewed and the session can't continue. Start a new session to go on. | Start a new session. |
| `session_unavailable` | Session can't be read right now. Try again later. | Try again in a while; this is common with disk errors or too many open files. |
| `dir_too_wide` | Directory too broad. | Use a smaller directory. |
| `attachment_too_big` | Attachment too large (max 20 MiB; images 5 MiB, 8000 px). | Make the attachment smaller, or give only its path. |
| `attachment_in_data_root` | Files in the data directory cannot be attached. | Copy the file outside the data root, then attach it. |
| `export_exists` | File already exists. | Use another file name, because export does not overwrite existing files. |
| `unknown_config_key` | Config key not found. | Run `miyu config get` to see which keys exist. |
| `config_invalid` | Invalid config, not saved. | Change the value as the error says; `miyu config explain <key>` shows what can be written. |
| `config_file_broken` | Config file is invalid. Fix it first. | Run `miyu check`. |
| `unknown_package` | Package not found. | Run `miyu pkg search` to find the package's id. |
| `package_invalid` | Invalid manifest, cannot install. | Run `miyu pkg info <package directory>` to see what is wrong. |
| `depends_missing` | Required packages are missing. | Install the packages it depends on first. |
| `extension_off` | Extension disabled. | Turn it on in the packages page. |
| `bad_password` | Incorrect access password. | Run `miyu web --reset`. |
| `protocol_mismatch` | Protocol version mismatch. Upgrade to the same release. | Upgrade the interface and the core to the same version, then run `miyu core stop`. |
| `internal_error` | Internal error. See the runtime log. | Read `core.log`, then report the problem as described below. |

For all reason codes see [Protocol reference: errors](../reference/errors.md).

## Reporting a problem

If the steps above do not solve it, report it in the core repository: <https://github.com/miyu-agent/miyu/issues>. Attach:

1. The version that `miyu --version` prints.
2. Your system and its version, for example Arch Linux, macOS 15, Windows 11; for a terminal UI problem, also give the name of the terminal program.
3. The output of `miyu check`.
4. A few lines of `core.log` from around the moment of the problem; for a package problem, attach the logs in `~/.miyu/var/log/<id>/`; if the terminal UI crashed, attach that part of `crash.log`.
5. The steps that make the problem happen again.

Read it through yourself before you paste it. Logs and the output of `miyu check` contain your paths, user name, session ids and package names; an exported session carries the conversation, command output and file contents as they are, with nothing masked. Do not paste `~/.miyu/etc/private/secrets.toml`.
