# Permissions and sandbox

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page explains what the AI can do on your computer, when it asks you first, and which folders it cannot reach.

## Two permission levels

Each session can use one of two permission levels, `Full access` or `Read-only`, and each session keeps its own choice. A new session uses full access by default.

| | Full access | Read-only |
|---|---|---|
| File tools reading | They can read anywhere, including Miyu's own data root. | The same as full access. |
| File tools writing | They can write anywhere, including Miyu's own data root. | They do not write, and the timeline records `Read-only mode, not run`. |
| Commands | They do not run in the sandbox; protected commands ask you first, and a few kinds of dangerous commands are refused outright. | They run in the sandbox and cannot write anywhere (see below). |
| Tools in extensions that go online | They are used directly. | They are used directly. |
| Tools of MCP servers that are not marked read-only, and tools in extensions that send messages out | They are used directly. | They ask you before each use. |
| Installing and removing packages, turning on an extension | Miyu asks you first every time. | Miyu does not do it. |

The data root is the folder where Miyu keeps its own data. By default it is `~/.miyu`, and on Windows it is `%USERPROFILE%\.miyu`; if you set `MIYU_HOME`, the data root is the folder it points to. Miyu does not give the data root any extra protection: under full access, file tools and commands read and write it just like any other folder, and `~/.miyu/etc/private/secrets.toml`, which holds your keys, can be read too; under read-only, the data root can be read but not written, like everywhere else. Only deleting the whole data root, moving it away or putting it in the trash asks you first, see "Commands that need confirmation" below; files and folders inside the data root are treated like anywhere else, and you are not asked about them. When `glob` and `grep` search down from a folder above it, they skip the data root, for the same reason they skip `.git`; if the search starts inside the data root, it works as usual.

Under full access, commands can do anything your system user can do. Miyu recognizes a few kinds of dangerous commands only by their literal text (see "Commands that need confirmation" below). This protects against the AI's momentary mistakes, but it cannot stop a command written on purpose to get around it. If you want the AI to be unable to change anything, use read-only.

Read-only only stops writing; it does not hide anything from the AI: `~/.ssh`, browser data, other programs' logins and the like can still be read under read-only, and whatever the AI reads goes into the context and is sent to the model provider. If you do not want the AI to read these, you need to put Miyu inside another sandbox yourself, or run Miyu as a different system user. Miyu's own data root is the same: it can be read at both permission levels, including the secrets file that holds your keys, and under full access it can be written too.

Commands under read-only behave like this:

- They can read the whole disk (on Windows, the machine's fixed drives), including the data root. The read-only sandbox hides no folder; it only blocks writing.
- They cannot write anywhere, not even to the temp folder, and a command that tries to write reports that it has no permission.
- They can go online. On macOS and on Linux with a new enough kernel, commands cannot reach system services such as Docker and ssh-agent.
- If the sandbox cannot be used on this computer, every command asks you first, and once you allow it, the command runs outside the sandbox.

## Switching the permission level

You can switch the permission level in the following ways:

- Terminal interface and web interface: press `Tab` or `Shift+Tab` in the input box. In the terminal interface, while the command list or the `@` file list is open, `Tab` goes to the list, and `Shift+Tab` still switches. In the web interface you can also click `⏵⏵ Full access` or `⏸ Read-only` at the left of the line below the input box.
- Command line: add `--permission` when you start a new session, with the value `read-only` or `full`. It only applies to a new session and cannot be used together with `-c` or `-s`. For example:

  ```bash
  miyu ask -C ~/src/app --permission read-only "check the code here"
  ```

  ```powershell
  miyu ask -C $HOME\src\app --permission read-only "check the code here"
  ```

- To make new sessions start in read-only: on the settings page, turn on `General → New sessions → Start new sessions read-only`, or run:

  ```sh
  miyu config set permission.start_read_only true
  ```

You can also switch while the AI is working. Switching to read-only takes effect immediately, and write operations in the current step that have not run yet are refused; switching back to full access takes effect from the AI's next request to the model.

## Commands that need confirmation

Under full access, the five kinds of commands below ask you first. On the settings page (type `/settings` in the terminal interface or web interface to open it), `Privacy & security → Protected commands` has one switch for each kind, and all of them are on by default.

| Name on the settings page | Config key | Which commands it catches |
|---|---|---|
| `Destructive git operations` | `permission.confirm.git` | It catches `git push --force` (`-f` and `+branch` count too), `git reset --hard`, `git clean -f`, `git checkout .`, `git restore .`, `git stash drop` and `git stash clear`. |
| `Recursive deletes` | `permission.confirm.delete` | It catches deleting the working directory or a parent of it, for example running `rm -rf ..` inside `~/src/app`; deleting Miyu's whole data root or a folder that contains it, moving it away or putting it in the trash, whichever command is used, for example `rm -rf ~/.miyu`, `mv ~/.miyu ~/x`, `gio trash ~/.miyu`, `trash-put ~/.miyu` or `rsync` with `--remove-source-files`, and the AI deleting it with the `trash` tool counts too, while files and folders inside the data root are not asked about; and deleting a whole folder tree where the target is only known at run time, for example `rm -rf "$OUT"` or `… \| xargs rm -r`. `find` with `-delete` counts too. |
| `Shutdown and restart` | `permission.confirm.power` | It catches `shutdown`, `reboot`, `halt`, `poweroff`, `init 0` and `init 6`, and `systemctl` with `poweroff`, `reboot`, `halt`, `suspend`, `hibernate` or `kexec`. |
| `Running a download directly` | `permission.confirm.pipe_to_shell` | It catches commands that download with `curl` or `wget` and hand the result to a shell, `python`, `python3`, `perl`, `ruby` or `node` to run, for example `curl … \| sh`, `bash <(curl …)` and `sh -c "$(curl …)"`. |
| `Containers using host devices` | `permission.confirm.container` | It catches `run` or `create` of `docker`, `podman` or `nerdctl` with `--device` or `--device-cgroup-rule`, with `--pid`, `--net`, `--network` or `--ipc` set to `host`, or mounting something under `/dev` or `/sys`, for example `-v /dev/snd:/dev/snd`. |

Miyu still recognizes these when the command is prefixed with `sudo`, `doas`, `env`, `nice`, `nohup`, `timeout`, `time`, `stdbuf`, `command`, `exec` or `xargs`, or written inside `sh -c '…'`, `bash -lc '…'` or `eval`. A command whose substitutions are nested too deeply for Miyu to see through also asks you first, and this rule has no switch.

To turn off one kind, switch it off on the settings page, or run:

```sh
miyu config set permission.confirm.git false
```

The change takes effect from the next turn.

The kinds below are refused outright. They do not run even if you approve them, and they have no switch:

- Deleting the root `/`, the home directory or a parent of it, or a folder one level under the root (such as `/usr` or `/etc`).
- Formatting a disk: commands starting with `mkfs`, and `wipefs`, `mke2fs`, `blkdiscard`, `mkswap` and `sgdisk -Z` (`--zap-all`).
- Writing directly to a disk device: `dd of=/dev/…`, `> /dev/…`, and `tee`, `shred` or `cp` writing to a device. A device here means anything under `/dev/` that starts with `sd`, `nvme`, `mmcblk`, `disk`, `rdisk`, `vd`, `hd`, `xvd`, `mapper/`, `dm-`, `md`, `loop` or `nbd`.
- Letting a container take over the whole computer: `--privileged`, `--cap-add` with `ALL` or `SYS_ADMIN`, and mounting the host's `/`, `/dev` or `/sys`.

### How it is written on Windows

On Windows the AI runs commands in PowerShell (see [Tools the AI can use](tools.md#shell)). On Windows the rules above recognize PowerShell and cmd syntax; which kinds ask first and which are refused outright is the same as on Linux and macOS, and the five switches work the same way:

| Kind | What is recognized on Windows |
|---|---|
| Destructive git operations, containers using host devices (ask first) | The same as the table above; `git.exe` and `git.exe` with a path are recognized too. |
| Recursive delete (ask first) | Deleting the working directory with `Remove-Item -Recurse` (aliases `rm`, `del`, `erase`, `rd`, `rmdir`, `ri`, and cmd's `rd /s`, `del /s`), for example `Remove-Item -Recurse -Force .`; deleting or moving away the whole data root or a folder that contains it, where moving is recognized as `Move-Item` (aliases `mi`, `mv`, `move`, and cmd's `move`) and `Rename-Item` (`rni`, `ren`); and deletes whose target is only known at run time, for example `Remove-Item -Recurse $target` or `… \| Remove-Item -Recurse`. |
| Shutdown and restart (ask first) | This covers `Stop-Computer` and `Restart-Computer`; `shutdown` with any switch counts (`/s`, `/r`, `/h`, and `/l` for logging off too), except `/a` and `/?`. |
| Running a download directly (ask first) | A download by `irm`, `iwr`, `curl` or `wget` that is handed to `iex` (`Invoke-Expression`), `powershell`, `pwsh` or `cmd` to run, for example `irm … \| iex` and `iex (irm …)`. |
| Deleting the root, the home directory or system directories (refused outright) | A drive letter itself (`C:\`) counts as the root; folders one level below a drive letter (`C:\Windows`, `C:\Users`, `C:\Program Files`, and also ones you created such as `C:\dev`) are treated like folders one level below the root; `~`, `$HOME`, `$env:USERPROFILE` and `%USERPROFILE%` all count as the home directory. |
| Formatting disks (refused outright) | This covers `Format-Volume`, `Clear-Disk`, `Remove-Partition` and `format D:`. |
| Containers taking over the whole computer (refused outright) | The same as the list above. |

- Commands written inside `cmd /c "…"`, `powershell -Command "…"` or `iex '…'` are recognized all the same. Program names, parameter names and paths are not case-sensitive, and parameter names shortened to their first letters (`-r`, `-rec`) are recognized too. A delete with `-WhatIf` does not count.
- These are not recognized on Windows: commands encoded in `-EncodedCommand`, writing directly to disk devices (`\\.\PhysicalDrive0`), `Set-ExecutionPolicy`, deleting from the registry (`reg delete`, `Remove-Item HKLM:\…`), and deletes on network paths (`\\server\share`). Under full access these commands neither ask you first nor get refused.

### The confirmation box

The confirmation box has two choices:

1. `Allow once`.
2. `Don't allow`: you can write a reason, and the AI will see it.

The confirmation box for a protected command is marked `Dangerous command`.

The confirmation box waits at most `permission.confirm.timeout` seconds. The default is `300`, you can set it from `0` to `86400`, and `0` means it waits forever. The box shows `Auto-deny in …`; if nobody answers in time, the timeline records `No one confirmed in time, denied automatically`, and the AI tries another way to continue. Questions the AI asks you are not subject to this time limit.

Wherever there is no confirmation box, anything that needs confirmation is not done: `miyu ask` ends with exit code `4` after this turn, and sessions on chat platforms behave the same way.

## Project config

A repository's `.miyu/config.toml` (for how to use project config, see [Configuration](config.md)) can only tighten the settings on this page: project config recognizes only `permission.start_read_only = true`, and writing `false` has no effect. `permission.confirm.*` is recognized only in your own config; putting it in a project config has no effect, and `miyu config explain <key>` shows that it did not take effect.

## The three platforms

Under read-only, each of the three platforms confines commands with a mechanism built into the system: Landlock on Linux, Seatbelt on macOS, and Microsoft's MXC base container on Windows. The differences you will notice are:

| | What you will run into |
|---|---|
| Linux | When the kernel has no usable Landlock, the sandbox cannot be used. On a new enough kernel, commands cannot reach the sockets of system services such as Docker and ssh-agent. |
| macOS | When Miyu itself runs inside another sandbox, the sandbox cannot be used. Commands cannot reach the sockets of system services such as Docker and ssh-agent. |
| Windows | The sandbox only works inside a logged-in desktop session: if the core is not running in a desktop session (for example a core started over SSH), every command is refused under read-only, with exit code `125`. Under read-only only the machine's fixed drives can be read; removable drives such as USB sticks, network drives and optical drives cannot. The clipboard and simulated keyboard and mouse are unavailable. Commands that use WMI (`Get-CimInstance`, `Get-WmiObject`, `wmic`, `systeminfo`, `Get-ComputerInfo` and the like) cannot run; if you need them, switch to full access. |

Under full access, commands do not run in the sandbox on any of the three platforms; the table above only applies to read-only.

When the sandbox cannot be used, `miyu ask` prints a line `sandbox unavailable: <reason>` at the start, and if the problem can be fixed, a separate line explains how. The reasons on the three platforms are:

| | The reason printed | When it happens |
|---|---|---|
| Linux | `the kernel has no usable Landlock` | The kernel is older than 5.13, or `landlock` is not in the `lsm=` boot parameter. |
| macOS | `the Seatbelt profile cannot be applied; Miyu may be running inside another sandbox` | The Seatbelt profile cannot be installed. |
| Windows | `this Windows cannot start an MXC base container` | The base container the sandbox needs cannot start on this Windows. |

When the working directory is too broad: the root counts as too broad on all three platforms, and on Windows the home directory itself and a folder that contains the data root count too. A folder that is too broad can still be the working directory, and commands start from there; when you switch to it with `/workspace`, the reply shows `Workspace switched to … (broad directory).`.

## Sessions on chat platforms

If you have connected chat platforms, group sessions and private chats with someone other than you are locked down separately, whatever the permission level (only accounts you have put in `Advanced → Platform accounts` on the settings page count as you):

- File tools can only reach this session's workspace, and the folders of enabled skills can only be read.
- Commands run in a sandbox that confines reading to the workspace as well. Commands cannot run on Windows, nor on Linux where the sandbox cannot confine Unix sockets.
- Packages cannot be installed or removed.
- The switches for protected commands have no effect on these sessions.

## Common problems

| What you see | How to fix it |
|---|---|
| `Read-only mode, not run` | Switch back to full access. |
| `Needs confirmation, no one to confirm`, and `miyu ask` exits with code `4` | Do this in the terminal interface or web interface, or turn off the matching kind of protected command. |
| `No one confirmed in time, denied automatically` | Raise `permission.confirm.timeout`; setting it to `0` makes it wait forever. |
| `not run: would delete the home directory` and similar messages | These kinds cannot be let through; if you really need it done, do it yourself in a terminal. |
| `miyu-sandbox: cannot confine: no desktop session, programs in the sandbox cannot start here; use Miyu from the desktop, or turn the sandbox off` (exit code `125`) | On Windows, start Miyu from the logged-in desktop, or switch to full access. |
| Under read-only on Windows, the command output is followed by `The sandbox blocks WMI. Commands that need it work outside the sandbox.` | The command needs WMI, which cannot run in the sandbox. Switch to full access and have the AI run the command again. |
| `sandbox unavailable: the kernel has no usable Landlock` | Use Linux 5.13 or a newer kernel, and add `landlock` to the `lsm=` boot parameter. |
