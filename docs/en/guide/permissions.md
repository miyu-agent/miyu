# Permissions and sandbox

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page covers what the AI can touch on your machine, when it asks you first, and which folders it cannot reach. Chinese version: [中文](../../zh/guide/permissions.md).

## Two permission levels

Each session is set to either "Full access" or "Read-only", and each session keeps its own. A new session is full access by default.

| | Full access | Read-only |
|---|---|---|
| File tools, read | Can read anywhere, Miyu's own data root included | Same |
| File tools, write | Can write anywhere, Miyu's own data root included | Does not write; the timeline says "Read-only mode, not run" |
| Commands | Do not run in the sandbox; protected commands ask you first, and a few kinds of dangerous commands are refused outright | Run in the sandbox, which can write nowhere (see below) |
| Tools in extensions that go online | Used directly | Used directly |
| Tools of MCP servers that are not marked read-only, and tools in extensions that send messages out | Used directly | Ask you each time |
| Installing and removing packages, turning on an extension | Asks you each time | Not done |

The data root is the folder where Miyu keeps its own data. By default it is `~/.miyu`, on Windows `%USERPROFILE%\.miyu`; if `MIYU_HOME` is set, it is that folder. Miyu does not guard it separately: under full access, file tools and commands read and write it like any other directory, and `~/.miyu/etc/private/secrets.toml`, which holds your keys, can be read too; under read-only it can be read and not written, like everywhere else. Only deleting, moving away or trashing the whole data root asks you first, see "Commands that need confirmation" below; files and directories inside the data root are treated like anywhere else and are not asked about. When `glob` and `grep` search down from a directory above, they do not go into the data root, for the same reason they do not go into `.git`; a search that starts inside the data root works as usual.

Under full access, commands can do anything your system user can do. Miyu recognizes a few kinds of dangerous commands only by their literal text (see "Commands that need confirmation" below). That guards against the AI's momentary slips and cannot stop a command written to get around it. To keep the AI from changing anything, use read-only.

Read-only means no writing; it does not hide things for you: under read-only the AI can still read `~/.ssh`, browser data, other programs' logins and the like, and what it reads goes into the context and is sent to the model provider. If you do not want it to read something, put Miyu inside another sandbox yourself, or run it as a different system user. Miyu's own data root is the same: it is readable at both permission levels, the secrets file that holds your keys included; under full access it can be written too.

Commands in read-only:

- The whole disk is readable (on Windows, the machine's fixed drives), the data root included. The read-only sandbox hides no directory; it only blocks writing.
- Nothing can be written anywhere, the temp folder included; a command that writes reports that it has no permission.
- Network access works. On macOS and on Linux with a new enough kernel, system services such as Docker and ssh-agent cannot be reached.
- When the sandbox cannot be used on this machine, every command asks you first, and if you allow it, it runs without the sandbox.

## Switching

- Terminal and web UI: press `Tab` or `Shift+Tab` in the input box. In the terminal, while the command list or the `@` file list is open, `Tab` belongs to the list and `Shift+Tab` still switches. In the web UI you can also click "⏵⏵ Full access" or "⏸ Read-only" at the left of the line under the input box.
- Command line: when starting a new session, write `--permission` with the value `read-only` or `full`. It applies only to a new session and cannot be combined with `-c` or `-s`:

  ```bash
  miyu ask -C ~/src/app --permission read-only "check the code here"
  ```

  ```powershell
  miyu ask -C $HOME\src\app --permission read-only "check the code here"
  ```

- To have new sessions start read-only, use "General → New sessions → Start new sessions read-only" on the settings page, or:

  ```sh
  miyu config set permission.start_read_only true
  ```

You can also switch while the AI is working. Switching to read-only takes effect immediately, and write operations in this step that have not run yet are refused; switching back to full access takes effect from the AI's next request to the model.

## Commands that need confirmation

Under full access, the five kinds of commands below ask you first. On the settings page (type `/settings` in the terminal or web UI), "Privacy & security → Protected commands" has one switch per kind, all on as shipped.

| On the settings page | Config key | Which commands it catches |
|---|---|---|
| Destructive git operations | `permission.confirm.git` | `git push --force` (`-f` and `+branch` count too), `git reset --hard`, `git clean -f`, `git checkout .`, `git restore .`, `git stash drop`, `git stash clear` |
| Recursive deletes | `permission.confirm.delete` | Deleting the working directory or a parent of it, for example running `rm -rf ..` inside `~/src/app`; deleting, moving away or trashing Miyu's whole data root or a directory that contains it, whichever command is used, for example `rm -rf ~/.miyu`, `mv ~/.miyu ~/x`, `gio trash ~/.miyu`, `trash-put ~/.miyu` or `rsync` with `--remove-source-files`, and the AI deleting it with the `trash` tool counts too, while files and directories inside the data root are not asked about; deleting a whole directory tree where the target is only known at run time, for example `rm -rf "$OUT"` or `… \| xargs rm -r`. `find` with `-delete` counts too |
| Shutdown and restart | `permission.confirm.power` | `shutdown`, `reboot`, `halt`, `poweroff`, `init 0`, `init 6`, and `systemctl` with `poweroff`, `reboot`, `halt`, `suspend`, `hibernate` or `kexec` |
| Running a download directly | `permission.confirm.pipe_to_shell` | `curl` or `wget` downloads handed to a shell, `python`, `python3`, `perl`, `ruby` or `node` to run: `curl … \| sh`, `bash <(curl …)`, `sh -c "$(curl …)"` |
| Containers using host devices | `permission.confirm.container` | `run` or `create` of `docker`, `podman` or `nerdctl` with `--device` or `--device-cgroup-rule`, with `--pid`, `--net`, `--network` or `--ipc` set to `host`, or mounting something under `/dev` or `/sys`, for example `-v /dev/snd:/dev/snd` |

These are still recognized when the command is prefixed with `sudo`, `doas`, `env`, `nice`, `nohup`, `timeout`, `time`, `stdbuf`, `command`, `exec` or `xargs`, or written inside `sh -c '…'`, `bash -lc '…'` or `eval`. A command whose substitutions are nested too deeply to see through also asks first; this one has no switch.

To turn off one kind, switch it off on the settings page, or:

```sh
miyu config set permission.confirm.git false
```

It takes effect from the next turn.

These kinds are refused outright. They do not run even if you approve, and they have no switch:

- Deleting the root `/`, the home directory or a parent of it, or a directory one level under the root (such as `/usr` or `/etc`).
- Formatting a disk: anything starting with `mkfs`, `wipefs`, `mke2fs`, `blkdiscard`, `mkswap`, `sgdisk -Z` (`--zap-all`).
- Writing directly to a disk device: `dd of=/dev/…`, `> /dev/…`, and `tee`, `shred` or `cp` writing to a device. A device means anything under `/dev/` that starts with `sd`, `nvme`, `mmcblk`, `disk`, `rdisk`, `vd`, `hd`, `xvd`, `mapper/`, `dm-`, `md`, `loop` or `nbd`.
- Containers taking over the whole machine: `--privileged`, `--cap-add` with `ALL` or `SYS_ADMIN`, mounting the host's `/`, `/dev` or `/sys`.

### How it is written on Windows

On Windows the AI runs commands in PowerShell (see [Tools the AI can use](tools.md#shell)). The rules above recognize PowerShell and cmd syntax; which kinds ask first and which are refused outright is the same as on Linux and macOS, and the five switches work the same way:

| Kind | What is recognized on Windows |
|---|---|
| Destructive git operations, containers using host devices (ask first) | Same as the table above; `git.exe` and `git.exe` with a path are recognized too |
| Recursive delete (ask first) | `Remove-Item -Recurse` (aliases `rm`, `del`, `erase`, `rd`, `rmdir`, `ri`, and cmd's `rd /s`, `del /s`) on the working directory, for example `Remove-Item -Recurse -Force .`; deleting or moving away the whole data root or a directory that contains it, where moving is recognized as `Move-Item` (aliases `mi`, `mv`, `move`, and cmd's `move`) and `Rename-Item` (`rni`, `ren`); a target only known at run time, for example `Remove-Item -Recurse $target` or `… \| Remove-Item -Recurse` |
| Shutdown and restart (ask first) | `Stop-Computer`, `Restart-Computer`; `shutdown` with any switch counts (`/s`, `/r`, `/h`, and `/l` for logging off too), except `/a` and `/?` |
| Running a download directly (ask first) | A download by `irm`, `iwr`, `curl` or `wget` handed to `iex` (`Invoke-Expression`), `powershell`, `pwsh` or `cmd` to run: `irm … \| iex`, `iex (irm …)` |
| Deleting the root, the home directory or system directories (refused outright) | A drive letter itself (`C:\`) counts as the root; directories one level below a drive letter (`C:\Windows`, `C:\Users`, `C:\Program Files`, and ones you created such as `C:\dev`) count like directories one level below the root; `~`, `$HOME`, `$env:USERPROFILE` and `%USERPROFILE%` are the home directory |
| Formatting disks (refused outright) | `Format-Volume`, `Clear-Disk`, `Remove-Partition`, `format D:` |
| Containers taking over the whole machine (refused outright) | Same as the list above |

- Commands written inside `cmd /c "…"`, `powershell -Command "…"` or `iex '…'` are recognized all the same. Program names, parameter names and paths are case-insensitive, and parameter names cut to their first letters (`-r`, `-rec`) are recognized too. A delete with `-WhatIf` does not count.
- Not recognized on Windows: commands encoded in `-EncodedCommand`, writing directly to disk devices (`\\.\PhysicalDrive0`), `Set-ExecutionPolicy`, deleting from the registry (`reg delete`, `Remove-Item HKLM:\…`), and deletes on network paths (`\\server\share`). Under full access these are neither asked about nor refused.

### The confirmation box

The confirmation box has two choices:

1. "Allow once".
2. "Don't allow": you can write a reason, which the AI sees.

The confirmation box for a protected command is marked "Dangerous command".

The wait for your confirmation lasts at most `permission.confirm.timeout` seconds. The default is `300`, you can set `0` to `86400`, and `0` waits forever. The box shows "Auto-deny in …"; if nobody answers in time, the timeline says "No one confirmed in time, denied automatically" and the AI tries another way. Questions the AI asks you are not covered by it.

Wherever there is no confirmation box, anything that needs confirmation is not done: after this turn `miyu ask` ends with exit code `4`; sessions on chat platforms are the same.

## Project config

A repository's `.miyu/config.toml` (for how to use project config, see [Configuration](config.md)) can only tighten things on this page: only `permission.start_read_only = true` is recognized, and `false` does not count. `permission.confirm.*` is recognized only in your own config; putting it in a project config does not count, and `miyu config explain <key>` shows that it did not take effect.

## The three platforms

In read-only, each platform confines commands with a mechanism of its own system: Landlock on Linux, Seatbelt on macOS, Microsoft's MXC base container on Windows. The differences you will notice:

| | What you will run into |
|---|---|
| Linux | The sandbox is unavailable when the kernel has no usable Landlock. On a new enough kernel, sockets of system services such as Docker and ssh-agent cannot be reached |
| macOS | The sandbox is unavailable when Miyu itself runs inside another sandbox. Sockets of system services such as Docker and ssh-agent cannot be reached |
| Windows | Works only inside a logged-in desktop session: if the core is not in a desktop session (for example one started over SSH), every command is refused in read-only, with exit code `125`. Read-only reaches the machine's fixed drives; removable drives such as USB sticks, network drives and optical drives cannot be read. The clipboard and simulated keyboard and mouse are unavailable. Commands that use WMI (`Get-CimInstance`, `Get-WmiObject`, `wmic`, `systeminfo`, `Get-ComputerInfo` and the like) fail; to use them, switch to full access |

Under full access, commands do not run in the sandbox on any of the three platforms; the table above covers read-only only.

When the sandbox is unavailable, `miyu ask` prints a line "sandbox unavailable: <reason>" at the start, and if it can be fixed, a separate line says how. The reasons on the three platforms are:

| | The reason line | When |
|---|---|---|
| Linux | the kernel has no usable Landlock | The kernel is older than 5.13, or `landlock` is not in the `lsm=` boot parameter |
| macOS | the Seatbelt profile cannot be applied; Miyu may be running inside another sandbox | The Seatbelt profile cannot be installed |
| Windows | this Windows cannot start an MXC base container | The base container the sandbox needs does not start on this Windows |

When the working directory is too broad: the root counts as too broad on all three platforms; on Windows the home directory itself and a directory that contains the data root count too. A directory that is too broad still works as the working directory and commands start from there; when you switch to it with `/workspace`, the reply says "Workspace switched to … (broad directory)."

## Sessions on chat platforms

If chat platforms are connected, group sessions and private chats with someone other than you (only accounts you have put in "Advanced → Platform accounts" on the settings page count as you) are locked down, whatever the permission level:

- File tools can reach only this session's workspace, and open skill folders can only be read.
- Commands run in a sandbox that confines reads to the workspace too. Commands cannot run on Windows, nor on Linux where the sandbox cannot confine Unix sockets.
- Packages cannot be installed or removed.
- The switches for protected commands have no effect on them.

## When something goes wrong

| What you see | What to do |
|---|---|
| "Read-only mode, not run" | Switch back to full access |
| "Needs confirmation, no one to confirm", `miyu ask` exit code `4` | Do this in the terminal or web UI, or turn off the matching kind of protected command |
| "No one confirmed in time, denied automatically" | Raise `permission.confirm.timeout`; `0` waits forever |
| "not run: would delete the home directory" and similar | These kinds cannot be let through; if you need it done, do it yourself in a terminal |
| `miyu-sandbox: cannot confine: no desktop session, programs in the sandbox cannot start here; use Miyu from the desktop, or turn the sandbox off` (exit code `125`) | On Windows, start Miyu from the logged-in desktop, or switch to full access |
| In read-only on Windows, the command output is followed by `The sandbox blocks WMI. Commands that need it work outside the sandbox.` | The command needs WMI, which does not work in the sandbox. Switch to full access and have the AI run it again |
| "sandbox unavailable: the kernel has no usable Landlock" | Use Linux 5.13 or newer, and add `landlock` to the `lsm=` boot parameter |
