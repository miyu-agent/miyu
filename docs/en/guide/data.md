# Data and backups

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Where Miyu keeps your sessions, settings, keys and memory, what to back up, what you can delete, and how to move to another machine or another location are all on this page. Chinese version: [中文](../../zh/guide/data.md).

## Where the data root is

Almost everything of Miyu's is in one directory, called the data root (`~/.miyu` by default):

| System | Default location |
|---|---|
| Linux, macOS | `~/.miyu` |
| Windows | `%USERPROFILE%\.miyu` |

Installing, upgrading and uninstalling Miyu never touch the data root.

### Moving it to another location

Set the environment variable `MIYU_HOME` to point at another directory:

```bash
export MIYU_HOME=/data/miyu
```

```powershell
$env:MIYU_HOME = 'D:\miyu'
```

Set this way, it applies only to this one shell window. To make it stick, see the table below and the notes after it.

- Write an absolute path; a leading `~` is replaced with the home directory. If you write a relative path, it reports "MIYU_HOME must be an absolute path, got …".
- Set to empty, it counts as not set.
- If the directory does not exist, it is created on first use. On Linux and macOS, the new directory is accessible only to you (`0700`); on Windows it inherits the access control of the parent directory.

`MIYU_HOME` is read from the environment at the moment of startup, so what counts is the environment of whatever started the program:

| Who | How it picks it up |
|---|---|
| Command line, terminal, web UI, shell integration | The environment of the shell where you type the command. If you set it in the shell's config (`~/.bashrc` or `~/.zshrc` for bash and zsh, `$PROFILE` for PowerShell), every new shell picks it up; on Windows you can also set it as a user environment variable, see after the table |
| Packages, scripts, MCP servers, commands the AI runs | The core hands it to them when it starts them, so it is the same as the core's |
| The service installed by `miyu service enable` | If it was set at install time, it is written into the service file. After changing the data root, run `miyu service enable` again. On Windows, a service cannot be installed with `MIYU_HOME` set, see [Keeping it running, and servers](service.md#starting-at-boot-or-login) |
| Tray | The command line's `--home <data root>`; if not given, `MIYU_HOME`. "Start at Login" writes it into the startup entry, and on Windows it can carry it too, see [Tray](heads/applet.md#start-at-login) |
| herdr restore pane | It does not keep temporary variables written in front of the command, see [Terminal](heads/tui.md#using-it-with-herdr) |

A tray opened from the application menu cannot see variables set in a shell config; the same goes for `Miyu.app` opened from Finder or the Dock on macOS. Open the tray from a terminal with `--home`, check "Start at Login", and the startup entry records this argument, so later logins start it with this data root:

| System | Type in a terminal |
|---|---|
| Linux | `miyu-applet --home /data/miyu` |
| macOS | `/Applications/Miyu.app/Contents/MacOS/miyu-applet --home /data/miyu` (if `Miyu.app` is not in the Applications folder, use its location instead) |

On Windows, set the user environment variable with `setx MIYU_HOME D:\miyu`, and programs opened afterwards pick it up. For starting at boot, use the tray's "Start at Login", not `miyu service`: a service cannot be installed with `MIYU_HOME` set.

### The marker file

At the top of the data root there is a `.miyu-layout`, with one line in it: `This directory is a Miyu data root (layout 3).`. Miyu only accepts a directory that has this marker:

- The directory does not exist or is empty: the marker is written and it is treated as a new data root.
- It has other things in it and no marker: not a single byte is touched, and it reports "… has other things in it and isn't a Miyu data root, so it was left alone. If it's the data folder of Miyu 0.7, run mv … …-0.7, then miyu pkg install migrate and miyu migrate …-0.7. Otherwise set MIYU_HOME to an empty folder". The data directory of the old 0.7 version is this kind, see [Migrating from the old 0.7 version](migrate.md).
- Only the old marker `.miyu-root` is there: it is a data root left by a development build from before release, and it reports "… is an old Miyu data root, which this version doesn't read, so it was left alone. Set MIYU_HOME to an empty folder".
- The layout number in the marker is not this version's: it reports "… uses a layout this version doesn't know, so it was left alone".

Do not delete or edit this file.

## What is in each place

```text
~/.miyu/
├── .miyu-layout          marker
├── etc/                  config and credentials
│   ├── config.toml
│   ├── trust.toml
│   ├── extensions.json
│   ├── kb.toml
│   ├── private/          secrets.toml, access.json, logins.json
│   ├── removed/
│   ├── leftover/
│   └── <id>/             config of each package
├── opt/<id>/             packages you installed
├── root/                 your own things
│   ├── sessions/  personas/  presets/  prompts/  tools/
│   ├── skills/  scripts/  commands/  kb/  memory/  blobs/
│   ├── workspace/  pictures/  videos/  documents/  downloads/
│   ├── trash/  state/
│   ├── schedules.db  projects.json  avatar.<png|jpg|webp>
├── var/
│   ├── lib/              state of Miyu and of each package
│   ├── cache/            caches that can be recomputed or downloaded again
│   ├── log/              logs
│   └── tmp/              scratch space that survives restarts
├── tmp/                  short-lived scratch space
└── run/                  locks, socket location, local token
```

In the "Hand edit" column, "Yes" means you can edit those files directly; where a command is named, use that command to change it. The "Delete" column says what happens if you delete it while the core is stopped.

| Location | What it is | Hand edit | Delete | Back up |
|---|---|---|---|---|
| `etc/config.toml` | System config, see [Configuration](config.md) | Yes | Settings go back to shipped | Yes |
| `etc/private/secrets.toml` | Secrets, written by `miyu provider login` | Yes | All stored keys are gone | Yes |
| `etc/private/access.json` | Hash of the web UI access password | No | The access password is gone; set it again | Yes |
| `etc/private/logins.json` | Hashes of the tokens browsers use to sign in | No | Other devices have to sign in again | Yes |
| `etc/trust.toml` | Which project configs you have trusted | Use `miyu config trust` | Project configs have to be trusted again | Yes |
| `etc/extensions.json` | Whether extensions are on, which capabilities were approved | No | Extensions have to be turned on and approved again | Yes |
| `etc/kb.toml` | The switch for automatic recall of knowledge bases that come with packages | No | Goes back to shipped | Yes |
| `etc/removed/<id>` | Marks for shipped packages you uninstalled and packages installed by the system package manager | No | The uninstalled ones load again | Yes |
| `etc/leftover/<id>.toml` | Which package a setting left in the config when a package was uninstalled belongs to | No | Do not delete | Yes |
| `etc/<id>/` | A package's own config, kept by default when the package is uninstalled | As each package describes | That package goes back to shipped | Yes |
| `opt/<id>/` | Packages you installed, see [Packages](packages.md) | No; if you change them, `miyu pkg check` reports it | The packages are gone; install them again | Yes |
| `root/sessions/<session id>/` | A session's log, written by the core | No | The session is gone | Yes |
| `root/personas/`, `root/presets/` | Your personas and presets, see [Personas and presets](personas-presets.md) | Yes | The personas and presets are gone | Yes |
| `root/prompts/`, `root/tools/` | Overrides of prompts and tool descriptions | Yes | Goes back to the shipped wording | Yes |
| `root/skills/`, `root/scripts/`, `root/commands/` | Your skills, scripts and slash command templates, see [Extending Miyu](extending.md) | Yes | Gone | Yes |
| `root/kb/<id>/` | Knowledge bases, see [Knowledge base](knowledge.md) | Yes | The knowledge base is gone | Yes |
| `root/memory/<persona id>/` | The memory log, see [Memory](memory.md) | No, use `miyu memory` | The memory is gone | Yes |
| `root/blobs/` | Images, attachments and over-long tool output from sessions, stored by content hash | No | Images and attachments in sessions cannot be opened | Yes |
| `root/workspace/<session id>/` | A session's default workspace, where the AI puts things | Yes | The files in it are gone | Yes |
| `root/pictures/`, `videos/`, `documents/`, `downloads/` | Files the AI made or downloaded for you, created when first used | Yes | The files are gone | Yes |
| `root/trash/` | Deleted sessions and personas, kept for 7 days | No | Those sessions and personas are really gone | No |
| `root/schedules.db` | Schedules, see [Letting the AI keep working on its own](automation.md#schedules) | No, use `miyu schedule` | The schedules are gone | Yes |
| `root/projects.json` | Projects in the web UI | No | The projects are gone | Yes |
| `root/state/` | Which session each terminal window is in, and state of scripts | No | Terminal windows no longer continue their old sessions, and script state is gone | Yes |
| `root/avatar.<png\|jpg\|webp>` | Your avatar | No | The avatar is gone | Yes |
| `var/lib/journal.jsonl` | The record of changes to config, secrets and trust, and the usage of sessions that were cleared | No | The usage of cleared sessions can no longer be looked up | Yes |
| `var/lib/models/` | What was learned from use: context windows, which model in a pool is next, names providers changed | No | Do not delete | Yes |
| `var/lib/packages/` | Which packages are installed, what version, where from, the hash of every file | No | Do not delete | Yes |
| `var/lib/<id>/` | A package's state, for example the chat history of the chat platforms in `var/lib/im/` | No | That package's state is gone, and it is deleted with the package when you uninstall it | Yes |
| `var/lib/mcp/<server name>/` | The working directory of an MCP server that is a local program | As that server describes | That server's state is gone | Yes |
| `var/cache/` | Indexes of the session list, memory and knowledge bases, usage totals, model lists, the package source index and downloaded packages, script caches, each package's caches | No | Rebuilt or downloaded again as needed | No |
| `var/log/` | The core's `core.log`, the memory usage log `memory.jsonl`, each package's logs | No | The logs are gone | No |
| `var/tmp/` | Scratch space that survives restarts | No | None | No |
| `tmp/` | Short-lived scratch space: unpacking when installing packages, and each package's own space, cleared before every start | No | None | No |
| `run/` | Locks, socket location, local token (for where the socket itself is, see [Troubleshooting](troubleshooting.md#the-core-will-not-start-or-cannot-connect)) | No | If deleted while the core is running, heads cannot connect to it, see [Troubleshooting](troubleshooting.md#the-old-core-is-still-running) | No |

On Linux and macOS, the files under `etc/private/` can be read and written only by you (`0600`). On Windows, Miyu sets no separate permissions and they inherit the access control of the data root.

## Outside the data root

| What | Linux | macOS | Windows |
|---|---|---|---|
| Cache directory | `~/.cache/miyu` (under `XDG_CACHE_HOME` if that is set) | `~/Library/Caches/Miyu` | `%LOCALAPPDATA%\Miyu\cache` |
| Programs | See [Installing, upgrading and uninstalling](install.md#what-gets-installed) | Same | Same |
| Service file that starts the core at boot | `~/.config/systemd/user/miyu.service` or `~/.config/autostart/miyu.desktop` (under `XDG_CONFIG_HOME` if that is set) | `~/Library/LaunchAgents/io.github.miyu-agent.core.plist` | Task Scheduler task `Miyu`, `%USERPROFILE%\AppData\Local\Miyu\miyu-task.xml` |
| The tray's start at login | `~/.config/autostart/miyu-applet.desktop` | `~/Library/LaunchAgents/io.github.miyu-agent.miyu-applet.plist` | `Miyu` in the registry `Run` key |
| The tray's own directory | `~/.local/state/miyu-applet` | `~/Library/Application Support/miyu-applet` | `%LOCALAPPDATA%\miyu-applet` |
| Shell integration | A marked section in `~/.bashrc` or `~/.zshrc`, or `~/.config/fish/conf.d/miyu-shellhook.fish` | Same | A marked section in PowerShell's `$PROFILE` |

The cache directory is shared by the whole machine and does not follow `MIYU_HOME`. On Linux, `XDG_CACHE_HOME` only counts if it is an absolute path; on Windows it is found from the environment variable `LOCALAPPDATA`. It holds the model catalog and provider icons (`models/`), the terminal's crash records and image cache (`tui/`), and scratch space for shell integration (`shellhook/`). All of it can be deleted and is generated again when needed; if the terminal crashed and you want to report it, keep `tui/crash.log` first.

For details on these, see [Keeping it running, and servers](service.md), [Tray](heads/applet.md) and [Terminal](heads/tui.md#shell-integration). LiteMiyu, for emergencies, has its own directory, see [Rescue](rescue.md).

## Backups

What to back up is `etc/`, `opt/`, `root/` and `var/lib/`, plus the `.miyu-layout` at the top. `var/cache/`, `var/log/`, `var/tmp/`, `tmp/` and `run/` do not need a backup: indexes and usage totals are recomputed from the sessions' logs, and the model lists and package source index are fetched again.

Stop the web UI and the core before backing up, so you do not back up a half-written file:

```bash
miyu web --stop
miyu core stop
tar -czf ~/miyu-backup-$(date +%F).tar.gz -C ~ \
  --exclude=.miyu/var/cache --exclude=.miyu/var/tmp \
  --exclude=.miyu/tmp --exclude=.miyu/run \
  .miyu
```

If `MIYU_HOME` is set, replace `-C ~` with its parent directory, and `.miyu` (including the ones in `--exclude`) with its name. In Windows PowerShell, use the `tar` that comes with the system:

```powershell
miyu web --stop
miyu core stop
tar -czf "$HOME\miyu-backup.tar.gz" -C $HOME --exclude=.miyu/var/cache --exclude=.miyu/var/tmp --exclude=.miyu/tmp --exclude=.miyu/run .miyu
```

`miyu core stop` stops the core, and extensions such as chat platforms stop with it. When the backup is done, open `miyu` or the web UI and the core starts; if you have the start-at-boot service installed and want the service to manage it again, run `miyu service enable`, see [Keeping it running, and servers](service.md#making-the-service-take-over-now).

The backup contains plain-text keys (`etc/private/secrets.toml`), all conversations and memory. Encrypt it yourself before putting it anywhere else, for example `gpg -c miyu-backup-2026-11-14.tar.gz`.

To move just one or two sessions, use session export, see [Sessions](sessions.md#export-and-import).

## Restoring, moving to another machine

1. Install Miyu on the new machine, see [Installing, upgrading and uninstalling](install.md). Do not open it yet.
2. Stop the core: `miyu core stop`.
3. If a data root already exists, move it aside:

   ```bash
   mv ~/.miyu ~/.miyu.old
   ```

   ```powershell
   Rename-Item $HOME\.miyu .miyu.old
   ```

4. Unpack the backup:

   ```bash
   tar -xzf miyu-backup-2026-11-14.tar.gz -C ~
   ```

   ```powershell
   tar -xzf $HOME\miyu-backup.tar.gz -C $HOME
   ```

5. Run `miyu check` and fix what it says.
6. Open `miyu`.

Things outside the data root are not in the backup; do again on the new machine the ones you need: `miyu service enable`, the tray's "Start at Login", `miyu shellhook install`.

### Versions

Restore with the same or a newer Miyu.

- In a version where the data root layout changed, the layout number in the marker changes with it. For a data root whose layout number does not match, Miyu reports "… uses a layout this version doesn't know, so it was left alone" and changes nothing.
- If you open a data root that a newer version has written with an older version: the schedule table was created by the newer version, so the older version does not use it this time and does not touch it; everything else it can read, it reads. Do not do this.

### Moving to a different operating system

When you move from Linux to macOS or Windows, or the other way round, a few things do not carry over:

- Packages that come with a program (extensions and MCP server programs, for example `im` and `embed`) are built per system and will not run on the new system. Reinstall them one by one: `miyu pkg list` shows what is installed, and `miyu pkg install <id>` installs this system's build.
- Places written as absolute paths: a session's working directory, the directories of projects in the web UI, mounted knowledge base directories (`mount` in `kb.toml`), paths in the config (`skills.external.dirs`, the command of an MCP server). Where a path does not exist on the new machine, change it to the new location.
- The `#!` interpreter of scripts, and scripts such as `.ps1` that run on only one system.

## Cleaning up

First see where the space goes:

```bash
du -h -d 2 ~/.miyu | sort -h | tail -20
```

In PowerShell, this lists the size in MB of each directory two levels below the data root:

```powershell
Get-ChildItem $HOME\.miyu\*\* -Directory | ForEach-Object { [pscustomobject]@{ MB = [math]::Round(((Get-ChildItem $_.FullName -Recurse -File -Force -ErrorAction SilentlyContinue | Measure-Object Length -Sum).Sum) / 1MB, 1); Path = $_.FullName } } | Sort-Object MB | Select-Object -Last 20
```

For what can be deleted, run `miyu core stop` before deleting:

| What to delete | What happens | Does it clean itself |
|---|---|---|
| All of `~/.miyu/var/cache/` | Indexes and usage totals are rebuilt the next time they are needed; the first time you open the session list or search memory is a little slower; model lists and the package source index are fetched again | Script caches untouched for 30 days are cleaned when the core starts |
| Download cache of packages | None | No; run `miyu pkg clean`: it deletes package files that are not the installed version |
| Old logs under `~/.miyu/var/log/` | None | `core.log` is replaced with a new file at 10 MB, with at most 5 old ones kept; an extension's `stderr` is moved to `stderr.old` when it gets too large |
| `~/.miyu/var/tmp/` | None | Files untouched for 7 days are cleaned when the core starts |
| `~/.miyu/tmp/` | None | The unpacking space for installing packages is cleared when the core starts; each package's own space is cleared before every time that package is started |
| `~/.miyu/root/trash/` | Deleted sessions and personas are really gone | Kept for 7 days; items that are 7 days old are cleaned when the core starts |
| `~/.miyu/root/workspace/<session id>/` | Files the AI made in that session's default workspace are gone | No: deleting a session does not delete its workspace; delete it yourself |
| Cache directory (`~/.cache/miyu` and the like) | The model catalog and icons are fetched again | No |
| Chat history of chat platforms | See [Connecting chat platforms](heads/im.md#chat-records) | No; clear it on im's back-office page |

Do not delete `run/` while the core is running. `root/blobs/` does not shrink when you delete sessions, and there is no command to clean it; several sessions may share what is in it, so do not delete from it by hand.

## Several data roots on one machine

To keep work and personal use apart, use one data root for each; they do not affect each other: sessions, settings, keys, memory and installed packages are each separate, and each runs its own core.

```bash
alias miyu-work='MIYU_HOME=$HOME/miyu-work miyu'
miyu-work            # use the work one
miyu                 # use the default ~/.miyu
```

In PowerShell, write it as a function that sets this window's `MIYU_HOME` back to what it was when it finishes:

```powershell
function miyu-work { $old = $env:MIYU_HOME; $env:MIYU_HOME = Join-Path $HOME 'miyu-work'; try { miyu @args } finally { $env:MIYU_HOME = $old } }
miyu-work            # use the work one
miyu                 # use the default ~/.miyu
```

Put the `alias` or `function` line in your shell config (`~/.bashrc`, `~/.zshrc`, `$PROFILE`), and every window you open later has it.

- Two cores can be on at the same time; the command line, terminal and web UI connect to their own according to their own `MIYU_HOME`.
- Web UI: if neither has had a port written, the one opened later moves itself to a free port starting from 8301. To keep the address the same every time, set one for the second: `miyu-work config set web.port 8310`.
- Chat platforms: if both have `im` installed, the ports of the back-office page and of the QQ connection must be kept apart, see [Chat platforms](heads/im.md).
- There is one tray per data root; open the second with `--home <data root>`. The tray's "Start at Login" is also one per user, and follows the data root of the tray that last turned it on.
- The service that starts the core at boot can be installed only once per user, and follows the data root of the last `miyu service enable`. On Windows a service cannot carry `MIYU_HOME`, so only the default data root can have a service; a second data root cannot.
- The cache directory is shared by both, which causes no trouble.

## When something goes wrong

| What you see | What to do |
|---|---|
| "MIYU_HOME must be an absolute path, got …" | Write an absolute path, or one starting with `~` |
| "… has other things in it and isn't a Miyu data root, so it was left alone. …" | `MIYU_HOME` points at the wrong directory, or `.miyu-layout` was deleted. Point it at an empty directory; if it is your own data root and only the marker is missing, get `.miyu-layout` back from the backup |
| "… uses a layout this version doesn't know, so it was left alone" | The restored backup was written by a newer version; upgrade Miyu |
| After restoring, the web UI asks you to sign in again and extensions have to be turned on again | `etc/private/` and `etc/extensions.json` were not backed up; set them again as prompted |
| After changing the data root, what starts at boot is still the old one | Run `miyu service enable` again; for the tray's "Start at Login", turn it off and on again |
