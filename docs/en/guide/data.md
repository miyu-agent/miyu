# Data and backups

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page explains where Miyu keeps your sessions, settings, keys and memory, which of them need backing up and which can be deleted, and how to move to another computer or store them somewhere else.

## Location of the data root

Almost all of Miyu's data lives in one directory, called the "data root" (`~/.miyu` by default):

| System | Default location |
|---|---|
| Linux, macOS | `~/.miyu` |
| Windows | `%USERPROFILE%\.miyu` |

Installing, upgrading and uninstalling Miyu never change the data root.

### Changing the data root location

If you want to put the data root somewhere else, set the environment variable `MIYU_HOME` to point at another directory. For example:

```bash
export MIYU_HOME=/data/miyu
```

```powershell
$env:MIYU_HOME = 'D:\miyu'
```

Set this way, it applies only to the current shell window. If you want this location to be used from now on, see the table below and the notes after it.

- `MIYU_HOME` must be an absolute path; a leading `~` is replaced with your home directory. If you write a relative path, you get the error `MIYU_HOME must be an absolute path, got …`.
- Setting it to an empty value is the same as not setting it.
- If the directory does not exist, it is created automatically on first use. On Linux and macOS, the new directory is accessible only to you (`0700`); on Windows, it inherits the access control of its parent directory.

`MIYU_HOME` is read from the environment at the moment a program starts, so what counts is the environment of wherever the program was started from:

| Program | How it reads it |
|---|---|
| Command line, terminal UI, web UI, shell integration | From the environment of the shell where you run the command. If you put it in your shell's config (files such as `~/.bashrc` or `~/.zshrc` for bash and zsh, `$PROFILE` for PowerShell), every shell you open afterwards reads it; on Windows you can also set it as a user environment variable, see the notes after the table |
| Packages, scripts, MCP servers, commands the AI runs | The core passes it to them when it starts them, so they use the same one as the core |
| The service installed by `miyu service enable` | If it was set at install time, it is written into the service file. After changing the data root, run `miyu service enable` again. On Windows, the service cannot be installed while `MIYU_HOME` is set; for details, see [Keeping it running, and servers](service.md#starting-the-core-at-boot-or-login) |
| System tray | Uses the command line argument `--home <data root>`; when that argument is not given, it uses `MIYU_HOME`. `Start at Login` writes it into the startup entry, and on Windows it can carry it too; for details, see [System tray](heads/applet.md#start-at-login) |
| A pane restored by herdr | Does not keep temporary variables written in front of the command; for details, see [Terminal UI](heads/tui.md#using-it-with-herdr) |

A system tray opened from the application menu cannot see variables set in a shell config; on macOS, the same goes for `Miyu.app` opened from Finder or the Dock. The fix is to open the system tray from a terminal with the `--home` argument and then check `Start at Login`; the startup entry then records this argument, so later logins start it with this data root:

| System | Run in a terminal |
|---|---|
| Linux | `miyu-applet --home /data/miyu` |
| macOS | `/Applications/Miyu.app/Contents/MacOS/miyu-applet --home /data/miyu` (if `Miyu.app` is not in `Applications`, use its actual location instead) |

On Windows, you can set the user environment variable with `setx MIYU_HOME D:\miyu`, and programs you open afterwards will read it. For starting at boot, use the system tray's `Start at Login` rather than `miyu service`, because the service cannot be installed while `MIYU_HOME` is set.

### The marker file

At the top level of the data root there is a `.miyu-layout` file containing a single line, `This directory is a Miyu data root (layout 3).`. Miyu only treats a directory that has this marker as a data root:

- If the directory does not exist or is empty: Miyu writes the marker and treats it as a new data root.
- If the directory has other things in it but no marker: Miyu does not change a single byte of it, and reports `… has other things in it and isn't a Miyu data root, so it was left alone. If it's the data folder of Miyu 0.7, run mv … …-0.7, then miyu pkg install migrate and miyu migrate …-0.7. Otherwise set MIYU_HOME to an empty folder`. The data directory of the old 0.7 version falls into this case; for details, see [Migrating from the old 0.7 version](migrate.md).
- If only the old marker `.miyu-root` is there: this is a data root left by a development build from before the official release, and Miyu reports `… is an old Miyu data root, which this version doesn't read, so it was left alone. Set MIYU_HOME to an empty folder`.
- If the layout number in the marker is not this version's: Miyu reports `… uses a layout this version doesn't know, so it was left alone`.

Do not delete or edit this file.

## What is inside the data root

The directory structure inside the data root looks like this:

```text
~/.miyu/
├── .miyu-layout          marker
├── etc/                  config and credentials
│   ├── config.toml
│   ├── trust.toml
│   ├── extensions.json
│   ├── kb.toml
│   ├── private/          secrets.toml, access.json, logins.json
│   ├── removed/
│   ├── leftover/
│   └── <id>/             config of each package
├── opt/<id>/             packages you installed
├── root/                 your own things
│   ├── sessions/  personas/  presets/  prompts/  tools/
│   ├── skills/  scripts/  commands/  kb/  memory/  blobs/
│   ├── workspace/  pictures/  videos/  documents/  downloads/
│   ├── trash/  state/
│   ├── schedules.db  projects.json  avatar.<png|jpg|webp>
├── var/
│   ├── lib/              state of Miyu and of each package
│   ├── cache/            caches that can be recomputed or downloaded again
│   ├── log/              logs
│   └── tmp/              scratch space that survives restarts
├── tmp/                  short-lived scratch space
└── run/                  locks, socket location, local token
```

In the table below, `Yes` in the "Edit by hand" column means you can edit those files directly; where a command is named, use that command to change them. The "If deleted" column says what happens if you delete the item while the core is stopped.

| Location | Contents | Edit by hand | If deleted | Back up |
|---|---|---|---|---|
| `etc/config.toml` | System config, see [Configuration](config.md) | Yes | Settings go back to their shipped state | Yes |
| `etc/private/secrets.toml` | Secrets, written by `miyu provider login` | Yes | All stored keys are lost | Yes |
| `etc/private/access.json` | Hash of the web UI access password | No | The access password is lost and has to be set again | Yes |
| `etc/private/logins.json` | Hashes of the tokens each browser uses to sign in | No | All other devices have to sign in again | Yes |
| `etc/trust.toml` | Which project configs you have trusted | Use `miyu config trust` | Project configs have to be trusted again | Yes |
| `etc/extensions.json` | Whether each extension is on, and which capabilities were approved | No | Extensions have to be turned on and approved again | Yes |
| `etc/kb.toml` | The automatic recall switch for knowledge bases that come with packages | No | Goes back to its shipped state | Yes |
| `etc/removed/<id>` | Marks for shipped packages you uninstalled and for packages installed by the system package manager | No | The uninstalled packages are loaded again | Yes |
| `etc/leftover/<id>.toml` | Which package each setting left in the config after uninstalling a package belongs to | No | Do not delete | Yes |
| `etc/<id>/` | A package's own config, kept by default when the package is uninstalled | As each package describes | That package goes back to its shipped state | Yes |
| `opt/<id>/` | Packages you installed, see [Packages](packages.md) | No; if you change them, `miyu pkg check` reports it | The packages are lost and have to be installed again | Yes |
| `root/sessions/<session id>/` | A session's log, written by the core | No | The session is lost | Yes |
| `root/personas/`, `root/presets/` | Your personas and presets, see [Personas and presets](personas-presets.md) | Yes | The personas and presets are lost | Yes |
| `root/prompts/`, `root/tools/` | Your overrides of prompts and tool descriptions | Yes | Goes back to the shipped wording | Yes |
| `root/skills/`, `root/scripts/`, `root/commands/` | Your skills, scripts and slash command templates, see [Extending Miyu](extending.md) | Yes | All of them are lost | Yes |
| `root/kb/<id>/` | Knowledge bases, see [Knowledge base](knowledge.md) | Yes | The knowledge base is lost | Yes |
| `root/memory/<persona id>/` | The memory log, see [Memory](memory.md) | No, use `miyu memory` | The memory is lost | Yes |
| `root/blobs/` | Images, attachments and over-long tool output from sessions, stored by content hash | No | Images and attachments in sessions can no longer be opened | Yes |
| `root/workspace/<session id>/` | A session's default workspace, where the AI keeps files | Yes | The files in it are lost | Yes |
| `root/pictures/`, `videos/`, `documents/`, `downloads/` | Files the AI made or downloaded for you, created the first time they are needed | Yes | The files are lost | Yes |
| `root/trash/` | Deleted sessions and personas, kept for 7 days | No | Those sessions and personas are lost for good | No |
| `root/schedules.db` | Schedules, see [Letting the AI keep working on its own](automation.md#schedules) | No, use `miyu schedule` | The schedules are lost | Yes |
| `root/projects.json` | Projects in the web UI | No | The projects are lost | Yes |
| `root/state/` | Which session each terminal window is in, and the state of scripts | No | Terminal windows no longer continue their previous sessions, and script state is lost | Yes |
| `root/avatar.<png\|jpg\|webp>` | Your avatar | No | The avatar is lost | Yes |
| `var/lib/journal.jsonl` | The record of changes to config, secrets and trust, plus the usage of sessions that were cleared | No | The usage of cleared sessions can no longer be looked up | Yes |
| `var/lib/models/` | Information gathered through use: learned context windows, which model in a pool is next, names that providers changed | No | Do not delete | Yes |
| `var/lib/packages/` | Which packages are installed, their versions, where they came from, and the hash of every file | No | Do not delete | Yes |
| `var/lib/<id>/` | A package's state, for example the chat platforms' chat history in `var/lib/im/` | No | That package's state is lost; it is deleted along with the package when you uninstall it | Yes |
| `var/lib/mcp/<server name>/` | The working directory of an MCP server that runs as a local program | As that server describes | That server's state is lost | Yes |
| `var/cache/` | Indexes of the session list, memory and knowledge bases, usage totals, model lists, the package source index and downloaded packages, script caches, and each package's caches | No | Rebuilt or downloaded again when needed | No |
| `var/log/` | The core's `core.log`, the memory usage log `memory.jsonl`, and each package's logs | No | The logs are lost | No |
| `var/tmp/` | Scratch space kept across restarts | No | No effect | No |
| `tmp/` | Short-lived scratch space: the unpacking directory used when installing packages, and each package's own directory, cleared before every start | No | No effect | No |
| `run/` | Locks, socket location, local token (for where the socket itself is, see [Troubleshooting](troubleshooting.md#the-core-will-not-start-or-cannot-connect)) | No | If you delete it while the core is running, interfaces cannot connect to the core, see [Troubleshooting](troubleshooting.md#the-old-core-is-still-running) | No |

On Linux and macOS, the files under `etc/private/` can be read and written only by you (`0600`). On Windows, Miyu sets no separate permissions, and these files inherit the access control of the data root.

## Files outside the data root

Besides the data root, Miyu also puts files in these places:

| What | Linux | macOS | Windows |
|---|---|---|---|
| Cache directory | `~/.cache/miyu` (under `XDG_CACHE_HOME` if you have set it) | `~/Library/Caches/Miyu` | `%LOCALAPPDATA%\Miyu\cache` |
| Programs | See [Installing, upgrading and uninstalling](install.md#what-gets-installed) | Same | Same |
| Service file that starts the core at boot | `~/.config/systemd/user/miyu.service` or `~/.config/autostart/miyu.desktop` (under `XDG_CONFIG_HOME` if you have set it) | `~/Library/LaunchAgents/io.github.miyu-agent.core.plist` | Task Scheduler task `Miyu`, `%USERPROFILE%\AppData\Local\Miyu\miyu-task.xml` |
| The system tray's start at login | `~/.config/autostart/miyu-applet.desktop` | `~/Library/LaunchAgents/io.github.miyu-agent.miyu-applet.plist` | `Miyu` in the registry `Run` key |
| The system tray's own directory | `~/.local/state/miyu-applet` | `~/Library/Application Support/miyu-applet` | `%LOCALAPPDATA%\miyu-applet` |
| Shell integration | A marked section in `~/.bashrc` or `~/.zshrc`, or `~/.config/fish/conf.d/miyu-shellhook.fish` | Same | A marked section in PowerShell's `$PROFILE` |

The cache directory is shared by the whole computer and does not change with `MIYU_HOME`. On Linux, `XDG_CACHE_HOME` only takes effect if it is an absolute path; on Windows, the cache directory is found from the environment variable `LOCALAPPDATA`. The cache directory holds the model catalog and the providers' icons (`models/`), the terminal UI's crash records and image cache (`tui/`), and scratch space for shell integration (`shellhook/`). All of it can be deleted and is generated again when needed; if the terminal UI crashed and you want to report the problem, keep `tui/crash.log` first.

For details on these places, see [Keeping it running, and servers](service.md), [System tray](heads/applet.md) and [Terminal UI](heads/tui.md#shell-integration). LiteMiyu, the emergency tool, has its own separate directory; for details, see [Rescue](rescue.md).

## Backups

What you need to back up are the four directories `etc/`, `opt/`, `root/` and `var/lib/`, plus the `.miyu-layout` at the top level. `var/cache/`, `var/log/`, `var/tmp/`, `tmp/` and `run/` do not need backing up: indexes and usage totals can be recomputed from the sessions' logs, and model lists and the package source index can be downloaded again.

Before backing up, stop the web UI and the core so that you do not back up a half-written file. On Linux and macOS, run:

```bash
miyu web stop
miyu core stop
tar -czf ~/miyu-backup-$(date +%F).tar.gz -C ~ \
  --exclude=.miyu/var/cache --exclude=.miyu/var/tmp \
  --exclude=.miyu/tmp --exclude=.miyu/run \
  .miyu
```

If `MIYU_HOME` is set, replace `-C ~` with its parent directory, and `.miyu` (including the ones in `--exclude`) with its directory name. In Windows PowerShell, use the `tar` that comes with the system:

```powershell
miyu web stop
miyu core stop
tar -czf "$HOME\miyu-backup.tar.gz" -C $HOME --exclude=.miyu/var/cache --exclude=.miyu/var/tmp --exclude=.miyu/tmp --exclude=.miyu/run .miyu
```

When `miyu core stop` stops the core, extensions such as chat platforms stop with it. Once the backup is done, open `miyu` or the web UI and the core starts again; if you have the start-at-boot service installed and want the service to keep managing the core, also run `miyu service enable`; for details, see [Keeping it running, and servers](service.md#making-the-service-take-over-now).

> The backup contains plain-text keys (`etc/private/secrets.toml`), as well as all your conversations and memory. Before you put the backup anywhere else, encrypt it yourself, for example with `gpg -c miyu-backup-2026-11-14.tar.gz`.

If you only want to move one or two sessions, you can use session export; for details, see [Sessions](sessions.md#export-and-import).

## Restoring and moving to another computer

Follow these steps to restore a backup on a new computer:

1. Install Miyu on the new computer, see [Installing, upgrading and uninstalling](install.md). Do not open it after installing yet.
2. Stop the core: `miyu core stop`.
3. If the new computer already has a data root, move it aside first:

   ```bash
   mv ~/.miyu ~/.miyu.old
   ```

   ```powershell
   Rename-Item $HOME\.miyu .miyu.old
   ```

4. Unpack the backup:

   ```bash
   tar -xzf miyu-backup-2026-11-14.tar.gz -C ~
   ```

   ```powershell
   tar -xzf $HOME\miyu-backup.tar.gz -C $HOME
   ```

5. Run `miyu check` and make the changes it suggests.
6. Open `miyu`.

Things outside the data root are not in the backup; if you need them, set them up again on the new computer: `miyu service enable`, the system tray's `Start at Login`, `miyu shellhook install`.

### Version requirements

When restoring, use the same version of Miyu or a newer one.

- If a version changes the layout of the data root, the layout number in the marker changes with it. For a data root whose layout number does not match, Miyu reports `… uses a layout this version doesn't know, so it was left alone` and changes nothing.
- If you open a data root written by a newer version with an older version: because the schedule table was created by the newer version, the older version does not use it this time and does not change it; everything else it can read, it reads as usual. Do not use it this way.

### Moving to a different operating system

When you move from Linux to macOS or Windows, or the other way round, a few things cannot be carried over directly:

- Packages that come with a program (extensions and MCP server programs, for example `im` and `embed`) are built separately for each system and will not run on the new system. You need to reinstall them one by one: use `miyu pkg list` to see what is installed, then `miyu pkg install <id>` to install the build for the current system.
- Places written as absolute paths: a session's working directory, the directories of projects in the web UI, mounted knowledge base directories (`mount` in `kb.toml`), and paths in the config (`skills.external.dirs`, the command of an MCP server). If these paths do not exist on the new computer, change them to the new locations.
- The `#!` interpreter of scripts, and scripts such as `.ps1` that only run on one system.

## Freeing up space

When the data root grows large, first check where the space goes. On Linux and macOS, run:

```bash
du -h -d 2 ~/.miyu | sort -h | tail -20
```

In PowerShell, the command below lists how many MB each directory two levels below the data root takes:

```powershell
Get-ChildItem $HOME\.miyu\*\* -Directory | ForEach-Object { [pscustomobject]@{ MB = [math]::Round(((Get-ChildItem $_.FullName -Recurse -File -Force -ErrorAction SilentlyContinue | Measure-Object Length -Sum).Sum) / 1MB, 1); Path = $_.FullName } } | Sort-Object MB | Select-Object -Last 20
```

The following can be deleted; run `miyu core stop` before deleting:

| What to delete | Effect of deleting it | Is it cleaned automatically |
|---|---|---|
| All of `~/.miyu/var/cache/` | Indexes and usage totals are rebuilt the next time they are needed, so the first time you open the session list or search memory is a little slower; model lists and the package source index are downloaded again | Script caches unused for 30 days are cleaned when the core starts |
| Download cache of packages | No effect | Not automatically; run `miyu pkg clean`, which deletes package files that are not the installed version |
| Old logs under `~/.miyu/var/log/` | No effect | `core.log` switches to a new file at 10 MB, keeping at most 5 old ones; an extension's `stderr` is moved to `stderr.old` when it gets too large |
| `~/.miyu/var/tmp/` | No effect | Files unused for 7 days are cleaned when the core starts |
| `~/.miyu/tmp/` | No effect | The unpacking space for installing packages is cleared when the core starts; each package's own directory is cleared before every start of that package |
| `~/.miyu/root/trash/` | Deleted sessions and personas are lost for good | Kept for 7 days; when the core starts, items that are 7 days old are cleaned |
| `~/.miyu/root/workspace/<session id>/` | Files the AI made in that session's default workspace are lost | Not automatically: deleting a session does not delete its workspace, so you need to delete it yourself |
| Cache directory (`~/.cache/miyu` and the like) | The model catalog and icons are downloaded again | Not automatically |
| Chat history of chat platforms | See [Connecting chat platforms](heads/im.md#chat-records) | Not automatically; you can clear it on im's back-office page |

Do not delete `run/` while the core is running. `root/blobs/` does not shrink when you delete sessions, and there is no command to clean it; because several sessions may share what is in it, do not delete from it by hand.

## Using several data roots on one computer

If you want to keep work and personal use apart, you can use one data root for each, and they do not affect each other: sessions, settings, keys, memory and installed packages are all separate, and each runs its own core. In bash you can set it up like this:

```bash
alias miyu-work='MIYU_HOME=$HOME/miyu-work miyu'
miyu-work            # use the work one
miyu                 # use the default ~/.miyu
```

In PowerShell, write it as a function, which sets this window's `MIYU_HOME` back to its previous value when it finishes:

```powershell
function miyu-work { $old = $env:MIYU_HOME; $env:MIYU_HOME = Join-Path $HOME 'miyu-work'; try { miyu @args } finally { $env:MIYU_HOME = $old } }
miyu-work            # use the work one
miyu                 # use the default ~/.miyu
```

Put the `alias` or `function` line in your shell's config file (`~/.bashrc`, `~/.zshrc`, `$PROFILE`), and it will be available in every window you open later.

- Two cores can run at the same time; the command line, the terminal UI and the web UI connect to the matching one according to their own `MIYU_HOME`.
- Web UI: if neither copy has had a port set, the one opened later automatically moves to a free port starting from 8301. If you want the address to be the same every time, set a port for the second copy: `miyu-work config set web.port 8310`.
- Chat platforms: if both copies have `im` installed, the ports of the back-office page and the QQ connection must not overlap; for details, see [Chat platforms](heads/im.md).
- Each data root has its own system tray; open the second system tray with `--home <data root>`. The system tray's `Start at Login` also exists only once per user, and uses the data root of the system tray that last turned it on.
- The service that starts the core at boot can be installed only once per user, and uses the data root from the last time you ran `miyu service enable`. On Windows, because a service cannot carry `MIYU_HOME`, only the default data root can have a service installed; a second data root cannot.
- The cache directory is shared by both copies, which causes no problems.

## Common problems

| What you see | How to fix it |
|---|---|
| `MIYU_HOME must be an absolute path, got …` | Write an absolute path, or a path starting with `~` |
| `… has other things in it and isn't a Miyu data root, so it was left alone. …` | `MIYU_HOME` points at the wrong directory, or `.miyu-layout` was deleted. Point it at an empty directory; if it really is your own data root and only the marker is missing, get `.miyu-layout` back from your backup |
| `… uses a layout this version doesn't know, so it was left alone` | The restored backup was written by a newer version of Miyu; upgrade Miyu |
| After restoring, the web UI asks you to sign in again and extensions have to be turned on again | `etc/private/` and `etc/extensions.json` were not in the backup; set them up again as prompted |
| After changing the data root, what starts at boot still uses the old data root | Run `miyu service enable` again; turn the system tray's `Start at Login` off and on again |
