# Architecture

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

For developers who want to connect to Miyu or change its code: which processes and repositories Miyu is made of, which parts a message passes through from the moment you type it to the model's answer, and where the piece you want to change or connect to sits. For each protocol method see the [protocol reference](../../reference/README.en.md); for writing packages see the [author guides](../../authors/README.en.md). Chinese version: [中文](../../zh/dev/architecture.md).

## Processes

The core is a process with no interface, and it holds all the state. A head only handles display and input, and talks to the core over the protocol.

```text
     you type miyu, miyu tui    miyu ask …        browser         tray
            │                      │               │ HTTP, WebSocket /ws
         miyu-tui                  │         miyu-web serve      miyu-applet
            │                      │               │                 │
            └──────────────────────┴───────┬───────┴─────────────────┘
                              local socket (Windows: named pipe)
                                one JSON-RPC 2.0 message per line
                                           │
                                   miyu core (the core)
      ┌──────────────┬───────────────┬─────┴─────────┬────────────────┐
  extension       MCP server       miyu-sandbox      miyu-extract       miyu-embed
  stdin/stdout    stdin/stdout    wraps a command    extracts text     worker, stdin/stdout
```

| Process | Program | Started by | How it talks to the core |
|---|---|---|---|
| Core | `miyu core` (a hidden subcommand of the main program) | The first head that can't connect to a core; or the system service installed by `miyu service enable` | Waits for connections on the local socket |
| Terminal | `miyu-tui` | You type `miyu` (swapped for that UI package's program according to the config `ui.head`) or `miyu tui` | Local socket |
| Command line | Subcommands such as `miyu ask` and `miyu config` | You | Local socket |
| Web server | `miyu-web serve` | `miyu web` hands over to `miyu-web open`, which starts it | Local socket; the browser connects to its `/ws`, which it forwards to the core unchanged |
| Tray | `miyu-applet` | You, or at login | Local socket for status and notifications; to open the web UI or stop the core it calls `miyu web` and `miyu core stop` |
| Extension | The package's `bin/<program>` | The core, according to the switch; when the core exits it asks them to exit too | Stdin and stdout, the same protocol |
| MCP server | The command written in the manifest or config | The core | MCP over stdin and stdout; a server given as a URL starts no process |
| Sandbox helper | `miyu-sandbox` | The core, one for each command that must be confined | No protocol: it tightens itself according to the spec the core wrote, then turns into that command |
| Text extractor | `miyu-extract` | The core, one run per file when the knowledge base extracts text from a PDF or web page | Hands over one JSON array of strings on stdout and exits |
| Worker | The program named in a package's `[worker]`, for example `miyu-embed` | The core, started when needed and exits after sitting idle for a while | Stdin and stdout, one question at a time |
| Command added by a package | The program named in a package's `[command]` | The main program: when `miyu <name>` is not a built-in subcommand it hands over unchanged | Up to the package |

A few rules:

- One data root runs one core, enforced by the file lock `run/core.lock`. When a head can't connect, it takes `run/spawn.lock`, tries to connect once more, and only then starts `miyu core`, waiting for the core to write the `ready` line on stdout before it connects.
- A head starts the core using the main program path it was given: the terminal honors `MIYU_CORE_BIN` and `MIYU_PROGRAM`, the web UI honors `MIYU_PROGRAM`. When the main program hands over a command, and when the core starts an extension, both set `MIYU_PROGRAM` to the real location of the main program.
- The socket's actual location is written to `run/socket` in the data root, and the local token to `run/token`. A head shows the token during the handshake; an extension does its handshake over stdin and stdout and shows no credentials.
- The core exits when it has no connections, no turn running, and has been idle for `core.idle_exit` minutes; the default is `0`, which means it never exits. Workers don't count as the core being busy.
- Scripts inside a command call the session's tools through `miyu call`: before each command it runs, the tool that runs commands opens an endpoint for that one run only, and puts its address and token in `MIYU_CALL_SOCK` and `MIYU_CALL_TOKEN`.

## How a turn goes

1. The head sends `session.send`. The protocol endpoint (`miyu-endpoint`) dispatches it in `methods.rs`, and `connection/rights.rs` checks whether this connection may call it.
2. The session actor (`miyu-session`) takes it: one session is one async task, and people's commands and the executors' reports all go into its inbox and are fed to the kernel one by one.
3. The kernel (`miyu-kernel`) is a pure-logic state machine: you feed it one input and it hands back a list of actions (request the model, call a tool, append an event), and it does no I/O itself.
4. Building the request:
   - Policy snapshot (`miyu-policy`): when the session is created, the system prompt, the tool surface and a few switches are assembled from the persona and preset, and stored as a blob keyed by content hash. At the start of each turn, if the persona or preset files or a package's tools have changed, the actor swaps in a new snapshot (`actor/persona.rs` in `miyu-session`).
   - Facts: the environment (time, time zone, working directory), the permission level and the session id, which the kernel injects when they change (`facts` in `miyu-kernel`).
   - Injections at the start of a turn: memory, the knowledge base, and the text extensions hand over through hook points (`actor/injects.rs` in `miyu-session`; the path that asks extensions is in `hooks.rs` in `miyu-endpoint`).
   - Assembly (`miyu-assemble`): the stable region (tool surface, system prompt, example dialogue) comes first, then the summary of the latest compaction, then the effective history, arranged into one unified request.
5. Sending the request: routing (`route.rs` in `miyu-session`) picks the provider, key and model according to the config, and switches to a candidate on error; the driver (`miyu-drivers`) encodes the unified request into the bytes each provider's API expects; the HTTP executor (`miyu-http`) sends it and reads the stream back, handing it to the driver to decode as it reads; the kernel stitches the increments into complete content blocks. For a driver provided by an extension, the core sends `driver.call` to the extension.
6. Tool calls: before running, the call goes through the permission policy (`guard.rs` in `miyu-session`; file paths are resolved to real locations and checked against boundaries through `miyu-fs`) and the extensions' guards, and if it needs to ask the person, it waits for the head's answer. Running:
   - Built-in tools are registered in the tool catalog (`miyu-tool`); the ones that read and write files and run commands are in `miyu-basesystem`, and memory, the knowledge base, goals and schedules each have their own crate;
   - Commands under read-only get a spec written by `sandbox.rs` in `miyu-session` and run wrapped by `miyu-sandbox`;
   - An extension's tools are called by the core sending `tool.call` to the extension; an MCP server's tools are called through `miyu-mcp`.
7. Persisting: events are appended to the session log (`log.rs` in `miyu-store`), written once and synced once per batch. The command is answered and pushed to heads only after it has hit the disk.
8. Pushing to heads: `miyu-view` turns events into entries a head can draw directly, and the endpoint pushes them to connections subscribed to `view` (`view.add`, `view.update`, `view.append` and so on); connections subscribed to `events` receive the events as they are.

## Crate map

The core repository's workspace members are `crates/*` and `xtask`. The crates fall into six layers: an upper layer may depend on a lower one, and a lower one must not depend on an upper one; layers 1 and 2 are pure logic and touch no files, network, subprocesses, environment variables, threads or clocks.

| crate | What it does | Layer |
|---|---|---|
| `miyu-kernel` | Events, effective history, the unified request, the session state machine, the ports for executors to implement | 1 kernel |
| `miyu-assemble` | Default request assembly: arranges the effective history into a unified request, and also assembles the requests for compaction, review and title generation | 2 modules |
| `miyu-config` | The config manifest: each item declared once, layered merging into the final value, JSON Schema generation; reads package manifests | 2 modules |
| `miyu-drivers` | Model drivers: encoding, decoding and error classification between the unified request and each provider's API | 2 modules |
| `miyu-models` | Provider config items, profiles, how models are written, picking a key by session id, the models.dev catalog | 2 modules |
| `miyu-policy` | Policy snapshots: all the text and switches a session needs to send requests, archived by content hash | 2 modules |
| `miyu-recall` | Tokenizing for retrieval: Chinese and Japanese split into overlapping pairs, assembling FTS5 queries | 2 modules |
| `miyu-seeds` | Picks candidate theme colors from an image: shared by persona avatars and wallpapers | 2 modules |
| `miyu-view` | View projection: turns events into entries a head draws directly; exports a session to Markdown | 2 modules |
| `miyu-store` | Data root, session logs, blobs, config files, secrets, indexes and the retrieval database | 3 executors |
| `miyu-http` | HTTP executor: sends requests with the bytes the driver encoded, reads the stream back | 3 executors |
| `miyu-log` | Runtime log: one English line per entry, rotated by size | 3 executors |
| `miyu-ipc` | Local transport: sockets, named pipes, the local token, the single-instance lock, starting the core when a head can't connect | 3 executors |
| `miyu-pipe` | Windows named pipes open to the owner only, checking the process on the other end | 3 executors |
| `miyu-call` | The channel for scripts calling tools: the end that `miyu call` connects to | 3 executors |
| `miyu-tool` | The tool interface and the tool catalog | 3 executors |
| `miyu-fs` | How the file tools touch files: the boundary table, resolving to real locations, safe opening, the system trash | 3 executors |
| `miyu-basesystem` | The base system: the tools `read`, `glob`, `grep`, `write`, `edit`, `trash` and `shell` | 3 executors |
| `miyu-sandbox` | The sandbox: the spec, the `miyu-sandbox` helper, probing how far this machine can tighten | 3 executors |
| `miyu-mermaid` | Optional package `mermaid`: draws mermaid source as SVG | 3 executors |
| `miyu-net` | Optional package `net`: fetches web pages for link cards, the tool `web_fetch` | 3 executors |
| `miyu-memory` | The memory tools: `remember`, `forget`, `memory_search` | 3 executors |
| `miyu-goal` | The goal tool `goal` | 3 executors |
| `miyu-schedule` | The tools for schedules and loops: `cron_*`, `schedule_next` | 3 executors |
| `miyu-client` | The facade for heads and components: connecting to the core, finding the data root, the types in the protocol, text for people | 3 executors |
| `miyu-heap` | The process heap: limits arenas on glibc, returns memory when idle; memory accounting | 3 executors |
| `miyu-mcp` | The MCP client: speaks MCP over stdin and stdout, lists and calls tools | 3 executors |
| `miyu-knowledge` | The knowledge base tools: `kb_search`, `kb_read`, `kb_save` | 3 executors |
| `miyu-extract` | The small program `miyu-extract`: extracts the text of one PDF or web page | 3 executors |
| `miyu-source` | Package sources: packing and unpacking package files, the index, signing, listing; the program `miyu-index` | 3 executors |
| `miyu-wallpaper` | Reads the desktop wallpaper, used only inside a head's process | 3 executors |
| `miyu-session` | The session actor: connects the kernel to disk, the model and tools; routing, permissions, sandbox specs | 4 core |
| `miyu-endpoint` | The protocol endpoint: JSON-RPC on connections, the session table, supervision of extensions and MCP | 4 core |
| `miyu-core` | The core process: builds the skeleton, reads config, opens the socket, starts extensions, exits when idle | 4 core |
| `miyu-cli` | The command-line head: `miyu ask` and the other subcommands | 5 head |
| `miyu` | The main program: dispatches by subcommand | 6 main program |
| `miyu-perf` | The measuring tool: starts the release `miyu` and measures startup, memory and requests | Tool, nothing depends on it |
| `xtask` | The gate and development tools (`cargo xtask …`, see [Contributing](contributing.md)) | Tool, nothing depends on it |

The cargo features `mermaid` and `net` of `miyu-core` are on by default; turning them off gives a core without these two optional packages.

## What gets written to disk

It is all in the data root, `~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows, or the value of `MIYU_HOME` if you set it. For a full description of the directories see [Data and backups](../guide/data.md).

| What | Where | Where the format is defined |
|---|---|---|
| Sessions | `~/.miyu/root/sessions/<session id>/`: the event log, append-only, stored as JSONL in segments | `event` in `miyu-kernel`; see [Events](../../reference/events.en.md) |
| Large content | `~/.miyu/root/blobs/`, stored by content hash | `blob` in `miyu-store` |
| Config | `~/.miyu/etc/config.toml`; secrets in `~/.miyu/etc/private/secrets.toml` | Each module declares its items with `settings!` from `miyu-config`, and the core generates a JSON Schema from them at `~/.miyu/var/cache/config/config.schema.json` |
| Packages | Installed ones in `~/.miyu/opt/<id>/`, a package's state in `~/.miyu/var/lib/<id>/` | [The manifest](../../authors/manifest.en.md) |
| Indexes | The session list index is in `~/.miyu/var/cache/index/`; the usage summary and the retrieval database are SQLite too | All derived: delete them and they are rebuilt from the logs |
| Runtime | `~/.miyu/run/`: locks, the socket's location (where the socket itself lives is under [Three platforms](#three-platforms) below), the local token | `miyu-ipc` |
| Runtime log | `~/.miyu/var/log/` | `miyu-log` |

A session's state is all a projection of its event log: the session list, the view and usage are all computed from the log.

## Protocol

Heads and extensions speak the same protocol: JSON-RPC 2.0, one message per line, UTF-8, at most 1 MiB per line. The first message after connecting is `hello`, carrying the protocol version as `[lowest, highest]`. Protocol version 1 is frozen: its methods are listed in [methods-v1.txt](../../reference/methods-v1.txt), and from now on it is only added to, with nothing changed or removed; removing, renaming or changing the meaning of a method requires protocol 2. What the core sends on its own are pushes, which have no `id` and go only to connections subscribed to that stream: `view` (entries for the UI to draw and the session status), `events` (events as they are) and `config` (config changed, model list changed), plus streams for the session list, packages, extensions, schedules and so on. For every method and every kind of push see the [protocol reference](../../reference/README.en.md).

## Packages

A folder is a package, the folder name is its id, and the manifest is `package.toml`. The core looks for packages in three layers: shipped ones are in `packages/<id>/` in the resources directory, ones installed by the system package manager are in the system add-on locations, and ones you install are in `opt/<id>/` in the data root. When the same id exists in several layers, an installed one overrides a system add-on, and a system add-on overrides a shipped one. An extension declares the capabilities it needs in `[process] capabilities` in its manifest. The person approves them when installing or turning it on, and approvals are recorded in `~/.miyu/etc/extensions.json`; shipped packages count as approved, except for the two capabilities `login.page` and `provider.key`. When the core starts an extension it gives it directories such as `MIYU_APP_DIR` and `MIYU_STATE_DIR`. The extension sends `hello` first, then `provide` to register its tools; reading end of file on stdin is the request to exit, and exit code `1` means "restarting won't help". For how to write one see [Writing a Miyu package](../../authors/README.en.md), [Writing an extension](../../authors/extensions.en.md) and [The manifest](../../authors/manifest.en.md).

```text
miyu (the core)
 ├─ Cargo git dependencies, pinned to one core commit:
 │    miyu-tui, miyu-web, miyu-desktop ──────── miyu-client
 │    miyu-im, miyu-migrate ─────────────────── miyu-client plus a few core crates
 │    miyu-embed ────────────────────────────── miyu-recall
 │    miyu-render ───────────────────────────── third_party/mermaid-rs-renderer
 │    packages (miyu-rev) ───────────────────── miyu-index, miyu
 └─ heads.toml pins the miyu-tui and miyu-web commits ──── built into the bundle at release
miyu-sdk ──── miyu-ocr
Protocol only: miyu-memes, script packages, skill packages
Each package's release ──── packages/.github/workflows/pack.yml
```

- Heads and components use the core's things only through the facade `miyu-client`: what the facade has is what you can use, and a change or removal follows the rules for changing the protocol. The `http`, `tool`, `wallpaper` and `view` features of `miyu-client` are off by default; turn on only the ones you use.
- Each repository pins a different core commit, and upgrading means changing the `rev` in `Cargo.toml`.
- When the core is released, it takes the commits that `heads.toml` pins for the terminal and web repositories, builds the programs and puts them next to `miyu`, and puts the package folders in `packages/tui/` and `packages/webui/` in the resources directory.
- Package repositories all release by calling `miyu-agent/packages/.github/workflows/pack.yml@main` in `release.yml`: push a `v<version>` tag, and the template checks the manifest by the same rules as installing a package, packs it as a `.miyu` file and uploads it to the Release.

## Three platforms

The main places where the three platforms differ are below. When you add code that runs commands, touches paths or starts subprocesses, think about all three platforms. Windows differs the most: there are no Unix sockets, no `SIGTERM`, no permission bits, and the AI's commands run in PowerShell.

| | Linux | macOS (Apple silicon) | Windows |
|---|---|---|---|
| Local transport (`miyu-ipc`) | Unix socket: with `$XDG_RUNTIME_DIR` set, at `$XDG_RUNTIME_DIR/miyu-<fingerprint>/core.sock`; without it, at `~/.miyu/run/core.sock` | Unix socket `~/.miyu/run/core.sock` | Named pipe `\\.\pipe\miyu-<fingerprint>`, open to the owner only; after a head connects, the process on the other end is checked to belong to this same user (`miyu-pipe`) |
| Sandbox for read-only commands (`miyu-sandbox`) | Landlock | Seatbelt | MXC process container; with no desktop session every command is refused, exit code `125` |
| Sandbox also confines reads (`CONFINES_READS` in `miyu-sandbox`) | Yes; on machines where neither Landlock nor seccomp can control Unix sockets, other people's sessions on a chat platform don't run commands | Yes | No: commands are always refused in other people's sessions on a chat platform (groups, private chats that aren't the owner's) (`guard.rs` in `miyu-session`) |
| When the core is gone, the commands it started stop too | One watchdog per process group | One watchdog per process group | A job object |
| The shell the AI runs commands in (`shell/program.rs` in `miyu-basesystem`) | bash: looked up in `PATH`, falling back to `/bin/bash` | zsh: fixed `/bin/zsh` | PowerShell 7: first `pwsh/pwsh.exe` in the resources directory, then `pwsh.exe` in `PATH`; if neither exists, `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` (5.1) |
| Recognizing dangerous commands (`shell/hazard.rs`, with the rules in `hazard` of `miyu-policy`) | Understands bash syntax | Understands zsh syntax | Understands PowerShell and cmd syntax (`hazard/windows*`); the kind for writing directly to disk devices is not recognized |
| Signals that stop the core (`serve.rs` in `miyu-core`) | `Ctrl+C`, `SIGTERM` | `Ctrl+C`, `SIGTERM` | Only `Ctrl+C`. `miyu core stop` goes through the protocol and is the same on all three platforms |
| Keeping the core running (`miyu service enable`) | A systemd user service; without systemd, writes `~/.config/autostart/miyu.desktop` | launchd | Task Scheduler |
| Cache directory (`root.rs` in `miyu-store`, does not follow `MIYU_HOME`) | `$XDG_CACHE_HOME/miyu`, or `~/.cache/miyu` if unset | `~/Library/Caches/Miyu` | `%LOCALAPPDATA%\Miyu\cache` |
| System add-on packages (`packages/distro.rs` in `miyu-store`) | `miyu/packages/` in each entry of `$XDG_DATA_DIRS`, or `/usr/local/share:/usr/share` if unset | `share/miyu/packages/` under the Homebrew prefix, which is the parent of the directory `miyu` is in | No such layer |
| Secrets file and newly created directories (`miyu-store`) | Secrets file `0600`, directories `0700` | Secrets file `0600`, directories `0700` | No permission bits; access control is inherited from the parent |
| Heap (`miyu-heap`) | Limits arenas on glibc, returns memory when idle | The system allocator | The system allocator |

On Unix, when the socket path would be too long, it falls back to `$TMPDIR/miyu-<uid>/<fingerprint>.sock`. The fingerprint is computed from the data root, so cores of different data roots never collide.
