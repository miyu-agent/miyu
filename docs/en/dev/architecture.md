# Architecture

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page is for developers who want to connect to Miyu or change its code. It covers which processes and repositories Miyu is made of, which parts a message passes through from the moment you type it to the model's answer, and where the piece you want to change or connect to sits. For each protocol method see the [protocol reference](../reference/README.md); for writing packages see the [author guides](packages.md).

## Processes

The core is a process with no interface, and it holds all the state. A head (an interface program that connects to the core, such as the terminal UI or the web UI) only handles display and input, and talks to the core over the protocol. The processes relate to each other like this:

```text
     you type miyu, miyu tui    miyu ask …        browser         tray
            │                      │               │ HTTP, WebSocket /ws
         miyu-tui                  │         miyu-web serve      miyu-applet
            │                      │               │                 │
            └──────────────────────┴───────┬───────┴─────────────────┘
                              local socket (Windows: named pipe)
                                one JSON-RPC 2.0 message per line
                                           │
                                   miyu core (the core)
      ┌──────────────┬───────────────┬─────┴─────────┬────────────────┐
  extension       MCP server       miyu-sandbox      miyu-extract       miyu-embed
  stdin/stdout    stdin/stdout    wraps a command    extracts text     worker, stdin/stdout
```

| Process | Program | Started by | How it talks to the core |
|---|---|---|---|
| Core | `miyu core` (a hidden subcommand of the main program) | The first head that cannot connect to a core, or the system service installed by `miyu service enable` | Waits for connections on the local socket |
| Terminal | `miyu-tui` | Started when you run `miyu` (swapped for the program of the UI package named in the config `ui.head`) or `miyu tui` | Local socket |
| Command line | Subcommands such as `miyu ask` and `miyu config` | You | Local socket |
| Web server | `miyu-web serve` | `miyu web` hands the command over to `miyu-web open`, which starts it | Local socket; the browser connects to its `/ws`, and it forwards the messages to the core unchanged |
| Tray | `miyu-applet` | You start it by hand, or it starts automatically at login | Uses the local socket to read status and receive notifications; to open the web UI it calls `miyu web`; to stop, it first calls `miyu web stop` and then `miyu core stop` |
| Extension | The package's `bin/<program>` | The core starts it according to its switch; when the core exits, it asks the extensions to exit too | Stdin and stdout, using the same protocol |
| MCP server | The command written in the manifest or config | The core | Speaks MCP over stdin and stdout; a server given as a URL starts no process |
| Sandbox helper | `miyu-sandbox` | The core, one for each command that must be confined | Uses no protocol: it first tightens its own permissions according to the spec the core wrote, then replaces itself with that command |
| Text extractor | `miyu-extract` | The core, one run per file when the knowledge base extracts the text of a PDF or web page | Hands over one JSON array of strings on stdout, then exits |
| Worker | The program named in a package's `[worker]`, for example `miyu-embed` | The core starts it when needed, and it exits by itself after sitting idle for a while | Stdin and stdout, one question and one answer at a time |
| Command added by a package | The program named in a package's `[command]` | The main program: when `miyu <name>` is not a built-in subcommand, it hands the command over unchanged | Up to the package |

The processes follow a few rules:

- One data root runs only one core, which the file lock `run/core.lock` enforces. When a head cannot connect to the core, it first takes `run/spawn.lock` and tries to connect once more; only if that still fails does it start `miyu core`, and it waits for the core to write the `ready` line on stdout before it connects.
- When a head starts the core, it uses the main program path it was given: the terminal honors `MIYU_CORE_BIN` and `MIYU_PROGRAM`, and the web UI honors `MIYU_PROGRAM`. When the main program hands over a command, and when the core starts an extension, both set `MIYU_PROGRAM` to the real location of the main program.
- The socket's actual location is written to `run/socket` in the data root, and the local token to `run/token`. A head must show the token during the handshake; an extension does its handshake over stdin and stdout and does not need to show any credentials.
- The core exits when it has no connections, no turn running, and has been idle for `core.idle_exit` minutes; the default is `0`, which means it never exits. A running worker does not count as the core being busy.
- Scripts inside a command call the session's tools through `miyu call`: before each command it starts, the tool that runs commands opens an endpoint for that one run only, and puts the endpoint's address and token in `MIYU_CALL_SOCK` and `MIYU_CALL_TOKEN`.

## The flow of a turn

From the moment a message is sent until the answer appears in the interface, it goes through the following steps:

1. The head sends `session.send`. The protocol endpoint (`miyu-endpoint`) dispatches the request in `methods.rs`, and `connection/rights.rs` checks whether this connection is allowed to call it.
2. The session actor (`miyu-session`) receives the request. Each session is one async task: people's commands and the executors' reports all go into its inbox, and are fed to the kernel one by one.
3. The kernel (`miyu-kernel`) is a pure-logic state machine: you feed it one input, it hands back a list of actions (request the model, call a tool, append an event), and it does no I/O itself.
4. Building the request:
   - Policy snapshot (`miyu-policy`): when the session is created, the system prompt, the tool surface and a few switches are assembled from the persona and preset, and stored as a blob keyed by content hash. At the start of each turn, if the persona or preset files or a package's tools have changed, the actor swaps in a new snapshot (`actor/persona.rs` in `miyu-session`).
   - Facts: the environment (time, time zone, working directory), the permission level and the session id, which the kernel injects whenever they change (`facts` in `miyu-kernel`).
   - Injections at the start of a turn: memory, the knowledge base, and the text that extensions hand over through hook points (`actor/injects.rs` in `miyu-session`; the path that asks extensions is in `hooks.rs` in `miyu-endpoint`).
   - Assembly (`miyu-assemble`): the stable region (tool surface, system prompt, example dialogue) comes first, then the summary from the latest compaction, then the effective history, all arranged into one unified request.
5. Sending the request: routing (`route.rs` in `miyu-session`) picks the provider, key and model according to the config, and switches to a candidate on error; the driver (`miyu-drivers`) encodes the unified request into the bytes each provider's API expects; the HTTP executor (`miyu-http`) sends the request and reads the response back as a stream, handing it to the driver to decode as it reads; the kernel then stitches the increments into complete content blocks. If the driver is provided by an extension, the core sends `driver.call` to the extension.
6. Tool calls: before a call runs, it goes through the permission policy (`guard.rs` in `miyu-session`; file paths are resolved to real locations and checked against boundaries through `miyu-fs`) and the extensions' guards, and if the person must be asked, it waits for the head's answer. When it runs:
   - Built-in tools are registered in the tool catalog (`miyu-tool`); the tools that read and write files and run commands are in `miyu-basesystem`, and memory, the knowledge base, goals and schedules each have their own crate;
   - For commands in read-only mode, `sandbox.rs` in `miyu-session` writes a spec, and the command runs wrapped by `miyu-sandbox`;
   - An extension's tools are called by the core sending `tool.call` to the extension; an MCP server's tools are called through `miyu-mcp`.
7. Writing to disk: events are appended to the session log (`log.rs` in `miyu-store`), with one write and one sync per batch. Only after the events are on disk does the core answer the command and push it to heads.
8. Pushing to heads: `miyu-view` turns events into entries a head can draw directly, and the endpoint pushes them to connections subscribed to `view` (`view.add`, `view.update`, `view.append` and so on); connections subscribed to `events` receive the events as they are.

## Crate map

The core repository's workspace members are `crates/*` and `xtask`. The crates fall into six layers: an upper layer may depend on a lower one, and a lower layer must not depend on an upper one. Layers 1 and 2 are pure logic and touch no files, network, subprocesses, environment variables, threads or clocks.

| crate | What it does | Layer |
|---|---|---|
| `miyu-kernel` | Events, the effective history, the unified request, the session state machine, and the ports for executors to implement | 1 kernel |
| `miyu-assemble` | Default request assembly: arranges the effective history into a unified request, and also assembles the requests for compaction, review and title generation | 2 modules |
| `miyu-config` | The config manifest: declares each item once, merges the layers into the final value, generates the JSON Schema; reads package manifests | 2 modules |
| `miyu-drivers` | Model drivers: encoding, decoding and error classification between the unified request and each provider's API | 2 modules |
| `miyu-models` | Provider config items, profiles, how models are written, picking a key by session id, and the models.dev catalog | 2 modules |
| `miyu-policy` | Policy snapshots: all the text and switches a session needs to send requests, archived by content hash | 2 modules |
| `miyu-recall` | Tokenizing for retrieval: splits Chinese and Japanese into overlapping pairs of characters (bigrams), and assembles FTS5 queries | 2 modules |
| `miyu-seeds` | Picks candidate theme colors from an image, shared by persona avatars and wallpapers | 2 modules |
| `miyu-view` | View projection: turns events into entries a head can draw directly; exports a session to Markdown | 2 modules |
| `miyu-store` | The data root, session logs, blobs, config files, secrets, indexes and the retrieval database | 3 executors |
| `miyu-http` | HTTP executor: sends requests with the bytes the driver encoded, and reads the response back as a stream | 3 executors |
| `miyu-log` | Runtime log: one English line per entry, rotated by size | 3 executors |
| `miyu-ipc` | Local transport: sockets, named pipes, the local token, the single-instance lock, and starting the core when a head cannot connect | 3 executors |
| `miyu-pipe` | Keeps Windows named pipes open to the owner only, and checks the process on the other end | 3 executors |
| `miyu-call` | The channel for scripts to call tools: the end that `miyu call` connects to | 3 executors |
| `miyu-tool` | The tool interface and the tool catalog | 3 executors |
| `miyu-fs` | How the file tools touch files: the boundary table, resolving to real locations, safe opening, the system trash | 3 executors |
| `miyu-basesystem` | The base system: the tools `read`, `glob`, `grep`, `write`, `edit`, `trash` and `shell` | 3 executors |
| `miyu-sandbox` | The sandbox: the spec, the `miyu-sandbox` helper, and probing how far this machine can tighten | 3 executors |
| `miyu-mermaid` | Optional package `mermaid`: draws mermaid source as SVG | 3 executors |
| `miyu-net` | Optional package `net`: fetches web pages to make link cards, and the tool `web_fetch` | 3 executors |

| `miyu-mcp` | The MCP client: speaks MCP over stdin and stdout, lists tools and calls tools | 3 executors |

| `miyu-endpoint` | The protocol endpoint: JSON-RPC on connections, the session table, and supervision of extensions and MCP | 4 core |
| `miyu-core` | The core process: builds the skeleton, reads the config, opens the socket, starts extensions, exits when idle | 4 core |
| `miyu-cli` | The command-line head: `miyu ask` and the other subcommands | 5 head |
| `miyu` | The main program: dispatches by subcommand | 6 main program |

The cargo features `mermaid` and `net` of `miyu-core` are on by default; turning them off gives you a core without these two optional packages.

## Data written to disk

All of it is in the data root, which is `~/.miyu` by default and `%USERPROFILE%\.miyu` on Windows; if you set `MIYU_HOME`, it is the directory that variable points to. For a full description of the directories see [Data and backups](../guide/data.md).

| What | Where | Where the format is defined |
|---|---|---|
| Sessions | `~/.miyu/root/sessions/<session id>/`: the event log, append-only, stored as JSONL in segments | `event` in `miyu-kernel`; see [Events](../reference/events.md) |
| Large content | `~/.miyu/root/blobs/`, stored by content hash | `blob` in `miyu-store` |
| Config | `~/.miyu/etc/config.toml`; secrets are in `~/.miyu/etc/private/secrets.toml` | Each module declares its config items with `settings!` from `miyu-config`, and the core generates a JSON Schema from them and writes it to `~/.miyu/var/cache/config/config.schema.json` |
| Packages | Installed packages are in `~/.miyu/opt/<id>/`, and a package's state is in `~/.miyu/var/lib/<id>/` | [The manifest](manifest.md) |
| Indexes | The session list index is in `~/.miyu/var/cache/index/`; the usage summary and the retrieval database are SQLite too | All derived: if you delete them, they are rebuilt from the logs |
| Runtime | `~/.miyu/run/`: locks, the socket's location (where the socket itself lives is under [Three platforms](#three-platforms) below), the local token | `miyu-ipc` |
| Runtime log | `~/.miyu/var/log/` | `miyu-log` |

A session's state is entirely a projection of its event log: the session list, the view and usage are all computed from the log.

## Protocol

Heads and extensions use the same protocol: JSON-RPC 2.0, one message per line, UTF-8, at most 1 MiB per line. The first message after connecting is `hello`, which carries the protocol version as `[lowest, highest]`. Protocol version 1 is frozen: its methods are listed in [methods-v1.txt](../../../internal/blueprint/methods-v1.txt), and from now on methods are only added to it, never changed or removed; removing a method, renaming it or changing its meaning requires moving to protocol 2. Messages the core sends on its own are called pushes. A push has no `id` and goes only to connections subscribed to that stream: `view` (entries for the UI to draw, and the session status), `events` (events as they are) and `config` (the config changed, the model list changed), plus streams for the session list, packages, extensions, schedules and so on. For every method and every kind of push see the [protocol reference](../reference/README.md).

## Packages

A folder is a package: the folder name is the package's id, and the manifest is `package.toml`. The core looks for packages in three layers: shipped packages are in `packages/<id>/` in the resources directory, packages installed by the system package manager are in the system add-on locations, and packages you install yourself are in `opt/<id>/` in the data root. When the same id exists in several layers, the one you installed overrides the system add-on, and the system add-on overrides the shipped one. An extension declares the capabilities it needs in `[process] capabilities` in its manifest, and the person approves them when installing or turning on the extension; approvals are recorded in `~/.miyu/etc/extensions.json`. Shipped packages count as approved, except for the two capabilities `login.page` and `provider.key`. When the core starts an extension, it gives the extension directories such as `MIYU_APP_DIR` and `MIYU_STATE_DIR`; the extension's first message is `hello`, and it then sends `provide` to register its tools. Reaching end of file on stdin means the core is asking the extension to exit, and exit code `1` means "restarting won't help". For how to write a package see [Writing a Miyu package](packages.md), [Writing an extension](extensions.md) and [The manifest](manifest.md).

## Repositories

Miyu's code is spread across several repositories under the `miyu-agent` organization:

| Repository | What it is | How it uses the core |
|---|---|---|
| `miyu` | The core, the main program `miyu`, the command line, the protocol reference and the author guides | — |
| `miyu-tui` | The terminal; the program is `miyu-tui` and the package id is `tui` | Cargo git dependency on `miyu-client` |
| `miyu-web` | The web server `miyu-web` and the pages; the package id is `webui` | Cargo git dependency on `miyu-client` and `miyu-ipc` |
| `miyu-desktop` | The tray `miyu-applet`; its installer bundles the core and the web UI | Cargo git dependency on `miyu-client`; the installer takes the core and web commits from `pins.toml` |
| `miyu-im` | The chat platform bridge; the package id is `im`, and it is an extension | Cargo git dependency on `miyu-client` and a few kernel and config crates |
| `miyu-migrate` | Migrates data from older versions; the package id is `migrate`, and it adds the command `miyu migrate` | Cargo git dependency on `miyu-client`, `miyu-kernel` and `miyu-store`, and calls the protocol at runtime |
| `miyu-embed` | The built-in semantic model, worker package `embed` | Cargo git dependency on `miyu-recall` |
| `miyu-render` | Draws Markdown as images, extension package `render` | Cargo git dependency on `mermaid-rs-renderer` in the core repository's `third_party/` |
| `miyu-ocr` | Recognizes text in images locally, extension package `ocr` | Through `miyu-sdk` |
| `miyu-memes` | Sticker packs, extension package `memes` | Protocol only |
| `miyu-sdk` | Development kits for writing extensions: `miyu_ext.py` for Python, `miyu-ext` for Rust | Protocol only |
| `miyu-package-template` | The template repository for packages | — |
| `packages` | The official package source: listing, signing, indexing, and the packing workflow `pack.yml` | The file `miyu-rev` holds one core commit, and the package source builds `miyu-index` from it for listing and `miyu` for packing |
| `litemiyu` | A single-process lightweight harness; `miyu rescue` starts it in rescue mode | No code dependency |
| `miyu-scripts-*`, `miyu-skills-*` | Each repository is one script package or skill package; the list is in `official.toml` in `packages` | Just files |

The dependencies between these repositories:

```text
miyu (the core)
 ├─ Cargo git dependencies, pinned to one core commit:
 │    miyu-tui, miyu-web, miyu-desktop ──────── miyu-client
 │    miyu-im, miyu-migrate ─────────────────── miyu-client plus a few core crates
 │    miyu-embed ────────────────────────────── miyu-recall
 │    miyu-render ───────────────────────────── third_party/mermaid-rs-renderer
 │    packages (miyu-rev) ───────────────────── miyu-index, miyu
 └─ heads.toml pins the miyu-tui and miyu-web commits ──── built into the bundle at release
miyu-sdk ──── miyu-ocr
Protocol only: miyu-memes, script packages, skill packages
Each package's release ──── packages/.github/workflows/pack.yml
```

- Heads and components use the core's code only through the facade `miyu-client`: what the facade offers is what you can use, and changing or removing anything on it follows the rules for changing the protocol. The `http`, `tool`, `wallpaper` and `view` features of `miyu-client` are off by default; turn on only the ones you use.
- Each repository pins a different core commit, and upgrading means changing the `rev` in `Cargo.toml`.
- When the core is released, it takes the commits that `heads.toml` pins for the terminal and web repositories, puts the built programs next to `miyu`, and puts the package folders in `packages/tui/` and `packages/webui/` in the resources directory.
- Package repositories all release by calling `miyu-agent/packages/.github/workflows/pack.yml@main` in `release.yml`: after you push a `v<version>` tag, the template checks the manifest by the same rules as installing a package, packs it as a `.miyu` file, and uploads it to the Release.

## Three platforms

The main places where the three platforms differ are listed below. When you add code that runs commands, touches paths or starts subprocesses, you have to consider all three platforms. Windows differs the most: it has no Unix sockets, no `SIGTERM` and no permission bits, and the AI's commands run in PowerShell.

| | Linux | macOS (Apple silicon) | Windows |
|---|---|---|---|
| Local transport (`miyu-ipc`) | Unix socket: with `$XDG_RUNTIME_DIR` set, at `$XDG_RUNTIME_DIR/miyu-<fingerprint>/core.sock`; without it, at `~/.miyu/run/core.sock` | Unix socket `~/.miyu/run/core.sock` | Named pipe `\\.\pipe\miyu-<fingerprint>`, open to the owner only; after a head connects, it checks that the process on the other end belongs to the same user (`miyu-pipe`) |
| Sandbox for read-only commands (`miyu-sandbox`) | Landlock | Seatbelt | MXC process container; with no desktop session, every command is refused with exit code `125` |
| Whether the sandbox also confines reads (`CONFINES_READS` in `miyu-sandbox`) | Yes; on machines where neither Landlock nor seccomp can control Unix sockets, other people's sessions on a chat platform do not run commands | Yes | No: in other people's sessions on a chat platform (group chats, and private chats that are not the owner's), commands are always refused (`guard.rs` in `miyu-session`) |
| After the core exits, the commands it started stop too | One watchdog per process group | One watchdog per process group | A job object |
| The shell the AI runs commands in (`shell/program.rs` in `miyu-basesystem`) | bash: looked up in `PATH`, falling back to `/bin/bash` if not found | zsh: always `/bin/zsh` | PowerShell 7: first `pwsh/pwsh.exe` in the resources directory, then `pwsh.exe` in `PATH`; if neither exists, `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` (5.1) |
| Recognizing dangerous commands (`shell/hazard.rs`, with the rules in `hazard` of `miyu-policy`) | Recognizes bash syntax | Recognizes zsh syntax | Recognizes PowerShell and cmd syntax (`hazard/windows*`); the kind that writes directly to disk devices is not recognized |
| Signals that stop the core (`serve.rs` in `miyu-core`) | `Ctrl+C`, `SIGTERM` | `Ctrl+C`, `SIGTERM` | Only `Ctrl+C`. `miyu core stop` stops the core through the protocol, the same way on all three platforms |
| Keeping the core running (`miyu service enable`) | A systemd user service; without systemd, it writes `~/.config/autostart/miyu.desktop` | launchd | Task Scheduler |
| Cache directory (`root.rs` in `miyu-store`, does not change with `MIYU_HOME`) | `$XDG_CACHE_HOME/miyu`, or `~/.cache/miyu` if it is not set | `~/Library/Caches/Miyu` | `%LOCALAPPDATA%\Miyu\cache` |
| System add-on packages (`packages/distro.rs` in `miyu-store`) | `miyu/packages/` under each entry of `$XDG_DATA_DIRS`, or under `/usr/local/share:/usr/share` if it is not set | `share/miyu/packages/` under the Homebrew prefix, which is the parent of the directory `miyu` is in | No such layer |
| Secrets file and newly created directories (`miyu-store`) | Secrets file `0600`, directories `0700` | Secrets file `0600`, directories `0700` | No permission bits are set; access control is inherited from the parent |
| Heap (`miyu-heap`) | Limits arenas on glibc and returns memory when idle | The system allocator | The system allocator |

On Unix, when the socket path would be too long, it falls back to `$TMPDIR/miyu-<uid>/<fingerprint>.sock`. The fingerprint is computed from the data root, so the cores of different data roots never collide.
