# The manifest `package.toml`

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page explains how to write a package manifest, one table and one field at a time. A manifest accepts only the tables and keys listed below; an unknown table or key is an error (`miyu pkg install` and `miyu check` both tell you which line is wrong and where).

**Text for people** (`name`, `summary`, `about`, a setting's `name` and `description`…) is written in the "language to sentence" form: `{ en = "Hello", zh = "打招呼" }`. Only `zh`, `en` and `ja` are accepted; the UI picks the person's language, and when that language is missing it falls back to `en`, then `zh`, then `ja`.

**The kind of package** is not written anywhere; Miyu works it out from the tables the manifest contains: a package with `[process]` is an extension; a package with no program but with `[[mcp]]` is an MCP server package; a package with `[mascot]` is a mascot package, and one with `[theme]` is a theme package (both are covered at the end of this page); a package with only `[package]` carries only skills, scripts, command templates, knowledge bases, personas and presets, which by convention sit in the package folder's `skills/`, `scripts/`, `commands/`, `kb/`, `personas/` and `presets/` and are not written in the manifest (see [Things that work as files](scripts-skills.md)). There are also UI, built-in and worker packages; Miyu uses those kinds itself, so this page does not cover them.

## A complete extension manifest

```toml
[package]
version = "0.1.0"                                   # semver; optional for installing, required for packing and publishing to a package source; other packages' version floors are compared against it
protocol = [1, 1]                                   # required for extensions: the protocol major versions it can use, [lowest, highest]; only 1 exists now
name = { en = "Hello", zh = "打招呼" }
summary = { en = "Greets people by name", zh = "照名字打招呼" }   # optional
author = "Alice <alice@example.com>"               # the author, optional
upstream = "https://github.com/alice/hello"         # the source repository, optional
license = "MIT"                                     # the license; an SPDX expression is recommended; optional
icon = "hand"                                       # a Lucide icon name, optional
logo = "art/logo.png"                               # a picture shipped in the package, optional
needs = ["images"]                                  # optional: where images can't be shown (voice), the whole package counts as off
targets = ["linux-x86_64", "macos-aarch64"]         # optional: when it carries native programs, the systems they run on
systems = ["linux", "macos"]                        # optional: the only systems it supports; leave it out to support all of them

[command]                                           # required for extensions
name = "hello"                                      # when someone runs `miyu hello …`, the core hands the arguments to your program
program = "miyu-hello"                              # the program name under bin/, without a path
about = { en = "Hello extension", zh = "打招呼扩展" }

[process]                                           # a package with this table is an extension
args = ["serve"]                                    # the arguments the core starts the program with
start = "manual"                                    # manual: started when switched on (default); always: started as soon as the core starts
capabilities = ["tools", "widgets", "commands"]     # the capabilities it needs, see "Capabilities" below; [[widget]] needs widgets, [[slash]] needs commands

[check]
args = ["check"]                                    # when you run `miyu check`, the core runs <program> check

[settings.greeting]                                 # a setting; its key is hello.greeting
type = "text"
max = 40
default = "Hello"
layers = ["system"]
applies = "now"
name = { en = "Greeting", zh = "问候语" }

[features.greet]                                    # one switch in presets
name = { en = "Greeting", zh = "打招呼" }
tools = ["hello_greet"]

[page]
dir = "page"                                        # the package page: the folder needs an index.html

[tray]
name = { en = "Open Hello", zh = "打开打招呼" }      # a line in the tray menu; clicking it opens the page above

[export]
provides = ["hello"]                                # a name you provide on the bus: other packages call you by this name, not by your package id
methods = ["hello.greet"]                           # the methods other packages can call under that name: <name>.<method>

[[slash]]
name = "hi"
summary = { en = "Say hi", zh = "打个招呼" }

[[widget]]
id = "status"
place = "status"
```


## The format is frozen

The tables and fields on this page are stable: from now on they are only added to, never changed or removed, so a manifest you have already written can still be read by newer versions of Miyu. New fields and tables state the version they first appeared in; if you use one, you need to put the lowest version you require in `[package] miyu`, and an older Miyu that reads such a manifest will say it needs updating. Unknown tables and fields are always errors, so write nothing that is not on this page.
## `[package]`

| Field | Notes |
|---|---|
| `name` | Required. It is the name shown to people. |
| `protocol` | Required for packages with a program. It is written as `[lowest, highest]`; only `1` exists now. |
| `version` | The package version, written in semver (`1.2.0`, `1.2.0-rc.1`). It is optional for installing, but `miyu pkg pack` and package sources need it, so a package without one cannot be packed. Version floors that other packages set on yours are compared against it, and package sources use it to tell whether there is a new release. |
| `summary` | A one-sentence description. |
| `prefix` | The prefix used by your settings keys and recorded event kinds. It starts with a lowercase letter, uses only lowercase letters, digits, `-` and `_`, is at most 32 characters (shorter than an id's 64), and must not be a reserved Windows name such as `con` or `nul`; when it is left out, the package id is used, and the 32-character limit does not apply then (an id can be up to 64 characters). If it clashes with another package's prefix (the id for a package that has none), the package cannot be installed. A package with a long id can use it to keep keys short: for example, with the id `qq-bridge` and `prefix = "qq"`, the settings keys are `qq.*` and the recorded events are `ext.qq.*`. |
| `author` | The author: a person or organization name, which may include an email address. It must be one line of at most 100 characters, and it is shown on the package info page. |
| `upstream` | Upstream, that is, the package's source repository. It starts with `https://`, contains no whitespace and is at most 300 characters, and it is shown on the package info page. |
| `license` | The license; writing it is recommended. Use the [SPDX](https://spdx.org/licenses/) form, for example `MIT`, `CC-BY-SA-4.0` or `MIT OR Apache-2.0`. It must be one line of at most 100 characters. The core does not check that it is valid SPDX and shows it to people as written (on the package info page, in the `License` line of `miyu pkg info`, and in package sources). A package without it still installs and publishes; people who see it just can't tell how they may use it. |
| `icon` | A Lucide icon name. Not every UI recognizes every Lucide name: the terminal UI recognizes only the names in its mapping table and draws the generic tool icon (a wrench) for the rest. |
| `logo` | A picture shipped in the package, written as a relative path inside the package folder, in `.png` or `.webp`. It may be at most 256 KiB and 512 pixels on each side; when packing, `miyu pkg pack` shrinks a larger picture to fit, keeping its format (the original in the folder is left unchanged). If the file is missing, is not a picture or is over the limits, the package counts as having no logo: it still installs, and `miyu check` gives a warning. The UI draws the logo first and falls back to `icon` when there is none. |
| `needs` | What a place must have for the package to be useful. Only `images` is accepted for now (in sessions that can't show images, the whole package counts as off). |
| `miyu` | The lowest Miyu version it needs: three numbers, such as `"2026.11.0"` (year.month.release within that month); a release candidate adds `-rc.N` (for example `"2026.11.0-rc.2.4"`, which is older than the release with the same number). Write it when you use newly added fields or methods; an older Miyu then says it needs updating instead of reporting keys it doesn't understand. When a Miyu is too old to even compare this field, it adds `This package may need a newer Miyu` after reporting an unknown table or key. |
| `groups` | Only for packages that ship with Miyu: the groups the package belongs to (for example `["basesystem"]`). A preset that names a group switches the packages in it. Other packages that write it get an error. |
| `targets` | The systems the package can be installed on: `linux-x86_64`, `linux-aarch64`, `macos-aarch64`, `windows-x86_64`. Leaving it out means it installs on any system; once it is written, other systems refuse to install it, and `miyu pkg pack --target` makes one package file per system. |
| `systems` | The systems the package supports: `linux`, `macos`, `windows`, with no repeats. Leaving it out means every system is supported. It is not the same as `targets`: `targets` is for packages carrying native programs, with one package file per system, while `systems` says which systems you support, and packages without programs (scripts, extensions) can write it too (for example `["linux", "macos"]` when you haven't done Windows support). When both are written, the system of every entry in `targets` must be in `systems`. When `systems` is left out, the package source works out support from `targets`. On other systems, the package source list hides the package by default (it is listed only after you turn on `Packages for other systems` in settings, and is then marked `Not supported on this system`), and installing it is refused. |

## `[command]`

Extensions and UIs need this table. `name`: when a person runs `miyu <name> …` in a terminal, the core hands the rest of the arguments to your program as-is and uses your program's exit code (`miyu help <name>` becomes `--help`; a bare `miyu <name> --version` or `-V` is not handed to you, and Miyu prints `miyu <name> <[package] version>` itself). The name starts with a lowercase letter, uses only lowercase letters, digits and `-`, and is at most 32 characters; when it clashes with a built-in subcommand (`ask`, `config`, `pkg`, `web` and so on), the built-in one wins. `program`: the program name under `bin/`; on Windows the core looks for `<name>.exe`. `about`: a one-sentence description. `args`: optional; when the arguments are handed over, these are put before the ones the person typed. A package that adds several subcommands writes several `[[command]]` sections, each written as above; the first section's `program` is the package's program (the one an extension starts).

So besides arguments meant for the core, such as `serve`, your program should also handle the arguments people type.

## `[process]`

A package with this table is an extension, and it also needs `[command]`.

| Field | Notes |
|---|---|
| `args` | The arguments the core starts the program with. |
| `start` | `manual`: started only when switched on (default); `always`: started as soon as the core starts. |
| `capabilities` | The capabilities it needs, described below. |

**Capabilities**: only the following twenty-three are accepted. The install screen lists each capability your package asks for (Miyu supplies the name and the one-sentence description; a package can't write its own), and the person approves them by answering yes. After an upgrade, the upgrade screen lists only the newly requested ones; approvals for capabilities the manifest no longer asks for are dropped, and must be approved again if they come back later. For packages installed from a local folder or a package file (including reinstalling while developing), earlier approvals are not kept, and each install asks for approval again. For community packages that screen also shows `this is a community package. It has not been reviewed and may be risky`, and for packages installed from a local file it shows `this package comes from a local file. It has not been reviewed and may be risky`. **Declare honestly**: when a capability is not declared, calling the matching method returns `needs_approval`.

| Capability | Allows |
|---|---|
| `tools` | Registering tools in the tool catalog. |
| `tools.commands` | Registered tools run commands (`runs_commands` in the spec): those commands can use `miyu call` to call the AI's tools as the session, see [Writing an extension](extensions.md). |
| `commands` | Providing slash commands (`[[slash]]`). |
| `search` | Acting as a search provider (`[[search]]`). |
| `model.driver` | Providing a model driver (`[[driver]]`): when its models are used, the whole conversation sent to the model goes through it. This capability does not include network access; if the program needs the network itself, declare `network` as well. |
| `provider.key` | Getting the key of one model provider the owner has already set up on the models side (`[provider_key]`). Packages that ship with Miyu also need the person's approval for it. |
| `widgets` | Showing its own content in the UI (`[[widget]]`). |
| `context.inject` | Adding a few lines to the AI's context at the start of a turn. |
| `context.system` | Putting a section at the end of the system prompt. |
| `packages.call` | Calling methods that other packages export, over the bus (`bus.call`). |
| `act_for_external` | Speaking for people on a chat platform; only for platform bridges. |
| `login.page` | Getting sign-in tickets for pages opened on this computer (`login.ticket {"via": "page"}`); a ticket can only be turned into a device token over a connection from this machine. Packages that ship with Miyu also need the person's approval for it. Only ask for tickets for pages you have verified come from this machine; pages from other machines always sign in with the access password, see the "Signing in pages on this machine" section of [the extensions reference](../reference/extensions.md). |
| `sessions.drive` | Driving sessions: creating sessions, sending messages, interrupting, reverting, compacting, forking and sending slash commands. |
| `events.read` | Reading sessions: subscribing to events, reading history and reading background command output; receiving notices after tool calls (`[after]`). |
| `events.write` | Recording your own events in a session. |
| `memory.write` | Writing memories and knowledge bases. |
| `fs.read`, `network` | Reading files and fetching links through the core. |
| `fs.write` | Writing given paths. Extensions do not run in a sandbox now, so files your program writes itself do not go through this capability; once extensions are put in a sandbox, writes will be let through according to it. |
| `audio.record` | Recording from this computer's microphone (for speech recognition and voice assistants). |
| `audio.play` | Playing sound through this computer's speakers or headphones (for reading aloud and voice assistants). |
| `tool.guard` | Deciding, before a tool call runs, whether to allow it, deny it or ask the person (`[guard]`). |
| `tool.rewrite` | Rewriting a tool's result after it runs: this capability is not available yet. |

## `[settings.<name>]`

Each setting is one table, and its key is `<prefix>.<name>` (see `prefix` above; when it is left out, the package id is used). When you have many settings you can group them by adding one level, `[settings.<group>.<name>]`, which gives the key `<prefix>.<group>.<name>` (for example `im.qq.listen`); only one extra level is allowed, and a setting in a group can't be called `type`, `name` or `shown_when`; sections are described below. The settings screen's `Packages` page has a group of settings for your package. **Don't read config files yourself**: an extension receives the values in the handshake, and changes are pushed to it (see [Writing an extension](extensions.md)); in a package with only scripts, the scripts read them from the environment variable `MIYU_SETTINGS_JSON` (see [Scripts and skills](scripts-skills.md)). When a package is removed, the values people wrote in the config are kept by default, as pacman does (they take no effect, and `miyu check` only notes that your package left them); reinstalling makes them take effect as they were, and only `miyu pkg remove --purge` deletes them.

| Field | Notes |
|---|---|
| `type` | Required. It can be `bool`, `int` (`min`, `max`), `number` (a decimal; `min` and `max` are required), `option` (`choices`, at least two), `text` (`max`, default 200 characters; `lines`), `name`, `model` (picks a model: `<provider>/<model>` or a pool `@<pool>`), `persona` (picks a persona by its id), `knowledge` (picks a knowledge base by its id), `preset` (picks a preset by its id), `url`, `secret` (only as a `{ secret = … }` reference), or `list` (`element` is the element type; `record` makes each entry a set of fields, see below). |
| `choices` | The options of an `option`: either an array of texts (`["auto", "opaque"]`) or an array of tables, where each table requires `value` and may have `name` and `description`, written like the setting's own `name` and `description` (the settings screen shows `name` in the dropdown and `description` dimmed below it). The two forms can't be mixed; the config stores `value`. |
| `choices_from` | Allowed only on a `text` (not one with `lines`, and not a list element or a field of a record): the name of a method your program registers. The settings screen asks that method for the choices and draws them as a dropdown; see "Choices from your program" below. |
| `lines` | `lines = true` on a `text` shows a box with several lines (for prompt templates and the like); without `max`, it holds at most 2000 characters. |
| `min`, `max` | The range of an `int`; when left out, it is the whole integer range. They are required for a `number` and accept integers only (such as `0` to `2`); use `step` for finer values. |
| `step` | The size of one step for an `int` or `number` (used by the settings screen). It is a positive number, and a whole number for an `int`. |
| `slider` | `slider = true` on an `int` or `number` draws a slider, which needs `min` and `max`. Without `step`, an `int` moves by 1 and a `number` moves by a hundredth of its range; a `number` slider whose `min` equals its `max` needs a `step`. |
| `default` | The default value, which must match the setting's type; a `secret` can't have one. |
| `layers` | Only `system` (the system config) can be written, and it is also the default. |
| `fields`, `title` | Only for a list with `element = "record"`. Under `fields`, each field is one table, `[settings.<name>.fields.<field>]`, written like a setting (`type`, `default`, `name`, `description` and `hidden`, plus the `number` type, `choices` with `name` and `description`, `lines`, `step` and `slider`), but without `layers` or `applies`, and it can't be a `list` itself; a field can't be called `fields`, and a field without `default` must be filled in for every entry. `title` names the `text`, `name` or `option` field used as each entry's title. The whole list can't have a default and holds at most 100 entries. |
| `applies` | When a change takes effect: `now`, `new_session`, `next_turn`, `restart` (after the core restarts), or `program_start` (the next time your program starts; this is the default). |
| `name`, `description` | The name and description shown to people. |
| `hidden` | With `true`, the settings screen doesn't show the setting, but it can still be written and read. |

When a setting is a list whose entries are sets of fields (for example several accounts, each with a name, an endpoint and a key), write it like this:

```toml
[settings.accounts]
type = "list"
element = "record"
title = "name"
name = { en = "Accounts" }

[settings.accounts.fields.name]
type = "text"
name = { en = "Name" }

[settings.accounts.fields.base_url]
type = "url"
default = "https://api.example.com/v1"
name = { en = "Endpoint" }

[settings.accounts.fields.key]
type = "secret"
name = { en = "Key" }
```

People fill it in card by card on the settings screen, and the config file holds it as an array of tables, `[[<prefix>.accounts]]`; a `secret` field is still only a reference, and the key itself is stored separately in the secrets file. The value you receive is an array of objects, `[{"name": "Home", "base_url": "https://api.example.com/v1", "key": "sk-…"}]`, where the key is the real value; fields that weren't filled in take their default, and fields without a default are left out.

The group's own table, `[settings.<group>]`, can hold two keys, and the settings screen uses them to split your group into sections. `name` is the section's display name (written like a setting's `name`; when it is left out, the group id is shown). `shown_when` decides when the section is shown, written as `{ "<a setting of this package>" = "<value>" }`; the value can also be a list (`["mimo", "openai"]`), and the section is shown only while that setting's current value is one of them. `shown_when` can only point at an `option` in your own manifest, or at a `text` with `choices_from` (whose choices are only known at run time, see below), by the setting's name (`engine`, or `<group>.<name>` for one in a group) without the prefix; it can't point at a setting inside its own section; for an `option` the values must be among its choices, while for a `text` they aren't checked and are compared as they are. A package that breaks these rules can't be installed (`bad_shown_when`). A section that isn't shown is only not drawn: its values are still stored, handed to you and checked as usual.

```toml
[settings.engine]
type = "option"
choices = ["minimax", "mimo", "openai"]
name = { en = "Engine", zh = "引擎" }

[settings.minimax]
name = { en = "MiniMax" }
shown_when = { engine = "minimax" }

[settings.minimax.key]
type = "secret"
name = { en = "Key" }

[settings.cloud]
shown_when = { engine = ["mimo", "openai"] }

[settings.cloud.voice]
type = "text"
name = { en = "Voice" }
```

### Choices from your program

When the choices are only known at run time (for example the microphones on this machine, or the voices an engine currently offers), write a `text` and add the field `choices_from = "<method>"`. The method is one your program registers with `package.methods` after it connects to the core (see [Writing an extension](extensions.md)), and its name is written the same way as when it is registered: it starts with a lowercase letter, uses only lowercase letters, digits, `_`, `.` and `-`, and is at most 64 characters. If the name is wrong, or `choices_from` is written in one of the places listed above where it isn't allowed, the package can't be installed (`bad_choices_from`); other types don't accept this field (`unknown_key`).

```toml
[settings.mic]
type = "text"
name = { zh = "麦克风", en = "Microphone" }
choices_from = "devices.list"
```

When the settings screen shows this setting, it calls your method without parameters, and you return:

```json
{"choices": [{"value": "hw:1,0", "name": "USB microphone", "description": "48 kHz"}]}
```

`value` is required and is the text stored in the config; `name` is the name shown to people, and `value` is shown when it is left out; `description` is optional and is drawn dimmed below. Pick the language of the names and descriptions yourself before returning them. If the call fails (your program isn't connected, the method isn't registered, or it times out) or the returned list is empty, the settings screen falls back to a text box that people fill in by hand; a stored value that isn't in your list (for example because the device was unplugged) is still shown. The core never checks values against your list: the setting is still a plain `text`, you receive the text as written, and you handle values that no longer work yourself.

## `[features.<id>]`

One switch in presets controls a group of tools. When you don't write this table, the whole package counts as one feature; when you write several features, every tool you register must be listed under some feature, or it can't be registered.

| Field | Notes |
|---|---|
| `name` | Required. It is the name shown to people. |
| `summary` | A one-sentence description. |
| `tools` | The names of the tools this feature controls. |

```toml
[features.greet]
name = { en = "Greeting", zh = "打招呼" }
summary = { en = "Greet people" }                  # optional
tools = ["hello_greet"]
```

Feature ids must be unique across all packages, so prefixing them with the package id is recommended.

For packages that connect a chat platform (packages with `[connection]`): presets only govern local sessions, so the preset menu lists only tools registered with `local` in `venues`, and leaves out a feature that has no such tool. Tools used only in groups and private chats are controlled by your own venue switches.

## `[check]`

`args`: when you run `miyu check`, the core runs `<program> <args…>`. Your program reports problems on standard output, one JSON object per line (`kind`, `file`, `level` and `message` are required; `line` and `column` are positive integers and `code`, `key`, `rule` and `source` are strings, all optional; other fields are not accepted). It exits with 0 when there are only warnings and with 1 when there are errors. The program may run for at most 30 seconds. This table requires `[command]` in the manifest.

## `[page]`

`dir`: the folder of the package page, which needs an `index.html`; the page is opened from the web UI's `Packages` page. The page calls the methods you registered through a channel the web UI provides (`package.methods`, `method.call`; see [Writing an extension](extensions.md)).

`server`: `true` means your program starts its own web server, and that server is the package page. Write either this or `dir`, not both, and only extensions can write it. Your registered `status` method includes `web` in its reply: the port the server actually listens on (leave it out until it is listening). Heads (UI programs that connect to the core, such as the terminal UI and the web UI) and `miyu pkg page` use it to open `http://127.0.0.1:<port>/#miyu=<…>`; the fragment carries a sign-in ticket, which your page trades for a device token before connecting to the core.

## `[tray]`

This table adds a line to the tray menu (Miyu's tray icon, or the menu bar icon on macOS); clicking the line opens your package page (`[page]`, the section above) in the browser. A package can add only one line, and that line can only open your own package page, never a command, a URL or another package.

| Key | Notes |
|---|---|
| `name` | The text of the line, written like `[package] name` and picked by the person's language. |

```toml
[tray]
name = { en = "Open IM connections", zh = "打开通讯平台接入界面" }
```

Only extensions and built-in packages that have `[page]` can write this table; without `[page]`, or with any key other than `name`, it is reported as `bad_tray`. The tray lists the line only while the package is installed and switched on and the package page's `index.html` exists.

## `[[mcp]]`

A package can bring MCP servers, one per entry; for details see [MCP servers](mcp.md).

| Field | Notes |
|---|---|
| `name` | The server name (the table name in the configuration). It starts with a lowercase letter, then uses only lowercase letters, digits and `-`, and is 1 to 32 characters long; it must be unique across all packages. |
| `command` | The command and its arguments. The first item is looked up in the package's `bin/` first, then on `PATH` (`npx`, `uvx`, `docker` and the like). Write either this or `url`. |
| `url` | The server's address, starting with `https://`; `http://` is only for servers on this machine (`localhost`, `127.0.0.1`), and servers on other machines are not connected, so that the token is not sent in the clear. Write either this or `command`. |
| `bearer` | Used with `url`: the token, sent as `Authorization: Bearer <value>`. It is written like an `env` value; please write the token as `{ secret = … }`. |
| `headers` | Used with `url`: other request headers, such as `{ X-Api-Key = { secret = "key" } }`, written like `env`. |
| `env` | Environment variables for the server. Write secrets as `{ secret = "<name>" }` (stored with `miyu provider login` or on the settings screen); don't put the values in the manifest. |
| `venues` | One or more of `local`, `private` and `group`, meaning local sessions, private chats on chat platforms, and groups; when it is not written, only local sessions get the server. |
| `timeout_ms` | The longest one call may take, in milliseconds: 1000 to 3600000, and 600000 when it is not written. |
| `clicall` | Whether the AI can call this server's tools with `miyu call` from a script it writes in a command; when it is not written, it can. For servers that write or send things, write `false`. |

## `[[slash]]`

Slash commands the extension provides, one per entry; `capabilities` must include `commands`.

| Field | Notes |
|---|---|
| `name` | The command name, written like `[command] name`; a name that clashes with one of Miyu's built-in commands is not accepted. |
| `summary` | The sentence shown in the command menu. |
| `argument` | A hint for what follows the name, for example `{ en = "<city>", zh = "<城市>" }`. |
| `access` | Who can use it: `admin` (the default: the person, and the owner and managers in groups), `anyone`, or `off` (disabled for now). A value you write in the config overrides it. |

When someone types the command, the core calls your program with `command.call`; see [Writing an extension](extensions.md). If you only want the command to expand into a message to the AI, a command template is enough and no program is needed (see [Scripts, skills, command templates](scripts-skills.md)).

## `[[search]]`

This table registers your program as a search provider, one per entry; `capabilities` must include `search`.

| Field | Notes |
|---|---|
| `id` | The id, written like `[command] name`; it must be unique within the package. |
| `name` | The name shown to people. |

Once it is registered, the `Web provider` dropdown on the settings screen gets one more entry, whose value is `<package id>/<id>`. It is used only when a person picks it, and it never joins the `Auto` order, so your program never receives search terms without the person knowing. When the AI searches the web, the core calls your program with `search.query`; when your program can't answer (an error, a rate limit), the providers that ship with Miyu take over. See [Writing an extension](extensions.md).

## `[guard]`

This table registers your program as a guard before tool calls: before one of the AI's calls runs, the core asks you whether to allow it, deny it or ask the person; `capabilities` must include `tool.guard`.

| Field | Notes |
|---|---|
| `tools` | The tools to ask you about: an array of tool names. Built-in tools, other packages' tools and MCP tools are all matched by name. |
| `access` | The access classes to ask you about: any of `read`, `write`, `execute`, `network`, `outbound`, `venue` and `install`. |
| `timeout_ms` | How long to wait for your answer, in milliseconds: 100 to 5000, and 1000 when it is not written. No answer by then counts as a deny. |

```toml
[guard]
tools = ["write", "edit"]
access = ["execute"]
```

The core asks you only when the call's tool name is in `tools` or its access class is in `access`; you must write at least one of the two, and asking about everything is not allowed. Tools you register yourself are never asked about. When the guard is switched on but your program isn't running, times out or fails, the call counts as denied. The core calls your program with `tool.guard`; see [Writing an extension](extensions.md).

## `[[driver]]`

This table provides a model driver, one per entry; `capabilities` must include `model.driver`, and declaring `model.driver` requires at least one entry.

| Field | Notes |
|---|---|
| `name` | The driver name, written like `[command] name`; it must be unique within the package. |
| `cache` | The cache type: `contract` (the cache hits as long as the prefix is unchanged; you must implement `driver.encode` and check it with `miyu dev driver-check`), `best_effort` (default), or `none`. |
| `key` | Whether Miyu needs to hand the driver that provider's key: `none`, `optional` (default) or `required`. |
| `base_url` | Whether the driver needs that provider's address: `none`, `optional` (default) or `required`. For a driver that writes `none` (for example one that signs in by itself or drives a local program), the settings interface doesn't show the address; `key = "none"` likewise hides authentication and the key. |
| `images` | Write `true` if it can see images (the default is `false`). |
| `hosted` | The names of tools this driver has the provider run on its own, such as `["search_web", "read_url_content"]` (empty by default): when the package is installed, the core uses it to show the owner `has the provider run on its own: …`. Each name is 1 to 64 bytes, without control characters or repeats. If the driver sends a name that isn't in this list, Miyu still accepts and shows it, and only writes a warning line in the run log; see [Writing extensions](extensions.md#tools-the-provider-runs-on-its-own). |
| `quiet_secs` | How long the driver may stay silent before the call counts as dropped, in seconds, 1 to 900 (the default is Miyu's idle limit, 180 seconds or more). It applies both to the wait for the first token and to the wait between deltas, and a value shorter than Miyu's limit doesn't make the wait shorter. A driver writes this field when its provider doesn't stream reasoning and often takes a minute or two before the first token, for example `quiet_secs = 300`. |

The driver is used only when the owner writes `driver = "<package id>/<driver name>"` in a provider's settings, or when your package brings a provider pointing at it with `[providers.<id>]` (see the next section); model profiles, the npm table and the default always use the built-in drivers, so installing your package can't take over a provider the owner already set up. If the package isn't installed or isn't approved, or the driver name is wrong, `miyu check` reports it and that provider counts as unusable; Miyu never falls back to a built-in driver. How Miyu calls your driver (`driver.call`, `driver.delta`, `driver.cancel`) is described in the [protocol reference](../reference/extensions.md#drivercall-driverdelta-drivercancel).

## `[providers.<id>]`

This table brings a model provider, one table per provider. While the package is installed and switched on, the provider appears in the owner's provider list, and the owner can switch to its models right away (`/model`, the default model) without copying any config. When the package is removed or switched off, the provider disappears. Extensions and packages carrying only scripts or skills can both write this table.

```toml
[providers.agy]                                     # the id: starts with a lowercase letter; only lowercase letters, digits, -, _, at most 32; models are written agy/<model>
name = { en = "Antigravity", zh = "Antigravity" }   # optional: falls back to the catalog's name, then the id
driver = "antigravity/antigravity"                  # required: one of this package's [[driver]] (<package id>/<driver name>), or the built-in openai-chat, anthropic, openai-responses
local = true                                        # optional: priced as free

[providers.agy.models."gemini-3-pro"]              # optional: hand-written model facts, written the same way as in the config
window = 1000000
```

| Field | Notes |
|---|---|
| `name` | The name, which can be written in three languages and is picked by the owner's interface language; when it is left out, the catalog's name is used, then the id. |
| `driver` | Required. Your own extension driver is written `<package id>/<driver name>` (the driver must be in this manifest's `[[driver]]`); the built-in `openai-chat`, `anthropic` and `openai-responses` also work. A driver of another package is not accepted. |
| `base_url` | The address, which can only be plain fixed text (not `{ env = … }`); you can leave it out when your driver connects by itself. |
| `catalog` | Which models.dev provider it corresponds to, written the same way as in the config. |
| `price_multiplier` | The price multiplier, written the same way as in the config. |
| `local` | Marks a service on this machine, which is priced as free. |
| `cache` | The cache class: `contract`, `best_effort` or `per_request`, written the same way as in the config. |
| `models` | Hand-written model facts, written as `[providers.<id>.models."<model>"]` with the same fields as in the config (`window`, `max_output`, `inputs`, `tools`, `reasoning`, `effort`, `price` and so on). The model list comes from your driver's `driver.models`, so you don't need to list every model here. |

`key` is not accepted: keys belong to the owner, who sets them in settings (if your driver has `key = "required"` and the owner hasn't set one, `miyu check` reports it). When other fields are written wrong, those fields are not accepted and `miyu check` points them out.

When the owner changes this provider's settings, the changes go into the owner's own config and override the values you provide (Miyu adds `package = "<your package>"` along the way). If the owner's config already has a provider with the same id that isn't an override of yours, the owner's provider wins, yours does not appear, and `miyu check` points it out; so pick an id that is unlikely to clash (for example one that includes your package name). When two packages bring the same id, the package installed first gets it.

## `[provider_key]`

This table asks for the key of one model provider the owner has already set up on the models side, so the owner doesn't have to enter it again; `capabilities` must include `provider.key`, and declaring `provider.key` requires this table.

| Field | Notes |
|---|---|
| `catalog` | Which provider you want: its id in the model catalog, from the same set of ids as `catalog` in a provider's settings, for example `deepseek`. |

```toml
[process]
capabilities = ["provider.key"]

[provider_key]
catalog = "deepseek"
```

The install screen shows `This package gets your DeepSeek key`, and the key is handed to you only after the person approves it. Miyu works out which of the owner's providers is the one you asked for from the owner's provider settings: a provider with `catalog` written is matched by its `catalog`; one without it is matched if its address contains that provider's official address (only DeepSeek's `api.deepseek.com` is recognized for now); one with neither is matched by its id. Among the providers that match and have a key set, the first one by id is the one whose key you get; no other provider's key is ever handed over. How to read the key is described in the "Handshake and settings" section of [Writing an extension](extensions.md).

## `[after]`

After one of the AI's tool calls has a result and it has been written to the session, the core notifies your program (read-only; no answer is expected); `capabilities` must include `events.read`.

| Field | Notes |
|---|---|
| `tools` | The tools to notify you about: an array of tool names. Built-in tools, other packages' tools, MCP tools and your own tools are all matched by name. |
| `access` | The access classes to notify you about: the same ones as in `[guard]`. |

```toml
[after]
tools = ["shell"]
access = ["write", "network"]
```

You must write at least one of the two, and receiving everything is not allowed; this table has no timeout field (writing one makes the manifest fail to load). The core sends your program `tool.after`; see [Writing an extension](extensions.md).

## `[[side]]`

This table registers the model requests your program makes outside the conversation (side requests), one per entry, and declares which tier of model each one needs. No capability needs to be declared for it.

| Field | Notes |
|---|---|
| `id` | The id, written like `[command] name`; it must be unique within the package. |
| `tier` | The tier it needs: `lite` (cheap and fast, for high-volume judgements), `normal` (for requests that have to understand a stretch of conversation), or `flagship` (the best models). |
| `name` | The name shown to people. |
| `summary` | A one-sentence description: when it is called and what it does. |

```toml
[[side]]
id = "judge"
tier = "lite"
name = { en = "Reply judge", zh = "判断要不要回" }
summary = { en = "Decides whether to reply in a group.", zh = "群里有人说话时判断要不要回" }
```

Call `model.call` with `"side": "judge"` (only an id registered in your own package, without the package name) and without `model` or `use`: the core takes a model from the pool named after the tier (`lite`, `normal`, `flagship`; people put models into these pools in settings). If that pool is empty, or every model in it is cooling down or has failed, the core uses the session's model — the model of the session you pass as `session`, or `models.chat` if you pass none. People don't need to configure a model for your request. If you pass an id you didn't register, the call returns `bad_params`. `model.list` lists the requests you registered under `side` (with ids written `<package id>/<id>`), together with the model each one would land on right now. See [Writing an extension](extensions.md).

## `[[purpose]]`

This table gives a name people can read to a purpose (`purpose`) your program writes when it calls `model.call`, one per entry. When people look at usage, the rows grouped by purpose (`purpose_name` in `usage.query`, `/usage` in the terminal UI, the usage page in the web UI) show this name; a purpose that isn't declared is shown as written in `purpose`. No capability needs to be declared for it.

| Field | Notes |
|---|---|
| `id` | The purpose, exactly the same as `purpose` in `model.call`: 1 to 32 lowercase letters, digits and `-`; it must be unique within the package. |
| `name` | The name shown to people, written per language. Write it the way software names things, as a noun phrase ("Join review", not "Deciding whether to let someone in"). |

```toml
[[purpose]]
id = "join-approval"
name = { en = "Join review", zh = "入群审核" }
```

The core's own purposes (`title`, `compaction`, `vision` and so on) keep the names the core gives them, even if you declare them. When several packages declare the same purpose, the package whose id sorts first wins.

## `[[widget]]`

This table puts a block of your own content in the terminal UI and the web UI; `capabilities` must include `widgets`. A package can have at most 16 blocks.

| Field | Notes |
|---|---|
| `id` | Unique within the package: it starts with a lowercase letter, uses only lowercase letters, digits and `-`, and is at most 32 characters. |
| `place` | Where the block goes: `home` the home screen, `sidebar` the sidebar, `status` a small slot in the status bar, `page` a full page. |
| `title` | Required for sidebar and page blocks. |
| `scope` | `global` (default); `session` means the block follows the session, with one copy per session; it is only for the sidebar. |
| `command` | Only for pages: typing this slash command opens the page. |
| `state` | With `true`, the block's content comes from your package's state in the session (a tool result's `state`, or `session.set_state`; see [Extensions](../reference/extensions.md)), and it is still shown when your program isn't running; only for blocks with `scope = "session"`. |

Your program pushes the block's content; see [Writing an extension](extensions.md).

## `[export]`

Other packages can only call you by name over the bus (`bus.call`); they can't reach you by your package id. So you declare a name first, then list the methods under it; methods that only your own package page or widgets call don't belong here, and registering them with `package.methods` is enough.

`provides`: the names you provide on the bus (for example `["stt"]`); among installed packages, a name has only one provider, and installing a second one is reported as a conflict. `plugs`: the names you plug into (for example `["tts.engine"]`); several packages can plug into the same name, and whoever uses the name picks one. A name consists of dot-separated parts, each starting with a lowercase letter and containing only lowercase letters, digits and `-`; the same name can't be in both lists. `methods`: the methods under those names that other packages can call (they still have to be registered with `package.methods`); each method name is prefixed with its name and has a one-part short name: `stt.transcribe` for `stt`, `tts.engine.synthesize` for `tts.engine`. Every name you declare needs at least one method, and every entry in `methods` has to be under a name you declare; without a declared name you can't write `methods`. A manifest that gets this wrong can't be read (`bad_export`).

## `[content.<package id>]`

This table brings a folder of content for another package (sticker content packs work this way): `dir` is a relative folder in your package. The extension of the package the content is for reads it with `content.list` and `content.read`. You can write several of these tables.

## `[connection]`

`platform`: the chat platform the package connects to, written like a package id (for example `qq`); when it connects several, write a list (`["qq", "tg"]`). Only extensions can write this field; chat platform bridges write it.

When a package connects several platforms, its tool names start with the platform: `qq_send` is only offered in `qq:` groups and private chats, and `tg_send` only in `tg:` ones; local sessions get all of them. Tools without a platform prefix are offered everywhere.

## `[depends]`, `[recommends]`

`packages`: the ids of the packages it depends on or recommends (the older spelling `workers` is still recognized and is read into the same list). When a dependency is missing, the package can't be installed, and an installed one can't start; when a recommended package is missing, it still installs and starts, and only loses some abilities.

To require at least a certain version of another package, write `<id>>=<version>`:

```toml
[depends]
packages = ["onebot>=1.2.0", "embed"]
```

- Only `>=` is accepted, with no spaces; the version is written in semver (`1.2.0`, `1.2.0-rc.1`). A two-part `1.2`, a leading `v`, `=`, `<` and the like are reported as `bad_dependency`. `workers` takes ids only.
- Versions are compared by semver: `1.10.0` is newer than `1.2.0`, and `1.2.0-rc.1` falls short of `1.2.0`. An installed package with no `version`, or with one that isn't semver, counts as falling short.
- An installed version below the floor counts the same as a missing package: the package can't be installed (`depends_missing`), and an installed one can't start. When installing from a package source, Miyu picks a version from the source that meets the floor and installs or upgrades it along with the package.
- Older versions of Miyu can't read this spelling, so a package using it should set `miyu` in `[package]` to the lowest version it needs (see the table above).

## `[mascot]`

This table makes the mascot on the terminal UI's home screen into a package:

```toml
[package]
name = { zh = "布丁", en = "Pudding" }
icon = "cat"            # optional

[mascot]
model = "mascot.json"   # a relative path inside the package folder
```

- `model` is required: a relative path inside the package folder, with no `..` and no leading `/`. No other field is accepted.
- A mascot-only package writes just `[package]` and `[mascot]`, and may also write `[depends]` and `[recommends]`. Such a package uses no protocol, so writing `protocol` or any other table is reported as `wrong_kind`. An extension package may also carry a `[mascot]`.
- `miyu check` checks the model file: a missing file, a file over 256 KiB, or a file that isn't a JSON object is an error. What goes inside the file is defined and checked by the terminal UI; see [docs/blueprint/tui.md](https://github.com/miyu-agent/miyu-tui/blob/main/docs/blueprint/tui.md) (`mascot.json`) in the terminal UI's repository.
- A mascot package has no switch, settings or program; the terminal UI picks which mascot to use by its setting `tui.mascot`.

## `[theme]`

This table makes a look (box lines, symbols, text styles, colors and so on) into a package: it can carry a terminal theme, a web theme, or both.

```toml
[package]
name = { zh = "夜", en = "Night" }

[theme.tui]
file = "theme.json"     # the terminal theme: a relative path inside the package folder

[theme.web]
dir = "web"             # the web theme: a relative directory inside the package folder
```

- `[theme]` holds two subtables, `tui` and `web`. You must write at least one; when neither is present, it is reported as `missing_key`.
- `[theme.tui]` has only the field `file`, which is required and written like `[mascot] model`; a wrong one is reported as `bad_theme_file`. What goes inside the file is described in [docs/blueprint/tui.md](https://github.com/miyu-agent/miyu-tui/blob/main/docs/blueprint/tui.md) (the "主题", themes, section) in the terminal UI's repository.
- `[theme.web]` has only the field `dir`, which is required and written like `[page] dir`; a wrong one is reported as `bad_theme_dir`. The directory is an ordinary web package (`manifest.json`, `index.js` and other files; scripts are allowed), and what goes inside it is defined by the web UI.
- The older spelling, `file` written directly under `[theme]`, is still recognized and is read as `[theme.tui] file`; when it is written together with `[theme.tui]`, it is reported as `unknown_key`.
- A theme package writes just `[package]` and `[theme]`, and may also write `[depends]` and `[recommends]`. Writing `protocol`, `[command]`, `[mascot]` or any other table is reported as `wrong_kind`: a theme package can't carry a mascot, and no other package can carry a theme.
- `miyu check` checks the terminal theme file by the same rules as a mascot's file, and also reports a missing web theme directory as an error.
- A theme package has no switch, settings or program; the terminal UI picks which look to use by its setting `tui.look`, and the web UI picks by its own setting.
