# Things that work as files: scripts, skills, command templates, knowledge bases, personas

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

None of these need a long-running program; files are enough. This page is the full format, written for people who put them into a package; if they are only for yourself, start with [Extending Miyu](../guide/extending.md) in the user guide, which goes step by step.

| | What it is | How the AI uses it |
|---|---|---|
| **Script** | An executable file, which is one tool | The AI calls it directly, like any other tool |
| **Skill** | A `SKILL.md`, which describes a way of doing something | The AI normally sees only its name and one line, and reads the body when it needs it |
| **Command template** | A `<name>.md`, which is one slash command | When a person types `/<name>`, the body is sent to the AI as that person's message |
| **Knowledge base** | `kb/<id>/`: a `kb.toml` and some documents | The AI searches it with the knowledge base tools; when recall is on, related passages come along every turn |
| **Persona, preset** | `personas/<id>/`, `presets/<id>.toml` | People pick them from the list |

Where to put them: in a package, they go under the package folder's `scripts/`, `skills/` and `commands/`, with a manifest of just `[package]`; if they are just for you, put them straight into `~/.miyu/root/scripts/`, `skills/`, `commands/` (on a name clash, the ones there win). The next session sees them, and each script, skill and template can be switched on and off separately in presets. Broken ones, and scripts with the same name as another tool, aren't registered, and `miyu check` says which ones and why; if you check right after putting a file in and it says the core hasn't picked it up yet, check again a little later.

Links work too, pointing at files or folders elsewhere (for example, kept together in a repository of your own): what the link points at is what counts, and the AI sees the real path; broken links are skipped. Links into other parts of Miyu's data folder (such as the local token or the secrets file) are not accepted, and `miyu check` says where they point.

```text
dice/
├── package.toml          # the manifest has only [package]
├── scripts/
│   └── dice.py
├── skills/
│   └── take-notes/
│       └── SKILL.md
└── commands/
    └── review.md
```

```toml
[package]
version = "0.1.0"           # optional for installing, but required to pack and publish to a source
name = { en = "Dice and notes", zh = "骰子和笔记" }
```

## Scripts

One file is one tool. The tool name comes from the file name (with the extension removed, and characters outside `[A-Za-z0-9_-]` replaced by `_`), and a comment header at the top of the file gives the description and parameters. Here is a working example, `dice.py`:

```python
#!/usr/bin/env python3
# Display name: Dice
# 显示名称：掷骰子
# Description: Roll dice and return each face and the total.
# 描述：掷骰子，交回每一颗和总数。
# Timeout: 10
# Parameters:
# {"type": "object", "properties": {"count": {"type": "integer"}, "sides": {"type": "integer"}}, "required": ["count", "sides"]}
import json
import random
import sys

args = json.load(sys.stdin)
count = max(1, min(int(args["count"]), 100))
sides = max(2, min(int(args["sides"]), 1000))
faces = [random.randint(1, sides) for _ in range(count)]
print(f"{count}d{sides}: {faces} = {sum(faces)}")
```

Because its first line is a `#!` line, it needs no `chmod +x`: Miyu starts the interpreter and passes the script file to it. A script without `#!` is started directly on Linux and macOS, so it needs `chmod +x` first.

**The header**

| Key | Notes |
|---|---|
| `Description` | The description for the model, written as a short English sentence. It is required. |
| `描述` | The description for people (in Chinese). |
| `Display name`, `显示名称` | The name for people (in English and in Chinese); the timeline shows it. |
| `Parameters` | The parameters' JSON Schema, starting on the next line, and it may span several lines; when it is omitted, the tool has no parameters. |
| `Timeout` | The timeout in seconds; the default is 60. |
| `Clicall` | With `yes` or `true` (in any case), the AI can also call the tool with `miyu call` from a script it runs, and the result goes to that script. With `no`, `false` or no value, it can't, and the tool can only be called directly; any other value keeps the whole script from being registered. Scripts that read or look things up, and that the AI can't easily do from a command on its own, should set it: the AI can then call them in bulk from a script and skip many round trips. Don't set it on scripts that change or send things or spend quota. |
| `Venues` | Which kinds of session get the tool: some of `local` (this machine: the terminal, the web page and so on), `private` (private chats on a messaging platform) and `group` (groups), separated by commas, for example `Venues: local, private`. When it is unset, every kind of session gets it; if it is wrong, the whole script is not registered and `miyu check` reports it. |
| `Role` | What the tool is for, written the same way as an extension's `role`: `read_file` means the tool reads a text file. A wrong value rejects the whole script, and so does a key that looks like it but is misspelled (such as `role` or `Rloe`: the wrong case or one letter off). |
| `Scope` | Which sessions get the tool, written the same way as an extension's `scope` (`local`, `local_main`, `local_main_attended`, `spawn`), narrowing further within `Venues`; when it is unset, it is `any`. A wrong value rejects the whole script, and so does a misspelled key such as `scope` or `Scpoe`. |

The header is the run of comment lines (lines starting with `#` or `//`) at the very top of the file, and it ends at the first line that is not a comment. Leave a blank line after the header before any other comment; otherwise a sentence like "Timeout: …" in your notes is read as part of the header.

**How it runs**

- A script with a `#!` line is started by that line: the interpreter runs with the script file as an argument (on Windows, the interpreter's name in the `#!` line is looked up on `PATH`; with `env`, the name after it is used; `python3` becomes `python`). Without a `#!` line, Linux and macOS start the file directly; on Windows, the interpreter is found by the extension: `.py` uses `python`, `.ps1` uses PowerShell, `.js` uses `node`, `.cmd` and `.bat` use `cmd /C`, and anything else is started directly.
- The arguments are one JSON object. Stdin always has all of it, and the environment variable `MIYU_ARGS_JSON` also has it when it is at most 30 KiB. Long arguments are only on stdin, so reading stdin is the safe way.
- Stdout and stderr both go to the AI, in the order they were written; a non-zero exit code counts as failure, so write the reason to the output.
- To report progress during a long run, print a whole line starting with `miyu-progress: `: people see it in the interface, the AI doesn't, and it stays out of the result. Write it to stderr and flush it right away (because Python buffers stdout in blocks when it goes to a pipe, progress would otherwise only show up at the end):

  ```python
  import sys
  print("miyu-progress: 3/10 downloaded", file=sys.stderr, flush=True)
  ```

- `miyu call` doesn't work inside a script tool: the channel for calling tools is only opened for a `shell` command the AI runs directly, not for script tools, so that calls don't nest. If your script needs to call tools and then work on the results, don't make it a script tool; have the AI run it from `shell` instead (for example, ship it in a skill and say in the body how to run it).
- The working directory is the session's workspace. A writable cache directory is given in `MIYU_CACHE_DIR` (it is in the data root's `var/cache/scripts/`, one folder per script, and it is kept across reboots; a folder untouched for 30 days is cleared, so keep only what can be made again there).
- Files meant for people (images you draw, videos you download, documents you make) go into the folders in your home directory, where people can find them in the terminal and web interface: `MIYU_PICTURES_DIR`, `MIYU_VIDEOS_DIR`, `MIYU_DOCUMENTS_DIR`, `MIYU_DOWNLOADS_DIR`. These folders are created and writable before the script runs. Only your own sessions on this machine get them; group chats and strangers' private chats don't, so write to the cache folder or the workspace there, and check that a variable is set before using it.
- Anything that must last (a login, where the last run stopped) goes in `MIYU_STATE_DIR`: one folder per script, still there the next time. Local sessions share one folder, and each group and each stranger's private chat gets its own (split by venue, so a new session in the same group finds the same folder). For a script in a package, the folder is deleted when the package is removed; for a script you put in `scripts/` yourself, it stays after you delete the script, and `miyu check` points it out.
- A script in a package also gets `MIYU_APP_DIR`: the package folder it sits in (which holds the manifest and the package's other files), read-only. Scripts you put in `scripts/` yourself don't get it.
- The old names `MIYU_SCRIPT_CACHE_DIR`, `MIYU_SCRIPT_STATE_DIR`, `MIYU_SCRIPT_IMAGES_DIR` and `MIYU_PACKAGE_DIR` are still set during the transition and point at the same places; they go away in the next release, so write new scripts with the names above.
- Who called: `MIYU_CALLER_VENUE` is the kind of session the script was called in (`local` on this machine, or the venue id for a group or private chat, for example `qq:group:123`); `MIYU_CALLER_OWNER` says whether the person speaking this turn is the machine's owner (`1` or `0`; it is always `1` in local sessions, and it is `0` when one of several people in a group is not the owner, or when it can't be told).
- The model this turn uses: `MIYU_MODEL` is the model name, and `MIYU_EFFORT` is the reasoning effort (`default` when the config doesn't set one); `MIYU_SESSION_LOG` is this session's log directory, given only in the machine owner's own sessions (because other people don't get to see the computer Miyu runs on). Calls made before a model is settled, and calls from outside a session, have none of these, so check that they are set before using them.
- These two variables are facts, not a gate: they can't stop the AI from writing `MIYU_CALLER_OWNER=1 ./script` in a command itself. To keep a script to some kinds of session, write `Venues` in the header; use the variables only to adjust what the script does, for example to stay read-only in groups:

  ```python
  import os
  if os.environ.get("MIYU_CALLER_OWNER") != "1":
      print("Read-only here: only the owner can change the title.")
  ```

- Settings of a script package: a package can declare `[settings.<name>]` in its manifest, with the same rules as an extension package (type, `default`, `applies`, `name`, `description`, `hidden`; a `secret` cannot have a default). People fill them in under Settings → Packages, in this package's group. When a script under the package's `scripts/` runs, the environment variable `MIYU_SETTINGS_JSON` holds their current values as one JSON object: the keys are without the package's settings prefix (`[package] prefix` in the manifest, or the package id when it is not written), and grouped ones are written as `group.name`; a `secret` is the real value; a list of field sets (`element = "record"`) is an array of objects, with secret fields as real values and unwritten fields taking their default; keys that are neither set nor defaulted are left out, so check that a key is there before using it. The variable is read again on every call, so a change applies from the next call. Only the package's own scripts get it: other packages' scripts, scripts you put in `scripts/` yourself and the commands the AI runs do not.

  ```python
  import json, os
  settings = json.loads(os.environ.get("MIYU_SETTINGS_JSON", "{}"))
  key = settings.get("api_key")
  if not key:
      print("Set the API key in Settings → Packages first.")
  ```

- A script runs under the same rules as the commands the AI runs: whether it is sandboxed is explained under "When a script runs in the sandbox" below; in the sandbox, it can't read Miyu's data directory, and only the script file itself is made readable.

**Handing over images**

To let the AI see images directly (screenshots, frames from a video), copy them into `MIYU_IMAGES_DIR`: it is a new empty folder for each call, and Miyu collects the images after the run and then deletes the folder.

```python
import os, shutil
shutil.copy("frame-01.png", os.environ["MIYU_IMAGES_DIR"])
print("Grabbed 1 frame.")
```

- Images are taken in file-name order, at most 4, in PNG, JPEG, GIF or WebP. An image over 5 MiB, or over 8000 pixels on a side, is first scaled down to fit before it is handed over; one that can't be scaled down, or a file over 64 MiB, is not handed over.
- Only regular files directly in the folder count, and links are not followed: copy the images in, and don't link them.
- An image that doesn't fit these rules is not handed over, and the AI doesn't learn of it; the run log has a `script image dropped` line saying which script and why (without the file name).
- A call stopped at its timeout hands over no images; a call with a non-zero exit code still hands them over.

**When a script runs in the sandbox**

- In your own sessions (terminal, web, your QQ private chat, desktop voice), under full access (the default), scripts run outside the sandbox with your own permissions.
- With read-only on, scripts run in a read-only sandbox: they can write only to their own state, cache and image folders (`MIYU_STATE_DIR`, `MIYU_CACHE_DIR`, `MIYU_IMAGES_DIR`), plus, in local sessions, to `pictures`, `videos`, `documents` and `downloads` under the data root's `root/`, and nowhere else. In group chats and strangers' private chats, scripts run in the sandbox and can write only to that venue's own workspace. Scripts that touch hardware or need root (`sudo`) don't work there, and there is no way to exempt a single script.

## Skills

Skills use the public Agent Skills format (Claude Code, Codex and others read it too), so existing skills from the web just work. If you turn on "Read skills from other folders" (`skills.external.enabled`), skills that other clients install into `~/.agents/skills/` are picked up too (the folder list `skills.external.dirs` can be edited). They come after your own skills and those from packages; on a name clash, Miyu's own wins, and Miyu does not delete anything there. A skill goes in `skills/<name>/SKILL.md`:

```markdown
---
name: take-notes
description: "Keep meeting notes in notes/YYYY-MM-DD.md: decisions, owners, open questions. Use when the user asks to take or tidy notes, 记笔记."
metadata:
  display_name: Take notes
  summary: Meeting notes in a fixed format
  display_name_zh: 记笔记
  summary_zh: 照固定格式记会议笔记
---

# Taking notes

1. Create `notes/` in the workspace if it doesn't exist.
2. …
```

| Field | Notes |
|---|---|
| `name` | Only lowercase letters, digits and `-`, the same as the folder name (a different name is used as written, and a missing or invalid one falls back to the folder name; `miyu check` gives a warning for each case). |
| `description` | The description for the model: in English, saying what the skill is and when to use it; it may include a few trigger words people actually say in other languages. Put it in quotes (because an unquoted "colon space" inside is not valid YAML: Miyu reads it again as plain text and gives a warning, but other tools may not read it at all); it is at most 1024 characters, and the rest is cut. |
| `metadata` `display_name`, `summary` | The name and one line for people (in English); Chinese and Japanese go in `display_name_zh`, `summary_zh`, `display_name_ja`, `summary_ja`. |
| `disable-model-invocation` | With `true`, only a person can invoke the skill: the AI doesn't see it and won't pick it on its own (for releases, deleting things, or anything the AI shouldn't start by itself). |
| `user-invocable` | With `false`, a person can't invoke the skill and it stays out of the command menu; only the AI uses it (for background knowledge and the like). |

The AI normally sees only the skill's name, its description and the path of `SKILL.md`, and reads the body when it's useful. A person can also name skills with `$skill-name` in the input box, several in one message: their bodies go straight to the AI ahead of what was said. The AI can read other files in the folder (references, bundled scripts) but can't change them; bundled scripts aren't tools, so the body has to say how to run them.

## Command templates

Command templates use Claude Code's format: `commands/<name>.md`. When a person types `/<name> args`, the body is sent to the AI as that person's message.

```markdown
---
description: Review the changes in the working tree
argument-hint: "[focus]"
metadata:
  summary_zh: 检查工作区里的改动
---

Review the uncommitted changes in this repository. Focus on: $ARGUMENTS
```

- `$ARGUMENTS` is replaced by everything after the name, and `$ARGUMENTS[0]` by the first word (the text is split on whitespace; a value with spaces goes in English double quotes, so for `/review "my file.rs"`, `$ARGUMENTS[0]` is `my file.rs`); if the body doesn't use `$ARGUMENTS`, the arguments are appended to the end.
- `description` is the line shown in the command menu (in English); Chinese and Japanese go in `metadata` as `summary_zh` and `summary_ja`. `argument-hint` is a hint at what follows the name.
- Names start with a lowercase letter and use only lowercase letters, digits and `-`. A template with the same name as a Miyu built-in command doesn't take effect (the built-in wins).
- The timeline shows the line the person typed. Who can use a template is the same as for built-in commands.

For slash commands that a program handles (looking something up, changing state, replying with text), use an extension's `[[slash]]`; see [Writing an extension](extensions.md).

## Knowledge bases

A knowledge base is material for the AI to look things up in (lore, a product manual, notes). `kb/<id>/` in the package folder is a knowledge base, and nothing needs to go in the manifest. The id is written the same way as a package id.

```text
lighthouse/
├── package.toml          # the manifest has only [package]
└── kb/
    └── lighthouse/
        ├── kb.toml
        └── people.md
```

```toml
# kb/lighthouse/kb.toml; this file is optional
name = "Lighthouse lore"                               # the name; the id is used when it is not written
description = "People, places and rules of the lighthouse story"   # one sentence on what this base is
auto = true                                            # recall on its own; it is off when not written
```

- The name and description are listed in the AI's system prompt, so the AI knows the base exists and when to search it; keep them short. `kb.toml` knows only these three fields; a broken one is treated as if it were absent, and `miyu kb list` shows the error on that base.
- `auto = true` means that every turn, related passages from this base come along with what the person said, without the AI having to search. People can switch it on and off on the knowledge base page, and their choice is kept on their side.
- Documents: `.md`, `.markdown`, `.txt`, `.pdf`, `.html` and `.htm` files count, including those in subfolders; files starting with a dot and links don't count. Text files can be up to 4 MiB and must be UTF-8; PDF and web files can be up to 64 MiB. Files that can't be read are skipped, with a line in the log.
- Keywords: in Markdown, the first line under a heading can be `keys: keeper, the lighthouse girl, Eileen` (`关键词：` works too, and `,`, `，`, `、` all separate keywords). In a base with recall on, mentioning any of them brings that section along.
- Read-only: the AI can't write into a package's base, and people can't change its name, description or documents (rebuilding the index still works). Removing the package removes the base and its index.
- If the person has a base with the same id, theirs wins; a package bringing an id that another package already brings won't install (`package_conflict`).
- Once the package is installed, `miyu kb list` shows the base (saying which package it comes from), and you can try `miyu kb search <word>`.

## Personas and presets

- **Personas**: `personas/<id>/`, the same shape as a persona made in Miyu: `persona.toml` (`name`, `summary` and the like under `[persona]`), `prompts/persona.md` (the character), `prompts/examples.md` (example dialogue), `prompts/reminders.md` (role-play reminders), each of them optional. The easy way is to make and tune the persona in the terminal or web interface first, then copy `root/personas/<id>/` from the data root into the package's `personas/`. The character and the example dialogue are the persona's own text, and they can be in any language.
- **Presets**: `presets/<id>.toml`, likewise made in Miyu first and then copied from `root/presets/`.
- Read-only: what people change goes into their own layer on top of the package; removing the package removes its copy but keeps their changes, and `miyu check` mentions them.
- A package with an id already used by a shipped persona or preset, by another package, or by the person's own won't install (`package_conflict`).
