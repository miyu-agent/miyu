# Putting things on the screen

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Suppose you wrote an extension and want it to show up on the terminal interface and the web interface, which are "heads" (interface programs that connect to the core): for example a block of status in the sidebar, a section on the home screen, a small cell in the footer, a whole page of settings you can change, a backstage web page of its own, or a row in the tray menu. This page explains how to do each of them. For how to write the extension itself, see [Writing an extension](extensions.md).

## The options

An extension can put things in the interface in the following places:

| Way | Where it appears | Manifest | Capability needed |
|---|---|---|---|
| Widget: home | Terminal: below the working directory on the home screen of an empty session; web UI: the home screen of a new session | `[[widget]]`, `place = "home"` | `widgets` |
| Widget: sidebar | Terminal: the sidebar on the right (only when the window is 120 columns or wider); web UI: the `Panel` in the right column | `[[widget]]`, `place = "sidebar"` | `widgets` |
| Widget: footer | Terminal: the line below the input box; web UI: the right side of the line below the input box | `[[widget]]`, `place = "status"` | `widgets` |
| Widget: full page | Terminal: a whole page shown in the center; web UI: a standalone full page of the software. Type its slash command to open it | `[[widget]]`, `place = "page"` | `widgets` |
| Slash command | The command menu of both heads | `[[slash]]` | `commands` |
| Backstage page | Web UI settings page, `Dashboards`; terminal `Packages` page, `Backstage` tab; `miyu pkg page <id>` | `[page]` | If you run your own web server and ask for login tickets on the page's behalf, you need `login.page` |
| A row in the tray menu | The tray menu (on macOS, the menu bar icon) | `[tray]`, which must come with a `[page]` | No extra capability needed |

All of these require the package to bring a long-running program: the manifest must have `[process]` (that is, an extension), and the capabilities go in `[process] capabilities`. For the web UI's colors and shapes, see [Writing themes and appearance](themes.md).

## Widgets

Widgets work like this: the manifest declares which blocks there are, your program pushes their content to the core, the core passes it on to the heads that are looking, and each head draws it itself.

### The manifest

Declare widgets in the manifest, for example:

```toml
[process]
args = ["serve"]
capabilities = ["widgets"]

[[widget]]
id = "now"
place = "sidebar"
title = { zh = "时间", en = "Time" }
```

| Field | Description |
|---|---|
| `id` | Unique within the package: starts with a lowercase letter and contains only lowercase letters, digits and `-`, at most 32 characters. |
| `place` | `home` means the home screen, `sidebar` the sidebar, `status` the footer, and `page` a full page. |
| `title` | Required for the sidebar and full pages, written as `{ zh = "…", en = "…" }`. |
| `scope` | `global` (the default) means one copy for everyone; `session` means one copy per session, and is for the sidebar only. |
| `command` | Full pages only: typing this slash command opens the page; it is written like `[command] name`. |
| `state` | When `true`, the content comes from the package's state in the session (the `state` of a tool result, `session.set_state`), and it exists even when the program isn't running; only for blocks with `scope = "session"`. |

A package can have at most 16 blocks. A mistake gets `bad_widget`, and `miyu pkg install` and `miyu check` say which field is wrong.

### On the program's side

Your program handles widgets as follows:

1. When someone starts looking at a block, the core sends the notification `widget.watch {"widget", "session"?}`; when the last person stops looking, the core sends `widget.unwatch`. After your program connects and finishes the handshake, the core sends one more `widget.watch` for each block someone is looking at right now. Fetch data only while someone is looking.
2. Push content: `widget.set {"widget", "session"?, "title"?, "content"}`. A block that follows a session must have `session`, and a global one must not. `title` replaces the title in the manifest. The core replies `{"kept": true}`; for a block that follows a session when nobody is looking at that session, it replies `{"kept": false}`, and nothing was stored.
3. Take the content down: `widget.clear {"widget", "session"?}`.
4. Things you can click on a block call your methods: first register them with `package.methods {"methods": [{"name": "refresh"}]}`; when a person clicks, the core sends `method.call {"method", "params"}`, and the head gets whatever you reply.

Each push replaces the whole block. The content lives only in the core's memory: after the core or your program restarts, everything starts empty and waits for the next `widget.watch` to push again. When your program stops, all its blocks are cleared, and heads show `<software name> is not running` (the web UI shows `Not running`). For the same block to the same head, pushes go out at most once every 250 milliseconds, and in between only the latest one is kept.

For every field of these methods and their errors, see the [extension reference](../reference/extensions.md#widgetset-widgetclear-widgetwatch-widgetunwatch).

### Content

The content of a widget is an array with one item per section, and each section says which kind it is with `type`:

| `type` | Fields |
|---|---|
| `heading` | `text` |
| `text` | `text` (may contain line breaks, at most 2000 characters), `tone` |
| `pairs` | `items`: `{"label", "value", "tone"?}`, at most 50 pairs |
| `progress` | `value` (0 to 1, required), `text`, `mark` (0 to 1, the position marked on the bar) |
| `list` | `items`: `{"title", "detail"?, "right"?, "state"?, "action"?}`, at most 200 rows; `right` is a piece of text, or at most 4 pieces `{"text", "tone"?}` |
| `buttons` | `items`: `{"label", "action"}`, at most 8 |
| `sections` | Full pages only: `items` (`{"id", "title", "subtitle"?, "badge"?, "state"?, "blocks"}`) and `add` (`{"label", "call", "options"?}`) |
| `form` | Full pages only: `id`, `fields` (`{"key", "label", "hint"?, "control", "value", …}`) and `submit` (`{"label", "call", "params"?}`) |

For example:

```json
[
  {"type": "heading", "text": "This week"},
  {"type": "text", "text": {"zh": "晴 23°C", "en": "Sunny 23°C"}, "tone": "accent"},
  {"type": "pairs", "items": [{"label": "Humidity", "value": "40%"}]},
  {"type": "progress", "value": 0.42, "text": "Indexing 42%"},
  {"type": "list", "items": [{"title": "Build #128", "right": "3m", "state": "doing", "action": {"call": "build.open", "params": {"id": 128}}}]},
  {"type": "buttons", "items": [{"label": "Refresh", "action": {"call": "refresh"}}, {"label": "Details", "action": {"open": "detail"}}]}
]
```

- Text is a string, or a table from language to text (`{"zh": "…", "en": "…"}`, accepting `zh`, `en` and `ja`), and the core picks according to the head's language. A `text` section's text is at most 2000 characters, and any other text at most 200. It is drawn as plain text only: Markdown and HTML are not recognized, and control characters are not allowed (except line breaks in a `text` section).
- `tone` is one of `normal`, `dim`, `accent`, `good`, `warn`, `bad`; the head decides the actual colors from its own color scheme. A list's `state` is one of `todo`, `doing`, `done`, `failed`, `off`; a section's `state` is one of `good`, `warn`, `bad`, `off`.
- `action` has three forms: `{"call": <a method you registered>, "params"?}`; `{"open": <the id of one of your full-page blocks>}`; and `{"copy": <text>}`, which copies the text to the clipboard.
- A whole block has at most 64 sections and at most 64 KiB as JSON; `home` has at most 8 sections; `status` can only be one `text` section of one line, at most 40 columns (a Chinese character counts as two columns).

**Forms on a full page**: the `control` of a `form` is `toggle`, `select` (with `options: [{"value", "label"}]`), `text`, `textarea`, `list` or `number` (which may carry `min`, `max` and `integer`). A `value` of `null` means use the default, and `default` is written `{"text", "value"?}` to tell the head what the default is. When a person clicks save, the head calls your `submit.call` through `package.call`, with the parameters `submit.params` plus `{"values": {only the fields that changed}}`. You may reply `{"saved": true}`; or `{"saved": false, "problems": [{"key", "message"}]}` (each problem is shown under its field); or `{"saved": false, "message"}` (shown under the form). After saving, push the new content with `widget.set` as usual. When the `add` of `sections` is clicked, `add.call` is called with the parameters `{"value": <the chosen item>}`, and you may reply `{"id": <the new item>}`.

### How the two heads draw them

The two heads draw widgets in different ways and with different limits:

| | Terminal | Web UI |
|---|---|---|
| Home | At most 3 blocks, at most 6 rows per block, at most 12 rows together | At most 3 blocks, at most 8 rows per block |
| Sidebar | At most 10 rows per block; placed after the sidebar's own sections | At most 8 blocks in the `Panel`, at most 12 rows per block |
| Footer | At most 3 cells, at most 40 columns per cell | At most 3 cells |
| Full page | Shown in the center; scroll to read | A standalone full page of the software |
| `sections`, `form` | Not drawn | Drawn, can be edited and saved |

When something doesn't fit in the terminal: a list is collapsed the way the to-do list is, `text` is cut off with `…`, and for any other kind, a section that doesn't fit is left out together with all the sections after it; click elsewhere in the block to expand it, and click again to collapse it. The order of sections in the terminal sidebar can be changed in the config file: `tui.side` has one entry per section, and you write your block as `pkg:<package id>/<block id>`.

### Full pages and slash commands

For a full-page block that has `command`, its command is listed in `command.catalog` (with `opens`). When a person types it, `command.run` replies `{"command", "opens": {"package", "widget"}, "said": ""}` and the head opens that page; the command does not go into the session log. Group chats and private chats on chat platforms don't list or recognize this kind of command.

If a slash command only needs to reply with one sentence, write `[[slash]]`: when a person types it, the core calls your `command.call`, and you reply `{"said": "<reply>"}`. For details, see [Writing an extension](extensions.md).

## Backstage pages

A backstage page is a web page for your package, which you can use for settings, management or looking at data. The manifest picks one of two:

- `[page] dir = "page"`: static files; the directory must contain `index.html`.
- `[page] server = true`: your program starts its own web server.

### Static backstage pages

A static backstage page can be opened from these places: the web UI settings page under `Dashboards`, the terminal `Packages` page under `Backstage` (`Enter` opens it in the browser), and the command line `miyu pkg page <id>` (with `--print` it only prints the URL).

- It can be opened even without the web UI installed: `miyu pkg page` has the core start a backstage page server on `127.0.0.1`, which shuts down after ten minutes with no requests and no open push stream.
- The page sits in an isolated frame and talks to the outside over a message channel. After the frame has loaded, the outside hands in a `MessagePort` with `postMessage({"miyu": "port"}, "*", [port])`, and only once, so the page must be a single page (if you navigate to another page inside the frame, the channel is gone).
- The channel speaks JSON-RPC 2.0, and you can call only the following four methods:

  | Method | Params | Reply |
  |---|---|---|
  | `context` | None | `{"package", "language", "theme", "colors"?}`: your package, the language, and light or dark (`light`, `dark`); in the web UI a few main colors are added |
  | `settings.get` | None | `{"items", "values"}`: your package's config items and their final values |
  | `settings.set` | `{"changes": [...]}`, written like `config.set` | You may only write keys starting with `<your prefix>.`; if there is any other key, the whole request is refused with `forbidden` |
  | `call` | `{"method", "params"?}` | Passed on to your program (`method.call`); the page gets whatever you reply |

  The outside also pushes these messages: `settings.changed` (your config items changed), `theme.changed` (light or dark changed), `package.event` (what your program pushed to the page through `package.emit`) and `resync` (pushes fell behind; pull everything again).
- An example to copy from: `package/page/` of the `memes` package (the channel code is in `app.js`).

### Backstage pages that run their own server

- Only extensions can have this kind of backstage page. Register a `status` method with `package.methods`, and put `web` in the reply: the port the server is actually listening on (leave it out if it isn't listening yet).
- Heads and `miyu pkg page` open `http://127.0.0.1:<port>/#miyu=<…>` from it: after the `#` is JSON `{"v": 1, "ticket", "lang"}` encoded as base64url (without `=`), and `ticket` is a one-time login ticket valid for 60 seconds. Your server exchanges it for a device token: on the extension's connection, call `login.redeem {"ticket"}`, which replies `{"login": {"token", "expires"}}`; from then on, the server connects to the core on the page's behalf with this device token (the handshake credential `login`).
- To get a ticket yourself (for example to reopen a page that has expired): declare the capability `login.page` and call `login.ticket {"via": "page"}` on the extension connection. This kind of ticket can only be exchanged on a connection from this machine; ask for and exchange tickets only for requests you have checked came from this machine, and pages from elsewhere always use the access password. The rules to follow are in "Signing in pages on this machine" in the [extension reference](../reference/extensions.md).
- Example: the `im` package that connects chat platforms (its manifest is `im/package.toml`).

## A row in the tray menu

The manifest looks like this:

```toml
[page]
dir = "page"

[tray]
name = { zh = "打开时钟后台", en = "Open Clock" }
```

With this, the tray menu gets one more row, and clicking it opens your backstage page in the browser (the same as `miyu pkg page <id>`). Each package can have only one row, and it can only open its own backstage page. Not writing `[page]`, or writing a field other than `name`, gets `bad_tray`. The package must be installed and turned on for the tray to list it.

## Front-end packages in the web UI

The shipped web UI is put together from web packages (each is a `manifest.json` plus an `index.js`). The only thing a third party can bring into the web UI is the `[theme.web]` of an appearance package, whose publicly documented uses are color schemes, themes and mascots (see [Writing themes and appearance](themes.md)). For adding other functions to the web UI (new panels, buttons, pages), there is currently no way open to third parties: use the widgets and backstage pages above.

## Example: a clock in the sidebar

The following writes an extension that puts a `Time` block in the sidebar showing the current time and date, refreshed once a minute. It is written with the Python development kit `miyu_ext` (see [Writing an extension](extensions.md#using-a-development-kit)).

1. Create the directory and copy the development kit's `miyu_ext.py` into `bin/`:

   ```text
   clock/
   ├── package.toml
   └── bin/
       ├── miyu-clock      # the program below, executable on Linux and macOS
       └── miyu_ext.py
   ```

2. Write `package.toml`:

   ```toml
   [package]
   version = "0.1.0"
   protocol = [1, 1]
   name = { zh = "时钟", en = "Clock" }
   summary = { zh = "侧边栏显示现在几点", en = "Shows the time in the sidebar" }

   [command]
   name = "clock"
   program = "miyu-clock"
   about = { zh = "时钟扩展", en = "Clock extension" }

   [process]
   args = ["serve"]
   capabilities = ["widgets"]

   [[widget]]
   id = "now"
   place = "sidebar"
   title = { zh = "时间", en = "Time" }
   ```

3. Write `bin/miyu-clock`:

   ```python
   #!/usr/bin/env python3
   """A clock in the sidebar: pushes the current time once a minute."""
   import os
   import sys
   import threading
   import time

   sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))

   from miyu_ext import Extension  # noqa: E402

   ext = Extension("clock", "0.1.0")
   wake = threading.Event()

   @ext.on("widget.watch")
   def watched(params):
       wake.set()                     # someone started watching: push right away

   @ext.ready
   def tick():
       while True:
           now = time.localtime()
           ext.call("widget.set", {"widget": "now", "content": [
               {"type": "text", "text": time.strftime("%H:%M", now), "tone": "accent"},
               {"type": "pairs", "items": [
                   {"label": {"zh": "日期", "en": "Date"}, "value": time.strftime("%Y-%m-%d", now)},
               ]},
           ]})
           wake.wait(60 - now.tm_sec)     # until the next minute, or until someone starts watching
           wake.clear()

   if __name__ == "__main__":
       if sys.argv[1:] == ["serve"]:
           ext.run()
       else:
           print("usage: miyu-clock serve (started by the Miyu core)", file=sys.stderr)
           sys.exit(2)
   ```

   On Windows this same file works as is: when the core doesn't find `bin/miyu-clock.exe`, it starts the file with the `python` in `PATH`, found from the `#!` on the first line, and no executable permission is needed. The file name follows `program` in the manifest, `miyu-clock`, without `.py`; Python 3 must be installed, with `python` findable in `PATH`. See [Writing a Miyu package: three platforms](packages.md#three-platforms).

4. Install: `miyu pkg install ./clock`. The screen lists the capability `widgets` it needs; answer `Y`. When it asks `Enable 'clock' now? [Y/n]`, answer yes too.
5. Look at the result:
   - Terminal: widen the window to 120 columns or more, and the sidebar on the right gains a `Time` section, with `14:05` in the accent color on the line below and a line `Date 2026-11-14` after that.
   - Web UI: open the `Panel` in the right column, and there is a `Time` block with the same content as in the terminal.

If it doesn't appear: first check on the `Packages` page whether it is running, then look at `var/log/clock/stderr` in the data root (`~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows).

## Troubleshooting

Common problems and what to do about them:

| What you see | What to do |
|---|---|
| `widget.set` replies `bad_widget_content` | `data.path` tells you where the mistake is (for example `content[1].items[0].label`), and `data.problem` says which kind: `type`, `missing`, `too_long`, `too_many`, `too_big`, `control_char`, `tone`, `state`, `value`, `action`, `place`, `unknown`, `duplicate` |
| `widget.set` replies `unknown_widget` | `widget` isn't one of the `id`s written in the manifest |
| `widget.set` replies `bad_params` | A block that follows a session has no `session`, or a global block has one |
| Calling a method replies `needs_approval` | `capabilities` in the manifest doesn't list `widgets` (or whichever other capability it is); add it and install again |
| The block says `<software name> is not running` (terminal) or `Not running` (web UI) | The program isn't running: on the `Packages` page, look at the reason and the last few lines of stderr |
| The row isn't in the tray | The package isn't turned on, or the backstage page's `index.html` doesn't exist |
