# Writing an extension

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

An extension is a standalone program, written in any language you like. The core starts it and talks JSON-RPC 2.0 with it over stdin and stdout, one message per line. The extension shakes hands first, then registers its tools; when the AI calls one of those tools, the core in turn asks the extension to carry it out. Every method is described in full in [protocol reference: extensions](../reference/extensions.md).

## A minimal extension

A minimal extension has just two files: a manifest and a program.

```text
hello/
├── package.toml
└── bin/
    └── miyu-hello
```

`package.toml`:

```toml
[package]
protocol = [1, 1]
name = { en = "Hello", zh = "打招呼" }

[command]
name = "hello"
program = "miyu-hello"
about = { en = "Hello extension", zh = "打招呼扩展" }

[process]
args = ["serve"]
capabilities = ["tools"]

[settings.greeting]
type = "text"
max = 40
default = "Hello"
layers = ["system"]
applies = "now"
name = { en = "Greeting", zh = "问候语" }
```

`bin/miyu-hello` (written in Python; on Linux and macOS, run `chmod +x` on it to make it executable):

```python
#!/usr/bin/env python3
import json
import sys

TOOLS = [{
    "name": "hello_greet",
    "description": "Greet someone by name.",
    "input_schema": {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]},
    "access": "read",
    "venues": ["local"],
    "display_name": {"en": "Greet", "zh": "打招呼"},
    "subject": "name",
}]


def send(message):
    sys.stdout.write(json.dumps(message, ensure_ascii=False) + "\n")
    sys.stdout.flush()


def serve():
    send({"jsonrpc": "2.0", "id": "h1", "method": "hello",
          "params": {"protocol": [1, 1], "head": {"kind": "hello", "version": "0.1.0"}}})
    greeting = "Hello"
    for line in sys.stdin:  # when standard input reaches its end, the core is asking you to exit
        message = json.loads(line)
        if message.get("id") == "h1":
            if "error" in message:
                sys.exit(1)  # the handshake was refused, and restarting won't help
            greeting = message["result"].get("config", {}).get("hello.greeting", greeting)
            send({"jsonrpc": "2.0", "id": "p1", "method": "provide", "params": {"tools": TOOLS}})
        elif message.get("method") == "extension.config":
            greeting = message["params"]["keys"].get("hello.greeting") or "Hello"
        elif message.get("method") == "tool.call":
            name = message["params"]["args"].get("name", "there")
            send({"jsonrpc": "2.0", "id": message["id"],
                  "result": {"blocks": [{"type": "text", "text": f"{greeting}, {name}!"}]}})


if __name__ == "__main__":
    if sys.argv[1:] == ["serve"]:
        serve()
    else:
        print("usage: miyu hello serve (started by the Miyu core)", file=sys.stderr)
        sys.exit(2)
```

To install and try it, run `miyu pkg install ./hello`, answer yes when asked "Turn it on now?", then ask the AI to "say hello to Ann". An extension written in Python can be used as is like this on all three platforms: start `bin/miyu-hello` with `#!/usr/bin/env python3`, make it executable on Linux and macOS, and on Windows the core finds `python` from that line. If your extension needs Python 3 installed, please say so in the package's description.

## Using a development kit

The extension above is written by hand: the protocol doesn't care about the language, so any language can be used this way. If you use Python or Rust, you can use the ready-made development kits, [miyu-agent/miyu-sdk](https://github.com/miyu-agent/miyu-sdk) (Apache-2.0). They already handle the handshake, sending and receiving one message per line, answering concurrent calls by their ids, cancellation, settings pushes, quitting when standard input ends, and the exit-code-1 rule. The kits add no powers of their own: what an extension can do is still set by the protocol. Each kit also comes with a fake core, so you can test without starting Miyu.

**Python**: the kit is a single file, `miyu_ext.py`, which uses only the standard library and works with Python 3.9 or later, without pip. Copy it into the package's `bin/`, next to your program; the manifest is the same as the one above:

```text
hello/
├── package.toml
└── bin/
    ├── miyu-hello        # your program, whose first line is #!/usr/bin/env python3
    └── miyu_ext.py       # the file copied from the kit
```

```python
#!/usr/bin/env python3
import os, sys
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from miyu_ext import Extension

ext = Extension("hello", "0.1.0")

@ext.tool("hello_greet", "Greet someone by name.",
          {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]},
          access="read")
def greet(args, call):
    return f"{ext.config.get('hello.greeting', 'Hello')}, {args['name']}!"

if __name__ == "__main__":
    ext.run()
```

This one file runs on all three platforms, just like the hand-written one above. Settings are in `ext.config`, and you call core methods with `ext.call(method, params)`.

**Rust**: the kit is the crate `miyu-ext`, which is synchronous and depends only on `serde_json`. It isn't published on crates.io, so depend on a version tag of the repository:

```toml
[dependencies]
miyu-ext = { git = "https://github.com/miyu-agent/miyu-sdk", tag = "v0.1.0" }
```

The kit's own guide lists the available versions. Put the built program in the package's `bin/`; on Windows its file name is `miyu-hello.exe`.

**Testing**: the fake core `FakeCore` plays the core inside your process, so you don't need to start Miyu:

```python
from miyu_ext import FakeCore
core = FakeCore(ext, config={"hello.greeting": "Hi"})
assert core.call_tool("hello_greet", {"name": "Ann"})["blocks"][0]["text"] == "Hi, Ann!"
core.close()
```

How to write slash commands, methods and pushes, the Rust example, and the full example package are all in the kit's own guide, so they aren't repeated here.

## Being started

This section explains what the core gives an extension when it starts it: the program, its arguments, environment variables and folders.

- The program the core starts is the one in `bin/`, and its arguments are `[process] args`.
- The environment is inherited from the core, plus `MIYU_HOME` (the data root), `MIYU_RESOURCES`, `MIYU_PROGRAM` (the real path of the main `miyu` program: to start the core, run `$MIYU_PROGRAM core`; don't look beside your own binary, because a package installed into the data root has no main program next to it), and your package's own folder in each part of the data root. These folders are all already created and given as real paths:
  - `MIYU_APP_DIR`: your package folder (find the files your package brings from here; don't build paths yourself);
  - `MIYU_CONFIG_DIR`: configuration that people edit by hand (`etc/<id>/`; it is kept when the package is removed and read again on reinstall, and only `miyu pkg remove --purge` deletes it);
  - `MIYU_STATE_DIR`: data that must be kept, such as databases and logins (`var/lib/<id>/`; it is also the working directory when the core starts you);
  - `MIYU_CACHE_DIR`: data that can be made again after it is deleted (`var/cache/<id>/`);
  - `MIYU_LOG_DIR`: your own logs (`var/log/<id>/`; the core keeps your standard error here as `stderr` and `stderr.old`, so don't use those two names);
  - `MIYU_TMP_DIR`: short-lived scratch files (`tmp/<id>/`, emptied before each start);
  - `MIYU_RUNTIME_DIR`: locks, sockets, addresses and other files that only mean something while running (`run/<id>/`);
  - `MIYU_PICTURES_DIR`, `MIYU_VIDEOS_DIR`, `MIYU_DOCUMENTS_DIR`, `MIYU_DOWNLOADS_DIR`: files meant for the person go here.

  The same set of variables is given when a person runs `miyu <your command>` in a terminal. The old names `MIYU_PACKAGE_DIR` (same as `MIYU_APP_DIR`) and `MIYU_PACKAGE_STATE` (same as `MIYU_STATE_DIR`) are still set during the transition and go away in the next release.
- Keep your files apart in the categories above; all of these folders are removed on uninstall (the four for the person are not, and the config directory is kept by default as pacman does: the confirmation screen before removing says `Config kept in <path>`, and only `--purge` deletes it, with the screen saying `Will delete <path>`). Put what people edit in `MIYU_CONFIG_DIR`, which is still there after a remove and reinstall; put your own state in `MIYU_STATE_DIR`, which is deleted with the package. Don't keep people's data in `MIYU_STATE_DIR`: the confirmation screen before removing says `Will delete <path> (<size>)`, and once it is deleted it is gone; put what should stay with the person in `MIYU_DOCUMENTS_DIR` (`root/documents/`) and the other places people can see. Always find these folders through the variables: don't rely on the working directory (it is `MIYU_STATE_DIR` when the core starts you, but the person's current directory when they run your command), and don't build paths under `MIYU_HOME` yourself.
- Only your extension itself and the commands people run get these variables: commands and script tools the AI runs don't get them (script tools have their own set of folders, see [Scripts](scripts-skills.md)), and the AI's file tools can't reach these folders in the data root either.
- Your stderr goes to `~/.miyu/var/log/<id>/stderr` (inside `MIYU_LOG_DIR`); when something goes wrong, look there first.

## Handshake and settings

The first message your extension sends is `hello`, without any credentials. The core's response contains:

- `config`: the final values of your package's settings (for example `{"hello.greeting": "Hello"}`; secrets are given as their real values, and unset keys are left out). **Don't read config files yourself.**
- `language`: which language to use for the text you show to people (`zh`, `en`, `ja`).

When the settings change later, the core sends the notification `extension.config {"keys": {"hello.greeting": "Hi"}}`, which contains only the keys that changed; a key that became unset has the value `null`. An extension that hasn't finished the handshake within 10 seconds of connecting is disconnected.

**Using a model key the owner already set up**: declare `provider.key` in the manifest and write `[provider_key] catalog = "deepseek"` (see `[provider_key]` in [the manifest](manifest.md)). Once the owner approves it, `config` has one more field, `"provider_key": "<that provider's key>"`. The field is absent when the owner hasn't set up that provider, or when that provider has no key. When the owner changes the key, the core sends `extension.config {"keys": {"provider_key": "<new one>"}}`, and it sends `null` when the owner removes the provider or its key. What you get is the real key: keep it in memory only, never write it to logs or files, and never pass it on to anyone.

## Registering tools: `provide`

After the handshake, send `provide`. Its `tools` is **all** the tools you provide now, and each time you send it, it replaces the previous set as a whole. A tool has these fields:

| Field | Notes |
|---|---|
| `name` | Made of letters, digits, `_` and `-`, 1 to 64. It must not clash with other tools; prefixing it with the package id is recommended. |
| `description`, `input_schema` | Content for the model: short English sentences, at most three per tool. |
| `access` | Required. It says what the tool touches: `read` (only looks, and stays inside Miyu), `write` (changes files), `execute` (runs commands), `network` (goes online), `outbound` (sends things out of Miyu), `venue` (takes actions on a chat platform, such as recalling a message or muting someone). The permission policy decides from it whether to ask a person, so **be honest**: a tool that changes your own data (adding or deleting a ledger entry) is `write` too, or read-only mode can't stop it. |
| `venues` | Required. It says which sessions get the tool: one or more of `local` (sessions on this machine), `private` (private chats on platforms) and `group` (groups). |
| `plugin` | The name of a venue plugin, written like a package id. In groups and private chats the tool is offered only where that venue has the plugin switched on; local sessions get it as usual. When it isn't written, the tool is always offered. |
| `timeout_ms` | From 1000 to 600000, 60000 by default. |
| `display_name` | The name shown to people, per language: `{"zh": "打招呼", "en": "Greet"}`. |
| `subject` | Which argument's value the timeline shows after the name, for example `Greet · Ann`. Tools that search, or that act on a particular file or id, should set it: without it the timeline shows only the name, and nobody can tell what was searched for or which one was touched. |
| `clicall` | `true` means the AI can also call the tool with `miyu call` from a script it writes in a command, and the result goes to the script. Only read, network and execute tools can be called this way; when it isn't written, the tool can't be. Tools that read or look things up, and that the AI can't easily do from a command on its own, should set it: the AI can then call them in bulk from a script and skip many round trips. Don't set it on tools that change or send things. A tool with a structured result puts that result in the answer's `data`, and the script gets one line of JSON. |
| `result` | When there is a structured result, the shape of that result, in one line, such as `{"items":[{"id","title"}]}`: it tells the AI which fields a script can take directly (`miyu call --schema` prints it too). When it isn't written, there is none. |
| `role` | What the tool is for: `read_file` means the tool reads a text file (the path is given as a parameter). The core recognizes tools by their role, not by their name, so if you replace the file reader, the AI still sees the skill list. When it isn't written, there is none. |
| `scope` | Narrows further, within `venues`, which sessions get the tool: `local` (sessions on this machine), `local_main` (the main session on this machine, not subagents), `local_main_attended` (the main session on this machine with someone watching, e.g. a tool that asks the user), `spawn` (a tool that starts subagents). When it isn't written, it is `any`. |
| `paths` | Which arguments are file paths, and whether they are read or written: `[{"parameter": "file_path", "write": true}]`. Every tool that reads or writes files should set it: the core runs the permission check from it (writing outside the workspace asks a person), and only then are the file effects you report taken. See **Tools that change files** below. |
| `background_parameters` | Names of arguments that only make sense when the session can run things in the background (such as `["run_in_background"]`): in sessions with background running switched off, the parameter schema the AI sees doesn't have them. These arguments must be optional. |
| `runs_commands` | `true` means this tool runs commands (for example a tool that replaces the built-in `shell`, or one that runs commands in a container). The manifest must declare the capability `tools.commands` and a person must approve it, or the whole `provide` returns `needs_approval`. See **Tools that run commands** below. |

If anything is wrong, the whole set is rejected, and the response's `data` says which tool and what is wrong (`{"tool": "hello_greet", "problem": "name"}`).

## Being called: `tool.call`

When the AI calls one of your tools, the core sends `tool.call`:

```json
{"jsonrpc":"2.0","id":"core-1","method":"tool.call","params":{"session":"…","call_id":"…","tool":"hello_greet","args":{"name":"Ann"},"cwd":"/home/me/src","owner":true}}
```

Your response looks like this:

```json
{"jsonrpc":"2.0","id":"core-1","result":{"blocks":[{"type":"text","text":"Hello, Ann!"}]}}
```

- `args` are already corrected against your `input_schema`. `by` is who asked the AI to do it, and `owner` is whether the core recognizes that person as the owner. If a tool acts in groups, it is up to you to decide from these two fields who may use it.
- `blocks` is the content for the model: text is written as `{"type": "text", "text"}`; for an image, upload it with `blob.put` first, then put `{"type": "image", "blob", "media_type", "width", "height"}`. An image your package ships can simply be uploaded with `{"path": "<MIYU_APP_DIR>/files/cat.png"}` (other files in the data directory are refused).
- Where to save images you draw or generate: calls inside a session carry one more field, `pictures`, which is the picture folder in the data root (a real path that may not exist yet, so create it before writing). Images saved there can be found by people in the terminal UI and the web UI. Without that field (calls outside a session, venue sessions such as groups and private chats, older cores), keep saving to the workspace: because a venue session can only reach its own workspace, an image saved elsewhere couldn't be read or sent by the AI.
- On failure, still return a result, with `error: true` and the reason written for the model; returning a JSON-RPC error also counts as a failure.
- To have the AI "send" an image (stickers and the like, drawn in the reply and sent as an image on chat platforms), add `"sent": [{"blob", "media_type", "width", "height", "alt"?, "sticker"?}]` to the result, with at most 4 images. The AI doesn't see `sent`.
- To have heads (the UI programs that connect to the core, such as the terminal UI and the web UI) draw the result as a card, add `detail` to the result in one of the three common shapes: a link list `{"kind": "links", "links": [{"title", "url", "snippet"?}]}`, a table `{"kind": "table", "columns": [...], "rows": [[...]]}`, or images `{"kind": "images", "images": [{"blob", "media_type", "caption"?}]}`. The AI doesn't see `detail`; if the shape is wrong, the core drops the field and writes a line `tool detail dropped` to the run log. Fields and limits are in the [protocol reference](../reference/extensions.md#toolcall-toolcancel).
- For a tool with `clicall`, to give scripts a structured result, add `data` to the answer, which can be any JSON (for example `{"items": [...]}`; when nothing is found, send the same shape with an empty list, so that scripts that parse it as JSON don't break). When the AI calls the tool with `miyu call` inside a command, the script gets that `data` as one line of JSON; without `data` it gets the text in `blocks`. The AI doesn't see `data`, and it isn't passed on when `error` is true.
- Several `tool.call`s may be in flight at the same time; answer each one by its `id`.
- After `timeout_ms` has passed, or when a person interrupts, the core sends the notification `tool.cancel {"session", "call_id"}`: drop that call when it arrives.

## Tools that change files

If you write an editor, formatter, renamer or similar tool of your own and want it to work like the built-in `edit`, with the lines added and removed shown on the timeline, a diff you can view, and the AI not having to re-read a file you changed, follow these steps:

1. Declare `paths` in the tool's spec, saying which argument is a path and whether it is written, and set `access` to `write`:

   ```json
   {"name": "my_edit", "access": "write", "venues": ["local"],
    "input_schema": {"type": "object", "properties": {"file_path": {"type": "string"}, "old": {"type": "string"}, "new": {"type": "string"}}, "required": ["file_path", "old", "new"]},
    "paths": [{"parameter": "file_path", "write": true}]}
   ```

   The argument must be a top-level one in `input_schema.properties`, and its type is a string or an array of strings (each item of an array counts as one path). The core runs the permission check from it, as it does for the built-in `edit`: with read-only on, every write is refused; reads are allowed at both levels; the data root gets no extra protection and is judged by the permission level like any other folder; in a venue session confined to its own workspace, reads and writes whose real path is outside the workspace and the added folders are all refused (the data root included). You get no `tool.call` for a refused call. Without `paths`, the core doesn't know which files you touch, and none of the file effects you report are taken.
2. `tool.call` carries one more field, `checked`: the real locations the check approved, in the order of the paths in the arguments. Write to these locations: resolve the path from the arguments to a real location yourself (relative paths against `cwd`, `~` as the home directory, following links), and don't touch it unless it is in `checked`, because a link on the way may have been swapped after the check, and writing there would not be what the person agreed to.
3. Add `effects` to the answer, saying only *which* file and what happened to it; the core reads the contents itself:

   ```json
   {"blocks": [{"type": "text", "text": "Edited a.txt."}], "effects": [{"kind": "file.changed", "path": "a.txt"}]}
   ```

   - `file.changed {"path"}`: the file was changed or created. The before is the copy the core read before sending `tool.call`, and the after is what the core reads again once you answer; if the two are the same, the effect isn't taken. For an extra check you may add `before`, `after` (hashes starting with `sha256:`) or `before_text`, `after_text`; anything that doesn't match isn't taken.
   - `file.read {"path", "lines"?}`: the file was read (`lines` is `[from, to]`, counted from 1, with from not above to). Before the AI changes a file, the core checks against this whether the AI has seen it.
   - `file.trashed {"path", "trash"}`: the file was moved to the trash; `trash` is where it is in the trash, and is only shown to people.
   - `todo.written {"todos", "done"?}`: a whole new to-do list, written the same way as for the built-in `todowrite` (for tools that replace it).
   - Paths must be in `checked`, and paths that are changed or trashed must have been checked as writes. Other kinds, unchecked paths and malformed items are dropped one by one, and the result is still handled as usual; the core writes a line `tool effect dropped` to the run log, and its `why` helps when you debug.
   - If you fail halfway, still answer `error: true` and report the files you did change, because those changes really happened.
4. Undo doesn't put files back (it doesn't for the built-in tools either); it only rolls back what the AI has seen. So after a turn is undone, the AI has to re-read that file before changing it again.

## Tools that run commands

If you write your own tool that runs commands (replacing the built-in `shell`, or running commands in a container or on another machine) and want the AI to be able to use `miyu call` inside those commands, as with the built-in `shell`, follow these steps:

1. Add `tools.commands` to the manifest's `[process] capabilities` (people see "Tools that run commands" when installing), put `"runs_commands": true` in the tool's spec, and set `access` honestly (usually `execute`). The description the AI sees gets the section on how to use `miyu call` appended automatically, so you don't need to write it yourself.
2. When the session has tools the AI can call from scripts, `tool.call` carries one more field, `channel`: `{"sock", "token", "bin"}`. When you start commands for this call, set them in the commands' environment:

   ```python
   env = dict(os.environ)
   if "channel" in params:
       ch = params["channel"]
       env["MIYU_CALL_SOCK"] = ch["sock"]
       env["MIYU_CALL_TOKEN"] = ch["token"]
       if "bin" in ch:
           env["PATH"] = ch["bin"] + os.pathsep + env.get("PATH", "")
   subprocess.run(command, shell=True, env=env, cwd=params["cwd"])
   ```

3. The commands must be started by your extension process (children and grandchildren are fine): the core follows parent processes up level by level until it reaches yours, and the token alone isn't enough. Commands detached with `setsid` or a double `fork`, or handed to some other long-running process, can't call (exit code 2). This rule guards against mistakes (a token leaked to another process, a command that detached and keeps calling), not against your extension: you can call just by starting a child process. The real gate is step 1, `tools.commands`, which a person approves.
4. The channel closes as soon as you respond to the call, so `miyu call` in a command must finish before you respond. Commands still running in the background after your response can't call (exit code 3).
5. Tools called from those commands go through the session's permissions and preset, the same as direct calls from the AI, and they are recorded under this call. Commands that people type in the session (`!`) are not handed to you; they go only to the built-in `shell`.

## Writing a model driver

Some model services sign in with a subscription, speak WebSocket or sign their own requests, and Miyu's three built-in drivers can't reach them; your extension can reach them instead. Miyu hands you a request in a unified format; you encode it in the wire format, sign in, send it, parse the response and stream deltas back. Retries, cooldowns, failover and pricing are all handled by Miyu.

Declare the capability `model.driver` in the manifest and write a `[[driver]]` table:

```toml
[process]
capabilities = ["model.driver", "network"]

[[driver]]
name = "relay"          # driver name
cache = "contract"      # the cache hits while the prefix is unchanged; you need to implement driver.encode
key = "required"        # Miyu needs to hand you this provider's key
images = false          # write true if the driver can see images
hosted = ["search_web"] # tools the provider runs on its own (see "Tools the provider runs on its own" below); leave it out if there are none
```

The driver is used only when the owner writes `driver = "<your package id>/relay"` in a provider's settings (the address can be left out). For the models that use it, Miyu sends `driver.call`:

```json
{"jsonrpc":"2.0","id":"core-7","method":"driver.call","params":{"call":"d3","driver":"pi-relay/relay","request":{"tools":[],"system":"…","messages":[{"role":"user","blocks":[{"type":"text","text":"Hello"}]}],"stable":0},"fingerprint":{"tools":"…","system":"…","messages":["…"]},"params":{"model":"relay-pro","max_output":4096},"key":"sk-…"}}
```

Each time part of the model's reply comes in, send a `driver.delta` notification (with no `id`), and answer at the end:

```json
{"jsonrpc":"2.0","method":"driver.delta","params":{"call":"d3","deltas":[{"start":{"index":0,"kind":"text"}},{"text":{"index":0,"text":"Hi!"}}]}}
{"jsonrpc":"2.0","method":"driver.delta","params":{"call":"d3","deltas":[{"end":{"index":0}}]}}
{"jsonrpc":"2.0","id":"core-7","result":{"usage":{"uncached":12,"cache_read":0,"cache_write":0,"output":3},"sent":"sha256:…"}}
```

- **Encode from the params only**: no time, no random numbers, fields in a fixed order, and don't encode `call`. The same request must give the same bytes for the prefix cache to hit. Report the hash of the bytes you actually sent in `sent`; if the same request gets a different `sent` twice, Miyu logs a warning.
- **Report errors by class**: `{"error": {"class", "message", "retry_after_ms"?}}`, where `class` is one of `retryable`, `rate_limited`, `context_too_long`, `auth`, `quota`, `content_policy`, `unclassified`. Don't retry a call yourself after you have sent deltas (the reply would repeat); Miyu retries and fails over by class. Before any delta is sent, handle failed connections and token refreshes yourself.
- **Private data** (reasoning signatures, the provider's own call ids) is sent as `{"private": {"index", "data"}}`; later requests hand it back to you as is, and other drivers never see it. `hosted_tool` blocks in the request (tools the model ran on the provider's side) are told apart the same way: a block carrying your private data comes to you as is, and any other becomes a `text` block holding the text Miyu writes for the model.
- **Time limits**: from sending to the first delta, between two deltas, and from the last delta to the answer, no wait may exceed the idle limit (from 180 seconds up, scaled by reasoning effort; if the first token often takes a long time, write `quiet_secs` in the `[[driver]]`, up to 900 seconds). When the limit is passed, or when the person interrupts, Miyu sends `driver.cancel {"call"}`; send nothing more for that call.
- **Keys**: you only get the one key in this provider's settings, and a driver that declared `key = "none"` gets none. Tokens you get by signing in yourself belong in your own data directory.

**Check that your encoding is steady**: implement `driver.encode` (with the same params as `driver.call`; answer `{"body": "<the bytes you would send>"}` without actually sending), then run `miyu dev driver-check <your package id>`. Each sample is encoded twice, once more after restarting your program, and once more with one more message added at the end; if any byte doesn't match, the check fails. A driver that declares `contract` must pass this check.

**List models** (optional): implement `driver.models` (its params are `{"driver", "key"?, "base_url"?}`) and answer `{"models": [{"id", "window"?, "max_output"?, "tools"?, "vision"?}]}`. The models then show up in the owner's model list, with the window, maximum output, tool use and image support you report (values the owner writes by hand win over yours). If you don't implement it, the owner writes model names by hand.

Every param, delta and error is described in detail in the [protocol reference](../reference/extensions.md#drivercall-driverdelta-drivercancel).

### Tools the provider runs on its own

Some providers and agent CLIs run tools on their own side (searching, reading web pages) and then carry on writing the reply; Miyu doesn't run these tools and can't stop them. Report them as they happened, so that the person sees on the timeline what the model searched for, and a different model can pick up from there:

```json
{"jsonrpc":"2.0","method":"driver.delta","params":{"call":"d3","deltas":[{"start":{"index":0,"kind":{"hosted_tool":{"name":"search_web"}}}},{"text":{"index":0,"text":"{\"query\":\"rust\"}"}}]}}
{"jsonrpc":"2.0","method":"driver.delta","params":{"call":"d3","deltas":[{"private":{"index":0,"data":{"step":7}}},{"outcome":{"index":0,"text":"1. Rust https://www.rust-lang.org"}},{"end":{"index":0}}]}}
```

- **How to report**: one block per run. The block's `start` has `kind` set to `{"hosted_tool": {"name"}}`, with the provider's own name as is; the block's `text` is the raw arguments; the result is `{"outcome": {"index", "text", "failed"?}}`, at most once per block and before its `end`, with `"failed": true` when the run failed. The result is text that both the model and a person can read (titles, URLs, excerpts); Miyu cuts it at 64 KiB, and it is better to cut it yourself first. If the run was interrupted and has no result, send no `outcome`.
- **To get it back as is**: send a `private` along with it (anything you like, such as the provider's step id), and later requests hand that block back to you unchanged. Without one, Miyu hands it back to you as a `<hosted-tool name="…">` piece of text, the same one other drivers get.
- **Native tools that change things must not be reported as provider-run tools**: when running commands, writing files or anything else that touches the owner's machine or the outside world happens on the provider's side, it is beyond Miyu's permissions, confirmations and undo. Turn those tools off in the CLI or at the provider, and go through Miyu's tools instead (send an ordinary `tool_call`, and Miyu runs it). Only read-only tools that don't touch the local machine (search, reading web pages) are reported this way.
- **List every name in `hosted`**: put every name you may send in the `[[driver]]`'s `hosted`, so that the owner knows at install time what the provider will run on its own. If you send a name that isn't listed, Miyu still takes it and shows it, and writes a warning to the run log.

## Exiting and crashing

- Stdin reaching its end means "please exit", on all three platforms; an extension that hasn't exited after 5 seconds is killed.
- If the core crashes or is killed, you and the processes you started end with it: on Unix the whole process group ends (processes that left with `setsid` or moved to another process group are not covered), and on Windows everything in the same job object ends. Don't count on finishing any cleanup at that moment.
- Exiting on your own (exit code 0 included), a failed handshake, or a closed stdout each counts as a failure; the core restarts you after 1, 2, 4, 8 and 16 seconds, and stops after 5 failures in a row.
- **Exit code 1 is for problems a restart won't fix, like bad config or a taken port**: the core stops at once without retrying, and waits for the person to fix the problem and turn you on again.
- Once you have been running for 60 seconds in a row, the failure count starts over at the next failure.

## More abilities

Each of the abilities below needs the matching capability declared in the manifest (see [The manifest](manifest.md)).

**Your own slash commands** (`commands`): declare `[[slash]]` in the manifest. When a person types one of your commands, the core sends `command.call {"command", "argument", "text", "session", "by", "owner", "language"}`; answer `{"said": "<reply, may span lines>"}`, and that text is shown to the person as is. Your program must `provide` once after it starts (an empty list if you have no tools) so that the core recognizes your connection.

**Being a search provider** (`search`): declare `[[search]]` in the manifest. When a person has picked you in the settings and the AI searches the web, the core sends `search.query {"source", "query", "want", "allowed_domains", "blocked_domains"}`; answer `{"hits": [{"title", "url", "snippet"?, "date"?}]}`. When you are rate limited, answer with an error whose `data.reason` is `limited`, and the core lets you rest for a while. As above, `provide` once first.

**Adding a few lines to the AI's context at the start of a turn** (`context.inject`): at the start of every turn the core sends `user.append {"session", "venue", "text"?}`; answer within 300 ms with `{"content": [{"kind", "text"}]}` (at most 3 blocks), or with `{"content": []}` when there's nothing to add. The core only asks extensions that have a tool in the session's tool set. This text is for the model: write short English, wrapped in an XML tag.

**A check before tool calls run** (`tool.guard`): write `[guard]` in the manifest, listing the tool names and access classes you want to be asked about (see [Manifest](manifest.md)). After one of the AI's calls passes the permission policy and before it runs, the core sends `tool.guard {"session", "call_id", "tool", "args", "access", "cwd", "owner", "venue"}`; answer `{"verdict": "allow"}`, `{"verdict": "deny", "reason": "<why>"}` or `{"verdict": "ask", "reason": "<why>"}` (the person confirms). On a deny the AI sees `Blocked by <your package id>: <reason>`, with the reason cut to 300 characters and escaped into one line: write the reason as one English sentence saying why and what to change (a guard doesn't change arguments; if they need changing, let the AI call again). An allow adds nothing to the context. This needs no `provide`.

- Answer fast: the person waits on this step, so aim for a p95 under 20 ms; no answer within `timeout_ms` (1 second when it isn't written) counts as a deny.
- While you aren't running (starting, or crashed), every call you guard is denied: a failing guard fails closed. Don't load your rules slowly after the handshake.
- When the person interrupts or you time out, the core sends `guard.cancel {"session", "call_id"}`, and you no longer need to answer that call.
- When there are several guards, all of them are asked, and one deny is enough to deny; you can only tighten the permission policy, never loosen it.

**Logging after tool calls** (`events.read`): write `[after]` in the manifest, listing the tool names and access classes you want to receive (see [Manifest](manifest.md)). Once a call's result is written to the session, the core sends the notification `tool.after` (with no `id`; don't answer it). It is read-only: you can't change the result, and nothing reaches the AI's context. Direct calls and calls from scripts (`miyu call`) come in different shapes; tell them apart by whether `blocks` is present:

```python
def on_tool_after(params):
    if "blocks" in params:
        # a direct call: call_id looks like call_12_1, and blocks is what the AI sees
        log(params["session"], params["call_id"], params["tool"], params["status"], params["blocks"])
    else:
        # a call from a script: call_id looks like call_12_1#3, and the result is only a blob reference (result, bytes); fetch it yourself with blob.get if you need the content
        log(params["session"], params["call_id"], params["tool"], params["status"], params.get("result"))
    # in both cases args is a JSON string (not an object): to read the arguments, call json.loads(params["args"]) yourself
```

- The core doesn't wait for you: each extension has one queue of at most 256 notifications; if you read slowly and it fills up, new ones are dropped, and notifications sent while you are crashed or restarting are not resent. **`tool.after` is not guaranteed delivery**: for a complete audit, subscribe to the event stream (`subscribe` `events`).
- You only receive sessions you can reach: an extension that isn't a platform bridge receives local sessions and the owner's own unconfined private chats; a platform bridge receives only venue sessions on its own platforms.

**A section at the end of the system prompt** (`context.system`): call `system.append {"content", "session"?}`. Without `session` it applies to all sessions; `content: null` removes the section. A change makes the whole system prompt be computed again at the next turn, so don't change it often; if you only want a few fixed lines, calling it once at startup is enough.

**Searching by meaning**: call `model.embed {"texts": [...]}` to get vectors (it uses the embedding model the person chose in the settings). If no embedding model is configured you get `embedding_off`; in that case, fall back to keyword search. This needs no extra capability approval.

**Calling a model once**: call `model.call` (for example to have the AI describe an image, with `"use": "vision"`). It spends the person's budget, so use it sparingly. For calls that are made outside the conversation and over and over (deciding whether to reply, scoring), register them in your manifest with `[[side]]` and call with `"side": "<id>"`: the calls then use whatever models the person put in the `lite`, `normal` or `flagship` pool for the registered tier, so the person doesn't need to configure anything for you (see [Manifest](manifest.md)).

**Methods for your page and widgets**: register them with `package.methods {"methods": [{"name": "status"}]}`. When the page or a button calls one, the core sends `method.call {"method", "params"}`, and whatever you answer is what the caller gets. Answer methods you don't recognize with the JSON-RPC error `-32601`.

**Widgets** (`widgets`): declare `[[widget]]` in the manifest. When someone starts looking at one of your widgets, the core sends `widget.watch {"widget", "session"?}`, and when the last viewer leaves, it sends `widget.unwatch`. Only fetch data while someone is looking; don't refresh on a timer. Push content with `widget.set {"widget", "session"?, "title"?, "content"}`:

```json
[{"type":"heading","text":"This week"},{"type":"text","text":{"zh":"晴 23°C","en":"Sunny 23°C"},"tone":"accent"},{"type":"pairs","items":[{"label":"Humidity","value":"40%"}]},{"type":"progress","value":0.4,"text":"Indexing 40%"},{"type":"list","items":[{"title":"Build #128","right":"3m","state":"doing","action":{"call":"build.open","params":{"id":128}}}]},{"type":"buttons","items":[{"label":"Refresh","action":{"call":"refresh"}}]}]
```

Widgets hold text only: Markdown, HTML and color codes aren't recognized. Full-page widgets (`place = "page"`) can also hold editable forms (`sections`, `form`). Every section and form field is described in [protocol reference: widgets](../reference/extensions.md#widgetset-widgetclear-widgetwatch-widgetunwatch).

**Being called by other packages, and calling them**: go through the bus and call by name, without naming the other package (see [The bus](../reference/bus.md)). List the methods other packages may call in the manifest's `[export] methods`, and declare the names under `[export]`: `provides = ["stt"]` means you provide that name (one provider per name), and `plugs = ["tts.engine"]` means you plug into it (several are allowed, and the side using it picks one). Method names are prefixed with the name (`stt.transcribe`) and are still registered with `package.methods`; `bus.list` reports you as `ready` only once all of them are registered. When another package calls you, `method.call` carries one more field, `from` (the caller's package id, which can't be faked). To call other packages, declare `packages.call` and send `bus.call {"name", "method", "params"}` (`method` is the short name, such as `transcribe`; for a `plugs` name, also add `package` to pick which one). You can't reach another package by its id: an extension sending `package.call` with another package's id gets `own_package_only`, and a manifest whose `methods` has an entry outside the names you declare can't be read (`bad_export`). The shapes of well-known names (`stt`, `tts` and so on) are in the reference documents: answer and call in those shapes. Run `miyu bus list` to see who provides what on this machine.

**Reading content other packages bring for you**: when another package writes `[content.<your id>] dir = "…"` in its manifest, it brings you a folder. Call `content.list {}` to see which packages brought something, and `content.read {"package", "path", "offset"?}` to read in chunks; after installs, removals and upgrades the core sends `content.changed`.

**Recording your own events in a session**: call `events.append {"session", "kind": "ext.<your prefix>.<name>", "body"}`. It doesn't start a turn and isn't shown to the model; UIs see it, and so do you when you read the log later. The prefix is `prefix` in your manifest, or your package id when that isn't written.

## Don't

- Don't read or write anywhere else in the data root (sessions, other packages, config files, the secrets file): when you need information, ask through the protocol.
- Methods meant only for people (answering confirmations for the person, changing the permission level, deleting sessions, changing config, installing and removing packages, `extension.*` and so on) are refused when an extension calls them (`local_only`).
- **Declare capabilities honestly**: calling a method whose capability you haven't declared returns `needs_approval`, with the missing one named in `data.capabilities`. What you say without `as` is recorded as said by you (named after the package id), not by the person.
