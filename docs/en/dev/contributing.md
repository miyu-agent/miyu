# Contributing code

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page is for developers who want to propose a change to the core or to a head (a head is an interface program that connects to the core, such as the terminal UI or the web UI). It covers what to read first, how to build, run and pass the gate, and how to write commits and PRs. For where each part lives see [Architecture](architecture.md).

## What to read first

`AGENTS.md` in the root of the core repository holds the rules for the AIs and people who work in the repository; below is only the part that an outside contributor needs to know. The repository's documents are spread across several places:

| Directory | What it holds | When to look |
|---|---|---|
| `internal/blueprint/` | Blueprints: what Miyu looks like now, one page per part, including formats, every cell of the UI, the text shown to the model, and which code it lives in and which tests guard it | Before changing a part, read its page first |
| `internal/designs/` | Design documents: what was decided, why, and what was not chosen; read them by number, starting with `00-设计理念.md` | When you want to know why something is done a certain way, or want to change a settled approach |
| `internal/construction/` | Work orders: how one change is made, which blueprint sections it changes, and how it is accepted; `README.md` is the master table and the work order format | When you want to see which step added a feature and how it was verified at the time |
| `docs/zh/reference/`, `docs/en/reference/`, `docs/zh/dev/`, `docs/en/dev/` | The protocol reference and the developer docs (including the tutorials for writing packages and extensions), in Chinese and English, with the Chinese authoritative | When you changed the protocol or how packages are written |

Development follows the order "blueprint → work order → code": when the design changes, change the blueprint page first, then the code; when merged, the code and the blueprint must match.

## Setting up the environment

Before you build the core, set up the following:

- The Rust toolchain is pinned in `rust-toolchain.toml`: `1.97.0`, with `rustfmt` and `clippy`. Run `rustup toolchain install` in the repository directory to install it.
- The core's three-platform CI installs nothing but the toolchain, so building the core on Linux, macOS and Windows needs no extra system libraries. On Windows the release build uses the MSVC toolchain (`x86_64-pc-windows-msvc`).
- Optional: on Linux, check the clippy findings that only show up on Windows (imports unused only on Windows, code written differently under `cfg`). Install mingw-w64 first, then run:

  ```sh
  rustup target add x86_64-pc-windows-gnu
  cargo clippy --target x86_64-pc-windows-gnu --workspace --all-targets -- -D warnings
  ```

Other repositories need a few more things installed separately: the tray needs `libgtk-3-dev` on Linux (on macOS and Windows the tray repository's CI installs no extra system libraries); the web UI's page tests need Node.

## Build and run

The four steps below take you from building the core to running it with a development data root and stopping it:

1. Build in the root of the core repository:

   ```sh
   cargo build
   ```

   When the build finishes, `target/debug/` holds the main program `miyu`, the sandbox helper `miyu-sandbox`, `miyu-extract` and the watchdog `miyu-watchdog` (all with `.exe` on Windows; on Windows `miyu-watchdog` does nothing and is not packed into the release archive). If you build only `-p miyu`, the sandbox helper stays at the old version, and commands in read-only mode fail with a message saying the helper and the core are not the same build.

2. Create a data root for development, so that your own `~/.miyu` is left alone:

   ```bash
   MIYU_DEV_BASE_URL=https://api.example.com/v1 MIYU_DEV_MODEL=example-chat cargo xtask dev-home $HOME/miyu-dev
   ```

   ```powershell
   $env:MIYU_DEV_BASE_URL = 'https://api.example.com/v1'
   $env:MIYU_DEV_MODEL = 'example-chat'
   cargo xtask dev-home "$HOME\miyu-dev"
   ```

   In PowerShell, variables set with `$env:` stay only in this window, so do the next steps in the same window.

   This command builds the skeleton in `$HOME/miyu-dev` and writes `etc/config.toml`: one provider `dev` (with the driver `openai-chat`) and the default model `dev/example-chat`. The address is read from the environment variable `MIYU_DEV_BASE_URL` and the key from `MIYU_DEV_API_KEY`; neither is written to the file. You can set a different context window with `MIYU_DEV_WINDOW`. If the directory already has a config, it is not overwritten.

3. Run:

   ```bash
   MIYU_HOME=$HOME/miyu-dev MIYU_RESOURCES=$PWD/resources \
     MIYU_DEV_BASE_URL=https://api.example.com/v1 MIYU_DEV_API_KEY=sk-example \
     target/debug/miyu ask "hello"
   ```

   ```powershell
   $env:MIYU_HOME = "$HOME\miyu-dev"
   $env:MIYU_RESOURCES = "$PWD\resources"
   $env:MIYU_DEV_API_KEY = 'sk-example'
   .\target\debug\miyu.exe ask hello
   ```

   In a window where `MIYU_HOME` is set, every `miyu` you run afterwards uses the development data root.

   `MIYU_RESOURCES` points at `resources/` in the source tree, because there is no resources directory next to `target/debug/`. The address and key only take effect if they are in the environment of the process that starts the core; changing the variables after the core has started has no effect.

4. Stop the core of this data root:

   ```bash
   MIYU_HOME=$HOME/miyu-dev target/debug/miyu core stop
   ```

   ```powershell
   .\target\debug\miyu.exe core stop
   ```

### Connecting the terminal UI and the web UI to the core you're developing

Terminal UI: in the root of the `miyu-tui` repository, first install the terminal UI's package into the development data root, then run:

```bash
MIYU_HOME=$HOME/miyu-dev MIYU_RESOURCES=<core checkout>/resources \
  MIYU_DEV_BASE_URL=https://api.example.com/v1 MIYU_DEV_API_KEY=sk-example \
  <core checkout>/target/debug/miyu pkg install ./tui --yes
MIYU_HOME=$HOME/miyu-dev MIYU_RESOURCES=<core checkout>/resources MIYU_CORE_BIN=<core checkout>/target/debug/miyu cargo run
```

```powershell
$env:MIYU_HOME = "$HOME\miyu-dev"
$env:MIYU_RESOURCES = '<core checkout>\resources'
$env:MIYU_DEV_BASE_URL = 'https://api.example.com/v1'
$env:MIYU_DEV_API_KEY = 'sk-example'
<core checkout>\target\debug\miyu.exe pkg install ./tui --yes
$env:MIYU_CORE_BIN = '<core checkout>\target\debug\miyu.exe'
cargo run
```

`miyu pkg install` starts the core and leaves it running, so the address and key variables have to go on that command. When the terminal UI starts a core, it honors only `MIYU_CORE_BIN` and does not look for `miyu` in `PATH`; if a core is already running, it connects even without that variable.

Web UI: in the root of the `miyu-web` repository, build the demo bridge. The bridge serves the page files and forwards the browser's `/ws` to the core:

```bash
cargo build --manifest-path web-demo/bridge/Cargo.toml
MIYU_HOME=$HOME/miyu-dev MIYU_RESOURCES=<core checkout>/resources MIYU_CORE_BIN=<core checkout>/target/debug/miyu \
  MIYU_DEV_BASE_URL=https://api.example.com/v1 MIYU_DEV_API_KEY=sk-example \
  web-demo/bridge/target/debug/miyu-web-bridge 8766
```

```powershell
cargo build --manifest-path web-demo/bridge/Cargo.toml
$env:MIYU_HOME = "$HOME\miyu-dev"
$env:MIYU_RESOURCES = '<core checkout>\resources'
$env:MIYU_CORE_BIN = '<core checkout>\target\debug\miyu.exe'
$env:MIYU_DEV_BASE_URL = 'https://api.example.com/v1'
$env:MIYU_DEV_API_KEY = 'sk-example'
.\web-demo\bridge\target\debug\miyu-web-bridge.exe 8766
```

Then open the link it prints (`http://127.0.0.1:8766/#k=…`). The last number in the command is the port; if you leave it out, it is `8765`. In the web repository's CI, the demo bridge is built and tested on Linux only.

### Making a head use the core code you changed

A head pins one commit of the core through a Cargo git dependency. To make the head build against the core you changed in your local checkout, temporarily add a `[patch]` section to the head's `Cargo.toml`, with one line for each core crate that the head's `Cargo.toml` names directly:

```toml
[patch."https://github.com/miyu-agent/miyu"]
miyu-client = { path = "../miyu/crates/miyu-client" }
miyu-ipc = { path = "../miyu/crates/miyu-ipc" }
```

Do not commit this section. Merge the core change into the core's main first, then change the head's `rev` to that commit.

## The gate

The gate is a set of checks that must all pass before you commit. Run:

```sh
cargo xtask check
```

Local acceptance and the three-platform CI both run this same command. It runs the items one by one and prints a result table at the end; if any item fails, it exits with a non-zero code. What each item checks:

| Item | What it checks | If it fails |
|---|---|---|
| Format | `cargo fmt --all --check` | Run `cargo fmt --all` |
| clippy | `cargo clippy --workspace --all-targets -- -D warnings`; the workspace forbids `unwrap` (allowed in tests), forbids swallowing errors with `let _ =` and `.ok()`, and forbids `unsafe` | Fix what it reports; if you really need to discard a result, write `#[expect(..., reason = "...")]` |
| clippy (core without optional packages) | `cargo clippy -p miyu-core --no-default-features -- -D warnings`: the core must also build with `mermaid` and `net` turned off; CI runs this item on Linux only, but you must still run it locally | Put code used only by an optional package behind the matching `cfg(feature)` |
| Docs | `cargo doc --workspace --no-deps --document-private-items`, with warnings treated as errors; it also runs the seven checks below | Fix broken doc links and malformed syntax |
| Docs: ledger | Every file under `resources/` that the model sees is registered in the ledger in `internal/designs/26-提示词.md`, and its fingerprint (the first 8 hex digits of the SHA-256 of the file's bytes) matches | For a new or changed file, add a row to the ledger or change its row: file, where it goes, when it was added, tokens, why it was added, fingerprint |
| Docs: prompts page | `internal/blueprint/prompts.md` agrees with the ledger and the resources | Run `cargo xtask prompts` to regenerate it |
| Docs: sample blocks | A code block in a blueprint marked `样本` ("sample") is identical, character for character, to the file it points to | Change both sides together |
| Docs: `heads.toml` | Exactly two tables, `tui` and `webui`, each with only `repo` and `rev`; the repository is under `miyu-agent`; `rev` is a full commit id or a tag starting with `v` | Write it that way |
| Docs: protocol reference | Every method the code dispatches has an entry in both the Chinese and the English reference; every method written as a heading in the reference exists in the code; every `#anchor` in `docs/zh/reference/` and `docs/en/reference/` finds a matching heading | Add the reference entry, in both languages |
| Docs: what extensions can call | Every method the code dispatches is listed in the table in `crates/miyu-endpoint/src/connection/rights.rs`, stating whether extensions may call it | Add a row to the table |
| Docs: the frozen method list | `internal/blueprint/methods-v1.txt` matches the code: it reports methods that are in the snapshot but gone from the code (deleted or renamed), and it also reports methods newly added to the code | For a new method, run `cargo xtask methods` to register it; an existing method cannot be deleted or renamed |
| Layers | Every crate is registered in the code layering table in `internal/designs/01-架构.md`, and depends only on its own layer or a lower one; the external dependencies of the two pure-logic layers must come from an allowlist | Register a new crate in the table; move the dependency to the right layer |
| Pure logic | The `src/` of the kernel and module layers has no files, network, subprocesses, environment variables, threads, clocks or standard I/O, and uses no `HashMap` or `HashSet` | Move the I/O to the executor layer; use `BTreeMap` and `BTreeSet` instead |
| Line count | No `.rs` file is over 500 lines, test files included | Split the file |
| Logs | The runtime log does not write conversation text, tool arguments and results, or paths: field names may not be a path or body text, values may not contain `.display()` or `format!(`, and messages may not interpolate | Write only ids, lengths and categories; running `cargo xtask logs` on its own is faster |
| Licenses | Every third-party dependency used on the four release platforms can be distributed together with AGPL-3.0-or-later; `THIRD-PARTY-LICENSES.txt` is up to date | Swap the dependency; after adding or upgrading a dependency, run `cargo xtask notices` |
| Tests | `cargo test --workspace --no-fail-fast`, with `CI=1` set and the temp directory pointed at a new empty directory; every test file is part of a test program | Fix the test; for a new test file, add a line `mod <name>;` to `tests/all.rs` |
| Temp directory | Nothing is left in the temp directory after the tests finish; checked on Linux only | Have the test fixtures clean up after themselves |

`cargo xtask` has other subcommands as well:

| Command | What it does |
|---|---|
| `cargo xtask dev-home <dir>` | Creates a development data root with a config (see step 2 of "Build and run" above) |
| `cargo xtask logs` | Runs only the "Logs" item of the gate |
| `cargo xtask methods` | Registers protocol methods newly added in the code into `internal/blueprint/methods-v1.txt`, only adding and never deleting |
| `cargo xtask prompts` | Regenerates `internal/blueprint/prompts.md` from the ledger and the resources |
| `cargo xtask notices` | Regenerates `THIRD-PARTY-LICENSES.txt` |
| `cargo xtask perf [measuring tool args]` | Builds the release `miyu`, `miyu-sandbox` and the measuring tool `miyu-perf`, and measures startup, memory, requests on a long session and binary size, writing the result into `target/perf-out/`; the remaining arguments go to the measuring tool unchanged, for example `--runs 3`. Memory can only be measured on Linux; on macOS and Windows those cells in the table say `not measured` |
| `cargo xtask dist [--target <os>] [--out <dir>]` | Builds the command-line archive for the system you are on: takes the terminal and web UI according to `heads.toml`, builds the release `miyu`, `miyu-sandbox`, `miyu-extract`, `miyu-watchdog` (only on Linux and macOS), `miyu-tui` and `miyu-web`, and packs them as `miyu-<version>-<os>.tar.gz` (`.zip` on Windows), placed under `dist/` in the target directory by default; `--target` can only name the system you are on |
| `cargo xtask dist-check <archive>` | Checks an archive before release: compares the name, the programs, the licenses and the resources byte by byte, and runs `miyu --version` and `miyu check` from the archive; for a Windows archive it also reads the import table of every `.exe`, and the check fails if a program depends on the VC++ runtime (`VCRUNTIME*.dll`, `MSVCP*.dll`) |
| `cargo xtask packaging <tag> --sums <SHA256SUMS> [--applet <tray tag> --applet-sums <tray SHA256SUMS>] [--out <dir>]` | Fills in the AUR `PKGBUILD` and the Homebrew formula from a release's `SHA256SUMS` |
| `cargo xtask version <year.month.number>` | Changes the workspace version (for example `2026.12.0`), and `Cargo.lock` is updated to match |

## Tests

Tests follow these rules:

- To fix a bug, first write a test that reproduces it; the test must be red before the fix. For a new feature, first write the tests that prove it is correct.
- Tests always point `MIYU_HOME` at a temp directory and never touch real data.
- Each crate's integration tests are merged into one program, `tests/all.rs`, with one module per file, and shared fixtures go in `crate::support::`. Tests that install a log subscriber, and tests that measure the memory of the whole process, are listed separately as their own `[[test]]`.
- Tests of the measuring-tool kind are marked `#[ignore]`, and they assert on results, not on timing.
- Test toward the bad cases: edge cases, odd combinations, breaking it on purpose.

The core's CI (`.github/workflows/ci.yml`) runs `cargo xtask check` once on each of `ubuntu-24.04`, `macos-latest` and `windows-latest`; it also runs the long runs on Linux (random `#[ignore]` tests whose names end in `for_longer`) and the measuring tool, and going over the budget in the measuring tool also counts as a failure. CI runs on pushes to `main` and to branches starting with `step/`, and on PRs to `main`, including PRs from forks; it does not run when the change touches only `internal/construction/`, `docs/zh/dev/` or `internal/designs/` (except `01-架构.md`, `23-性能预算.md` and `26-提示词.md`). For changes that touch paths, the file system, subprocesses or the terminal, merge only after all three platforms pass.

## Code rules

Code follows these rules:

- Comments are in Chinese, names are in English.
- Write `///` on every public type, function, field and enum variant, and `//!` at the start of a module: what it handles, why it is that way, and the traps. If it can fail, write a `# Errors` section; if it can panic, write a `# Panics` section. Doc comments on public items must not link to private ones.
- Text the model sees is always short English sentences, kept in `resources/` and never written into the code. Add it only if it has to be added, and when you add it, register it in the ledger.
- Numbers, text and lists are data and are not hard-coded in the code.
- Do not hard-code paths, line endings or encodings; platform differences are kept at the boundary, and the code asks "can this be done here", not "is this macOS".
- Do not swallow errors: either handle them or report them as they are.
- Before adding a third-party dependency, check its license: it must be distributable together with AGPL-3.0-or-later.
- Follow the style of the surrounding code; keep files small, with one responsibility per module; do not write types, fields or config items that this change does not use.

## Other places to update

When you change something in the left column, also update the places in the right column:

| You changed | Also change |
|---|---|
| A protocol method, params, reply, error or push | Both `docs/zh/reference/` and `docs/en/reference/`; for a new method, run `cargo xtask methods`, and state in the table in `rights.rs` whether extensions can call it |
| How packages, extensions, scripts, skills or MCP are written | Both `docs/zh/dev/` and `docs/en/dev/` (tests check that `manifest.md`, `mcp.md` and `scripts-skills.md` cover every field) |
| Text the model sees in `resources/` | Add a row to the ledger or change its row, then run `cargo xtask prompts` |
| Dependencies | Run `cargo xtask notices` |
| A part's behavior, format or UI | Its page in the blueprints |

The gate checks that the two language versions of the protocol reference match, but it does not check the author guides, so you have to match those two versions yourself.

## Commits and PRs

Write commits and PRs in the following format:

- One change per commit, and every commit must build and pass the whole gate; an unrelated change you made in passing goes in its own commit.
- Write the title as `<type>(<scope>): <the effect of this change, in plain words>`, where the type is one of `feat`, `fix`, `perf`, `refactor`, `docs`, `test` and `chore`. This repository writes its commits in Chinese, so the scope and the effect are in Chinese, for example `fix(终端): 窄窗口里输入框不再错位` (meaning: in a narrow window the input box no longer shifts out of place). The title does not carry implementation details.
- The body has three parts: why, what changed, and how it was verified.
- Open the PR against `main`. CI must pass on all three platforms.
- Contributions are under the license of the repository they go to.

## Other repositories

The terminal, web UI, tray, im and other repositories each have their own `AGENTS.md`, `README.md` and gate, and follow the same rules as the core. They pin one core commit through a Cargo git dependency (see "Making a head use the core code you changed" above). The checks to run locally and the CI systems for each repository:

| Repository | Run locally | CI systems |
|---|---|---|
| `miyu-tui` | `cargo fmt --check`; `cargo clippy --all-targets --locked -- -D warnings`; `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --document-private-items --locked`; `cargo test --locked --no-fail-fast`; `cargo xtask licenses` | Linux, macOS, Windows (Windows runs only the `--bins` unit tests; `cargo xtask licenses` runs on Linux only); Linux also runs the measuring tool `cargo test --release --locked --test meters -- --ignored --test-threads=1` |
| `miyu-web` | The same first four as for the terminal, plus `cargo xtask licenses`; `MIYU_RESOURCES=<core checkout>/resources node --test 'web-demo/tests/**/*.test.js'`; `cargo clippy --manifest-path web-demo/bridge/Cargo.toml --all-targets --locked -- -D warnings`; `cargo test --manifest-path web-demo/bridge/Cargo.toml --locked` | Linux x86_64, Linux aarch64, macOS, Windows; `cargo xtask licenses`, the page tests and the demo bridge run on Linux only |
| `miyu-desktop` (the tray) | `cargo fmt --check`; `cargo clippy --workspace --all-targets --locked -- -D warnings`; `cargo test --workspace --locked --no-fail-fast`; `cargo xtask licenses`; `cargo build --release --locked` | Linux, macOS, Windows; `cargo xtask licenses` runs on Linux only |
| `miyu-im` | `cargo xtask check` | Linux, macOS, Windows |
| `miyu-migrate` | `cargo fmt --all --check`; `cargo clippy --workspace --all-targets --locked -- -D warnings`; `cargo test --workspace --locked` | Linux, macOS, Windows |
| `miyu-embed` | `cargo fmt --check`; `cargo clippy --all-targets --locked -- -D warnings`; `cargo test --locked` | Linux, macOS, Windows |
| `miyu-render`, `miyu-memes` | `cargo fmt --check`; `cargo clippy --all-targets --locked -- -D warnings`; `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --document-private-items --locked`; `cargo test --locked --no-fail-fast` | Linux, macOS, Windows |
| `miyu-ocr` | The same four as the row above, all with `--workspace`; plus `cargo xtask licenses` | Linux, macOS, Windows; `cargo xtask licenses` runs on Linux only |
| `miyu-sdk` | `python -m unittest discover -s python/tests`; in `rust/`, run `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` | Linux, macOS, Windows; Python also runs once with 3.9 on Linux |

In the table, `NAME=value command` is bash syntax; in PowerShell, first run `$env:NAME = 'value'`, then run the command.

The CI of these repositories also runs on PRs. All of them except `miyu-migrate` and `miyu-sdk` limit every `.rs` file to 500 lines (`miyu-im` checks this in its `cargo xtask check`). The page tests of `miyu-web` read the core's shipped resources, so `<core checkout>` must be the commit pinned in its `Cargo.toml`.
