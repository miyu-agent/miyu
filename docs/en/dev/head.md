# Writing a head

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

A head is an interface program that connects to the core and lets people talk to the AI; the terminal interface and the web interface are the two heads that ship with Miyu. This page takes you from zero to a head of your own (for example an editor plugin, a phone app or another kind of interface), packaged and installed as a package. All the parameters of every protocol method are in the [protocol reference](../reference/README.md); this page only strings together the steps you have to take.

## The steps a head takes

From starting up to talking with the AI, a head goes through the following steps in order:

1. Find the data root and connect to the core's local socket; if the core is not running, start it first.
2. Handshake with `hello`, showing the local token.
3. Open a session (`session.create`), or attach to an existing one.
4. Subscribe to the session's view stream (`subscribe`, with `stream` set to `view`).
5. Send a message (`session.send`).
6. Draw the timeline from the entries the core pushes to you; when an action needs confirming or the AI asks a question, ask the person first, then answer with `session.answer`.

## A minimal example

The head below uses only the Python standard library, and the same file works on all three platforms. It opens a new session, sends one message, prints the answer text to the terminal as it arrives, and asks you in the terminal when there is a confirmation or a question. It has been run on Linux and macOS; on Windows it takes the lines under `WINDOWS`, which follow the way `miyu-client` does it and have not been tested on Windows yet. Save it as `tiny-head`; on Linux and macOS, also make it executable:

```python
#!/usr/bin/env python3
"""A minimal head: open a session, send one message, print the answer text."""
import io, json, os, socket, subprocess, sys, time, uuid
from pathlib import Path

ROOT = Path(os.path.expanduser(os.environ.get("MIYU_HOME") or "~/.miyu"))
WINDOWS = os.name == "nt"
PREFIX = uuid.uuid4().hex[:8]          # one random prefix per connection, so ids don't collide with ones used before
seq, entries, shown, answered, done = 0, {}, {}, set(), False

def connect():
    """Return (write function, read file) if connected; None if not."""
    try:
        where = (ROOT / "run" / "socket").read_bytes().rstrip(b"\n")
        if WINDOWS:                    # named pipe: open it as a file, one handle for reading and writing
            pipe = open(where.decode(), "r+b", buffering=0)
            return pipe.write, io.BufferedReader(pipe)
        sock = socket.socket(socket.AF_UNIX)
        sock.connect(where)
        return sock.sendall, sock.makefile("rb")
    except OSError:
        return None

def start_core():
    ROOT.mkdir(parents=True, exist_ok=True)
    flags = subprocess.DETACHED_PROCESS | subprocess.CREATE_NEW_PROCESS_GROUP if WINDOWS else 0
    core = subprocess.Popen([os.environ.get("MIYU_PROGRAM", "miyu"), "core"], cwd=ROOT,
                            stdin=subprocess.DEVNULL, stdout=subprocess.PIPE,
                            stderr=subprocess.DEVNULL, start_new_session=not WINDOWS,
                            creationflags=flags)
    line = core.stdout.readline().decode().strip()      # ready, running, or error …
    if not line or line.startswith("error"):
        sys.exit(f"The core won't start: {line}")

def read():
    line = lines.readline()
    if not line:
        sys.exit("The core disconnected")
    return json.loads(line)

def call(method, params):
    global seq
    seq += 1
    rid = f"{PREFIX}-{seq}"
    msg = {"jsonrpc": "2.0", "id": rid, "method": method, "params": params}
    send(json.dumps(msg, ensure_ascii=False).encode() + b"\n")
    while True:
        got = read()
        if got.get("id") == rid:
            if "error" in got:
                sys.exit(f"{method}: {got['error'].get('data', {}).get('reason')}")
            return got["result"]
        push(got.get("method"), got.get("params", {}))

def push(method, p):
    global done
    if method in ("view.add", "view.update"):
        entry = entries[p["entry"]["id"]] = p["entry"]
    elif method == "view.append" and p["id"] in entries:
        entry = entries[p["id"]]
        entry["text"] = entry.get("text", "") + p["text"]
    elif method == "view.status":
        for wait in p["status"].get("waiting", []):
            if wait["call"] not in answered:
                answered.add(wait["call"])
                respond(p["session"], wait)
        return
    elif method == "resync":
        sys.exit("Fell behind by reading too slowly: resubscribe")
    else:
        return
    if entry["kind"] == "reply":
        print(entry["text"][shown.get(entry["id"], 0):], end="", flush=True)
        shown[entry["id"]] = len(entry["text"])
    if entry["kind"] == "end":
        done = True

def respond(session, wait):
    entry = entries.get(wait["entry"], {})
    if wait["what"] == "approve":
        title = entry.get("title", {})
        yes = input(f"\nAllow {title.get('name')} {title.get('object', '')}? [y/N] ").strip() == "y"
        answer = {"decision": "once" if yes else "deny"}
    else:
        answer = {"answers": [{"text": input(f"\n{q['question']} ")} for q in entry.get("questions", [])]}
    if "nested" in wait:
        answer["nested"] = wait["nested"]
    call("session.answer", {"session": session, "call": wait["call"], **answer})

got = connect()
if got is None:
    start_core()
    for _ in range(50):
        if (got := connect()):
            break
        time.sleep(0.2)
    else:
        sys.exit("Can't connect to the core")
send, lines = got
token = (ROOT / "run" / "token").read_text().strip()   # connect first, then read the token

call("hello", {"protocol": [1, 1], "head": {"kind": "tiny", "version": "0.1.0"},
               "locale": os.environ.get("LANG", ""), "caps": {"input": True}, "token": token})
session = call("session.create", {})["session"]
call("subscribe", {"session": session, "stream": "view"})
call("session.send", {"session": session, "text": " ".join(sys.argv[1:]) or "Hello"})
while not done:
    got = read()
    push(got.get("method"), got.get("params", {}))
print()
```

On Linux and macOS, run:

```bash
./tiny-head introduce yourself in one sentence
```

On Windows, run:

```powershell
python tiny-head introduce yourself in one sentence
```

The sections below go through what it sends and what it receives, step by step. `→` marks a message the head sends, `←` marks a message the core sends, and `…` marks omitted fields.

### Connecting to the core

Keep the following points in mind when you connect to the core:

- The file `run/socket` in the data root (`~/.miyu` by default, `%USERPROFILE%\.miyu` on Windows, or the directory `MIYU_HOME` points to if you set it) holds a single line with a path: the socket the core is waiting on for connections. On Linux and macOS it is a Unix domain socket; on Windows it is a named pipe `\\.\pipe\miyu-<fingerprint>`, open to your user only. The pipe is read and written as a byte stream, and you can open it like a file; after that the rules are the same as on a Unix socket: one message per line, and the first one is `hello`, showing the token.
- When you connect, check that the other end is your own core, so that another user can't grab the spot first and pose as the core: on Linux and macOS, before connecting, check that the directory holding the socket belongs to you and nobody else can get into it; on Windows, after connecting, check that the process at the other end of the pipe belongs to your user. The example leaves this step out; `miyu-client` (see [Writing it in Rust](#writing-it-in-rust-miyu-client) below) does this check for each platform when it connects.
- `run/token` is the local token, 64 hex digits. The core changes it every time it starts, so you must connect first and read the token afterwards.
- If you can't connect, start the core: run `miyu core` with the working directory set to the data root, and stdin and stderr connected to the null device. Detach it from your terminal so that pressing `Ctrl+C` doesn't affect it: on Linux and macOS, give it a process group of its own; on Windows, start it with `DETACHED_PROCESS` and `CREATE_NEW_PROCESS_GROUP`, so that it doesn't take over your console or open a new window. Once the core is up, it writes one line to stdout: `ready` (it is ready), `running` (a core is already running, so this one exits and you connect to the existing one), or `error <reason>` (it failed to start). If you read `running`, connect again after a moment.
- A head opened with `miyu <name>` has `MIYU_PROGRAM` in its environment, which is the real location of the main program `miyu`: use it to run `<that> core`, and don't look in `PATH`. If you are the default interface opened by running plain `miyu`, the core was already started before you were opened.
- One data root has exactly one core. A head determines the data root from `MIYU_HOME` and connects only to that data root's core.

### The handshake

The first message you send after connecting must be `hello`; if the handshake isn't completed within 10 seconds, the core disconnects.

```json
→ {"jsonrpc":"2.0","id":"3f2a91c0-1","method":"hello","params":{"protocol":[1,1],"head":{"kind":"tiny","version":"0.1.0"},"locale":"zh_CN.UTF-8","caps":{"input":true},"token":"9c41…"}}
← {"id":"3f2a91c0-1","jsonrpc":"2.0","result":{"core":{"version":"…"},"host":{"home":"/home/alice","platform":"linux","workspace":"…","dirs":{…}},"language":"zh","protocol":1,"sandbox":{"usable":true},"view":1}}
```

| Field you report | Description |
|---|---|
| `protocol` | The protocol major versions you can speak, written as `[lowest, highest]`. The core only has version `1`; if it isn't in that range, the core replies `protocol_mismatch` and disconnects. |
| `head` | `kind` and `version`: what program you are and which version. They are recorded only in the core's runtime log. |
| `locale` | The system language (both `zh-CN` and `en_US.UTF-8` forms are accepted). When `ui.language` is `auto`, the core uses it to decide which language this connection speaks. |
| `caps.input` | Whether a person can answer on the spot. When left out it is `false`: nobody can confirm anything in the sessions you open, so tool calls that need confirming don't run, and the AI's questions immediately get `No one can answer questions here.` as the result. |
| `caps.prefix_ask` | Declares that when a file has changed and the next turn's request prefix would change, you ask the person first (see "The prefix is about to change" below). |
| `token` | The local token. |

You will use these fields of the reply: `language` (which of `zh`, `en` and `ja` the text shown to people is in from now on), `host.workspace` (the default workspace used when a session doesn't give a working directory), and `sandbox.usable`. Every field of the handshake is in [Connection](../reference/connection.md#hello).

### Opening a session and subscribing to the view stream

After the handshake succeeds, open a session and subscribe to its view stream:

```json
→ {"jsonrpc":"2.0","id":"3f2a91c0-2","method":"session.create","params":{}}
← {"id":"3f2a91c0-2","jsonrpc":"2.0","result":{"cwd":"…","events":[1],"session":"01a14aca-d2c4-768c-acc6-a67e35106d22"}}
→ {"jsonrpc":"2.0","id":"3f2a91c0-3","method":"subscribe","params":{"session":"01a14aca-…","stream":"view"}}
← {"id":"3f2a91c0-3","jsonrpc":"2.0","result":{"entries":[],"more":false,"status":{"state":"idle",…},"permission":…,"model":…,…}}
```

When `session.create` has no `cwd`, the session uses its own default workspace; when `persona`, `preset` or `model` is left out, the configured default is used. To attach to an existing session, skip `session.create` and subscribe to it directly; get the list of sessions with `session.list`.

The reply to the subscription carries the latest page of entries and the complete session state `status`. After that, every change to the session is pushed to you.

### Sending a message

Send a message with `session.send`:

```json
→ {"jsonrpc":"2.0","id":"3f2a91c0-4","method":"session.send","params":{"session":"01a14aca-…","text":"Introduce yourself in one sentence"}}
← {"jsonrpc":"2.0","method":"view.add","params":{"session":"01a14aca-…","after":null,"entry":{"id":"m2","kind":"user","text":"Introduce yourself in one sentence",…}}}
← {"jsonrpc":"2.0","method":"view.status","params":{"session":"01a14aca-…","status":{"state":"running",…}}}
← {"id":"3f2a91c0-4","jsonrpc":"2.0","result":{"cwd":"…","events":[2]}}
```

The core replies once the message is saved to disk, without waiting for the AI to finish answering. Pushes caused by a request always arrive before its reply, so you must handle pushes while you wait for the reply too. If the AI is busy, the message is queued; one with `urgent: true` is inserted at the next step.

### Drawing the answer

While the AI answers, the core pushes messages like these:

```json
← {"jsonrpc":"2.0","method":"view.add","params":{"session":"01a14aca-…","after":"m2","entry":{"id":"b3.0","kind":"reply","text":"I am","open":true,"persona":null,…}}}
← {"jsonrpc":"2.0","method":"view.append","params":{"session":"01a14aca-…","id":"b3.0","text":" an assistant that works on your computer."}}
← {"jsonrpc":"2.0","method":"view.update","params":{"session":"01a14aca-…","entry":{"id":"b3.0","kind":"reply","text":"I am an assistant that works on your computer.",…}}}
← {"jsonrpc":"2.0","method":"view.add","params":{"session":"01a14aca-…","after":"b3.0","entry":{"id":"e5","kind":"end",…}}}
```

Keep the following in mind when you draw the answer:

- Store entries by `id`. `view.add` is a new entry, placed after the entry named by `after` (`null` means first); `view.update` replaces the whole entry, and if it carries `after`, the entry has moved; `view.append` appends text to that entry's `text` (`args` for a tool entry); `view.hidden` hides several entries or shows them again, for undo and restore; `view.remove` removes an entry.
- The same entry may get an `add` and then an `update`, and the text in the `update` may already include parts that never came as a separate `append`. So draw from the text of the whole entry, and don't just concatenate the increments. The example remembers how many characters of each entry it has already printed and prints only what is new.
- `kind` is one of: `user` (what the person said), `reply` (the answer text as Markdown source; rendering it is the head's job), `media` (an image the AI sent), `group` (a section of the timeline), `thought` (one step of thinking), `tool` (one tool step), `end` (the end of a turn) and `notice` (an aside such as compaction, undo or a model change; look at `what` to see which).
- `open: true` means the entry is still being written. While a tool runs, `progress` (the latest progress line) and the `retitle_failed` aside are pushed only on the view stream; paging and resubscribing don't return them.
- When a turn ends, the core adds an entry whose `kind` is `end`, and the session state `status.state` goes back to `idle`.

For the fields of each kind of entry, every `what` of `notice`, and every field of the session state, see [View stream](../reference/view.md).

### Falling behind and reconnecting

If you read too slowly and the messages the core holds for a subscription reach the limit (1024 entries for a session), the core pushes `resync {session, stream: "view"}` and that subscription stops. A session that stops also pushes `resync`. In that case, subscribe again: the reply holds the latest page and the complete state, and you replace everything you hold with it.

After a disconnect, reconnect, handshake again and subscribe again. Use `view.page` to page back through history.

The view stream is for drawing the interface; if you want the raw events (for example to keep your own log), subscribe to `stream: "events"`, which can take `after` to fill in the events you missed. For details, see [Events](../reference/events.md).

## Confirmations and questions

When the AI is about to do something protected (for example a dangerous command under full access, or a write under read-only), it stops and waits for confirmation; it also waits when it asks a question with `ask_user`. Both are recorded in the session state: `status.state` is `waiting`, and `status.waiting` has one item `{what, entry, call}` for each, where `what` is `approve` (a confirmation) or `ask` (a question) and `entry` points to the entry of that tool step.

Handling confirmations:

- That step's entry has `approval`, containing `access`, `rule` and `detail`. A confirmation that carries `expires_at` is denied automatically if nobody has answered by that moment, and the head can draw a countdown. The waiting time is set by the config `permission.confirm.timeout`; the shipped value is 300 seconds, and 0 means wait forever.
- To answer, use `session.answer {"session", "call", "decision"}`, where `decision` is `once` (allow this once), `session` (allow for this whole session; you can only pick it if the entry has a `rule`) or `deny` (refuse; it may carry a `reason` for the AI to see).

Handling questions:

- That step's entry has `questions`: each question has a `question`, an optional `header`, `options` (with `label`, `description` and `preview`) and `multiple`. Questions wait forever and don't time out.
- To answer, use `session.answer {"session", "call", "answers"}`, with one item `{"picked": [the label of each chosen option…], "text": <what they wrote themselves>}` per question, in the order of the questions.

If an item in `waiting` carries `nested` (meaning a tool the AI called from inside a command through `miyu call` needs confirming), write it back unchanged in your answer. When several heads have the same session open, the first answer counts, and a later one gets `not_asking`. Every field and error is in [Sessions](../reference/sessions.md#sessionanswer).

A head with nobody watching (for example a script that runs on a schedule, or a program that only pushes notifications) leaves `caps.input` out of the handshake or sets it to `false`. In the sessions it opens, anything that needs confirming doesn't run, and a question immediately gets `No one can answer questions here.` as the result; the AI carries on from that result and doesn't get stuck waiting for a person.

## The rest of the session operations

The other common session actions in an interface, and the methods behind them, are listed below:

| Action in the UI | Method |
|---|---|
| New session | `session.create` |
| List sessions, follow changes to the list | `session.list`; after you subscribe to the `sessions` stream, `sessions.changed` is pushed when the list changes |
| Tell the core which session you have open | `session.viewing`: you issue the background notifications for the session you have open, and other heads no longer pop them up |
| Page back through history | `view.page` |
| Send a message | `session.send` |
| Send with attachments | First upload with `blob.put` (`path` for a local file, or `data` for base64 content), then put the reply's `blob`, `name` and `media_type` into `attachments` of `session.send` |
| Interrupt | `session.interrupt`; `queued` is required and decides what happens to queued messages: `send` (sent right after the interrupt), `return` (handed back) or `keep` (left in the queue) |
| Take back a queued message | `session.withdraw` |
| Undo, restore | `session.revert`, `session.unrevert` |
| Redo the last turn | `session.redo` |
| Compact, clear the context | `session.compact`, `session.clear` |
| Change persona, preset, model, vision model, thinking effort | `session.configure` |
| Switch to read-only, switch back to full access | `session.set_permission_level`, with `{"read_only": true}` or `false` |
| Change the working directory | `session.set_workspace` |
| Change the title, pin | `session.set_meta`; to have the model pick a new title, use `session.retitle` |
| Fork | `session.fork` |
| Export | `session.export`: `format` is `bundle` (the raw bundle) or `markdown` |
| Delete | `session.delete` |

Most methods only reply with `{}` or the numbers of a few events, and the change itself arrives as pushes. For details on each method, see [Sessions](../reference/sessions.md).

**The prefix is about to change**: if a head set `caps.prefix_ask: true` in its handshake, a request that starts a new turn (`session.send`, `session.redo`, or a `command.run` that starts a turn) may get `prefix_changing`, which means files such as the persona, preset or prompts have changed and the next turn's cache will be invalidated. `data.files` lists the changed files. Ask the person to choose `Send anyway`, `Compact and send` or `Cancel`, then send again with `"prefix": "keep"` or `"compact"` according to their choice. A head that doesn't declare it still sends directly.

## Slash commands

A head must be able to list and run slash commands:

- List: call `command.catalog {"session"}`; the reply has `commands` (`name`, `aliases`, `summary`, `argument`, `usage`, `opens`) and `skills` (skills named in the input box as `$skill-name`).
- Run: hand the whole line the person typed to `command.run {"session", "text"}`; `said` in the reply is the acknowledgement, shown to the person as is. If the reply carries `opens`, it opens a whole page of an extension (see [Putting things on the screen](ui-surfaces.md)).
- The head's own commands (for example `/help` or switching the theme) are recognized and handled by the head itself and merged into the same menu.

The commands the core recognizes and their errors are listed in [Packages and commands](../reference/packages.md#commandrun).

## The head's own settings

A head's settings come in several kinds, and each kind is stored in a different place:

- Settings that follow the person, such as skin and colors, are stored in the core: read them with `prefs.get {"package"}` and write them with `prefs.set {"package", "values"}`, where `package` is the package id of your head and the whole set is at most 64 KiB. When another head changes them, `prefs.changed` is pushed (you need to subscribe to the `prefs` stream with `package`). Only a head installed as a UI package (see below) can use this; others get `unknown_package` or `not_a_ui_package`. For details, see [A head's own settings](../reference/prefs.md).
- Settings that only concern this device (for example window size and input history) are stored by the head itself.
- Read the core's config with `config.get`; after you subscribe to the `config` stream, `config.changed` is pushed when the config changes. A head needs to follow these items: `ui.language` (the interface language) and `ui.startup` (whether opening the head starts a new session, `new`, or picks up the most recent one, `recent`).
- Your own config items go in the manifest under `[settings.<name>]`, with the key `<prefix>.<name>`, and the settings page draws them from there (see [The manifest](../../authors/manifest.en.md)).

## Writing it in Rust: `miyu-client`

The crate `miyu-client` in the core repository is the facade for heads. Depend on it pinned to a specific commit:

```toml
[dependencies]
miyu-client = { git = "https://github.com/miyu-agent/miyu", rev = "<core commit id>" }
serde_json = "1"
tokio = { version = "1", features = ["macros", "rt", "io-util"] }
```

The core's crates need Rust 1.97 or later. `miyu-client` is licensed under AGPL-3.0-or-later; programs that only talk to the core over the protocol are not bound by that license.

It takes care of connecting, finding the data root and starting the core; you write the handshake, subscribing, and sending and receiving yourself, the same way as above:

```rust
use std::process::Command;

use miyu_client::connect::connect_or_start;
use miyu_client::places::{DataRoot, Env};
use serde_json::{Value, json};
use tokio::io::{AsyncBufReadExt, AsyncWriteExt, BufReader};

#[tokio::main(flavor = "current_thread")]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let root = DataRoot::locate(&Env::current())?;
    root.prepare()?;
    let miyu = std::env::var_os("MIYU_PROGRAM").unwrap_or_else(|| "miyu".into());
    let (connection, token) = connect_or_start(&root, move || {
        let mut core = Command::new(miyu);
        core.arg("core");
        core
    })
    .await?;
    let (read, mut write) = tokio::io::split(connection);
    let mut lines = BufReader::new(read).lines();
    let hello = json!({"jsonrpc": "2.0", "id": "h1", "method": "hello", "params": {
        "protocol": [1, 1],
        "head": {"kind": "tiny", "version": "0.1.0"},
        "locale": miyu_client::places::locale().unwrap_or_default(),
        "caps": {"input": true},
        "token": token,
    }});
    write.write_all(format!("{hello}\n").as_bytes()).await?;
    while let Some(line) = lines.next_line().await? {
        let got: Value = serde_json::from_str(&line)?;
        if got["id"] == "h1" {
            println!("{}", got["result"]);
            break;
        }
    }
    Ok(())
}
```

`connect_or_start` returns the connection and the local token once it has connected; if the core isn't running, it starts the core with the command you give and waits for the core's line, and when several heads start the core at the same time, only one is started. It doesn't reconnect for you: after a disconnect, you call it again, then handshake again and subscribe again.

| Module | What it provides |
|---|---|
| `connect` | `connect` (connect only), `connect_or_start` (start the core if it isn't running), `Connection` (an async byte stream) and the error type |
| `places` | `DataRoot` (`locate`, `prepare`), `Env`, `locale`, the cache directory, and reading and writing config files |
| `open` | `Core`: handshakes with the local token and works by question and answer, without receiving pushes. Programs that ask a few things and exit (for example command-line tools) use it |
| `texts` | The core's text for people, read by language |
| `protocol`, `ids`, `time`, `events` | The protocol's types: session ids, events, times and so on |
| `settings` | The kinds of config and how they are read |
| `widgets` | Validating UI block content and picking the language |
| `manifest` | Reading your own package manifest |
| `log`, `heap`, `open_files` | The runtime log, the process heap, the limit on open files |
| `seeds` | Picking candidate theme colors from an image |

A few features are off by default; turn on the matching feature when you need it: `view` (the types for view stream entries, pushes and session state), `wallpaper` (finding the desktop wallpaper and following changes to it), `http` and `tool`.

## Making it a package

Once it is a UI package, `miyu tiny` opens your head, and people can also set it as the interface that opens when they run plain `miyu`.

The package's directory looks like this:

```text
tiny-head/
├── package.toml
└── bin/
    └── tiny-head      # the Python file above, executable on Linux and macOS
```

Write `package.toml` like this:

```toml
[package]
version = "0.1.0"
protocol = [1, 1]
name = { zh = "小头", en = "Tiny head" }
summary = { zh = "一个最小的头", en = "A minimal head" }

[command]
name = "tiny"
program = "tiny-head"
about = { zh = "打开小头", en = "Open the tiny head" }

[ui]
```

1. Install: `miyu pkg install ./tiny-head`.
2. Open: `miyu tiny hello`. The arguments the person types are handed to your program unchanged, with `MIYU_PROGRAM` in the environment. On Linux and macOS, the `miyu` process is replaced by your program; on Windows, `miyu` starts your program and waits for it to exit, its exit code is your program's, and `Ctrl+C` is passed on to your program.
3. Set it as the default: `miyu config set ui.head tiny-head`. After that, running plain `miyu` in a terminal opens it (only when both stdin and stdout are a terminal). When two or more interfaces are installed, the settings page also has a `Default interface` item under `General`.

- A manifest that has the `[ui]` table makes a UI package. `opens` lists the pages you handle, for example `opens = ["config"]`: when the person runs `miyu config`, the core opens your head with `--page config`; if it isn't listed, `miyu config` doesn't open your head.
- Every field of `[command]` and how to write `[settings]` are in [The manifest](../../authors/manifest.en.md). The `[ui]` table is only for UI packages and is not among the frozen formats listed on that page, so it may change later: after upgrading the core, you must check it again first.
- On Windows, the core looks for `bin/tiny-head.exe` first; if there isn't one, it finds an interpreter from the `#!` on the first line of `bin/tiny-head`, and `#!/usr/bin/env python3` finds `python` in `PATH`. So this package works on all three platforms, and the file name doesn't end in `.py`; on Windows, Python must be installed first, with `python` findable in `PATH`. For details, see [Writing a Miyu package: three platforms](../../authors/README.en.md#three-platforms).
- If the package ships compiled programs, you must write `targets`, with one package per system; for packing and publishing to a package source, see [Writing a package](../../authors/README.en.md).

## Web-type heads

A browser can't connect to a local socket, so this is how the shipped web interface is connected: the web server `miyu-web` listens on a local port, the browser connects to it over WebSocket, it forwards every line to the core unchanged, and the page shows its own credentials in the handshake (`miyu-web` doesn't read the local token).

There are two ways to make a web-type head:

- **Run a local service of your own to forward the connection**, as above. If what you forward is a connection from another machine, you must first write a line on its behalf before the handshake, `{"jsonrpc":"2.0","method":"connection.remote","params":{"from":"<source address>"}}`: the connection then counts as remote, methods that read local files or take local paths always reply `local_machine_only`, and the credentials must use the access password. For details, see [Connection](../reference/connection.md#connecting).
- **Add things to the shipped web interface**: see [Putting things on the screen](ui-surfaces.md).

## Things to watch for

- Protocol 1 is frozen: existing methods and fields are never removed, renamed or given a new meaning, only added to. An older core answers `unknown_method` to a new method and ignores a new field; before relying on a new method or field, look at the core version in the handshake reply, or fall back to the old way when you get `unknown_method`.
- To tell what went wrong, look at `error.data.reason`, not `error.message`: `error.message` is a sentence written for people in the connection's language. All the reason codes are in [Errors](../reference/errors.md).
- Each message takes one line, at most 1 MiB. Large content goes through `blob.put`, and a file over the upload limit is passed as a path only (see [Sessions](../reference/sessions.md#sessionsend)).
- A request's `id` must differ on every connection from all ids used before: the core recognizes a resend after a disconnect by its `id`, so if you reuse an old one, you get the previous reply and the core does nothing. The way to do this is to take a random prefix for each connection and follow it with an increasing number.
- Your head is not the only head. The terminal, the web interface and the tray may have the same session open at the same time: messages other people send, confirmations other people answer and settings other people change must all be updated from pushes, so don't assume you are the only one making changes.
