# Schedules: `schedule.*`

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

A schedule hands one line to a session at a set time and lets the session run a turn: for example, a morning briefing at 8, or a look at the server every hour. All schedules are kept in one table, `root/schedules.db`, so they survive a core restart; times missed while the core was down are skipped, not made up.

| Method | Does |
|---|---|
| [`schedule.add`](#scheduleadd) | Adds a schedule |
| [`schedule.list`](#schedulelist) | Lists all schedules |
| [`schedule.cancel`](#schedulecancel) | Deletes a schedule |
| [`schedule.pause`](#schedulepause) | Pauses a schedule |
| [`schedule.resume`](#scheduleresume) | Resumes a schedule |
| [`schedule.update`](#scheduleupdate) | Changes the time or the line |

**Who can call**: people can call these methods; an extension needs an approved `sessions.drive`, and without it gets `needs_approval`. A schedule that an extension adds is recorded as added by its package, and the extension can see, cancel, pause, resume and update only those schedules: touching one it did not add always gets `unknown_schedule`. To keep up with the latest state, subscribe to the `schedules` stream ([connection](connection.md)); the core then pushes `schedules.changed` ([pushes](pushes.md)).

## An item

| Name | Meaning |
|---|---|
| `id` | The id is `t1`, `t2`…, counting up; ids of deleted schedules are never reused |
| `when` | When it runs: `{"cron": "0 8 * * *", "recurring": true, "zone": "Asia/Tokyo"}` (the standard five fields, read in the time zone `zone` names: the one given when the schedule was added, or, when none was given, the zone of the core's machine at that moment; older schedules without `zone` use the zone of the core's machine), `{"at": "<time>"}` (runs once), `{"every": <seconds>}` (runs at an interval of at least 60) |
| `prompt` | The line handed to the session, kept as written |
| `target` | Where it runs: `{"session": <id>}`; or `{"new": {"persona", "preset", "cwd"}}` (a new session is opened with these each time, and `persona` `null` means no persona); or `{"package": {}}` (no session: when it is due, [`schedule.fired`](#schedulefired) goes to the extension that added it) |
| `by` | Who added it: a person is `{"kind": "person"}`, the AI in a session is `{"kind": "model", "session"}`, and a package is `{"kind": "package", "package"}` |
| `recurring` | Whether the schedule stays after it runs: `false` for `at`, `true` for `every`, and as written for `cron` |
| `paused` | Whether the schedule is paused |
| `loop` | Present only for loops: `fixed` means a fixed interval, and `dynamic` means the AI sets the pace |
| `next` | The next time it runs; absent while the schedule is paused, or while a dynamic loop waits for the AI to set the next time |
| `last` | The last run: `{"at", "result", "session"?}`; `result` is `ran` (a turn started), `queued` (the session was busy running a turn, so this run waits its turn), `held` (the prompt was recorded in the session without starting a turn, and is seen the next time someone speaks there: this is what happens to schedules the AI added and to loops in a session opened by `miyu ask` that no head (an interface program that connects to the core, such as the terminal interface or the web interface) has open; schedules you added still start a turn in such a session), `sent` (it was pushed to the extension that added it) or `skipped:<why>` (`session_gone`: the session is gone and the schedule paused; `preset_off`: the AI added the schedule and the session's preset turns it off; `not_opened`: the new session could not be opened; `package_unavailable`: the extension that added it is not running and could not be started) |
| `created` | When it was added |

Fields without a value are left out. Times are written the same way as elsewhere: `2026-10-26T08:00:00.000Z`.

## `schedule.add`

| Param | Type | Meaning |
|---|---|---|
| `when` | object, required | One of the three forms above; `recurring` and `zone` (an IANA time zone name such as `Asia/Tokyo`) can only go with `cron` |
| `prompt` | string, required | Must not be empty |
| `target` | object, optional | One of `{"session": <id>}`, `{"new": {"persona"?, "preset"?, "cwd"?}}` or `{"package": {}}`; when omitted, a new session is opened each time. Only extensions may write `package`; a person who writes it gets `bad_params` (without `data.problem`). When `persona` or `preset` is missing, it is fixed to the current default; when `cwd` is missing, it is the home directory |

The response is `{"schedule": <item>}`. A malformed request adds nothing and gets `bad_params`, with `data.problem` saying what was wrong: `when` (not exactly one valid form, or a malformed time), `cron` (the expression can't be read), `past` (the time has already passed), `short` (the interval is under 60 seconds), `prompt` (it is empty), `session` (there is no such session, or this connection can't reach it: the answer is the same in both cases), `target` (both forms were written). An unknown persona or preset gets `unknown_persona` or `unknown_preset`, the same as when opening a session. The other problems are `zone` (the time zone is unknown) and `cwd` (the working folder for new sessions is missing, is not a folder, or is inside the data root but outside the workspace folder). When there are already 200 schedules (added by people, the AI and packages together; this is a safety limit), adding one gets `too_many_schedules`, and you need to remove some first; the existing ones keep running.

## `schedule.list`

The param `session` is optional: when you give it, only the schedules running on that session are listed. The response is `{"schedules": [<item>…]}`: schedules with a next time come first, ordered by that time, and paused ones and ones waiting for a next time come after them.

## `schedule.cancel`

The param is `id`. The response is `{}`.

## `schedule.pause`

The param is `id`. A paused schedule does not run when it is due, and its next time is cleared. The response is `{"schedule": <item>}`.

## `schedule.resume`

The param is `id`. The next time is counted from now, and missed runs are not made up. A one-off schedule whose time has already passed gets `bad_params` (`past`). The response is `{"schedule": <item>}`.

## `schedule.update`

Changes a schedule's time or line. The id stays the same; `last`, the creation time, `target` and `by` are kept; anything you don't write stays as it is.

| Param | Type | Meaning |
|---|---|---|
| `id` | string, required | The schedule's id |
| `when` | object, optional | Written and checked the same way as in `schedule.add` |
| `prompt` | string, optional | Must not be empty |

Write at least one of `when` and `prompt`; writing neither gets `bad_params` (without `data.problem`). When `when` changes, `next` is counted again from now, and missed runs are not made up. A paused schedule stays paused after the change, and `resume` counts from the new time. A loop keeps its kind: a `dynamic` loop only takes `at` for `when` (which sets when the next round starts), and a `fixed` loop only takes `every`; anything else gets `bad_params` (`when`). `prompt` can be changed on both kinds. A malformed request changes nothing and gets `bad_params`, with the same `data.problem` values as `schedule.add` (`when`, `cron`, `past`, `short`, `prompt`, `zone`). The response is `{"schedule": <item>}`, and `schedules` subscribers get `schedules.changed` as usual.

```json
{"jsonrpc": "2.0", "id": "u1", "method": "schedule.update", "params": {"id": "t1", "when": {"every": 1800}}}
{"jsonrpc": "2.0", "id": "u1", "result": {"schedule": {"id": "t1", "when": {"every": 1800}, "prompt": "look at CI", "target": {"session": "<id>"}, "by": {"kind": "person"}, "recurring": true, "paused": false, "created": "2026-10-26T00:00:00.000Z", "next": "2026-10-26T00:50:00.000Z", "last": {"at": "2026-10-26T00:10:00.000Z", "result": "ran"}}}}
```

## `schedule.fired`

This is a notification from the core to an extension: when a schedule that an extension added with `target` `{"package": {}}` is due, the core sends it to that package's process. No subscription is needed, and no reply is expected.

| Name | Meaning |
|---|---|
| `id` | The schedule's id |
| `at` | When this run was due |
| `prompt` | What was written when the schedule was added, handed back as is (the extension picks the format, for example JSON) |
| `missed` | How many runs were missed while the core was stopped, counting up to 1000; missed runs are not made up, only counted. Absent when no run was missed |

If the package isn't connected, the core doesn't start it. When the package cannot be reached, the run is recorded as `skipped:package_unavailable`; a one-off schedule is removed as usual, and a recurring one waits for its next time.
