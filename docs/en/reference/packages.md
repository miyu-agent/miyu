# Packages and commands: `package.*`, `extension.*`, `mcp.*`, `skill.list`, `skill.remove`, `script.list`, `feature.set`, `command.*`, `check`

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page covers the methods that manage packages, extension processes and the MCP servers in the system config, and the methods that list skills and scripts, change how tools load and the global switches of skills, scripts and MCP servers, run slash commands, and check files for mistakes. The methods extensions call themselves, and the calls the core makes to extensions, are described in [Extensions](extensions.md).

**Who can call**: `package.install`, `package.remove`, `package.enable`, `package.disable`, `package.restart`, `package.sync`, `package.search`, `package.clean`, `package.upgrades`, `package.upgrade`, `package.file`, `package.page`, `extension.*`, `mcp.*` and `feature.set` are for people only, and an extension that calls them gets `local_only`. `package.info` with `path` is also for people only (because it looks at any folder on this machine, like `package.install`). People and extensions can call all the other methods; an extension calling `package.call` reaches only itself (see below).

**Three layers**: packages come in three layers: built-in (installed with Miyu, `shipped`); system-installed (put there separately by the system package manager, `distro`: on Linux it is `miyu/packages/` under each entry of `$XDG_DATA_DIRS`, with `/usr/local/share:/usr/share` used when the variable is unset, and with Linuxbrew you add its own `share` to `XDG_DATA_DIRS`; on macOS it is `share/miyu/packages/` under the Homebrew prefix; Windows has no such layer; when `MIYU_DISTRO_PACKAGES` is set, only the place it names is looked at); and installed (`opt/` in the data root, `home`). When several layers have the same id, installed covers system-installed and system-installed covers built-in; the covered copy is not loaded, and this is not an error. Installing a package with the same id in the home layer is an upgrade and replaces the old copy; when you remove a built-in or system-installed package, the core records it in `etc/removed/` (an empty file named `<id>`) without touching the package's files, so it can be installed back later.

## `package.list`

**Params**: none. **Response**: `{"packages": [...], "groups": [...]}`. The packages are sorted by id; the groups are those in the shipped group table, each `{"id", "name", "summary"?, "packages"}`, in the connection's language; `packages` lists the installed packages in the group by their order of use (the order comes from the shipped group table, and any packages it doesn't list come after, sorted by id). A head (an interface program that connects to the core, such as the terminal interface or the web interface) uses it to gather a group's packages together in that order. Each item has these fields:

| Name | Notes |
|---|---|
| `package`, `layer` | The id; the layer it is in, which is `shipped`, `distro` or `home` |
| `shadowed` | Only a copy covered by an upper layer has this field: `{"by", "version", "over", "newer"}`, which are the covering layer, this copy's version, the version of the copy in use, and whether this copy is newer. This is not an error, so there is no `code` |
| `kind` | `builtin` (compiled into the core), `process` (an extension), `worker` (a small program started on demand), `ui` (an interface), `mascot`, `theme` (a look: a terminal theme or a web theme, see the `theme` row below), `bundle` (no program; it carries only MCP servers, skills, scripts and the like) |
| `name`, `summary`, `icon` | The name, a one-line summary and the Lucide icon name |
| `name_en` | The English name: present only when the connection's language isn't English and the manifest has an English name, and heads search with it too; `package.info` has it the same way |
| `logo` | The version of the package's own logo: present only when the manifest has `[package] logo` and the picture follows the rules; read the picture with `package.logo` |
| `author`, `upstream` | The author and the upstream source repository (starting with `https://`); left out when the manifest doesn't give them |
| `installed_at` | When the package was installed; shipped packages don't have this field. Heads sort the rest by it |
| `from` | Where it came from: `shipped` (built in), `official` (installed from the official package source), `local` (installed from a local folder or package file); once community sources exist there will also be `community` |
| `source` | How it got here, with the same values as an install preview's `source`: `official` (accepted by the official source), `community` (community-listed in the official source, or from a source you added in the config), `file` (installed from a local folder or package file), `shipped` (built in), `distro` (installed by the system package manager); an older install whose way in can't be worked out is `unknown`, which is never treated as official |
| `feed` | Present only for packages installed from a package source: which source it was, `official` for the official one, otherwise the name of the source you added in the config |
| `version`, `protocol`, `state` | The version, the protocol version it speaks, and the real path of its state directory |
| `groups` | The groups it is in (only shipped built-in packages have them; `basesystem` is the base system); left out when it is in no group |
| `features` | The features in the package (presets switch these) |
| `status`, `enabled` | Present only for packages with a process: whether it is running, and whether it is on |
| `connection` | Present only for a platform bridge (its manifest has `[connection]`): `{"platform", "platforms"?, "owner_builtin"?}`. `platform` is the platform it connects; when it connects several, it is the first one, and then `platforms` also comes (all of them, in manifest order). Heads use `platform` to draw "your account on this platform" on the package's info page, written into the owner bindings `external.bindings`. A platform with `owner_builtin: true` (only `voice` today) needs no account from the owner in the bindings, so heads don't draw that block; other platforms don't carry the key |
| `page` | Present only for packages with a package page; heads list it under package pages |
| `page_server` | The package page is a web service the package's program runs itself (manifest `[page] server = true`): heads ask its `status` for the `web` port and go there with a `login.ticket`, instead of putting it in a frame |
| `tray` | Present only for packages with a package page whose manifest has `[tray]`: `{"name"}`, the text of the tray menu line, in the connection's language; clicking it opens the package page. The tray lists only packages that are on |
| `theme` | What a theme package carries: `{"tui"?: {"file"}, "web"?: {"dir"}}`, where `tui` is the terminal theme file and `web` the web theme directory (an ordinary web package), with at least one of them; the paths are relative to the package directory, and the files are read with `package.file` |
| `mcp` | The MCP servers the package carries: `name`, `command` (`url` for a URL server), `venues`, `state`, `failures`…; `on` and `skipped` are the same as in an item of `mcp.list`. An extension that doesn't act for the owner (a platform bridge acting for outsiders in a venue) gets only `name` and `state` (`reason` for a stopped server) for each server; the package item itself also has none of `state` (the state directory), `pages_dir`, `command`, `commands`, `process`, `worker`, `check`, `problem`, `line` |
| `widgets` | The widgets it declares: `id`, `place`, `title`, `scope`, `command` |
| `command`, `commands` | The subcommands it adds to `miyu`: `command` is the first one, `{"name", "program", "about"}`, and `commands` all of them in manifest order (a package can add several) |
| `contents` | Which packages it carries content for (the ids under `[content.<package>]` in its manifest); left out when it carries no content |
| `provides` | What it carries, written the same way as the `provides` of each `package.search` row: kind mapped to names, the kinds being `command` (subcommands), `features` (features its manifest writes out), `mcp` (MCP servers), `slash` (slash commands), `content` (packages it carries content for), `skills`, `scripts` (script file names), `personas`, `presets`, `knowledge` (knowledge base ids: the folders under `kb/` in the package folder whose names are valid ids), each sorted by name; kinds it doesn't carry are left out, and it is `{}` when it carries none of them. Shipped, system-installed and installed packages, and removed shipped packages, all have this field, which the core works out from the package folder on the spot; heads use it to mark skills and scripts under "Installed" |
| `removed` | Marks a built-in package that has been removed |

A package that is broken, conflicting or unreadable has only `package`, `layer`, `code`, `problem` (in the connection's language) and `line` in its item. To keep the list up to date, subscribe to the `packages` stream.

## `package.info`, `package.files`, `package.owns`, `package.check`

| Method | Params | Response |
|---|---|---|
| `package.logo` | `package`, `from`? | `{"package", "logo", "media_type", "data"}`: the package's own logo, where `logo` is its version (the first 16 hex digits of the content's SHA-256, the same as that field in `package.list`), `data` is base64, and `media_type` is `image/png` or `image/webp`; all three are `null` when the manifest has no logo or the logo breaks the rules (missing, not PNG / WebP, over 256 KiB, wider or taller than 512). You can also add `from` (a package source's name, the same as the `source` of a `package.search` row) to read the logo of a package in that source, whether it is installed or not; an unknown source returns `unknown_source`, a package missing from the index returns `unknown_package`, and a failed download returns `download_failed` |
| `package.info` | `package`, `source`? | With `source: true` it looks only in the package sources, and with `false` only at installed packages; without it, it looks at installed packages first and then at the sources. An installed package returns `{"package", "layer", "from", "files", "size", "version"?, "author"?, "upstream"?, "license"?, "installed"?, "path"?, "source", "feed"?, "name"?, "summary"?, "depends"?, "recommends"?, "contains"?, "capabilities"?, "required_by"?, "origin"?, "tools"?}`: where it came from (`from`, `source`, `feed` as in `package.list`), the file count, the bytes, the author, the upstream, the license (the manifest's `[package] license` as written, left out when it has none), the install time, the local path it was installed from (`path`, for the owner only); the name, summary, dependencies, recommendations, what it contains (`contains`, the same as the "includes" of an install preview; it isn't shaped like `provides` from a source), the capabilities it asks for, the installed packages that depend on it, and the origin repository; `tools` lists the tools the model gets once it is installed, `[{"name", "title"?, "from"}]`: `name` is the tool name the AI sees, `title` the display name `{"zh"?, "en"?}`, and `from` is `script` or `extension` (MCP tools and tools known only once running are not listed). A package that isn't installed returns, from a source, `{"from": "source", "source", "package", "version", "depends", "recommends", "provides", "capabilities", "origin", "official", "name"?, "summary"?, "author"?, "upstream"?, "license"?, "download"?, "installed_size"?, "tools"?, "hosted"?, "unsupported"?, "stale"?}`: `source` is the source's name, `unsupported` is `true` when the package doesn't support this system (installing is refused with `wrong_target`), `provides` and `license` are as in the index, `download` is the size of the file this machine would download, `installed_size` the size once installed, `tools` comes from the index and is written as for installed packages, and `hosted` lists the tools a model driver has the provider run on its own, from the index, written as in the install preview |
| `package.info` | `path` (instead of `package`; `source` isn't accepted) | Looks at the absolute path of a package folder on this machine (or the `package.toml` in it) or of a `.miyu` package file, like pacman's `-Qip`: nothing is installed, and only the checks a real install makes are run. The response is shaped like the one for an installed package: `{"from": "file", "path", "package", "files", "size", "version"?, "name"?, "summary"?, "author"?, "upstream"?, "license"?, "depends"?, "recommends"?, "contains"?, "capabilities"?, "skipped"?, "replaces"?}`: `path` is as written (for a package file, that file, not the place it was unpacked to), `files` and `size` count the package's files and bytes, and `contains`, `capabilities`, `skipped` (skills, scripts and slash command templates that cannot be read, `[{"file", "why"}]`) and `replaces` are the same as in the `package.install` preview; there is no `layer`, `installed`, `required_by` or `origin` |
| `package.files` | `package` | `{"dir", "files": [{"path", "sha256", "size"}…]}`; `path` is relative to `dir` |
| `package.owns` | `path` (absolute) | `{"package", "layer", "path", "recorded"}`; `{"package": null}` when no package contains the path |
| `package.check` | `package` (optional) | `{"packages": [{"package", "modified", "missing", "extra"}…]}`: lists, for packages in the home layer, the files changed, missing or added since installation. A system-installed package has its own entry with `"layer": "distro"` and no hash comparison: it has `manifest` when the manifest cannot be read, and the programs the manifest names that are not in `bin/` go into `missing` |

**Errors**: `unknown_package` (`package.info` found it in neither place); `source_unreachable` (`package.info` with `source: true` looks only in the package sources, but the source can't be reached and there is no local index); `bad_params` (the path for `owns` is relative; `info` has both or neither of `package` and `path`, has `source` together with `path`, or has a relative path). `info` with `path` also refuses the way `package.install` does: `path_unreadable`, `package_invalid`, `package_conflict`, `wrong_target`, `package_exists`, `package_file_bad` and `depends_missing`; for details see the next section.

## `package.install`, `package.remove`

| Method | Params | Response |
|---|---|---|
| `package.install` | `path`: the absolute path of a local package folder (the folder name is the id), of the `package.toml` in it, or of a `.miyu` package file | The same as an item of `package.list` |
| `package.install` | `package`: a built-in or system-installed id installs the removed package back; any other id works the same as `source` and installs from the package source | The same |
| `package.install` | `source`: installs this id from the package source (missing dependencies are installed along with it, and first; a dependency with a version floor is picked to meet the floor, and an installed one below the floor is upgraded along with it); everything is downloaded first, then each file is checked, then each package is installed, and `package.progress` is pushed to this connection at every stage (see below). `from` (optional): which package source to install from (`official` or the name of a source added in the config); without it the sources are tried in order | The same, plus `with` when dependencies were installed along with it |
| `package.install` | `package`: a group id (from `groups` at the top of `package.list`, such as `basesystem`) installs all of the group's removed shipped packages back | `{"group", "packages": [<an item as in `package.list`>…]}`, which is empty when none was removed |
| `package.remove` | `package`; `purge` (optional, default `false`): `true` also deletes the config directory `etc/<id>/` and the package's settings in the system config; without it both are kept, and a reinstall of the same id uses them again (as pacman does). An id that is already removed but still left these behind also accepts `purge: true`, which then deletes only what was left; without `purge` it still returns `unknown_package` | `{"package", "removed": true, "layer"}` (no `layer` when purging an id that isn't installed) |
| `package.remove` | `package`: a group id removes all of the group's installed packages; when an installed package outside the group depends on one in the group, the whole request is refused (`package_depended`, with `data.by` naming those packages); `purge` works as above and is passed on to every package in the group | `{"group", "removed": [<id>…]}` |

Both methods take `preview: true`: it only previews and changes nothing, and it is refused in the same cases the real call would be. The install preview returns `package`, `version`, `replaces: {"version"}` when an existing copy is replaced, `restores: true` when a built-in or system-installed package is brought back, and what it carries (`program`, `mcp`, `drivers` (the model drivers it provides), `hosted` (the tools a driver has the provider run on its own: `{"<driver>": ["<tool>", …]}`, from the manifest's `[[driver]]` `hosted`; drivers that don't declare any are left out, and so is the whole field when none does), `command` (the first subcommand name), `commands` (every subcommand name), `page`, `mascot`, `theme`, `connection`, `settings`, `skills`, `scripts`, `slash`, `personas`, `presets`, `knowledge` (knowledge base ids), `capabilities`, `files`, `size`); the remove preview returns `package`, `layer`, `version`, `files`, `size`, `settings` (the config keys removed along with it: listed only with `purge`, and `[]` otherwise), `state` (the state directory removed along with it: `{"path", "size"}`, where `path` is the location of `var/lib/<id>/` and `size` the total bytes of the files under it, not following symbolic links; left out when there is no state directory) and `config` (the config directory and settings: `{"path"?, "kept", "settings"?}`, where `path` is the location of `etc/<id>/`, left out when the directory is missing or empty; `settings` is how many of the package's settings the system config has, left out when there are none; `kept` is `true` when both stay and `false` when both are deleted (with `purge: true`); the whole field is left out when there is neither). Settings that a removed package left in the config take no effect, and `check` doesn't report them as unknown keys; instead it reports one `settings_left` per package.

An install preview from a package source also has `source` (where it comes from: `official` for an official entry of the official source, `community` for one the official source lists from the community or for anything in a source added in the config), `feed` (the source's name, `official` for the official one), `official`, `origin`, `download` (the bytes to download, dependencies included), `with` (the dependencies installed along with it, `[{"package", "version", "source", "feed", "capabilities"?}]`), `recommends` (packages that the packages being installed recommend and that aren't installed yet, without duplicates: `[{"package", "version", "source", "feed", "capabilities"?, "download", "installed_size"?}]`, empty when there are none) and `installed` (the total bytes once every package being installed is in place, recommendations not counted; left out when the index lacks the size of one of them); `capabilities` is shaped the same as for a package folder (`{"id", "name", "summary"}`); `hosted` comes from the index, is shaped the same as for a package folder, and is left out when the index doesn't have it.

Where it comes from and what it needs: the preview's `source` is one of five values: `official` or `community` when installing from a package source, `file` when installing from a package folder or package file, and `shipped` or `distro` when bringing one back. Each capability that is already approved right now and stays approved after the install has `held: true`: this happens only when installing from a package source with the same source and origin repository as the installed copy (installing from a local file, from another source or from another origin repository doesn't carry earlier approvals over). Community and local-file previews have `notice`: the text to show the person, in the connection's language, one sentence per string (`This is a community package. It has not been reviewed and may be risky.` for community packages, `This package comes from a local file. It has not been reviewed and may be risky.` for local files; when several packages are involved they are named, with one sentence for each of the two cases when both occur); when this applies to recommended packages, it goes into `recommends_notice` as well. Heads must print it as it is; a prefix such as "Note:" is the head's own wording.

Approving while installing: `package.install` (`path`, `source`) and `package.upgrade` take `approve`: `{"<id>": ["<capability>", …]}`, with one entry for each package installed this time (build it from what the preview lists: the package being installed and those in `with`; for upgrades, those in `upgrades` and `with`). A malformed capability name or id returns `bad_params`; the core ignores capabilities the installed copy doesn't declare and ids that aren't installed this time; without `approve` the package is installed unapproved, and is approved when it is opened, through the `approve` of `package.enable` or `extension.enable` as before. Approved capabilities go into `approved` in `extensions.json`, worked out as "(earlier approvals when source and origin repository are unchanged ∪ this approval) ∩ what this copy declares", so a capability a new version no longer asks for is dropped and has to be approved again if it comes back later. A manual (`start = "manual"`) extension then opens without being approved again, and an extension that runs whenever it is on starts running right after the install.

During a real install, the core pushes `package.progress` to this connection: `{"package", "stage", "index", "count", "done"?, "total"?}`. `stage` is `download` (with `done` and `total` bytes), `verify` (before checking) or `install` (before installing); `index` and `count` say which one of how many it is (counting from 1). Installing from a package folder or package file pushes only one `verify` and one `install` (`1` of `1`). Older cores push only `{"package", "done", "total"}`: treat a missing `stage` as `download`.

Installing and removing take effect at once: packages with a process start or stop according to their switches, their tools enter or leave the tool catalog, and open sessions pick up the new tools at the next turn.

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | Both params were given; the path isn't absolute |
| `path_unreadable` | The folder can't be read |
| `package_invalid` | The manifest is wrong; see `data.problem` and `data.line`; for a package that needs a newer Miyu, `data.problem` is `needs_newer_miyu` |
| `package_conflict` | A name the package brings clashes with another installed package: a subcommand, feature, tool, skill, MCP server, knowledge base, slash command, persona, preset, prefix or bus name (`bus`: a name has only one provider, and a name can't be provided by one package and plugged by another) |
| `not_permitted` | The `package` tool in a session: when the session isn't the owner's (one acting for outsiders in a venue), installing, upgrading, removing or restoring a package, and enabling an extension, are refused; listing, looking and searching still work |
| `package_exists` | The package has the same id as a built-in package |
| `package_file_bad` | The package file can't be unpacked; or, when installing from a package source, the id inside the package doesn't match the index entry |
| `download_failed` | When installing from the package source, the package file couldn't be downloaded from anywhere (a size or hash mismatch counts too); `data.why` gives each place's reason |
| `wrong_target` | The package isn't supported on this system: the manifest lists `targets` without this one, or `systems` without this system. When installing from the package source, the core refuses based on the index, before downloading |
| `depends_missing` | A dependency isn't installed, or the installed version is lower than the floor the manifest asks for; `data.missing` lists the missing ones as the manifest writes them (`"onebot>=1.2.0"` for one with a floor) |
| `package_depended` | Another installed package depends on it; see `data.by` |
| `unknown_package` | The package isn't installed, or was never removed |
| `unknown_source` | The source named in `from` doesn't exist (it wasn't added, or it is misspelt) |

## `package.sync`

This method fetches the index from the package source. Param `force` (optional): `true` fetches again no matter how recent the local copy is; without it, a local copy younger than 24 hours is used as is. Addresses are tried in the order of the system config's `packages.mirrors`, then `packages.source`; the index's signature is verified against the official public keys built into Miyu, and an index older than the local copy is not accepted.

Response `{"generated", "fetched", "packages", "stale"?}`: when the index was generated, when it was fetched (both RFC 3339), and how many packages it lists; when nothing could be fetched this time and the local copy is used, it carries `stale` (the last place's reason, in English).

Other package sources: these are the `packages.sources.<name>` entries in the system config that have a `url` and a `key` (a base64 Ed25519 public key). The core fetches them after the official index, verifying each against its own key; the response adds `sources: [{"source", "generated", "fetched", "packages", "stale"?}]`, with `{"source", "error"}` for a source that couldn't be fetched.

**Errors**

| `data.reason` | When |
|---|---|
| `source_unreachable` | Nothing could be fetched from anywhere and there is no local index; `data.why` is the last place's reason |

## `package.search`

This method searches the package source. Param `query` (optional): a few words separated by whitespace, each of which must appear in the id, name or summary (in any language), case-insensitive; when it is absent or empty, everything is listed. Before searching, it fetches the index the way `package.sync` does (a local copy younger than 24 hours is used as is).

Response `{"packages": [...], "generated", "stale"?}`, where each item is `{"package", "version", "name", "summary", "official", "installed", "blocked", "contents", "provides", "depends", "kind"?, "icon"?, "logo"?, "license"?, "published"?, "downloads"?, "downloads_week"?, "unsupported"?}`: the name and summary are picked by the connection's language (falling back to English, Chinese, then Japanese), and are `null` when there are none; `installed` is the installed version (an empty string when installed without one), `null` when not installed; `official` says whether it comes from the owner's own repositories; `blocked` is the reason it was blocked, `null` when it wasn't; `contents` lists which packages it carries content for (as in `package.list`), an empty array when none; `provides` is what it carries, kind mapped to names, the kinds being `command` (subcommands), `features`, `mcp` (MCP servers), `slash` (slash commands), `content` (packages it carries content for), `skills`, `scripts`, `personas`, `presets`, `knowledge` (knowledge bases), with kinds it doesn't carry left out and `{}` when it carries none of them; `depends` lists the packages it depends on as the index has them: an id, or an id with a version floor `<id>>=<version>`, an empty array when there are none; `kind` is the package kind: manifests don't state a kind, so when the index is generated it is worked out from the tables the package carries, and it is one of `ui`, `process`, `builtin`, `worker`, `mascot`, `theme`, `bundle` (kinds added later are passed through as they are), missing from indexes generated earlier; `source` is which package source it comes from (`official` or the name given in the config), and `official` is always `false` for packages in other sources; `icon` is the Lucide icon name and `logo` the version of the package's own logo (as in `package.list`; read the picture with `package.logo` and `from`), present only when the index has them; `license` is the license the manifest writes (an SPDX expression is recommended; the core does not check it), present only when the index has it; `published` is when this version first entered the package source (RFC 3339), `downloads` how many times all its versions and systems were downloaded in total, and `downloads_week` how many times in the last 7 days, present only when the index has them and they are written correctly (heads use them to sort by newest, downloads and trending, with missing ones last). Packages that don't support this system (the manifest lists `systems` or `targets` without this one) are left out by default; with the `packages.other_systems` setting on they are still listed, that row carries `unsupported: true`, and installing them is still refused with `wrong_target`. The errors are the same as for `package.sync`.

## `package.clean`

This method deletes downloaded package files that aren't the installed version. It takes no params; the response is `{"removed", "freed"}`: how many files were deleted and how many bytes were freed.

## `package.upgrades`, `package.upgrade`

These two methods upgrade packages from the package source. They only touch packages installed from a package source into the data root; packages installed from a folder or a package file are left alone, and so are shipped packages and packages installed by the system package manager (`distro`), because Miyu's own installer and the system package manager upgrade those. The core doesn't compare versions by size: whenever the index's version differs from the installed one, it upgrades. When the new version in the index needs a newer Miyu than the one running (the manifest's `[package] miyu`), the package does not count as upgradable and goes into `needs_newer_miyu`.

| Method | Params | Response |
|---|---|---|
| `package.upgrades` | None | `{"upgrades": [{"package", "from", "to"}], "moved": [{"package", "was", "now"}], "gone", "blocked": [{"package", "reason"}], "held", "needs_newer_miyu": [{"package", "to", "miyu"}], "generated", "stale"?}`: in order, the packages that can be upgraded; those whose origin repository changed and that are therefore not upgraded; those gone from the package source; those blocked; those skipped by the system config's `packages.hold`; those whose new version needs a newer Miyu and that are therefore not upgraded (`to` is the version in the index, `miyu` is the Miyu version it needs) |
| `package.upgrade` | `packages` (optional; when given, only these are upgraded), `preview`, `approve` (as for `package.install`) | A preview returns `{"upgrades", "download", "with", "notice"?}`: each item of `upgrades` also has `source`, `feed` and `capabilities` (the capabilities the new version declares, with `held`), and `with` lists the new dependencies installed along with it (shaped as in the `package.install` preview); a real upgrade returns `{"upgraded": [{"package", "from", "to"}]}` and pushes progress while downloading, as `package.install {"source"}` does |

## `package.enable`, `package.disable`, `package.restart`

**Params**: `package`; `enable` also takes `approve`, which approves the capabilities the package declares (see "Capabilities" in [Extensions](extensions.md)). **Response**: the same as an item of `package.list`.

- Extensions: turning one on starts the process; turning it off asks it to exit, and the tools it registered leave the tool catalog.
- `bundle`: turning one on starts its MCP servers; turning it off stops them.
- Shipped built-in packages: turning one off removes it, and turning it on installs it back.
- `restart`: restarts the extension process and its MCP servers, and the count of consecutive failures starts over from zero.

**Errors**

| `data.reason` | When |
|---|---|
| `unknown_package` | There is no such package |
| `program_missing` | The package's program wasn't found (neither in the package folder's `bin/` nor next to `miyu`) |
| `needs_approval` | Some of the capabilities it needs aren't approved yet; see `data.capabilities` |
| `package_depended` | The package being turned off is a dependency of another package |
| `package_off`, `not_restartable` | `restart` was called on a package that's off; there is no process or server to restart |

## `package.file`, `package.call`, `package.page`

**`package.file`**: params `package`, `path`, `offset`. Response `{"data", "size", "eof"}`, at most 512 KiB at a time. The web interface's package pages, mascot model files and theme packages' themes are all read this way. For a package page, `path` is a path relative to the page folder; for a mascot package it can only be the `model` file; for a theme package it is written relative to the package directory and can only be the terminal theme `file`, or any regular file under the web theme directory (e.g. `web/index.js`). The core resolves real paths: links that lead out of the package directory or the web directory, the directory itself, and any other path all return `not_found`.

**`package.call`**: params `package`, `method`, `params` (optional). The core forwards it to that package's program (`method.call`) and returns whatever the program answers. This method is answered in the background. Widget buttons and saving full-page forms go through it.

**`package.page`**: param `package`. Response `{"url"}`: this is the package's host page on the local package page service the core starts on demand (`http://127.0.0.1:<port>/h/<ticket>/`); hand it to a browser to open, and you don't need the web interface installed (`miyu pkg page` opens it this way). It works only for packages whose page is inside the package directory (manifest `[page] dir`). The service starts the first time it is needed and stops after ten idle minutes (no requests and no open push stream); its addresses stop working then, and asking again is all it takes. The host page puts the page in an isolated frame the way the web interface does, calls `settings.get`, `settings.set` and `call` for it, and follows the system's light or dark mode.

`package.call` is for people's connections (the heads, the command line, programs a person starts in a terminal): they reach every method any package registered, whether or not it is in `[export]`, and the forwarded call carries no `from`. An extension (a package's program the core started) reaches only itself by package id: when `package` holds another package's id, it gets `own_package_only`, whether or not that package exists or exports the method; to call itself, it must declare the `packages.call` capability, it can call only the methods listed in its own manifest's `[export]`, and the forwarded call carries `from` (its own id). To call another package, an extension must go by name through [`bus.call`](bus.md).

**Errors**

| `data.reason` | When |
|---|---|
| `no_page`, `not_found` | `package.file`: there is no package page; there is no such file, the path leads outside the folder, or it isn't a regular file. `package.page`: there is no page inside the package directory (`no_page`) |
| `program_not_running` | The program isn't connected |
| `unregistered` | The program didn't register that method; see `data.method` |
| `method_failed` | The program answered with an error; see `data.message` and `data.code` (an extension that answers with a string error code puts it in `error.data.code`, and the core passes it on; otherwise `error.code` is used). When the program's answer is a line over 1 MiB the core doesn't read it, and `data.code` is then `line_too_long` |
| `method_timeout` | There was no answer within the time limit |
| `own_package_only` | Called by an extension: `package` isn't its own id, and `data.package` is the id it wrote. Use `bus.call` across packages |
| `needs_approval`, `not_exported` | An extension calling itself: it hasn't declared `packages.call`; the method isn't in its manifest's `[export]` (see `data.method`) |

## `extension.status`, `extension.enable`, `extension.disable`, `extension.restart`

**Params**: `status` takes none; the other methods take `package`, and `enable` also takes `approve`. **Response**: `status` returns `{"extensions": [...]}`, and the other methods return the one extension. Each extension has these fields:

| Name | Notes |
|---|---|
| `package`, `name` | The id and the name |
| `start` | When the manifest says to start it |
| `on` | The switch |
| `state` | `off`, `starting`, `running`, `waiting` (it failed and is waiting to be restarted), `stopped` |
| `failures` | How many times in a row it has failed |
| `pid` | The id of the running process |
| `retry_in` | Present only while waiting: how many milliseconds until the next start |
| `reason`, `stderr` | Present only when stopped: why it stopped (`failed_repeatedly`, `config_error`, `needs_approval`, `needs_login` for a URL server that needs a browser login…), and the last lines of its stderr |
| `capabilities`, `unapproved` | The capabilities it declares `[{id, name, summary}]`, and those not yet approved |

To keep the status up to date, subscribe to the `extensions` stream.

**Errors**: `unknown_package`; `not_an_extension` (it is a UI package); `extension_off` (an extension that's off was restarted); `needs_approval`.

## `driver.check`

This method checks that a package's model drivers encode steadily (authors call it with `miyu dev driver-check <package id>`). It is for people only. **It restarts the extension.**

The core calls the extension's `driver.encode` with a small built-in set of sample requests (five of them: plain text, a tool surface, one with private data (reasoning, a provider-run tool and a tool call in the same message, each carrying private data), image descriptions for an endpoint that can't see images, and a continuation; the provider-run tool is a `hosted_tool` of this driver's own, with a result and private data, handed over as is just like in a real call): each sample is encoded twice; then the extension is restarted, and once it has shaken hands again, each sample is encoded once more; all three results must be byte for byte the same. There is also a pair of samples that differ only by one more message at the end: the last stable-region message carries the mark `miyustableend7f3a`, the bytes of both encodings must contain it, and they must be byte for byte the same up to it. If the mark can't be found, the stable region can't be checked, and that counts as a failure.

**Params**: `package`. **Response** `{"package", "drivers": [...]}`, with one entry per driver:

| Name | Meaning |
|---|---|
| `driver` | `<package id>/<driver name>` |
| `cache` | The cache type the manifest gives |
| `result` | `passed`, `failed`, `skipped` |
| `samples` | `[{"sample", "ok", "why"?}]`: `plain`, `tools`, `private`, `image`, `continuation`, `pair`; a sample that failed has `why`, an English sentence saying what differs (at which byte) |
| `why` | Present only when `driver.encode` isn't implemented: `driver.encode is not implemented`. A `cache = "contract"` driver then counts as `failed`, and other drivers as `skipped` |

**Errors**: `unknown_package`; `no_drivers` (the manifest has no `[[driver]]`); `program_not_running` (it isn't connected, or there was no handshake after the restart); `driver_busy` (a session is calling a model through its driver right now, and `data.running` is how many calls are still unanswered: check again once they are done; nothing is restarted); `extension_off`, `needs_approval` (as for `extension.restart`).

## `mcp.list`, `mcp.restart`, `mcp.set`, `mcp.remove`

These methods manage the MCP servers in the system config (`[mcp.<name>]` in `config.toml`). Whether you edit the system config by hand or change it through `mcp.set` and `mcp.remove`, the change takes effect at once: new servers start, changed ones stop and start again, and removed ones stop.

**`mcp.list`**: no params. Response `{"servers": [...]}`, where each item has `name`, `command` (a URL server doesn't have this field and has `url` instead), `venues`, `state` and `failures`; a running server has `pid` (a URL server doesn't), a waiting one has `retry_in`, and a stopped one has `reason` and `stderr`; `covers` lists the packages whose same-named server it covers. When its tools are known it also has `tools`: the server's tool names in the tool catalog right now (`mcp__<server>__<tool>`), whether listed by the server after it started or registered first from the catalog cache; a server that declares resources also has the two tools `mcp__<server>__list_resources` and `mcp__<server>__read_resource`; the field is left out while the tools are unknown (never started, no cache). Tools the server listed this time but that were not registered come in `skipped: [{"tool", "why"}]` (`{"prompt", "why"}` for a prompt), sorted by their original names: `tool` is the server's own name for it (empty when it had none), and `why` is one of `name` (it has no name), `parameters` (the parameters schema is not an object) or `name_taken` (it clashed with another name after being cut to 64 characters, or another tool already has the name); the field is left out when everything was registered, or when the tools were only registered from the catalog cache and haven't been listed yet, and `miyu check` reports it as `mcp_tool_skipped`. `on` is the server's global switch (`features.mcp-<server>`, see `feature.set`), `true` when unset. A server logged in through the browser (a token from `mcp.login` is stored) has `logged_in: true`; a server that never logged in, or one after `mcp.logout`, doesn't have this field. Heads use it to show "Log out" instead of "Log in"; the field tells only whether a token is stored, and the token itself is never handed out over the protocol. So that editing can start from what was written before, the response also carries `env` (each value text, or `{"secret": …}`, `{"env": …}`; left out when none) and `timeout_ms` (only when not the default), plus `bearer` and `headers` for a URL server (written like `env`). These fields come back as written (they are in plain text in the system config anyway): heads mask them on display and show them in full only in the edit box; values worth hiding should be written as secret references; `command` is the program together with its arguments, and must be split into `command` and `args` when it is sent back to `mcp.set`.

**`mcp.restart`**: param `name`. The response is the item of the restarted server. **Errors**: `unknown_server`.

**`mcp.set`**: adds a server to the system config, or replaces the server with the same name as a whole.

| Name | Type | Notes |
|---|---|---|
| `name` | string, required | The server name: it starts with a lowercase letter and contains only lowercase letters, digits and `-`, at most 32 |
| `command` | string | The program; write only one of this and `url` |
| `args` | array of strings | The arguments after the program; it needs `command` as well |
| `env` | object | Environment variables: each value is text, or `{"secret": …}`, `{"env": …}`; it is used together with `command` |
| `url` | string | A server at a URL: it starts with `https://`, and a server on this machine can use `http://`; write only one of this and `command` |
| `bearer` | text or object | A token, sent as `Authorization: Bearer <value>`; it is written like an `env` value; it is used together with `url` |
| `headers` | object | Other request headers, with values written like `env` values; `Authorization`, `Mcp-Session-Id`, `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` are reserved for the core; it is used together with `url` |
| `venues` | array of strings | Which sessions get the server: `local`, `private`, `group`; when it is left out, only local sessions get it |
| `timeout_ms` | integer | How long one call may wait, from 1000 to 3600000; 600000 when it is left out |
| `clicall` | boolean | Whether the AI can call this server's tools with `miyu call` inside a command; when it is left out, the value written before stays, and if nothing was written before, the AI can |

Fields you don't send are not written: when a server is replaced as a whole, what was written before and isn't sent this time is dropped. Before writing, the server is checked by the same rules as reading the server table, and it is written the way `config.set` writes (with a version, never over a hand edit made at the same time). Response `{"name"}`; the server then changes to follow what was written, and state changes push `mcp.changed`. **Errors**: `mcp_invalid` (it is badly written; `data.problem` says what is wrong, and this error is also returned when neither or both of `command` and `url` are written); `bad_params` (`args` was sent without `command`); `server_from_package` (the system config has no server by that name, but a package brings a server with the same name: servers that come with packages can't be changed through this method); `config_file_broken` (the system config can't be read, or `mcp` is written in a shape that can't hold a server); `config_conflict`.

**`mcp.remove`**: param `name`. It removes the server (with its sub-tables) from the system config, and the response is `{}`. A package server with the same name that it covered starts again according to the package's switch. **Errors**: `unknown_server`; `config_file_broken`; `config_conflict`.

## `mcp.login`

When a URL MCP server answers `401` and needs a browser login (`reason` is `needs_login`, and its table has no token of its own), this method gets the authorization page: after the person agrees in the browser, the core exchanges the code for a token and stores it in the secrets file (`mcp-oauth-<server>`, a value never handed out over the protocol), and the server connects by itself (`mcp.changed` and the package list pushes arrive as usual). It is for people only, remote connections included: the core only hands back the address, and the head opens it on its side; the callback listens on `127.0.0.1` of the core's machine, so when the browser isn't on that machine, paste the address back with `mcp.login_finish`.

**Params**: `service` (the server name, from the system config or carried by a package).

**Response**: `{"url"}`: the address of the authorization page, which the head opens. The core waits for the callback on `127.0.0.1` on this machine, for up to 10 minutes; when the same server logs in again, the earlier login that was waiting is stopped.

**Errors**: `unknown_server`: there is no such server; `bad_params`: it isn't a URL server, or its table has its own token (`bearer`, or `Authorization` in `headers`); `oauth_unregistered`: there is no client and the authorization server doesn't accept dynamic registration, so a person has to register a client with the service and put its `client_id` in the table; `oauth_failed`: the authorization server can't be found or used (every address on the way must be `https`, and a loopback address such as `127.0.0.1` is accepted only when the server itself is on this machine), or it refused, and `data.why` says why (the authorization server's own words, shortened).

After logging in: when the token is about to expire or the server answers `401`, the core renews it with the `refresh_token` itself, and writing the renewed token back to the secrets doesn't restart the server. If renewing fails, or the server says the scope isn't enough (`403 insufficient_scope`), the server stops at `needs_login`, and you need to call `mcp.login` again (this time it asks for the earlier scope plus the one needed now).

## `mcp.login_finish`, `mcp.logout`

**`mcp.login_finish`**: when the browser isn't on the core's machine (the web interface connected from another machine), after the authorization the browser lands on an unreachable `http://127.0.0.1:<port>/callback?…`; hand back that whole address from the address bar, and that is all. Params `service`, `url`. The core checks `state` and `iss` in the same place as for a callback received locally. It is for people only, remote connections included. **Response**: `{}`: the token has been exchanged and stored, and the server connects by itself. **Errors**: `not_waiting`: no login is waiting for this server, so call `mcp.login` first; `oauth_failed`: the address doesn't match (that login keeps waiting, so you can paste again), or the token exchange was refused.

**`mcp.logout`**: deletes what's stored (the token, the client, the callback port) and cancels a login that is waiting; the server restarts and stops at `needs_login`. The core doesn't revoke the token at the authorization server. Param `service`. It is for people only, remote connections included. **Response**: `{}`. **Errors**: `not_logged_in`: this server has never been logged in.

## `command.run`

This method runs a slash command: the head passes along exactly what the person typed, and the core recognizes the command, checks who may use it, and runs it.

**Params**

| Name | Type | Notes |
|---|---|---|
| `session` | string, required | Which session |
| `text` | string, required | Exactly what the person typed, e.g. `/stop` |
| `cwd` | string | The head's directory; it is only used to resolve a relative path after `/workspace` |
| `as` | object | For venue sessions: speaks for a person on the platform, as in `session.send` |
| `prefix` | `"keep"` or `"compact"` | For commands that start a new turn (templates, MCP prompts, setting or resuming `/goal`): the person's choice when the prefix is about to change, as in `session.send` (**Prefix changing**) |

**Response**: `{"command", "events", "said"}`: the canonical name (aliases are resolved to it), the events appended this time, and the reply line (in the connection's language, shown to the person as it is). A command that opens a full page returns `{"command", "opens": {"package", "widget"}, "said": ""}`, and the head opens that page.

**Commands the core knows**:

| Command | What it does |
|---|---|
| `/clear` (`/reset`) | Clears the context and the to-do list, like `session.clear` |
| `/stop` | Removes this session's loop, interrupts this turn, and stops the background commands and subagents this session spawned, and the organizing in progress |
| `/workspace <path>` | Changes the working directory; without a path, tells you where it is now |
| `/context <tokens>`, `/context unset` (or `off`), `/context` | Sets this session's context limit (`128000`, `128k` and `1m` all work), like `context` in `session.configure`; removes the limit; tells you the limit and the compaction line right now |
| `/todo`, `/todo clear` | Shows the to-do list; clears it |
| `/remember <words>` | Records a memory |
| `/dream`, `/dream stop` | Organizes memory right now (answered in the background); stops the organizing in progress, keeping what has already been merged |
| `/clear-memory` (`/reset-memory`) | Clears the memories this session recorded |
| `/goal` family | Shows, sets, pauses, resumes, edits or clears the standing goal |
| `/loop <interval> <prompt>`, `/loop <prompt>`, `/loop`, `/loop off` | Sends the prompt at a fixed interval; lets the model decide when to run next (if its turn sets no next run, the loop ends and its row is removed); lets the model decide what to do and when (an autonomous loop); stops this session's loop (`/loop clear` and `/loop stop` do the same). A session has only one loop, and typing the command again replaces the old one; a command typed (or due) while the session is running a turn waits for that turn to end before running, instead of joining it; when the session's preset has loops off, the command doesn't exist. |

When it is none of these, the core looks it up, in order, among your own command templates (`commands/<name>.md`), the commands extensions declare (the core forwards them to the extension, `command.call`), and the command templates packages carry. A template expands into a message sent as if the person said it: the response's `events` is that message, and `said` is empty.

A command named `<server>:<prompt>` (with exactly one `:`) is an MCP server's prompt: the core fetches it with `prompts/get`, splitting the words the person typed after it on whitespace (a pair of English double quotes makes one word, and the quotes are removed) and matching them to the prompt's declared arguments in order, with the last argument taking the whole rest. The text and images that come back are merged into one message from this person and sent, the same as a template. These commands are recognized only in local sessions, and they follow the switch of the server's feature `mcp-<server>`.

**Who can use them**: everyone can use them in local sessions; in venue sessions, the owner and managers can. The system setting `commands.<name>.access` can change that to `anyone` (anyone can use it) or `off` (disabled). `/workspace` is for the owner only.

The same `id` sent again counts only once: with the same parameters you get the first response back (the `events` and `said` from that time), and the command isn't run again; with different parameters it is refused with `id_reused`, and the command isn't run. The core remembers the last 1024 and forgets them on restart, after which the command runs again. Refused requests are not remembered, so sending again is judged again.

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | It doesn't start with `/`; `cwd` isn't absolute; the words after the command are wrong (for `/loop`, `data.why` is the usage in the connection's language, one form per line); the `/context` limit is too small (`data.field` is `context`, and `data.min` is the least accepted) |
| `unknown_command` | There is no such command |
| `command_not_allowed` | This person can't use the command, or it is disabled or off in the preset; `data.why` is a sentence for people |
| `owner_only` | Only the owner can use the command |
| `command_unavailable`, `command_failed` | An extension's command: the extension isn't connected or didn't answer within a minute; it answered with an error (`data.why` is its own words) or without `said` (`data.why` is in the connection's language). An MCP prompt: the server isn't running, didn't list that prompt, the session isn't local, or it didn't answer in time (the server's `timeout_ms`, at most a minute); a required argument is missing (`data.why` names them in the connection's language), or the server answered with an error (`data.why` is its own words) |
| `memory_unavailable`, `goal_unavailable` | This session has no memory, or no standing goal; see `data.why` |
| the command's own | `/clear`'s `turn_running`, `nothing_to_clear`; `/workspace`'s `path_unreadable`…, the same as for the matching method |

## `command.catalog`

**Params**: `session` (optional): when it is given, only the commands this connection can type in this session without being refused are listed; without it, everything is listed, except that commands that come with a package (`/loop`, `/goal`, `/todo`) are filtered by your default preset and left out when the default preset doesn't turn that package on.

**Response**: `{"commands": [{"name", "aliases", "summary", "argument"?, "usage"?, "opens"?}…], "skills": [{"name", "summary"}…]}`, sorted by name. Skills are listed separately in `skills`: name them with `$skill-name` in the input box, and put them in `skills` when sending `session.send` (see [Sessions](sessions.md)); one message can name several skills. Skills with `user-invocable: false` are left out, and when a session is given, only the skills its preset turns on are listed. The prompts of running MCP servers are listed too: they are named `<server>:<prompt>`, `summary` is the `title` the server gives (or its `description` when there is none; not per language), and `argument` is built from the declared arguments (`<name>` for required ones, `[name]` for optional ones). `argument` hints at what follows the name, `usage` lists the forms of a command that has several, one per line (`{"form", "summary"}`), and `opens` marks commands that open a full page. `summary` and `argument` are in the connection's language.

Heads add their own commands (such as `/help`) to the menu themselves.

## `check`

**Params**: `cwd` (where to look for a project config from), `file` (check only this one file).

**Response**: `{"problems": [...]}`, one item per problem: `kind` (`config`, `secrets`, `persona`, `preset`, `package`, `script`, `skill`, `slash`, `mcp`, `schedule` (an unreadable row in the schedule table, `schedule_unreadable`); a package's own check passes on whatever it reported, e.g. `venue`), `file`, `code`, `level`, `message`, plus `line` and `column` when the position is known, `key`, `got`, `suggest` and `using` for config problems, and optionally `key`, `rule` and `source` from a package's own check.

Without `file` it checks everything: the system config, the project config of `cwd`, the secrets file, personas and presets in every layer, package manifests, and packages' own checks; scripts, skills and command templates that can't be read, are covered, or are links into a part of the data root that isn't recognized; scripts not registered because of a name clash; command templates named like a built-in command; tools and prompts an MCP server listed that weren't registered; and installed files that were changed or went missing. The response also carries `embedding`, the state of the semantic model, which is not a problem: `model` (`null` with `why` when it can't be used), `filling` while it backfills in the background, `memory` and `turns` with one `{persona, have, total}` per persona, `kb` with one `{id, name, have, total}` per knowledge base, and `no_recall`, which of `memory` and `kb` this model does not recall on its own (a model missing from the threshold table doesn't recall on its own; search still works).

**Errors**: `unknown_file`: `file` isn't one of the kinds of file Miyu reads.
