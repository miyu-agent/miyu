# Extensions: how programs the core launches talk

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

An extension is a program that a package brings: the core launches it according to the manifest and talks to it in the same protocol over stdin and stdout. This page lists what is specific to extensions: what the core gives them at launch, which methods only extensions may call, and which methods the core calls on them. For a tutorial that writes an extension from scratch, see [Writing an extension](../dev/extensions.md).

| Method | Direction | What it does |
|---|---|---|
| [`provide`](#provide) | extension → core | Registers the tools it provides |
| [`tool.call`, `tool.cancel`](#toolcall-toolcancel) | core → extension | Calls one of its tools; drops a call |
| [`package.methods`, `method.call`](#packagemethods-methodcall) | both | Registers the methods its background page and widgets call; receives calls the core forwards |
| [`package.emit`](#packageemit) | extension → core | Pushes to people who have its page open |
| [`feature.offer`](#featureoffer) | extension → core | Offers features to this person's preset menu |
| [`port.claim`, `port.release`, `port.list`](#portclaim-portrelease-portlist) | extension → core (`port.list` for the owner) | Claims and releases the ports it listens on; shows the whole table |
| [`command.call`](#commandcall) | core → extension | A person typed a slash command it declared |
| [`user.append`](#userappend) | core → extension | At the start of a turn, asks whether it wants to add a few lines to the context |
| [`tool.guard`, `guard.cancel`](#toolguard-guardcancel) | core → extension | Before a tool call runs, asks it whether to allow, deny or ask the person; stops waiting for its answer |
| [`tool.after`](#toolafter) | core → extension | Tells it after a tool call's result is written to disk (read-only, no answer expected) |
| [`driver.call`, `driver.delta`, `driver.cancel`](#drivercall-driverdelta-drivercancel) | both ways | The model driver it provides: takes one model call and streams deltas back; stops waiting |
| [`driver.approve`](#driverapprove) | extension → core | In the middle of a call, asks the core to show Miyu's confirmation to the owner |
| [`driver.encode`](#driverencode) | core → extension | Encodes once without sending, to check that the encoding is steady |
| [`driver.models`](#drivermodels) | core → extension | Lists the models it can use (optional) |
| [`system.append`](#systemappend) | extension → core | Puts a section at the end of the system prompt |
| [`widget.set`, `widget.clear`, `widget.watch`, `widget.unwatch`](#widgetset-widgetclear-widgetwatch-widgetunwatch) | both | Widget content |
| [`extension.config`](#extensionconfig) | core → extension | Its own settings changed |
| [`schedule.fired`](schedules.md#schedulefired) | core → extension | A schedule it created is due |
| [`content.list`, `content.read`, `content.changed`](#contentlist-contentread-contentchanged) | both | Reads content that other packages bring for it |
| [`events.append`](#eventsappend) | extension → core | Records an event of its own in a session |

Other methods are checked against one table: methods for people only (answering an approval for the person, changing the permission level or the workspace, deleting sessions, changing config, installing and removing packages…) return `local_only`; a method that needs a capability returns `needs_approval` when the manifest doesn't declare that capability (see "Capabilities" below); the rest work as usual. Each page's "Who can call" says which kind a method is, and a method missing from the table counts as people only.

## Launch

- **Program**: the core looks for the program in the package folder's `bin/` first, then in the directory next to `miyu`, and never on `PATH`; the arguments are the manifest's `[process] args`.
- **Environment**: the extension inherits the core's environment, and the core also sets `MIYU_HOME` (the data root), `MIYU_RESOURCES` (the resources directory), `MIYU_PROGRAM` (the real path of the main `miyu` program), and this package's own directory in each part of the data root (all already created and given as real paths): `MIYU_APP_DIR` (the package's folder), `MIYU_CONFIG_DIR`, `MIYU_STATE_DIR` (also the working directory), `MIYU_CACHE_DIR`, `MIYU_LOG_DIR`, `MIYU_TMP_DIR` (emptied before each start), `MIYU_RUNTIME_DIR`, and the four folders `MIYU_PICTURES_DIR`, `MIYU_VIDEOS_DIR`, `MIYU_DOCUMENTS_DIR` and `MIYU_DOWNLOADS_DIR` (`root/pictures/`, `root/videos/`, `root/documents/` and `root/downloads/` in the data root). During the transition, the old names `MIYU_PACKAGE_DIR` and `MIYU_PACKAGE_STATE` are also set.
- **Working directory**: the working directory is the package's state directory `var/lib/<id>/`.
- **Stderr**: stderr is appended to `var/log/<id>/stderr`; when the file is over 1 MiB, the core first moves it to `.old`.
- **Handshake**: the extension sends `hello` as usual, without credentials. The `config` in the response holds the final values of its own settings (secrets are given as their real values); an extension with `provider.key` approved gets one more field, `provider_key` (see "`provider_key`" below).
- **Exit**: when the core closes the extension's stdin, that means "please exit"; an extension that hasn't exited after 5 seconds is killed.
- **When the core dies unexpectedly**: if the core crashes or is killed, you and the processes you started end with it. On Unix you run in a process group of your own (you are not its leader), together with a process the core watches; as soon as the core is gone, the whole group is killed. Processes that detach with `setsid` or move to another process group are not covered. On Windows, you and the processes you start are in the core's job object. A planned stop follows the previous item. Because you are not in the core's process group, pressing Ctrl+C in a terminal doesn't reach you.
- **Crashes**: an exit with any code other than 1, being killed, or a failed handshake each count as one failure; the core restarts the extension after waiting 1, 2, 4, 8 and 16 seconds in turn, and stops it after 5 failures in a row (`failed_repeatedly`). **Exit code 1** means a problem that a restart won't fix, such as bad config or a port already in use: the core doesn't restart the extension and stops it at once (`config_error`). Once the extension has run for 60 seconds without stopping, the failure count starts again from zero.

## `feature.offer`

Offers a few features to this person's preset menu, such as `QQ history`, together with the features' tools:

```json
{"features": [{"id": "qq-history", "name": {"zh": "查询 QQ 群聊记录", "en": "QQ history"}, "summary": {"en": "…"}, "tools": ["qq_history"]}]}
```

- It returns `{}`. Each call sends the whole set, which replaces what you last offered for this person; an empty list withdraws them all.
- The features are kept only in the core's memory: offer them again every time you connect or your own switches change, and again after the core restarts. They are not cleared when your process exits.
- `id` is written like a package id and must not clash with the features this person has installed or with features other packages offer; `name` and `summary` are one string or a table from languages to strings (as in the manifest's `[features]`); `tools` must be tools you have `provide`d. If anything is wrong, the call returns `bad_params` (`field` is `features`) and nothing is replaced.
- Offered features appear in this person's preset menu under your package; the tools a feature lists belong to that feature, not to your package's own feature. Whether they are on is decided by the preset: the shipped "Everything" preset turns them on, the other shipped presets turn them off, and people can turn them on in their preset. Open sessions follow the new set from their next turn.
- In group chats and private chats on the platforms you connect to, your whole package bypasses presets (`venues.md`), so the features offered here only matter in local sessions and on other platforms.

The core also has a `feature.set` that people use to change global switches; the names differ, so don't mix them up.

## `port.claim`, `port.release`, `port.list`

An extension that opens a port of its own to listen on (such as the one NapCat connects back to for im) claims the port first: that way a clash shows up at once, instead of waiting for the operating system to report a failed bind. The core only keeps a table and doesn't listen for you; the operating system still decides who actually gets the port.

- **`port.claim {"port": 1–65535}`**: a port nobody has claimed is recorded as yours and returns `{}`; claiming it again on the same connection also returns `{}`; a port another extension has claimed returns `port_taken`, without saying who claimed it. A port of `0` returns `bad_params`.
- **`port.release {"port"}`**: if you claimed the port, it is removed; if you didn't, nothing changes. Both cases return `{}`.
- **Released on exit**: when the process exits or the connection drops, every port it claimed counts as released, so you don't need to release them yourself. After a core restart the table is empty, and the extension claims its ports again when it starts.
- **`port.list {}`**: only the owner can call it (others get `not_permitted`); it returns `{"ports": [{"port", "package"}]}`, sorted by port.

A connection the core didn't launch gets `not_an_extension` when it calls `port.claim` or `port.release`.

## Capabilities

The manifest's `[process] capabilities` declares which capabilities the extension needs. Packages you installed yourself need a person's approval: it can be given while installing (`package.install` and `package.upgrade` with `approve`, see [Packages](packages.md)), and anything not yet approved can be approved when the extension is switched on (`extension.enable` with `approve`); shipped packages count as approved, except for `login.page` and `provider.key` (shipped packages need a person's approval for these too). An extension with capabilities still unapproved isn't launched. Approvals are kept in the switches file `extensions.json` under `approved` (from package id to capabilities), and only what the current manifest declares is kept; if the package is installed another way (a local file over it, another source, another origin repository), earlier approvals are not carried over; they are removed when the package is removed.

| Capability | Allows |
|---|---|
| `tools` | Providing tools to the tool catalog (`provide`) |
| `tools.commands` | Provided tools run commands (`runs_commands` in the `provide` spec): during a call, the commands you start can use `miyu call` to call the AI's tools as that session |
| `commands` | Providing slash commands (the manifest's `[[slash]]`) |
| `widgets` | Showing its own content in the interface (widgets) |
| `context.inject` | Adding a few lines to the context at the start of a turn (`user.append`) |
| `context.system` | Putting a section at the end of the system prompt (`system.append`) |
| `packages.call` | Calling methods that other packages export on the bus (`bus.call`); calling itself by package id (`package.call`) |
| `search` | Being a web provider (the manifest's `[[search]]`, `search.query`) |
| `model.driver` | Providing a model driver (the manifest's `[[driver]]`): when its models are used, the whole conversation sent to the model goes through it. This capability doesn't include network access |
| `provider.key` | Getting the key of one model provider the owner has already set up (the manifest's `[provider_key]`, see "`provider_key`" below): shipped packages need a person's approval for it too |
| `act_for_external` | Speaking for people on a platform (`session.send` and `command.run` with `as`), `session.note`, `session.respond` without `to`, `venue.*`, and recording `venue.*` events: for chat platform bridges only |
| `login.page` | Getting sign-in tickets for pages opened on this machine (`login.ticket {"via": "page"}`, see "Signing in pages on this machine" below): shipped packages need a person's approval for it too |
| `sessions.drive` | Driving sessions: `session.create`, `send`, `interrupt`, `revert`, `unrevert`, `redo`, `compact`, `clear`, `configure`, `fork`, `set_meta`, `retitle`, `respond`, and also `command.run`, `job.stop` |
| `events.read` | Reading sessions: subscribing to the `events`, `view` and `sessions` streams, and calling `session.list`, `session.recap`, `view.page`, `view.detail`, `job.output`; receiving notices after tool calls (the manifest's `[after]`, `tool.after`) |
| `events.write` | Recording your own events in a session (`events.append`) |
| `memory.write` | Writing memories and knowledge bases: `memory.remember`, `import`, `update`, `forget`, `restore`, `dream`, `dream_stop`, and also `kb.add`, `create`, `update`, `mount`, `remove`, `delete`, `reindex` |
| `fs.read` | Reading files through the core (`fs.*`) |
| `network` | Fetching links through the core (`link.preview`) |
| `fs.write` | Writing given paths: once extensions run in a sandbox, access is granted according to this capability |
| `audio.record` | Recording from this computer's microphone: the extension opens the device itself, and the core isn't involved; once extensions run in a sandbox, the recording side of the sound card is opened according to this capability |
| `audio.play` | Playing sound through this computer's speakers or headphones: the extension opens the device itself; once extensions run in a sandbox, the playback side of the sound card is opened according to this capability |
| `tool.guard` | Allowing, denying, or asking the person before a tool call runs (the manifest's `[guard]`, `tool.guard`) |
| `tool.rewrite` | Rewriting a tool's result after it runs: not available yet |

When a capability isn't declared, calling the matching method returns `needs_approval`, with the missing capability in `data.capabilities`. `network` and `fs.*` cover what is done through the core; your program's own network and file access is only checked against them once extensions run in a sandbox.

## Signing in pages on this machine: `login.ticket`

Your package serves a web page (for example a platform bridge's admin page), and you want the owner to open it on this computer without typing the access password (only this machine can skip the password). After you declare `login.page` and a person approves it, call `login.ticket {"via": "page"}` on the extension connection; it returns `{"ticket", "expires"}`: the ticket is valid for 60 seconds and can be used once. The page signs in with this ticket the same way as with a hand-off ticket: with the `ticket` credential in the handshake (for pages that connect to the core directly), or you call `login.redeem {"ticket"}` on the extension connection for it and get a device token (see [Connection](connection.md), "`login.ticket`, `login.redeem`").

- The core only accepts a `via` of `"page"`: without `via`, or with another value, the call returns `local_only`; without `login.page` approved, it returns `needs_approval` with `data.capabilities` set to `["login.page"]`. A shipped package that declares this capability needs a person's approval too; it doesn't count as approved.
- The ticket can only be redeemed on this machine: a remote connection passed on by the web software (a connection that sent `connection.remote` before the handshake, whatever address it named) gets `bad_ticket` when it uses the ticket in the handshake or with `login.redeem`, and the ticket is spent at once. Your own `login.redeem` on the extension connection counts as this machine: because the core can't see who opened your page or from where, only you can keep the rules below.
- For every ticket issued, the core's run log records one line `ticket issued purpose=page by=extension package=<your id>`; the ticket itself is never recorded.

**Your obligations**:

1. Only ask for and redeem a ticket for a request that meets all of the following:
   - It comes from a loopback address: IPv4 `127.0.0.0/8` or IPv6 `::1`; an IPv4 address mapped into IPv6 (`::ffff:127.0.0.1`) counts as IPv4.
   - It carries none of the headers that reverse proxies add (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `Via`, `CF-Connecting-IP`, `True-Client-IP`, `Tailscale-*` and the like): because a request forwarded by a reverse proxy on the same machine also comes from a loopback address, these headers are the only way to recognize it, and a request recognized this way must be treated as coming from elsewhere.
   - Its `Host` is written the local way: `127.0.0.1`, `localhost` or `[::1]`, plus the port you listen on; even when you listen on the LAN, accept only these forms (this protects against DNS rebinding).
   - Its `Origin` is exactly `http://` plus the `Host` (same origin), or the request carries no `Origin`.
2. Pages from elsewhere (from the LAN, or forwarded by a reverse proxy) always sign in with the core's access password (the `password` credential in the handshake, `connect_password` in `miyu-client`). Never hand them this ticket instead, and don't set up a password of your own and redeem tickets for them after checking it.
3. Keep tickets out of your logs; when you hand a ticket to the page, put it in the URL fragment (`#`), and have the page redeem it as soon as it gets it and remove it from the address bar.
4. Recommended, as the web software's `/ticket` does: add one more check by requiring a custom header on the request for a ticket (such as `X-Miyu-Local: 1`) and a request body that isn't one of the three form types; pages on other sites can't send requests with a custom header.

## `provide`

Registers every tool this package provides now, replacing the tools it registered last time. Only extensions the core launched may call it.

**Params** `{"tools": [...]}`. The fields of each tool:

| Name | Notes |
|---|---|
| `name` | Only letters, digits, `_` and `-`, 1 to 64 characters long; must not clash with the core's built-in tools or with another package's tools |
| `description` | The description for the model, written in short English sentences |
| `input_schema` | `{"type": "object", …}` |
| `access` | What the tool touches: `read` (only looks, stays inside Miyu), `write`, `execute`, `network`, `outbound` (sends things out), `venue` (takes actions on a chat platform, such as recalling a message or muting someone), `install` |
| `venues` | Which kinds of session get it: one or more of `local`, `private`, `group` |
| `plugin` | A venue plugin name, written like a package id: in group chats and private chats the tool is only given where that venue has the plugin switched on ([`venue.plugins`](venues.md#venueplugins)); local sessions are unaffected. When unset, the tool is always given |
| `role` | What the tool is for: the core recognizes the tool by its role, not by its name. The only role now is `read_file` (reads a text file: the AI sees the skill list only when the tool set has a tool like this). When unset, the tool has no role |
| `scope` | Which sessions get it, narrowing further within `venues`: `any` (the default when unset), `local` (sessions on this machine), `local_main` (the main session on this machine, not subagents), `local_main_attended` (the main session on this machine, with someone watching), `spawn` (sessions on this machine where subagents haven't yet reached the depth limit) |
| `timeout_ms` | From 1000 to 600000, default 60000 |
| `clicall` | When `true`, the AI can also call the tool with `miyu call` inside a command (only read, network and execute tools can be called this way); when unset, it cannot. A tool with a structured result puts it in the response's `data`, and the script gets one line of JSON |
| `result` | For a tool with a structured result, the shape of that result written on one line, for example `{"memes":[{"id","tags"}]}`: it tells the AI which fields a script can take directly (`miyu call --schema` prints it too). When unset, there is none |
| `display_name` | The name shown to people: `{"zh": "…", "en": "…"}` |
| `subject` | Which argument's value is shown after the name; it must be one of `input_schema.properties` |
| `paths` | Which arguments are paths: `[{"parameter": "file_path", "write": true}]`. The argument must be a top-level one in `input_schema.properties` whose type is a string or an array of strings; when `write` is unset it means a read, and when it is true, `access` must be `write`. The core uses it to judge the paths each call touches (writing outside the workspace asks the person, as with the built-in `edit`), `tool.call` carries `checked`, and the file effects in the response are accepted only for these paths. When unset (`null` is the same as unset), no paths are reported and no file effect is accepted |
| `background_parameters` | Names of arguments that are only given when the session has a background, such as `["run_in_background"]`. Each must be a top-level argument in `input_schema.properties` that isn't in `required`. In sessions with background running turned off, the argument schema the AI sees doesn't have them. `null` is the same as unset |
| `runs_commands` | `true` means this tool runs commands, and the package must then have the capability `tools.commands` approved. The description the AI sees gets the section on how to use `miyu call` appended (as with the built-in `shell`); calls that get a channel carry `channel` in `tool.call` (see **Running commands** below). Unset, `null` or `false` means the tool doesn't run commands |

**Response**: `{"tools": <count>}`. When the connection drops, the tools stay in the catalog, and when called they return "temporarily unavailable".

**Errors**: `not_a_provider` (the caller is not an extension the core launched); `bad_tool`: `data.tool` is the tool at fault, and `data.problem` is one of `duplicate`, `name`, `parameters`, `access`, `venues`, `timeout`, `clicall`, `result`, `display_name`, `subject`, `feature`, `plugin`, `role`, `scope`, `paths`, `background_parameters`, `runs_commands` (set to anything other than a boolean or `null`); `needs_approval`: a tool sets `runs_commands` while its package doesn't have `tools.commands` approved; `data.capabilities` is `["tools.commands"]`, and none of the tools are accepted.

## `tool.call`, `tool.cancel`

**`tool.call`** (core → extension, with an `id`, expects a response):

| Name | Notes |
|---|---|
| `session` | Which session |
| `call_id` | This call's id |
| `tool` | The tool name |
| `args` | The arguments |
| `cwd` | This turn's working directory: a real absolute path with `~` already expanded to the home directory (when the home directory is unknown, it is given as the session recorded it) |
| `pictures` | The picture folder (`root/pictures/` in the data root): put images you draw or generate here, where people can find them in the terminal interface and the web interface. It is a real path, but the folder may not exist yet, so create it (along with any missing parents) before writing. Calls outside a session have no such field, and keep using the workspace there. Only local sessions get it: venue sessions (group chats, private chats) are kept inside their own workspace and don't have it either |
| `by` | Who asked the AI to do this: the `by` of the message that triggered the turn; omitted for turns without a triggering message |
| `owner` | Whether the core recognizes `by` as the owner |
| `permission` | The permission in effect at the moment this call was dispatched, `{"level", "read_only"}`: `level` is `full`, and with `read_only` on the session is read-only. Use it to decide how far you may reach; for example, a fully open session may send any file. Outsiders' sessions are confined separately (`owner` is false), and you apply your own rules for outsiders |
| `persona` | The session's persona id for this turn; omitted when there is no persona. Use it to pick a voice or tone |
| `voice_max_ms` | Only for venue sessions, and only when that platform limits the length of voice messages: how many milliseconds one voice message may last at most (the latest value the bridge reported when it opened or found the session, passed on as is). A synthesized voice longer than this isn't delivered; return an error so that the AI says it again |
| `checked` | Only for tools that declare `paths`: the real locations the permission check approved, in the same order as the paths in the arguments (one per array item). Only write to these locations: after you resolve a path from the arguments to its real location yourself, don't touch it unless it is in this list (a link along the path may have been swapped after the check) |
| `channel` | Only for tools that declare `runs_commands`, and only when this call opened a channel: `{"sock", "token", "bin"}`, see **Running commands** below |

**Response** `{"result": {"blocks": [...], "error"?, "end_turn"?, "sent"?, "detail"?, "data"?, "state"?, "effects"?}}`:

| Name | Notes |
|---|---|
| `blocks` | Content blocks for the model: `{"type": "text", "text"}`, `{"type": "image", "blob", …}`. Upload images with `blob.put` first |
| `error` | Marks the call as failed |
| `end_turn` | Once all of this step's results are in, the model isn't asked again and the turn ends |
| `sent` | What the AI "sends". It isn't shown to the model; heads (interface programs that connect to the core, such as the terminal interface and the web interface) draw it in the reply, and chat platforms send it. At most 4 images: `{"blob", "media_type", "width", "height", "name"?, "alt"?, "sticker"?}`; at most one voice: `{"blob", "media_type", "voice": true, "duration_ms"?, "name"?}`, with a `media_type` starting with `audio/` (`audio/mpeg`, `audio/wav`, `audio/ogg`) and a blob of at most 10 MiB. Too many items or a wrong shape makes the whole result an error, and your raw answer is given to the AI; a voice that is too large isn't delivered, and the AI is told `The audio was not delivered: it is larger than 10 MB.` (this 10 MB is the 10 MiB above). Heads decide whether to play the voice based on who opened the turn (see `voice` in [The view stream](view.md)); in a local session, when a turn nobody spoke in (a due schedule or a loop) produces a voice and no head has the session open, the core plays it through this computer's speakers by calling `tts.play {"audio": <blob>}` on the bus; in venue sessions, the bridge sends it as a voice message |
| `detail` | A structured result for heads, written in one of the three common shapes below; it isn't shown to the model. If the shape is wrong or `error` is true, the core drops this field and handles the rest of the result as usual |
| `data` | A structured result for scripts, in any JSON: when the AI calls this tool with `miyu call` inside a command (`clicall`), it is printed as one line of JSON for the script. It isn't shown to the model and isn't kept in `tool.result`. It isn't passed on when `error` is true |
| `state` | Your package's state in this session, written as described in **`session.set_state`, `session.state`** below: the core keeps the latest one for each session, and the state follows undo and clearing the context. A malformed state is dropped whole and the rest of the result is handled as usual; `null` means not written, and `{}` clears it; it is ignored when `error` is true |
| `effects` | Which files this call read, changed or trashed, and a new to-do list, in order: see **Effects** below. The core checks them before accepting them; once accepted, they are the same as the effects the built-in tools report: the timeline shows the lines added and removed, the diff can be viewed, and the AI doesn't need to read a file again after you changed it |

**Effects** (each item of `effects`, told apart by `kind`):

| `kind` | Other fields | What the core checks |
|---|---|---|
| `file.changed` | `path`; optionally `before`, `after` (content hashes `sha256:…`), `before_text`, `after_text` | `path` must be in `checked` as a write. The before is what the core read before sending `tool.call`, and the after is what the core reads when the response arrives; the effect is dropped when the two are the same, when a hash or text you gave doesn't match, or when the file is over 20 MiB |
| `file.read` | `path`; `lines`: `[from, to]`, counted from 1, with from not above to (otherwise the whole item is dropped) | `path` must be in `checked` (as a read or a write); the core computes the hash from the whole file as it is now |
| `file.trashed` | `path`, `trash` (where it is in the trash, only shown to people, at most 4096 characters) | `path` must be in `checked` as a write and must no longer exist |
| `todo.written` | `todos: [{"content", "status"}]`, `done`? (as in the built-in `todowrite`; `null` is the same as unset) | Only the shape is checked; it is ignored when `error` is true |

- A relative `path` is resolved from this call's `cwd`, and one starting with `~` from the home directory. You only report *which* file: the core reads the contents itself, so what you report can't mislead the people looking at the diff.
- Items of other kinds, malformed items, items whose path wasn't checked, and a second item of the same kind for the same file are dropped one by one; the rest of the result is handled as usual, and the call doesn't fail. The core's run log records a line `tool effect dropped` (`why` is one of `not_checked`, `unchanged`, `mismatch`, `too_big`, `kind`, `shape`).
- File effects are still accepted when `error` is true: when a change fails halfway, the part already changed is real.
- Undo doesn't put files back (as with the built-in tools); it only rolls back what the AI has seen.

**Running commands** (tools that declare `runs_commands`): when the session has tools the AI can call from scripts, the call opens an endpoint just for it, and `tool.call` carries `channel`:

| Name | Notes |
|---|---|
| `sock` | The endpoint: a socket path on Unix, and a named pipe name on Windows (`\\.\pipe\miyu-call-…`). Set it as the environment variable `MIYU_CALL_SOCK` |
| `token` | The token, made of 32 hex characters. Set it as the environment variable `MIYU_CALL_TOKEN` |
| `bin` | A directory holding only `miyu`; put it first on `PATH`, so that the `miyu` a command calls is the same version as the running core. It is left out when the directory couldn't be created |

- Set these three in the commands you start for this call. `miyu call <tool>` in those commands calls the AI's tools under the session's permissions and preset, with the same usage and exit codes as inside the built-in `shell` (1 means the tool failed or was denied, 2 bad usage or the caller isn't recognized as yours, 3 the call is already over, 4 a person's approval is needed).
- The endpoint only accepts descendants of your extension process: the core follows the connecting process's parents up level by level, and must reach your process; your own process, anything detached with `setsid` or a double `fork`, and other processes holding the token can't connect (exit code 2). This guards against mistakes (a token leaked to another process, a command that detached and still tries to call); it isn't meant to stop your extension, which can call by starting a child process. The real gate is the package capability `tools.commands`, which a person must approve.
- Once the call is answered, times out or is cancelled, the endpoint closes, and a `miyu call` that is still waiting or connects later exits with 3. So to call tools from a command, wait for the command to finish before you respond.
- Commands people type in the session (`!`) aren't handed to you; they only go to the built-in `shell`.

The three shapes of `detail` (at most 64 KiB in all, written as JSON):

| `kind` | Other fields | Limit |
|---|---|---|
| `links` | `links: [{"title", "url", "snippet"?, "site"?, "date"?}]`; `url` only accepts `http` and `https` | 50 links |
| `table` | `columns: ["name", …]`, `rows: [[cell, …], …]`; each row has as many cells as there are columns, and a cell is a string, a number, a boolean or `null` | 20 columns, 200 rows |
| `images` | `images: [{"blob", "media_type", "caption"?}]`; `media_type` starts with `image/`; upload images with `blob.put` first | 20 images |

A shape with an extra field or a missing field isn't accepted. Heads that know the shape draw it as a card, and the result is kept in the `detail` of `tool.result` (see [Events](events.md)).

A JSON-RPC error or a malformed answer counts as a failed call. When there is no answer by `timeout_ms`, the call reports "didn't finish within N seconds".

**`tool.cancel`** (core → extension, notification): `{"session", "call_id"}`. The core sends it on a timeout, on an interruption, or when it is shutting down: when you get it, drop that call.

Who may ask a tool for what, and whom a tool may act on, is the providing side's own job: check `by` and `owner`, and when you refuse, say so in the result and set `error` to true.

## `session.set_state`, `session.state`

A package's state in one session: what you draw in widgets, what you leave for the model at compaction, and your own data. This needs the `sessions.drive` capability; you can only read and write your own package's state, in the sessions of the person you act for.

```json
{"widgets": {"todos": {"content": [<widget content>], "title"?: <title>}}, "note": "Todo list:\n- [ ] ...", "data": {...}}
```

| Field | Meaning |
|---|---|
| `widgets` | From widget id to `{"content", "title"?}`: the widget must be one your manifest marks with `state = true` (only `scope = "session"` widgets can be marked this way). The content is written as for `widget.set` and checked against that widget's place. Heads draw from it, even when your program isn't running |
| `note` | English text written verbatim into the checkpoint at compaction for the model (at most 2000 characters, less than half of them CJK, no control characters except newlines). It isn't sent to the model on ordinary turns |
| `data` | Your own data, in any JSON up to 16 KiB as written: the core only stores it, and `session.state` hands it back as is |

- All three fields are optional; `{}` or `null` clears the state. A malformed state is refused whole: bad widget content gives `bad_widget_content` (the `path` starts at `widgets.<id>`), and any other problem gives `bad_params` with `field` naming the field at fault (for example `state.widgets.other`: a widget you didn't declare as a state widget).
- **`session.set_state {"session", "state"}`**: replaces your state with a new one. It is accepted during a turn and between turns, doesn't start a turn, and returns `{}` once the state is on disk. A state written during a turn belongs to that turn: undoing the turn goes back to the earlier state.
- **`session.state {"session"}`**: returns `{"state": {...} | null}`, your package's current state (including `note` and `data`).
- Clearing the context (`/clear`) clears every package's state; ordinary compaction leaves it alone.

## `package.methods`, `method.call`

**`package.methods`** (extension → core): `{"methods": [{"name", "timeout_ms"?}…]}` registers the methods its background page and widgets call, replacing the methods registered last time. The response is `{"methods": <count>}`. Other connections get `not_an_extension`.

**`method.call`** (core → extension): `{"method", "params", "from"?, "language"?}`: a person's head called it through `package.call` or `bus.call`, or another package called it through `bus.call`; `from` is the calling package's id (absent when a person called); `language` is the interface language of the calling connection at that moment (`zh`, `en`, `ja`): a head's own language when a head called, and the language of the calling package's connection when a package called; when the config `ui.language` is `auto`, it follows the `locale` that connection reported in its handshake. Pick the language of text meant for people based on it. Calls the core makes itself (such as playing a voice for a session nobody has open) don't carry it. Whatever you answer is what the caller gets; when you return a JSON-RPC error, the other side gets `method_failed`. An answer is also one line of at most 1 MiB: the core doesn't read a longer one, sends you `line_too_long` (with the `id` of that `method.call`), and the other side gets `method_failed` at once with `data.code` set to `line_too_long`; store large content as a blob (`blob.put`) and put only its hash in the answer.

To let other extensions call your methods, declare a name on the bus under the manifest's `[export]` (`provides` or `plugs`), and list each method in `methods` as `<name>.<method>` (see [The bus](bus.md)). Other extensions can only call you by that name; calling you by package id doesn't reach you (it returns `own_package_only`).

## `package.emit`

Extension → core: `{"event", "data"?}` pushes to the connections that subscribed with `subscribe {"stream": "package", "package": <its id>}`, and they get `package.event {"package", "event", "data"}`. Pages update from it instead of polling. The response is `{}`, also when nobody is subscribed. `event` follows the rules for method names (it starts with a lowercase letter and has only lowercase letters, digits, `_`, `.` and `-`, at most 64 characters), and `data` is at most 256 KiB as JSON; otherwise the call returns `bad_params`. Other connections get `not_an_extension`. This push isn't stored on disk and isn't replayed.

## `search.query`

When a person has picked a source declared in this package's `[[search]]` as the web provider, the core calls this method while the AI searches the web (core → extension, with `id`, needs a response):

`{"source", "query", "want", "allowed_domains", "blocked_domains"}`: in order, the source (`<package>/<id>`), what to search for, at most how many results to return, only results from these domains, and no results from these domains (after getting the results, the core filters them by these two again).

**Response** `{"hits": [{"title", "url", "snippet"?, "date"?}]}`: entries without a title or a URL are dropped, excerpts are shortened, and extra entries are ignored, the same as for the shipped providers. When you are rate limited, answer with a JSON-RPC error whose `data.reason` is `limited`: the core cools you down step by step (starting from 30 minutes) and doesn't ask you while you are cooling down. For other errors, or when there is no answer within 20 seconds, the shipped providers take over for that search. The extension is only asked when it is switched on and has registered its connection (`provide`; the tool list may be empty).

## `command.call`

When a person types a slash command declared in this package's `[[slash]]`, the core calls this method (core → extension):

`{"command", "argument", "text", "session", "by", "owner", "language"}`: in order, the command name, the words after the name, the whole line the person typed, the session, who typed it, whether that is the owner, and the connection's language.

**Response** `{"said": "<reply, may span lines>"}`; the core records a `command.ran` and hands the reply to the person who typed the command as is. When there is no answer within a minute, the answer is an error, or the answer has no `said`, the person gets `command_unavailable` or `command_failed`.

## `user.append`

At the start of a turn, the core asks extensions (core → extension). It only asks extensions that declare `context.inject`, are running, and have a tool in this session's tool set; several extensions are asked in parallel, with **a 300 ms limit**.

`{"session", "venue", "text"?}`: `venue` is one of `local`, `private`, `group`; `text` is what the person said to start the turn (absent for turns not started by a person).

**Response** `{"content": [{"kind", "text"}…]}`, at most 3 blocks: `kind` is made of lowercase letters, digits, `-` and `_`; `text` is 1 to 4000 characters long. What you return is recorded in the session after the message that started the turn, and replayed as is later. Empty, late or malformed answers all count as returning nothing this turn.

## `tool.guard`, `guard.cancel`

Before one of the AI's tool calls runs, the core asks you whether to allow it, deny it, or ask the person (core → extension, with an `id`, expects a response). This suits company policies (no writes under some folders, ask before some commands), auditing and the like.

**Who is asked**: extensions whose manifest declares `tool.guard` in `[process] capabilities` and has a `[guard]` table, that the owner has approved and that are switched on. `[guard]` is a static table, and the core builds its lookup from it at startup:

```toml
[guard]
tools = ["shell", "write", "edit"]   # tool names, optional
access = ["execute", "write"]        # access classes, optional
timeout_ms = 1000                    # how long to wait for you, optional
```

- The core asks you about a call only when its tool name is in `tools` or its access class is in `access`. A manifest that sets neither can't be loaded (`bad_guard`, reported by `miyu check`): "ask about everything" isn't allowed. The access classes are `read`, `write`, `execute`, `network`, `outbound`, `venue`, `install`.
- Built-in tools, other packages' tools and MCP servers' tools are all matched by name and access class; you aren't asked about tools you `provide` yourself. You can be a guard without using `provide` at all.
- `timeout_ms` is 1000 when unset, and can only be 100 to 5000.
- The permission policy decides first: calls it denies never reach you; calls it allows or would ask the person about are then sent to you. Several guards are asked in parallel, and the strictest answer wins: one deny means deny; with no deny, one ask means asking the person; when the policy asks the person, your allow still asks the person. You can only tighten, never loosen, and you don't change the sandbox.
- Tools called from scripts (`miyu call`) are asked about too; `call_id` is the nested call's id (for example `call_12_1#3`).

**Params**: `{"session", "call_id", "tool", "args", "access", "cwd", "owner", "venue"}`: in order, the session, this call's id, the tool name, the repaired arguments (exactly what will run), the access class, the turn's working directory (a real path, the same as `cwd` in `tool.call`), whether the person speaking is the owner (the same as `owner` in `tool.call`), and where it was said (`local`, `private`, `group`).

**Response** `{"verdict": "allow" | "deny" | "ask", "reason"?}`:

- `allow`: go ahead. This answer doesn't enter the context; the AI only sees the tool's result.
- `deny`: deny, and the tool doesn't run. The AI sees the result `Blocked by <your package id>: <reason>`: `reason` has the surrounding whitespace removed, is cut to 300 characters, and has newlines, quotes and angle brackets escaped into forms like `\n` and `\u0022`, so the whole sentence takes one line; without a `reason`, it says `no reason given`. The result on the timeline has `by` set to your package, and people see your original words.
- `ask`: ask the person through the usual approval flow (`tool.approval_requested`, with `by` set to your package and `detail` set to `{"guard", "tool", "reason"?}`); the person can only allow this one call or deny it. Sessions where no one can approve treat it as a deny.
- Extra fields, a `verdict` that isn't recognized, or a `reason` that isn't a string all count as a deny, with the reason `the guard answered in a wrong format`.

**No answer counts as a deny** (a failing guard fails toward the strict side):

| When | Reason the AI sees |
|---|---|
| No answer before `timeout_ms` has passed | `the guard did not answer in time` |
| You are switched on but not running (starting, just crashed, or unable to start), or the connection dropped while you were being asked | `the guard is not running` |
| You returned a JSON-RPC error | `the guard returned an error` |

Extensions the owner switched off are not asked. Aim for a p95 under 20 ms, because the person is waiting on this step the whole time.

**`guard.cancel`** (core → extension, notification): `{"session", "call_id"}`. The person interrupted, the turn was cancelled, or you timed out, so the core no longer waits: the call ends as interrupted (or was already denied for the timeout), and your answer is ignored even if it arrives.

## `tool.after`

After one of the AI's tool calls has a result and it has been written to the session log, the core tells you (core → extension, notification: no `id`, no response needed). This suits audits (recording every call in an outside log), call statistics and the like. It is read-only: what you get is the copy written to disk, you can't change the result, and nothing of it reaches the AI's context.

**Who is told**: extensions whose manifest declares `events.read` in `[process] capabilities` and has an `[after]` table, that the owner has approved, that are switched on, and that are running (have finished the handshake). No new capability is added: an extension that can read a session's event stream sees this anyway, and this only saves you from subscribing to the whole event stream to watch tool calls. `[after]` is written the same way as `[guard]`, except that it has no timeout:

```toml
[after]
tools = ["shell", "write"]   # tool names, optional
access = ["network"]         # access classes, optional; at least one of the two
```

- The core tells you about a call only when its tool name is in `tools` or its access class is in `access`. A manifest that sets neither, names an access class that isn't recognized, has a malformed tool name, or doesn't declare `events.read` can't be loaded (`bad_after`, reported by `miyu check`). A tool missing from the catalog (the AI got its name wrong) has no access class, and only matches `tools`.
- You are also told about tools you `provide` yourself. Calls that were denied (by the permission policy, a guard or the kernel), skipped, cancelled or failed are all sent, with `status` set to what really happened.
- **Sessions follow the rules for subscribing to the event stream**: you aren't told about sessions you can't reach. An extension that isn't a platform bridge only hears about local sessions and the owner's own private chats that aren't confined; a platform bridge only hears about venue sessions on its own platforms (the manifest's `[connection] platform`).
- Tools called from scripts (`miyu call`) are sent too, but in a different shape; see below.

**Params**:

| Field | Direct call (`tool.result`) | Called from a script (`tool.nested`) |
|---|---|---|
| `session` | The session id | Same |
| `call_id` | The call id (`call_12_1`) | The nested call's id (`call_12_1#3`) |
| `tool` | The tool name | Same |
| `access` | The access class; left out when the tool isn't in the catalog | Same |
| `status` | The same as in `tool.result`: `ok`, `error`, `denied`, `cancelled`, `skipped`… | The same as in `tool.nested`: `ok`, `error`, `denied`, `needs_approval`, `cancelled` |
| `duration_ms` | How many milliseconds it took to run; left out when it never really ran | Same |
| `by` | The event's `by`, the same as in the event stream: the call itself when it ran normally, and whoever denied it when it was denied (`{"kind": "module", "id": "<package>"}`) | Same |
| `args` | The arguments as the model wrote them (a JSON string, the same as the `args` of the `tool_call` block in the event stream) | The repaired arguments as written (the same as the `args` of `tool.nested`) |
| `blocks` | The same as the `blocks` of `tool.result`: what the AI sees, with large blocks given only as references | Left out |
| `result`, `bytes` | Left out | The hash and the size in bytes of the blob holding the result handed to the script (the same as in `tool.nested`), left out when nothing was stored; read the contents with `blob.get` |

`args` is a string, not an object (the `args` of `tool.guard` is a parsed object): you get it exactly as the event stream records it. To tell the two shapes apart, check whether `blocks` is there, or whether `call_id` contains a `#`.

**No waiting, no blocking**:

- The core sends the notice and moves on, and the turn doesn't wait for you; being slow or crashing doesn't hold up the session.
- Each extension has one queue of **at most 256**; when it is full, new notices are dropped and a `WARN` line is logged (for a run of drops only the first one is logged, with the running total of notices dropped for you; another line is logged once there is room again).
- When the connection drops or you crash, the whole queue is thrown away and nothing is resent; after a restart, notices start again from new calls. An extension that is switched on but hasn't finished the handshake isn't sent anything.
- **`tool.after` doesn't guarantee delivery**: for a complete audit, subscribe to the event stream (`events` in `subscribe`, which needs `events.read`); the event stream replays from the log.

## `driver.call`, `driver.delta`, `driver.cancel`

The model driver you provide takes one whole model call (core → extension, with an `id`, expects a response): Miyu hands you the unified request, and you encode it in the wire format, sign in, send it, parse the response, classify errors, and stream it back as deltas. Retries, cooldowns, failing over within a pool, and pricing all stay in Miyu.

**Who is called**: extensions whose manifest declares `model.driver` in `[process] capabilities` and has a `[[driver]]` table, that the owner has approved and that are switched on. A driver is only used by providers whose config the owner has written with `driver = "<your package id>/<driver name>"` (see `[[driver]]` in the [manifest](../dev/manifest.md)).

**Params** `{"call", "driver", "request", "fingerprint", "params", "key"?, "base_url"?, "blobs"?}`:

| Field | Meaning |
|---|---|
| `call` | This call's id; `driver.delta` and `driver.cancel` use it to refer to this call |
| `driver` | `<package id>/<driver name>`; if you declared several drivers, use it to tell them apart |
| `request` | The unified request, given as is: `tools`, `system`, `messages`, `stable`, and, only when they have content, `continuation`, `described` (descriptions of the images, for when images can't be seen), `output_cap`, `tail`. The same state gives exactly the same request; other drivers' private data has been removed. A `hosted_tool` block (a tool the model ran on the provider's side, such as a search) that carries your driver's private data is handed to you as is, and you decide whether to send it back to the provider; a block from another driver, or one with no private data, is replaced by a `text` block holding the text Miyu writes for the model (`<hosted-tool name="…">` wrapping the arguments and the result, both kept as they are except that every `</` becomes `<\/`; no trailing newline). Only the private data on a block tells whether it is "yours" |
| `fingerprint` | `{"tools", "system", "messages": [...]}`: one hash (a string of 16 hex digits) each for the tool surface, the system prompt and every message; the same content gives the same hash, so you can use it for your own cache |
| `params` | `{"model", "max_output"?, "effort"?, "temperature"?}` |
| `key` | The key this provider's config refers to; it isn't handed to you when you declared `key = "none"` or the provider has no key written |
| `base_url` | The address this provider wrote; it isn't handed to you when the provider wrote none |
| `blobs` | Only for drivers that declare `images = true` or `files = true`: with `images`, the request's images, and with `files`, the request's files (`file` blocks such as PDFs, audio and video), as `{"<blob hash>": {"media_type", "data"}}`, with `data` in base64. Without `images`, the request uses the descriptions in `described` for its images; without `files`, a file is only the name and type on its block |

**Deltas** `driver.delta` (extension → core, notification): `{"call", "deltas": [...]}`; one notification can carry several deltas, in order:

| Entry | Meaning |
|---|---|
| `{"start": {"index", "kind"}}` | Block `index` starts; `kind` is `"text"`, `"reasoning"`, `{"tool_call": {"name"}}` or `{"hosted_tool": {"name"}}` (a tool the provider ran on its own side, with `name` being the provider's own tool name as is; Miyu doesn't run it). Blocks are numbered from 0 and start one after another |
| `{"text": {"index", "text"}}` | A piece of that block's text: the reply, reasoning, or a piece of the raw arguments of a tool call or a provider-run tool |
| `{"private": {"index", "data"}}` | Private data for a reasoning, tool call or provider-run tool block (a signature, the provider's own call id or step id), in any JSON, at most one per block. Later requests hand it back to you as is, and never to another driver |
| `{"outcome": {"index", "text", "failed"?}}` | A provider-run tool's result: text that both the model and a person can read (titles, URLs, excerpts, the text of the page read), cut by the core at 64 KiB; `failed` is `true` when the provider says the run failed, and counts as `false` when left out. Only for a provider-run tool block, at most once per block, and before the block is complete; leave it out when the run was interrupted and has no result |
| `{"end": {"index"}}` | That block is complete |
| `"truncated"` | The output limit was reached before the reply was finished |

A block can only have text after it starts, and nothing can be written to it after it is complete. A wrong delta ends the call as `unclassified` (`the driver sent a bad delta: …`), and deltas arriving after it are dropped. Deltas for a `call` that isn't recognized are dropped without an error.

List the names of provider-run tools in this driver's `hosted` in the manifest ([manifest](../dev/manifest.md#driver)), so that the owner knows from it at install time what the provider will run on its own. A name that isn't listed is still accepted and shown as usual, and the core logs a warning in its run log (once per driver and name each time the core runs; at most 64 names are listed per driver, and for names beyond that, or names longer than 64 bytes, only one more line is logged saying there are more, without the names). Tools that change things (running commands, writing files) are best turned off in favor of the core's tools; if you can't turn one off and want to let it run, ask the owner first with [`driver.approve`](#driverapprove).

**Response** `{"usage"?, "error"?, "sent"?}`, sent after all of this call's `driver.delta`:

- `usage`: `{"uncached", "cache_read", "cache_write", "output", "reasoning"?, "context"?}`. Items you don't report are recorded as not reported, and nothing is estimated. `context` is how many tokens the context holds when this call ends (the input plus this call's output). If your driver makes several requests within one call (drivers that borrow an agent program often do), report the first four items as the sum of those requests, which is what Miyu bills; report `context` as the size of the last request, which is what Miyu uses to judge whether the context is full and when to compact. A driver that makes one request per call doesn't need to report it.
- `error`: `{"class", "message", "retry_after_ms"?}`. `class` is one of `retryable`, `stalled` (stuck: nothing new for a long time; the kernel stops retrying after two in a row), `rate_limited`, `context_too_long`, `auth`, `quota`, `content_policy`, `unclassified`, and a value that isn't recognized counts as `unclassified`. `retry_after_ms` only takes effect for `rate_limited`. `message` is cut to 500 characters and only shown to people. Once you have sent part of the deltas, don't retry the call yourself (the reply would repeat); Miyu retries, cools down and fails over within the pool according to the class.
- `sent`: the SHA-256 of the bytes you actually sent this time, written as `sha256:<64 hex digits>`, and recorded in `model.called`. If the same request is sent again (a retry) and the `sent` you report differs, your encoding looked at something besides the params, and the cached prefix can't hit; Miyu logs a `WARN` line (once per driver per run).

A response with extra fields or in a wrong format counts as `unclassified` (`the driver sent a bad answer: …`); so does a JSON-RPC error (`the driver refused the call: …`).

**Time limits**: the same as for built-in drivers: from sending to the first delta, between two deltas, and from the last delta to the response, none may exceed the idle limit (180 seconds, scaled up by reasoning effort; when the manifest's `[[driver]]` sets a longer `quiet_secs`, that value is used), and the whole call may not exceed ten times the idle limit. A call past the limit counts as `retryable` (`the driver went quiet`). Time spent waiting for the owner to answer a `driver.approve` doesn't count toward either limit. When the extension crashes or the connection drops, a waiting call counts as `retryable` (`the driver went away`). While you are backing off and waiting to be launched again, a call counts as `retryable`, with the wait taken from `retry_in`; an extension that is switched off, not approved or stopped isn't called, so the provider counts as unusable, and a pool moves on to its next member.

**`driver.cancel`** (core → extension, notification): `{"call"}`. The person interrupted, the turn was cancelled, the call timed out, or a delta was wrong, so the core no longer waits: don't send any more requests for this call; later deltas and the response are ignored.

## `driver.approve`

In the middle of a `driver.call`, asks the core to show Miyu's own confirmation to the owner (extension → core, with an `id`, expects a response). It is for when the program behind your driver (for example an agent connected over ACP) wants to run a command or change files outside Miyu's sandbox and needs the owner's go-ahead. The confirmation is the same kind as a tool call's: heads show it as usual, the owner answers it as usual with [`session.answer`](sessions.md#sessionanswer), and the only choices are "allow once" and "deny".

**Who can call it**: needs `model.driver`; only during the `driver.call` in progress on this connection, with that call's `call`.

**Params** `{"call", "index", "access", "title", "command"?, "text"?, "options"}`:

| Field | Meaning |
|---|---|
| `call` | The id of the `driver.call` in progress |
| `index` | Which block the confirmation is shown on: the number of a provider-side tool block (`hosted_tool`) this call has already started. Start the block with `driver.delta` first, then call this method |
| `access` | What kind of thing is about to happen: `read`, `write`, `execute` or `network` |
| `title` | The title people see, at most 200 characters; the rest is cut |
| `command` | The command to run, verbatim (at most 4000 characters). With it, the confirmation is shown like running a command: the title on top, the command below |
| `text` | Without a command, the description verbatim, such as the paths of the files to change (at most 4000 characters). The confirmation is shown like an extension asking |
| `options` | The options on your side, 1 to 16 of them, each `{"id", "name"?, "kind"}`, where `kind` is one of `allow_once`, `allow_always`, `reject_once` and `reject_always` (the same as ACP's option kinds) |

**Response**:

| Field | Meaning |
|---|---|
| `decision` | `once` (the owner allowed it once), `deny` (denied), or `cancelled` (this call is gone: it was answered, interrupted, timed out, or the session stopped) |
| `option` | The `id` of your option picked by `decision`: `allow_once` when allowed, or `allow_always` if there is none; `reject_once` when denied, or `reject_always` if there is none; absent when nothing matches. Miyu doesn't remember "always allow" for your side |
| `reason` | The reason the owner wrote when denying, only when they wrote one |
| `auto` | Why Miyu denied without asking the owner: `unattended` (no one in the session can confirm: venue sessions such as group chats and private chats, or a session not opened by a head that takes input), `read_only` (the session is read-only and the request is `write` or `execute`), `expired` (no one answered by the confirmation deadline, see `session.answer`), or `aside` (asked during a helper request such as compaction or titling) |

```json
→ {"jsonrpc":"2.0","id":"p1","method":"driver.approve","params":{"call":"d12","index":0,"access":"execute","title":"List files","command":"ls -la","options":[{"id":"allow","kind":"allow_once"},{"id":"reject","kind":"reject_once"}]}}
← {"jsonrpc":"2.0","id":"p1","result":{"decision":"once","option":"allow"}}
```

**Errors**

| `data.reason` | When |
|---|---|
| `unknown_call` | `call` isn't a call in progress on this connection: it was answered already, the core stopped waiting, or it belongs to another connection |
| `bad_params` (`-32602`) | The params are malformed, or `index` isn't a provider-side tool block this call has started; `data.why` says why, in English |

- Before answering, the session records a `tool.approval_requested` (`by` is your package, `driver` says which block it is shown on, and `call_id` is a number the core assigns that matches no tool call; see [events](events.md)); an answer from the owner, no one answering in time, and the call going away each record a `tool.approval_decided`.
- While waiting for the owner, this call's time limits stop; they go on once it is answered.
- Older cores don't have this method and answer "method not found" (`-32601`): treat that as a denial.

## `driver.encode`

Encodes once without sending (core → extension, with an `id`, expects a response): the params are the same as for `driver.call`, and the response is `{"body"}`, where `body` is the bytes you would send for those params (as a string). `driver.check` (which authors run with `miyu dev driver-check`) uses it to check whether your encoding is steady: the same params must give the same bytes, also after a restart, and adding one message only at the end must not change any byte before the end of the stable region.

- Encode from the params only: put in no time and no random numbers, and keep the fields in a fixed order. `call` is this call's id; don't encode it.
- A driver that declares `cache = "contract"` must implement this method; without it, `driver.check` counts the driver as failed. Other drivers without it are reported as skipped. If you don't implement this method, answer with the JSON-RPC "method not found" error (`-32601`).
- The owner's key isn't handed to you (neither `key` nor `base_url` is given), and neither are images.

## `driver.models`

Lists the models this driver can use (core → extension, with an `id`, expects a response). This method is optional: the core calls it when the owner fetches the model list (`model.list` with `refresh`, opening the settings page, or after a model request returns 404). If you don't implement it, answer with the JSON-RPC "method not found" error (`-32601`), and the owner then writes model names by hand.

**Params** `{"driver", "key"?, "base_url"?}`: `key` and `base_url` are the same as for `driver.call` (handed to you according to your `key` declaration, and left out when not written).

**Response** `{"models": [...]}`, one entry per model:

| Field | Meaning |
|---|---|
| `id` | The model name; the owner writes it in the config as `<provider>/<id>` |
| `window` | The context window, in tokens |
| `max_output` | The maximum output, in tokens |
| `tools` | Whether it can call tools |
| `vision` | Whether it can see images: `true` counts as "inputs are text and images" |
| `reasoning` | The core recognizes this field but doesn't use it yet |

Each field is looked up in the order "written by the owner > listed by you > catalog", so what the owner writes by hand wins over what you list. The whole call waits at most 30 seconds; extra fields or a wrong format reject the whole list, and the previous list stays in use.

## `system.append`

Puts a section at the end of the system prompt (extension → core). It requires declaring `context.system`.

**Params**: `content` (1 to 4000 characters; `null` removes it), `session` (applies only to this session; applies to all sessions when omitted). **Response**: `{}`.

The section only goes into sessions whose tool set includes this package's tools; after a change, the new content takes effect from the next turn. It is kept only in the core's memory, so set it again after the core restarts.

**Errors**: `not_a_provider`; `needs_approval` (`data.capabilities` is `["context.system"]`); `bad_params`.

## `widget.set`, `widget.clear`, `widget.watch`, `widget.unwatch`

A widget is a block of content declared in the manifest's `[[widget]]` and shown on a head, in one of these places: the home screen (`home`), the sidebar (`sidebar`, which can follow the session), the status bar (`status`), or a full page (`page`, opened by a slash command). It requires declaring `widgets`.

**Extension → core**

| Method | Params | Response |
|---|---|---|
| `widget.set` | `widget`, `session` (required for widgets that follow the session), `title` (replaces the manifest's title), `content` | `{"kept": true}`; for a widget that follows the session, `{"kept": false}` when nobody is watching it in that session |
| `widget.clear` | `widget`, `session` | `{}` |

**Core → extension** (notifications): `widget.watch {"widget", "session"?}` means someone started looking at this widget, so fetch your data and push content; `widget.unwatch` means the last viewer has left. After the handshake, the core sends a `widget.watch` for each widget being watched at that moment.

**Content** is an array, with one section per item:

| Section | Fields |
|---|---|
| `heading` | `text` |
| `text` | `text` (may span lines, at most 2000 characters), `tone` |
| `pairs` | `items`: `{"label", "value", "tone"?}`, at most 50 pairs |
| `progress` | `value` (0 to 1), `text`, `mark` (0 to 1, a point marked on the bar) |
| `list` | `items`: `{"title", "detail"?, "right"?, "state"?, "action"?}`, at most 200 items |
| `buttons` | `items`: `{"label", "action"}`, at most 8 buttons |
| `sections` | Full pages only: `items`: `{"id", "title", "subtitle"?, "badge"?, "state"?, "blocks"}`, `add`: `{"label", "call", "options"?}` |
| `form` | Full pages only: `id`, `fields` (`{"key", "label", "hint"?, "control", "value", …}`), `submit` (`{"label", "call", "params"?}`) |

- Text is a string, or a table from languages to strings (`{"zh": "…", "en": "…"}`) that the core picks from by the connection's language. Markdown and HTML aren't supported.
- The values of `tone` are `normal`, `dim`, `accent`, `good`, `warn`, `bad`. A list item's `state`: `todo`, `doing`, `done`, `failed`, `off`; a section's `state`: `good`, `warn`, `bad`, `off`.
- `action`: `{"call": <method>, "params"?}` calls a method it registered; `{"open": <widget>}` opens one of its full pages; `{"copy": <text>}` copies the text to the clipboard.
- The form controls are `toggle`, `select` (with `options: [{"value", "label"}]`), `text`, `textarea`, `list` and `number` (`min`, `max`, `integer`); a `value` of `null` means the default is used; `default` is `{"text", "value"?}`: the line shown to people, and what the default actually is (heads draw a field whose value is `null` from it). On save, the head calls `submit.call` with `submit.params` plus `{"values": {only the changed fields}}`; the extension answers `{"saved": true}`, or `{"saved": false, "problems": [{"key", "message"}]}`, or `{"saved": false, "message"}`. The `add` call gets the params `{"value": <the option picked>}`, and the extension may answer `{"id": <the new item>}`.
- A widget has at most 64 sections and 64 KiB; `status` can only be a single `text` section of one line, at most 40 columns wide; `home` has at most 8 sections. A widget is pushed to heads at most every 250 ms, and only the newest content in that interval is kept.

**Errors**: `unknown_widget` (`data.widget`); `bad_widget_content`: `data.path` says where the error is (e.g. `content[4].items[2].title`), and `data.problem` is one of `type`, `missing`, `too_long`, `too_many`, `too_big`, `control_char`, `tone`, `state`, `value`, `action`, `place`, `unknown`, `duplicate`; `bad_params` (`session` is missing for a widget that follows the session, or given for a global one).

## `extension.config`

When its own settings (those starting with "package id plus dot") change, the core tells the extension (core → extension, notification): `{"keys": {<key>: <new value> or null}}`, with only the keys that changed; secrets are given as their real values; a key that is no longer set or can't be read is `null`. This notification needs no subscription. For an extension with `provider.key` approved, changes to the `provider_key` field are pushed the same way.

### `provider_key`

An extension whose manifest has `[provider_key] catalog = "<catalog id>"`, that declares `provider.key` and that a person has approved, gets one more field in the handshake's `config` and in `extension.config`'s `keys`: `"provider_key": "<the real key>"` (a string). The field only exists on extension connections the core launched, never on head connections.

- **Which provider**: it is worked out from the owner's provider settings `providers.<id>` (`miyu_models::provider_key`): a provider with `catalog` written is matched by it; without it, a provider whose literal address contains that provider's official address counts (only DeepSeek's `api.deepseek.com` for now; an address that is an environment-variable reference doesn't count); with neither, a provider whose id is that catalog id counts. If several providers count, the first one by id is used; a provider without a key doesn't count.
- **Not handed over**: the field is absent when `provider.key` isn't approved (shipped packages need a person's approval too), when the owner hasn't set up that provider, or when its key can't be read. No other provider's key is ever handed over.
- **Changes**: a changed key (`secret.set`, an edited reference) is pushed as the new value; removing the provider or its key pushes `null`.
- The value never goes into the run log or into events. `config.get` still only returns the reference `{"secret": "<name>"}`.

## `content.list`, `content.read`, `content.changed`

Another package can write `[content.<its id>] dir = "…"` in its manifest to bring a folder of content for it (that is how sticker content packs work).

| Method | Params | Response |
|---|---|---|
| `content.list` | none | `{"packages": [{"package", "version"?}…]}`: the packages that bring it content, sorted by id |
| `content.read` | `package`, `path`, `offset` | `{"data", "size", "eof"}`, at most 512 KiB at a time |
| `content.changed` (core → extension, notification) | `{}` | A package that brings it content was installed, removed or upgraded: list again |

**Errors**: `not_a_provider`; `unknown_package` (there is no such package, or it brings no content for it); `bad_params`; `not_found`.

## `events.append`

Records an event without a turn number in a session: it doesn't start a turn, doesn't interrupt one, and isn't shown to the model.

**Params**: `session`, `kind`, `body` (a JSON object, at most 16 KiB). Extensions can only record events of the form `ext.<own prefix>.<name>` (the prefix is the manifest's `prefix`, or the package id when that is unset; each segment starts with a lowercase letter and has only lowercase letters, digits, `_` and `-`, with at most 128 characters in all). Chat platform bridges can also record `venue.recalled` and `venue.delivered` (see [Venues](venues.md)).

**Response**: `{"seq": <number>}`.

**Errors**: `bad_params`; `session_not_found`.
