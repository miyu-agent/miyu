# Miyu core protocol reference

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This reference is for programs that connect to the core: "heads" (interface programs that connect to the core, such as the terminal interface and the web interface), and the extensions the core launches. It covers how to call each method that exists today, what it returns, and how it can fail. It does not cover why things were designed this way or in which step they were built (that is in `internal/blueprint/`). This reference is licensed under Apache-2.0 (see `LICENSES/Apache-2.0.txt` at the repository root), so you can write your own clients and extensions from it under any license.

## Conventions

- **One message per line**: the core and its peer exchange JSON-RPC 2.0 messages over one connection. Each message takes one line (UTF-8, ending in `\n`), and a line is at most 1 MiB.
- **Hello first**: the first message after connecting must be `hello`; before the handshake, every other method returns `hello_first`.
- **Fields**: params are an object. Writing `null` has the same effect as leaving the field out. Fields the core doesn't recognize are ignored.
- **Errors**: the errors JSON-RPC defines itself use its standard codes; Miyu's own errors all use `-32010`, with the reason in `error.data.reason`, and some errors carry a few more fields (listed under each method's "Errors"). `error.message` is a sentence for people, written in the language reported in the handshake; don't use it to tell which error happened.
- **Who can call**: each method says whether people (head connections) and extensions (connections of packages the core launched) can call it, and how the two differ when they do.
- **Protocol 1 is frozen**: its methods are listed in [methods-v1.txt](../../../internal/blueprint/methods-v1.txt), plus `hello` for the handshake, and `subscribe`, `unsubscribe` and `provide`. From now on protocol 1 is only added to, never changed or trimmed: existing methods are not removed, renamed or given a new meaning, and replies only gain fields. New methods and fields say which core version they first appear in. An older core answers `unknown_method` to a new method and ignores fields it doesn't recognize, so before using new methods and fields, check the core version in the handshake reply, or fall back to the old way when you get `unknown_method`. Removing, renaming or changing the meaning of a method can only happen in protocol 2: during the handshake the core negotiates from the `[lowest, highest]` version range you send, and returns `protocol_mismatch` when no version fits.
