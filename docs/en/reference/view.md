# View stream: ready-to-draw entries and session status

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

The core turns a session log into entries that a UI can draw directly (the view projection), so heads (interface programs that connect to the core, such as the terminal interface and the web interface) draw from these entries and don't have to work them out from events. There are two ways to get them: page through them with `view.page {view: true}`, or subscribe to the view stream with `subscribe {stream: "view"}`.

## Subscribing

The response to `subscribe {"session", "stream": "view"}` carries the latest page of entries (the same as `view.page {view: true}`: `entries`, `more`, `first`, `last`, `capped`), the full session `status`, and the fields of an events subscription response. After that, the core pushes these messages:

| Push | Meaning |
|---|---|
| `view.add {session, entry, after}` | A new entry, placed after the entry `after` names (`null` means it goes first) |
| `view.update {session, entry}` | An entry changed to this (its state changed); it carries `after` when the entry's position changed too |
| `view.append {session, id, text}` | Text appended to a reply or thought that is being written, or to the `args` of a tool whose arguments are being written |
| `view.hidden {session, ids, hidden}` | On an undo or a restore: these entries are hidden or shown again |
| `view.remove {session, id}` | An entry goes away (half-written parts dropped on an interrupt, or a compaction still unfinished when the turn ended) |
| `view.status {session, status}` | The session status changed: the whole status is pushed |
| `resync {session, stream: "view"}` | The connection fell behind: subscribe again |

The view stream doesn't push raw events. Text in the entries comes written in the connection's language; if the connection's language changes, later entries follow the new one.

## Entries

Each entry is one object, with the common fields `id`, `kind`, `turn` (which turn it belongs to), `hidden` (whether an undo hid it) and `at` (when it began).

**Ids** follow positions in the log, so paging and subscribing give the same ids: `m<number>` is a message, `b<seen>.<block>` a block of a reply, `g…` a stretch of the timeline, `c<number>` a compaction, `e<number>` a turn's end and asides, `s<number>.<n>` an image the AI sent, and `x<number>.<n>` an aside that exists only in the stream.

| `kind` | Fields |
|---|---|
| `user` | `text`; `attachments` (`kind`, `name`, `media_type`, `blob`, plus `width` and `height` for images, and `path` when one was given; a path-only attachment has `kind` `file`, no `media_type` or `blob`, and has `name`, `path` and `path_only: true`, plus `size` when the head gave one); `from` (where a message from elsewhere came from, written like an event's `by`; a message from someone at a venue also has `name`: that message's `venue.name` (group card or nickname), which is a display name only and untrusted, so heads escape it as usual, for example drawing it as "nickname (qq:number)"; absent when no name was given); `poke: true` (someone at the venue poked the AI, the same as that message's `venue.poke`; absent otherwise); `poke_text` (the poke's suffix, the same as that message's `venue.poke_text`, such as "的小脑袋": untrusted, so heads escape it as usual; absent when not given); `level`; `queued: true` (the message is queued and the AI hasn't heard it yet); `withdrawn: true` (a queued message was handed back: the head puts the text back in the input box); `command` (only on a message sent by a slash command the person typed; its value is the command's name, such as `loop`, `goal` or a command template's name: `text` is then the line the person typed, not what the AI gets; `from` copies the event's `by`, so words a loop delivered carry `loop`, `person` and `builtin` there); `round` (which round of a standing goal this is); `shell` (a command the person typed with `!`, with `text` being the command line: it is `{"running": true}` until the command finishes, and then `exit` or `signal`, `text` (the output), `omitted` and `duration_ms`, plus `reason` if it ended abnormally: `timed_out`, `interrupted`, `aborted`); `media` (images, stickers, videos, voice clips and files a venue message carried that were not downloaded, in the order of that message's `venue.media`, each `{kind, name?, size?}`: `kind` is `image`, `sticker`, `video`, `voice` or `file`; `name` is the file name or the sticker's text, untrusted, so heads escape it as usual; `size` is the byte count the platform gave. An original image already handed in as an image block is in `attachments` and is not repeated here; absent when nothing was carried. Heads can draw "[Image]", "[Sticker]", "[Video]" from it); `trigger: true` (this message called the AI, starting this turn or joining the turn in progress: the `trigger` of `turn.started`, or the last one of a `turn.joined` batch. When a turn starts from several recorded messages, the other overheard messages taken into it only have `turn`, not this field; heads can draw just the message that called the AI as a bubble and fold the rest) |
| `reply` | `text` (the Markdown source; parsing and rendering are the head's job); `open: true` (still being written); `persona`: the persona that replied in this turn (its id, `null` for none). After a mid-session persona change, earlier replies keep the old persona: the change a person makes is recorded first, and only replies after it actually takes effect (at the start of the next turn) have the new one |
| `media` | An image the AI sent: `image`, `alt`, `sticker` |
| `voice` | A voice the AI spoke (an item with `voice` in the `sent` a tool returned, numbered like images, `s<seq>.<item>`): `blob`, `media_type`, `name`, `duration_ms`, and who opened the turn: `by` (the `by` of the message that opened the turn, written as in events; words said on a local head carry `head`, and a wake-up from a schedule is `schedule`; absent when no such message opened the turn) and `cause` (the id of the request that opened the turn, the same as the `cause` of `turn.started`). Heads draw a player; when `cause` is the id of the head's own `session.send`, the words were said on that head, so it plays the voice at once; when `by` is `schedule` or absent, nobody spoke, so every head with the session open plays it; when another head's words opened the turn, the head just draws the player without playing |
| `group` | A stretch of the timeline (thought and tool steps): `steps`, `open`, `summary`, `summary_en` (the line shown when collapsed), `took_ms`, `failed` |
| `thought` | A thought step: `group`, `text`, `open`, `took_ms` |
| `tool` | A tool step: `group`, `call`, `name`, `hosted` (`true` for a tool the model ran on the provider's side, see "Provider-side tools" below; absent for tools the core runs), `title`, `state`, `args`, `diff` (`{added, removed}`), `images`, `job`, `approval` (a request that needs a person to confirm: `access`, `rule`, `detail`, plus `decision`, `reason` and `by` once decided; with `expires_at`, it is denied automatically if no one confirms by then, heads draw a countdown from it, and the denial's `by` is then `kernel`), `took_ms`, `files` (`[{path, action}]`, where `action` is `created`, `changed` or `trashed`), `skill`, `shown` (a file the model showed with `show`: `{path, name, media_type, size, modified, title?, language?, width?, height?}`; `modified` is the file's modification time at the moment it was shown, written like an event's `at`; the content isn't kept in the core: local heads read it from `path`, and remote heads read it in chunks with [`session.shown`](blob.md#sessionshown) and this step's `call`; a new one with the same `path` replaces the old one), `detail` (structured details the tool returned, for example the items it found; one with `kind` is one of the three common shapes `links`, `table`, `images`, see [Extensions](extensions.md#toolcall-toolcancel)), `output` (the start of the result text: at most 100 lines or 8 KiB; when it was cut, `output_cut: true` is set, and `view.detail` gives the whole), `questions` (the set of questions a question step asked, present as soon as they are asked), `nested` (a `shell` whose script called tools: `{count, last}`, with `last` being the highest-numbered `{n, name, title, state, started?}`; heads append `· #n display name` to the line and fetch the full list with `view.detail`), `progress` (while the step is running, its latest progress line: a line of the tool's output that starts with `miyu-progress: `, without the prefix, at most 200 characters; pushed at most every 0.5 seconds per step; removed once the result arrives, and never present in a page or a fresh subscription) |
| `end` | A turn's end: `reason`, `model`, `endpoint`, `took_ms`, `usage`, `speed` (`{output, ms}`: the output tokens and the milliseconds from first token to finish, each summed over the turn's main requests, leaving out tool runs, waiting for the user and side requests; absent when no timing was recorded; a request whose reply arrived in one burst is left out, meaning under 100 ms from first token to finish, or over 5000 tokens a second); on an error, also `error` and `explain` |
| `notice` | An aside: see the values of `what` below |

**A `tool`'s `state`**: `preparing` (the arguments are still being written), `running`, `ok`, `error`, `denied`, `cancelled`, `skipped`.

**A `tool`'s `title`**: `{"name", "object", "said", "via"}`: the tool's display name, its object (a path, a command's short title…), the result sentence, and who did it (for example the web search source `Exa`, shown in parentheses after the name; absent when there is none). A denied step (`state` is `denied`) carries the result sentence whatever the tool is, saying who blocked it and why (for example `Blocked by acme-guard: reason` or `Read-only mode, not run`); it is absent when the result has no words for people.

**Provider-side tools** (`hosted: true`): these are searches or page reads the model ran on the provider's side. The core doesn't run them, and they are drawn as the same kind of tool step. `name` is the provider's own tool name, as is; for tools the core knows (`search_web`, `web_search`, `WebSearch`; `read_url_content`, `web_fetch`, `WebFetch`), the `title` takes the display name and object of the core's web search or page fetch, while unknown tools have their raw name as `title.name` and no object. `title.via` says who ran the tool: the display name of the provider that wrote the reply (set in the config, or the catalog's name for that provider), or the provider id when there is none. The state is `preparing` while the arguments are being written, `running` once they are complete, and `ok` when the result arrives (`error` if the provider says it failed); for a reply that was saved without a result, it is `cancelled` if the reply was interrupted and `ok` otherwise. These steps never have an `approval` or a `said`, and they are never `denied`. `output` and `output_cut` come from the result the provider returned; get the whole result with `view.detail` and this step's `call`, which is present once the reply is saved.

**The collapsed line** (`summary`): a list of segments `{"text", "tone"?}`, with `tone` being `added`, `removed` or `error`. For example `Ran 2 commands · 1 edit +3 -1 · 5s`.

**A `notice`'s `what`**:

| `what` | Fields |
|---|---|
| `compaction` | `trigger` (`auto`, `manual`, `overflow`), `state` (`running`, `done`, `failed`), `written`, `expected`, `prepared`, `before`, `after`, `took_ms`, `usage`, `instructions`, `truncated` (when the summary request was too long and some of the oldest groups were cut, this is how many were cut, and the earliest part is not in the summary; left out when nothing was cut); fetch the summary text with `view.detail` |
| `cleared` | The context was cleared |
| `paused` | Automatic compaction was paused: `reason`, `failures` |
| `reverted` | Some turns were undone: `turns`, `said`, `jobs` |
| `job` | A background job finished: `job`, `job_kind`, `title`, `mark` (`done`, `failed`, `stopped`), `report`, `command`, `output` (`{blob, chars}`), `exit_code`, `signal`, `took_ms`, `nested` (present when the command's script called tools, the same as on `tool`) |
| `lines` | A watched background command printed a batch of lines (`job.lines`): `job`, `title`, `command`, `text` (the whole batch, at most 4000 characters; a batch that was cut has a line in the middle saying how much was left out), `lines` (how many lines), `omitted` (how many characters were left out). This doesn't mean the job has ended: its row in `jobs` is still running |
| `answered` | A set of questions was answered: `questions`, `answers`, `by` |
| `persona` | The persona or preset changed mid-session; the notice appears at the moment the change takes effect: `persona: {from, to}`, `preset: {from, to}`, only the ones that changed; the values are ids, `null` for none |
| `recap` | A recap: `text`, `covers` |
| `model` | The model changed: `endpoint`, `model`, `from`, `why` (`failover`, `replaced`) |
| `workspace` | The workspace changed: `cwd`, `dirs` |
| `peer` | A session being waited on went idle, or can't be waited on any more: `session`, `reason`, `status` |
| `retitle_failed` | A new title that a person asked for ([`session.retitle`](sessions.md#sessionretitle)) failed, and the title is unchanged: `text` (the line written in the connection's language: `Failed to change the title`), `error` (the error of that request). This notice exists only in the view stream; paging and resubscribing don't bring it back |

## Session `status`

| Name | Notes |
|---|---|
| `state` | `idle`, `running`, `waiting` (an approval or a question is still open) |
| `waiting` | `[{what: "approve" | "ask", entry, call}]` |
| `since` | When this turn started |
| `waited_ms` | How long this turn has waited on a person (for an approval or an answer) in finished stretches, in milliseconds, with overlapping waits counted once; absent when the turn never waited. Waiting does not count as time spent |
| `waiting_since` | When the current wait on a person began; absent when not waiting. Time spent is now − `since` − `waited_ms` − (now − `waiting_since`), so the clock stops while waiting; the `took_ms` of entries leaves out waiting time too |
| `doing` | What is happening right now: `thinking`, `writing`, `tool` (with `entry`); `retrying` (`attempt`, `limit`, `at`, `class`, `message`); `compacting` (`trigger`, `written`, `expected`) |
| `context` | `{window, compaction_line, context, used}`: the context window (when the session has a context limit, this is the window in effect, the smaller of the model's window and the limit), the compaction line, the session's context limit (absent when not set), and the latest usage (that request's input plus output; right after a compaction, the compacted size) |
| `speed` | `{output, ms}`: the output tokens and milliseconds of the latest request that has a speed (a request whose reply arrived in one burst is left out and does not replace it; the same rule as the `speed` of `end`) |
| `cooling_until` | When every candidate is cooling down, the earliest time one recovers |
| `preparing` | Compaction is being prepared ahead of time in the background: `{seen, since}` |
| `usage` | This session's total usage, written like a row of `usage.query` (including `converted` and `converted_parts`) |
| `model`, `permission`, `todos`, `workspace`, `persona`, `preset` | The same as in the subscription response; a persona or preset changed mid-session is pushed. A no-tools session has `preset: null` plus `no_tools: true`, the same as in the session list |
| `vision` | The multimodal model pinned for the session (`vision` in `session.configure`): a model or `@pool`, as written; pushed as soon as it is pinned, and absent when nothing is pinned (the session then follows `models.vision`) |
| `compaction_line` | The compaction line pinned for the session (`compaction_line` in `session.configure`): a percentage of the window; pushed as soon as it is pinned, and absent when nothing is pinned (the session then follows `compaction.line`). The line in effect is `context.compaction_line` |
| `todos_done` | When the to-do list was cleared because everything was done, this is the list from before the clearing (heads tick everything, pause, and then collapse it) |
| `goal` | The standing goal: `{text, limit, state, reason, round, since, usage}`, with `state` being `running`, `paused`, `completed`, `blocked` or `waiting` |
| `jobs` | The jobs this session started directly (the running ones and the last 20 finished): `{job, what, title, state, started, ended, session, command, exit_code, signal, why, nested, fork}` (`nested` is the same as on `tool`, present only for a command whose script called tools; `fork` is present only on forked subagents and is `true`, so heads can show a fork icon), with `state` being `running`, `done`, `failed`, `stopped` or `aborted`. In a venue session, the parallel branches the bridge forked off (`session.fork`) are listed here too, after the jobs: `{job, what: "agent", fork: true, session, title, state, started, ended?}`, where `job` and `session` are both the branch's session id, `title` is the branch's title or, when it has none, the first line of its first message, and `state` is `running` (running, with its first turn not finished yet), `done` or `stopped` (interrupted); all running branches are listed, and only the last 20 finished ones; to open one, subscribe to its view stream with `session` |
| `title` | The session's title, present only when it has one; a change pushes a new status. Venue sessions aren't in the session list, so heads take the session name from here |
