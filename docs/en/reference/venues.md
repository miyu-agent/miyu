# Venues: sessions on chat platforms

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

A venue is where a session happens: either this machine (`local`), or a private chat or a group on a chat platform. A chat platform bridge (such as the bridge to QQ) is an extension, and its manifest lists the platforms it connects to in `[connection] platform`. Venue sessions all belong to the owner: a private chat whose peer is in the owner bindings (that is, the owner in person) is treated like a local session, while groups and strangers' private chats are confined to the sandbox. This page lists the methods that bridges use.

| Method | What it does |
|---|---|
| [`venue.session`](#venuesession) | Finds or creates a venue's main session |
| [`venue.sessions`](#venuesessions) | Lists all of this bridge's venue sessions |
| [`venue.binding`](#venuebinding) | Asks whether a platform identity is the owner |
| [`venue.plugins`](#venueplugins) | Tells the core which venue plugins a venue has turned on |
| [`as` and `venue` in `session.send`](#as-and-venue-in-sessionsend) | Speaks for a person on the platform |
| [`session.respond`](#sessionrespond) | Starts a turn from messages recorded while listening |
| [`session.note`](#sessionnote) | Records a few facts without starting a turn |
| [`venue.records`](#venuerecords) | Returns the group chat records the judge reads |
| [`venue.*` in `events.append`](#venue-in-eventsappend) | Records recalls, and records the messages the AI delivered |

**Who can call**: `venue.sessions`, `venue.binding`, `venue.plugins`, and `venue.session` for a confined venue (a group, a stranger's private chat), are only for platform bridges (a platform bridge is an extension started by the core whose manifest has `[connection] platform` and that was granted `act_for_external`); any other caller gets `needs_approval` (`data.capabilities` is `["act_for_external"]`). The owner's own private chat can also be opened from the owner's connections. A bridge can reach only the venue sessions of its own platforms (judged by the platform prefix of the venue id). Speaking for people on a platform (`session.send` and `command.run` with `as`), `session.note`, `venue.*`, and recording `venue.*` events all require the `act_for_external` capability.

**The owner viewing venue sessions**: only the bridge for that platform can speak into, change or delete a confined venue session (a group, a stranger's private chat). The owner's connections (people's heads; a head is an interface program that connects to the core, such as the terminal interface or the web interface) can only view it read-only: reading methods work as usual, and writing methods return `session_not_found`, as if there were no such session:

- Reading methods: `subscribe`, `unsubscribe` (the `events` and `view` streams, and catching up with `after` works as usual), `view.page`, `view.detail`, `session.prompts`, `session.tools`, `session.context`, `session.usage_parts`, `session.quota`, `job.output`, `blob.get` with `session`, and `session.shown`.
- Every other method with a `session` returns `session_not_found`: sending, `command.run`, redo, revert, interrupt, compact, clear, configure, `set_*`, fork, retitle, delete and so on.
- Extensions and platform bridges aren't affected by this rule: a bridge still reaches only the venue sessions of its own platforms, and that applies to reading too.

**Venue ids**: short names that the bridge chooses (1 to 128 bytes, with no control characters), such as `qq:private:10001` and `qq:group:123456`. The core doesn't interpret them, apart from the platform prefix before the first `:`.

**Owner bindings**: the system setting `[external.bindings]`. Every platform identity written there is the owner (because there is only one owner, any value counts; an empty value doesn't):

```toml
[external.bindings]
"qq:10001" = "owner"
```

In a private chat, this identity is the owner in person; in a group, it is the owner.

The voice assistant's `voice:owner` is the owner without being written into the bindings: this holds only in venues whose platform is `voice`, and a bridge for another platform that reports this identity is treated as an outsider.

## `venue.session`

**Params**

| Name | Type | Notes |
|---|---|---|
| `venue` | string, required | The venue id |
| `kind` | `private` or `group`, required | Whether it is a private chat or a group |
| `peer` | string | The other side of a private chat; required for `private`, and not allowed for `group` |
| `persona` | string or `null` | The persona to use when creating the session (the bridge works it out from its own rules); `null` means no persona |
| `preset` | string | The preset to use when creating the session |
| `profile` | boolean | Whether to include the owner's "about you" when creating the session: set it to `true` only for the owner's own private chat |
| `images` | boolean, default `true` | Whether this venue can display images |
| `voice_max_ms` | positive integer | How many milliseconds a voice message may last on this platform; set it only for platforms that have such a limit. It is recorded in `session.created` and passed on with every tool call in the session (`voice_max_ms` of an extension's `tool.call`); `say` answers with an error when what it synthesized is longer, so the AI says it again. It is also read when an existing session is found: a value different from the recorded one is recorded in a `session.policy_changed` (`voice_max_ms`), and later calls carry the new value; leaving it out keeps the recorded one. `0` is `bad_params` (`data.field` is `voice_max_ms`) |
| `titles` | boolean, default `true` | Whether this session gets automatic titles: with `false` it never gets one again, and renaming by hand still works. This is ignored when an existing session is found |
| `cwd` | string | The working directory when creating the session; the owner's default workspace when it is omitted |
| `recent` | integer, 1 to 1000 | Groups only: at most this many recent group messages (counting back from the newest) go in front of a turn; the byte budget still caps it, and the smaller of the two wins; when it is omitted, only the byte budget applies. It is fixed when the session is created |
| `fresh` | boolean, default `false` | Don't look for an existing session, always create a new one: when the newest session's log is broken (`session_read_only`), the bridge opens another one this way; from then on the new one is found as usual, and the old one stays and can still be viewed |

The fields used for creating a session are ignored when an existing session is found.

**Response**: `{"session", "created"}`: the session id, and whether it was just created. Sessions are found by venue plus whether they are confined: when a private chat's peer is added to the bindings later, the old confined session is not reused, and a new unconfined one is opened instead.

Nobody can approve anything in venue sessions: everything that needs approval is refused. The same `id` sent again returns the same session.

**Errors**: `needs_approval`; `unknown_persona`, `unknown_preset`, `preset_invalid`; `bad_params`.

## `venue.sessions`

**Params**: none. **Response**: `{"sessions": [{"session", "venue"}…]}`, newest first. These are the venue sessions of the platforms this bridge serves (read from the manifest's `[connection] platform`, which may list several platforms); local sessions that the bridge opened itself are not listed. Only the newest session of each venue is listed. Bridges subscribe to these sessions when they start.

## `venue.binding`

**Params**: `id`: a platform identity. **Response**: `{"owner": true|false}`: whether the identity is the owner (whether it is in the owner bindings). The core answers from the config at that moment. Bridges use this method when guarding owner-only actions: before acting on someone, check who the target is.

## `venue.plugins`

**Params**: `venue`: the venue; `on`: the names of the venue plugins it has turned on (as in `provide`'s `plugin`); leaving it out or leaving it empty means none. **Response**: `{}`.

Each call replaces the whole list. Tools with a `plugin` are only given in this venue's sessions while that plugin is on, starting from the next turn; a call this turn to a tool that was just turned off gets "not available right now". The core keeps this list in memory only, so after a restart no venue has any plugins: send it once for each venue after connecting. A bridge can only set this for venues on its own platforms (read from the manifest's `[connection] platform`, which may list several platforms): venues on other platforms get `bad_params` (`data.field` is `venue`), and badly written names get `bad_params` (`data.field` is `on`).

## `as` and `venue` in `session.send`

Venue sessions only accept messages with `as` (a message without it gets `venue_session`); `as` in a local session is `bad_params`.

**`as`**: `{"external": <platform identity>, "role": "manager" | "member"}`. `role` defaults to `member`, and slash commands check it to decide who may use them. The owner isn't recognized by `role` but by the bindings.

**`venue`**: the fields of one platform message, which the core records as they are:

| Name | Notes |
|---|---|
| `msg` | The platform's message id; required |
| `reply_to` | The id of the message it quotes |
| `name` | What the sender is called here right now (the group card, or the nickname when there is none), at most 64 characters |
| `my_name` | What the AI is called here right now (the group card, or the nickname when it is empty; in a private chat, the nickname), at most 64 characters. Memory treats it like the persona's name when recognizing the AI: things about this name are kept as the AI's own, not as someone it knows |
| `place` | What the group is called right now (its name), at most 64 characters; not written for private chats. Only memory uses it: memories saved in the group carry it, and nothing the AI reads shows it |
| `mentions` | Who was @-mentioned (a list of platform identities) |
| `mentions_me`, `mentions_all` | The AI was @-mentioned; everyone was @-mentioned |
| `media` | What the message carries, `[{"kind", "id", "name"?, "size"?, "shown"?}]`: `kind` is `image`, `file`, `voice`, `video` or `sticker`; `id` is the platform's id (nothing is downloaded); `shown` means the original of this item was already passed in as an attachment |
| `forwards` | Merged forwards: `[{"nodes": [{"name", "text", "media"?, "forwards"?}], "more"?}]`; `media` is as above, and each item may also carry `index` (a positive integer the bridge assigns, rendered as `[image #3]` and used to fetch the item; it is only allowed inside forwards, and in the top-level `media` it is `bad_params`); forwards can be nested at most 8 deep; there is no separate cap on how many nodes one forward or the whole message carries, or on the length of names and text, only the 1 MiB line limit (see [Connection](connection.md)). The text must contain a placeholder (such as `[forward]`) |
| `quoted` | The content of the quoted message (sent when this message quotes one, and accepted in groups and private chats alike): `{"name", "text", "media"?, "forwards"?}`, exactly like one node in `forwards`, with forwards inside nested at most 8 deep and, like `forwards`, no other cap on count or size. It needs `reply_to`. When it is present, it is always written under the quote line, whether or not the session log has the quoted message; without it, only the number is written. Private chats get the quote line too, as a block of its own |
| `poke` | A poke (QQ's nudge: the person double-clicked the AI's avatar); it can only be `true` (`false` is `bad_params`). The bridge sends it as a message from the person who poked: `text` may be empty; the AI sees one sentence, `<name> poked you (a QQ nudge: they double-clicked your avatar)`, with the platform taken from the venue's platform and the name from `name` (the platform identity when there is none). Every other rule (listening, the judge, parallel branches) is the same as for an ordinary message |
| `poke_text` | The poke's suffix: the half sentence the person set on the platform (for example 的小脑袋, "on the little head"), escaped and appended to that sentence. It is only allowed with `poke` (on its own it is `bad_params`); it must not be blank, and it is at most 64 characters with no control characters |
| `ambient` | Listening only: the message is recorded and doesn't start a turn |
| `asleep` | The message was received while asleep |
| `backfill` | The message was fetched back (missed while the bridge was disconnected and fetched from the platform later): it is kept in the chat record only, and left out of the recent chat and the judge's records; it requires `ambient` |
| `sent` | The time the platform gives, written like an event's `at` (`2026-10-20T04:30:00.000Z`); `history` shows it. The log still keeps the order things were recorded in, and sequence numbers don't move back |
| `show_ids` | Whether to show the sender's platform identity when rendering this message |

**Recorded as**: the owner recognized through the bindings in a private chat is recorded as `{"kind": "person", "via"}`; anyone else is recorded as `{"kind": "external", "venue", "id", "role"}`, plus `"owner": true` for the owner in a group.

**Command ids**: bridges build `id` from the platform, the logged-in account, the message id and the platform's timestamp, so that reconnect resends and platform resends take effect only once.

## `session.respond`

This method starts a turn from messages recorded while listening (when it has been decided that the AI should answer in a group); without `to`, it starts a turn from a few facts (for example, a timed look at a private chat).

**Params**: `session`; `to`: optional, the numbers of those `message.user` events, at most 64; `facts`: optional, a few facts `[{"kind", "text"}]` (`text` at most 4 KiB), placed before the trigger. At least one of `to` and `facts` must be non-empty. Without `to`, the facts are recorded first and the last one starts the turn; an extension calling it this way needs `act_for_external`. `tail`: optional, one piece of text (at most 2 KiB; an empty one counts as not given). Every model request of the turn this opens gets it at the very end (after the newest message or tool result); it doesn't go into the history, the view, exports or compaction, and the next turn doesn't have it. It is meant for a fixed hint that every turn should carry.

**Response**: `{"events": [...]}`. If a turn is running, these messages join it and the AI hears them at the next step; a `tail` given here replaces that turn's, and leaving it out keeps the one the turn has.

**Errors**: `not_ambient` (`to` has messages that weren't recorded while listening; the error has `data.messages`); `already_answered` (already used as a trigger; the error has `data.messages`); `bad_params` (for a `tail` that isn't a string or is over 2 KiB, `data.field` is `tail`).

## `session.note`

This method records a few facts without starting a turn, interrupting, or setting the AI going when it is idle (for example, when the AI's message couldn't be delivered and it should know at the next step).

**Params**: `session`; `facts`: 1 to 16 blocks `{"kind", "text"}`. **Response**: `{"events": [...]}`. During a turn, the facts belong to that turn and the AI sees them at the next request; when it is idle, the AI sees them at the start of the next turn.

## `venue.records`

This method returns the group chat records the judge reads (the judge is the small request that decides whether to answer a group message), in the same line format the AI sees.

**Params**: `session`; `msg`: the number of the message being judged (a `message.user` with `venue`); `count`: 1 to 100; `grow`: optional, the step for aligning the start, at least 1, with `count + grow` at most 100. With `grow`, the start sits on a multiple of it (`(earlier messages − count) / grow × grow`, from the beginning when below 0), so between `count` and `count + grow − 1` messages come back: the start stays put for a while, so the judge's request prefix stays stable and the cache keeps hitting.

**Response**: `{"records": "<earlier messages, one per line>", "current": "<that message>", "count": <how many earlier messages>}`. The model's own replies are `[you]` lines, and recalled messages are marked as well. When `current` quotes another message, the sender and content of the quoted message follow the number (`reply-to: msg=8805 小林: @Miyu 在吗`); if that message is not in the log, only the number is written. A `quoted` is written indented below it (both appear when the log has that message too). Earlier lines work the same way: a line with `quoted` gets it written below.

**Errors**: `bad_params`; `session_not_found`.

## `venue.*` in `events.append`

Besides its own `ext.<prefix>.*` (see [Extensions](extensions.md#eventsappend)), a bridge can record two kinds of events in venue sessions:

| `kind` | `body` | Meaning |
|---|---|---|
| `venue.recalled` | `{"msg", "by"}` | Someone recalled a message: the platform id, and who recalled it |
| `venue.delivered` | `{"line", "turn", "to", "msg", "text", "images"?}` | The AI's message reached the platform: which session, which turn, to whom (a list of platform identities), the platform id, the text, and the image hashes |

These two kinds are only accepted in venue sessions, and malformed ones are `bad_params`. In the group chat the AI sees later, recalled messages are marked, and `[you]` lines are what the AI said.
