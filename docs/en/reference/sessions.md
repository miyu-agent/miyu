# Sessions: `session.*`, `view.*`

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

A session is one conversation: it is an append-only event log, and the core works out the session's current state from that log. A head (an interface program that connects to the core, such as the terminal interface or the web interface) creates sessions, sends messages into them, and subscribes to their events to draw its interface.

| Method | What it does |
|---|---|
| [`session.create`](#sessioncreate) | Creates a session |
| [`session.list`](#sessionlist) | Lists sessions |
| [`session.send`](#sessionsend) | Sends a message into a session |
| [`session.interrupt`](#sessioninterrupt) | Interrupts the running turn |
| [`session.withdraw`](#sessionwithdraw) | Takes back one queued message without interrupting the turn |
| [`session.tools`](#sessiontools) | Shows the tools the AI can use next turn |
| [`session.context`](#sessioncontext) | Shows which parts the context is made of and how much each part takes |
| [`session.usage_parts`](#sessionusage_parts) | Shows cumulative usage, split by context part |
| [`session.quota`](#sessionquota) | Shows the provider's quota: how much of each window is used and when it resets, or the account balance |
| [`session.answer`](#sessionanswer) | Answers an approval request or a set of questions |
| [`session.revert`, `session.unrevert`](#sessionrevert-sessionunrevert) | Undoes; restores the last undo |
| [`session.redo`](#sessionredo) | Redoes the last turn |
| [`session.compact`](#sessioncompact) | Compacts the context now |

Venue sessions (group chats and private chats on a chat platform) have a few more methods; for details see [Venues](venues.md).

## Common

- **Session ids** are UUIDv7 strings, ordered by when the sessions were created.
- **Who can call**: people can call all of the methods below. On venue sessions confined to a sandbox (group chats, private chats with strangers), people can only look in read-only mode: the reading methods still work, and the others return `session_not_found` (see "The owner viewing venue sessions" in [Venues](venues.md)). An extension can call these methods only on the sessions it can see (a platform bridge sees only the venue sessions of its own platforms; other extensions see local sessions and your own private chats), and it also needs the matching capability: the reading methods (`session.list`, `session.recap`, `session.tools`, `session.context`, `session.usage_parts`, `session.quota`, `session.prompts`, `view.page`, `view.detail`) need `events.read`; creating sessions, sending, interrupting, reverting, unreverting, redoing, compacting, clearing, configuring, forking, renaming and retitling need `sessions.drive`; `session.answer`, `session.set_permission_level`, `session.set_workspace`, `session.terminal`, `session.set_terminal`, `session.delete`, `session.export` and `session.import` are for people only (`local_only`). When an extension sends a message without `as`, the message is recorded as said by the extension itself (`harness`, named after the package's id); an extension can't set `from`.
- **Sessions that aren't running are loaded first**: if the core has restarted, or a session has idled long enough to retire, the session is loaded automatically the first time it is used, and the head doesn't need to handle this.
- **Changes arrive as pushes**: most methods return only `{}` or a few event numbers; the change itself is pushed as events to the heads subscribed to the session (see [Pushes](pushes.md)).
- **Errors when looking up the session**: every method that takes a `session` parameter can return these errors:

| `data.reason` | When |
|---|---|
| `session_not_found` | There is no such session; a deleted session also returns this error |
| `session_broken` | The session can't be loaded: its log is broken or can't be parsed |
| `session_read_only` | A line in the middle of the session log is broken: what came before that line can still be read with `view.page`, but the session can't be loaded or continued, so start a new session to go on. `data.segment` is which log segment (file name only), and `data.line` is which line |
| `session_unavailable` | The session can't be read right now: an I/O error happened while reading its log. The log itself is intact, so try again a little later |
| `session_stopped` | The session has stopped (its log couldn't be written, or there was a bug); sending again reloads the session |
| `session_sealed` | A forked session has run its turns and was sealed; commands that change the conversation are no longer accepted |
| `restoring` | A command arrived while an undo was still finishing (this normally can't happen) |

## `session.create`

**Params**

| Name | Type | Notes |
|---|---|---|
| `cwd` | string | The head's working directory, written the way a person sees it, for example `~/src/miyu`. When it is omitted, the session uses its own default workspace; remote connections can't give this parameter |
| `persona` | string or `null` | Which persona to use; `null` means no persona; when it is omitted, the `persona.default` setting is used |
| `preset` | string or `null` | Which preset to use; when it is omitted, `preset.default` is used, and `full` when neither is set; `null` means no tools, so the session gets no tools at all (this is the old way to say it and is still accepted; when a new session picks "Nothing", it is written `none`) |
| `model` | string | `<provider>/<model>` or `@<pool>`; when it is omitted, `models.chat` is recorded as it is right now (a pool is recorded as the pool), and later changes to `models.chat` don't affect this session. An empty fixed pool (`@lite`, `@normal`, `@flagship`) is treated as omitted |
| `vision` | string | Which model describes images for this session, written the same way as `model`; when it is omitted, the session follows the configured `models.vision`; an empty fixed pool is treated as omitted too. When it is given and resolves, a `session.policy_changed` is recorded once the session is created, the same as `vision` in `session.configure` |
| `compaction_line` | integer | This session's compaction line, a percentage of the window from 20 to 95; when it is omitted, the session follows the configured `compaction.line`. Once the session is created, a `session.policy_changed` is recorded, the same as `compaction_line` in `session.configure` |
| `memory` | `persona`, `off` | `persona` means memory follows the persona, and `off` means memory is off; when it is omitted, memory follows the persona. Any other value (including the old `session`) returns `bad_params` |
| `dirs` | array of strings | Extra directories, which can be read and written like the working directory |
| `oneshot` | boolean, default `false` | Whether this is a one-shot session (such as the sessions the `miyu ask` command creates) |
| `images` | boolean, default `true` | Whether your interface can display images |
| `titles` | boolean, default `true` | Whether the session gets automatic titles: with `false`, the core never writes a title by itself, and a person can still rename the session by hand |
| `project` | string | Which project to create the session in ([Projects](projects.md)): `persona` and `preset`, when omitted, use the project's settings, and once the session is created a `session.meta_changed` is recorded (the response's `events` is then `[1, 2]`) |

**Response**

| Name | Notes |
|---|---|
| `session` | The new session's id |
| `events` | `[1]`, which is the `session.created` event; with `project` it is `[1, 2]`; with `vision` and `compaction_line` there is one more event for each (in that order, after the project's) |
| `cwd` | The directory the session actually works in, written the way a person sees it (paths under the home directory are written as `~/…`, the same as in `session.list`) |
| `wide` | `true` means the directory is too wide (the root; on Windows also the home directory or a folder that holds the data directory); it is used because the person chose it, but the only place the session may freely write is its own default workspace |
| `untrusted_project` | If the directory has a project config that hasn't been trusted or rejected yet, this gives where that config is |

```json
→ {"jsonrpc":"2.0","id":"c1","method":"session.create","params":{"cwd":"~/src/miyu"}}
← {"id":"c1","jsonrpc":"2.0","result":{"cwd":"~/src/miyu","events":[1],"session":"01a14aca-d2c4-768c-acc6-a67e35106d22"}}
```

If you send the same `id` again, the core returns the session it created the first time and doesn't create another one.

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | The persona or preset id is malformed; `memory` is not `persona` or `off`; `model` or `vision` is not a string; `compaction_line` is not an integer from 20 to 95 |
| `unknown_persona`, `persona_invalid` | There is no such persona, or the persona's files are wrong (`data.problem` says which layer, which file and which line) |
| `unknown_preset`, `preset_invalid` | The same as the row above, for presets |
| `unknown_model` | `model` or `vision` can't be resolved: it is malformed, the provider doesn't exist, the pool doesn't exist, or a pool you created yourself is empty (an empty fixed pool doesn't count; it is treated as omitted) |
| `dir_too_wide` | An entry in `dirs` is too wide (the home directory, the root, or a directory that contains the data directory) |
| `internal_error` (`-32603`) | The core couldn't create the session |

## `session.list`

**Params**: `oneshot` (boolean; `true` lists only one-shot sessions), `dream` (boolean; `true` lists only consolidation sessions, `false` leaves them out, and all sessions are listed when it is omitted), `limit` (the most sessions to list; all of them when it is omitted).

**Response** is `{"sessions": [<item>…]}`, newest first. Each item has these fields:

| Name | Notes |
|---|---|
| `session` | The session id |
| `cwd` | The working directory, written the way a person sees it |
| `last_active` | The time of the last event |
| `last_spoken` | The time a person last spoke, that is, the time of the latest message from a person (the owner on a head, or someone on a chat platform); turns started by loops, schedules, reports or resumes don't count. Heads sort the session list by it: just switching into a session doesn't move it, and only a person speaking moves it to the top. It is omitted until a person has spoken |
| `oneshot` | Whether it is a one-shot session |
| `parent` | A child session's parent; for main sessions this field is `null` |
| `title` | The title; omitted when there is none |
| `named` | `true` means a person gave the title |
| `preview` | Given when there is no title: the first line of the first message, at most 50 characters |
| `pinned` | `true` means the session is pinned |
| `busy` | `true` means a turn is running |
| `viewed` | `true` means at least one head is showing it ([`session.viewing`](#sessionviewing)), and that head is the one that shows its background notices |
| `persona`, `preset` | The persona and preset in use; omitted when there is none. With no tools, `preset` is `null` and `no_tools: true` is added |
| `tokens` | How many tokens this session and every session it spawned (all the way down) have used: the input (uncached, cache read, cache write) plus the output of every model call (main requests, titles and compactions all count), the same sum as the terminal footer's `Σ`; omitted while it is 0 |
| `context` | `{"used", "window"?}`: how many tokens are in context (the input of the latest main request: uncached, cache read and cache write, the same figure as the terminal footer and the session status); omitted before the first request and right after a compaction. `window` is the context window of that request's model, looked up under the current config, and is omitted when it is unknown |
| `project` | Which project the session is in; omitted when it is in none |
| `kind`, `dream` | Only on consolidation sessions (the sessions memory consolidation runs in): `kind` is `"dream"`, and `dream` is `{"persona"?, "session"?, "manual"?, "from"?}`, which says whose memory is consolidated (the persona's; `session` only appears on older sessions); `manual: true` is set when a person asked for the run, and `from` is the session it was asked from. A finished run adds `result`: `{"given", "revised", "retired", "summary", "stopped"?}`, which says how many memories it added, revised and retired, whether it wrote the summary, and `stopped: true` when it was stopped; a run that did not finish has no `result`. A main session list usually leaves these sessions out (pass `dream: false`), and a memory page lists the ones for its memory by `dream` |
| `origin` | Where the session was opened: `"terminal"` on sessions the shell integration opened (with `session.terminal`), which heads show as "shell" in the session list; `"advisor"` on advisor sessions the AI opened by asking the advisor (child sessions, with `parent`). Other sessions and older ones don't have this field |
| `forked` | Only on forked subagent sessions, where it is `true`: heads use it to show a different icon. Ordinary subagents and main sessions don't have this field |
| `archived` | Only on imported read-only archives, where it is `true`: heads list these in their own section and replace the input box with a line saying it is an archive |
| `default_workspace` | The session's default workspace, an absolute path: a main session uses its own `…/workspace/<session id>/`, and child sessions and forks use their main session's. When `cwd` equals it, the interface can show it as "default workspace" |

This method lists only local sessions; venue sessions aren't included (for those, see `venue.sessions` in [Venues](venues.md)). To keep the list up to date, subscribe to the `sessions` stream ([Connection](connection.md)).

**Errors**: `bad_params`; `internal_error` when the session directory can't be read.

## `session.send`

**Params**

| Name | Type | Notes |
|---|---|---|
| `session` | string, required | Which session to send to |
| `text` | string, required | What to say |
| `attachments` | array | Attachments, in order. Each item is the `blob`, `name` and `media_type` from a `blob.put` response, optionally with `path` (where the file was on this machine); or it is a path-only item `{"path", "name", "size"?}` that has no `blob` (see item 3 below) |
| `urgent` | boolean, default `false` | Cut in: if the AI is busy, it sees this message at its next step |
| `shell` | boolean, default `false` | A command the person typed with `!` in the input box: `text` is the command line, and the core runs it in the session's working directory (see item 4 below) |
| `skills` | array of strings | Skills the person named with `$` in the input box, in order (pick the names from `skills` in [`command.catalog`](packages.md#commandcatalog)): each skill's body is wrapped in `<skill name=… path=…>` and sent to the AI before the message; the timeline still shows `text` as typed. An unknown skill, or one people can't name, returns `unknown_skill`; a skill turned off by the session's preset returns `command_not_allowed` (`data.why` names the preset); a skill listed twice, skills together with `shell`, skills in a venue session, or skills in a message said by someone else return `bad_params` |
| `prefix` | `"keep"` or `"compact"` | What the person chose when the prefix is changing: send as is, or compact the context and send (see **Prefix changing** below) |
| `from` | string | If you are another agent program, write your name here; the message is then recorded as yours, not as the person's |
| `cwd` | string | Move to this working directory first, then send (shell integration: each turn's working directory follows the shell): it is checked the same way as in [`session.set_workspace`](#sessionset_workspace), `wide` for too-wide directories included; the same directory as now records nothing, and a change pushes `session.workspace_changed`. Venue sessions don't accept this parameter |
| `as`, `venue` | object | Only for venue sessions; see [Venues](venues.md) |

**Response**: `events` (this message's number), `cwd` (the working directory after any move), `untrusted_project` (the same as in `session.create`); when the session moved somewhere too wide, `wide: true` is added. If `cwd` is wrong (`path_unreadable`, `not_a_directory`, `path_forbidden`), the whole message is refused.

1. If the AI is idle, the message starts a turn; if the AI is busy, the message is queued (an `urgent` one cuts in at the next step). The `turn.started` of the turn it starts has this request's `id` as `cause`, so you can tell that the turn is yours.
2. The call returns once the message is on disk, without waiting for the AI to finish answering; watch the pushes to see how the AI answers.
3. The core checks attachments before it looks up the session: each attachment's blob must exist, and the core recognizes it again from its content (see [Attachments](blob.md)).
   - **Path-only items**: a file over the upload limit (20 MiB) doesn't need its content uploaded; you hand over only its path on the core's machine. `path` is an absolute path (starting with `/`, `~/`, a Windows drive letter or `\\`), with no control characters, at most 4096 bytes; `name` is the file name (no path, at most 255 bytes); `size` is the size in bytes, a non-negative integer, and is optional. A malformed item returns `bad_params`.
   - The core doesn't read the file or check that it exists: the AI sees one line with the name, path and size, and the content isn't included; when the AI needs the content, it reads the file from that path with its tools (permissions are checked at that point). Path-only items can be mixed with `blob` items, and the order you write them in is kept.
   - The item is recorded as a `{"type": "path", "name", "path", "size"?}` block in `message.user` (see [Events](events.md)); in the view it is still an attachment, but without `blob` and `media_type`, and with `path_only: true` added (see [View](view.md)).
   - Only `session.send` and `session.redo` accept these items: venue sessions (messages with `as`) and the attachments of [`session.answer`](#sessionanswer) don't, and return `bad_params`. `path` is a path on the core's machine, so a remote connection that sends one still gets `local_machine_only` (see [Connection](connection.md)).
4. `shell: true`: only accepted from a person typing in a head; there is no permission check, no sandbox and no confirmation. It is recorded as a `message.user` with `shell`, and the call returns once that is on disk. At the moment the AI hears it (the first thing in the turn it starts when the AI is idle, or before the next model request when the AI is busy), the core runs it in the session's working directory at that moment; the result is recorded as `shell.ran` (see [Events](events.md)), and then the AI answers. A queued command can be handed back like any other message, and a command handed back never runs. After 120 seconds the command is killed together with its whole process group; interrupting (`session.interrupt`) while it runs also kills the whole process group, and the AI doesn't answer. Together with `attachments` or `venue`, it returns `bad_params`. In the view stream, the `user` entry gets an extra `shell` field (see [View](view.md)).

**Prefix changing** (only heads that sent `caps.prefix_ask: true` in the hello see this): if files in your tool descriptions, prompt overrides, personas or presets change (skills don't count: a skill change in the middle of a session goes into the end of the messages and leaves the prefix alone), the next request's prefix changes and the cache is lost. The core judges this for each session on its own: if the change is to another persona, to pictures such as avatars and backgrounds, or to overrides the session doesn't use, the session's prefix hasn't changed at all, and the person isn't asked. Starting a new turn in an idle session (`session.send`, `session.redo`, or a `command.run` that starts a turn) without `prefix` is refused with `prefix_changing`: `data.files` lists the changed files that actually go into this session's prefix (as paths relative to the data root, at most 20), and `data.more` counts the rest. A session that has just switched persona or preset was compacted at that point and isn't asked again. The head offers the person "Send", "Compact and send" and "Cancel", and once the person chooses, sends again with `"prefix": "keep"` or `"compact"`. `compact` compacts first and then sends; if the context can't be compacted, you get the compaction's refusal (for example `nothing_to_compact`), and the message is not sent. A batch of changes that was let through is not asked about again.

```json
→ {"jsonrpc":"2.0","id":"m1","method":"session.send","params":{"session":"01a14aca-…","text":"Look at this image","attachments":[{"blob":"sha256:9f86d0…","name":"shot.png","media_type":"image/png"}]}}
← {"id":"m1","jsonrpc":"2.0","result":{"cwd":"~/src/miyu","events":[42]}}
```

A path-only attachment:

```json
→ {"jsonrpc":"2.0","id":"m2","method":"session.send","params":{"session":"01a14aca-…","text":"Have a look at this image file","attachments":[{"path":"/home/alice/Downloads/disk.iso","name":"disk.iso","size":31457280}]}}
← {"id":"m2","jsonrpc":"2.0","result":{"cwd":"~/src/miyu","events":[47]}}
```

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | An attachment is missing fields or is malformed; a path-only attachment was sent to a venue session; `from` is not a string, or is empty after control characters are removed |
| `empty_message` | There is no text and no attachment |
| `unknown_attachment` | An attachment's blob isn't in the core |
| `attachment_too_big` | An attachment is an image over the limits |
| `venue_session` | A message was sent into a venue session without `as` |
| `shell_not_allowed` | The `shell` command wasn't typed by the person in a head: it came with `from` or `as`, from an extension, or into a venue session |
| `shell_unavailable` | With `shell`, no installed package has a tool that runs commands (none is installed, or it is turned off) |

## `session.interrupt`

**Params**: `session`; `queued` (required): what to do with queued messages that haven't been sent yet: `send` sends them right after the interrupt, `return` hands them back, and `keep` keeps them without sending.

**Response**: `{"events": [<the events appended>…]}`.

**Errors**: `not_running`: no turn is running.

## `session.withdraw`

Takes back one queued message that the AI hasn't heard yet, without interrupting the turn.

**Params**: `session`; `message` (optional): which message to take back, given as the seq of its `message.user`; when it is omitted, the latest one is taken back.

**Response**: `{"events": [<the seq of the message.withdrawn>]}`. The push is the same as when `session.interrupt` hands messages back: one `message.withdrawn` whose `messages` holds just this message; the view marks that message `withdrawn: true`. The turn keeps running, and when it is done, the remaining queued messages start the next turn.

**Errors**: `already_heard`: the named message isn't in the queue, because a request already took it (or it started the next turn); `nothing_queued`: no message was named and nothing is queued.

## `session.tools`

Shows the tools the AI's next request will carry.

**Params**: `session` (optional; without it, the result is what a new session would get); without `session` you may pass `persona` (`null` for no persona) and `preset` (`null` for no tools), the same as in `session.create`.

**Response**: `{"tools": [{"name", "source": {"kind", "id", "name"}, "summary"?}]}`, in the order the tools are sent to the model (the byte order of their names). `kind` is one of `builtin`, `package`, `mcp` and `script`; `source.name` follows the connection's language. Only scripts have `summary`. Tools are always sent in full, so there is never a `loaded: false` for tools that show only their names.

```json
{"tools":[{"name":"edit","source":{"kind":"builtin","id":"basesystem","name":"Base system"}},{"name":"mcp__notes__search","source":{"kind":"mcp","id":"notes","name":"notes"}}]}
```

**Errors**: `bad_params` (`session` was given together with `persona` or `preset`); and the errors for looking up the session.

## `session.context`

Shows which parts this session's context is made of right now: how much the system prompt, tool definitions, example dialogue, checkpoint summary and conversation each take. The core computes this only when the method is called, and it doesn't affect the session.

**Params**: `session` (optional; without it, the result is the context a new session would get); without `session` you may pass `persona` (`null` for no persona) and `preset` (`null` for no tools), the same as in `session.create`.

**Response**: `{"window"?, "line"?, "context"?, "used"?, "basis", "anchor"?, "estimated_total", "parts": [...]}`. `window` and `line` are the context window (the window in effect when a context limit is set) and the compaction line (absent before the limits are known); `context` is the session's context limit (absent when it isn't set); `used` is how much is in use right now, measured the same way as in the status bar; `basis` is `measured` (counted from the `anchor` the provider reported for the latest request) or `estimated` (all local estimates). Each item of `parts` is `{"part", "label", "tokens", "children"?}`: `part` is a stable id, `label` follows the connection's language, and parts of 0 are left out. When there is `used`, the parts are already scaled so that they add up to exactly `used` (parts scaled to 0 are left out); `estimated_total` is the sum of the local estimates before scaling.

The part ids are: `system` (with, in composing order, `system.persona`, `system.venue`, `system.group`, `system.profile`, `system.project`, `system.core`, `system.clicall`, `system.show`, `system.skills`, `system.knowledge`, `system.style_lock`, `system.appended:<package>`; in older sessions, the stretches that no longer match the current text are merged into `system.other`), `tools` (with `tools.builtin`, `tools.package:<package>`, `tools.mcp:<service>`, `tools.scripts`), `demos`, `summary`, `messages` (with `messages.user`, `messages.assistant`, `messages.memory` (with `messages.memory.resident`, `messages.memory.recall`), `messages.knowledge`, `messages.facts`, `messages.project_docs` (the repository's AGENTS.md), `messages.reports` (reports from subagents and background commands), `messages.tool_results`). The `label` of a package or service is its own name.

```json
{"window":128000,"line":102400,"used":45231,"basis":"measured","anchor":41000,"estimated_total":43800,"parts":[{"part":"system","label":"System prompt","tokens":6100,"children":[{"part":"system.persona","label":"Persona","tokens":4300},{"part":"system.core","label":"Core instructions","tokens":900},{"part":"system.skills","label":"Skills","tokens":900}]},{"part":"messages","label":"Conversation","tokens":37700,"children":[{"part":"messages.user","label":"Your messages","tokens":4200},{"part":"messages.assistant","label":"AI replies","tokens":33500}]}]}
```

**Errors**: `bad_params` (`session` was given together with `persona` or `preset`); the errors for looking up the session; `internal` when the context of a new session can't be composed.

## `session.usage_parts`

Shows how much this session has used so far, split into the same parts as `session.context`, plus one more part for AI output. Only main requests are counted; for compaction, subagents, recaps and other uses, query `usage.query` by use.

**Params**: `session` (required); `tree` (boolean, optional): also counts the subagent sessions it dispatched.

**Response**: `{"requests", "input", "output", "parts": [...]}`. `requests` is the number of main requests, `input` is the sum of the reported input (uncached, cache read, cache write), and `output` is the sum of the output. `parts` are the same as in `session.context`, with a final `output` part added; together they add up to exactly `input + output`. Each request's input is split by the share each part had at that moment, and then summed; cached and uncached input are not split separately, so some cached input is counted against newer content.

```json
{"requests":503,"input":80000000,"output":203822,"parts":[{"part":"system","label":"System prompt","tokens":220000},{"part":"tools","label":"Tool definitions","tokens":1900000},{"part":"messages","label":"Conversation","tokens":77880000},{"part":"output","label":"AI output","tokens":203822}]}
```

**Errors**: `bad_params`; and the errors for looking up the session.

## `session.quota`

Shows the quota of the provider this session will send its next request to: how much of each window is used and when it resets, or how much money is left on the account. Only providers whose quota can be queried have this (for now, opencode Go's windows and official DeepSeek's balance), and the head's usage panel draws from it. After each turn of the session, the core checks once in the background, and for the same provider it reuses the previous result within 60 seconds. It checks the provider in `model.endpoint` of the `subscribe` response: if the session has just switched models and hasn't started a new turn yet, that is the provider it switched to (when it switched to a pool, there is none until the next turn starts).

**Params**: `session` (required).

**Response**: `{"windows": [...]}`, in the order `rolling`, `weekly`, `monthly`; windows the provider didn't report are left out. Each item has `id` (`rolling` is the rolling 5-hour window, and the other two are `weekly` and `monthly`), `label` (in the connection's language: `5 hours`, `Weekly`, `Monthly`), `percent` (how much is used, as reported, possibly with decimals), `status` (the provider's status, as reported, for example `ok`) and `resets_at` (when it resets). If this provider's quota can't be checked (not supported, a rotating pool, unreachable, or a bad reply), the response is `{}`, not an error.

```json
{"windows":[{"id":"rolling","label":"5 hours","percent":4,"status":"ok","resets_at":"2026-11-14T08:31:28.000Z"},{"id":"weekly","label":"Weekly","percent":12,"status":"ok","resets_at":"2026-11-17T00:00:00.000Z"},{"id":"monthly","label":"Monthly","percent":30,"status":"ok","resets_at":"2026-12-01T00:00:00.000Z"}]}
```

With an official DeepSeek provider (no address written, or an address whose host is `api.deepseek.com`), the response is the balance, `{"balance": {...}}`, and this field is left out when the balance couldn't be checked: `available` (whether it can be used, as DeepSeek says) and `items` (one per currency, in DeepSeek's order: `currency` is the currency, `total` the total, `granted` the granted amount and `topped_up` the topped-up amount, every amount being the string DeepSeek wrote). Providers that run DeepSeek models through a relay, and providers whose address is written as an environment variable, get no balance check, because that key isn't an official DeepSeek key. `windows` and `balance` are independent: having one doesn't affect the other.

```json
{"balance":{"available":true,"items":[{"currency":"CNY","total":"12.34","granted":"2.00","topped_up":"10.34"}]}}
```

A response with `windows` or `balance` also has `provider`: `{"id", "name"}`, which says which provider was checked: `id` is that provider's id in the config, and `name` is the name shown to people (`providers.<id>.name` when the config sets it; otherwise the name of the matching catalog provider; otherwise the id; the same as `name` in `model.list`). Heads use it to show "{provider} quota" and "{provider} balance", instead of guessing from the current model they remember. A `{}` response doesn't have this field.

```json
{"provider":{"id":"deepseek","name":"DeepSeek"},"balance":{"available":true,"items":[{"currency":"CNY","total":"12.34","granted":"2.00","topped_up":"10.34"}]}}
```

**Errors**: `bad_params`; and the errors for looking up the session.

## `session.answer`

When the AI does something that needs approval, it stops and asks (pushed as `tool.approval_requested`); when the AI asks a question with `ask_user`, it waits too (pushed as `question.asked`). This method answers both. If an approval request has `expires_at` and no one has answered by then, it is denied automatically (set by the config `permission.confirm.timeout`, 5 minutes by default); questions wait forever.

**Params**

| Name | Type | Notes |
|---|---|---|
| `session` | string, required | Which session |
| `call` | string, required | That call's `call_id` |
| `decision` | `once`, `session`, `deny` | Answers an approval request: allow this once, allow for this whole session, or deny |
| `reason` | string | Why it was denied, which the AI can see; only allowed with a denial |
| `attachments` | array | Images or files attached to a denial, in the same shape as in `session.send` (`blob`, `name`, `media_type` from `blob.put`, optionally `path`); the AI gets them together with the reason; only allowed with a denial |
| `answers` | array | Answers questions: one item per question, in order, `{"picked": [chosen option labels…], "text": <written answer>, "notes": <note>, "attachments": [<as above>]}`, where every field is optional; the attachments go to the AI with that question |
| `nested` | positive integer | When a tool the AI calls with `miyu call` inside a command needs approval, the request carries `nested` (its number), and you send it back as it is. Leaving it out also works, and then the answer goes to the one that is waiting under that command |

Give exactly one of `decision` and `answers`. **Response**: `{"events": [numbers…]}`.

**What choosing `session` remembers**: it remembers the pushed request's `rule` (without a `rule`, `session` can't be chosen, and choosing it returns `no_rule`). The approval requests the core sends now never carry a `rule` (this covers commands, risky commands, installing packages and extension guards), so they can only be allowed once or denied. Reading another program's private folder in read-only mode used to carry one (the folders allowed for reading), and that went away together with private folders. Heads offer "allow for this session" only when there is a `rule`.

```json
{"read":["/home/me/.ssh"],"tool":"read"}
```

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | `decision` and `answers` were both given, or neither was; `reason` or top-level `attachments` were given with answers to questions; `decision` is not one of the three values; an attachment is missing a field or is malformed |
| `unknown_attachment`, `attachment_too_big` | The same as in `session.send`: the attachment's blob doesn't exist, or it is too big |
| `not_asking` | The call isn't waiting for an answer: it was already answered, it has finished, it is waiting for the other kind of answer, or it is past the request's `expires_at` and was already denied automatically |
| `no_rule` | `session` was chosen, but this approval has no scope that can be remembered |
| `unexpected_reason` | The request was allowed, but a reason or attachments were given |
| `bad_answer` | The answers don't match the questions: the count is wrong, an option doesn't exist, or several options were picked on a single-choice question |

## `session.revert`, `session.unrevert`

Undo takes the last turn (or every turn from a given turn on) out of the conversation; files the AI changed are left as they are. Restore takes back the last undo.

**Params**: `session`; `revert` also takes `turn`: which turn to undo from (that turn's `turn.started` number); when it is omitted, the last turn is undone.

**Response**

| Name | Notes |
|---|---|
| `events` | The events appended this time: `turn.reverted` or `turn.unreverted` |
| `cwd` | The session's working directory (its real path) |
| `turns` | How many turns were undone (or restored) |
| `said` | The first line of what the person said in the first of those turns; omitted when there is none |
| `compactions`, `clears` | Undo only: how many compactions and clears were inside the undone turns; the context is back to the state before them. Omitted when 0 |
| `jobs` | Undo only: the background jobs that were stopped, `[{"job", "what", "title"}]`; omitted when there are none |

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | `turn` is 0 |
| `turn_running` | A turn is running, so interrupt it first |
| `nothing_to_revert` | There are no turns at all |
| `unknown_turn` | That turn isn't in the current history |
| `nothing_to_unrevert` | There is nothing to restore: nothing was undone, or a new turn has started or a compaction has happened since the undo |

## `session.redo`

Undoes the last turn and sends the messages that started it again, which starts a new turn. Editing your last message in the web interface also goes through this method.

**Params**: `session`; `text`: replaces the text of the message that started the turn (when it is omitted, the original text is kept); `attachments`: replaces that message's attachments (when it is omitted, the original attachments are kept; an empty array removes them); `prefix`: the same as in `session.send` (**Prefix changing**).

**Response**: the same as for undo; `events` ends with the numbers of the resent messages. The new turn's `turn.started` has this request's `id` as `cause`.

**Errors**: `not_redoable` (the last turn wasn't started by a person speaking, or there are no turns), `turn_running`, `empty_message` (nothing is left after the replacement), the attachment errors of `session.send`, and `prefix_changing`.

## `session.compact`

**Params**: `session`; `instructions`: what the person asks for, for example "keep the database design discussion".

**Response**: `{"events": [<that turn's turn.started number>]}`, returned as soon as the compaction starts, without waiting for it to finish. Progress arrives in the pushes as `compaction.progress`, `compaction.done`, `context.compacted` and `turn.ended`.

**Errors**: `turn_running`; `nothing_to_compact` (there is nothing new since the last compaction).

## `session.clear`

Clears the context: the core starts a turn that only records an empty checkpoint, with no model request. The to-do list is cleared too.

**Params**: `session`. **Response**: the same as for `session.compact`; by the time the response arrives, that turn's start, the empty checkpoint and the turn's end have already been pushed. If you undo that turn, the context comes back to the state before the clear.

**Errors**: `turn_running`; `nothing_to_clear` (the context is already empty).

## `session.recap`

Writes a one-line recap: what this session is doing, what is done and where it is stuck. The core sends a separate model request that is fed only the last few turns.

**Params**: `session`. **Response** is `{"text", "upto", "cached"}`: the recap line, the event it covers up to, and whether it is the previous recap returned again (nothing new has happened since, so no request was sent).

When the recap is written, every head subscribed to the session first receives `model.called` (`purpose` is `recap`) and `session.recapped`.

**Errors**: `nothing_to_recap` (the AI hasn't said anything yet); `recap_failed` (the request failed, or the reply had no text).

## `session.set_permission_level`

**Params**: `session`; `level`: only `full` (fully open); `read_only`: the read-only switch. Write the one you want to change, and give at least one.

Both modes can read the same things, the data root included (`etc/private/secrets.toml` too); read-only mode adds only one rule: nothing can be written anywhere, and commands run in a read-only sandbox. In fully open mode, the data root can be written like any other folder; only deleting the whole data root (by a command or by `trash`, including commands that move the whole data root away or into the trash) makes the core ask the person first, as the delete kind of "protected commands", and the deletion runs only once the person allows it; files inside the data root are handled like files anywhere else.

**Response**: `{}`. A change is pushed as `session.policy_changed`: `permission` is the new setting and `from` the setting before it, so a head can draw the messages before this event without reading further back (older logs have no `from`). Tightening takes effect at once; loosening takes effect from the next request. Whether to ask the person before switching to fully open is up to the head.

**Errors**: `bad_params`: neither was given; or `level` is not `full`.

## `session.set_workspace`

**Params**: `session`; `cwd`: the new working directory (an absolute path, or one starting with `~`); `dirs`: the new extra directories, which replace all of the old ones (an empty array removes them all). Give at least one.

If `cwd` is the workspace folder itself (`host.workspace` from the handshake), it means going back to this session's own default workspace: the core replaces it with the default workspace (the `default_workspace` in the session list and the subscribe reply).

**Response**: `{"cwd", "dirs"}`, with `wide: true` added when the directory is too wide. A change is pushed as `session.workspace_changed`; the turn in progress keeps the old directory, and the next turn starts with the new one.

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | Neither was given |
| `path_unreadable` | The directory doesn't exist or can't be read |
| `not_a_directory` | The path is a file |
| `path_forbidden` | The directory is inside Miyu's data directory (except the workspace folder `workspace/`) |
| `dir_too_wide` | An entry in `dirs` is too wide |

## `session.terminal`, `session.set_terminal`

The terminal session is the one long-running session that what you say in the shell goes into (used by shell integration). There is one by default, and one per terminal for calls that carry a `terminal` key; the core decides which session counts as the terminal session and when a new one starts.

**`session.terminal`** takes these params: `cwd` (optional): where a new session starts when one is needed; without it, the default workspace is used. `fresh` (optional, default false): when true, the core starts a new session as in rule 3 below and points at it, whatever is pointed at now (this is `/new`). `terminal` (optional): which terminal, given as a key the head makes up, 1 to 128 characters with no control characters (anything else is refused with `bad_params`); with it, the core keeps a separate pointer for each key, and without it the original pointer is used. `create` (optional, default true): when false, the call only asks and doesn't start anything: in cases 2 and 3 below the response is `{"session": null}`, no session starts and the pointer doesn't move (this is for showing which session a freshly opened terminal is in before anything is said); together with `fresh: true` it is refused with `bad_params`. The response is `{"session"}`, decided by these rules:

1. If the session pointed at still exists and is a local main session (not a child, venue or one-shot session), that session is returned.
2. If it has been idle longer than `terminal.idle_new_after` minutes (0 means it is never replaced), a new session starts, the pointer moves to it, and the response adds `renewed: {"last"}` (when the old session last had an event); the old session is left as it is. The moment a session is pointed at (with `session.set_terminal`, or by being started) also counts as activity: if you switch to a session that has been quiet for a long time, its idle time counts from the switch.
3. If nothing has been pointed at yet, or the session pointed at was deleted or doesn't qualify, a new session starts and the response adds `created: true`.

A new session uses `terminal.persona` and `terminal.preset` (when they aren't set, it follows `persona.default` and `preset.default`). When a new session would need to start and `cwd` is inside the data root (and outside its `workspace/`), the core doesn't start one and doesn't move the pointer, and refuses the request with `path_forbidden`, the same way `session.send` refuses that directory; when the session pointed at still exists and no new one is needed, that session is still returned. If several connections ask at the same moment (with the same key), only one session starts. Each key remembers when it was last used; keys unused for 7 days are dropped when a pointer is written, and at most 64 keys are kept (the least recently used go first). A dropped key that is used again starts over as if it had never pointed at anything.

**`session.set_terminal`** takes these params: `session`: point the terminal session at this session (the one picked in `/sessions`). `terminal` (optional): whose pointer to change, written as above. Only local main sessions are accepted; any other session is refused with `session_not_found`. The response is `{"session"}`.

## `session.set_meta`

**Params**: `session`; `title`: the new title, 1 to 200 characters, and `null` removes the title; `pinned`: `true` pins the session and `false` unpins it; `project`: a project id moves the session into that project, and `null` moves it out (only local main sessions can join a project: venue sessions, subagents and forks are refused with `bad_params`, with `data.field` `project`). Give at least one. Pinning and projects are separate fields: if a head wants to unpin a session when it is dragged into a project, the head sends `pinned` itself.

**Response**: `{}`. A change is pushed as `session.meta_changed`. For a session without a name, the core writes a title by itself after the first turn is answered, which is also pushed as `session.meta_changed` (`by` is the kernel).

**Errors**: `bad_params`: nothing was given; the title is empty or over 200 characters; `project` is an empty string, or this session can't join a project (`data.field` is `project`). `unknown_project`: there is no such project.

## `session.retitle`

Has the model write a new title from the latest part of the conversation. It uses the same instruction and the same model as the title the core writes by itself, and usage is recorded the same way (`model.called` with `purpose` `title`); the only difference is that it reads at most the last three answered turns (the automatic title reads only the first turn). Each turn carries only what the person said and the AI's final text answer; tool calls and reasoning are left out, and a turn the AI hasn't finished answering is not included. A title a person gave is replaced too; sessions created with `titles: false`, one-shot sessions, subagent sessions and venue sessions get a new title all the same.

**Params**: `session`.

**Response**: `{}`, returned as soon as the request is sent, without waiting for the model. The new title is pushed as `session.meta_changed` with `by` set to the person who asked, so it counts as a title a person gave: the session-list item carries `named`, and the core's automatic title never replaces it. If a title request is already on its way, nothing more is sent, and the response is still `{}`. A turn in progress is left out and isn't interrupted; if the AI's first turn hasn't finished, the title is written when that turn ends. If it fails (the model errors, hasn't finished 180 seconds after the request was sent, writes no title, or asks for a tool), the title stays as it is, a failed `model.called` is recorded, heads subscribed to the events stream get the transient event `session.retitle_failed` (see [Events](events.md#transient-events)), and the view stream gets a `retitle_failed` notice (see [View stream](view.md)), so the head can tell the person "Failed to change the title". If a person sets a title with `session.set_meta` after asking and before the new title arrives, the person's title is kept and nothing is pushed. When a title the core writes by itself fails, nothing is pushed.

**Errors**: `bad_params`: there is no `session`; or there is nothing to write a title from (the AI has no reply with text yet, and no turn is running). `session_not_found` when there is no such session.

## `session.viewing`

A head tells the core which session it is showing right now: send this on switching sessions, on opening a new session, and right after starting. It is for people's heads only; an extension that calls it gets `needs_approval`.

**Params**: `session`: the session being shown; `null` or omitted means no session is shown.

**Response**: `{}`. The core keeps one per connection and forgets it when the connection drops. While at least one head is showing a session, its session-list item carries `viewed: true`, and a change is pushed in `sessions.changed` the same way as `busy`. The head that is showing a background session shows that session's "answered", "asking" and "needs approval" notices as usual; other heads skip those notices when they see `viewed`, so several heads don't each pop one up.

**Errors**: `bad_params`; `session_not_found` when there is no such session.

## `session.configure`

Changes the session's model, multimodal model, persona, preset, reasoning effort or compaction line, which take effect from the next turn, or its context limit, which takes effect from the next request. A model or effort change shows at once, and requests use it from the next turn: `model` in the `subscribe` response and in `view.status` shows the new value right away, and it is also new after switching to another session and back, or after reconnecting.

**Params**: `session`; give at least one of the seven below:
- `model`: `<provider>/<model>` or `@<pool>`; `null` stops pinning a model and goes back to following the configured `models.chat` (read every turn from the config at that time, so a config change is followed). One of the three fixed pools (`@lite`, `@normal`, `@flagship`) given while it is empty is the same as `null`.
- `vision`: the model that describes images, written the same way as `model`: `<provider>/<model>` or `@<pool>`; `null` stops pinning one and goes back to following the configured `models.vision`; one of the three fixed pools given while it is empty is the same as `null`. When the session's model can't view images, the core has this model turn each image into text (without a pin, `models.vision` is used). If the pinned model later can't be resolved (its provider or pool was removed), that image counts as not turned into text; the core does not fall back to `models.vision`.
- `persona`: a persona id; `null` means no persona.
- `preset`: a preset id; `null` switches to no tools.
- `effort`: a reasoning effort level, checked against the levels of the session's model right now (`facts.reasoning` in `model.list`; when the same call also changes the model, the new model's levels). A session on a pool can't set it: you get `bad_params` (`data.field` is `effort`), and each member of the pool follows its own config; `null` goes back to following the config. It affects only this session: `providers.<id>.models.<model>.effort` in the config is the default for new sessions. On a model without that level the config is used, and switching back uses the level again.
- `context`: a context limit in tokens; `null` removes the limit. The window in effect is the smaller of the model's window and this limit (the limit alone when the model reports no window), and the compaction line is worked out from that window. The limit stays with the session, and is still used after model changes and pool member changes. If the limit is too small to give a compaction line, you get `bad_params` (`data.field` is `context`, and `data.min` is the least it accepts), and nothing changes. Typing `/context` changes this value too.
- `compaction_line`: the compaction line, a percentage of the window, an integer from 20 to 95; `null` stops pinning one and goes back to following the configured `compaction.line`. The session compacts automatically once the context reaches this line. The line still stays below the window minus the output reserve and a margin: with a 200K window anything above 85 has no effect, and only a 1M window can reach 95.

Changing the persona or preset compacts first: the core right away summarizes the conversation so far under the old persona, and the next turn switches to the new persona or preset and continues from the summary. Memory that follows the persona is kept in the new persona's room from this turn on; earlier memories stay in the room they were in.

**Response**: `{}`. A change is pushed as `session.policy_changed`; a model or effort change also pushes one `model.changed` right away (`why` is `turn`): a model carries `endpoint` and `model`, and `effort` only when it can be worked out; a pool carries only `ref`, and the window and compaction line stay as they were. When the next turn starts and the change actually takes effect, nothing more is pushed if it matches what was just pushed; otherwise one more `model.changed` is pushed (a pool has pinned a member, or the window changed). A context limit change shows at once in `limits` of the `subscribe` response and `view.status` (`window` is the window in effect, `context` the limit, absent when it isn't set). From then on, `model.effort` in the `subscribe` response and in `model.changed` is `{"level", "from"}`: `from` is `session` for the level the session recorded, and `system` for the config. `persona` and `preset` in `session.list` and the `subscribe` response show the new values right away (after switching to no tools, they show `preset: null` and `no_tools: true`). A pinned multimodal model shows at once as `vision` in `view.status`, and once the pin is removed it is absent. A pinned compaction line likewise shows at once as `compaction_line`, and `limits.compaction_line` follows it from the next turn.

**Errors**: `bad_params` (nothing was given, an empty string, or a wrong type; a subagent changing persona or preset, with `data.field` naming that field; an `effort` the session's model doesn't have, with `data.field` `effort`, and nothing changes; a `context` that isn't a non-negative integer; a `context` that is too small, with `data.field` `context` and `data.min` the least accepted, and nothing changes; a `compaction_line` that isn't an integer or is outside 20 to 95, with `data.field` `compaction_line`, and nothing changes); `unknown_model`: `model` or `vision` can't be resolved, and nothing changes; `unknown_persona`; `unknown_preset`; `turn_running`: a turn is running while the persona or preset is being changed (wait for the turn to finish).

## `session.fork`

Forks a child session from a main session: the child carries on from the main session's history up to the fork point, and its request prefix is byte-for-byte the same as the main session's, so the cache is reused.

**Params**: `session` (the parent, which must be a main session); `seal_after`: seal the child after it has run this many turns (counting from 1); when it is omitted, the child is never sealed.

**Response**: `{"session": <child id>, "upto": <fork point number>}`. If the parent is in the middle of a turn, the fork point is just before that turn.

**Errors**: `bad_params`: the parent is a subagent or a fork; or `seal_after` isn't an integer from 1 up.

## `session.delete`

Moves the session to the trash, where it is kept for 7 days. The child sessions it spawned are deleted with it.

**Params**: `session`. **Response**: `{}`, returned only once the session has been moved. Heads subscribed to it get `resync`.

**Errors**: `turn_running`: a turn is running (interrupt it first); `internal_error`: the session couldn't be moved.

## `session.prompts`

Lists everything you asked in a session, in order. Heads build a "jump to a prompt" list from it: for a prompt that isn't loaded yet, page back with `before` in `view.page` until its `seq` is on a page, and then jump to it. This method only reads the log; the session isn't loaded.

**Params**: `session`.

**Response**: `prompts`, with one item per prompt:

| Name | Notes |
|---|---|
| `seq` | The number of that `message.user` |
| `turn` | Its turn: for a prompt queued during a turn, that turn; for a prompt said while idle, the turn it started; omitted when it is neither |
| `at` | Its time, written the same way as an event's `at` |
| `text` | The first line, trimmed, at most 100 characters; for a prompt expanded from a slash-command template, the line you typed (the same rule as `preview` in `session.list`). It is empty when the prompt has only images or files |

- **Only what you said here is listed**: what you said locally and what a bridge relayed for you from a private chat on a platform are listed; messages from child or parent sessions, messages from other people on a platform (a group message recognized as yours still counts as from a platform person), injected messages (such as the rounds of a long-running goal), and messages handed in by other harnesses or by schedules aren't listed.
- **It follows the effective history**: reverted prompts are left out, unreverted ones come back, a redo (editing the last prompt) lists the final version, and withdrawn queued messages are left out; compacted prompts are still listed.
- **A forked session** lists only its own prompts; the prompts in the part it was forked from are listed in the parent.

**Errors**: `bad_params`; `session_not_found`; `session_broken`.

## `session.export`

Exports a session to a path you give, or into the reply: the raw bundle (ZIP) is for archiving, moving to another machine and debugging, and importing accepts only the raw bundle; Markdown is for people to read. This method is for people's heads only.

**Params**:

| Name | Notes |
|---|---|
| `session` | The session id |
| `format` | `bundle` is the raw bundle; `markdown` is Markdown |
| `to` | `{"path": "<absolute path>"}` makes the core write this file; `"inline"` puts the result in the reply's `text`, and works only for Markdown |
| `for` | Markdown only, who it is for: `read` is for reading it yourself (also the value when it is left out), `agent` is for another agent (such as Claude Code or codex), and `chat` is for pasting into a web chat |
| `range` | Markdown only, how much to export: `all` is everything (the default for `read` and `chat`); `context` is what the AI has in context now, from the latest compaction on (the default for `agent`); `{"turns": N}` is the last N turns |
| `thinking` | Markdown only, a boolean: whether to include thinking. When it is left out, it follows `for` (`read` includes it, and the other values don't) |
| `tools` | Markdown only, how much of each tool call to write: `line` writes one line; `seen` writes what the AI saw at the time; `full` writes everything, and also fetches background command output and what tools called from scripts returned. When it is left out, it follows `for` (`line` for `chat`, `seen` for the other values) |
| `children` | Markdown only, how to write subagents: `reports` (also the value when it is left out) writes their briefs and reports as `for` says; `append` also adds each subsession in full after the session, written the same way, in task order |
| `assets` | Markdown only, how to handle images and attachments: `placeholder` (also the value when it is left out) writes placeholders; `files` exports them too: they are copied into a `<file name>_files/` folder next to the Markdown and linked by relative path. It works only with `to: {"path"}` |
| `locale` | Markdown only: the language of display names and notes (`zh`, `ja`, and any other value means English); when it is left out, the language from the handshake is used |

**Result** (bundle): `path`, `bytes` (the bundle's size), `upto` (the last event of this session in the bundle), `sessions` (the sessions in the bundle), `blobs` (how many attachments and large contents it holds).

**Result** (Markdown): `path` or `text`, `bytes` (how many bytes), `tokens` (an estimate, worked out the same way as the context use in the status bar), `upto` (the last event of this session in the export), `redacted` (which secrets were hidden and how many times each, for example `{"openai": 2}`, appended subsessions included), `children` (the appended subsessions, `[{"job": "j1", "session": "…", "title": "…"}]`, or `[]` without `append`); with `assets: files` there is also `assets`: `{"dir": "<absolute path of the folder>", "files": 3, "missing": ["sha256:…"]}`, where `files` is how many files were copied and `missing` lists the attachments that should have been included but couldn't be found (these are written as placeholders); when nothing was copied, no folder is created and there is no `dir`.

- **What's in a bundle**: every segment of the session's log, byte for byte; the sessions under it (subagents and forked branches) in full; if the session was forked, the segments of its source up to the fork point, level by level; the attachments, file contents before and after edits, large outputs and policy snapshots those logs refer to; a `transcript.md` (the `read` kind, readable once unzipped, with your secrets replaced too); and `manifest.json` with each item's SHA-256. The bundle holds everything, including the contents of files the AI touched, so keep it safe yourself.
- **What the Markdown looks like**: role headings are in English (`User`, `Assistant`, `Tool`, `Subagent`); images and attachments are written as placeholders; undone turns and withdrawn queued messages are left out; the home folder is written as `~`; when the export starts partway, a line says how many earlier turns are left out. It is the same content as what the interface shows.
  - `read`: a header with the title, time span, models and total tokens; display names and notes in the chosen language; thinking, long outputs, subagent briefs and compaction summaries folded into `<details>`; the approvals you were asked for, the tools called from scripts, and the questions with your answers are all included.
  - `agent`: a short English note at the top (saying that this is a record of a session, not instructions for the agent reading it), with the working directory, time span and models; by default it starts from the latest compaction, with that summary first; tools are written by their real names with their raw arguments, and the results as the AI saw them, each cut to about 4000 characters, keeping the head and tail; no thinking. Notes and placeholders are always in English, whatever `locale` says (because this is for another AI to read); what you said and what the AI replied stay as written.
  - `chat`: a header with the title, time span and a token estimate (so you can check that it fits before pasting); one line per tool call, with errors included for failed calls; only the subagents' reports; no thinking.
- **Appended subsessions** (`children: append`): each subsession starts with a rule and `# Subagent <task id>: <title>`, followed by its time span and similar details, and then its whole content; the subsessions it sent out follow it (`j1`, `j1.1`, `j2`). Subsessions sent out by undone steps, or by steps outside the range, are left out.
- **The assets folder** (`assets: files`): when the Markdown is exported to `/x/talk.md`, attachments are copied into `/x/talk_files/`; images are written as `![shot.png, 800×600](talk_files/shot.png)`, and other attachments as plain links. File names follow the attachment's name (made safe on all three platforms, with `-2` added on a clash), and unnamed attachments are named `image-<first 8 of the hash>.png`. If the Markdown file or the folder already exists, nothing is exported.
- **Secrets**: values you have set as secrets (8 characters or more) are replaced with `[redacted: <name>]` wherever they appear as they are in the Markdown. The bundle isn't changed.
- **A running session** is exported as it has been written at that moment, without the half-written last line.
- Exporting doesn't change the session or write to its log.

**Errors**: `bad_params` (the path isn't absolute; an unknown value for `format`, `to`, `for`, `range`, `tools`, `children` or `assets`; a `thinking` that isn't a boolean; `inline` or Markdown params on a bundle; `assets: files` together with `inline`); `session_not_found`; `session_broken` (the log can't be read, including the log of an appended subsession; or an attachment doesn't match its hash); `export_exists` (the file already exists and isn't overwritten; an existing folder for `assets: files` also counts); `export_in_data_root` (the core won't write inside the data root); `export_unwritable` (the folder doesn't exist or can't be written); `export_too_big` (the content for the reply is over 512 KiB, so save it to a file instead).

## `session.import`

Imports a raw bundle made by `session.export`: use it to move sessions to another machine or another data root. The migration tool for the old Miyu also uses it. This method is for people's heads only.

**Params**:

| Name | Notes |
|---|---|
| `blob` | The bundle, uploaded first with `blob.put` |
| `path` | A bundle on this machine, given as an absolute path (used by the CLI); give only one of `blob` and `path` |
| `archive` | Boolean, default `false`: when true, the bundle is imported as a read-only archive |

**Result**: `main` (the bundle's main session), `sessions` (the sessions newly imported this time), `present` (the sessions that were already there and were skipped).

- **Checked before anything is written**: every item's hash and the log's sequence numbers must match before anything is written; if anything doesn't match, the whole bundle is refused, and the data root gains nothing.
- **Ids are kept as they are**: if a session with the same id and the same content already exists, it counts as already imported and is skipped; if the content is different, the import is refused. Importing the same bundle again changes nothing.
- **Archives** can be read, searched and exported, and the AI finds them when it searches past conversations; but they can't be continued: sending, reverting, compacting and other changes to the session return `archived`. A session marked as an archive in the bundle is still an archive after import. A session that isn't an archive can be continued right after import.
- Imported sessions can be searched right away, without opening them first. The session list gets a change pushed.

**Errors**: `bad_params`; `unknown_attachment` (the `blob` doesn't exist); `bad_bundle` (it isn't a session bundle); `bundle_mismatch` (the bundle is damaged); `bundle_too_new` (the bundle was made by a newer version); `session_exists` (a session with this id and different content already exists; `data.session` says which one).

## `view.page`

Reads history page by page, from the newest page back; each page's edges fall between two turns.

**Params**

| Name | Type | Notes |
|---|---|---|
| `session` | string, required | Which session |
| `before` | positive integer | Only events numbered below this; when it is omitted, the newest page is returned. To page back, pass the previous page's `first` |
| `turns` | 1 to 50, default 20 | The most turns to return |
| `view` | boolean, default `false` | `true` returns entries the interface can draw directly (the view projection) instead of raw events |

**Response**: `events` (or `entries`) and `more` (whether there is more before), plus `first` and `last` when the page isn't empty; `capped: true` when fewer turns came back to stay under 1 MiB; `jobs` for jobs that finished on this page but were started earlier; `broken` when a line in the middle of the log is broken and this page stops before that line.

The newest page's `last` is the last event right now: after that, `subscribe {"after": last}` gets only the new events.

`broken` is `{"segment", "line"}`: which log segment (file name only, such as `000000000001.jsonl`) and which line of it is broken. When the lines a page needs reach a broken line, the page reads as if the log ended just before that line; when the broken line is outside the lines this page reads, the page is returned as usual, without `broken`. Such a session can't be loaded, and sending and subscribing return `session_read_only`: the interface shows it read-only through `view.page` and says where it broke, and to go on, you start a new session. The core doesn't change or repair the log.

**Errors**: `bad_params`; `session_not_found`; `session_broken` (the log can't be parsed and there is nothing to show, for example when even the first line can't be read).

## `view.detail`

**Params**: `session`; exactly one of `call` (a tool call's `call_id`), `job` (a background job's id) and `compaction` (the number a compaction replaced up to); optionally `nested_after` (an integer): only the nested calls numbered above it, plus earlier calls that are still running.

**Response**

- A call: `{"files": [...], "output"}`. `output` is the full result text, not cut; `files` has one item per file: `path`, `action` (`write` or `trash`), `diff` (unified format, with 3 lines of context), `added` and `removed`; when no diff can be computed, `skipped` is given instead (`too_big`, `binary`, `missing`).
- A provider-side tool (a view step with `hosted: true`): `{"files": [], "output"}`, where `output` is the result the provider gave (cut when it is over 64 KiB, and then `output_cut: true` is added); a call without a result yet counts as no such call.
- A compaction: `{"summary"}`, the full summary text of that compaction.
- When a script called tools (`miyu call`): a call's response also has `nested`, and a job's response is just `{"nested"}`. There is one item per call, by number: `n` (its number), `name`, `title` (`{name, object}`, the display name in the connection's language), `args` (the raw arguments), `state` (`running`, `ok`, `error`, `denied`, `needs_approval`, `cancelled`), and, when present, `started` (when a running call started), `took_ms`, `reason` (the refusal or error message), and `result` (`{blob, bytes}`, the result the script got back, fetched with `blob.get`). A `shell` that is still running with no result yet also returns `{"nested"}`.

A call's result never changes, so asking once is enough; the nested calls grow while they run, and `nested_after` gets only the new ones.

**Errors**: `bad_params`; `session_not_found`; `unknown_call` (there is no result for that call, or no such compaction); `session_broken`.
