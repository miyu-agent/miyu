# Pushes

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

Pushes are notifications the core sends on its own, in the form `{"jsonrpc": "2.0", "method": <name>, "params": {…}}`: they have no `id`, and the receiver doesn't respond. Pushes only go to connections that subscribed to the matching stream (how to subscribe is in [Connection](connection.md)); extensions also receive a few notifications the core sends to them, described in [Extensions](extensions.md).

| Push | Stream | `params` |
|---|---|---|
| `event` | `events` | `{"session", "event"}`: one event of the session, passed on as-is (see [Events](events.md)); replayed events use this push too |
| `view.add`, `view.update`, `view.append`, `view.hidden`, `view.remove`, `view.status` | `view` | For details see [View stream](view.md) |
| `sessions.changed` | `sessions` | `{"session", "entry"}`: one item of the session list is replaced whole (it has the same content as an item of `session.list`); when a session is deleted, the push is `{"session", "removed": true}`. When a child session changes, the items of its parent and of every ancestor (whose `tokens` include their descendants) are pushed too, level by level. A push is also sent when a person speaks (when `last_spoken` changes), including a message added in the middle of a turn |
| `config.changed` | `config` | `{"layer", "via", "by"?, "version", "keys", "problems"}`: one config layer changed. `keys` is the same as in `config.set`'s response; `via` says where the change came from: `set`, `edit`, `file` (the file was edited by hand) or `package` (after installing or removing packages) |
| `models.changed` | `config` | `{"providers"}`: the model lists of these providers changed (a list the core fetched in the background differs from the one it had). The push carries no entries; when you get it, call `model.list` again with your own params. It is sent only when a list really changed; pushes missed because of slow reading are not replayed, so after `resync` or a reconnect, read everything again |
| `extension.changed` | `extensions` | `{"entry"}`: one extension's status, with the same content as an item of `extension.status` |
| `package.changed` | `packages` | `{"package", "entry"}`: one item of the package list; when the package no longer exists, `entry` is `null` |
| `package.progress` | No subscription needed: it is sent only to the connection that called `package.install` (a real install) | `{"package", "stage", "index", "count", "done"?, "total"?}`: `stage` says which step is running: `download` (with `done` and `total`, the bytes of the package file downloaded from the source so far and in all; sent once at the start and once at the end, and at most every 200 ms in between), `verify` (before checking) or `install` (before installing); `index` and `count` say which package this is and how many there are. Installing from a package folder or a package file sends only one `verify` and one `install`. Older cores push only `{"package", "done", "total"}`; treat a push without `stage` as `download` |
| `bus.changed` | `bus` | `{"names": […]}`: the whole list of names on the bus (the same as `bus.list`'s response). It is pushed when packages are installed or removed, extensions start or stop, or methods are registered; when you get it, replace your list with it |
| `projects.changed` | `projects` | `{"project": <item>}`: one project is replaced whole (with the same content as an item of `project.list`); when a project is deleted, the push is `{"project": <id>, "deleted": true}` |
| `prefs.changed` | `prefs` | `{"package", "values"}`: another connection changed a UI package's settings; `values` is the whole changed object, and you replace yours with it (see [A head's own settings](prefs.md)). The connection that made the change doesn't get this push, because its response already contains the whole object. When the subscription falls behind, the push is `resync {"stream": "prefs", "package"}` |
| `schedules.changed` | `schedules` | `{"id", "entry": <item>}`: one schedule is replaced whole (with the same content as an item of `schedule.list`; it is also pushed after the schedule runs); when a schedule is deleted, or a one-off schedule has finished, the push is `{"id", "removed": true}` |
| `package.event` | `package` | `{"package", "event", "data"}`: what a package pushed to people with `package.emit`; the package decides its shape. This push isn't stored on disk, so connections that aren't subscribed miss it; when the subscription falls behind, the push is `resync {"stream": "package", "package"}` |
| `notice` | `notices` | `{"kind", "at", …}`: a notice for people; heads (interface programs that connect to the core, such as the terminal interface and the web interface) show a system notification based on `kind`. `schedule.ran` is `{"schedule", "session", "ok"}`: for a schedule that opens a new session each time, it is sent when the turn in that new session ends, and `ok` says whether the turn finished (it is `false` after an error or an interruption); schedules that run in an existing session don't send it. `schedules.reset` means the schedule table broke: the core renamed it to keep it and put an empty table in its place, so the old schedules are gone. This push isn't stored on disk, so connections that aren't subscribed miss it |
| `notices.claimed` | `notices` | `{"claimed"}`: whether some connection has claimed sending background notices ([`notices.claim`](connection.md#noticesclaim)) changed. `true` means a connection has claimed it, so other heads stop showing system notifications for sessions nobody has open, and for `notice`; `false` means every claiming connection has left, so other heads show them as before |
| `kb.indexing` | `kb` | `{"kb", "done", "total"}`: a knowledge base is building its index, and `done` of the `total` documents to rebuild are finished. The first push is 0, the push for the last document is always sent, and in between it is sent at most every 0.1 s |
| `kb.indexed` | `kb` | `{"kb"}`: the index is built; read that knowledge base's current state again with `kb.list` |
| `mcp.changed` | `packages` | `{"name", "server"}`: one MCP server in the system config; when the server is removed, `server` is `null` |
| `widget.changed` | `widgets` | `{"package", "id", "widget"}`: one widget is replaced whole; it is `null` when the widget is turned off or removed |
| `memory.event` | `memory` | `{"event", "persona"? | "session"?}`: a new line in one memory's log |
| `memory.dreaming` | `memory` | `{"upto", "kind", …, "persona"? | "session"?}`: while organizing memory, a revision or removal the AI has just finished writing, or how far the summary has been written; this push isn't stored on disk and isn't replayed (see [`memory.dream`](memory.md#memorydream)) |
| `resync` | Every stream | `{"stream", "session"?}`: the subscription fell behind because of slow reading, or the session stopped. The subscription has now stopped, and you need to subscribe again |

**Ordering**

1. The pushes a command causes always arrive before that command's response.
2. Pushes always carry whole items (`entry`), so repeated or late pushes are handled correctly by replacing items by id.
3. A widget is pushed at most every 250 ms, and only the newest content in that interval is kept.

**Falling behind**: the core doesn't wait for heads that read slowly. A session keeps at most 1024 pushes for each subscription, config at most 16, and memory at most 64; beyond that the core pushes `resync` and stops the subscription. When you subscribe again, pass the last sequence number you saw as `after` for sessions and memory to get back what you missed; the subscription responses of the other streams are already complete.
