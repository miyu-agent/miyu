# Attachments and file contents: `blob.*`

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

A blob is a piece of file content that the core stores, named by its content hash (`sha256:` plus 64 lowercase hex digits): the same content always has the same hash, and it is stored only once however many times you store it. Images and files people attach to messages, and images that extensions hand back, are all stored as blobs first and then used by their hash.

| Method | What it does |
|---|---|
| [`blob.put`](#blobput) | Uploads a file in one go (local heads give a path, remote ones give the content; a head is an interface program that connects to the core, such as the terminal interface or the web interface) |
| [`blob.open`, `blob.write`, `blob.close`](#blobopen-blobwrite-blobclose) | Uploads a large file in chunks |
| [`blob.get`](#blobget) | Reads a blob in chunks |
| [`session.shown`](#sessionshown) | Reads a file the AI showed, in chunks |

An attachment is at most 20 MiB (20,971,520 bytes). A larger file isn't uploaded; instead, you hand over only its path on the core's machine in the `attachments` of [`session.send`](sessions.md#sessionsend) (`{"path", "name", "size"?}`, see item 3 there).

## `blob.put`

This method stores a file and returns its hash and what it was recognized as.

**Who can call**: people, extensions. A blob that an extension stores can be read by that extension later without a `session` (see `blob.get`).

**Params**

| Name | Type | Notes |
|---|---|---|
| `path` | string | An absolute path to a local file, or a path starting with `~` or `~/…`. The core reads the file itself |
| `data` | string | The file content in standard base64 (padded with `=`). Remote heads use this parameter |
| `name` | string | The file name (just a name, without directories). It is optional with `path`, in which case the last segment of the path is used; it is required with `data` |
| `media_type` | string | The media type, such as `text/markdown`. When it is omitted, the type is recognized from the content |

Give exactly one of `path` and `data`. Because `data` sits on one line and a line is at most 1 MiB, it can hold only a bit over 700 KiB; use a chunked upload for anything bigger.

**Response**

| Name | Notes |
|---|---|
| `blob` | The content hash |
| `name` | The file name |
| `media_type` | The recognized media type |
| `kind` | `image` or `file` |
| `width`, `height` | Images only: the width and height in pixels |

```json
→ {"jsonrpc":"2.0","id":"c3","method":"blob.put","params":{"path":"~/Pictures/shot.png"}}
← {"jsonrpc":"2.0","id":"c3","result":{"blob":"sha256:9f86d0…","height":600,"kind":"image","media_type":"image/png","name":"shot.png","width":800}}
```

**How the type is recognized**: from the content only, never from the extension.

1. PNG, JPEG, GIF and WebP files whose size can be read are recognized as images, with the recognized media type. Images are at most 5 MiB and at most 8000 pixels on each side.
2. Content that starts with `%PDF-` is recognized as `application/pdf`.
3. Anything else takes the `media_type` you gave; without one, content that is entirely valid UTF-8 text is `text/plain`, and anything else is `application/octet-stream`. If you give `application/pdf` or `image/…` as the `media_type` and the content doesn't match, the type you gave is ignored.

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | Both or neither of `path` and `data` were given; `path` is relative; `data` isn't base64; `data` was given without `name`; `name` or `media_type` is malformed |
| `attachment_in_data_root` | `path` is inside Miyu's data directory; files in an extension's own package folder don't count (this is judged by the real path, so a link pointing outside is still refused) |
| `attachment_unreadable` | `path` doesn't exist, isn't a regular file, or can't be read |
| `attachment_too_big` | The file is over 20 MiB, or an image is over 5 MiB or over 8000 pixels on a side |
| `internal_error` (`-32603`) | The core couldn't store the file |

Reasons without a code in the table are `-32010`.

## `blob.open`, `blob.write`, `blob.close`

These methods upload a file in several chunks and store it as a blob; the result is the same as with `blob.put`. Remote heads use them for big files.

**Who can call**: people, extensions.

| Method | Params | Response |
|---|---|---|
| `blob.open` | `name` (required), `media_type` (optional), `size` (required, the total number of bytes) | `{"upload": "<upload id>"}` |
| `blob.write` | `upload`, `offset` (counting from 0), `data` (base64, at most 512 KiB per chunk) | `{"received": <bytes received so far>}` |
| `blob.close` | `upload` | The same as the response of `blob.put` |

```json
→ {"jsonrpc":"2.0","id":"u1","method":"blob.open","params":{"name":"notes.pdf","size":1048576}}
← {"jsonrpc":"2.0","id":"u1","result":{"upload":"5f0c2a9b7e41d3c8"}}
→ {"jsonrpc":"2.0","id":"u2","method":"blob.write","params":{"upload":"5f0c2a9b7e41d3c8","offset":0,"data":"JVBERi0x…"}}
← {"jsonrpc":"2.0","id":"u2","result":{"received":524288}}
→ {"jsonrpc":"2.0","id":"u4","method":"blob.close","params":{"upload":"5f0c2a9b7e41d3c8"}}
← {"jsonrpc":"2.0","id":"u4","result":{"blob":"sha256:…","kind":"file","media_type":"application/pdf","name":"notes.pdf"}}
```

1. Each chunk's `offset` must equal the number of bytes received so far; otherwise you get `upload_offset`, where `data.received` says how much has arrived, and you continue from there.
2. An upload id works only on the connection that opened it. It expires when the connection closes, after 60 seconds without a `blob.write`, and after `close`; the staged content is then deleted.
3. A connection can have at most 4 uploads open at once.

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | `name` or `media_type` is malformed; `data` isn't base64, is over 512 KiB, or goes past `size` |
| `attachment_too_big` | `size` is over 20 MiB, or at `close` an image is over the limits |
| `too_many_uploads` | This connection already has 4 uploads open |
| `upload_offset` | The `offset` is wrong; the error also has `data.received` |
| `upload_incomplete` | `close` came before everything arrived; the error also has `data.received` |
| `upload_unknown` | The upload id is unknown or expired, or another connection opened it |
| `internal_error` (`-32603`) | The core couldn't store the file |

## `blob.get`

This method reads part of a blob.

**Who can call**: people and extensions, but what each can reach is different:

- **People**: without `session`, any blob; with `session`, the session must be a local session, your own private chat, or a confined group chat or stranger's private chat (you can view those read-only, as with the sessions themselves; see "The owner viewing venue sessions" in [Venues](venues.md)).
- **Extensions, without `session`**: only blobs the extension stored itself (with `blob.put` or a chunked upload), and hashes in responses it got back from calling another package (`bus.call`) that the answering package can read itself. What it stored itself stays readable after the core restarts; what it got back from another package lasts only until the core restarts, so it has to get it again after that. Removing and reinstalling the package starts everything over.
- **Extensions, with `session`**: the session must be one the extension can see, and the blob must be referenced in that session (images and files in messages and tool results, and images that were sent out); a hash merely written in some text doesn't count.

**Params**

| Name | Type | Notes |
|---|---|---|
| `blob` | string, required | The content hash |
| `session` | string | Looks the blob up through this session |
| `offset` | integer, default 0 | The byte to start reading at |
| `length` | integer, default 524288 (512 KiB) | The most bytes to read, at most 512 KiB; 0 asks only for the size |

**Response**: `data` (this part, in base64) and `size` (the total number of bytes). Reading stops at the end; if `offset` is past the end, `data` is empty.

```json
→ {"jsonrpc":"2.0","id":"g1","method":"blob.get","params":{"blob":"sha256:9f86d0…","offset":0,"length":4}}
← {"jsonrpc":"2.0","id":"g1","result":{"data":"iVBORw==","size":48213}}
```

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | `blob` isn't a content hash; `session` is malformed; `length` is over 512 KiB |
| `unknown_blob` | There is no such blob, or this connection can't read it. The two cases aren't told apart, so that nobody can use this error to probe whether a blob exists |
| `internal_error` (`-32603`) | The core couldn't read it |

## `session.shown`

Files the AI shows with `show` aren't stored as blobs: the core only records the file's real path on the core's machine, its size and its modification time (the `shown` of the tool entry; see [View](view.md)).

- **Local heads** (connections whose hello response has `host`): read the file at `shown.path` straight from disk; you don't need this method.
- **Remote heads** (connected over the LAN through the web app): they can't reach that computer's disk, so they read through this method by "session + the step's call id", in chunks. Video and audio can be streamed as they play: when the user seeks, compute `offset` and `length` for the part you need (like HTTP Range). For a very large text, read only the start as a preview. The core doesn't cut anything for you; you decide how much to fetch.

**Who can call**: people and extensions, with the same reach as `blob.get` with `session`: people can read files shown in local sessions, in your own private chat and in confined venue sessions; extensions need a session they can see.

**Params**

| Name | Type | Notes |
|---|---|---|
| `session` | string, required | The session id |
| `call` | string, required | The call id of the step that showed the file, which is the tool entry's `call` |
| `offset` | integer, default 0 | The byte to start reading at |
| `length` | integer, default 524288 (512 KiB) | The most bytes to read, at most 512 KiB; 0 asks only for the size |

This method takes no path: it reads only the file that was recorded when that step showed it. Any other field is `bad_params`.

**Response**: the same as for `blob.get`: `data` (this part, in base64) and `size` (the total number of bytes). Reading stops at the end; if `offset` is past the end, `data` is empty.

```json
→ {"jsonrpc":"2.0","id":"s1","method":"session.shown","params":{"session":"0193…","call":"call_12_1","offset":1048576,"length":524288}}
← {"jsonrpc":"2.0","id":"s1","result":{"data":"AAAAIGZ0eXBpc29t…","size":734003200}}
```

Before every read, the core checks the file's size and modification time: if they differ from what was recorded when the file was shown (because it was edited or replaced), the read is refused; if the file is gone, the read is refused too.

**Errors**

| `data.reason` | When |
|---|---|
| `bad_params` (`-32602`) | `session` or `call` is malformed; `length` is over 512 KiB; another field was given |
| `unknown_shown` | There is no such shown file: the session doesn't exist, this connection can't read it, or the step didn't show anything. These cases aren't told apart |
| `file_changed` | The file's size or modification time has changed. Heads show "The file has changed" |
| `file_gone` | The file is gone, or is no longer a regular file. Heads show "The file no longer exists" |
| `internal_error` (`-32603`) | The core couldn't read it |

Reasons without a code in the table are `-32010`.
