## 量尺

状态：施工 V-1（2026-10-10）；V-3 进 CI、加闸门（2026-10-11）；V-7 三家对比（2026-10-15）；V-27 三家对比照现在的样子跑（2026-10-30）；V-29 工具一步（2026-10-31）。

### 是什么

一个量性能的小程序 `miyu-perf`：照 `23-性能预算.md` 第一节的量法量核心这一边，原始数据和对照预算的表写进 `docs/perf/`。它是工具 crate，不属于任何一层，谁都不许依赖它（`01-架构.md` 第九节规则 5）。

### 在哪

| 文件 | 管什么 |
|---|---|
| `xtask/src/perf.rs` | `cargo xtask perf`：编 release 的 `miyu`、`miyu-sandbox`、`miyu-extract`（施工 K-5），再编量尺、跑它 |
| `crates/miyu-perf/src/main.rs` | 照先后量一遍，写结果 |
| `args.rs` | 参数 |
| `budget.rs` | 预算照 23 第二节的表读，判超没超 |
| `fake.rs` | 假模型服务；`fake/script.rs`：照剧本回工具调用（施工 V-29） |
| `cpu.rs` | 读核心花的 CPU：各线程的 `schedstat`；放进了自己的 scope 的再读 cgroup 的 `cpu.stat`，连子进程（施工 V-29） |
| `sandbox.rs` | 沙盒数据根，拉起、停掉核心 |
| `rpc.rs` | 在连接上说 JSON-RPC，等一轮结束 |
| `memory.rs` | 读进程的内存 |
| `machine.rs` | 量的条件 |
| `measure/startup.rs`、`sessions.rs`、`large.rs`、`stream.rs`（施工 V-22）、`append.rs`、`size.rs` | 每一项怎么量 |
| `measure/tools.rs`、`tools/calls.rs`、`tools/split.rs`、`report/tools.rs` | 工具一步（施工 V-29，下面「工具一步」）：量、量哪几种调用、照日志拆段、写结果 |
| `report.rs`、`report/raw.rs`、`report/rows.rs`、`report/load.rs` | 写原始数据、写表；从原始数据读回来（`--render`） |
| `report/gate.rs` | 闸门：有预算的几行和表照同一份（`rows::checks`），时间超过预算的倍数、内存超过预算的报错（施工 V-3） |
| `.github/workflows/ci.yml` 的 `perf` | CI 里每次都量一遍，表贴进那一次跑的摘要和日志，过不了闸门的这一项红（施工 V-3） |
| `stats.rs` | 分位数 |

### 对外的样子

`cargo xtask perf [参数]`，参数原样交给量尺，可以不写：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--runs` | 10 | 冷启动量几次 |
| `--sessions` | 10 | 小会话几个 |
| `--events` | 10000 | 大会话说到第几条事件 |
| `--tail` | 30 | 到了以后再说几轮 |
| `--reloads` | 20 | 重启核心再打开大会话几次：原来 5 次，p95 就是最慢的那一次，一个冷启动的异常值就让闸门红；20 次的 p95 才是真的 p95（施工 V-13，2026-10-20 项目主人定先把量法做稳，预算不动） |
| `--appends` | 2000 | 追加几条 |
| `--reply-bytes` | 3500 | 假模型每次回多少字节的正文 |
| `--streams` | 10 | 流式一轮（施工 V-22）：大会话上说几轮 |
| `--pieces` | 300 | 流式一轮：回答切成几块 |
| `--idle-wait` | 200 | 不订阅大会话以后等几秒再量内存 |
| `--out` | `docs/perf` | 结果写到哪 |
| `--render` | 不写 | 不量：照这一份原始数据（`.json`）、照 23 现在的预算重出同名的 `.md`，原始数据不动。只编量尺，不编 `miyu` |
| `--gate` | 不写 | 闸门的倍数（施工 V-3）：量完、表写好以后，有预算的哪一行时间超过预算的这么多倍、内存超过预算，报出来、退出码 1。不写的只出表 |
| `--tools` | 不写 | 工具一步（施工 V-29）：写了的只量这一场，每种调用量这么多次（另加头一次不计），别的几场不量 |
| `--tree` | `cargo xtask perf` 填源码树的 `crates/` | 工具一步拷进工作区的树（不拷 `target/`），`grep`、`glob` 在它里面找 |
| `--tools-log` | 不写 | 工具一步：核心的 `MIYU_LOG`；拆得更细写 `debug`（记日志本身也花一点，主数照不写的那一次） |
| `--tag` | 不写 | 工具一步：结果的文件名后面接 `-<标签>` |

结果：`docs/perf/<日期>-<系统>-<架构>.json`（原始数据）和同名的 `.md`（条件、表）。日期是 UTC。同一天再量一次，盖掉同名的。

预算改了（23 F1：实测后校准），用 `cargo xtask perf --render docs/perf/<那一份>.json` 重出表。

### 怎么走

1. 沙盒在 `target/perf/` 下，每次量之前删掉重建。不放系统的临时目录：那里常是内存盘，同步不算数。
2. 核心的环境照集成测试拉核心的那一套：不拉 models.dev 的目录，缓存目录放进数据根，不用 `$XDG_RUNTIME_DIR`，不走代理。核心空闲一小时才走，量的时候不会自己退出。
3. 系统配置里一家 `perf`（`openai-chat`），地址是假模型服务，模型 `perf/perf-model` 不在目录里，窗口照配置写成 200000（施工 V-2 上）：压缩线 170000，大会话照真用时那样到线就压，量的是压过的会话。V-1 没写窗口，会话一直不压，大会话的投影是把一万条事件整份组装，真用时到不了。
4. 假模型服务和量尺在同一个进程里，时刻可以直接比。每个 `POST` 回同一段字（正文一块、收尾一块带用量、`[DONE]`），别的请求回空的模型列表。用量照请求体、正文的字节数估，四个字节一个 token；带出厂摘要指令那一句的（摘要请求）回一段几百字节的摘要（施工 V-2 上）。它记下请求头读全的时刻：驱动编好整份请求体才发头，所以这个时刻包含组装和编码，不含请求体在回环上传多久。
5. 会话都关着记忆造（`memory: off`，2026-10-17 项目主人定）：这一组量核心自己。以前量尺的会话无人格、本来不接记忆；P-12 起无人格也有记忆，接上以后重启打开大会话 p95 114 ms、追加 p99 78 ms（本机，预算 50、20），这才看出开着记忆的会话一直超预算。开记忆的另量一组，用同样的预算卡（施工 V-9）：大会话再造一个开着记忆的（无人格，`memory: persona`），重启打开、投影、从头投影三行照同样的预算比，原始数据记在 `large_memory`。V-9 把回合索引挪到后台写（`miyu-session/src/memory/lane.rs`）：开回合库要跑一遍 `quick_check`，跟着人格的那一间越用越大，原来整笔压在打开会话上。
6. 每一句话带一个只此一句的记号，量尺照记号认出这一轮的主请求，起标题这些辅助请求跳过。请求编号整个进程里不重复：核心照编号认重发，造会话会交回上一次造的那一个、说话不再开一轮，连接换了、核心重启了都照认。每一次等最多 120 秒，等不到的报是在等什么。
7. 照先后量：
   1. **冷启动**：先空跑一次（第一次起来要建索引），再量 `--runs` 次。每次从拉起 `miyu core` 算起，记三个点：写来 `ready`、握完手、造好会话并订阅上（能提交第一轮）。每次量完停掉核心，等它放开数据根的锁。
   2. **热启动、每多一个会话**：造 `--sessions` 个小会话各说一句，重启核心。歇两秒量核心空闲的内存。再一个个新连上、握手、订阅（订阅时核心才载入它），记这一段。都订阅着、各再说一句，歇两秒量内存。最后再重启一次核心，歇两秒，像头那样连上、握手，照先后问一遍头起来时问的六样（`config.get`、`human.get`、`model.list`、`persona.list`、`preset.list`、`package.list`，参数都空着），歇四秒（核心最后一个请求过去 2 秒还内存，`heap.md` 第 2 条），连着量内存（施工 V-5 下）。
   3. **大会话**：造一个会话，一句一句说，直到说之前的事件数到了 `--events`，再说 `--tail` 轮。每一轮记说出去到模型收到请求、到推来 `turn.ended`。歇两秒量载着它的内存。断开连接，等 `--idle-wait` 秒（会话 actor 空闲 180 秒退出）再量一次。然后重启核心 `--reloads` 次：每次连上、握手、订阅大会话（从头读日志、重放），记这一段；再说一句，记到模型收到请求。最后一次歇两秒量内存。
   4. **流式一轮**（施工 V-22，`measure/stream.rs`）：重启核心、订阅关着记忆的大会话，假模型的回答切成 `--pieces` 块（`Fake::split_into`，一块一个事件，接起来是原文），先说一句不量（载入以后头一次从头投影），再说 `--streams` 轮：每一轮记核心进程花的 CPU（各线程 `/proc/<进程号>/task/*/schedstat` 头一格加起来，只有 Linux 上有）、说出去到 `turn.ended`。量完假模型换回一块。别的几场假模型一次回一整块，核心每收一块要做的活量不出来。
   5. **追加并同步**：在进程里，大会话日志里的事件从第一条起，一条一条追加进 `target/perf/append/` 下的一份新日志，每条写一次、同步一次，走会话 actor 落盘用的同一个函数。
   6. **二进制**：`miyu`、`miyu-sandbox`、`miyu-extract`（施工 K-5，知识库抽字的小程序，随主程序放在旁边）的字节数；拷一份 `strip` 以后再量，没有 `strip` 的平台不写。
8. 内存读 `/proc/<进程号>/smaps_rollup` 的 `Pss`、`Anonymous`、`Rss`，核心和它拉起的子进程各一行，子进程照 `/proc/<进程号>/task/*/children` 找。只有 Linux 上读得到，别的平台写「不量」。
9. 对照预算的表：
   - 预算照 23 第二节的表读，第一格是名字。只写了一个数的照 p50 比，写了分位的照那个分位比；内存照核心进程的 PSS 比。
   - 比的几项：

     | 表里的一行 | 量的是哪一段 | 照 23 的哪一行比 |
     |---|---|---|
     | 热启动：订阅一个没载入的小会话 | 连上、握手、订阅 | 热启动到能提交第一轮 |
     | 热启动：重启核心后打开大会话 | 连上、握手、订阅 | 热启动到能提交第一轮 |
     | 一次请求的投影 | 大会话到了以后的那几轮，收到 `session.send` 的回应（这一句落了盘才回）到模型收到请求：组装、编码、连接，不含落盘的同步（施工 V-2 中；以前量的是说出去到收到请求，同步占了大半） | 一次请求的投影（增量，一万条事件的会话） |
     | 从头投影 | 重启、打开大会话以后头一次说，同样从落了盘算到模型收到请求：没有投影缓存，这一次从头算 | 同一个会话从头投影一次 |
     | 追加一条事件并同步 | 每一条的写加同步 | 追加一步的事件并同步 |
     | 核心空闲 | 一个会话都没载入时核心的 PSS | 核心空闲、没有会话载入 |
     | 连着一个头 | 头起来时问的六样过去、安静下来以后核心的 PSS（施工 V-5 下） | 核心空闲、连着一个头 |
     | 每多一个活动会话 | 小会话都订阅着时核心 PSS 涨的，除以会话数 | 核心里每多一个活动会话 |

   - 判：没超的「过」，超了的「超」，量不了的「不量」。
   - 23 第二节缺了要比的一行，量尺一开始就报错，不白量。
10. 没有预算的也列出来：冷启动的三个点、说出去到模型收到请求（含这一句落盘的同步，大会话到了以后的那几轮、重启以后头一次各一行：和投影那两行一比就是同步占了多少，施工 V-2 中）、流式一轮的核心 CPU 和一轮多久（施工 V-22；以前的原始数据没有，`--render` 时不出这两行）、大会话有多大、载着它和空闲以后的内存、二进制大小。另有一张「会话长大的一路上」：照说之前的事件数每一千条一档，报说一句到收到请求、落了盘到收到请求、一轮的 p50、p95。V-2 中以前的原始数据没有「落了盘到收到请求」，`--render` 时照说出去到收到请求算（上界）。
11. 条件写机器（CPU 型号、逻辑核数、内存）、系统、内核、rustc、提交（工作区有没提交的改动的标「+改动」）。不写主机名、用户名、路径。

### 工具一步（施工 V-29）

模型发出一个工具调用以后，核心多久把结果送回模型：agent 干活时这一段占的时间最长（2026-10-31 项目主人要每个工具都够快）。只量、不进闸门，没有预算；`cargo xtask perf --tools 20` 单独跑。

**怎么走**

1. 工作区在沙盒下的 `tools/`：两 KB 的小文件、8 MB 的大文件（十万行）、改的文件、拷进来的树（`--tree`），起成一个新的 git 仓库：`grep`、`glob` 在仓库里时照仓库根往下的 `.gitignore` 走，不另起一个仓库整棵树都被源码树的 `target/` 挡掉。
2. 核心照别的几场拉起，有 `systemd-run` 的放进自己的 scope（`systemd-run --user --scope`，进程号不变）：连子进程的 CPU 读得到。会话都关着记忆、不起标题，照出厂预设（`full`）的工具面，工作目录是工作区。
3. 假模型照剧本回（`fake/script.rs`）：提到这一轮记号的请求，照请求体里已经有前几次调用的结果（照调用编号数，驱动交回结果用的是供应商给的编号），回下一次调用（正文一句 `Checking.`、一个调用、`tool_calls` 收尾带用量、`[DONE]`），都回完了回那一句收尾。一轮里同一种调用一次接一次。
4. 每一步记：假模型把带调用的回答连同 `[DONE]` 写完的那一刻，到读全带着这次结果的下一个请求头；两头各读一次核心的 CPU（各线程的 `schedstat`；在 scope 里的再读 cgroup 的 `cpu.stat`，核心拉起的 `miyu-sandbox`、`bwrap`、命令本身都算，挪到子进程的活照算，2026-10-30 项目主人定）。每种的头一次不算（头一回拉起沙盒、文件还不在页缓存里），之后的报 p50、p95。
5. 量哪几种（工具名、参数照 `resources/software/basesystem/tools/*.json`，`tools/calls.rs`）：`read` 小文件、8 MB 文件的末尾 200 行、列目录（`read` 读目录）；`write` 4 KB（同一个文件一次次盖）；`edit` 一处；`grep` 在树里搜（默认只列文件、带行两种）；`glob` 在树里找；`shell` 的 `true`、`echo`、`cat` 小文件，在工作区这一级（关进沙盒）和完全放开（沙盒关着）各一遍，两边一比是沙盒的开销。
6. 「什么都不做」的对照：同样一句回答不带调用，这一轮结束，量尺收到 `turn.ended` 当场再说一句；量回答写完到下一个请求头，拆成写完到收到 `turn.ended`、再说一句到核心落了盘回应、回应到请求头三段。这是核心收一轮、来回一趟、组装下一次请求的底子；工具一步减去它，大致是工具本身加上判权限、派、收回来的那几跳。
7. 拆段（`tools/split.rs`，不改核心）：停了核心以后读会话日志、运行日志，每一处取它在一步里头一回出现的时刻减去回答写完的那一刻，几十步取平均。会话日志：带这次调用的 `message.assistant`（actor 收到「说完了」）、这次的 `tool.result`（结果交进内核）；运行日志：`running`（判过权限、派之前）、`ran`（actor 收到做完）、`request`（交给请求模型的端口），`--tools-log debug` 另有每条输入、每个动作一行。时刻只到毫秒。顺手查每次调用的结果都是 `ok`，不是的报出来不白量。
8. 结果：`docs/perf/<日期>-tools-<系统>-<架构>[-<标签>].json`（每一步的毫秒和两种 CPU、对照、拆段）和同名的 `.md`。条件另记量之前、量完的 `/proc/loadavg`、握手回应里的 `sandbox`。没有 `--render`：表只照这一份数出。

**和 jcode 比**（`bench/rivals/toolstep.py`、`toolfake.py`、`toolkinds.py`）

1. 同一个假模型（Python，回法同上：提到记号、带工具表的请求才归剧本，起标题这些辅助请求回一句话不记），两家各收到同样意思的调用，工具名、参数照各家自己给模型的工具表（`toolkinds.py`：jcode v0.99.1 的 `read`、`write`、`edit`、`agentgrep`、`bash`；它的表里没有 `ls`，列目录不比；`agentgrep` 的 `find` 是照名字排出最像的前几个、带理由，和 `glob` 列全的口径不同）。
2. Miyu：核心放进自己的 scope 起着，每种跑一次 `miyu ask --no-memory`（沙盒关着的几种加 `--permission full`），CPU 只算核心那个 scope。jcode：每种跑一次 `jcode run`，整个进程放进自己的 scope；它的命令不进沙盒。家目录都在 `--out` 下，jcode 的 `HOME`、`XDG_*` 都指进去，不碰本机的 `~/.jcode`；不调真模型。
3. `--into docs/perf --tag <名>` 写 `docs/perf/<日期>-toolstep-<名>.json`、`.md`。只在有 systemd 用户会话的 Linux 上量。

### 闸门（施工 V-3，23 F4）

1. CI 每次推上去都量一遍（只在 Linux 上，预算照 Linux 定的）：编 release、照出厂参数量，不等闲够了退下（`--idle-wait 0`，那一项没有预算，等它要多三分多钟）。表贴进这一次跑的摘要，也印进日志（摘要经接口取不出来）。
2. 闸门的倍数是 1（施工 V-5 下，2026-10-14 项目主人定超了预算就拦）：时间、内存都照预算本身拦。以前（V-3）时间照 1.5 倍拦，下面是那时候的理由，留着当来历：GitHub 的机器是 4 个逻辑核的 EPYC 7763，比开发的机器慢、抖：第一次量（V-3 上，2026-10-11）重开大会话 p95 128.8 ms，本机绑 4 个核也有 62.6 ms，查出来是重开时整份日志读了三遍（V-2 三补修了）；修了以后重开 p95 54.4 ms、投影 p95 2.6 ms、追加 p99 0.4 ms，都在预算里（V-3，2026-10-11）；离预算最近的是重开（九成），1.5 倍给它留了六成多的抖动，原来那样读三遍的 128 ms 照样拦得下。内存不随机器快慢变：空闲 27.3 MB、每多一个会话 0.96 MB，和本机差不到 1 MB。
3. 收到 1 倍时（V-5 下）CI 上离预算最近的是重开大会话：p95 45.3 ms、预算 50 ms（V-5 中以后，run 38604763130）；release 同时开了整体优化（`lto = "fat"`、一份代码单元），本机核心空闲 24.3 → 20.4 MB。真要改预算照 23 F1 校准，不改倍数凑；CI 上抖到超了的，先查是不是量法的问题，不放宽倍数。

4. 2026-10-20 重开大会话又在 50 ms 边上来回红（p95 51 到 54 ms，`read_ms` 32 ms 上下），开着记忆的投影偶尔 p99 7.9 ms。施工 V-14 拆出两处：读日志时一条事件 480 字节、一万条拷了四遍，每一遍都是向系统新要的页（大块门槛 128 KiB），刚起的核心里一页缺一次，CI 的虚拟机上缺页贵；回合库读写共用一个连接，后台写一批提交时做检查点，回合开始找记忆跟着等。改成拷一遍、读写两个连接以后 CI 上重开 p95 34.3 ms（`read_ms` 21 到 23 ms），投影 p95 3.6、p99 4.4 ms（run 39406662380）。CI 每次把原始数据（`target/perf-out/*.json`）存成 `perf-raw`，查尾巴照每一次的数看。
5. 2026-10-26 开着记忆的投影又两趟贴着 5 ms 红（p95 5.2、5.08 ms，尾巴 30 轮冒一两个尖）。施工 PERF-1 拆开量：量尺的投影从回应算起，回应等同步（V-19），本机同步比回合开头慢，量出来几乎是 0，要在核心里插桩量回合开始到假模型收到请求整段，绑两个核学 CI。冒尖不和记忆的回合线程重叠，落在回合开头几跳阻塞线程上：取 blob 清单空的照样跳一趟，技能、项目指令排在挂接点前面干等。改成不跳、并着等以后，两核上开着记忆的这一段 p50 2.76 → 2.26、p99 4.91 → 3.56 ms。投影随上下文长成锯齿（每 142 轮压缩一次），闸门量的尾巴 30 轮落在锯齿顶上；请求体的 SHA-256 原来在交给网络之前算，挪到之后。本机量投影要让会话日志的同步不慢过回合开头（预加载小库让 `*.jsonl` 的 `fdatasync` 直接返回），不然回应晚于请求，量出来是 0。
6. 2026-10-27 又两趟过 5 ms（施工 PERF-2）。CI 的机器有四种 CPU（EPYC 7763、9V74、9V45，Xeon 6973P，都是 4 个逻辑核），比前后要照 CPU 分开（`perf-raw` 的 `machine.cpu`），PERF-1 报的 CI 前后差大半是机器差。在 CI 上原地插桩量（实验分支，只跑 perf）：记忆的三个挂接点 p99 不到 0.13 ms；偶发的尖是虚机上的调度停顿，落在不同的段（等阻塞线程、发出）；底子里每轮都重新读盘的刷新人格、找技能在 7763 上各约 0.5 ms，原来串着。改成并着找（人格真换了再照新的找一次）。量尺照旧取尾 30 轮的 p95（项目主人 2026-10-27 定）。
7. 2026-10-27「核心空闲、连着一个头」在 30 MB 边上来回红（施工 PERF-3）。`perf-raw` 照 CPU 分开比（从 10-20 起才有），四种机器一样：一周从 26.3 慢慢涨到 29.5 MB，没有台阶，跟着程序长（43.5 → 49.3 MB）。读 `pagemap` 拆开：核心碰到的代码页 16.8 MB（代码段 32.7 MB 空闲就碰了一半，缺页时内核顺带映射前后 64 KiB，`fault_around_bytes`，零散的代码一片片算进去），只读数据 1.5、重定位表 1.1、改写的 `.data.rel.ro` 0.86，匿名 5.3（线程的分配区），主堆 1.8。release 改照体积优化（`opt-level = "s"`）：连着头 28.7 → 25.2、空闲 23.9 → 21.9、每多一个会话 1.21 → 0.86、载着大会话 35.9 → 30.6 MB；吃 CPU 的路（载入大会话日志、数 token、召回、画 mermaid）慢了 1% 到 13%，都不到两成，没有哪个 crate 单独留在 3。重定位打包（RELR）再省约 0.9 MB，要 glibc 2.36 以上，Ubuntu 22.04 起不来，发行目标定了再看；不做非 PIE（主程序没了 ASLR）、符号排序（要打点、要维护）。
8. 2026-10-27、28「一次请求的投影：开着记忆的大会话」又几趟过 5 ms（施工 PERF-4）：尾 30 轮底子 2.4～2.8 ms，隔 21 轮冒一对 7～16 ms 的尖，冒尖那几轮整个回合都慢，关着记忆的那组没有。插桩（本机绑 4 核）：一直在忙的会话走「不等闲」抽取（`memory.extract_max_turns` 20 轮一次，`memory.md` 第六条第 1 款），每次在阻塞线程里整份读会话日志（9.7 MB，中位 20、最长 57 ms），读回来在会话 actor 上同步拼一万多条事件的历史、照组装器渲染、定怎么办（中位 5～8、最长 10～22 ms），这段 actor 被占，下一轮的回合开头排在后面。组装器改成共享的（`Policy.assembler` 是 `Arc<dyn Assembler + Send + Sync>`，`Session::assembler`），这一段整个挪进阻塞线程，定好了直接派出去。本机绑 4 核三遍、每遍各 2013 轮：开着记忆的那组过 5 ms 的 64 → 13 轮、最长 14.1 → 6.9 ms、p99 5.04 → 3.86 ms；剩下的是整份读日志抢 CPU，只读上次抽到以后那一段改的是抽取看多少上下文，归记忆那边定。

### 三家对比（施工 V-7，23 F6）

发版前和 jcode、codex 比一次：同一台机器、同一个模型端点、各自干净的沙箱家目录、同一套场景，量 CPU、内存、读写、硬盘。上面的量尺只量核心、每次都跑；这里量的是人真用的一整套（核心加终端界面），只在发版前跑。

**在哪**

| 文件 | 管什么 |
|---|---|
| `bench/rivals/main.py` | 入口：参数、照先后跑各场景。开头带 `uv` 认的依赖（`pyte`），`uv run` 直接跑 |
| `rivals.toml` | 每一家怎么配、怎么起、屏幕上看到什么算到了首屏、长会话的编号怎么找、装好的是哪几个文件。加一家只加一张表 |
| `places.py` | 程序、端点、输出目录在哪；占位怎么换 |
| `rival.py` | 一家：照它那张表换好占位，配沙箱家目录 |
| `conditions.py` | 量的条件 |
| `homes.py` | 家目录模板：做、存、还原 |
| `term.py` | 伪终端：像 kitty 那样回答终端界面问的几样，用 `pyte` 看屏幕 |
| `meter.py` | 一个 systemd scope 的计量：CPU、内存、读写、唤醒 |
| `reap.py` | 收拾残留的后台进程：只杀家目录指着沙箱的 |
| `leaks.py` | 跑完查输出目录里有没有 key：别家可能把环境写进自己的家目录（codex 的 `shell_snapshots`）；用转发的连真 key 一起查 |
| `relay.py` | 本机转发（施工 V-27）：各家连它，它换上真 key、补会话头再转给上游，每个请求记一行用量 |
| `screen.py`、`task.py`、`long.py`、`disk.py` | 各场景 |
| `summary.py` | 汇成表 |
| `fixture/calc/` | 真任务那一轮要修的小项目 |
| `test_rivals.py` | 不跑别家的那几条：表写得对、占位都认识、汇表 |

**怎么跑**

```
OPENAI_BASE_URL=… OPENAI_API_KEY=… MIYU_BENCH_MODEL=… uv run bench/rivals/main.py --tui <终端仓库> all --into docs/perf --tag v<版本>
```

经本机转发（施工 V-27，上游要每段对话带会话头的，例如 opencode）：

```
MIYU_BENCH_MODEL=… uv run bench/rivals/main.py --tui <终端仓库> --upstream https://opencode.ai/zen/go/v1 --upstream-key-env OPENCODE_GO_API_KEY all --into docs/perf --tag v<版本>
```

1. 端点、key、模型名只从环境变量来，三家用同一个。key 留在环境变量里交给各家：Miyu 的配置写成 `{ env = "OPENAI_API_KEY" }`，codex、jcode 照它们自己认的变量名去读，不写进任何文件、不打印；结果里只记模型名，不记地址。用转发的（`--upstream`）：真 key 只在 `--upstream-key-env` 那个变量里，测具只把它交给转发进程，各家的环境里去掉这个变量，`OPENAI_BASE_URL` 换成转发上这一家的路径、`OPENAI_API_KEY` 换成假的；这时不用设 `OPENAI_BASE_URL`、`OPENAI_API_KEY`。
2. 核心照 `--core`（默认这个仓库），终端界面照 `--tui`（终端界面的仓库，里面有装成软件包的 `miyu-tui/` 和编好的 `target/release/miyu-tui`；包的目录和编号同名，施工 PN-4 起，以前叫 `tui/`，旧的仓库一开始就报），都要先 `cargo build --release`。jcode、codex 照 `--jcode`、`--codex`，不写的照 `PATH` 找。`--only` 只量几家，`--cpus` 绑到几个核上。
3. 子命令可以分开跑：`homes`（做模板）、`screen`、`task`、`long gen`、`long open`、`disk`、`summary`；`all` 照这个先后全跑。`--runs`（默认 5）、`--settle`（默认 13 秒）、`--idle`（默认 60 秒）。
4. 家目录、模板、工作目录、原始结果都在 `--out`（默认 `target/rivals/`）下。`summary --into docs/perf --tag <名>` 再写一份 `docs/perf/<日期>-rivals-<名>.md`、同名 `.json`（汇总的数，加每一轮的原始结果 `runs`；命令输出的最后几行带着本机路径，不入库）。
5. 只在 Linux 上量：CPU、内存照 cgroup v2 和 `/proc` 读，要 systemd 的用户会话。别的系统上一开始就说清楚、退出码 2。

**怎么走**

1. 被测的程序都放进自己的 systemd scope 跑：CPU 照 scope 的 `cpu.stat`（退出了的子进程也算），内存报进程树的 PSS 之和和 scope 的 `memory.peak`，读写照每个进程 `/proc/<进程号>/io` 相加（写报两样：交给系统的 `wchar`，落到盘上的 `write_bytes`），唤醒照每个线程的上下文切换相加。都去掉 `XDG_RUNTIME_DIR`：沙箱的核心把套接字放进自己的数据根（`ipc.md`）。
2. 模板：每家在空的沙箱家目录里配好模型（Miyu 走 `miyu pkg install` 装终端界面的包、`miyu config set` 配模型，和人配的是同一条路；`tui.skip_pick` 开着，新会话照默认的人格、预设开，不然首屏是「请选择预设」的框、没有输入框，施工 V-27），跑一轮很短的任务，开两次终端界面、每次看到首屏等它安静再关、收掉后台进程，存成模板（第一次开留下的活有的要下一次起来才做完：Miyu 的核心在后台拉了新的模型目录，下一次起来才整理成摘要存进缓存；只开一次就存，每一轮冷启动都多做一遍，核心多花一百多毫秒 CPU、多写 1.6 MB，量的不是人平常起来的样子，施工 V-27 查出）。每次关掉界面以后，后台进程照「好好退出」收（自己的 `stop`、SIGTERM 等它收尾）。存、还原都不拷套接字（后台进程收掉时来不及删的，例如 Miyu 的 `run/core.sock`）。家目录、缓存都在沙箱里（Miyu 的缓存跟 `XDG_CACHE_HOME` 走、不跟 `MIYU_HOME` 走，也指进沙箱，`store.md`）。每次量之前照模板还原，还原完先 `sync`：拷出来的脏页没落盘，被测的程序一 fsync，文件系统会顺手一起刷，块设备的写就算到它头上（btrfs 上实测一轮多出 17 MiB）。三家的起点一样（23 第四节：jcode 测别家用真实的家目录，这里不照搬）。
3. 首屏：伪终端里起终端界面，屏幕上出现 `rivals.toml` 写的那几个字算到了。做模板时就开，对不上的当场报，改 `marker`。两家都挑「界面报出用哪个模型」那一刻，不挑先画的架子（施工 V-27 核对）：Miyu 的输入框照机器缓存里记的先画，那时底下写着「正在连接核心…」，连上核心才有权限级别，再晚几十毫秒状态行报出模型名，首屏字就是模型名（`{model}`，字里的占位照样换）；jcode v0.99.1 先画一个空架子（约 20 ms 就有输入框，写着「connecting to server…」），连上自己的服务头上那一行才报出 `OpenAI-compatible: <模型>`。
4. 场景：
   1. **冷启动到首屏**：没有后台进程，从起终端界面算到首屏；记时间、CPU、PSS。
   2. **空闲**：接着冷启动，首屏后先等 `--settle` 秒，再量 `--idle` 秒：CPU、每秒醒几次、终端每秒收到几个字节、结束时的 PSS。首屏后每秒的 CPU 都记下，汇表时出每秒的中位数，照它看收尾要等多久。
   3. **热启动到首屏**：后台进程（Miyu 的核心、jcode 的服务）先起来歇 3 秒，再开终端界面到首屏；两个 scope 相加。没有后台进程的一家不量。
   4. **三个会话同时开**：开三个终端界面都到首屏，同样先等 `--settle` 秒，再空闲 `--idle` 的一半：三个加起来的 PSS、空闲的 CPU。
   5. **一轮真任务**：不开终端界面，各家的一次性命令修好 `fixture/calc` 的 bug（先跑测试、读代码、改、再跑测试）：用时、CPU、峰值 PSS、读写、家目录多了多少，测试过没过。家目录多了多少报两种口径（2026-10-31 项目主人定，施工 V-27），两家同一种口径各一列：「直接杀掉」是命令跑完、等 CPU 停下以后，后台进程（Miyu 的核心、jcode 的服务）还活着时盘上的样子，等于这时崩溃、断电剩下的（SQLite 没合回去的 `-wal`、`-shm` 都在里面）；「好好退出以后」是再让它照自己的办法正常退出（`rivals.toml` 的 `stop`：jcode 是 `server stop`；没写的不跑，Miyu 的核心收到 SIGTERM 自己收尾），剩下的进程发 SIGTERM 最多等 30 秒，还不走的才硬杀（记在结果的 `shut.forced` 里），再量一次，等于平时正常用剩下的。CPU、内存、读写照退出之前的读。
   6. **长会话**：照同样的 50 轮话造各家自己的长会话（每轮二十几行填充文字，最后一轮只回一个记号），再开终端界面接着它，到屏幕上看见那个记号：时间、CPU、PSS。会话编号照各家存会话的地方找最新的那一个：Miyu 是数据根的 `sessions/<编号>/`（单人的，`store.md`），jcode 是 `.jcode/sessions/<编号>.json`。
   7. **硬盘**：装好占多大（`rivals.toml` 的 `install`，照占的块算，硬链接只算一次），家目录跑过一次多大，长会话那一个会话自己的文件多大。家目录跑过一次的数据同样报两种口径：模板是好好退出以后存的（「好好退出以后」）；做模板第二次开终端界面、关掉界面以后、让后台进程退出之前记下盘上有什么（`results/home-crash-<表名>.json`，「直接杀掉」）。配置参考（`state/config/config.schema.json`、`reference.toml`）这类核心生成的文件照实算在数据里（项目主人定：不为数字好看省）。家目录分两样（2026-10-31 项目主人定，施工 V-27）：会一直复用的缓存（`rivals.toml` 的 `caches`：模型目录、图标这类）单列一行，不算进「跑过一次多了多少」；剩下的是跑一次产生的数据（会话、日志、索引这些），Miyu 的这部分再按文件列出来（最大的 25 个，其余合成一行），看是什么占的。
5. 本机转发（`relay.py`，施工 V-27）：
   1. 各家连 `http://127.0.0.1:<端口>/<表名>/v1`，路径里的表名分出是哪一家；转发换上真 key、去掉压缩（流里的用量才读得出来），转给上游，流着回的原样流回去。
   2. 会话头 `x-opencode-session`：opencode 要每段对话带一个稳定的（不带回 400 `MissingSessionID`）。客户端带了的原样转；没带的照「这一家、这一场、这段对话第一句用户的话」算一个（`ses_` 加哈希）：同一段对话往后接着说的每一次请求都一样，换一场、换一段对话就换。测具在每一轮开头告诉转发现在是哪一场（`POST /_scene/<表名>`：`homes`、`screen-<轮>`、`task-<轮>`、`long-gen`、`long-open-<轮>`）。两家一样补；会话头是不是客户端自己带的记在日志里（`own_session`）。
   3. 每个请求记一行进 `results/relay.jsonl`：哪一家、哪一场、模型、状态码、流不流、会话头是谁带的、用了多久、用量（输入、其中缓存命中、输出、推理）；出错的记上游回的前 300 个字。不记请求体、回应体、key。汇表时照场合计成「模型用量」一节（请求数、出错几次、输入、缓存命中、输出），以后比 token 用。
6. 每个子命令跑完查一遍输出目录：哪个文件里有 key（测具自己不写，别家可能写），报出文件，不印 key。
7. 表：每一项报中位数，括号里是最小到最大。条件写机器（CPU 型号、逻辑核数、内存、内核）、绑没绑核、模型名、用没用转发、三家的版本、核心和终端的提交（有没提交的改动的标「+改动」）、终端是不是 `heads.toml` 钉的那一份、负载（量之前的 1、5、15 分钟负载，每一轮开头记的 1 分钟负载的最小到最大，施工 V-27：别的会话在编译时时间类的数会抖，CPU、内存、读写受的影响小）。不写主机名、用户名、路径、地址。

**发版前**
