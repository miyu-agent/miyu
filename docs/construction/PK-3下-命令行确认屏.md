## 施工单 PK-3 下：装包、升级的命令行确认屏说清来源和能力

状态：做完待合（2026-11-05）。core1 2026-11-05 派（派工单第 3、5 节），设计 `docs/designs/61-装包说清来源和能力.md`（第三节「确认屏怎么写」、第四节第 2、5 条、第七节「PK-3 下」、定了的 5、6）。核心、协议那一半是 PK-3 上（`docs/construction/PK-3上-装包说清来源和能力.md`），这一步只动命令行。

### 为什么

PK-3 上以后核心的看一眼已经说清每个包从哪来（`source`、`feed`）、要哪些能力（名字、一句说明、批过的 `held`）、社区的和本机文件的要给人看的话（`notice`、`recommends_notice`），`package.install`、`package.upgrade` 也收 `approve` 了；可命令行还照旧印「来源 : official，签名已验证」、能力只印名字、不印「注意」，答「是」也不带 `approve`，能力照旧等装好以后「现在启用？」时才批。这一步把确认屏照设计 61 第三节改过来，装、升级答「是」（或 `--yes`）就批。

### 做了什么

1. **从软件源装的确认屏**（`pkg/summary.rs`）：
   - 「来源」照每个包的 `source`、`feed` 说：官方的「官方，签名已验证」，官方源里社区收录的「社区，签名已验证」，别人加的源写源的名字；不是官方的接「（<来源仓库>）」。几个包都一样的只写一行，不一样的一个包一行、前面接编号（编号照这一次要装的最长的补齐、再空两格）。
   - 「需要的能力」一项一行：核心给的名字接「：」和说明，批过的接「（已批准）」；几个包的前面接编号。
   - 「键 : 值」的值有几行的（`info::aligned` 认值里的换行），后面几行缩进到值那一列。
   - 问的那一句：核心给了 `notice` 的，空一行以后先一行「注意：」接核心的句子（中文直接接、英文空一格），紧接着问；有要批的（列了、不是 `held` 的）问「安装 '<编号>' 并批准它要的能力？」「安装 N 个软件包并批准它们要的能力？」，没有的照旧。
   - 推荐的那一段（`recommended_question`）：推荐的里有列了能力的、核心给了 `recommends_notice` 的，第二句之前空一行另印「推荐的包要的能力 : <编号>  <能力>」、「注意：…」，问「同时安装推荐的 N 个软件包并批准它（们）要的能力？」；都没有的照旧那一句。
2. **从包文件夹、包文件装的确认屏**（`pkg/confirm.rs`）：「需要：」一项一行带说明（后面几行缩进到「需要：」后面）；新加「来源：」照 `source` 说本机文件、出厂、系统的包管理器（不写路径）；问的那一句同上（`confirm::question`，装回出厂的照旧「装回 '<编号>'？」）。卸的那一份不动。
3. **装的时候批**（`pkg/approve.rs`、`pkg/install.rs`）：
   - 答「是」、写 `--yes`（`--noconfirm`）的都算批（定了的 6）：真装那一条带 `approve`，看一眼列出的每个包（要装的、`with`）的能力编号照原样带上，`held` 的也带（核心照并集记）；没列能力的包不写，表空的不带。
   - 推荐的答「是」的另装另批：每一个带的是推荐那一段里列出来的它的那几样，真装之前那一次看一眼多出来的不批（照表批，设计 61 第四节第 1 条）。
   - 装好以后，「已安装」那几行后面一个包一行「已批准 <编号> 的能力：<名字>、…」，只列这一次新批的。
   - 「现在启用？」照旧（`manual` 的装完关着），答是发 `package.enable` 照旧带上看一眼的那几个能力。
4. **升级**（`pkg/upgrade.rs`）：一律先看一眼（写了 `--yes` 的也看，新多要的能力要照它批）；每个「将升级」下面一项一行「  新要：<能力>」（批过的不印）；一起装的新依赖一行「将安装 <编号> <版本>」，下面「  需要：<能力>」；社区的照 `notice` 印「注意」；有新要的问「升级 '<编号>' 并批准新要的能力？」（几个的「升级 N 个软件包并批准新要的能力？」）。答「是」、`--yes` 都带 `approve`（`upgrades` + `with` 列的），升好以后一个包一行说批了哪些（定了的 5、6）。
5. **字**：`language/pkg/approve.rs`（中英）：来源的几种说法、能力一项、「（已批准）」、「注意：」、升级的「新要：」「需要：」、带批准问的五句、批了哪些；`info` 的键多「推荐的包要的能力」。帮助页 `--yes, --noconfirm` 那一行改成「安装、升级或卸载前不确认，要的能力一并批准」。

### 定下的技术题

- **只对认 `approve` 的核心带它**：以前的核心 `package.install`、`package.upgrade` 的参数是 `deny_unknown_fields`，带了 `approve` 整条被拒。不能照「看一眼有没有 `capabilities`」判断——以前从包文件夹装、从软件源装的看一眼也有这一格。照 PK-3 上新写法认：从软件源装的看一眼写了 `feed`（新核心从软件源装的都写），从包文件夹、包文件装的 `source` 是 `file`（以前从软件源装的 `source` 是源的名字、没有 `feed`，从包文件夹装的没有 `source`）。认不出的不带、问的照旧那一句，能力照旧在「现在启用？」时批。升级不用另判：拼表只看 `upgrades`、`with` 里列的能力，以前的核心那里没有能力，表是空的、不带。装回出厂的（`source: "shipped"`）不带：出厂的算全批过。
- **`held` 的也带**：照「看一眼列出的每个包的能力编号原样带」，不挑；核心算的是 (接着用 ∪ 批的) ∩ 声明的，多带批过的不会多批，少带反倒要多一层判断。
- **批了哪些只列新批的**：`held` 的早就批过了，列出来像是这一次批的；答「是」的、`--yes` 的都印（定了的 6 说 `--yes` 输出照样列出批了哪些，答「是」的屏上已经列过，再印一行当作结果，两种输出一样好对）。印在「已安装」「已升级」后面：装不成的不印。
- **「注意」接在问的前面、不另空一行**：照设计 61 第三节的样子，空一行以后「注意」紧挨着问；做法是把「注意」并进问的那一句（`approve::noticed`），`confirm::asked` 照旧在前面空一行。
- **来源都一样的并成一行**：官方源装几个官方的包（最常见的）照旧一行「官方，签名已验证」，不印一串一样的；不一样的才一个包一行。能力几个包的一律接编号（只有一个包的不接）。
- **装的确认屏标批过的，升级的不印批过的**：派工单写装的确认屏「已批过的（held）标出来」，设计 61 第三节写升级「`held` 的不印」，各照各的。从包文件夹装的永远没有 `held`（来路算变了），标记的写法照样有。
- **推荐的照第一次看一眼列的批**：推荐的真装之前照旧另看一眼拿版本，那一次看一眼可能比第一次多（索引刷新了、它自己的新依赖），人只看过第一次那一段，所以照第一次的批；多出来的打开时再批。
- **升级一律先看一眼**：以前 `--yes` 不看一眼直接升；现在要拿新多要的能力，`--yes` 也看。多一条请求，索引照缓存拿、不多下载。

### 要拍板的

- 无。设计 61 第八节 core1 已定；「注意：」「（已批准）」「新要：」、带批准问的几句、「已批准 <编号> 的能力：…」是命令行自己的字，照命令行的规矩定了，中英见 `language/pkg/approve.rs`、蓝图 `cli/pkg.md`「给人看的字」。
