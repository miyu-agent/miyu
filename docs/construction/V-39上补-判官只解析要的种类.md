## 施工单 V-39 上补：判官只解析要的种类

状态：已完成（2026-11-03）。照 V-39 设计第六节问题 2、第八节「V-39 上补」那一行做；2026-11-03 项目主人拍板接受问题 2。

### 为什么

V-39 上以后，判官每问一次 `venue.records` 的堆峰值已经只多十来 MB，可指令还在 9～9.6 亿：几乎全是把日志的每一行解成事件（JSON 解析和里面的分配、释放），解完了大半扔掉。V-39 设计第一节造的 23.8 MB 群会话，字节的四分之三是她的回复（`message.assistant`，带推理，52%）、模型请求的记录（`model.called`，17%）、工具结果（`tool.result`，6%）；判官要的只是人话、她发进群里的、撤回、回合的开头结尾、撤销恢复、压缩这几种。

### 项目主人拍板的

1. 问题 2（2026-11-03）：判官读日志时，和它无关的种类不解析正文；行完整、序号连续照查。
2. 代价接受：有人从外面把某条无关种类（比如工具结果）的正文改得不合写法、但仍是合法 JSON 的，判官不再报 `session_broken`；下次打开这个会话照样整份自检、报出来。除这一处外行为一律不变。

### 照的图纸

- V-39 设计第六节问题 2、第八节、第九节。
- `docs/blueprint/kernel/events.md`「对外的样子」`Event::from_line`；`store.md` 第 7 条 `read_range`；`venues.md`「判官看的群聊记录」第 3 条；`kernel/history.md`、`history/undo.rs`（有效历史认哪几种、看哪几格）。

### 要解、不解的种类，和为什么

逐个从代码里推（V-39 上的 `read.rs`、`pass.rs`、`bones.rs`，`miyu-assemble` 的 `group/records.rs`，内核 `history.rs` 的 `append`、`history/undo.rs`）：

| 种类 | 解多深 | 谁看、看什么 |
|---|---|---|
| `session.created` | 全解 | 第一条：钉下的字照它的 `policy` 找（`records.rs` 的 `texts`） |
| `message.user` | 全解 | 渲染、引用、要判的那一条（`on_record`、`quoted_as`、`records_from`）；骨架记人话（`bones.rs`）；有效历史撤回、撤销拿走跟着撤的话、查排着的话（`said_by_the_person`、`left_queued`） |
| `venue.delivered` | 全解 | `[you]` 行、引用（`on_record`、`quoted_as`） |
| `venue.recalled` | 全解 | 撤回记号（`pass.rs` 收下时记） |
| `turn.started` | 全解 | 触发（骨架、有效历史 `taken_over`）；撤销以后开新的一轮（`pass.rs` 放不放、有效历史清掉放在一边的） |
| `turn.ended` | 全解 | 紧挨着这一轮开头结束的上一轮（骨架 `ended_before`、有效历史 `ended_before`） |
| `turn.reverted`、`turn.unreverted` | 全解 | 撤销、恢复（骨架的下界、`pass.rs`、有效历史） |
| `message.withdrawn` | 全解 | 撤回排着的话（骨架的下界、有效历史） |
| `context.compacted` | 全解 | 压缩以后恢复不了（`pass.rs`、有效历史清掉放在一边的） |
| `job.reported`、`child.reported`、`peer.idle` | 全解 | 撤销时触发是不是这几种，决定上一轮认不认紧挨着结束的那一轮（`taken_over`）；都很少、很小 |
| `message.assistant` | 只解 `seen`、`interrupted` | 撤销查上一轮排着的话：她看到了第几条（`left_queued` 取请求、回复的 `seen` 最大的）；`blocks` 不解（字节的一半） |
| `model.called` | 只解 `seen`、`messages`、`result`、`error` | 同上；暂停着没发出去的那一次（`error.class` 是 `compaction_paused`）不算看到；用量、金额、块的起止这些不解 |
| 别的（`tool.result`、`context.injected`、`session.meta_changed`、不认识的 `ext.*`……） | 不解 | 判官、骨架、有效历史都只认种类、回合、序号（撤销按 `turn` 拿走一整轮，外壳全解了）；正文只过一遍（是合法的 JSON 就行），读成不认识的种类，种类照写、正文是 `null` |

前十一种里，判官自己看正文的写在端点（`read.rs` 的 `ONLY`），有效历史照种类认的（撤销、恢复、撤回、压缩、回合开头结尾、人话、三种回报）和只解几格的两种写在内核（`event/only.rs` 的 `HISTORY`、`SEEN`），挨着有效历史的规矩：有效历史多认了别的种类、多看了别的格，这里跟着改。两边都列了的（判官看、有效历史也认）各写各的，一边改了另一边不受牵连。

**没解正文的事件进了 `History::whole`，撤销规则看的字段都在**：外壳（序号、回合、谁、命令编号）全解；有效历史照种类认的全解；`left_queued` 看的 `seen`、`error` 在。不解的读成不认识的种类，有效历史照先后留着（和全解时同一个位置），撤销照 `turn` 拿走、恢复照序号放回，留下的事件（序号、种类、认的那几种的内容）和全解一样（下面「验收」第 3 条按条比）。

### 做什么

1. **内核** `Event::from_line_only(行, 要的种类)`（`event/only.rs`、`event/read.rs`）：同一份外壳的读法，读到 `body` 时照种类定解多深（全解、只解几格、只过一遍）。种类写在 `body` 后面的（不是核心写的样子）照旧先原样截下来，再照种类定。读不成的照 `Event::from_line` 再读一遍、交它的错，报出来的错和全解一字不差；全解读得成的这里也读得成。
2. **存储** `read_range_only(目录, 从第几条, 到第几条, 要的种类, 每一块)`（`log/open.rs`）：同 `read_range`，一窗窗读、几个线程一起解、自检都照旧，只是每一行照 `from_line_only` 解（解法一路传到 `walk`、`parse::stream`、`chunk`；别的读法一律照旧全解）。
3. **判官**：会话目录的日志（`read.rs` 的 `Dir`）照 `read_range_only` 读，头一遍、再读一遍、读回引用、整份读的退路都照它（整份读改成从第一条读到最后，同 `read_events`）。边读边记的那一套一行没动。
4. 测试、蓝图（下面）；顺手把 V-39 上施工单第 5 条「各 2,300 条」改成「各 2,301 条」（每一条叫她的话一份数据根 2,301 条）。

### 不做什么

- 别的读者（载入会话、补发、撤销读回、分叉、回合索引、`history` 工具……）一律照旧全解。
- 不碰内核的撤销逻辑本身（`history.rs`、`history/undo.rs` 一行没动）、不碰 im、不碰 `root.rs`、`root/places.rs`、`config_file.rs`、`cache.rs`；不落缓存文件、不常驻额外状态。
- V-39 中、下（支线的分叉、载入）不在这一步。

### 和设计不一样的

- 设计说「`{"seq":N` 在行首，便宜」地认出种类：没有另写一套扫行首的，用的是同一份外壳的读法（serde），正文照种类定解多深，不要的用 `IgnoredAny` 过一遍。好处是外壳的查法、报错和全解一字不差，正文不是合法 JSON 的照样报坏了（比主人接受的代价还窄一点：只有「合 JSON、不合写法」的不报）；代价是不要的正文还得过一遍分词（不分配）。
- 设计只说「不解析」：`message.assistant`、`model.called` 解不了（有效历史撤销查排着的话要看它们的 `seen`），改成只解那几格。
- 读一行的法子放在内核（`event/only.rs`），存储只是照它解；有效历史认哪几种挨着有效历史写。
- **指令没降到设计估的 2～3 亿**：9.0～9.2 亿 → 7.0～7.2 亿（少 22%）。剖开看（`perf record`，只取判官那几段）：不要的正文照旧要过一遍分词（扫字符串的 `skip_to_escape`、`ignore_value`、`ignore_str` 合起来约四分之一），每一行照旧查 UTF-8（约 5%）、数换行，37,000 行的外壳照旧全解（时刻、种类、`by`、分配），要的人话一万一千多条照旧全解。设计估的是「不要的连扫都不扫」；要那样得在没解完的行里直接跳到行尾（核心写的行 `body` 在最后），可外人改过的行 `body` 后面还可能有外壳的格，跳过去就漏了，不在主人拍板的范围里，这一步不做；要再省可以另拍板。

### 风险

- 内核有效历史的规矩以后多认了别的种类、多看了 `message.assistant`、`model.called` 的别的格，`event/only.rs` 不跟着改的话，判官撤销以后算出来的会和全解的不一样。`only.rs` 开头、`kernel/events.md` 写了；对照测试（三千段、只要内核那几种的有效历史按条比）逮得到生成器造得出的那几种。
- 判官要看的种类以后多了（比如渲染加了别的种类的行），端点的 `ONLY` 要跟着加；没加的那一种读成不认识的、渲染不出来，对照测试会逮到。
- 不要的种类的正文被改得不合写法、仍是合法 JSON 的，判官不报（主人接受的代价）；正文不是合法 JSON 的照报。
