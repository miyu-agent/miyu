## 施工单 V-27：三家对比照现在的样子跑

状态：已完成（2026-10-31）。2026-10-30 项目主人要「对照 jcode 做对比测试，期望全方面优于 jcode」；这一步先让 10-15 写的测具（施工 V-7）照核心、终端、jcode 现在的样子跑得起来。2026-10-31 项目主人给了 opencode-go 的 key，跑正式对比：模型先用 opencode-go 的免费模型，实在不行再用 deepseek-v4.1-flash，别的不碰；硬盘那一场缓存和数据分开报；家目录两种口径都量、都列（直接杀掉，代表崩溃、断电；先好好退出，代表平时）；核心生成的配置参考两份照「不为数字好看省」留着、照实列。

### 目的

`bench/rivals/` 是 10-15 照当时的核心（多用户）、终端（包在 `tui/`）、jcode v0.95.0 写的，之后这几样都变了，测具跑不起来。照现在的样子改对，跑一遍正式的 Miyu 对 jcode（`--only miyu,jcode all`），结果写进 `docs/perf/<日期>-rivals-v27.md`、`.json`；codex 不在这一次。

为了两家走同一个入口、同一个模型，加一个本机转发（`relay.py`）：两家都连它，它换上真 key、补 opencode 要的会话头，再转给 opencode-go；key 只在转发进程的环境里，家目录里都是假 key；顺带记每家的请求数和用量，以后比 token 用。

### 查下来的

- 会话目录：单人的，会话在数据根的 `sessions/<编号>/`（`crates/miyu-store/src/root.rs` 的 `session_dir`，数据根就是 `MIYU_HOME`）。`rivals.toml` 的 `[miyu]` 还写着多用户时代的 `home/admin/sessions/*`，长会话找不到编号、硬盘量不到会话。
- 终端包的目录：施工 PN-4 起终端仓库里的包叫 `miyu-tui/`（和编号同名，核心设计 48，`heads.toml` 开头的注释），以前叫 `tui/`。`places.py` 的 `{tui_package}` 和查「是不是终端仓库」都还认 `tui/`，一开始就报「不是终端界面的仓库」。程序名照旧是 `target/release/miyu-tui`。
- Miyu 的首屏：新会话先开「请选择预设」的框、没有输入框（终端 `tui.skip_pick` 出厂关）；配置那几步加 `miyu config set tui.skip_pick true`，照默认的人格、预设开（10-15 那次没有这个框，条件和那次一样）。开了以后屏幕先后是：约 40 ms 照机器缓存画出输入框和「Tab 切换权限级别」，底下写「正在连接核心…」；连上核心换成「工作区」；再晚几十毫秒状态行报出模型名。`Tab切换权限级别` 是缓存里先画的架子，换成模型名（`{model}`，测具给首屏字也换占位），和 jcode 一样挑「界面报出用哪个模型」那一刻。
- 模板只开一次终端界面就存，Miyu 每一轮冷启动都多做一遍活：第一次开时核心在后台从 models.dev 拉了新的模型目录（缓存里 5.8 MB），下一次起来才照它整理成摘要（`models-dev.digest.json`，1.6 MB）存进缓存，模板里存的是对不上的旧摘要，每一轮还原后核心都重解原文、重写摘要。量出来空闲那段每轮写 1604 KiB（交给系统的），改成开两次再存以后 10.5 KiB；冷启动 CPU 中位数 173 → 133 ms。改成开两次终端界面、每次等安静、收掉后台进程再存。
- 后台进程被收掉时没删的套接字（Miyu 的 `run/core.sock`）留在家目录里，`copytree` 拷它报 ENXIO、模板存不成：存、还原都不拷套接字。
- jcode v0.99.1（`jcode v0.99.1 (7206efd0c)`）：照 `--help`、`run --help`、`serve --help` 核对，`--no-update`、`-p openai-compatible`、`run`、`serve`、`--resume` 都还在；`JCODE_OPENAI_COMPAT_API_BASE`、`JCODE_OPENAI_COMPAT_DEFAULT_MODEL`、`JCODE_OPENAI_COMPAT_API_KEY_NAME`、`JCODE_NO_TELEMETRY`、`JCODE_NO_AUTO_UPDATE` 这些变量程序里还认；会话照旧写 `.jcode/sessions/<编号>.json`（旁边一份 `.bak`）。首屏不再问「How would you like to begin」：v0.99.1 约 20 ms 先画一个空架子（输入框、右边的 Overview），连上自己的服务（约 90 到 120 ms）头上才报出 `OpenAI-compatible: <模型>`，首屏字只留后一句。
- opencode 要每个请求带 `x-opencode-session`，不带回 400 `MissingSessionID`。Miyu 只给内置的 opencode-go 供应商带（`ses_{session_digest}`），测具里配的是通用的 openai-chat 供应商，不带；jcode 的 openai-compatible 也不带（实测转发记的 `own_session` 两家都是否）。转发照「这一家、这一场、这段对话第一句用户的话」补一个：同一段对话的每次请求一样，换一场、换一段对话就换，两家同样对待。
- 硬盘那一场（2026-10-31 项目主人定）：会一直复用的缓存（Miyu 的 `.cache/`：模型目录 5.8 MB、摘要 1.6 MB、图标、终端记的首页；jcode 的 `.jcode/cache/`、`.config/jcode/remote_model_catalog_cache.json`）单列，不算进「跑过一次多了多少」；剩下的数据 Miyu 按文件列。
- 家目录两种口径：测具量完照 scope 整个杀掉（`cgroup.kill`），Miyu 的核心来不及把 SQLite 的 WAL 合回去，真任务那一轮多出的大半是 `-wal`、`-shm`（`usage.db-wal` 约 93 KiB、`sessions.db-wal` 约 52 KiB、几个库的 `-shm` 各 32 KiB）；同一轮让核心好好退出只多二十几 KiB。jcode 写的是 JSON 文件，两种口径几乎一样。两种都量：命令跑完、等 CPU 停下以后先量一次（后台进程还活着，盘上的就是这时崩溃、断电剩下的），再让它照自己的办法退出（jcode 跑 `server stop`，Miyu 的核心发 SIGTERM 等它收尾，最多等 30 秒，不走的才硬杀）再量一次。做模板时同样在退出之前记下一份。
- 机器上别的会话在编译时到首屏的毫秒数抖得厉害：量之前和每一轮开头记下负载，写进表头。
- jcode 没有 `XDG_RUNTIME_DIR` 时把服务的套接字放在 `/tmp/jcode-<uid>/`，不在沙箱家目录里（10-15 那次也一样）；本机没有别的 jcode 在跑，不影响量。

### 验收

1. `python3 -m unittest discover -s bench/rivals -p 'test_*.py'` 全过（没装 pyte 也能跑，CI 的量尺那一项就是这样）；新加的几条（终端包是 `miyu-tui/`、旧的 `tui/` 一开始就报、Miyu 在数据根的 `sessions/` 下找最新的会话、首屏字换占位、存模板不拷套接字）改之前红；jcode 照 `.jcode/sessions/<编号>.json` 找会话那一条是守着的，改之前也过。
2. `uv run bench/rivals/main.py --tui <终端工作树> --jcode <jcode 启动脚本> --upstream https://opencode.ai/zen/go/v1 --upstream-key-env OPENCODE_GO_API_KEY --only miyu --only jcode all --into docs/perf --tag v27` 跑通；跑完 `leaks.py` 不报，再拿真 key 搜一遍 `target/rivals/`，删掉它和 jcode 在 `/tmp` 的东西。
3. 转发的测试：同一段对话会话头不变、换场换家就换；换上真 key、补会话头、路径换成上游的、记用量、日志里没有 key；流里捡用量；用转发时各家只拿自己的路径和假 key，环境里没有真 key。硬盘把缓存和数据分开。好好退出：先跑自己的退出命令、SIGTERM 收尾的等它做完，不理 SIGTERM 的过了时限才硬杀；`disk` 把两种口径都读进去（跑出来的错先写成测试：局部变量盖住了函数名）。
4. `cargo xtask check` 全过。

### 结果

`docs/perf/2026-10-31-rivals-v27.md`、`.json`：opencode-go 的 `beam-free` 一次跑完 `all`（两家真任务都 5/5 过、转发记的对话请求一个没出错，没换模型），绑 12 到 15 号核，量之前 1 分钟负载 15.4、各轮开头 4.5 到 17.9。到首屏、空闲、热启动、三个会话、真任务的用时 CPU 内存读写、打开长会话、装好多大，Miyu 都比 jcode 少。Miyu 多的三样：

- 真任务那一轮家目录多了多少，直接杀掉的口径 376 KiB 对 104 KiB（多的是 SQLite 的 `-wal`、`-shm`）；好好退出的口径 27 KiB 对 104 KiB，Miyu 少。
- 家目录跑过一次的数据 352 KiB 对 312 KiB（直接杀掉 448 对 312）：两个刚建的回忆库各 60 KiB、配置参考 `config.schema.json` 56 KiB 和 `reference.toml` 36 KiB（留着，照实列）。
- 会一直复用的缓存 8.4 MB 对 24 KiB：models.dev 的模型目录 5.8 MB、摘要 1.6 MB、图标。

### 风险

- 首屏字挑得太早（界面还不能用就算到了）或太晚，两家的「到首屏」就不对等：两家都挑连上后台、报出模型那一刻。Miyu 照缓存先画输入框，连上以前打的字排着、连上再发，挑模型名对 Miyu 是从严算。
- 本机同时有别的会话在编译，到首屏的毫秒数抖得厉害；CPU、内存、读写受的影响小。表头记了负载，比时间类的数先看负载。
- 和 10-15 那一份不能直接比到首屏、CPU：那次 Miyu 的首屏字是输入框里的提示，这次等状态行的模型名，挑的那一刻不一样；那次的模板也是只开一次就存的。
