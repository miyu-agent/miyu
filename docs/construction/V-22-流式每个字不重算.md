## 施工单 V-22：流式每个字不重算

状态：已完成。2026-10-30 项目主人定这一轮性能优化「照推荐的做」，原则是不能为了数字好看而省；核心主会话同天同意开工，要求读到的配置一字不变、写给头的先后不乱。

### 目的

模型一点点回答时，核心每收一块只做这一块该做的，不再每一块都把跟着会话长的活重做一遍。量尺补上一场「流式一轮」：以前假模型一次回一整块，这一截从来没量过。

### 查下来的

真模型一轮回几百块，每一块：

- actor 送完一批收尾时重算「有没有能压的」（`push_now` → `compactable()` → `upto_before`）：过几遍整段有效历史，再排一遍。一块碎片动不了它。
- 视图流每一批都读连接的语言、`restatus` 里读币种：`Resolved::values()` 每读一次把整份配置拷一遍。
- 写给头：一条推送两次写、一次冲。

### 蓝图改哪几节

- `session/actor.md`「怎么走」第 7 条：全是流式碎片的一批不重算有没有能压的。
- `config.md`「最终值和来源」：最终值合完算一次，几份共用、改的才另拷；「守着它的」加一行。
- `protocol.md`「一个连接」第 2 条：排着的几行一起写、只冲一次，字节和先后不变；「在哪」「守着它的」各加一行。
- `perf.md`：参数加 `--streams`、`--pieces`；「怎么走」第 7 条加「流式一轮」；第 10 条、「在哪」「守着它的」跟着改。

### 不做什么

- 不给推送加时间节流（攒 16、33 毫秒再发）：多出来的延迟是体验的取舍，只合并已经排着的。
- `restatus` 照旧每批比一次状态：碎片会不会动投影的状态，这一步不去证。
- SSE 解析少分配、一个块的几个增量合成一封信、各订阅者共用序列化：收益要等这一场量出来再排。

### 量到的

用这一步加的「流式一轮」量：改前（main 2e0c7576a）、改后的 `miyu` 都是 debug 构建，量尺是改后的那一份，参数缩小（大会话 4000 条事件，`--streams 10 --pieces 300`，别的次数也缩小），交替各两次。机器上别的会话在编译。

| | 改前 | 改后 |
|---|---|---|
| 流式一轮核心花的 CPU p50 / p95 | 85.5 / 91.7、84.8 / 96.1 ms | 47.9 / 51.9、34.9 / 37.6 ms |
| 说出去到这一轮结束 p50 / p95 | 91.4 / 158.8、87.0 / 101.2 ms | 55.9 / 59.9、41.5 / 44.8 ms |

一轮三百块，核心少花一半左右的 CPU。release 构建、一万条事件的 CI 量尺上的数等合进去以后照 CI 的 perf 表看。

### 验收

1. `config/merge/tests.rs`：最终值和逐项 `get` 一样、几次取的一样，改一份不动合出来的；原有的配置测试、请求逐字节比对的测试照旧全过。
2. `connection/outbox/tests.rs`：回应、推送交错入队，写出去照入队先后、字节同一行行写；排着的一次冲完；没排着的不等；攒满分几次写；写不出去就停。端点原有的订阅、先见结果后见回应的测试照旧全过。
3. `compactable.rs` 等原有测试照旧：有没有能压的照样在落盘以后变、照样推。
4. 量尺：`fake/tests.rs` 切块接得回原文；`report/tests.rs` 两行进表、旧原始数据不出。改前（main）、改后各跑一次流式一轮，核心 CPU 前后对比写进提交。
5. `cargo xtask check` 全过、Windows 版 clippy、三平台 CI；量尺的预算不放宽。

### 风险

- 判「全是碎片」漏了会改状态的输入：只认 `chatty_input`、`chatty_action` 那几种；碎片出错的那一路交回落盘、取消，不是碎片，照常重算。
- `Values` 共用以后有人改了别人的：`set` 走 `Arc::make_mut`，共用着的先拷，第 1 条测着。
- 成批写攒得太大：一次最多 256 KiB，写完缓冲缩回 64 KiB。
