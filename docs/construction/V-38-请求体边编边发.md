## 施工单 V-38：请求体边编边发

状态：已完成（2026-11-02）。项目主人每天用的核心，glibc 的 mmapped 每隔一两分钟从 3 MB 跳到 100～190 MB；量实了是长会话里的图（36 张、原图 43.4 MB）每次请求在内存里同时放好几份。主人定：直接做彻底的方案，不做「发完就放」的过渡步；不靠多写硬盘，不能让慢盘电脑变慢，所以不新建任何缓存文件。

### 为什么

改前每次请求，这几份同样的内容同时在内存里，一直放到模型回完：

- 原图：`miyu-session` 的 `route/exchange.rs` 的 `fetch` 整份取出来；
- data URL 的字符串：驱动里 `format!("data:…;base64,{}")`；
- 序列化好的请求体；
- 交给 reqwest 的那一份：`miyu-http` 的 `send.rs` 里 `.body(attempt.body.to_vec())`；
- 还有请求本身（`Request`，主请求的那一份）和线上的中间结构（`Vec<Wire>`）。

有图时每次请求的 CPU 约 112 ms，大头是自己拼的 base64（22%）、JSON 转义（14%）、请求体的 SHA-256（9%）。

### 查下来的（reqwest、hyper 的几处，读 reqwest 0.12.28、tower 0.5.3、tower-http 0.6.11、hyper 1.11.1、hyper-util 0.1.21、h2 0.4.19、rustls 0.23.46 的源码）

- **reqwest 自己会拿同一份请求体重发的只有两处**，都要求请求体能克隆（`Body::try_clone`：只有整份在内存里的 `Bytes` 能克隆，流不能）：
  1. 跳转：tower-http 的 `FollowRedirect`，策略是 reqwest 的 `TowerRedirectPolicy`，默认 `Policy::limited(10)`。301、302（POST 改成 GET）和 303 把请求体换成空的再跟，用不着克隆；307、308 原样带着请求体跟，要克隆，克隆不了的直接把这个 3xx 交回来。跟之前：`Location` 照当前地址解析（解析不了、成不了 HTTP 地址的照原样交回 3xx）；跳过的地址记一串，多于 10 个（第 11 次跳）报 `error following redirect: too many redirects`；地址不是 http、https 的报造不出请求；每一跳的头从原来那一份起，和上一个地址跨了主机（主机名或端口不一样）的去掉 `Authorization`、`Cookie`、`Cookie2`、`Proxy-Authorization`、`WWW-Authenticate`；带 `Referer`（`referer` 默认开着）：上一个地址去掉用户名、密码、`#` 后面的，https 跳 http 的不带。
  2. 对方没处理的重试：`tower::retry`，reqwest 默认的策略 `ProtocolNacks`、不设预算、每个请求最多再发 2 次（`max_retries_per_request`，一共 3 回），不等，立刻再发。只认 h2 的两种错：对方发来的 `GOAWAY`、原因 `NO_ERROR`（对方正常关连接，这个流在它说的最后一个之后），对方发来的 `RST_STREAM`、原因 `REFUSED_STREAM`。HTTP/1 不重试。这一层在跳转那一层里面，每一跳各算各的。
  3. 另有一处不用克隆：hyper-util 的连接池，复用的连接在写请求之前就断了的，hyper 把没动过的请求原样交回来、换连接再发（`retry_canceled_requests`）。流没被读过，照旧。
- **hyper 的 HTTP/1 在 TLS 上不会把整份请求体拷进写缓冲**（原来凭记忆的那一条不对）：hyper 照连接 `is_write_vectored()` 选写法，是真的选 `Queue`（交来的 `Bytes` 照原样排着、分散写，不拷），不是才选 `Flatten`（拷进自己的缓冲）。我们的连接一路转下来（reqwest 的 `Conn`、`Verbose`、`RustlsTlsConn` → hyper-util 的 `TokioIo` → tokio-rustls 的 `TlsStream`）都照实转发，tokio-rustls 答真；明文的 `TcpStream` 也答真。rustls 每次写最多收 64 KiB 明文（`DEFAULT_BUFFER_LIMIT`）。h2 那一头 hyper 把交来的块交给 h2 排队、按窗口切帧，也不拷。所以改前多出来的那一份是我们自己的 `to_vec()`，不是 hyper 的；HTTP/1.1 和 h2 只量了 h2 那一种（量尺本来走的就是 TLS+h2），不另量 HTTP/1.1。
- 主请求出错后内核照历史重新组装再发，不拿旧的请求体重发；提前压缩的摘要请求走同一条路；`side.rs`、`once.rs` 换人时把同一个 `Request` 再发，每发一次重新编码；`miyu-http` 自己不重发。所以请求体只为上面那两样重发留着，收到响应头就不用留了。

### 选的办法

1. **编码产出片段清单**（`miyu-drivers` 的 `fragments.rs`）：`Fragments` 是一串 `Fragment`，`Text`（编好的字）或者 `Base64 { blob, size }`（某个 blob 整份的 base64，只记哈希和大小）。线上的结构里内嵌 blob 的那一格（`Inline`）照常经 serde 写，写的时候交出一个记号（`serialize_bytes`，线上的结构里没有别的一串字节），编码器自己的 JSON 写法（serde_json 的 `Formatter`，别的全用默认的紧凑写法）认得它：写下开头的引号和前缀（`data:<类型>;base64,`，照 JSON 转义）、一个 `0xFF`、结尾的引号，记下是哪个 blob；写完照 `0xFF` 切开，前面的字收成一段、那里记一段 base64。`0xFF` 在 UTF-8 里不会出现，serde_json 写出来的都是合法的 UTF-8，切不错；一张图都没有的消息不切，和原来直接写进 `Vec<u8>` 一样快（头一版用 `RefCell` 接着写，纯文字的请求每次多 230 万条指令，改成这样）。base64 的字母表里没有要转义的字，拼起来和整份写的一个字节都不差。三个驱动都走它（`Driver::fragments`）；原来的 `Driver::encode` 留着（测试、对照），是片段清单拼起来的整份字节。线上的消息写完一条放一条。
2. **发的时候边编边送**（`miyu-http` 的 `body.rs`）：编好的字转成共享的 `Bytes`（不拷）照原样送；blob 那一段在阻塞线程里一次读 48 KiB（3 的倍数，编出来正好 64 KiB）、编成 base64、经容量 1 的通道交过来，送完就扔。`Content-Length` 照片段清单算，和原来一样长。blob 读出来比量的短了、长了、读不了：请求体出错，请求断掉。
3. **哈希边送边算**：请求体的 SHA-256 跟着交出去的字节一路算，几条流共用一份，重放的从算过的地方接着算。响应头早到（401、413）、被叫停、造不出请求的：剩下的照样生成出来算完（要读 blob 的在阻塞线程里），不往外送，再报 `Sent`。`Sent` 的意思和报的时机不变（收到响应头、出错、叫停以后）。
4. **重发补回来**（`resend.rs`）：照上面查到的条件、次数，307、308 和 h2 上对方没处理的，从同一份片段清单从头造一条流再发。片段清单只引用 blob 的哈希，留着它重发不占图的内存。
5. **base64 换成 `base64` 这个库**（锁文件里本来就有 0.22.1）：标准字母表、补 `=`、不换行，和原来逐字一样。
6. **该放的当场放**：取 blob 时照原样发的图片、PDF 只核对、量大小（`Blobs::check`），发的时候才读（`Blobs::open_at`）；照字放进消息的文件照旧取整份（要认是不是文本、截前 64 KiB）。编完，主请求的 `Request`（交进来的那一份）、取来的字节当场放；收到响应头、哈希算完，片段清单放掉（还在送的那一条流送完放）。等模型回答时手里不留整份请求。

没选的：

- 「发完就放」的过渡步：主人定直接做彻底的。
- 把编好的 base64、请求体缓存成文件：不多写硬盘（主人定）。
- 在 `miyu-http` 外面另装一层 reqwest 的重试、跳转策略：流的请求体 reqwest 根本不重发，策略换成什么都没用，只能自己从片段清单造。

### 片段清单留着的账

为了跳转、对方没处理的重发，片段清单（编好的字 + blob 的引用）从编完留到收到响应头：

- 纯文字的会话：编好的字就是请求体那么大（量尺的纯文字会话约 3.3 MB），只留到响应头回来；改前整份请求体有两份（编好的、交给 reqwest 的）一直留到模型回完。
- 有图的：字那几段（20 张图的会话约 3.7 MB），图一张都不在里面。
- 送的路上：每张图最多三块 64 KiB（阻塞线程正在编的、通道里压着的、HTTP 客户端正在写的）。

### 下一步要处理的情况（「文字按消息缓存编好的段、下次只追加」那一步，这一步不做）

编好的字想按消息缓存、下次只追加新的，先得认清下面这些会改动已经编好的前缀：

1. **anthropic 的缓存打点会挪**（`anthropic/marks.rs`）：第 3、4 处（上一次请求的末尾、这一次请求的末尾）每次往后挪，`,"cache_control":{"type":"ephemeral"}` 插在前面某一块的最后一格后面；system 是空的时打在最后一件工具上。缓存的段要先去掉打点（`unmarked` 的做法）再拼、再按这一次的位置补上。
2. **anthropic 相邻同角色的合成一条**（`anthropic/messages.rs`）：tool 结果、后面跟着的 user 都写成线上的 `user`，新来的一条接在上一条线上消息的块后面，上一条的结尾 `]}` 要挪；一块都没有的消息不发。
3. **openai-chat 工具结果里的图挪位置**（`openai_chat/messages.rs` 的 `flush`）：一串 tool 消息里的图片、PDF 攒到这一串后面另起一条 user（先一句说明）；这一串再接一条 tool，那条 user 要往后挪、内容要变。
4. **思考回传看驱动和开关**：openai-chat 的 `ReasoningReplay`（`Drop`、`Echo` 照来路、`Replay` 写进哪一格、`always` 时没有也写空串），anthropic 只回传自己家带签名的、responses 只回传带加密内容的。换了端点、换了驱动或档案的开关，前面每条 assistant 都变。
5. **接着写**（`continuation`）：openai-chat 开着前缀续写的，最后那条 user 不发、半截那条 assistant 加 `"prefix":true`/`"partial":true`，路径也换；下一次不接着写了又恢复。
6. **`retext`**（`Route::retext`）：策略快照换了，驱动的占位（看不了图、文件的那几句、带名字的图片的标签、文本文件的开头收尾、替它看的图的标签）全换，前面所有用到占位的消息都变。
7. **压缩**：历史压成检查点，整个前缀重来；提前压缩到线换上的那一次也是。
8. **事实块插入**（`miyu-assemble` 的 `render.rs`）：回合开始时注入的事实和触发它的那条放在一起、排在触发的前面；人这一边的块攒着合成一条 user，碰到回复、工具结果才收；角色扮演提示排在触发后面；群聊近况排在事实后面、触发前面。新的一块可能插进还没收尾的那条 user 里。
9. **替它看的图**（`described`）：看不了图的模型，转述来了以后，前面那张图的占位换成转述。
10. **工具面**：anthropic 的 `tools` 在 `messages` 前面，工具面一变（占位工具补上的、预设换的），后面所有消息在字节里的位置都挪；openai-chat、responses 的在后面，不影响前缀。占位工具只在缺的时候补（`placeholder.rs`）。
11. **模型名在最前**：`{"model":…` 是第一段，换模型（池里换成员、出错换端点）整份的位置都挪。
12. **调用编号**：线上的调用编号照这个驱动家族的私有数据取，没有的用内核的；换驱动家族前面的编号都变。
13. **输出上限、温度、思考强度**在最后（`capped` 压输出上限、思考强度换档），只动尾巴，不碍前缀。
14. **文本文件**照快照里的三句、截前 64 KiB，图片带名字的标签照快照：同 6。

### 做什么

- `miyu-drivers`：`fragments.rs`（片段清单、`Builder`、`Inline`、认记号的写法）；三个驱动的 `encode` 改成写 `Builder`、交 `Encoded<Fragments>`（`fragments`），原来的 `encode` 是它拼起来的；`Encoded` 带一个类型参数（默认整份的字节）；`BlobBytes::size`（默认照整份量）；`Driver::blobs_whole`、`Driver::fragments`，`encode` 有默认的写法；`media.rs` 的 `inline`、`blobs_whole`；`base64.rs` 换成库，`CHUNK`、`encoded_len`；线上的结构里 base64 的几格换成 `Inline`；线上的消息写完一条放一条。依赖加 `base64`（白名单加一行，`01-架构.md`）。
- `miyu-http`：`body.rs`（`Body`、`BlobSource`、能重放的流、哈希、没送完的算完）；`resend.rs`（307、308，对方没处理的重发）；`send.rs` 的 `Attempt.body` 换成 `Body`，收到响应头报 `Sent` 后放掉请求体。依赖加 `bytes`、`http-body`、`h2`（都是 reqwest 本来就带进来的同一版），tokio 加 `rt`、`sync`。
- `miyu-store`：`Blobs::check`（只核对、量大小，一块一块地算）、`Blobs::open_at`（打开、定位，变过的先整份核对）。
- `miyu-session`：`route/exchange.rs` 收 `Cow<Request>`，照原样发的只核对、量大小，编完放请求和取来的字节，`StoreBlobs` 照 `Blobs::open_at` 读；主请求交自己那一份，旁路请求、一次性入口借着；`probe.rs` 走片段清单。

### 不做什么

- 不改发出去的任何一个字节：字段先后、转义、base64 的写法、补换行；日志里的哈希也一样。
- 不建缓存文件，不改 blob 的存法。
- 不做「文字按消息缓存编好的段」（上一节，下一步）。
- 不改 reqwest 客户端的配置（MCP 也用这个客户端）：跳转、重试补在 `miyu-http` 里。

7. 原有测试照旧全过；`cargo xtask check`、Windows 版 clippy、三平台 CI。

### 实测

2026-11-02，本机，release（`line-tables-only` 调试信息），改前 `1b712ee5d`（到这一步的底子 `75e60fac1` 之间 route、`miyu-http`、`miyu-drivers`、`miyu-assemble` 没改过），改后这一步。合成的会话（全是造的数据，临时数据根），假模型在回环上，前面一层 TLS+h2 的转发（量尺走的就是 h2），核心、假模型、头都在 `unshare -rn` 的私有网络里，绑 12–15 号核。三场：纯文字（请求体 3.3 MB）、20 张图（2560×1440 的截图，原图 15.2 MB，请求体 24 MB）、20 张图加一份提前压缩的摘要请求同时在途。窗口配到 200 万，不让核心提前压缩（摘要那一场配 100 万）。

### 风险

- 发的时候 blob 被删了、被改了（编码前核对过、发的时候长短或修改时刻变了的先整份核对）：请求体出错、请求断掉，照「发不出去」可重试；内核重新组装再发时照旧报缺 blob。`Sent` 报的哈希这时是生成出来的那些的，对不上任何一份完整的请求体。
- 读盘：核心起来以后头一回用到的图读两遍（核对一遍、发的时候一遍）；同一张图在一次请求里出现几次就读几次（改前取一次、编几份）。多读的都是刚读过的，在页缓存里；内存紧到页缓存留不住的机器上会真的多读。平时每次请求每张图读一遍，同改前。
- 一张图送的时候占一个阻塞线程（tokio 的阻塞线程池，上限 512），慢网上传得慢就占得久。
- 跳转混着来（一跳里 reqwest 自己跟的 301、302、303，加上这里跟的 307、308）各数各的十次，和改前合起来数十次不一样；单一种跳转的一样。
- reqwest、h2 升级改了重发的条件：`tests/resend.rs` 的对照测试先红。
