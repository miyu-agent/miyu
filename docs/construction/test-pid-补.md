## 施工单 test-pid 补：测试认新桥不靠进程号

状态：施工中（2026-10-12；只改测试，没有产品代码和协议的改动，技术细节照推荐定；诊断主会话和核心都认可）。

### 目的

CI run 1840 在 Windows 上 `followed.rs` 的 `words_said_while_the_bridge_was_off_are_sent_while_still_fresh` 红：`bridge_up` 等不到 60 秒，核心那一项是 `{"state":"running","pid":1268,...}`。Windows 回收进程号快，新桥拿到了和停掉的那个一样的号，`pid != before` 永远假；桥的状态文件又是「和磁盘上一样的不写」，同号、同端口、NapCat 没连着，内容和旧的一模一样，新桥不会重写。这一步让测试认新桥不靠进程号。

### 蓝图改哪几节

`docs/blueprint/onebot.md` 的「施工时定的」：第 37 条末尾补一句（认新桥的做法照第 235 条）；新加第 235 条（换桥以前先清掉状态文件，认新桥看「核心说在跑、状态文件在且进程号是它的」；为什么、没选什么）。「守着它的」不动：行为没变，守的还是那几条。

### 做法

1. `support/spawning.rs`：认新桥的判断抽成纯函数 `is_up(核心那一项, 状态文件)`，去掉 `before`，`bridge_up` 少一个参数；新加 `forget_status(root)`：先等状态文件不在或 NapCat 显示没连着（旧桥因为 NapCat 断开会再写一次，删在它前面会被写回），再删。
2. 调用处：要换桥的地方在换以前 `forget_status`（`restart`、`stop` 再 `start`、杀进程）；`followed.rs` 里原来取进程号当 `before` 的两个小函数一起去掉。
3. 先红：纯函数先照旧条件（带 `before`）抽出来，写「进程号和换桥前一样、状态文件是新写的 → 认」，对旧条件是红的；再换成新条件变绿。另一条测 `forget_status` 的等法（NapCat 连着时不删、显示断开了才删、文件不在立刻返回）。

### 不做什么

- 不改桥和状态文件的写法（「变了才写」是对的，改它是为了测试迁就产品）。
- 不加产品里的「第几次启动」之类的字段去认新桥。

### 验收

- `cargo test -p miyu-onebot --test all` 连跑 3 遍全绿；`cargo xtask check` 八项。
- 手写变异（认新桥的判断）5 个左右，都被逮住。
- 三台 CI。真实的进程号重用造不出来，Windows 上偶发的那条靠 CI 多跑几遍看。

### 风险

- 删状态文件以后，旧桥若还有没处理完的写（连续两次通知），会把旧内容写回。窗口只在「断开已写过、删之前又来一次通知」，且只有进程号撞上才会误认；先等断开再删已经把常见的一次挡住，其余留着，真撞上再查。
