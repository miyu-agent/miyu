# AE-8：MCP 的两个队列有上限

状态：已完成（2026-10-30）。发布前第二轮审查查出（R2-9，材料在 `~/.cache/miyu-audit/2026-10-30/round2-core.md`），core1 排给 99 做，项目主人同意。

## 目的

往 MCP 服务标准输入写的队列、交给跟进度那一头的队列原来不限长：服务不读标准输入、跟进度的那一头不收时，核心的内存一直涨。做成以后各最多 256 条，满了的通知丢掉，请求等空位但不超过这次调用的时限。

## 蓝图改哪几节

- `mcp.md`「在哪」`link.rs` 那一行；「怎么走」第二条新加第 7 条「排队有上限」：多少条、和谁一样、满了什么丢、请求怎么等。测试表一行。

## 定了的

- 上限 256，同核心给每条连接的出站队列（`miyu-endpoint` 的 `connection::QUEUE`）；进度队列用同一个数。
- 满了的照扩展反向通道的写法（`miyu-endpoint` 的 `reverse.rs`）：通知用 `try_send`，满了丢掉记 `DEBUG`；请求 `send().await`。等空位算进等回应的时限：这次调用写了多久就最多等多久，到点照超时收。回服务的 `ping` 在读的那个任务里，不能等（等了就读不到回应），满了也丢。

## 不做什么

- 不改等回应的时限、不改断线的判法：队列满不算断。
- 网址的服务（HTTP）不走这条连接，不动。

## 验收

1. `miyu-mcp` 的 `link::tests::notices_to_a_server_that_does_not_read_do_not_pile_up` 修前红（一万条全送到了）、修后绿；`progress_nobody_takes_does_not_pile_up` 修前红（攒下了一万条）、修后绿；`a_request_waits_for_room_only_as_long_as_it_waits_for_the_answer` 修前修后都绿，护着「等空位不超过时限」。
2. 手写变异 2 个：两个队列各放大一百倍，都抓住。
3. `miyu-mcp` 原有测试照过；本地门禁、三平台 CI。

## 风险

- 满了丢掉的进度、通知：进度本来就是给人看的、丢几条不要紧；取消丢了，服务照算完再回，回来的没人等，照旧丢掉。
- 一下子发很多请求的调用方会在等空位时排队：上限 256 远多于一个核心同时调一个服务的件数。
