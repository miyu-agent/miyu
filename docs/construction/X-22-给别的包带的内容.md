## 施工单 X-22：给别的包带的内容

状态：合了（2026-10-16，5db6498a，CI run 38836604075）。设计 `34-表情包.md` 第三节「内容包」：表情包的内容包（`miyu-memes-shorin-collection`）只带图和说明、没有程序，`miyu-memes` 要找得到它、读得到它的文件。原写法（清单 `[memes] dir`、经 `package.list`、`package.file` 读）走不通：核心不认的表整份清单报错，`package.file` 只给头、只读后台页目录。

### 起因

一个包给另一个包带东西（表情包合集、人设卡、主题），是通用的写法，不是表情包一家的。核心不认里面是什么，只管「谁给谁带了哪个目录」、让被带的那个读得到。

### 这一步做什么

1. **清单 `[content.<包>] dir`**（`miyu-config` 的 `package/content.rs`）：键是被带的那个包的编号，`dir` 是包目录里的相对目录（写法同 `[page] dir`）。只有 `bundle`、扩展包能写；写错的 `bad_content`（代码表四十七个）。
2. **`content.list {}`**（`miyu-endpoint` 的 `content.rs`）：核心拉起的扩展问「谁给我带了」，`{"packages": [{"package", "version"?}]}`，照编号排。别的连接 `not_a_provider`。不要能力。
3. **`content.read {package, path, offset?}`**：分块读那个包给它带的目录里的一份，回应同 `package.file`（`{"data", "size", "eof"}`，一块至多 512 KiB）。没有这个包、它没给调的一方带的 `unknown_package`；路径空的、带 `..` 的 `bad_params`；没有这一份、经链接指出去的 `not_found`。
4. **`content.changed`**（推送，`{}`）：核心每重读一次清单（装、卸、升级、装回出厂的包），给这个扩展带内容的包前后有一个就推；扩展再 `content.list` 自己比。不相干的装卸不推。

### 施工时定的（主会话，技术题照推荐）

- 挂在「重读清单」上，不挂在软件包列表的推送上：同版本重装（图换了、列表那一项没变）也要推。
- 前后都没有给它带内容的包不推；有的时候一次装卸至多多推一回，扩展照 `version`、自己的摘要比，开销小。
- 不要能力、不要批：东西是别的包写明了给它的，读不到别处。
- 包自己给自己带的照样列（就是它自己的目录），不另拦。

### 验收

- 清单（`package/content/tests.rs`）：照编号排、没写的空、写错的 `bad_content` 在第几行、`dir` 必写、只认 `dir`、内置包 `wrong_kind`。
- 真核心（`tests/content.rs`）：扩展列得出给它带的、不列给别人带的；读得到、`..` 和空路径 `bad_params`、别人的 `unknown_package`、没有的 `not_found`、经指出目录的链接读不到；头调 `not_a_provider`；卸、装、再卸各推一条，不相干的装不推。
- 手写变异 7 个抓住 6 个；`beneath` 换成直接拼路径的那个在 Linux 上和原来一样（`miyu_fs::read_range` 本来就不走任何一层链接），它管的是先换成真实路径（macOS 的 `/var` 是链接），三平台 CI 里 macOS 会抓。
