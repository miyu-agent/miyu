## 施工单 P-6 补：头像的候选主色归核心

状态：已合（2026-10-14，68032763，CI run 38544244850）。

### 来由

项目主人 2026-10-14 验跟随壁纸时提出：MD3 一张图有好几个主色，要能自己选。终端、网页原来各自从头像、壁纸取色。网页那边查出，它用的官方 JS 版量化里有随机数，同一张图每次挑的会抖，和终端用的 Rust 版也有两处算法不同，两个头各算各的永远对不上。项目主人同一天定：头像取色归核心，壁纸取色还归头，但用同一份代码。图纸 `docs/blueprint/personas.md`「主题色、背景图」第 4 条、`client.md`、`protocol.md`。

### 做了什么

1. 新 crate `miyu-seeds`（模块层，纯逻辑）：从一张图挑最多 4 个候选主色，打分最高的排第一。
   - 先照 `image` 的 `thumbnail` 缩到边长 128，不透明度不到 200 的像素不算。
   - 再用 MD3 的 Celebi 量化成 128 种，Score 打分（太灰、太少见的滤掉，都不合格的给 Google 蓝）。
   - 参数和终端原来取头像主色的一样，同一个头像的第一个候选不变。
   - 白名单加了 `material-colors`（种子固定的伪随机，同一张图每次一样）和 `image`（只从内存解码，五种纯 Rust 解码器）。
2. 协议：`persona.list` 的每一格、`persona.get`、`persona.set` 的回应多一格 `seeds`。没有头像、解不开的是 `null`。
   - 同一张图照字节的哈希只算一次。
   - 读盘、解图挪进阻塞线程。
3. 门面 `miyu_client::seeds`：两个头算壁纸的候选用它，和核心算头像的是同一份。
4. 选哪个由头写进人格的 `seed`，两个头看到同一个；壁纸选第几个各头自己存。

### 验收

- `miyu-seeds` 单元测试 5 条；端点测试 `persona_seeds.rs` 2 条；原来的几条照 `persona.list`、`persona.get` 逐字比的测试补上 `seeds`。
- 变异 7 个全被拦下：缩图大小、透明阈值、候选个数、`#rrggbb` 大小写、缓存的键、`persona.list`、`persona.get` 不带。
- 三台 CI 过。
