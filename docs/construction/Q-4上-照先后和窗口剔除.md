## 施工单 Q-4 上：照先后的池，窗口放不下的不挑

状态：核心的分会话做。设计 `43-旁路请求和档位池.md` 第三节第 5 条第 1、2 款，第五节第 4 条（Q-4 拆三步，主会话 2026-10-27 认可：上是这两样，中是 `quota` 和非 API 应答，下是全冷却只探一个）。主会话补的一条照做：窗口剔除用的估算和压缩判线必须是同一个口径，不两处各估一份。

### 为什么

池只有钉住、轮换两种分法，「主力加备用」写不出来：钉住的出错换过去以后一直钉在备用上，轮换的每次都换。出错换人时也不看窗口：主力放得下、备用放不下的请求照样换过去，等着被拒。

### 做了什么

1. 分法多 `ordered`（照先后，`miyu-models` 的 `pools.rs`）：每次请求从第一个成员起排候选，不动指针、不钉；第一个出错（记了冷却）的，内核当场再来时照先后取下一个，第一个冷却过了下一次回到第一个。限额照第一个成员（主力），看不看得了图照全体（`route/pool.rs`）。配置项 `pools.<id>.strategy` 多一个选项，三语名字、说明，样本重生成、图纸里嵌的样本同步。
2. 窗口剔除：请求多一格 `used`（`miyu-kernel` 的 `request.rs`，`#[serde(skip)]`，不进规范字节、不算进指纹，同 `output_cap` 的先例），内核在填 `output_cap` 的同一处照压缩判线的同一个数填（`used`：锚加锚以后的估算）。执行器挑候选时（`route/base.rs` 的 `pick`，`Seat` 多 `used`，只有会话的主请求带）剔掉窗口说得出、不比它大的（`Routes::fitting`），出错也不换过去；一个都不剩的照上下文超长报（`Unsent::TooLong` → `context_too_long`，原话写用量和每个候选的窗口，内核先压再来）。窗口说不出的照旧算放得下；辅助请求、一次性入口没有用量，不剔。
3. 主请求的用量本来就照池的限额算过压缩线（轮换取最小窗口，钉住、照先后照那一个成员），所以剔掉的只会是出错换人时窗口比主力小的那几个；「一个都不剩」只在资料半路变了这种边角才出现，没另写测试。
4. 图纸 `models.md`（配置表、第三条第 6、7 条和新的第 8 条、第四条那张表、测试表），`kernel/request.md`（`used`），`config.md`（嵌的样本）。

### 不做的

- `quota` 一类、2xx 但不是 API 应答：Q-4 中。
- 全冷却只探一个：Q-4 下。

### 验收

1. `miyu-session/tests/route_ordered.rs`：照先后的池两个会话都发给第一个、限额照它；第一个出错换到第二个，冷却过了回到第一个；钉住的池主力出错时，约四万 token 的请求不换到窗口 32000 的成员。
2. 手改 5 个都红：不剔窗口、照先后的也照指针排、内核不填用量、剔的是放得下的、配置不认 `ordered`。
3. `cargo xtask check` 全过、Windows 版 clippy、三平台 CI。
