## 施工单 PF-2：CPU 被抢时，核心晚知道发完、收完

状态：查清了，运行时的代码没改，下一步待拍板（2026-11-13）。主会话派：bm 照 PF-1 以后的核心（aa60c6493）复测「组合加码」，同一个请求按字节数对上核心日志和假模型，第 1/2/3 档中位：假模型收齐请求体 → 核心记 `request_sent` 201 / 561 / 1451 ms，假模型回完 → 核心记 `http ended` 311 / 1274 / 2983 ms，字节早就进出连接了，核心过很久才知道；每轮 `run_turn_start_hooks` 93 / 609 / 321 ms（第 4 档 5.5 秒）。先查清再改，挑收益大、风险小的做。

### 查下来的

1. **两段是重叠的，不是相加**（实测，`retest5-combo-dbg` 的 `fake.jsonl` 对 `core-full.log`）：
   - 长会话一步的回复只有 6 帧（`frames` 中位 6，第 0～4 档都是），不是几百个 token（392 是那一步的 `seen`）。假模型收齐请求体以后 15～29 ms（它自己解析 2 MB 的 JSON）把响应头和 6 帧一口气写完：第一帧到写完只隔 0.2 ms。
   - `request_sent` 是 actor 收到 `Report::Sent` 时记的，`Sent` 是发请求的任务等到响应头才交（施工 PERF-1 定的）。所以「收齐 → `request_sent`」里含假模型自己那 15～29 ms，「回完 → `http ended`」和它从几乎同一刻起算：第 1 档收齐后 201 ms 记 `request_sent`，再过 72 ms 记 `http ended`（第 2、3 档 262、495 ms）。字节到齐以后核心收完，第 1 档实际约 260 ms，不是 201 + 311。
   - 一路几跳（读代码）：`Sent`：套接字可读叫醒 hyper 的连接任务 → 读到响应头经 oneshot 叫醒发请求的任务 → 交 `Sent` 经无界通道叫醒 actor，三跳。收完：hyper 1.11 的 h1 响应体通道容量是 0（`body/incoming.rs` 的 `mpsc::channel(0)`），连接任务交一个分块、发请求的任务取走才读下一块，6 帧 6 个来回；每段增量经无界通道交给 actor。
2. **miyu-http 这一路没有可省的跳**（实测，量尺 `crates/miyu-http/tests/reply_measure.rs`）：照假模型的样子回 6 帧，发的一方照核心在派出去的任务里跑、交出来的经无界通道送给另一个任务（替 actor），测试程序和压力（bm 的 `pressure` 原样编）挤在同两个核上，运行时两个工作线程，每格 20～30 轮的中位，几遍的范围：

   | 压力（两个核上） | 收齐 → 交出 `Sent` | 回完 → `send` 收场 |
   |---|---|---|
   | 不压 | 0.03 ms | 0.04 ms |
   | 烧 3、睡醒 34（≈第 1 档） | 0.38 ms | 0.42 ms |
   | 烧 11、睡醒 167（≈第 2 档） | 17～30 ms | 17～36 ms |
   | 同上，运行时里另有 6 个忙着的任务（`MIYU_PF2_BUSY=6`） | 42～59 ms | 69～88 ms |

   - 交出 `Sent` 和收场几乎同时：响应头一读到，6 帧的来回几乎不花时间。整段就是回复到了以后，核心的线程头一回排上 CPU 的那一下。
   - 增量不交给替身（没有每段一次叫醒 actor），烧 11、睡醒 167 下 17～28 ms，和交的一样（交替跑三遍）：每段增量一次叫醒不是它。
   - 运行时多久看一眼 IO（`event_interval`）61 改成 2：69～80 对 69～88 ms，看不出差别。
   - 运行时里另有活的时候翻两三倍：线程排上 CPU 以后，还要排在别的任务后面。

   推荐的几样做法，收回复时攒着批量交、少一跳中间任务、请求发完在同一个任务里接着读，在这一路上省不出东西（推断上限几毫秒），改了只是添代码，没做。
3. **bm 里一下就是一两百毫秒**（实测加推断）：
   - 不开 `DEBUG` 的那一趟（`retest5-combo`）也一样慢：假模型回完 → 会话记 `ended` 中位 234 / 644 / 1147 ms。`DEBUG` 加 strace 那一趟慢 1.5～3 倍。
   - 单个线程一次排队多久：日志行的时刻在格式化时取，写进文件要拿锁，写进去的顺序和时刻对不上的行，就是取了时刻以后线程没排上 CPU。不开 `DEBUG` 的那一趟第 1 档有 530 行晚了 50 ms 以上（最晚 194 ms），`DEBUG` 的那一趟 1456 行，其中 148 行晚 200 ms 以上；几乎都是一行一行单独晚（同一批晚到的中位 1 行、1 个会话），不是整个进程卡在日志的锁上。第 1 档里核心的一个线程，一次排队就可能一百毫秒上下。
   - 一次阻塞线程的来回（`append` → `stored`）20 / 80 / 108 ms，同一个数量级。
   - 所以步间的大头是：一步里「换一个线程接着做」的次数（阻塞线程来回、IO 叫醒、子进程）乘每次排队的时长。pi 是单线程的事件循环，一步只醒一两回。这一条是推断：bm 没有每个线程在哪儿等的数据（strace 只停了 `fsync`、`fdatasync`）。
4. **回合开始的挂接点**（读代码估，日志里没有分段）：`actor/model.rs` 的 `turn_start` 串着等：冻结配置（阻塞线程）→ 刷新人格、找技能（两个阻塞任务并着）→ 压缩线（一般不跳）→ 记忆（摘要和卡并着，再联想，两跳）、知识库自动想起、扩展（问扩展进程）、项目指令一起等最慢的那一个。最少串着 4 跳；第 1 档每跳照 `append` → `stored` 的 20 ms 算约 80～100 ms，对得上 93 ms。300 ms 的限时只管记忆、知识库两件，`DEBUG` 日志里一次都没超时；第 4 档 5.5 秒推断是每一跳排队到了秒级。不等阻塞池、不等盘的证据也没有：没有分段，哪一跳最慢看不出来。

### 待拍板（★ 是推荐）

1. ★ **先补量**（风险低，只加 `DEBUG` 日志）：回合开始加一行 `turn start timed`，照 YC-14 的 `request timed` 记配置、人格、技能、挂接点、扩展、项目指令各等了多少毫秒；bm 下一趟开 `DEBUG` 时加 off-CPU 采样（`perf sched record` 或 bpf 的 `offcputime`），看每一跳在等什么。有了数再定第 2、3 条做不做。
2. **回合开始少串两跳**（估第 1 档省 20～40 ms、第 2 档 80～160 ms，风险中）：冻结配置、刷新人格、找技能并成一个阻塞任务；记忆、知识库、项目指令不等人格看完就起（知识库要看工具面上有没有 `kb_search`，照上一轮的快照，人格真换了的少见情形再问一遍）。注入照模块编号排的先后不变。
3. **一步里少换线程**（估最大，风险中到大，要先有第 1 条的数）：一步里两次 `append` 各一个阻塞线程来回、判权限一个、跑工具一个、发请求一个 IO 叫醒。写盘挪回工作线程不推荐：bm 开着脏页压力，`write` 会被限流，正是会卡住整个运行时的那种。可以看的是几样连着的阻塞活并成一跳（例如工具跑完的 `append` 和下一次请求取 blob）。
4. **部署上**（不改代码）：核心作为 systemd 服务本来就自己一个 cgroup，开了 CPU 控制器时 PF-1 量过前后都只有 5～7 ms；bm 的压力和核心在同一个没开 CPU 控制器的 slice 里，是最坏的情形。复测加一组「核心单独一个 cgroup」对照，看真实部署里有多少。
5. 自己驱动 hyper 的连接，把连接任务和发请求的任务并成一个：`Sent` 省一跳，要自己管连接池、TLS、代理、重发，风险大、收益几毫秒，不推荐。
