## 施工单 K-5：PDF 和网页

状态：已完成（2026-10-12 写；头一回编进核心合了又撤回，改成抽字的小程序重做、合；19 N2 定了认 Markdown、纯文本、PDF、网页 HTML，PDF 照页引用、HTML 去掉版式只留正文）。

### 目的

知识库现在只认 `.md`、`.markdown`、`.txt`：放进去的说明书 PDF、存下来的网页她搜不到。这一步认 PDF 和 HTML：抽出文字切块进索引，搜到 PDF 的说是第几页，读 PDF 照页读。

### 定了的（技术细节照推荐定）

1. **库**：
   - PDF 用 `pdf-extract`（MIT），一页一页抽；HTML 用 `html2text`（MIT），照纯文本的写法换。
   - 两个都是纯 Rust，三个平台一样编。
   - 试过 `pdf_oxide`：最新版自己编不过，不用。
   - 放进抽字的小程序 `miyu-extract`（新 crate，第 3 层），不编进核心。核心照子进程拉起它，主程序真实位置的旁边找，同 `miyu-sandbox`。一份文档拉起一次，抽完就退，等 60 秒还没抽完的杀掉。
   - 为什么放小程序：头一回编进 `miyu-store` 合了，CI 的量尺「核心空闲」从 28.4 涨到 30.0 MB，正好压在预算线上，接着合的 P-8 就红了，只好撤回。本机量了：
     - `.data.rel.ro` 从 792 KB 到 1283 KB：两个库里成堆的字符串指针表，载入时重定位，成了脏页。
     - 载入时碰到的代码、只读数据也多出 1.1 MB。
     - 放进小程序还捎带两件好处：抽坏文件卡住了杀得掉，抽的时候吃的内存随它退出还回去。
2. **PDF**：
   - 一页一页抽字，每页照纯文本切块。块的键照旧是 `<路径>#<第几块>`，块的字头一行记着第几页，搜到的时候拆出来。
   - 抽 PDF 的库遇到坏文件可能 panic，在 `catch_unwind` 里抽；抽不出来的照「读不了」跳过。
   - 一个字都抽不出来的（扫描件、只有图）跳过，说为什么。
   - 中文 PDF 常把字映射成部首的码位：Chrome 打出来的 PDF 里「子」成了 U+2F26 `⼦`，「页」成了 U+2EDA `⻚`。
     - 照 Unicode 的 `EquivalentUnifiedIdeograph.txt`（16.0.0，Unicode 许可证，原样带进仓库）换成平常的字，别的字不动，全角标点照留。`pdftotext` 也这样换。
     - 不用 NFKC：NFKC 换得了康熙部首，换不了部首补充那一段（`⻚` 原样），还会把全角标点换成半角。
3. **HTML**：
   - 换成纯文本：标题写成 Markdown 的 `#`，链接只留字、不要脚注。
   - 换出来的字照 Markdown 切，标题路径照旧。
   - 只去掉标签，不挑正文：导航、页脚的字照留。量出来吵了再加挑正文。
4. **上限**：
   - PDF、HTML 文件最大 64 MiB。
   - 抽出来的字照文字文档的 4 MiB 封顶，超过的跳过。
5. **读**：
   - `kb_read`、`kb.read` 读 PDF 的第 `page` 页，就是 PDF 的那一页抽出来的字，`pages` 是 PDF 的页数。
   - 读 HTML 的是换出来的字，照 32 KiB 分页。
   - 每次读现抽，不存。
6. **搜到的**：
   - PDF 的那一块，她看到的头一行是 `[<库>] <路径>, page <页>`（新的一句，量了登记）。
   - 协议的一块多 `page`，只有 PDF 的带。
7. **写**：
   - `kb_save`、`kb_edit` 只写 `.md`、`.markdown`、`.txt`。写 PDF、HTML 的拒，说只有这三种能写（新的一句，量了登记）。
   - `kb_delete` 照样能删 PDF、HTML（挪进回收站）。
8. 别的格式（Word、EPUB）照旧不认。

### 不做什么

- 挑网页正文（readability）。
- PDF 里的图、扫描件认字（OCR）。
- 抽出来的字缓存起来。每次读现抽，量了一份 26 页的 57 毫秒。
- 她的工具说明里不改 `page` 的说法：搜到的头一行已经说了第几页，读的时候照着写就对上。

### 验收

1. 先写测试，没实现时要红：

     - 中英文的 PDF 照页搜到（部首换成平常的字搜得到）、照页读、页数对。
     - HTML 照标题搜到、读的是换出来的字。
     - 扫描件那样抽不出字的跳过。
     - 写 PDF、HTML 拒，删照删。

   - 真会话：搜到 PDF 那一块、读它那一页。
   - 真核心：`kb.search` 的 `page`、`kb.read` 的 PDF。
2. 测试用的 PDF 放进仓库（小的，几 KB 到几十 KB）。
3. 手写变异全被逮住；门禁全过；三台机器的 CI 全绿。

### 做了以后

- PDF 每页抽出来的字头尾常带空行（排版留下的），去掉了，读的时候字从头一行起。
- 中文测试用的 PDF 照 Chromium 打（54 KB），怎么打的写在 `crates/miyu-extract/tests/fixtures/README.md`。打出来的「页」是 U+2EDA，NFKC 换不了，改成照 Unicode 的对照表换。
- 量了 token：PDF 那一块的头一行 11（有标题的那一行 10），写不了的拒绝 22，登记了。
- 手写变异头一回 18 个，17 个逮住。活着的一个是「PDF 也照 32 KiB 再分页」：一页 PDF 抽出来的字到不了 32 KiB，测试的数据上一样，当等价的。
- 改成小程序以后又写了 20 个（小程序、拉起和等它、旁边找它，加头一回的几个照新地方再来）：「参数多一个照样抽」头一回活着，补了多一个参数的那种以后逮住；「测试里换小程序时不带家目录」活着：那个换法只有测试用，测试里没有同时挂 `~/` 的，核心自己造的照带。
- 没测到的三处：抽出来的字超过 4 MiB 才跳过（要几兆字的网页，调试编的 html5ever 太慢），抽字的库 panic 接住（手里没有让它 panic 的 PDF），等 60 秒杀掉（要一个卡住的小程序）。
- 2026-10-12 头一回合进 main（084a061f）以后撤回（60f72438），原因见「定了的」第 1 条；改成小程序以后本机量空闲核心回到撤回前的样子（见下一条）。
- 改成小程序以后本机量（release，空闲核心，三回）：PSS 29.4 到 29.6 MB，撤回前 29.1 到 29.4，K-5 头一回 30.9 到 31.3；匿名 12.3 MB，和撤回前一样；`.data.rel.ro` 回到 792 KB；`miyu` 57.37 MB（撤回前 57.32），`miyu-extract` 4.1 MB。
- 零页的 PDF 原来兜成一页空的，变异查出来测不到、也碰不到，去掉了：读第 1 页说没有这一页。

### 风险

- 依赖多了一百个上下的包：编译时间、CI 时间会涨，量一下。
- 恶意构造的 PDF 可能让抽字的库卡住或者吃很多内存：在小程序里，卡住的 60 秒杀掉，内存随它退出还回去。
- 一份 PDF 拉起一次小程序：Linux 上几毫秒，Windows 上慢些，几千份的库头一次补要多等一会儿。量出来是问题再改成一次抽一批。
- 很大的 PDF 头一次补慢：抽一份 26 页的 57 毫秒，几百页的要几秒。
