## 施工单 X-20：扩展往系统提示词尾部放一段

状态：施工完（2026-10-16），待合。设计 `34-表情包.md` 第五节第 5 条：项目主人 2026-10-16 先提「开会话的扩展给会话插一段」（原 X-20），又提「软件包自己的几行」（原 X-21），最后定静态、动态统一成一个方法，原来两步合成这一步。

### 起因

接入QQ 要照群、照私聊调她的说法，表情包这类包要一直让她记着几句规矩；有的固定、有的随时变。统一成一个方法：扩展往 system 尾部放一段。

### 这一步做什么

1. **方法 `system.append {content, session?}`**（`miyu-endpoint` 的 `appends.rs`）：不写 `session` 的管全部会话，写了的只管那一个、优先；`content` 1 到 4000 个字，写 `null` 去掉那一层。只给声明了新能力 `context.system` 的扩展（能力表十四个）：不是核心拉起的 `not_a_provider`，没声明的 `needs_approval`。只记在内存里。
2. **怎么进 system**：工具面上有这个包的工具的会话才带（`miyu-session` 的 `appended.rs`）；原文照放、不套包的编号，照包的编号排，接在整段 system 的最后（风格锁后面，项目主人定的「尾部」）。快照多一格 `appended`（包的编号到原文），没有的不写、字节和以前一样。
3. **什么时候换**：造会话时照这一刻的钉进快照；回合开始经 X-16 的端口 `HooksPort::appended` 问一声，和钉的不一样就照新的拼一份快照（整段重算一次，同改人格文件那条路）；包卸了、预设关了它的下一轮去掉。核心重启以后照钉的，扩展再设一样的不再换。
4. **拿掉的**：原 X-20 的 `venue.session` 的 `note`、原 X-21 的清单 `[prompt]` 表都没进 main，不留。

### 施工时定的（主会话，技术题照推荐）

- 要单独批的能力 `context.system`：它影响每一轮、改一次整段重算，和 `context.inject` 不是一个分量（项目主人两次没有另说，照推荐）。
- 拒绝照用已有的两个码，不另加：`not_a_provider`（不是扩展）、`needs_approval`（没声明，`data.capabilities` 写明缺哪个）。
- 只带技能、MCP 服务、没有程序的包调不了方法，放不了；以后真有需要再给清单加写法。
- 扩展交的字核心不改写、不量；由扩展自己登记（作者说明写上）。

### 验收

- 真核心四个测试扩展（`tests/system_append.rs`）：两个声明了的照编号接在 system 最后、造会话时就钉进快照；改了下一轮换上；`null` 去掉以后和没放过的逐字节相同；没声明的 `needs_approval`；空串 `bad_params`；工具只给群的不带。
- 内存表（`appends/tests.rs`）：单给会话的优先、去掉了退回全部的、全部的去掉了是去掉。
- 拼法（`miyu-policy` 的 `appended/tests.rs`）：照编号、接在风格锁后面、没有的一字不变。
- 手写变异全抓住（9 个）。
