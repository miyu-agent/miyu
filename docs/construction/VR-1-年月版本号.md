## VR-1 版本号改成 年.月.这个月第几版

状态：施工完，待 core1 审（2026-11-06）。项目主人 2026-11-06 定写法和范围，core1 转来；设计 `59-发版.md` 加第十节「版本号」，
第五节第 2 条、第七节第 7 条照它改。

### 目的

原来定的第一个正式版是 `1.0.0`。主人改成照 Home Assistant 的写法：`年.月.这个月第几版`，从 0 数起、月份不补零，预发布
`2026.11.0-rc.1`。核心、终端、网页、托盘四件统一用这套，扩展包照旧 semver。终端、网页、托盘三个仓库 core1 去通知，这一步只改核心。

### 定了的（core1 2026-11-06）

1. 工作区版本留在 `0.0.0`，这一步不定号；先加 `cargo xtask version`，到时一条命令改好、查好。
2. **演练（选 A）**：`release.yml` 照旧要求标签是 `v<工作区版本>` 或 `v<工作区版本>-rc.N`，另查工作区版本的写法。规则只有一条，
   演练前先用 `cargo xtask version` 定号，下一次演练（rc.6 以后）就是 `v<那个月>.0-rc.1`。工作区还是 `0.0.0` 时打不了演练标签。
3. AUR 的 `pkgver` 照 AUR 的规矩写：`2026.11.0rc1`。
4. 文档里「1.0 前」「1.0 后」「1.0.0」改成「首个正式版前、后」；`docs/reviews/` 下的旧审查记录不改。
5. PK-2 的 semver 比较、`miyu upgrade`、Homebrew、`cargo xtask packaging` 都照版本字符串走，不改逻辑，加测试证明比得对。
6. 安装包格式对版本号有限制的（MSI 主、次版本最大 255、第三段 65535；deb 的 `-` 是修订号；rpm 不许 `-`），在各自仓库换算，
   托盘仓库自己做；设计 59 第十节第 6 条只写约束和这一句（core1 2026-11-06，网页会话查出的）。

### 做了什么

- **`cargo xtask version <年.月.序号>`**（新的 `xtask/src/version.rs`）：
  - 写法照 `PATTERN`：年四位、不以 0 开头；月 1 到 12；序号 0 或不以 0 开头的数；不对的说清哪一段不对；
  - 只改 `[workspace.package]` 里那一行 `version`（正好一行，不是的报错，换行原样留着）；
  - 跑一次 `cargo metadata` 让 `Cargo.lock` 跟着改，再把两边读回来：都要是这一版、写法都对；
  - 只收正式版，预发布照旧由 `release.yml` 在 CI 机器上临时改（RL-2补2）。
- **`release.yml`**「标签和版本对得上」那一步多一条 bash 正则，写错了停下，提示先用 `cargo xtask version` 定号。正则同 `PATTERN`，
  `the_release_workflow_checks_the_same_pattern` 守着两边一样。
- **`cargo xtask packaging`** 的 `@PKGVER@` 改照 `pkgver()`：`-rc.` 换成紧跟的 `rc`，别的 `-` 去掉（原来是只去 `-`，写成 `rc.5`）。
- **示例的版本号**：清单 `[package] miyu` 的报错（`bad_miyu` 三种语言、读清单的那一句）、作者文档 `manifest`（中英）、蓝图
  `packages.md`、`cli/upgrade.md` 的样子，例子从 `0.2.0`、`1.0.0` 换成 `2026.11.0`。
- **文档**：设计 59 第十节；设计 61、65、66，施工单 RL-1、LP-1（变基到 4ddbadfa0 时新进来的那一处）的「1.0」换成「首个正式版」；施工单 RL-5 的 `@PKGVER@` 补一句；
  `packaging-test.yml` 的例子和造的假发布换成 `2026.11.0-rc.1`。
