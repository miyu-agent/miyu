## 施工单 B-3：流式回应有上限

状态：合了（2026-10-22，33c10bdc）。漏洞排查会话 2026-10-22 交来、复现测试是红的（补丁 `~/.cache/miyu-audit/core-robust-tests.patch`）；主会话排给 core2，上限由 core2 定。只有技术细节，直接做。

### 目的

供应商、中转站一直往下发、就是不收尾的流（一行一直不换行，或者一条事件的 `data:` 一行接一行、一直没有空行），三家驱动共用的 SSE 分帧（`sse.rs`）把还没收全的一行、这一条的 `data` 一直攒着，没有上限；读流那一头只有空闲超时（`miyu-http` 的 `send.rs`），不停地发就永远不超时，攒到核心的内存用完。做完以后一条事件连同还没收全的那一行攒过 64 MiB 就不再收，解码器照可重试的出错收尾、断开这一次。

### 蓝图改哪几节

- `drivers/openai-chat.md`「SSE 分帧」：多一条上限，攒过了怎么收尾；anthropic、openai-responses 两页本来就写「共用 `sse.rs`」，不另写。
- 定的：一个上限 64 MiB，管一条事件连同没收全的那一行（主会话建议单行 16 MiB、单个事件 64 MiB；一条事件里一整张 base64 的大图可能就是一行，单行不另设更小的上限，免得误伤）。

### 不做什么

- 不加整个回应的总时长、总字节上限：一条一条交出去的事件不攒，长回应本来就该收得下。
- 不改空闲超时。

### 验收

1. `cargo test -p miyu-drivers --test all robust_streams`：三家的解码器喂一行一直不换行的、一条一直不空行的，都在上限附近停下、`finish()` 带错。修之前是红的。
2. `cargo test -p miyu-drivers --lib sse`：正好 64 MiB 还收、多一个字节就不收，清掉攒的，后面再来完整的事件也不交；一行一行不长、一条事件一直不空行的也停。
3. 手写变异，七个都红：去掉上限那一道；只看还没收全的那一行、不算 `data`（一条一直不空行的那条红）；攒过了以后还接着收（后面完整的事件交出来了）；攒过了只记一笔、不清掉攒的（`finish()` 交出半截）；三家解码器各去掉看 `overflowed` 那一句，`robust_streams` 里那一家红。
4. 门禁全过；碰驱动，推 `step/` 过三台 CI。

### 风险

- 上限太小误伤真回应：64 MiB 一条事件远大于现在见过的（工具调用的参数、思考、图都是一段一段来的）；真撞上了照可重试报，日志里写着超了多少。
