## 施工单 YC-13：列会话带上限不扫全部

状态：施工中（2026-11-10）。压测报告 O3，YC-9 量出来要改的那一件。

### 为什么

`session.list` 带了 `limit: 50`，耗时照样跟着会话总数涨（压测 100、1000、2000、5000 个会话：5.1、11.8、16.4、26.6 毫秒），不带上限的 5000 个会话中位 230 毫秒。查下来日志那一头本来就是够数就停的，后面的会话一个都不读；涨的是索引这一头：

1. 列一次把索引整张表解出来三遍（`scan` 一遍，连同子孙的 token、默认工作区各一遍），每一行 24 格都解。
2. 连同子孙的 token 给列出来的每一项各排一遍「谁是谁的子会话」：带上限是上限乘会话数，不带上限是会话数的平方（5000 个会话时占了大半）。
3. 会话列表的推送算一个会话的一项，也是整张表解三遍。

### 做什么

1. 带 `limit` 的，索引的行照放会话的目录的先后一批批读（`list/pages.rs`、`SessionIndex::rows_between`）：一批是目录里挨着的一截，照两头的编号问；第一批照上限、至少 32 个，后面一批比一批大一倍。全要的读一批就够，挑得严的走完全部也只问十几次。不带 `limit` 的照旧一次读全部。
2. 认父子只读每一行的 `id`、`parent`、`tokens` 三格（`SessionIndex::links`），读一次，token、默认工作区共用；子会话的关系排一次，每一项共用；默认工作区只顺着列出来的往上追，不抄整张表。
3. 算一个会话的一项（`one`）只问它那一行。
4. 列出来的会话、先后、每一格都不变。蓝图 `protocol.md` 的 `session.list` 第 3 条、`store/index.md`「怎么走」第 3 条跟着写。

不做：放会话的目录照旧整个读一遍（目录才是真相：删了的、索引还没有的都照它）；不带上限时每个会话十来次文件系统调用（读目录、打开日志看末尾、看是不是存档）不动，那是「照到的是不是日志现在的末尾」这一条保证的价钱；不给索引加列、加 SQL 索引（结构不变，不重建）。

和以前不一样的一处：带上限时走不到的那一截里有读不懂的行，这一次认不出来、不重建，等走到它的那一次。

### 验收

- `list/tests/limited.rs`：带上限的就是不带上限的头几个，一字不差（各种各样的会话、四种挑法、空的索引先带上限列、跨批、索引缺行、目录没了行还在、日志比索引长）；200 个会话里列 5 个，从索引里读的整行不超过 50。先红：改之前读了 400 行。
- `miyu-store` 的 `index/tests/slices.rs`：一截的行两头都算、和读全部的是同一行；三格和整行对得上；读不懂的照实报。
- 量尺（`limited` 里标 `#[ignore]` 的那一条，release，中位）：

  带上限的剩下那一点还跟着会话数走：读一遍放会话的目录、读一遍三格。
