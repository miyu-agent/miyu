## 施工单 V-42：请求体按条留着编好的历史

状态：已完成（2026-11-04）。V-40 找大头第 7 项；项目主人 2026-11-03 拍板做。

### 为什么

V-40 量的小会话每轮（4 次请求、3 次 shell），核心用户态指令里组请求体（`OpenAiChat::fragments`）占 28%，和上下文一样大、和日志总长无关：同一轮的几次请求、前后两轮之间，前面那一大段没变的历史每次都重新拷成线上的结构、重新转义、重新写成 JSON（工具调用的参数、思考的私有数据还要每次重新解析一遍），system、工具面也每次重写。

### 项目主人拍板的（2026-11-03）

- **做**。代价是每个正在对话的会话多常驻一份编好的历史（大致和上下文一样大），会话退下就放；不落盘、不写缓存文件。
- core1 定的验收，三条都要过：
  1. V-38 的金样（`route/exchange/golden.rs`、`samples.rs` 那四份 SHA-256）不变；
  2. 请求形状探针那一类逐字节对比全过；
  3. 真端点两轮 `cache_read` 不掉（提示词缓存命中不变少）。

### 照的图纸

- `docs/blueprint/drivers/openai-chat.md`「留着编好的历史」（这一步加的）、「对外的样子」；`anthropic.md`、`openai-responses.md` 的 `fragments_memo` 一行；`session/actor.md` 第 8 条第 5 款第 2 点。
- V-38 施工单「下一步要处理的情况」那 14 条（下面逐条写怎么处理）。

### 选的办法

**按消息留，照原样逐条比，不靠哈希。** 一个会话一份 `Memo`（`miyu-drivers` 的 `memo.rs`），路由里放着（`miyu-session` 的 `route.rs`，`Arc<Mutex<Memo>>`），主请求编码时交给驱动（`Driver::fragments_memo`），旁路请求、一次性入口、探测照旧整份编（`Driver::fragments`）。里面留着：

- 编的时候照的设置：驱动家族、openai-chat 的开关（`Compat`）、占位的几句（`DriverTexts`）、模型能收什么（`Inputs`）、请求里图的转述（`described`）；
- 上一次编过的每一条消息（原样的一份）；每条编的时候查过的调用编号（和当时对出来的线上编号）、带来的调用编号、用过的 blob（大小、要不要整份）；
- 各驱动自己留的「这条消息自己写成的那一截」（片段，图片、PDF 照旧只记 blob）：openai-chat 是线上的那一条，tool 另留挪出来的图片、PDF（线上的结构，没编）；anthropic 是角色和一块一块（不带打点，记着能不能打点）；openai-responses 是几项；
- system、工具面原样的一份和它们编好的那一截。

下一次编码：

1. 设置有一样和留着的不同，整份扔掉。
2. 消息逐条比（`==`，就是 memcmp），从第一条不一样的起扔掉。
3. 剩下的里面，查过的调用编号这一次对出来的不一样（后面的消息带来了同一个编号，后来的说了算），或者用过的 blob 这一次没取到、大小不一样，从那一条起扔掉。当时就没取到、编码却成了的 blob（anthropic 不收的图片类型换成了字）编出来的和它无关，不记。
4. 剩下的接着用；后面的照 `Writer::one`（各驱动原来写一条消息的那一段，单独拿出来，整份编也走它）编、留下。
5. 照原来的排法把留着的和新编的排成请求体：openai-chat 一串 tool 后面挪出来的图片照 `Writer::flush` 现拼那条 user，接着写时最后那条 user 不发、半截那条 assistant 现编加字段（留着的是不加字段的那一份）；anthropic 相邻同角色合成一条、一块都没有的不发，缓存打点照 `marks::place`（改成认一个 `Shape`，整份编、现排两样都给它）现算、补在块的最后一格后面；各家头尾（模型名、输出上限、温度、思考强度、`stream`、`store`）照这一次的写；拼的时候照留着的字先留够地方。
6. 编码出错（缺 blob）整份扔掉；锁坏了（编到一半 panic 过）整份扔掉、清掉坏的标记。

没选的：

- **内容哈希做键**：V-40 的建议。指纹用的快哈希（`Quick`）能被造出碰撞，群里别人发的话照它算会发错字节；换成带密钥的 SipHash 每个字节约要 2～3 条指令，吃掉一半省下来的；逐条比是 memcmp，每个字节不到 0.2 条。代价是多留一份原样的消息（见下面「多占的内存」）。
- **只留一个前缀、找「安全的切点」**：anthropic 的合并要看后面的消息（中间一条一块都没有，前后两条 user 会合成一条），切点认错就发错。按消息留、每次现排，没有这个问题。
- **请求体和留着的共用 `Bytes`、不拷**：要改 `Fragment` 的公开写法，请求体会碎成几千段；拷一遍是 memcpy，量下来不显眼。

### 不做什么

- 不改发出去的任何一个字节、每条消息的位置、路径、报的错。
- 不建缓存文件，不落盘；旁路请求、一次性入口、探测不留。
- 不改内核：请求还是每次照历史整份组装。

### 实测

2026-11-04，本机，release（`line-tables-only` 调试信息）；改前 origin/main `ed0ca1e6a`，改后这一步。全程在 `unshare -rn` 里，假模型在回环上（openai-chat，DeepSeek 写法的流），临时数据根，核心绑 8–11 号核。每次照同一份事先造好的数据根新拷一份，先说一轮预热、等 3 秒，再量 N 轮（一轮四次请求、三次工具）。三场：

- **短会话**：新开的会话说 40 轮，每轮三次 shell `cat` 1.2 KB，最后一次请求体 311 KB。
- **长会话**：事先长到约 1.2 MB 的请求体（32 轮、每轮三次 `cat` 9 KB；按假模型的算法约 30 万 token，窗口配到 100 万不让它压缩），再说 20 轮。
- **带图会话**：事先 7 轮、每轮三次 `read` 一张 640×400 的 PNG（20 张轮着来，每张约 650 KB），再说 20 轮；最后一次请求体 72 MB（大头是图的 base64）。

**指令**（`perf stat -e instructions:u -p <核心>`，只套量的那 N 轮，只算核心自己，5 次中位；五次之间几乎不差）：

| 场景 | 每轮用户态指令 | 每轮 task-clock |
|---|---|---|
| 短会话 | 64.1 → 53.8 百万（−16%） | 25.2 → 24.5 ms |
| 长会话 | 132.3 → 75.7 百万（−43%） | 37.5 → 32.8 ms |
| 带图会话 | 1647.6 → 1642.2 百万（−0.3%） | 234 → 235 ms |

带图的每轮大头是 72 MB 请求体的 base64、SHA-256、TLS 前的拷贝（V-38 以后照原样），历史里的字只占一点，所以几乎不变。

**组请求体占核心的多少**（另编一份带帧指针的 release，`perf record -e instructions:u -c 2000000 --call-graph=fp -p <核心>`，只算核心自己的线程，样本的调用栈里有 `Driver::fragments`／`fragments_memo` 的占多少；3 次中位。头一遍用 `-c 200000` 被内核限流（`perf_event_max_sample_rate` 16000），丢样不均，作废重量）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 短会话 | 33.7% | 3.9% |
| 长会话 | 59.0% | 4.0% |
| 带图会话 | 0.5% | 0.2% |

改后剩下的是逐条比、拷留着的字、现排和新来的那一两条。

**内存**：

- heaptrack `--record-only`，只看 `heaptrack_print` 的汇总和 massif 时间序列里量的那 N 轮那一段（脚本一行行读，不整份进内存）；每次先空起一回同一个版本的核心写好模型目录的缓存（缓存照二进制记，不然改后每回从头读 5 MB 的目录，整个进程的峰值落在那里）；5 次中位：

| 场景 | 量的几轮里堆的最大 | 量完那一刻的堆 | 整个进程的堆峰值 |
|---|---|---|---|
| 短会话（请求体 311 KB） | 3.98 → 4.65 MB | 3.13 → 4.03 MB | 8.35 → 5.12 MB¹ |
| 长会话（请求体 1.19 MB） | 8.59 → 11.46 MB | 4.13 → 6.82 MB | 10.95 → 12.70 MB |

- 同一批 `perf stat` 那 5 次里每 5 ms 读一次 `RssAnon`（中位）：量完那一刻 短会话 9.5 → 9.5 MB、长会话 14.6 → 15.7 MB、带图 8.8 → 9.0 MB；峰值 10.0 → 9.8、16.4 → 16.9、9.1 → 9.4 MB。

### 真端点

core1 验收第 3 条。opencode-go 的免费模型 `space-bunny-free`、`longcat-2.5-preview-free` 各试一次（各 2 次调用），都回 `HTTP 400: Upstream request failed: Model is unavailable`，照规矩换 `deepseek-v4.1-flash`（同一家）。临时数据根、隔离的家目录，key 只 source 进环境；新开会话说两句（每句一次主请求，第一句另有一次起标题），只读日志里 `model.called` 的用量几格。

头一回两句隔 2 秒：改前第二句 `cache_read` 是 0（这一家的缓存几秒后才能用），改成隔 20 秒：

| | 第一句（`uncached`） | 第二句 `cache_read` / `uncached` |
|---|---|---|
| 改前 | 4355 | **4352** / 39 |
| 改后（第一回） | 4352 | **4224** / 148 |
| 改后（第二回） | 4391 | **4352** / 59 |

DeepSeek 照 64 个 token 一块存：第一句 4355、4391 个 token 存下的都是 4352（整块全中）。改后第一回少中了两块（4224），同样的字节再来一回又全中，是对方那边的抖动；发出去的字节和改前一样由金样、对照守着。一共调了 16 次（免费模型 4 次都是 400 没计费，隔 2 秒那一回 3 次，隔 20 秒三回 9 次）。

### 多占的内存

常驻多出来的就是 `Memo`：量完那一刻的堆多 0.9 MB（短会话，请求体 311 KB）、2.7 MB（长会话，1.19 MB），大约是请求体里的字的 **2.3～2.9 倍**，比拍板时估的「大致和上下文一样大」多一倍多：一份是原样的消息（拿来逐条比），一份是编好的字，再加每条消息、每一块的小分配。会话退下就放（路由跟着会话走）。

要压到一份左右的办法（这一步没做；2026-11-04 报给项目主人，主人定照现在的留两份，不改哈希）：不留原样的消息，改留每条消息带密钥的 SipHash（核心起来时随机定钥匙，外人造不出碰撞）。省下一份的内存，多的是每次请求把整段历史过一遍哈希，约每个字节 2～3 条指令，长会话每轮约多 1000 万条（省下的 5600 万条里还回去两成）；理论上有 2⁻⁶⁴ 的碰撞机会（发错字节）。

### 风险

- 留着的东西和这一次的对不上却没扔：对照测试、变异守着；设置、消息、调用编号、blob 四样之外，驱动编码还看什么的，要加进设置（加新的开关、新的占位、新的取 blob 的办法时记着）。
- 多占的内存跟着上下文走：长会话、开着很多会话时多一些；会话退下就放。
- 轮换的池里成员不是同一个驱动家族（或开关不同）的：每次请求设置都变，每次整份扔、整份编，比改前多一次拷消息、按条分配（同一家的池照样接着用）。
- 两个主请求同时编（提前压缩的摘要请求和主请求同时在途）排着拿锁，编码本身很短。
