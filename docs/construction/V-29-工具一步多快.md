## 施工单 V-29：工具一步多快

状态：已完成（只量、找慢点，不改核心）。2026-10-31 项目主人：每个工具都要够快，agent 干活时这一段占的时间最长，先量清楚。原则照 2026-10-30 定的：不为数字好看省、不改量法凑数，挪到子进程的开销算进去。

### 为什么

模型发出一个工具调用以后，核心多久把结果送回模型，以前没量过：量尺只量启动、内存、长会话上的投影和落盘。要知道这一段里核心自己的开销（收回答、判权限、沙盒、落盘、组装下一次请求）和工具本身干活各占多少，再和 jcode 比。

### 做了什么

1. 量尺加一场「工具一步」（`cargo xtask perf --tools 30`，蓝图 `perf.md`「工具一步」）：
   - 假模型照剧本回工具调用（`fake/script.rs`），一轮里同一种调用一次接一次；量假模型把带调用的回答连同 `[DONE]` 写完，到读全带着结果的下一个请求头；两头各读一次核心的 CPU：线程的 `schedstat`，核心放进自己的 systemd scope 后再读 cgroup，连 `miyu-sandbox`、`bwrap`、命令本身都算（`cpu.rs`）。
   - 十四种调用，工具名、参数照出厂预设的工具表：`read`（小文件、8 MB 文件末尾 200 行、列目录）、`write` 4 KB、`edit` 一处、`grep`（只列文件、带行）、`glob`、`shell`（`true`、`echo`、`cat` 小文件，工作区一级关进沙盒、完全放开不进沙盒各一遍）。工作区里有一份这个仓库 `crates/` 的拷贝（3152 个文件、26 MB），起成一个新的 git 仓库。
   - 「什么都不做」的对照：同一句回答不带调用，量尺收到 `turn.ended` 当场再说一句。
   - 拆段：不改核心，读会话日志（`message.assistant`、`tool.result` 的时刻）和运行日志（`ended`、`running`、`ran`、`request`；`--tools-log debug` 另有每条输入、每个动作一行），几十步取平均（`tools/split.rs`）。每次调用的结果都查过是 `ok`。
2. 和 jcode 比的测具 `bench/rivals/toolstep.py`（假模型 `toolfake.py`，调用 `toolkinds.py`）：同一个 Python 假模型，两家各收到同样意思的调用（jcode 照它自己的 `read`、`write`、`edit`、`agentgrep`、`bash`），每种调用两家挨着量；Miyu 走 `miyu ask`，jcode 走 `jcode run`，家目录都在临时目录里，不碰本机的 `~/.jcode`，不调真模型。
3. 结果在 `docs/perf/2026-10-30-tools-linux-x86_64-{1,2,3}.*`（出厂 `info` 量三遍）、`-拆分.*`（`debug`，只用来拆段）、`2026-10-30-toolstep-v29.*`（和 jcode 比）。

### 怎么验

1. `cargo test -p miyu-perf`：剧本照请求体里有几次结果回下一次调用、写完交来时刻；`cpu.stat`、cgroup 的读法；运行日志一行的读法、时区、各处平均和排先后、结果不是 `ok` 的报错；`--tools` 要 `--tree`。`python3 -m unittest discover -s bench/rivals -p 'test_*.py'`：剧本、每一步怎么算、两家的调用和量尺一一对上。
2. 本机：`cargo xtask perf --tools 30`（再跑一遍 `--tools-log debug --tag 拆分`）；`python3 bench/rivals/toolstep.py --jcode <jcode> --samples 20 --cpus 12-15 --into docs/perf --tag v29`。
3. `cargo xtask check` 全过。

- 同测具那一列量的时候负载涨到 21～22，比量尺三遍（12～14）慢一截；两家是挨着量的，比的时候看同一行。
- 对照「什么都不做」：回答写完到下一个请求 p50 14.2～20.8 ms，其中写完到量尺收到 `turn.ended` 12.1～19.1 ms（回合结束这一批要同步了才推），收到 `turn.ended` 到下一个请求头 1.9 ms（p95 2.3～2.7）：量尺再说一句、核心收下、回合开头、组装、发出，这是底子。工具一步不等同步（`tool.result` 只写不同步、带调用的回复在后台同步），所以 `read` 小文件一步比对照还短。

**一步拆开**（`-拆分`，`debug`，负载 14，`read` 小文件一步 2.3 ms，回答写完算 0）：

| 到这一刻 | 平均（毫秒） | 这一段是什么 |
|---|---|---|
| `ended`（actor 收到说完了） | 0.14 | 读完流的尾巴、交给 actor |
| `input stored` | 0.67 | 回复连同调用写进会话日志（阻塞线程里写，同步在后台），推给头 |

| `sent` | 1.97 | 选端点、编码、发出 |
| 假模型读全请求头 | 2.31 | 回环上连接、发头 |

工具以外的这几跳加起来约 1.9 ms，`read` 小文件本身 0.43 ms。结果越积越多，「写下结果、组装」跟着长：一轮里第三十次 `grep` 带行时 3.8 ms（`tool_done` 33.65 → `call_model` 37.45），`read` 大文件 1.1 ms。

### 慢在哪（照影响排）

剖析：帧指针的 release（另一个目标目录），`perf record -e task-clock:u --user-callchains -g` 录整场（只录得到用户态，内核里的同步、建命名空间看不见），`strace -f -tt -T` 看同步。

1. **`write`、`edit` 等一次同步**：墙上 13～33 ms，核心 CPU 只有 3 ms。`miyu_fs::replace`（`crates/miyu-fs/src/replace.rs` 的 `at::replace`）写临时文件后 `sync_all` 再改名，strace 里这一次 5～40 ms；同一时刻后台正在同步这一步带调用的回复（`fdatasync` 会话日志，V-19），btrfs 上两次同步排在一起。小内容不建 blob（V-18），没有别的同步。jcode 同样的写 12～13 ms，CPU 8 ms。
   - 建议：要不要每次写都同步，是崩溃安全和速度的取舍，请项目主人定。可选：写完不同步、交给会话日志下一次提交点一起同步（崩了可能留下改名前的旧文件，日志里也没有这一步）；或者先不动，只把回复的后台同步错开（收益看盘）。
2. **`grep`、`glob` 大半花在走目录上**：`grep` 一次 CPU 33～40 ms，在 `grep::grep` 里搜文件本身（`grep_searcher`、开文件）约两成，走目录六到七成：
   - `walk::each` 的 `filter_entry` 对每个目录调 `Fence::keeps_out`（`crates/miyu-basesystem/src/walk.rs`），拿数据根和这台机器上每一个私密目录逐个 `within`（`Path::starts_with` 一段段比），约占 `grep` 的 23%。`Fence::from` 只去掉了包住搜索起点的那几个，和起点不相干的（绝大多数）每个目录都比一遍。建议：`from` 里只留落在起点下面的，别的这棵树里碰不到。
   - `walk::relative`（同一个文件）每个文件 `strip_prefix` 再一段段拼字，约 14%。建议：照起点的长度直接截。
   - `ignore` 每个目录找、读 `.gitignore`（`create_gitignore`）约 12%，ripgrep 一样，不算浪费。
   - 走目录是单线程（`WalkBuilder::build`）。jcode 的 `agentgrep` 墙上 21～28 ms、CPU 31～34 ms，是并行走的。并行省的是人等的时间、CPU 不省，要不要做请定。
   - `glob` 一次 20 ms（同测具 26～28 ms），也是同一个 `walk::each`，上面前两条一样适用。
3. **`read` 大文件整份逐行解字**：8 MB 文件读末尾 200 行 17.5～21.7 ms（jcode 14.5～16），全是 CPU。`read::lines::read`（`crates/miyu-basesystem/src/read/lines.rs`）里：每一行都 `from_utf8_lossy` 成一个新的字串、拷进新的 `Vec`，不在这一页的也一样（约四成）；找换行用 `iter().position`（约 25%）；整份算 SHA-256 约 28%（她读过的文件要这个哈希，`write` 前核对，省不掉）。读第一页也要把整份过一遍（数行数、算哈希）。建议：页外的行只数换行、不解字不分配；找换行用 `memchr`。哈希照旧。
4. **沙盒每条命令多 5～6 ms、CPU 多约 5 ms**：`shell true` 关进沙盒 6.6～8.3 ms，不进 2.3～3.0 ms；连子进程的 CPU 8.9 对 3.8 ms，核心自己的线程两边一样（约 2 ms），多出来的全在子进程：`miyu-sandbox run` → `bwrap` → 里面再一次 `miyu-sandbox`（Landlock、seccomp）→ shell，外加每条命令一个看门的 `/bin/sh`（`miyu-sandbox/src/lifeline/unix.rs`）。用户态里这些进程加起来每条不到 1 ms，大头在内核（建命名空间、挂载、几次 exec），这台机器上只录得到用户态，没拆开。建议：先在能录内核的机器上拆这 5 ms，再看是复用一个关好的沙盒（长住）还是少 exec 一次。
5. **每一步固定约 1.9 ms 的几跳**（上面的拆段）：写回复 0.5 ms、判权限 0.3 ms、写结果加组装 0.3 ms、编码发出 0.2 ms，每一跳都过一次阻塞线程或任务。建议：判权限和写回复并着做（判权限不用等回复落了盘），能省约 0.3 ms；别的单看都小，不值得为它改结构。
6. **结果越积越多，组装跟着长**：上面一轮第三十次带行的 `grep` 组装要 3.8 ms。蓝图 `perf.md`「还没有的」里记着的「组装请求整段重渲染」是同一件事，长任务里每一步都付。
7. **回合结束要等同步才推 `turn.ended`**（对照里 12～19 ms）：不在工具一步里，人看到「这一轮完了」晚这么多；这是 V-19 定的「回应等同步」的口径，这里只记下。

jcode 那边：`bash` 每次 107～113 ms 起步（CPU 23～37 ms），`true` 和 `cat` 一样，像是一段固定的等待，原因没查；`read` 小文件 6～8 ms。

### 建议的下一步

照收益和改动大小排，都要项目主人点头再开：

1. `walk.rs` 两处（`Fence::from` 先剪掉碰不到的私密目录、`relative` 直接截）：`grep`、`glob` CPU 预计少三成多，行为不变，改动小。
2. `read::lines` 页外的行不解字、用 `memchr`：大文件 `read` 预计少一半。
3. `write`、`edit` 同步与否：要定口径（见慢点 1）。
4. 沙盒那 5 ms：先拆清楚再定。
5. 判权限和写回复并着做；`grep` 要不要并行走目录。

### 不做什么

- 这一步不改核心的行为，量法里没有为数字好看挑的东西：头一次调用不算是因为它量的是冷的那一下（拉起沙盒、页缓存），另外报了；三遍都写进来了。
- 量尺的这一场不进 CI、不设预算：CI 的机器上 bwrap 不一定能用，先在本机量清楚、定了预算再说。

### 风险

- 时刻：拆段靠日志里到毫秒的时刻，取那一毫秒的中间、几十步平均，单步看不准；假模型记下写完的时刻以后才读 CPU，读一次约 0.1～0.3 ms，算进了假模型自己，不算进核心那一段。机器上别的会话一直在编译，三遍之间差三成，表里给了范围。
- 只在 Linux、btrfs 上量过：同步的那几项在别的文件系统上会差很多。
