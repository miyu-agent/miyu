### 为什么

施工 7-8、V-48 让 `shell` 起的每条命令在核心崩了、被 `SIGKILL` 时跟着没（Unix 上组里一个看门的）。核心自己拉起的三种长住进程没走这一套：
扩展（`extensions/supervise.rs`）、命令型 MCP 服务（`mcp/launch.rs`）、语义模型小程序（`embed/worker.rs`）在 Unix 上和核心同一个进程组，
核心没了只能靠它们读到标准输入关了自己退：不读标准输入的、卡住的、它们起的子进程（`npx` 起的 `node`、扩展起的帮手进程）都留下来，
成了没人管的孤儿。Windows 上核心起来时已经进了 `KILL_ON_JOB_CLOSE` 的作业对象，它们照继承在里面，本来就跟着走。

### 做了什么

1. **`miyu-sandbox` 的 `lifeline::keep`**（`lifeline.rs`、`lifeline/unix.rs`）：给一条要起的命令，Unix 上在这个进程的生命线上起一个看门的
   （就是 `shell` 用的那个 `lifeline::watcher()`：核心设过助手的照 `miyu-sandbox lifeline` 起，没设、起不来的退回 `/bin/sh`），命令设成起在
   它的组里（`process_group(看门的组号)`），交回 `Kept`（拿着看门的）。看门的起不来的交回原话，命令照旧自成一组（`process_group(0)`），
   同 `shell` 的 `alone()`。Windows 和别的平台什么都不做、交回空的 `Kept`：Windows 上靠核心的作业对象（`bind_children`）。没另造办法：
   看门的、生命线、整组杀都是 7-8、V-48 那一套，`keep` 只是把 `shell` 里那几行「起看门的、进它的组」包成三处共用的一个函数。
2. **三处拉起都调它**，看门的跟着进程拿着，进程退出、收掉以后才丢：
   - 扩展：`supervise::spawn` 交回 `(Child, Kept)`，`run` 里这一次拉起的 `_kept` 活到这一次 `finish`（等退、杀掉）以后。
   - MCP 服务：`launch::spawn` 交回 `(Child, Kept)`，`Running::Child` 带着 `_kept`，`once` 里收尾以后才丢。
   - 语义模型小程序：`Worker` 多一格 `_kept`（放在 `child` 后面），`stop` 拆开时也留着它到等完。
   - 看门的起不来：各记一行 `WARN`（`extension lifeline not started`，带 `package`；`mcp lifeline not started`，带 `service`；`embedder lifeline
     not started`），都带 `error`，照旧拉起。
3. **测试扩展加一步 `child:<路径>`**（新文件 `src/bin/miyu-test-extension/spawn.rs`）：照自己的程序起一个 `hang`（三个标准流接空的、Windows 上
   不弹窗口），自己和它的进程号写进这个文件（先写旁边再改名）。主文件只多了一行说明、两行 `mod`、把最后的 `else` 改成 `else if
   !spawn::step(&step)`；为了不过 500 行，`stdin` 两行并成一行、两段说明并成一段（意思不变）。`drivers.rs` 没动。
4. **新测试** `crates/miyu/tests/crash_kept.rs`（`crash.rs` 的 `Rpc` 改成 `pub(crate)`、加 `Rpc::over` 共用）。

### 正常停止不变

- 停的顺序照旧：扩展、MCP 服务关标准输入、等 5 秒、只杀进程本身（`start_kill`）；小程序关标准输入、等 5 秒、杀。看门的丢掉时只杀看门的
  自己（`Watcher` 的 `Drop`：杀、收，不碰组），所以加了进程组不会提前掐，也不会多杀：停下的时刻、杀谁都和改前一样。
- 核心有计划地停下时，`serve` 先 `stop_extensions`（扩展、MCP 服务一起等完）再放锁、退出，退出那一刻生命线断了，组里已经没有它们了。
- 改前正常退出、被重启的进程在组里剩下的子进程留着；改后一样留着（看门的那时已经收掉），之后核心没了也收不掉。这一条没顺手改（派工单：
  正常停止照现在的顺序），列在「要拍板的」。

### 行为差别

1. 核心没了（崩了、`SIGKILL`）：三种进程和它们起的、还在组里的子进程都被整组 `SIGKILL`。改前留下来。`setsid` 出去、自己换了进程组的照旧
   收不掉（同 `shell` 的命令）。
2. 它们不在核心的进程组里了：核心在终端前台跑（`miyu core` 直接敲）时按 Ctrl+C，原来连扩展、MCP 服务一起收到 `SIGINT`、当场退；现在只有核心
   收到，照「停下」有计划地停它们。头拉起的核心本来就自成一组，这一条只影响直接在终端里跑核心的人。
3. 它们不是组长（组长是看门的）：自己调 `setsid()` 能成；`kill 0` 会连看门的一起打到（同 `shell` 的命令，V-48 第 6 条）。
4. Windows：没有差别（本来就在核心的作业对象里）。
5. `ps` 里每个这种进程多一个看门的（`miyu-sandbox lifeline`，或者 `sh`），活到它退出：跑着时 RSS 约 2.3 MB、匿名 124 KB（V-48 量的）。

### 先证明不修时会红

三处拉起照 `origin/main` 原样（测试扩展的新一步留着）、只跑 `crash_kept`：

- 带组的检查：三条都红在「组 … 是它自己的或者核心的」（和核心同一组）。
- 去掉组的检查只看硬杀以后：三条都红，`核心没了，扩展（[…]）还剩 [扩展, 子进程]`、`MCP 服务 … 还剩 [sleep]`、`语义模型小程序 … 还剩
  [sleep]`（MCP 服务、小程序读到标准输入关了自己退了，它们起的 `sleep` 留下来；扩展 `hang` 不读标准输入，两个都留下来）。

### 定的技术题

1. **Windows 不另建作业对象**：派工单写「放进 KILL_ON_JOB_CLOSE 的作业对象」。核心起来时（`core.md`「起来的先后」第 4 步，探沙盒、拉起扩展
   之前）已经把自己放进这样一个作业对象，子进程照继承都在里面（标准库、tokio 都不带 `CREATE_BREAKAWAY_FROM_JOB`）；再给每个进程套一个
   同样的只是重复。`keep` 在 Windows 上什么都不做，扩展那一条测试在 Windows CI 上跑，证明核心被结束以后扩展和子进程都没了。核心进不去作业
   对象的（`WARN children not bound`），命令、扩展一样不跟着走，和 7-8 一样。
2. **看门的起不来照 `shell`**：记 `WARN`、照旧拉起、自成一组。起不来只在 `/bin/sh` 也起不了、生命线建不起来时（文件描述符用完这类）。
3. **看门的照 `shell` 同一根生命线、同一个助手**：不为它们另开管道；看门的是谁（助手还是 `sh`）照核心探沙盒的结果，探沙盒在拉起扩展之前。
4. **测扩展用 `hang`**：扩展读到标准输入关了会自己退的话，改前也看不出扩展本身留没留；`hang` 不读标准输入，扩展本身也只能靠看门的收。
5. **MCP 服务、小程序用真程序加一段 `sh`**：`miyu-test-mcp`、`miyu-test-embed` 读到标准输入关了自己退，测不出看门的；一段 `sh` 先在后台起
   `sleep`（标准流接空的）、记下 `$$`、`$!`，再 `exec` 成真的程序：核心拉起的就是真程序（同一个进程号），它起的 `sleep` 是要收的孙进程。MCP
   服务写在系统配置的 `[mcp.kept]`（写了就起）；小程序是装在你那一层的 `miyu-embed` 小程序包（人格记忆出厂推荐它），程序是包 `bin/` 里的
   脚本，模型照会话测试的手造小模型；往无人格那一间记一条记忆，核心在后台补向量时拉起它。这两条只在 Unix 跑（Windows 上三种进程是同一个
   作业对象，扩展那一条测到了；也没有 `sh`）。

### 量尺

拉起一个长住进程时核心多等的就是起看门的那一下（`watcher()` 等它 `exec` 成）和设组号：在 `miyu-sandbox` 里临时写一个量尺（不提交，
`scratchpad/perf/xh1_bench.rs`），照 `keep` 的起法（同一根生命线）和改前的起法交替起 `miyu-test-extension wait`（三个标准流同扩展：两根管道、
标准错误另接），量从起看门的到 `spawn` 交回；release，绑 12～15 号核，每种 500 次，3 遍。机器负载 10 左右（别的会话在编译）。

| 每次拉起，核心等的 | 改前（不起看门的） | 改后（助手看门） | 退回 `/bin/sh` 看门 |
|---|---|---|---|
| p50 | 88 / 85 / 72 µs | 173 / 153 / 128 µs | 172 / 156 / 125 µs |
| p95 | 297 / 166 / 123 µs | 546 / 556 / 473 µs | 661 / 623 / 499 µs |

改后每次拉起多约 55～85 µs（p50）、p95 多 250～390 µs（负载下起两个进程，尾巴跟着长）。拉起只在核心起来、开扩展、重启、服务退避重来、
第一次要向量时才有，不在回合的路上；扩展拉起本身还要建目录、开标准错误文件、握手，这一截比它们小得多。常驻多的是每个进程一个看门的
（V-48 量的 2.26 MB RSS、124 KB 匿名），核心空着时没有扩展的就没有。

### 要拍板的

1. **正常退出、被重启以后组里剩下的子进程要不要一起收**（推荐：先不收，照现在）：`shell` 的命令退出以后整组杀（「做完了它起的不留」），扩展、
   MCP 服务不同：常有交出去的帮手进程（例如扩展起的本机服务）退出前自己收，核心替它整组杀可能杀掉它故意留的；而且派工单写「正常停止照现在
   的顺序」。要收的话是停的时候先关标准输入、等，到时整组杀（不只杀进程本身），会改变扩展看得见的行为，另开一步。
