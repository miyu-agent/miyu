## 施工单 R-33：测回合库不撞建表

状态：合了（2026-10-26）。只改测试。

### 查出来的

`miyu-endpoint` 的 `tests/memory.rs` 里 `a_turn_said_through_the_core_is_indexed_and_goes_with_the_session` 在 main 的 CI 上红过两次（U23 中上那一次，E-1 修二那一次的 ubuntu check），同一个报错：`读得出: SqliteFailure(SchemaChanged, "vtable constructor failed: terms")`，在测试自己的 `found` 里。

原因：测试另开一个只读连接，每 50 毫秒查一次回合库，看这一轮进没进去。回合库是回合索引的后台（V-9 那一条道）头一次写时才开的，开库时先建 `buried`、`marks`、`items`、`terms`，再一张张补 `vectors`、`uses`、`places`、`stamps`、`meta`（`miyu-store` 的 `recall.rs` 的 `add`）。测试的连接正好在这中间准备好语句、再去读，表结构变了，SQLite 重新准备时 FTS5 那张表连不上，报 `SchemaChanged`。`found` 只把开库、准备语句失败当成「还没有」，读的时候出错直接 `expect`，于是红了。生产代码没毛病：一个库只该有一个连接写，核心自己的搜（`memory.turns`、她的 `memory_search`）先等后台写完（`Memory::settle`）。

### 做什么

测试不再另开连接在核心建表时读库：「这一轮进了回合库」「删会话以后拿掉」都经协议 `memory.turns` 搜（核心先等回合索引的后台写完再搜）。日志先落盘、这一轮后交给后台，看到这一轮结束时可能还没交过去，所以照旧轮询（最多六十秒），只是每一次都经核心等过。删会话以后那一次搜也等过，库早建好了，这时再另开只读的连接看墓碑。

### 复现

本机照协调者说的把这条测试挤在一个核上（`taskset -c 2`）循环跑，修以前、修以后各跑同样的次数：

| 跑法 | 修以前 | 修以后 |
|---|---|---|
| 一个核、一次一个，2000 次 | 0 红 | 0 红 |
| 一个核、8 个同时跑，各 250 次（临时目录在 tmpfs 上） | 0 红 | — |
| 一个核、8 个同时跑，各 250 次（临时目录放到磁盘上，开库慢一些） | 0 红 | 0 红 |
| 一个核、16 线程跑整个 `memory` 那一组，60 次 | 0 红 | — |

本机复现不出来：这台机器开库太快，窗口只有补那几张表的几毫秒；CI 的机器慢、又同时跑几百条测试，才撞上。原因照报错和建表的先后读出来，修法不靠重试，靠核心自己的等。

### 不做什么

- 不改生产代码：一个库一个连接写是规矩，另开连接读本来就不保证读得到一致的结构。
- 别的测试里另开只读连接读回合库的（`miyu-session` 的几条）读之前都调了 `Memory::settle`，不在这一步。
