## 施工单 YC-14：每一步耗时拆开量

状态：施工中（2026-11-10）。压测报告（600 轮的会话，请求体从 100 KB 以内涨到 600～700 KB）。

### 为什么

长会话里每一步核心自己花的时间跟着上下文线性涨。照运行日志现有的几行只分得出两段在涨：「工具结束到出 `call_model`」0.45 → 3.67 毫秒，「`call_model` 到 HTTP 发出去」0.24 → 2.33 毫秒；存回复、判工具、跑工具是平的。这两段里各有好几件事（照历史重新组装、估用量、算指纹、编码、放掉请求），不拆开量，不知道该优化哪一件。

### 一次请求走过哪几段

从工具结果都落了盘，到字节交给 `miyu-http`：

| 段 | 在哪 | 那一行的哪一格 |
|---|---|---|
| 落盘的回报送进内核，出 `CallModel` | `miyu-session` `actor.rs` 的 `drain`（`timing::handle` 包着 `Session::handle`）；内核 `session/turn.rs` 的 `ask` | `kernel_us` |
| 　照有效历史组装 | `turn.rs` `ask`：`assembler.assemble(&self.history)`（`miyu-assemble`） | `assemble_us`（重跑） |
| 　看不了图的找没转述的图、放转述 | `session/sight.rs` 的 `look`、`with_descriptions` | 只在 `kernel_us` 里 |
| 　估用量：熔断、压回答、挑成员、起压线各估一遍 | `session/breaker.rs` 的 `before_asking`、`output_cap`，`session/compaction.rs` 的 `used`，`session/prepare.rs` 的 `prepare_up` | `estimate_us`（重跑一遍的） |
| 　算指纹、和上一次比出第一处不同 | `turn.rs` `ask`：`request.fingerprint()`（`request.rs`） | `fingerprint_us`（重跑） |
| 回 `CallModel`：记 `request` 那一行、交给端口、挑端点、派任务、任务排到 | `actor.rs` 的 `act`、`actor/model.rs` 的 `call`、`route.rs` 的 `call`（`choose`）、`route/send.rs` 的 `spawn`、`attempt` | `wait_us` |
| 列出、取好编码要的 blob | `route/exchange.rs` 的 `exchange`：`blobs_needed`、`fetch` | `blobs_us` |
| 补占位工具、压输出上限、编成片段清单 | `exchange`：`placeholder::missing`、`capped`、`fragments_memo`（`miyu-drivers`） | `encode_us` |
| 放掉请求、取来的字节 | `exchange`：两个 `drop` | `drop_us` |
| 交给 HTTP 执行器 | `exchange`：`Body::new`、`miyu_http::send`（`send.rs` 记 `sent`） | `bytes` |

请求体的哈希不在发之前算：跟着送出去的字节一路算（`miyu-http` 的 `body.rs`），不在这两段里，所以没有这一格。

### 做什么

1. `miyu-session` 新文件 `timing.rs`。只在来源 `session` 调到 `DEBUG` 时量（`tracing::enabled!`）：`INFO` 时不读时钟。
2. 内核是纯逻辑，不许读时钟：会话 actor 包着 `Session::handle` 量整个那一步（`kernel_us`）；出了 `CallModel` 的，照同一份历史、同一份请求再组装、再估用量、再算指纹各一遍，量出后三格。重跑的只读、结果扔掉，不在 `kernel_us` 里。内核为它多露两个只读的口子：`Session::assembled()`、`Session::used()`（原来只在内核里用；`context_used()` 就是这两步）。
3. 量好的随回报（`Reports`）带到发的任务里，`exchange` 接着量后几段，请求体编好、交给 HTTP 执行器之前记一行 `request timed`，紧挨着 `http` 的 `sent`。辅助请求（回顾、起标题、摘要）也记，没有内核那几格；扩展驱动的不记。
4. 蓝图 `session/actor.md`「运行日志」加这一行，`log.md` 写明这一行的用时是微秒，`kernel/session.md` 加两个口子。

发出去的请求一个字节不变，行为不变。

### 怎么读那一行

```
DEBUG session  <会话> request timed seen=7 kernel_us=310 assemble_us=120 estimate_us=40 fingerprint_us=25 messages=5 wait_us=90 blobs_us=3 encode_us=60 drop_us=4 bytes=5120
```

- 都是微秒。`kernel_us` 对「工具结束到出 `call_model`」那一段里内核的那一步；`wait_us + blobs_us + encode_us + drop_us` 对「`call_model` 到 HTTP 发出去」。
- `kernel_us` 减去 `assemble_us`、三四倍的 `estimate_us`、`fingerprint_us`，剩下的是看图、判线别的开销。哪一格跟着 `messages`、`bytes` 涨得最快，先优化哪一格。
- 开着 `DEBUG` 时每次请求多跑一遍组装、估用量、算指纹：量每一步总用时的时候，把这三格从外面量的里减掉。

### 验收

- `tests/timing_log.rs`：`INFO` 时发一次请求，没有这一行；调到 `DEBUG` 再发两次，每次主请求一行、照先后、`seen` 对得上 `request` 那一行、十格都在，`bytes` 和 `http` 的 `sent` 一样。先红：`exchange` 里不记时没有这一行。
- 请求字节不变：`route/exchange/golden.rs`（编出来的字节照金样）、`tests/http.rs` 照旧过，不用改。
- 日志门禁（`cargo xtask logs`）、本机门禁全过。
