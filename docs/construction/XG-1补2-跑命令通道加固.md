## XG-1补2 扩展跑命令的通道加固：父进程比创建时间、端点名不带令牌、令牌等时比较

状态：施工完，待 core1 审（2026-11-06）。来源：e0 复核 XG-1 下提的三点，core1 2026-11-06 派；第四点（Windows 管道的空档）是 e0 查
Windows 偶发时发现的，core1 同一天加进来。设计 `63-扩展工具的效果和声明.md`
第九节「已知边界」第 2 条照这一步改写；蓝图 `tools/shell.md`（脚本调工具第 2、5 条）、`providers.md`（「会跑命令的」第 2 条、守着它的）、
`ipc.md`（`miyu-pipe` 一行）。

### 目的

XG-1 下的端点认「扩展进程的子孙」加令牌，复核看出三处能再紧一点：

1. **Windows 的父进程号会被重用**：Windows 不过继，父进程走了以后编号可能给了一个后起的进程，快照里「子进程的父进程号」就指着它。
   扩展的进程号被重用了，一个不相干的进程的子孙也认得成「扩展的子孙」。原来靠令牌兜着（core1 接受过，设计 63 第九节记着）。
2. **端点名用的是令牌的前 16 个字符**：Windows 的命名管道名全机的进程都列得出来，等于摆出半个令牌（128 位剩 64 位）。Unix 上套接字
   在 `0700` 的目录里，别人看不到，顺手一起改。
3. **令牌用 `!=` 比**：在第一个不同的字节就停，量回答多快理论上能一个字节一个字节猜。

### 做了什么

- **`miyu_pipe::process_created`**（`miyu-pipe/src/process.rs`，Windows）：`OpenProcess`（只要查询信息）+ `GetProcessTimes` 的创建时间，
  拼成 1601 年起的 100 纳秒数。打不开的（不在了、别的用户的、受保护的）、问不出的是 `None`。两个 `unsafe` 块各写了为什么安全，同
  `process_running` 的写法。
- **`kin::elder_parent`**（`miyu-call/src/kin.rs`）：纯函数，表里记的父进程号，还要那个进程起得不比子进程晚；问不出时间的当问不出
  父进程，链到这里断。Windows 的 `descends_here` 每一层都过它（快照照旧拍一次，时间按链上的进程一个个问，一般三四层）。`descends`
  不动，Linux、macOS 不动（它们过继，链上的编号总是还在的进程）。
  - 用 `<=` 不用 `<`：创建时间照系统时钟走，父子可能落在同一刻；重用了编号的进程起在子进程之后，严格晚得出来。
  - 扩展自己（链到头的那一个）也照这条比：扩展的编号被重用了，也认不成。
  - 快照拍完到问时间之间进程走了、编号又给了别人的：新的那个起得更晚，照样断。
- **端点名**（`serve::endpoint_tag`）：另取一个随机串的前 16 个十六进制字符，Unix 的套接字文件名、Windows 的管道名都用它，不再用令牌的。
- **令牌等时比较**（`serve::same_token`）：长度不同直接不对（令牌长度本来公开，32 个字），同长的逐字节异或累加，比完再看，
  `std::hint::black_box` 挡着编译器提前退出。没加新的依赖（`subtle` 只是间接依赖，为一个函数加直接依赖还要写许可证，不值）。

### 测试

- `kin/tests.rs`（到处跑）：`a_parent_created_after_its_child_is_a_reused_pid`：正常的链认得；中间一层的编号被后起的进程重用、扩展自己
  的编号被重用，都断。`a_parent_born_at_the_same_moment_counts_and_an_unknown_time_does_not`：同一刻起的算数；父进程、子进程问不出时间
  的、表里没有父进程的，都是 `None`。
- `serve/tests.rs`（新）：令牌差在头、尾、中间的，长了、短了、空的都不对；端点名 16 个十六进制字符、两次不一样。
- `unix/tests.rs`、`windows/tests.rs` 交给扩展的那一格：端点名里找不到令牌的前一段、中间一段。
- `miyu-pipe/src/process/tests.rs`（Windows，CI 跑）：子进程的创建时间不早于测试进程的，系统里没有的进程号问不出。

手写变异 9 个全抓住（`elder_parent` 去掉比较、`<=` 改 `<`、改 `>=`、子进程问不出时间当最大；`same_token` 的或改与、去掉长度检查、
`answer` 不比令牌；Unix 端点名用回令牌；端点名截短）。Windows 上 `descends_here` 接没接 `elder_parent` 本机变异不了，靠
`a_real_child_descends_from_this_process`、`an_extension_s_endpoint_answers_its_descendants_only` 在 CI 的 Windows 上跑真进程守着
正常的那条路。

### 补：Windows 的管道不留空档（core1 2026-11-06 加）

`windows.rs` 的 `accept` 原来同一时刻只留一个空着的实例，有人连上了才建下一个。连上那一刻到建好下一个之间再来连的拿到
`ERROR_PIPE_BUSY`（231）。`miyu call` 碰到 231 会等着重试两秒（`miyu-cli/src/call.rs`），生产上不至于失败；扩展作者自己写的客户端
不一定重试。

- **改法**：一直留 `IDLE`（2）个空着的实例。客户端连到哪个空着的实例由系统挑，所以每个实例各自放进一个任务里等（`connected`），
  连上了的连同管道一起交回来；交回来以后先建好下一个顶上，再交给 `serve::answer`。多了的照旧断开，建不成、等的出错照旧停下。
  端点丢掉时等的任务跟着取消，管道照旧关上（`dropping_it_removes_the_pipe` 守着）。
- **测试**：`windows/tests.rs` 的 `a_second_client_right_after_the_first_is_not_busy`：100 对，每对两个客户端紧接着连、不重试，
  都得连上；每对之间歇 20 毫秒让端点补齐。只在 CI 的 Windows 上跑（本机的 Windows 虚拟机直通着显卡，这次没开）。
  - **对照**：另推一条只加这条测试、`accept` 照旧只留一个实例的分支（`exp/XG-1b2-pipe-control`，275e0e30e，手动跑 CI run
    42175000269）：Windows 上红在第 0 对，`第 0 对连不上：Some(231)`；别的五项都绿。这条测试抓得住那个空档，不只是守着正常的路。
    对照分支跑完已删。
  - 59f010e05 那一趟 CI 的 perf 红在「热启动到能提交第一轮」（84.5 ms，预算 50 ms），上一个提交 f30d15ae8 整套绿、这一个只改
    Windows 的代码，算 runner 抖，重跑那一项。
- **开发包**（`miyu-sdk`，Python、Rust 两份）不自己连这条通道：只把 `MIYU_CALL_SOCK`、`MIYU_CALL_TOKEN`、`bin` 设进命令的环境变量，
  连的是命令里的 `miyu call`（会重试）；假核心也不开通道。没有要给 memory 记的。
- 测试那一头的重试 e0 已经加了（c61458cb2，batch-1106-r4），这里只改生产。

### XG-1补3：Windows 照快照找的那一层接线测上（core1 2026-11-06，e0 复核 XG-1补2 提的）

- **缺口**：单元测试直接测 `elder_parent`；Windows 的 `descends_here` 有没有接上它没有测试守着。有人把那一层去掉，正常的父子链照样
  过，Windows 上也没有哪条测试会红（真机上造不出被重用的进程号）。
- **改法**：`descends_here` 里那个闭包抽成 `kin::descends_in_snapshot(pid, ancestor, parents, created)`：传入快照的父进程表、问创建
  时间的函数，里面照 `descends` 一层层找、每一层过 `elder_parent`。Windows 的 `descends_here` 只剩拍快照、把真的两样交给它。
- **测试**（`kin/tests.rs`，到处跑）：`a_snapshot_with_a_reused_parent_pid_is_not_a_descent`：正常的链是子孙；中间一层的编号被后起的
  进程重用、扩展自己的编号被重用、问不出时间的，都不是；同一刻起的照样是。
- **反向检查**：把 `descends_in_snapshot` 里那一层换成直接照表找、或者把创建时间都当成一样，这条测试都红。`descends_here` 自己
  只剩一行转交，改成绕过 `descends_in_snapshot` 的写法还是测不到（要真的 Windows 快照），这一行照现在的样子留着。
- **管道的两个标志**：
  - `FILE_FLAG_FIRST_PIPE_INSTANCE`：已经有。两处开端点的第一个实例都传 `first = true`（`miyu_pipe::create_for_containers`、核心协议的
    `create`，tokio 的 `first_pipe_instance`），名字被别的进程占了的建不成、报错；后面补的实例不带（带了就建不成第二个）。
  - `PIPE_REJECT_REMOTE_CLIENTS`：tokio 的 `ServerOptions` 本来默认开着（tokio 1.54.1，`reject_remote_clients: true`）。这一步在
    `miyu_pipe` 建实例的地方明写 `reject_remote_clients(true)`，免得默认值哪天变了跟着丢；行为不变，测不到（要另一台机器来连）。
  - 同一用户的进程抢先建同名实例不算新口子（e0 也这么判断）：名字是随机的，第一个实例带了那个标志，抢先建的会让核心这边建不成、
    通道开不了，不会让核心连到别人的实例上。
