## 施工单 V-48：看门换成自己的助手

状态：已完成（2026-11-05）。照 V-40 找大头第 6 项要拍板的那一半里的「看门进程」做。口径：项目主人 2026-11-03 先批的是「一个核心一个看门进程：做」；V-48 看下来那样做有几处保证守不住（见「没做的」），**2026-11-05 项目主人重新批：还是每条命令一个看门的，看门的程序从 `/bin/sh` 换成我们自己的 `miyu-sandbox` 助手，新加「生命线读到结尾就 `kill(0, SIGKILL)`」的模式；助手找不到、起不来时退回 `/bin/sh`。代替原来批的「一个核心一个」。** 原来看门的守着的每一条、附带的行为，一条不改。

### 为什么

核心崩了、被 `SIGKILL` 时，命令得自己知道核心没了（施工 7-8，`docs/blueprint/core.md`「子进程随核心退出」）：Unix 上每条命令的进程组里先起一个看门的 `/bin/sh`，标准输入是只在核心手里的生命线管道的读端，读到结尾就杀整组。V-40 量到这个 `sh` 每条命令约 1 ms 墙钟、0.6 ms CPU。V-48 先在核心里量了「完全不起看门的」当上限（3 遍 × 120 次 `shell true`）：每一步的墙钟没有变化（看门的启动和命令是并着走的，核心只等它 `exec` 成），省的只有 CPU，每条命令 0.45～0.66 ms，就是 bash（这台的 `/bin/sh` 是 bash）自己启动的那一份。所以要省的是看门的启动 CPU，换一个起得轻的程序就行，保证一条都不用动。

### 原来看门的守着什么

起命令都走 `basesystem` 的 `process::spawn` → `alone()`：她的前台、后台（7-3）、监视的（MN-1 上）、到时交出去的（7-12）、脚本工具（X-12 上）、人用 `!` 跑的（SH-1 上，`person.rs` → `process::start`），一条不漏，都有看门的。它守着：

1. **核心怎么死的都算**：生命线的写端只在核心手里（`O_CLOEXEC`），核心没了内核关掉它，看门的读到结尾，`kill -s KILL 0` 杀自己所在的整个组：命令、命令 fork 出去还在组里的孙进程，都在里面。
2. **没有空窗**：看门的先起，命令起的时候（`process_group(看门的组号)`）就在它的组里，从第一条指令起就有人看。
3. **组号不会被别人占**：看门的是组长，活到这条命令的 `Watch` 丢掉为止。核心照组号杀（到时、叫停、`Guard` 掐断、命令退出后杀剩下的、后台的停）不会杀错组；脚本调工具的通道照组号认人（M-3）也靠这一条。
4. **看门的手里干净**：环境变量清空、工作目录 `/`、标准输入是生命线的读端、标准输出和错误接空的；核心的管道都带 `O_CLOEXEC`，看门的不拿命令的输出管道，命令也不多继承一个文件描述符。丢掉时杀掉、收掉，不留僵尸进程。
5. **看门的起不来**：记一行 `WARN command lifeline not started`，命令照旧自成一组。
6. **附带的行为**：命令自己不是组长（组长是看门的），所以命令里的 `setsid()` 能成；命令 `kill 0`、`kill -TERM 0` 会连看门的一起打到；某一个看门的被杀了，只有那一条命令没人看着（永久）。`setsid` 出去的、自己换了进程组的不在组里，核心没了收不掉。

Windows 不用看门的：核心起来时进一个 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的作业对象，核心没了作业里全部结束（`lifeline/windows.rs`）。这一步不动它。

### 做什么

1. **助手的 `lifeline` 模式**（新文件 `src/bin/miyu-sandbox/lifeline.rs`，`main.rs` 入口最先认）：只认光秃秃的 `miyu-sandbox lifeline`（多了参数的照参数不对退出 125）；栈上 64 字节一块，用 `rustix::io::read` 读标准输入（不经标准库带缓冲的 `stdin`，那一份要分配 8 KiB），读到 0（结尾）或出错就 `kill_current_process_group(SIGKILL)`，被打断（`EINTR`）的接着读，读到的东西不管——和 `while read -r _; do :; done; kill -s KILL 0` 一样。不读规格、不建 Landlock、不碰环境变量、什么都不印。`miyu-sandbox` 在 Unix 上多依赖 `rustix` 的 `process`（工作区里本来就有）。
2. **生命线照助手起看门的**（`lifeline/unix.rs`）：`Lifeline::watcher(helper)` 给了助手的照 `<助手> lifeline` 起；没给的、起不来的（文件没了、执行不了，`spawn` 当场报）退回 `/bin/sh -c 'while read -r _; do :; done; kill -s KILL 0'`。两样起法同一个函数：`env_clear`、`current_dir("/")`、标准输入是读端的副本、输出接空、`process_group(0)`。`Watcher::by_helper` 说是哪一种（测试用）。
3. **核心设助手**（`miyu-core` 的 `sandbox.rs`）：探沙盒探成了、构建 id 对得上的助手（不管有没有收紧手段），交给 `lifeline::use_helper`，之后起的看门的都照它。没探成的（找不到、跑不起来、另一份源码编的）不设，看门的照旧是 `/bin/sh`：另一份源码编的助手可能不认得 `lifeline`，起来就退出，那条命令就没人看了，所以只用探过的。探的是核心起来时那一次（会话造好之前），命令起的时候已经设好。
4. `basesystem` 不动：`alone()` 照旧调 `miyu_sandbox::lifeline::watcher()`，组号、整组杀、`Watch` 丢掉时收掉都照旧。V-47 起助手改走 `pre_exec`（`miyu_sandbox::command`，只给关进沙盒的命令），和看门的无关：看门的不用 `pre_exec`，照旧 `posix_spawn`。

### 行为差别

没有。看门的从 `sh` 换成 `miyu-sandbox`，命令看得见的只有一处：`ps` 里组长的名字。读到的东西不管、读不了当结尾、对 `TERM`、`HUP`、`INT` 都是默认动作（跟着没），这些和 `sh` 那一段一样。核心没探成助手的机器上看门的照旧是 `sh`。

### 没做的：一个核心一个看门的

原来批的做法。V-48 看下来守不住「一样」，停下来报了：

1. 命令要自成一组，组长只能是命令自己：起好命令到写进看门的登记之间约 0.1～0.2 ms，核心这时被杀，命令就逃了（改前空窗是 0）。要补得在 `pre_exec` 里让子进程自己登记，标准库就从 `posix_spawn` 退回 `fork`，40 MB 的核心每条命令墙钟多 0.14 ms。
2. 命令成了组长：命令自己调 `setsid()` 会失败（改前能成），自己 `setpgid(0, 0)` 不再出组。
3. 一个看门的被杀，这个核心所有命令一起没人看（Landlock 只管了抽象 Unix 套接字、不管信号，bwrap 没开进程号命名空间，同一个用户的进程都杀得到它），得加常驻线程重起、限频率。
4. 组长退出、还没注销时核心死了，组号要靠僵尸占着；僵尸被 init 收掉以后，理论上组号能被别人用上。

省下的也只有 CPU（墙钟上限就没有变化），常驻还要多一个进程。2026-11-05 项目主人改批成换助手。

### 风险
