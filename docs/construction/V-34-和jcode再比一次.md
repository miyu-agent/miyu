## 施工单 V-34：和 jcode 再比一次

状态：已完成（2026-11-02）。只量、不改核心、不改测具。10-31 和 jcode 比过一次（施工 V-27）以后，核心合了一串性能步子，终端合了 TM-1～TM-5；照 V-27 同一套跑法再完整比一次，看现在的样子。原则照 2026-10-30 项目主人定的：不为数字好看省、不改量法凑数，挪到子进程的开销算总账；复用的缓存照 10-31 定的口径单列。

### 为什么

V-27 以后合进核心 main 的性能步子：V-24（图片、文件核对过的不每步重算哈希）、V-24补（快照直接比较）、V-26（模型列表自己刷新）、V-30（字表读一次）、V-25上/下（模型目录不常驻）、V-28（库日志闲时合回、空记忆库不建）、V-29（量尺加工具一步，只量）、V-31（grep、glob、read 少做白工）、V-32（`model.list` 照记下的答）、V-33（证书用到才读）。终端：TM-1（整屏记录少占）、TM-2（说法只留原文）、TM-3（读缓冲缩回）、TM-4（读配置的栈）、TM-5（发行配置 `lto = "fat"`、`codegen-units = 1`）。这些步子各自量的是核心或终端的一段，人真用的一整套（核心加终端，和 jcode 同一个模型端点）还没再比过。另有 PE-1（出厂带「软件工程师」人格）也在这一段里合进来，装好的大小、家目录里照实算。

### 怎么跑的

照 `docs/blueprint/perf.md`「三家对比」和 V-27 一样的跑法、一样的参数，测具（`bench/rivals/`）一行没改：

```
MIYU_BENCH_MODEL=beam-free uv run bench/rivals/main.py --tui <终端工作树> --jcode <jcode 启动脚本> --cpus 12-15 \
    --upstream https://opencode.ai/zen/go/v1 --upstream-key-env OPENCODE_GO_API_KEY --only miyu --only jcode \
    all --into docs/perf --tag v34
```

- 核心：`origin/main` c83b775bf（V-33），`cargo build --release -p miyu -p miyu-sandbox -p miyu-extract`（照 `cargo xtask perf` 的编法）。
- 终端：`miyu-tui` 的 `origin/main` 4e5a6be（TM-5），就是 `heads.toml` 钉的那一份，`cargo build --release`。
- jcode：同上次一个版本 v0.99.1（`jcode v0.99.1 (7206efd0c)`，官方 linux-x86_64 发行包，压缩包的 SHA-256 和它的 `SHA256SUMS` 对得上），启动脚本加程序。
- 模型：opencode-go 的 `beam-free`，经本机转发（`relay.py`）；两家的真任务都 5/5 过，对话请求一个没出错，没换模型。
- 绑 12–15 号核，同上次。这一次 12–15 号核本身就被别的程序占满（量之前采样四个核都是 100%），别的会话同时在编译：量之前 1、5、15 分钟负载 17.1、21.2、20.3，各轮开头 3.8–21.8（上次 15.4、19.9、20.0，各轮 4.5–17.9）。时间类的数和 CPU 毫秒都受影响，看下面 jcode 那一列：同一个程序，冷启动 CPU 多了 19%、长会话 CPU 多了 85%、空闲 CPU 翻倍。比 Miyu 前后先看内存、读写、硬盘、指令数这些不跟负载走的。
- 补一项指令数（不进测具，量法见下面「补充：指令数」）。

怎么读：

- **内存**：Miyu 每一场的 PSS 都少了 2.6～4.7 MiB（冷启动 42.5 → 37.8、空闲 39.4 → 36.7、真任务峰值 30.4 → 27.1）。jcode 同一个程序前后差 +2%～+12%，是这一次的抖动范围，Miyu 少的比它大。
- **CPU**：冷启动 110 → 64 ms（-41%）、热启动 66 → 28 ms（-58%）、真任务 148 → 113 ms（-24%），而同一时候 jcode 的同一个程序冷启动 +19%、热启动 +34%：机器比上次挤，Miyu 实际少的比表上的还多。长会话 CPU 58.2 → 58.4 ms 没动，同一时候 jcode +85%；这一段没有步子专门动过，看不出是真没变还是被挤掉的，没有指令数，不下结论。
- **时间**：冷启动、热启动、真任务的用时都短了；长会话「到看见最后一句」54.6 → 82.0 ms 变长，最小到最大 61～157 ms，jcode 同一项也 +77%，是负载（上一条），不当退步。
- **写**：空闲、真任务交给系统的写都少了或不变；真任务落到盘上的 1184 → 1248 KiB（+5%），在这一场的抖动以内（五轮 1092～1560 KiB，上次 1096～1272 KiB）。读盘照页缓存在不在走，两家都从几 MiB 到 0 抖，不比。
- **硬盘**：装好 68.9 → 64.4 MiB：终端 23.8 → 18.5 MiB（TM-5），核心 34.0 → 34.7 MiB（这一段新加的功能，含 PE-1），资源 7.52 → 7.54 MiB。家目录跑过一次的数据 352 → 300 KiB（好好退出）、448 → 396 KiB（直接杀掉）：空的记忆库 `memory-_none.db`（60 KiB）不建了（V-28）；多了 `state/models/catalog.json` 4 KiB（V-25下）；`reference.toml` 36 → 40 KiB（配置项多了，照实列）。上次「直接杀掉」那一份里没有 `-wal`、这次也没有（模板是界面关掉、核心安静以后记的，V-28 合回了），剩三个 `-shm` 各 32 KiB。
- **模型用量**（转发记的，请求数会随模型每次怎么做变）：做模板那一次 Miyu 5631 个输入 token 对 jcode 9289（上次 5596 对 9288）；真任务 Miyu 25 次请求 15.4 万输入，jcode 26 次 25.9 万。

现在和 jcode 比：冷启动、空闲、热启动、三个会话、真任务（用时、CPU、内存、写）、长会话（时间、CPU、内存）、装好多大、长会话那一个会话的文件、家目录跑过一次的数据（好好退出，300 对 312 KiB，这次 Miyu 少了），Miyu 都比 jcode 少。

#### 补充：指令数（不进测具）

CPU 毫秒跟着机器挤不挤走，补量一样不跟负载走的：两家的后台进程（Miyu 的 `miyu core`、jcode 的 `serve`）先起来歇 3 秒（同热启动），再开终端界面到首屏，马上给界面、后台进程各发 SIGTERM；两个进程各套 `perf stat -e instructions:u`（连它们拉起的子进程，退出了的也算），各 7 轮。用的是测具的模板、转发、沙箱家目录，脚本只在本机跑，不进提交。

### Miyu 还输的项和原因

1. **真任务「直接杀掉」口径的家目录多了多少：327 对 103 KiB**（上次 376 对 104）。另跑了两轮诊断（同模板、同任务、同转发，命令跑完 CPU 停下 1 秒时——测具量这一口径的那一刻——按文件记下数据根，再等 3 秒记一次，好好退出再记一次）：

   | 文件 | CPU 停下 1 秒时 KiB | 再等 3 秒 KiB | 好好退出 KiB |
   |---|---|---|---|
   | `state/usage.db-wal` | 76～92 | 0 | 0 |
   | `index/sessions.db-wal` | 44～52 | 0 | 0 |
   | `index/recall/turns-_none.db-wal` | 32 | 0 | 0 |
   | 四个库的 `-shm`（`usage`、`rates`、`sessions`、`turns`） | 各 32 | 各 32 | 0 |
   | 会话日志、`core.log` | 16 | 16 | 16 |
   | 合计 | 296～320 | 144 | 16 |

   原因：V-28 是库最后一次写以后安静 2 秒（`wal::QUIET`）才把 `-wal` 合回去，测具在 CPU 停下 1 秒时就量，这时还没合；再过 3 秒 `-wal` 全是 0，剩 144 KiB，其中 128 KiB 是 `-shm`（V-28「不做什么」：WAL 要它，读写两个连接靠它，项目主人那时同意留着）。jcode 写的是 JSON 文件，两种口径一样。测具量的那一刻是「命令跑完、CPU 停下就崩了」，照实算，不改量法。

2. **复用的缓存 8312 对 24 KiB**：models.dev 的模型目录原文 5.7 MB、摘要 1.45 MB、各家图标（单列，不算进跑一次多了多少）。jcode 存的是供应商的模型清单和远端的模型目录，一共 24 KiB。

3. **后台进程起来一次的用户态指令：Miyu 核心 1.84 亿对 jcode 服务 1.04 亿**（上面「补充」）。CPU 毫秒 Miyu 少，但核心自己做的活比 jcode 多。在同样的流程里对核心照用户态指令采样（`perf record -e instructions:u`，不带调用栈，平的）：
   - 约一半落在 libc 的 `malloc`、`free`、拷内存上：起来时造了、拷了、扔了很多小的字符串和表；
   - 字表 `BTreeMap<String, Arc<Phrase>>` 整张克隆再整张扔（`clone_subtree`、`drop`、`push_with_handle`）约 7%：V-30 以后读一次了，可用的地方还在整张拷；
   - 读 TOML（`toml_parser`、`toml_edit`）约 4%，配置键的切、拼（`miyu_config::key`）约 5%，拼带缩进的 JSON 文本约 4%，起来时造一个正则的 DFA（`regex_automata::dfa::minimize`）约 1%。

   采样不带调用栈，`malloc` 那一半是谁叫的拆不出来；下一步要带帧指针编一份再剖。

4. **长会话那一场的 CPU 没变**（58.2 → 58.4 ms，jcode 同一项 +85%）：这一段没有步子动过打开长会话；在这么挤的机器上看不出真假，留给下一次带指令数量。

### 测具这一次看到的（不改）

- `rivals.toml` 里 jcode 的 `stop` 是 `jcode server stop`；jcode v0.99.1 不带 `--force` 只印一句提醒（会断掉活着的会话，建议用 `server reload`），返回 0，服务不退（本机实测：20 秒后服务还在）。所以「好好退出以后」那一列 jcode 实际走的是测具的后备：给剩下的进程发 SIGTERM，服务 40～70 ms 就退了，五轮都没有硬杀（`task-jcode-*.json` 的 `shut.forced` 全是 0）。10-31（V-27）那次一样是这样。jcode 写的是 JSON 文件，两种口径本来就几乎一样（103 对 103 KiB），这一次的数照用。2026-11-02 核心主会话定：这一步不改测具，照实写进蓝图。

### 下一步最值得砍的

照「只砍真浪费」排：

1. **核心起来时的分配和整张克隆**（上面第 3 条）：同一个流程里 Miyu 核心比 jcode 服务多做 8 千万条用户态指令，一半在分配、释放、拷内存。字表整张克隆是看得见的一处（约 7%），换成共用一份（`Arc` 包整张表）就没了，行为一个字节都不变。冷启动、热启动、每一次 `miyu ask` 都走这一段。
2. **提示缓存命中**：转发记的真任务每一轮的头一次请求，上游缓存热了以后（第 3～5 轮），Miyu 5.7k 个输入 token 里只命中约 2.8k，jcode 9.3k 里命中约 9.0k；说明 Miyu 每次请求固定带的那部分，约 2.8k 之后有东西每段对话都不一样（是什么没查），后面整段跟着不命中。这关系到花的钱和首字延迟，不是本机 CPU；用量记录留给主会话看（见下面「用量记录」），要不要排步子由那边定。
3. **长会话里记忆抽取的请求**：造长会话那一场 Miyu 56 次请求、jcode 50 次，多的 6 次是记忆抽取（核心日志里 6 次 `memory extraction started`），这几次几乎不命中缓存；这一场没命中缓存的输入 Miyu 17.8 万对 jcode 11.4 万 token。这是功能，不是浪费；记一笔，量 token 时分开看。

### 风险

- 这一次比上次挤（12–15 号核被别的程序占满）：时间、CPU 毫秒两家都受影响，jcode 那一列就是对照。Miyu 的时间、CPU 降得比 jcode 的抖动大的才当真；长会话那一场的时间、CPU 不下结论。
- 指令数是补量的，只量了「后台先起来、开界面到首屏、关掉」这一种，和 V-30～V-33 量的「终端冷启动拉起核心」不是同一个流程，不能直接比那几步的数。
