## 施工单 V-25 下：目录不常驻

状态：已完成。2026-10-30 项目主人定模型资料「匹配一次就存下来，以后只读存下的」；核心主会话同天定了硬要求（对外逐字一样、记下的有上限、坏了当没有、版本键带全、起来时对上不读整份目录、补算不进 `observed` 的锁、后台换新重算）。接着 V-25 上（`V-25上-模型资料查表.md`）的查表接口。

### 目的

核心常驻整份 models.dev 目录（约 3.3 MB），可一个核心真问到的只有配置里那几家、那几个模型。用到的输入第一次照整份目录查一次，答（`Recalled`）存进 `state/models/catalog.json`，以后每一轮、核心重启都只照记下的；整份目录平时不进内存，只在没记过的输入、要整份目录的地方、后台拉到新目录时临时读、用完放。对外一个字节都不变。

### 查下来的

- 每一轮读目录的只有 V-25 上切出来的两处（认供应商、对模型），都经 `Knowledge.lookup`；要整份目录的是 `model.list`（列那一家目录里的全部模型、`family`、显示名）、`onboard::listed`（`provider.detect`、`provider.catalog`、常用的几家）、`provider.test` 照目录列模型和挑模型（`released`）、图标。
- `ModelData::with` 的调用点（路由、回合开始、池、配置检查、`session.configure`、拉列表、向量）都是同步的、在 tokio 的线程上，闭包都是纯的查资料。
- 现成的目录指纹（`models/digest.rs` 的 `fingerprint`）带了哪一份、原文大小和改动时间、`fetched`、程序的大小和改动时间；认原厂的表不在里面。
- 后台更新 304 只改 `meta` 的 `fetched`，指纹跟着变：每天一次版本对不上，下次起来读一次整份目录、重记。

### 蓝图改哪几节

- 「在哪」：`catalog/recall.rs` 一行补 `missed`、`rebuilt`；新加 `route/shared/recall.rs`、`miyu-core` 的 `models/recall.rs` 两行；`miyu-core` 的 `models.rs` 一行补起来时、后台更新、`follow_recall`。
- 「文件」：加 `state/models/catalog.json` 一行。
- 「怎么走」第二条第 2 条：加「不常驻」一款（认哪一份、起来时、临时读用完放、记不记、没记过的怎么补、对外不变）；第 3 条：200 时不常驻的怎么换、304 版本串跟着变；第 8 条：`CatalogLookup` 常驻给 `Full`、不常驻给 `Recalled`。
- 日志：`catalog loaded` 临时读的记 `DEBUG`；加 `catalog recalled`（取代那一回的 `catalog loaded`）、`catalog recall built`、`catalog recall rebuilt`、`WARN catalog recall unreadable`、`DEBUG catalog read for an input not recalled`。
- 「守着它的」：`catalog/recall/tests.rs` 补两条；加 `miyu-session` 的 `tests/catalog_recall.rs`、`miyu-core` 的 `tests/catalog_recall.rs`、`miyu-endpoint` 的 `tests/models_recall.rs` 三行。

施工时定的：

| 题 | 定的 | 为什么 |
|---|---|---|
| 没记过的输入在同步的 `with` 里怎么补 | 先只照记下的合一遍，`Recalling::missed` 立了就整遍作废；拿补算的锁再照记下的问一遍，还缺的读一次整份目录、重合、记下、写盘。读盘在调的线程上（只在头一回），不在 `observed` 的锁里；`with` 的闭包从 `FnOnce` 改成 `FnMut` | 路由在 tokio 的线程上同步问资料，改成异步要动每一个问的地方；作废重来保证「认不出」那种半截的答绝不交出去（上一步回报的坑）；配置里新写的由 `follow_recall` 先在阻塞线程里补，同步读只剩配置里没写、会话记着的 |
| 几把锁 | 补算的 `missing` → 读目录的 `slot`（弱引用：同时借的借同一份）→ 写盘的 `saving` → 记下的那份自己的锁；`observed` 里只合资料 | 只朝一个方向拿；同时遇到同一个没记过的只读一次；写盘拿着锁写最新的一份、换过版本的旧一份不写 |
| 换版本 | 记下的那份放在 `Arc<Mutex<Recalled>>` 里，换版本换整个 `Arc`；借整份目录的 `Holding` 带着读的那一刻对得上的那份 | 一次合资料前后用的是同一份目录的答，不会拼两份目录 |
| 版本串 | `fingerprint` 加 `vendors=<认原厂的表的哈希>`；哈希用标准库的 `DefaultHasher` | 程序换了指纹本来就变，算法跟着变无妨；不多加依赖 |
| 起来时要配置 | `begin` 多收起来时的配置（`Resolved`）；对上了的不看配置 | 对不上时照配置把写过的都记好再放掉整份目录 |
| 临时读回来版本不一样 | 照它重算换上（`why=changed`） | 缓存被同一台机器上别的核心换过；没有旧目录可借，重算是唯一不拼的办法。比常驻的早一点跟上新目录，写进蓝图 |
| 后台更新时版本串算不出来 | 从此常驻这一份 | 认不出记下的是哪一份就不能再照它答 |
| 临时读的日志 | `catalog loaded` 记成 `DEBUG` | 不然每次 `model.list` 都记一行 `INFO` |

### 不做什么

- 不写进 `config.toml`：记下的是派生数据。
- 不把路由改成异步问资料。
- 不清理记下的旧键：只多不少，都是配置里写过、真问过的；版本对不上时照配置重记，旧的就没了。
- 临时读、补算以后不另还堆：一阵请求过去以后核心本来就还（`settle`）；起来时、后台换新以后还一次。

### 验收

1. 单测：
   - `miyu-models` 的 `catalog/recall/tests.rs`：说不出来的立 `missed`、说得出来的不立；换了目录重算以后每个记下的输入和新目录现算逐字一样、旧的一份不动、新旧真有不同的答。
   - `miyu-session` 的 `tests/catalog_recall.rs`（读整份目录的办法注入、数次数）：记好的问配置里写过的 0 次；没记过的读一次、记下、写盘，再问不读；不记的问一次读一次、不落盘；两个线程同时问同一个没记过的只读一次；读回来的版本不一样的重算换上；后台换新以后记下的键全部按新目录重算、不另读、写盘。
   - `miyu-core` 的 `tests/catalog_recall.rs`：头一回读整份目录、记下写盘；下一回版本对上了不读整份目录（原文换成同样大小、同样改动时间的乱码、整理好的删掉，答的照旧，真读读不出来）；记下的那份坏了、写法的版本不对、认原厂的表换了、原文换了的整份重算；后台拉到新目录记下的那份换版本，下次起来照它。
2. 逐字一样：`miyu-endpoint` 的 `tests/models_recall.rs`，同一份配置和裁出来的目录，常驻、起来时记好的、什么都没记的三种各导一份逐字节比（供应商、配置过的和没写过的模型的资料、引用解析、档位，`model.list` 三种问法整份回应，`config.get` 的 `unknown_effort`/`unusable_temperature`、`config.check`、`session.configure` 的 `effort`）。
3. 原有测试全过（`miyu-models`、`miyu-session`、`miyu-endpoint`、`miyu-core`）；`cargo clippy -p miyu-models -p miyu-session -p miyu-endpoint -p miyu-core --all-targets -- -D warnings`、`cargo doc` 不报；`cargo xtask check` 全过。

### 风险

- 遇到配置里没写的输入（会话记着的旧模型），头一回在 tokio 的线程上同步读一次整份目录（有整理好的一份约 5 ms，没有的现解原文约 20 ms）。
- `model.list`、第一次接入、搜目录每问一次临时读一次整份目录：以前常驻不花这一下，现在每次多几毫秒、临时多占几 MB，答完放掉。
- 后台更新 304 也会让版本串变：下次起来读一次整份目录、照配置重记，比改前不慢。
- 缓存被同一台机器上别的核心换过：不常驻的在下一次临时读时就跟上新目录，常驻的要等自己下次后台更新——这一处对外的答换得早一点，其余逐字一样。
