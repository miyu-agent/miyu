## HT-1 供应商侧工具：内核的块、增量、收回复

状态：施工完，待 core1 审（2026-11-14）。设计 `71-供应商侧工具.md` 第三节第 1、2、3 条，第七节第一行。只有技术细节，照施工方案第一节第 1 条直接做。

### 目的

内核认得「供应商自己跑了一件工具」：驱动交得进来（一种新的块、一种新的增量），拼得成、落得了盘、读得回来，回合不因它派工具、
不等结果。这一步做完还没有哪个驱动交它（HT-4、HT-5），视图不画（HT-3），发请求时不带（HT-2）。

### 蓝图改哪几节

- `kernel/blocks.md`：六种块变七种，多 `hosted_tool`。格照先后：`call_id`、`name`、`args`、`outcome`（可以没有）、`private`
  （可以没有）；`outcome` 是 `{"text", "failed", "cut"}`，后两格是假的不写。旧版本读到它照第 7 条当不认识的块原样留着。
- `kernel/request.md`（流式累积器那几条）、`kernel/ids.md`（调用编号）：
  1. `Kind::HostedTool {name}`；`Delta::Outcome {index, text, failed}`。字照旧是参数原文；私有数据可以有，至多一份。
  2. 结果只有供应商侧工具有，一块至多一次，要在这一块收全以前；不对的是驱动的错（`DeltaError`）。
  3. 结果的字超过 64 KiB（`OUTCOME_BYTES`）的截在不超过它的最后一个字的边界上，`cut` 写真。留前面：搜到的条目、读到的正文
     都是前面要紧。
  4. 拼的时候供应商侧工具一律留下：正常说完的、被打断的、出错断了的、写到输出上限的、没收全的都留，供应商那边已经跑了。
     没收到结果的没有 `outcome`。
  5. 编号不和工具调用混着数：工具调用照旧 `call_<序号>_1` 到 `_k`（k 是这条回复里留下的工具调用数），供应商侧工具照先后接着
     排 `_k+1`、`_k+2`。混着数的话，旧版本把新块当不认识的留着，账本查「第 k 个工具调用编号是 `_k`」时后面的工具调用就对不上，
     整份日志读不进。账本的检查照这条认，欠着结果的调用（`pending`）不算它。
- `kernel/session.md`「收回复」：供应商侧工具不派、不过权限和挂接点、不发 `tool.called`、`tool.result`，不算「这条回复调了
  工具」；只有它和正文的回复照没有工具调用收尾。出错、写到上限时丢工具调用，不丢它；丢了工具调用以后它的编号照留下的
  重排（从 `_1` 起），不然账本不收。截编的下一轮只看正文，照旧。
- `kernel/events-bodies.md`、协议参考 `events.md`（中英）：`model.delta` 的 `start` 多一种 `"hosted_tool"`（同工具调用带
  `name`）；多一格 `outcome`：`{"text", "failed"?, "cut"?}`，就是会落进块里的那一份（截过的）。中途订阅补推照样带。
- `compaction.md`（本地估算）：这一块算工具名、参数、结果的字、私有数据的字节，同工具调用的算法。
- 样本：`samples/events/message.assistant.jsonl` 多一行带它的回复，`samples/transient/` 的 `model.delta` 多两行。

别的 crate 这一步只为编得过：凡是把块、增量的种类列全的地方给它一支，做法照「不认识的块」那一支（跳过、不算工具调用）。
投影（`miyu-assemble` 的 `known`）把它和不认识的块一起滤掉，请求的字节和以前一样（HT-2 接）；视图不画它（HT-3 接）；扩展
驱动线上写法不收它（HT-4 接），只在拿掉别家私有数据那一处认它；历史工具、整理会话的流照不认识的块不给。

### 不做什么

- 发请求时带回去、写成一段字、压缩时的摘要：HT-2。
- 视图的工具步骤、「供应商」标记：HT-3。
- `driver.delta` 的新写法、清单 `hosted`：HT-4。Anthropic 驱动：HT-5。
- 不加给模型看的字。

### 验收

1. `cargo test -p miyu-kernel`：
   - 块：`hosted_tool` 读写一字不差（带不带 `outcome`、`private`、`failed`、`cut` 各一份），缺格的报错。
   - 累积器：结果给了别的块、来了两次、收全以后才来的都拒；超长的截在字的边界上、带 `cut`；打断时没收全的也留、没有
     `outcome`；编号：`[供应商侧, 工具调用, 供应商侧]` 拼出 `_2`、`_1`、`_3`。
   - 账本：上面那种编号收，混着数的拒；供应商侧工具不进 `pending`（后面不用等它的 `tool.result` 回合也能结束）。
   - 会话：只有供应商侧工具和正文的回复，回合照常结束、执行器一次都没被叫去跑工具；和工具调用混在一条回复里，只派工具调用；
     出错断了的回复里它还在、工具调用不在；被打断的同样。
   - 瞬时事件：`start` 写 `hosted_tool`、带 `name`；`outcome` 那一条的样子；中途订阅补推带结果。
   - 估算：结果的字算进去。
2. 旧版本读得进：拿 `[供应商侧, 工具调用]` 的一条回复写成的日志行，把 `hosted_tool` 当不认识的块（测试里直接照 main 的
   `check_call_ids` 的规矩数一遍）也过。
3. 手搓变异 12 个左右全红（混着数、结果不截、截在字中间、打断时丢掉、进了 `pending`、算成调了工具、出错时丢掉、估算不算结果……）。
4. 门禁全过，分支三平台 CI 全绿。

### 风险

- 列全种类的地方多（驱动、视图、会话、记忆、历史工具）：编译器会一处处报，每一处照「不认识的块」那一支，别顺手做成后几步的事。
- 编号两趟数：先数留下的工具调用，再排供应商侧工具；打断时丢掉的半截工具调用不占号，数错了账本会拒，测试里钉死。

### 做下来的

- 施工单原来写「收回复不用改代码」，做的时候查出不成立：出错、写到上限时内核先照「留下 k 个工具调用」给它排了 `_k+1`，
  随后丢掉工具调用，账本要它从 `_1` 起，落盘那一刻内核自己的事件过不了账本。加了重排（`accumulate.rs` 的
  `renumber_hosted`，`settle.rs` 丢完调一次），两条会话测试守着。
- 蓝图多改了三页：`kernel/events.md`（`model.delta` 的写法表在这一页）、`kernel/history.md`（账本的报错）、`protocol.md`
  「补发」（中途订阅补推多带一条结果）。
- 测试：`miyu-kernel` 新加 21 条（块 1、累积器 7、账本 3、会话 8、瞬时事件样本 1、估算并进现成的一条）；别的 crate 各补一支。
- 手搓变异 17 个全红：混着数、不截、截到字中间、打断时丢掉、进了 `pending`、算成调了工具、出错时丢掉、不重排、估算不算
  结果、`cut` 不置真、结果来两次不拒、给正文块的结果不拒、补推不带结果、账本不查它、不写 `outcome`、推的没截、`start`
  写错种类。
