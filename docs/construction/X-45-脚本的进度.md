## 施工单 X-45：脚本的进度

状态：主会话审过（2026-10-22：标准输出、标准错误都认、不另开管道，理由成立；文档照写「写到标准错误」）。排在 X-44 之后（主会话 2026-10-22 排）。

### 目的

shorin-ac 会话移植旧 Miyu 的脚本时撞见的：下载、转码这类脚本跑得久，想一边跑一边说到哪了（「下好 3/10」），现在印出来的每一行都进结果，进度一多结果就被冲掉，交给她的字还白花钱。这一步给脚本一个只给人看的进度行。

### 蓝图改哪几节

`skills.md`「脚本」第 3 条（跑）：

1. **进度行**：一整行以 `miyu-progress: ` 开头的（前缀照字面，分大小写，后面带一个空格），不进交给她的结果。照旧边跑边推给头（`Progress::push`，头上现在就一边跑一边显示脚本的输出），所以人看得到、她看不到。别的行照旧进结果，已有的脚本不受影响。
2. **标准输出、标准错误都认**（和主会话原来说的「只认标准错误」不一样，主会话 2026-10-22 审过同意）：现在两样接在同一根管道上，照写出来的先后读（`process.rs`）。只认标准错误就要另开一根管道，两边的先后对不准了，结果里的字和现在不一样；真的结果里一行以 `miyu-progress: ` 开头的想不出来。作者文档写「写到标准错误」：标准错误不缓冲，写了马上到；Python 的标准输出接管道时整块缓冲，进度会攒到最后才出来。
3. **只管脚本工具**：她跑的命令（`shell`）照旧，什么行都进结果。
4. 截长（结果太长时留头尾）照去掉进度行以后的算；结果里报的行数、字数也是。到时被杀、退出码不是 0 的一样去掉。

别的几处（中英）：作者文档 `scripts-skills`「怎么跑」加一条进度行，带一个 Python 的例子（`print("miyu-progress: 3/10", file=sys.stderr, flush=True)`）。

### 代码放哪

- `miyu-basesystem` 的 `shell/output.rs`：一个按行滤的小东西，接在 `Capture` 前面，半行留着等下一段，读完时剩下的半行照一整行判。
- `shell/process.rs` 的 `start` 多一个开关，只有脚本工具打开；`shell` 照旧。

### 不做什么

- 不给进度另开协议、另造事件：头上本来就显示边跑边出来的字。
- 不认别的写法（JSON 的进度、百分比）：要的照这一行自己写。
- 不改结果里别的字。

### 验收

1. 先写会红的测试：
   - 按行滤：一行切在两段里、最后一行没有换行、前缀在行中间的（不算）、只差一个空格的（不算）。
   - 脚本工具（Python 的，三个平台都跑）：标准错误、标准输出写的进度行都不在结果里，别的行照写的先后在；推给头的那几段里有进度行。
   - `shell` 跑同样的命令，进度行照旧在结果里。
2. 手写变异 12 个左右。
3. `cargo xtask check` 全过；本机跑 Windows 的 clippy；碰子进程的输出，推 `step/` 过三台 CI。

### 做下来的

- `miyu-basesystem` 的 `shell/output.rs`：`Capture::new(progress_lines)`，打开的照行滤（`Line`：行首攒着最多前缀那么长，等于前缀的丢到换行，看出来不是的当场交出去）；`finished` 把读完时还攒着的开头照一整行交回去。`process::start` 多最后一格开关，只有脚本工具打开，`shell` 照旧；等完以后收尾（`wait` 里取输出时 `.finished()`）。`process.rs` 496 行、`shell.rs` 493 行，下一个往里加的要先挪一块出去。
- 主会话审时同意标准输出、标准错误都认、不另开管道；作者文档照写「写到标准错误、马上冲出去」，例子是 Python 的 `print(..., file=sys.stderr, flush=True)`。原来作者文档写的「标准输出就是交给 AI 的结果」改成两样都交、照写出来的先后（本来就是这样）。
- 看红：`Capture::new` 先放空壳（不滤），4 条单元测试里 1 条红（另 3 条守的是长行不攒着、读完时短的开头留着、命令的照旧，空壳下本来就对）；脚本工具那一条红，`shell` 那一条守着照旧绿。换上实现全绿；变异前又补了两处：一行在换行处才对不上（`miyu`）的下一行要重新看、读完时攒着的开头要进结果（脚本最后写 `mi`）。
- 手写变异 11 个，全抓住。头一遍有一个（换行处对不上不重来）`cargo fmt` 改了那一行、原文对不上没跑起来；另外补强的脚本测试期望写错了（结果末尾本来就补一个换行，该是 `mi\n`），基线是红的，靠那条测试的三个变异「红了」不算数：改对期望、基线绿了以后这四个补跑，都抓住。
- `cargo xtask check` 八项全过（头一回红在上面那条测试的期望）；本机 Windows 的 clippy 过；碰子进程的输出，推 `step/` 过三台 CI（见交接的消息）。
