## 施工单 PERF-3：发行版照体积优化，连着头的内存离开预算线

状态：核心的分会话做。perf 闸门「核心空闲、连着一个头」在 main 上 30 MB 边上来回红（47b063ba4 30.8、3cb18b346 30.2、edc85fecc 30.7、3642eca19 红），一大半的 CI 红在它上面。主会话派（2026-10-27）：预算不动（项目主人 10-19 定，超了就优化）；先量涨在哪，照 CPU 分开比，能二分就二分，没有台阶就找最大的几块常驻省；方案主会话过了再动。

### 查下来的

1. **没有台阶**：拉 main 最近 600 次 CI，262 份 `perf-raw`（10-20 以前的没留），照 `machine.cpu` 分开比，四种机器一样：连着头的 PSS 一周从 26.3 慢慢涨到 29.5 MB（EPYC 7763：10-20 26.4、10-23 27.4、10-26 28.6、10-27 29.5），10-26 那天涨得最多（约 1 MB），同期程序 43.5 → 49.3 MB。拆开：空闲的文件页多了约 2 MB，连着头多出来的匿名多了约 1 MB。30.8 那几趟是在这条线上抖了 1～2 MB。
2. **本机拆开**（main 001a4fa45 的 release，本机连着头 28.5～29.0 MB，和 CI 一样）。照 `smaps` 分映射：

   | 映射 | 连着头 | 空闲 |
   |---|---|---|
   | 程序的代码段 | 17.3 | 14.2 |
   | 匿名（线程的分配区） | 5.3 | 4.1 |
   | 程序的只读那一段 | 3.7 | 3.7 |
   | 主堆 | 1.8 | 1.8 |

   读 `/proc/<进程>/pagemap` 对回段：`.text` 16.8 MB、`.rodata` 1.5、`.rela.dyn` 1.1（PIE 起来时整张读一遍）、`.data.rel.ro` 0.86（重定位改写成脏页）。代码段 32.7 MB 空闲就碰了一半，按 crate 分很散（画 mermaid 的库空闲时也算进 0.27 MB）：缺页时内核顺带映射前后 64 KiB（`fault_around_bytes` 65536），零散的代码一片片算进 PSS。代码越长、越散，碰到的越多。
3. **两个实验**（同一个沙盒，起核心、像头那样问六样、歇四秒、量，各 3 次的中位）：
   - A 重定位打包（`-Wl,-z,pack-relative-relocs`）：`.rela.dyn` 1.1 MB → 20 KB，连着头 29.0 → 28.1 MB。
   - B release 照体积优化（`opt-level = "s"`）：`.text` 32.7 → 21.0 MB，程序 49.4 → 35.3 MB，连着头 29.0 → 26.2 MB。

### 做了什么（方案 B）

- `Cargo.toml` 的 `[profile.release]` 加 `opt-level = "s"`，注释写前后。`perf.md` 闸门第 7 条记来历。
- 只改 release：日常的门禁编 dev，不受影响；改了 release 的配置，大家的 release 产物要全量重编一次（合之前说一声）。

### 吃 CPU 的路（主会话要的补量）

量尺量的几样不吃 CPU，另照协议打到核心上，两个程序轮流起核心各 15 轮（大会话 10250 条事件、日志 9.7 MB，回合库约 2000 轮）。核心里没有 o200k：数 token 照大会话的上下文明细（`session.context`）量。

| 路 | 改之前 p50 / p95 ms | 改之后 p50 / p95 ms | 慢了 |
|---|---|---|---|
| 载入大会话日志（重启后头一次 `session.context`，15 次） | 23.57 / 28.06 | 26.55 / 30.19 | 13% |
| 数 token（大会话的 `session.context`，150 次） | 2.16 / 6.74 | 2.28 / 7.31 | 6% |
| 召回打分（`memory.turns`，450 次） | 0.35 / 5.54 | 0.36 / 6.10 | 1% |
| 画 mermaid（一张 13 个点、一个子图，每次换字避开缓存，150 次） | 60.21 / 64.76 | 66.36 / 70.67 | 10% |

都不到两成，没有哪个 crate 要单独留在 `opt-level = 3`（`[profile.release.package.<crate>]`）。

### 看过、不做的

- A 重定位打包：再省约 0.9 MB，可程序要 glibc 2.36 以上（`GLIBC_ABI_DT_RELR`），Ubuntu 22.04 是 2.35，直接起不来。发行目标还没定（重制版还没发过版），定了再看。
- 非 PIE：再省约 2 MB（重定位表和改写的那一段都没了），主程序没了 ASLR，不做。
- 符号排序、BOLT：把起来时碰的代码排在一起，要打点、要维护，不做。
- `madvise` 一类让量出来好看的办法：不做。

### 以后的候选（不在这一步）

- 画 mermaid 连同 `image`、`zune_jpeg`、`image_webp` 挪出核心进程：约 2.5 MB 冷代码。
- 匿名里最大的一块（约 3 MB）是活着的数据，要 heaptrack 一类的工具才看得清是谁（本机没装）。

### 验收

1. 量法、表在上面；本机 `cargo xtask check` 全过。
2. CI 的 perf 那一项真绿了才算数：分支那一趟（run 40542092098，EPYC 7763）连着头 25.6 MB、空闲 22.8 MB，程序 35.4 MB；改之前同一种机器上连着头 29.5 MB 上下。
