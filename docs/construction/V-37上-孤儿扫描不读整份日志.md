## 施工单 V-37 上：孤儿扫描不读整份日志

状态：已完成。2026-11-02 核心主会话照 V-37 的设计（第二项、第五项第 1、2 条）派下来；设计里的问题 3（顺手堵「刚造好、还没记下 `job.started` 的子会话被当成空子会话收掉」那条缝）这一步不做，行为照旧。

### 目的

每载入一个会话，后台收派到一半的空子会话（`agents.md` 第一条第 8 条）时都要把父会话的整份日志再读一遍、解一遍，只为攒三个小集合；绝大多数会话根本没有没派成的调用，这一遍是白读。大会话（四万条、20 MB 的日志）载入那一刻，这一路就是近 70 MB 的堆。改成载入读日志时一条条顺手记下交回，收的时候不再读父会话的日志。顺带两样常驻：有效历史压缩以后容量跟着缩；派生库开库跑完 `quick_check` 放掉为它读进来的页。行为不变。

### 查下来的

- 原来：`miyu-endpoint` 的 `sessions/found.rs` 载入以后 `orphans::sweep_later`，`orphans()` 第一行无条件 `read_events(父会话)`，攒派子代理的调用、结果里带着子会话的 `job.started` 的调用、那些子会话；调用都在后者里的什么都不做，否则列会话表、读每个会话的第一条认。载入本来就一条条看过每一条（施工 V-15 的 `Scan`）。
- 量（本机，release 核心，见下面「实测」的量法）：改前载入那一刻 heaptrack 峰值 141.7 MB，按分配点分：回合索引接上时整份读 42.1、孤儿扫描整份读 41.9、解析线程里的事件正文 54.1（三家读者合在一起，分不开）、有效历史 1.05、别的不到 3 MB。孤儿扫描一家连正文约 68 MB，和设计算的一样。
- 有效历史压缩以后还剩多少条：四万条的大会话载入以后有效历史 1,837 条（容量 2,048 条，一条 `Event` 512 字节，1.05 MB）；手动压缩一次（`session.compact`）以后剩 525 条，容量还是 2,048 条。模板会话里两次自动压缩以后剩 23、30 条（工具结果大，尾巴装得少）。
- 回合库：开库时跑一次 `quick_check` 会把整个库读进这条连接的页缓存（默认上限 2 MB），之后一直占着：三 MB 的回合库量到 2.29 MB；会话索引、用量汇总两份合计 0.78 MB。

### 选的办法

1. 孤儿扫描（设计第二项）：`miyu-session` 的 `open/scan.rs` 加 `Dispatched`，`Scan::note` 每条顺手记那三个集合（认法照抄原来的：`is_subagent` 两个名字都算，只认带子会话的 `job.started`）；只记自己的日志，分叉出来的底子不进来（原来也只读自己的目录）。`load_placed` 交回 `(Handle, Placed)`：`Placed { environment, recorded }`，`recorded` 是 `None`（派子代理的调用都记下了，不用认）或 `Some(记下了的子会话)`。`found.rs` 拿到 `None` 不起这一趟；`Some` 的照原来列会话表、读第一条、收，`orphans()` 不再读父会话的日志。
2. 有效历史压缩以后缩容（设计第五项第 1 条）：`History::append` 遇到压缩、`settle` 落到检查点上以后，一半以上空着、空着的不止 256 条（128 KB）的，缩到条数的一倍半（`fit`）。
3. 派生库（`miyu-store` 的 `sqlite.rs::connect`，回合库、检索库、会话索引、用量汇总共用）跑完 `quick_check` 以后 `PRAGMA shrink_memory`：只放掉这条连接的页缓存，之后用到再从系统的页缓存读回，结果不变；放不掉只是多占内存，不算库坏了。

### 「更早，不更晚」

认的依据原来是后台线程读完日志那一刻（载入后几毫秒到一百多毫秒），现在是载入读完日志那一刻：更早，不更晚。差别只在要认的时候（有没派成的调用）、而且只在一条原来就有的窄缝里：载入以后才派出去的子会话，正赶上这一趟列会话表的，会被当成空子会话收掉——原来是派出去以后还没记下 `job.started` 就赶上的才会，现在是载入以后记下的 `job.started` 都不算。要碰上，得是载入以后、这一趟认完以前（列会话表、读每个的第一条，毫秒级）这个会话就派出了子代理。设计的问题 3 就是堵这条缝，这一步不做。

### 和设计不一样的地方

- 设计照 `7503cd5b3` 写；之后 HV-1、R3E-2 等碰过的 `open/load.rs` 只多了一个 `jobs_dir` 字段，`sessions/`、`open/scan.rs` 没动，设计的读法照样成立。
- 设计写「交回多一格 `orphans: Option<BTreeSet<SessionId>>`」：这一格装的是记下了的子会话，不是孤儿，改叫 `recorded`，和在哪干活合成 `Placed`；`load.rs` 到了 499 行，构造挪进 `Dispatched::placed` 一行装下。
- 设计写蓝图 `agents.md` 第一条「第 7 条」：现在是第 8 条（第 7 条是交代没送进去）。`protocol.md`「会话表」第 8 条末尾原来那句「这时表拿着锁，它不在表里，也就派不出新的，认不错」从 V-2 三补挪到后台以后就不对了，这一步换成照实的「更早，不更晚」。
- 有效历史缩容的门槛：设计写「`len × 4 < capacity` 且容量过 1024 条，缩到两倍」。量下来手动压缩以后 525 / 2,048 条（25.6%），设计的条件刚好不中；改成「一半以上空着、空着的不止 256 条，缩到一倍半」，往后长先用留着的那一半。
- 设计说「`real.rs` 那几份真会话上逐个相等」：`miyu-store` 的 `real.rs` 是内核替身跑的一段会话，没有派子代理；换成照种子造的三千份日志（单元测试）加真会话的七种情形（集成测试）。
- 设计里「目录里的日志被删了也不报、不收（证明没读）」这条测试没写：`orphans()` 现在拿不到父会话的日志（参数里只有记下了的子会话），载入以后到起这一趟之间也插不进删日志的那一下，写出来是测时序；由「`None` 不起这一趟」和对照测试守。

### 不做什么

- 不堵设计问题 3 那条缝（只认载入以前造的子会话）：是行为变化，另记。
- 不碰日志读法（V-37 中，另一个帮手在做 `miyu-store` 的 `log/open`）、回合索引接上时的整份读和补发（V-37 下）。

### 验收

1. 对照测试：`miyu-session` 的 `open/scan/tests/dispatched.rs` 把原来的认法照抄一份当准绳，照种子造三千份日志（派子代理的两个名字和别的调用混着，一次回复调零到三次；结果对得上的、对不上的、还没有结果的；`job.started` 带子会话、不带子会话的后台命令、fork 出来的），一条一块、两条、七条、整份喂进 `Scan`，交回的和准绳逐个相等，「不用认」「要认、一个都没记下」「要认、记下了几个」三种各碰到五十份以上；`tests/spawn/recorded.rs` 真会话七种情形（没派过、派成了、派不成、两个只派成一个、没记下结果就崩了、改名以前的 `agent` 派成和派不成），载入交回的和载入以后照原来的认法读整份日志认的一模一样。
2. `miyu-endpoint` 的 `tests/orphans.rs` 原有四个（崩在 `job.started` 前收掉、改名以前的照样收、记下了的照留、两个只收没记下的）照旧过。
3. `history/tests/fit.rs`：压缩以后内容、先后不变，空着一大半的缩、空着的不多的不动、留着一切的那一份落到检查点上一样缩；`history` 其余测试照过。`sqlite/tests.rs`：有东西的库查过、放掉页以后读得回来、写得进。
4. `cargo xtask check`、Windows 版 clippy、三平台 CI。

### 实测

2026-11-02，本机，release 核心（改前 `5628a2667`，改后这一步），同一份数据根：照 V-38 的模板会话截成短回合、重排序号合成的大会话，40,061 条、21.1 MB，2,860 轮，每 150 轮自动压缩一次，开着记忆（无人格，回合库预先接好、3.0 MB）。核心在 `unshare -rn` 里起来，假模型在私有回环上，起来安静 3 秒，像头那样发 `session.context` 触发载入，采样 10 秒；再发 `session.compact` 手动压缩，等 5 秒。heaptrack 只用 `--record-only`，最后直接杀掉核心，杀的那一刻还活着的就是常驻。

### 风险

- 「更早，不更晚」那条窄缝（上面一节）：只在有没派成的调用的会话、载入以后毫秒级的窗口里派出子代理时才碰得到，原来就有，宽窄差不多；设计问题 3 另记。
- `Placed` 是 `miyu-session` 对外的类型：`load_placed` 的调用方只有会话表一处，测试的帮手跟着改了。
- 缩容只在压缩、落到检查点时做，是很少的事，一次拷几百条；一半以上空着才缩，往后再长不会马上又要搬。
