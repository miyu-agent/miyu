## 施工单 X-44：脚本的状态目录

状态：主会话审过（2026-10-22：家目录里删了的脚本旧状态留着，同卸了的包家目录留着一个口径，`miyu check` 报一条，人自己删；补的写进下面）。排在 X-43 之后（主会话 2026-10-22 排，只做持久的状态目录这一样；原来一起提的「脚本在退回的工作区里跑、交 `MIYU_WORKSPACE_DIR`、`MIYU_CWD`」项目主人否了，改成有 bwrap 时家目录不算太宽、照样可写，改 5-14，由核心那边做，不在这一步）。

### 目的

shorin-ac 会话移植旧 Miyu 的脚本时撞见的：B 站直播、网盘这类脚本要记登录态（cookie、令牌），现在只有缓存目录 `MIYU_SCRIPT_CACHE_DIR`，在系统的临时目录下，重启、清临时文件就没了，而且全机、全账号共用一份。这一步给脚本一个持久的、按账号分开的状态目录。

按账号分开顺带堵上 X-43 那件事的根：群聊、陌生人私聊的会话归包的系统账号（`venues.md`），和管理员自己的会话不是一个账号，登录态各是各的，群里调到的脚本拿不到主人的登录态。

### 蓝图改哪几节

`skills.md`「脚本」第 3 条（跑）：

1. **`MIYU_SCRIPT_STATE_DIR`**：`<数据根>/state/scripts/<会话属主账号>/<来处>/<工具名>/` 的真实位置。来处是包带的照包的编号，管理员家目录里放的是 `~home`（同登记时挂的那一个，`miyu_store::scripts::HOME_PACKAGE`）。跑之前建好（Unix 上 `0700`，一路缺的上级一起建）；建不成的这一次不给这个环境变量、照常跑，运行日志记一行 `WARN script state not prepared`（同交图的目录建不成）。会话外面的调用（没有属主的）不给。
2. **沙盒**：照常藏着数据根，这个目录放进规格的 `write`（「能写的落在藏起来的里面，照样能写」，`sandbox.md`，工作区就是这样）。只放这一个脚本自己的那一格：别的脚本的、她跑的命令都碰不到。管理员放行出沙盒的（`sandbox.tools.<名字>`）照样建、照样给。
3. **清**：
   - 卸包（`packages.md`「怎么走」第 7 条「卸就是清干净」）：连同 `state/packages/<编号>/` 一起删每个账号下的 `state/scripts/*/<编号>/`。家目录里的脚本删了的不清（放回来接着用）。
   - `miyu check` 报留下的（主会话审时加）：`state/scripts/<账号>/<来处>/<工具名>/` 在、这一刻登记上的脚本里没有这个来处的这个工具名的（家目录里删了、改了名的，包升级以后不带它了的），一条警告 `script_state_left`，带这个目录的路径，人自己删。
   - 删账号：现在还没有删账号这件事，有了以后随它清 `state/scripts/<账号>/`。
4. 缓存目录 `MIYU_SCRIPT_CACHE_DIR` 照旧：能丢的放那里，要留的放状态目录。

为什么放 `state/` 下面：包的状态目录（`state/packages/<编号>/`，施工 F-15）、MCP 服务的工作目录（`state/mcp/<服务名>/`，施工 X-3 下）已经放在那里，卸包照同一处清；`07-存储.md` 第二节写 `state/` 是「派生」的那一句跟着补一句「也放包、MCP 服务、脚本自己的状态」。

别的几处（中英）：作者文档 `scripts-skills`「怎么跑」加一条 `MIYU_SCRIPT_STATE_DIR`（例子：登录态写在这里，缓存目录会被清）。

### 代码放哪

- `miyu-store`：`DataRoot` 加一个 `script_state(account, source, tool)` 拼路径（纯的）；卸包那一处照 `state/scripts/*/<编号>/` 删。
- `miyu-basesystem` 的 `shell/script.rs`：脚本工具记下自己的来处（`Builtins::script` 多一个参数），跑之前照 `call.ids` 的属主、`call.data_root` 建目录、交环境变量、放进沙盒规格的 `write`。

### 不做什么

- 不给 shell 跑的命令这个目录：只给脚本工具。
- 不做按会话、按场所分的目录：按账号就够分开主人和群里；要再细的脚本自己在里面按 `MIYU_CALLER_VENUE` 分。
- 不管目录多大：同包的状态目录。

### 验收

1. 先写会红的测试：
   - `miyu-store`：路径照账号、来处、工具名拼。
   - 脚本工具：拿到的 `MIYU_SCRIPT_STATE_DIR` 是建好了的那一个，写进去的下一次调用还在；两个账号的不是同一个；没有属主的不给。
   - 沙盒里（Linux、macOS 能跑沙盒的机器上）：写得进自己的状态目录，写不进、读不到别的脚本的那一格。例外（core2 2026-10-22 说的，5-14 改以后）：Linux 上只有 Landlock（没有 bubblewrap、或者设了弱沙盒）、工作目录又包住数据根的（比如在 `~` 里开的会话），照 dsh 的做法能写的范围里不再挖洞，数据根在沙盒里不再藏着，这一条在那种机器上不成立，是预期的；有 bubblewrap 的、macOS 照旧成立。测试的工作目录不包住数据根，不为它改。
   - 真核心：卸掉带脚本的包以后 `state/scripts/<账号>/<编号>/` 没了，`~home` 的、别的包的还在。
   - `miyu check`：家目录里的脚本删了以后报 `script_state_left`、带路径；脚本还在的不报。
2. 手写变异 12 个左右。
3. `cargo xtask check` 全过；本机跑 Windows 的 clippy；碰文件系统和子进程的环境，推 `step/` 过三台 CI。

### 风险

- Windows 的沙盒还没收紧（5-9）：Windows 上照样建、照样给，沙盒规格写上，等 5-9 照它收。
- 工具名改了（文件改名）的换一格、旧的留着：同家目录里删了的脚本不清，靠人自己删。

### 做下来的

- `miyu-store` 的 `scripts.rs`：`state_root`、`state_dir`（照账号、来处、工具名拼路径），`states`（列出各账号的每一格、照路径排，不是文件夹的不算），`forget_states`（删每个账号下一个来处的，没有的不算错）。
- 脚本工具（`miyu-basesystem` 的 `shell/script.rs`）多记一格来处（`miyu_basesystem::script`、`Builtins::script` 多一个参数，登记时照 `scripts::package` 给），跑之前照 `call.ids` 的属主、`call.data_root` 建好（`DirBuilder` 一路建、Unix 上 `0700`）、取真实位置交 `MIYU_SCRIPT_STATE_DIR`，进沙盒的放进规格的 `write`；建不成的记 `WARN script state not prepared`、不给、照常跑。
- 卸包时和包的状态目录同一处删（`packages/manage.rs`）；`miyu check` 报 `script_state_left`（`check/skipped.rs`，字表中英日 `package-problems/script_state_left`），比的是来处加工具名。
- 主会话审时补的「`miyu check` 报留下的」和 core2 说的「只有 Landlock、工作目录包住数据根的机器上读得到别的脚本的那一格」都写进了验收、蓝图。
